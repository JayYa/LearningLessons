useEffect 与那个空数组

你从第 1 课起就在写 useEffect(..., [])。今天把那对方括号弄清楚 —— 顺便拆掉一个几乎人人都在传、但经不起实测的说法。

本课的收获

一句判据：Effect 是为「因为组件被显示出来」而必须发生的事准备的；由用户动作引起的事，写进事件处理函数。 做完之后，这四件事你都能讲出原因：那个 [] 到底是什么；为什么开发模式下 effect 跑了两次；为什么去掉 [] 有时会打爆后端、有时却只多发一个请求；以及最像加分题的那一问 —— 什么时候根本不该用 Effect。

一、Effect 不是「生命周期钩子」

先把最容易走偏的那条路堵死。很多教程会说「useEffect(fn, []) 就是 componentDidMount」。这个类比会在第 4 节把你坑得很惨。官方文档的定义完全不是这么说的：

“Effects let you specify side effects that are caused by rendering itself, rather than by a particular event. Sending a message in the chat is an event because it is directly caused by the user clicking a specific button. However, setting up a server connection is an Effect because it should happen no matter which interaction caused the component to appear.”
“Effects run at the end of a commit after the screen updates.” —— react.dev · Synchronizing with Effects

注意这里的分类维度：不是「什么时候跑」，而是「被什么引起」。

被什么引起写在哪
某个特定的用户动作
点了这个按钮、提交了这个表单		事件处理函数。你知道发生了什么，可以精确响应。
组件被显示出来这件事本身
不管用户是怎么走到这个页面的		Effect。它不关心是谁触发的，只关心「现在屏幕上有我，所以外部世界得跟我同步」。
找 C# 里的参照物 —— 但要找对

直觉会让你想到 WPF 的 Loaded / Unloaded，或者构造函数与 Dispose 的配对。「配对」这个直觉是对的（下面的 cleanup 就是它），但「一次性生命周期」这个直觉是错的。

更准的参照物是 event += / event -= 这对订阅动作，而且是写在一个会被反复执行的地方：每当依赖变了，React 先替你 -=（cleanup），再 +=（setup）。

所以官方用的词不是 lifecycle，是 synchronizing —— 把一个外部系统同步到你当前的 state 上。外部系统是谁？浏览器 DOM、定时器、WebSocket、你的 FastAPI 后端。

二、方括号里的三种写法

只有三种，官方文档把它们并排放在一起，请连着记：

useEffect(() => {
  // This runs after every render
});

useEffect(() => {
  // This runs only on mount (when the component appears)
}, []);

useEffect(() => {
  // This runs on mount *and also* if either a or b have changed since the last render
}, [a, b]);
—— react.dev · Synchronizing with Effects

关键在于「变了」是怎么判定的 —— 又是 Object.is，又是引用比较。这正是第 4 课末尾埋下的那颗雷，它马上要在动手环节炸给你看。

顺带说清楚一个反向的事实：没有依赖数组不等于「每次点击都跑」，而是「每次渲染之后都跑」。上次的追问里我们已经分清了这两件事 —— 点击调用的是 handler，state 真的变了才会调用组件函数、才会有渲染、才会有 effect。

三、拆掉一个流行说法

你大概率听过这句：「useEffect 里请求数据千万别忘了写 []，否则会无限循环把后端打爆。」

这句话只对了一半，而且错的那一半更值钱。我用你这套代码的等价版本实跑了一遍，数的是 fetch 被调用了几次：

effect 怎么写StrictMode请求次数
[] 依赖数组关1
[] 依赖数组开2
无依赖数组，setMessage(字符串)关2 ← 不是无限
无依赖数组，setMessage(字符串)开3 ← 还是不是无限
无依赖数组，setData(对象)关失控（设了 300 次上限，撞满）

实测环境：React 19.2.8 + react-dom 19.2.8，jsdom。你在第 2、3 步会在真浏览器 + 真 FastAPI 上复现出同样的数字。

为什么？把第 4 课那条脚注请出来

无依赖数组时，链条是：渲染 → effect → setState → 渲染 → effect → … 要让它停下来，只需其中一环断掉。而断点就在 setState：

“If you update a state variable to the same value as the current state, as determined by an Object.is comparison, React will skip re-rendering the component.” —— react.dev · useState · Caveats

后端每次都返回同一个字符串 "Hello from Python"。第二次 setMessage("Hello from Python") 时，Object.is 判定与当前 state 相同 → 跳过重渲染 → 没有新渲染 → 没有新 effect → 链条自己断了。

但如果你存的是对象 —— setData(result.data) —— 每次 await res.json() 都产出一个全新的对象。内容一模一样，Object.is 却永远判 false（比的是引用，不是内容）。链条永不断裂，后端被打爆。

所以真正的规则不是「别忘了写 []」，而是「JS 里 {} !== {}」。这一条会在 React 里咬你至少三次：依赖数组、useEffect 无限循环、state 的不可变更新。

四、为什么开发模式下跑了两次

你现在的代码写着 []，理论上「只在挂载时跑一次」。但去看 FastAPI 那个终端 —— 两条请求日志。这不是 bug：

“In development, React remounts every component once immediately after its initial mount.”
“When Strict Mode is on, React remounts each component once in development to verify that you've implemented cleanup well.” —— react.dev · Synchronizing with Effects

它是故意的，而且是一个测试。React 在替你检查：你的 effect 经得起「装上 → 拆掉 → 再装上」吗？这就是为什么 main.tsx 里包着 <StrictMode>，也是为什么它只在开发模式生效，生产构建不会双跑。

于是所有人第一反应都是去问「怎么让它只跑一次」。官方文档罕见地直接把这个问题判为无效：

“The right question isn't “how to run an Effect once”, but “how to fix my Effect so that it works after remounting”.”
“Usually, the answer is to implement the cleanup function. … The rule of thumb is that the user shouldn't be able to distinguish between the Effect running once (as in production) and a setup → cleanup → setup sequence (as you'd see in development).” —— react.dev · Synchronizing with Effects

cleanup 就是你 return 出去的那个函数：

“React will call your cleanup function each time before the Effect runs again, and one final time when the component unmounts.”
“‘connect’ needs ‘disconnect’, ‘subscribe’ needs ‘unsubscribe’, and ‘fetch’ needs either ‘cancel’ or ‘ignore’.” —— react.dev · Synchronizing with Effects

请求已经发出去了，收不回来 —— 所以 fetch 的 cleanup 走「ignore」这条路：把过期那次请求的结果丢掉。

useEffect(() => {
  let ignore = false;                      // ← 这个闭包属于「这一次」effect

  fetchHello().then((result) => {
    if (ignore) return;                    // ← 我已经过期了，闭嘴
    /* …setState… */
  });

  return () => { ignore = true; };         // ← cleanup：把上一次标记为过期
}, []);

看懂这段的关键，正是第 4 课那句话：每次渲染产生全新一批闭包。每一次 effect 都有它自己的 ignore。cleanup 关掉的永远是上一次那个，不会误伤新的那次。这不是新知识，是快照模型的又一个推论。

这才是 cleanup 真正解决的问题：竞态

StrictMode 的双跑只是让你提前发现问题。真正的杀伤场景是这个：

“If the userId changes from 'Alice' to 'Bob', cleanup ensures that the 'Alice' response is ignored even if it arrives after 'Bob'.” —— react.dev · Synchronizing with Effects

用户快速点了 Alice、又点 Bob。两个请求在飞，谁先回来是不保证的。如果 Alice 慢一步回来，屏幕上写着 Bob 的名字、显示着 Alice 的数据 —— 而且不报错、不复现、测试也测不出。这就是 race condition，是手写 useEffect 请求数据最经典的生产事故。
面试价值极高：能主动说出这个场景的人，明显比只会背「useEffect 用来发请求」的人多一层。

五、动手

两个终端开着（fastapi dev 与 pnpm dev）。这一课你要一直盯着 FastAPI 那个终端 —— 它的访问日志就是本课的测量仪器。全程只改 App.tsx。

  1. 先建立基线：数一数它请求了几次

    代码一行不改。把 FastAPI 终端清空（cls），然后刷新浏览器。

    INFO:  127.0.0.1:xxxxx - "GET /api/hello HTTP/1.1" 200 OK
INFO:  127.0.0.1:xxxxx - "GET /api/hello HTTP/1.1" 200 OK

    两条。你写着 []，它却跑了两次 —— 这就是 StrictMode 在替你做那个「拆了再装」的测试。

    去 main.tsx 看一眼，那个 <StrictMode> 是 Vite 模板默认包上的。别删它，删掉只是把问题藏起来。

  2. 删掉 [] —— 先预测，再看

    把 useEffect(..., []); 结尾的 , [] 删掉，变成 useEffect(() => { ... });。保存前先回答：

    先预测 · 别偷看

    删掉依赖数组后刷新页面，FastAPI 终端里会出现几条请求日志？

    3 条，然后停下来。不是无限循环。
    如果你预测的是「无限」—— 你答的是网上流传最广的那个版本，而它不准确。原因在第三节：后端每次返回同一个字符串，Object.is 判定 state 没变，React 跳过重渲染，链条自己断了。
    （[] 时是 2 次，去掉后是 3 次 —— 多出来的那一次，就是「effect 引起的那轮额外渲染」。）

    保存，刷新，数日志。数完先别改回去，下一步还要用。

  3. 同样是没有 []，这次真的打爆它

    依赖数组仍然不要。只把存字符串改成存整个对象：

    const [data, setData] = useState<{ message: string } | null>(null);

useEffect(() => {
  fetchHello().then((result) => {
    if (result.success) setData(result.data);     // ← 每次都是一个新对象
  });
});                                               // ← 依然没有依赖数组

// h1 改成：
<h1>{data?.message ?? "加载中…"}</h1>

    保存。盯着 FastAPI 终端。日志开始瀑布式滚动，停不下来。

    看够十秒就把浏览器标签页关掉（这是最快的止血方式），然后把这一步的改动撤销，, [] 也加回去，确认日志恢复正常。

    同一个「没有依赖数组」，第 2 步温和、第 3 步失控。差别只有一个：Object.is 比的是引用。后端返回的 JSON 内容完全一样，但 await res.json() 每次都造一个新对象 —— 内容相同，引用不同，React 认定「变了」，于是永远转下去。

    这一步是本课最值钱的十秒钟。真实项目里把后端打爆的，几乎都是这个形状。

  4. 让 lint 说话 —— 注意它的语气

    回到有 [] 的版本，制造一个「依赖漏了」的情形。加个 state 并在 effect 里读它：

    const [suffix] = useState("!");

useEffect(() => {
  fetchHello().then((result) => {
    if (result.success) setMessage(result.data.message + suffix);   // ← 读了 suffix
  });
}, []);                                                             // ← 却没申报

    跑 pnpm lint：

    warning react-hooks(exhaustive-deps): React Hook useEffect has
missing dependencies: 'suffix' help: Either include it or remove
the dependency array.

    请注意那个词是 warning，不是 error。命令照样退出 0，CI 不会拦你。回想第 4 课：把 hook 写进 if 是 error。

    这个差别是有意的，也是很好的面试谈资：Rules of Hooks 是纪律（违反必错），exhaustive-deps 是建议（违反通常错，但存在合理例外）。看完把 suffix 删掉。

  5. 写一次 cleanup，亲眼看到 setup → cleanup → setup

    把 effect 改成带 cleanup 的完整形态，并加三行 console.log：

    useEffect(() => {
  let ignore = false;
  console.log("① setup");

  fetchHello().then((result) => {
    if (ignore) { console.log("③ 结果被丢弃"); return; }
    if (result.success) setMessage(result.data.message);
    else setMessage("数据格式不对：" + z.prettifyError(result.error));
  });

  return () => { ignore = true; console.log("② cleanup"); };
}, []);

    刷新，看 Console。顺序是 ① setup → ② cleanup → ① setup，中间还夹着一条 ③ 结果被丢弃。

    这就是 StrictMode 那个测试的全过程 —— 而你通过了：第一次那个请求的结果被正确地丢掉了，界面上只反映最后一次。

    把 console.log 删掉，ignore 那套留着。它现在是这段代码的正确写法，不是练习。

  6. 最后一步：删掉一个不该存在的 Effect

    假设要显示「消息有多少个字」。先按错误的方式写 —— 这是新手最常见的 Effect 误用：

    const [length, setLength] = useState(0);
useEffect(() => { setLength(message.length); }, [message]);   // ← 多余的一轮渲染

    它能跑，但每次 message 变化都要多渲染一轮：渲染 → 提交到 DOM → 跑 effect → setState → 再渲染一轮。用户会看到一瞬间的旧长度。

    现在把上面两行全部删掉，换成一行：

    const length = message.length;   // 就这样。不需要 state，不需要 Effect。

    它自动就是对的 —— 因为组件函数在 message 变化时本来就会被重新调用（第 4 课）。能在渲染中算出来的东西，不要放进 state。

    收尾：pnpm lint 与 pnpm build 都应零错误，页面显示 Hello from Python + 能加 3 的按钮，刷新时 FastAPI 恰好两条日志。

    你现在拥有的

    你亲手让后端被打爆过一次，也亲手让它停下来过。你知道那两次的区别不在 useEffect，而在 Object.is。这个区别，网上大多数教 useEffect 的文章都没说对。

六、你可能根本不需要 Effect

第 6 步不是收尾彩蛋，它指向 React 官方文档里少见的一整篇反模式指南。开篇就点名两种情况：

“You don't need Effects to transform data for rendering. … If your Effect also immediately updates the state, this restarts the whole process from scratch!”
“You don't need Effects to handle user events. … By the time an Effect runs, you don't know what the user did (for example, which button was clicked).” —— react.dev · You Might Not Need an Effect

第二条那句理由特别漂亮，值得背下来：Effect 跑起来的时候，「是谁触发的」这个信息已经丢了。它只知道「渲染完成了」。所以凡是需要知道「用户干了什么」的逻辑，写在 Effect 里天然就是残缺的。

整篇文章可以压成一条判据：

“When you're not sure whether some code should be in an Effect or in an event handler, ask yourself why this code needs to run. Use Effects only for code that should run because the component was displayed to the user.” —— react.dev · You Might Not Need an Effect

问「为什么要跑」，不是问「什么时候跑」。答案是「因为组件被显示出来了」→ Effect；答案是「因为用户点了那个按钮」→ 事件处理函数。

七、检验一下

测验 1 / 5

删掉依赖数组后，effect 里 setMessage("同一个字符串")，结果是：

实测：[] 时 2 次，删掉后 3 次，然后停。
因为 Object.is 判定新旧 state 相同时，React 跳过重渲染 —— 没有渲染就没有下一次 effect，链条断了。
「忘了写 [] 就会无限循环」是个流传很广但不准确的说法。真正的变量是你 setState 传的是不是一个新引用。

测验 2 / 5

同样删掉依赖数组，改成 setData(result.data) 就失控了，因为：

await res.json() 每次都产出一个全新的对象。内容一模一样，但 Object.is 比的是引用，永远判 false → 每次都重渲染 → 每次都跑 effect → 死循环。
「React 会深度比较」是个危险的误解：React 从不深比较，依赖数组、Object.is、memo 全都是浅比较。记住 {} !== {}，你会少踩很多坑。

测验 3 / 5

开发模式下 effect 跑了两次。正确的应对是：

官方原话：“The right question isn't ‘how to run an Effect once’, but ‘how to fix my Effect so that it works after remounting’.”
双跑是 React 故意安排的一次测试，检查你的 cleanup 写没写对。删掉 StrictMode 或加 ref 标记位都只是把体温计摔了 —— 真正的 bug（竞态）在生产环境照样发生，只是更难复现。
最后一个选项本身就是错的：写了 [] 在开发模式下依然跑两次，你第 1 步已经亲眼见过。

测验 4 / 5

fetch 的 cleanup 里那个 let ignore = false 之所以有效，是因为：

这是第 4 课快照模型的直接推论：每次渲染产生全新一批闭包。第 N 次 effect 的 ignore 和第 N+1 次的是两个不同的变量，所以 cleanup 只会让过期的那一次闭嘴，不会误伤新的。
最后一个选项是常见混淆：ignore 并不取消请求，请求照发照回，只是结果被丢弃。想真的取消得用 AbortController。官方说的是 “fetch needs either cancel or ignore” —— 两条路。

测验 5 / 5

判断一段逻辑该不该写进 Effect，标准是：

判据是「为什么要跑」，不是「什么时候跑」。因为组件被显示出来 → Effect；因为用户点了某个按钮 → 事件处理函数。
官方给的理由很硬：Effect 跑起来时，「是谁触发的」这个信息已经丢了 —— 它不知道用户点的是哪个按钮。
其余选项描述的都是 Effect 的表现（跑在渲染之后、涉及外部系统）。把表现当判据，就会写出那种「用 Effect 把 A 同步到 B」的多余代码。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒：
（1）「忘了写 [] 就会无限循环」这句话哪里不准确？用你第 2、3 步数出来的数字讲；
（2）StrictMode 为什么要跑两次，它在替你测什么？
（3）第 4 课的「快照」怎么解释 ignore 那个变量能生效？

(1) 无依赖数组时链条是「渲染 → effect → setState → 渲染」。能不能停，取决于 setState 那一环断不断得掉。传字符串且内容相同时，Object.is 判相等，React 跳过重渲染 → 停（实测 3 次）。传对象时每次都是新引用，永远判不等 → 失控。真正的规则是「引用比较」，不是「别忘了写方括号」。

(2) 开发模式下 React 故意把每个组件挂载后立刻重挂载一次，用来检验 cleanup 写对了没有 —— 判据是「用户不应该能区分『跑一次』和『setup → cleanup → setup』」。生产构建不会双跑。正确应对是补 cleanup，不是删 StrictMode。

(3) 每次渲染都产生全新一批闭包，所以第 N 次 effect 里的 ignore 是它专属的变量。cleanup 把它置为 true，只会让第 N 次那个尚未返回的请求闭嘴，不影响第 N+1 次。
这就是为什么第 4 课必须先学：本课一半的内容是它的推论。

八、面试回答模板

如果面试官问：“useEffect 是干什么的？” / “依赖数组有什么用？”

“useEffect 是用来把外部系统同步到当前 state 的，不是生命周期钩子。判据是问『这段代码为什么要跑』—— 因为组件被显示出来了，就用 Effect；因为用户点了某个按钮，就写进事件处理函数。Effect 跑的时候已经不知道用户干了什么了，所以事件逻辑放进去天然是残缺的。
依赖数组三种形态：不写 = 每次渲染后都跑；[] = 只在挂载时；[a, b] = 挂载时 + a 或 b 变化时。比较用的是 Object.is，浅比较。
我自己实测过一件事：大家都说『忘了写 [] 会无限循环』，这不准确。如果 effect 里 set 的是同一个字符串，Object.is 判相等，React 跳过重渲染，多发一个请求就停了；但如果 set 的是 await res.json() 出来的对象，每次都是新引用，才会真的把后端打爆。根因是引用比较，不是方括号。
还有 cleanup。开发模式下 StrictMode 会故意让 effect 跑两次，目的是测你 cleanup 写没写对 —— 正确做法是补 cleanup，不是去掉 StrictMode。fetch 的 cleanup 用一个 ignore 标记丢弃过期结果，它能生效是因为每次渲染都有自己的闭包。真正要防的不是双跑，是竞态：用户先点 Alice 再点 Bob，如果 Alice 的响应后到，屏幕上就会是 Bob 的标题配 Alice 的数据。”

两个分水岭句子：「根因是引用比较，不是方括号」和「真正要防的是竞态」。前者证明你实际调试过，后者证明你想过生产环境。背文档的人给不出这两句。

九、去读原始资料

本课首选阅读：react.dev · Synchronizing with Effects（约 15 分钟）。请特别读 How to handle the Effect firing twice in development 那一节，它把聊天室连接、订阅、fetch 三类 cleanup 各演示了一遍。

紧接着读：react.dev · You Might Not Need an Effect（约 20 分钟）。这是整个 React 文档里性价比最高的一篇，通篇是「你以为要用 Effect，其实不用」的对照案例。哪怕只读结尾的 Recap 八条也值。「什么时候不该用 useEffect」是高频面试加分题，能立刻把你和只会用的人区分开。

如果还有余力：react.dev · useEffect 参考的 Caveats，以及 Lifecycle of Reactive Effects —— 后者提出了一个很好的视角：不要按组件的生命周期去想 effect，要按 effect 自己的「开始同步 / 停止同步」去想。
