TypeScript 不是 C#

两个类型系统，看着像双胞胎，底层假设完全相反。这一课你会亲手让 TypeScript 对你撒一次谎。

本课的收获

你会拿到两个可复述的判断：「TS 看形状，C# 看名字」与「TS 的类型在运行时不存在」。然后你会在 playground/ 里制造一次「编译完全通过、页面却显示 undefined」的事故 —— 这一次事故，比读十篇文章更能让你记住类型擦除意味着什么。

接上一课：你已经有了一条打通的链路（第 1 课）。现在我们把注意力从「进程」缩小到「类型」。

一、名义类型 vs 结构类型

你熟悉的世界 · 名义（nominal）

C# 里，一个类型能不能用在某处，看的是它叫什么、继承自谁。两个结构完全一样的 class，只要没有显式的继承或 implements 关系，就绝对不能互换。class Point { int X; int Y; } 和 class Coord { int X; int Y; } 是两个毫不相干的类型。

TypeScript 反过来 —— 只看形状。官方手册说得很直白：

“TypeScript's type system is structural, not nominal: We can use obj as a Pointlike because it has x and y properties that are both numbers. The relationships between types are determined by the properties they contain, not whether they were declared with some particular relationship.” —— TypeScript for Java/C# Programmers · Erased Structural Types 
interface Point { x: number; y: number }

function log(p: Point) { console.log(p.x, p.y) }

// 没有 implements、没有继承、甚至不知道 Point 存在
class Vec { x = 1; y = 2; scale() {} }

const v: Point = new Vec();   // ✅ 通过。形状够了就行

再往前一步，官方手册给了一个更好用的心智模型：把类型看成「值的集合」，而不是「对象的标签」。

“In TypeScript, it's better to think of a type as a set of values that share something in common. Because types are just sets, a particular value can belong to many sets at the same time.”

这解释了一堆你在 TS 里会觉得奇怪的东西。string | number 不是什么特殊语法，就是两个集合的并集。一个对象同时满足三个 interface 也不矛盾 —— 它同时属于三个集合。C# 里「一个值有且仅有一个确切类型」的直觉，在这里不成立。

直接推论 · 为什么 TS 代码里 class 那么少

既然满足形状就够用，那定义一个 class 只为了描述数据结构就是纯浪费 —— interface 或 type 更轻，而且编译后一个字节都不剩（下一节）。所以在 React 项目里你会看到大量 interface Props { … }，几乎看不到 DTO class。这不是风格偏好，是类型系统性质决定的。
面试时如果被问「你们为什么不用 class 建模」，答案就是这句：TS 是结构化类型，class 带来的名义身份在这里没有价值，反而多出运行时开销。

二、类型擦除：编译完就没了

C# 的类型是 reified 的 —— 类型信息编译进 IL，运行时还在，所以你有反射、有 obj is IFoo、有 typeof(T)、有基于类型的序列化。

TypeScript 没有。一个字节都不留。 官方手册在同一章里写：“There's nothing at runtime that will tell us that obj is Pointlike. In fact, the Pointlike type is not present in any form at runtime.”

下面是我用 tsc 真实编译出来的结果，不是示意图：

interface 没了，type 没了，所有注解没了。剩下的是纯 JavaScript —— 一个完全不检查任何东西的动态语言。

C# 里你会做的TS 里的下场
if (o is IFoo)做不到。interface 运行时不存在，没有东西可判断。
反射 / typeof(T)做不到。泛型参数 T 编译后消失。
反序列化时自动校验类型不会发生。res.json() 返回什么就是什么，无人核对。
class + instanceof这个还在。 class 会编译成真实的 JS 函数，所以 instanceof 能用 —— 这是运行时唯一残留的类型痕迹。

三、动手：让类型对你撒谎

把上面这句「无人核对」变成你亲眼看见的一次事故。两个终端都开着（fastapi dev 与 pnpm dev）。

  1. 给响应加上类型

    新建 frontend\src\api.ts：

    export interface HelloResponse {
  message: string;
}

export async function fetchHello(): Promise<HelloResponse> {
  const res = await fetch("http://127.0.0.1:8000/api/hello");
  return res.json();
}

    注意 res.json() 的真实类型是 Promise<any>。我们声明返回 Promise<HelloResponse>，TS 二话不说就接受了 —— 记住这个地方，它就是谎言的入口。

  2. 用起来

    App.tsx 改成：

    import { useEffect, useState } from "react";
import { fetchHello } from "./api";

export default function App() {
  const [message, setMessage] = useState("加载中…");

  useEffect(() => {
    fetchHello().then((data) => setMessage(data.message));
  }, []);

  return <h1>{message}</h1>;
}

    页面应该照常显示 Hello from Python。在编辑器里把光标放到 data. 后面 —— 会弹出 message 的自动补全。感觉上一切尽在掌握。

  3. 确认编译是干净的 
    pnpm build

    这条命令会跑 tsc -b（完整类型检查）再 vite build。应当零错误。记住这个状态。

  4. 在后端撒谎

    改 backend\main.py，把返回的键名 message 改成 msg：

    @app.get("/api/hello")
def hello() -> dict[str, str]:
    return {"msg": "Hello from Python"}

    保存。后端热重载。前端一行都不要改。

  5. 看着它烂掉

    刷新浏览器 —— 页面显示 undefined。

    现在再跑一次 pnpm build。依然零错误。

    停下来，把这件事想透

    TypeScript 从头到尾没有说谎的能力，是你骗了它：你在 fetchHello 上写了 Promise<HelloResponse>，那是一句承诺，不是一次检查。编译器信了你，然后自己被删掉了，运行时没有任何人再去核对。
    更要命的是这类 bug 的形态：它不在边界处报错，而是让一个 undefined 顺着数据流往下淌，最后在某个八竿子打不着的组件里炸掉。

  6. 改回来，并记下这笔债

    把后端改回 {"message": ...}，确认页面恢复。

    你刚刚亲手证明了

    类型注解只在系统内部有效；跨越系统边界的数据，必须在运行时校验。 边界包括：HTTP 响应、localStorage、URL 参数、用户输入、第三方 SDK 的回调。
    这正是下一课的主题 —— 后端用 Pydantic、前端用 Zod 在边界上立一道真实的检查。你现在有了一个具体的、自己造成的理由去学它。

四、预测编译结果

下面四段代码，先在脑子里判断，再点。（这些我都用 tsc --strict 实际跑过。）

预测 1 / 4

形状够了，但多带了一个属性：

interface Point { x: number; y: number }
function log(p: Point) {}

const obj = { x: 1, y: 2, name: "origin" };
log(obj);

obj 有 x 和 y，形状满足 Point，多出来的 name 不影响。这就是结构化类型：「至少有」，不是「刚好是」。C# 里这段代码连编译器的门都进不去。

预测 2 / 4

同样的东西，但直接写成字面量传进去：

interface Point { x: number; y: number }
function log(p: Point) {}

log({ x: 1, y: 2, name: "origin" });

error TS2353: Object literal may only specify known properties, and 'name' does not exist in type 'Point'.

和上一题唯一的差别是这个对象是新鲜的（fresh）—— 直接写在参数位置的字面量会触发 excess property checking（多余属性检查）。TS 的理由很实际：你当场手写一个用不到的属性，八成是拼错了字段名。官方说明

这一对题是最好的面试素材：同样的值，赋给变量再传就通过，直接传就报错。能讲清这个差别，说明你真的理解结构化类型，而不只是背过名词。

预测 3 / 4

一个 class，从没听说过这个 interface：

interface Point { x: number; y: number }

class Vec { x = 1; y = 2; scale() {} }

const v: Point = new Vec();

不需要 implements。Vec 有 x 和 y，它就是 Point。implements 在 TS 里只是一个给编译器的自查请求（「帮我确认这个类形状对不对」），它不建立任何身份关系，也不影响这个类能被赋给谁。这和 C# 的 implements 是截然不同的东西。

预测 4 / 4

两个一模一样的 class，字段是 private：

class A { private id = 1 }
class B { private id = 1 }

const a: A = new B();

error TS2322: Type 'B' is not assignable to type 'A'. Types have separate declarations of a private property 'id'.

这是结构化规则的唯一例外：带 private / protected 成员的类，TS 会按声明位置比较 —— 也就是退化成名义类型。所以「TS 全是结构化的」这句话严格说是错的。答成「TS 默认结构化，但含私有成员的 class 例外」，含金量完全不同。

五、检验一下

测验 1 / 2

「TS 的类型不是 reified 的」这句话，最直接的后果是？

编译期检查一切正常，那正是 TS 的价值所在。问题出在编译之后：interface 被整个删除，运行时没有任何东西可供比对，所以 o is IFoo 这类判断根本无从写起。要在运行时确认形状，只能靠代码自己去查每个字段 —— 或者用 Zod 这类库替你生成这些检查。

测验 2 / 2

后端把字段名改了，前端 pnpm build 却依然零错误。原因是？

res.json() 的类型是 any，等于对编译器说「这里我说了算」。你写下 Promise<HelloResponse>，编译器就照单全收 —— 它没有能力去访问你的后端确认。整条链路上唯一知道真相的是运行中的 Python 进程，而它和 tsc 之间没有任何通道。

顺带一提，这个通道其实可以建起来：FastAPI 会生成 OpenAPI schema，前端可以据此自动生成 TS 类型。那是后面的课。

回忆练习 · 不要跳过

合上这一页，出声回答两个问题：
（1）为什么 TS 里用 interface 描述数据，比用 class 更常见？
（2）上一课的 CORS 和这一课的类型擦除，有什么共同点？

(1) 结构化类型下，class 提供的「名义身份」没有价值 —— 形状满足就能用。而 interface 编译后完全消失，class 会留下真实的 JS 代码。用更轻的东西拿到同样的检查，没有理由不用。

(2) 两者都是「检查发生在哪一端」的问题，而且答案都反直觉：CORS 的检查发生在浏览器，不在服务端（所以 curl 不受限）；类型的检查发生在编译期，不在运行时（所以后端改字段编译器不知道）。「谁在检查、什么时候检查」是贯穿这套技术栈的一条主线 —— 面试时能主动把两件事串起来讲，效果远好于分别答对。

六、面试回答模板

如果面试官问：“TypeScript 和 C# / Java 的类型系统有什么区别？”

“两个根本差异。第一，TS 是结构化类型，C# 是名义类型 —— TS 只看形状，一个 class 不写 implements 也能满足接口。有个例外：带 private 成员的 class 会退化成名义比较。第二，TS 的类型不是 reified 的，编译后完全擦除，运行时什么都不剩，所以没有反射、没有运行时类型判断。
这在实践中的影响是：所有跨系统边界的数据 —— API 响应、localStorage、URL 参数 —— 类型注解都只是一句承诺，没人验证。我自己就踩过：后端改了个字段名，前端类型检查一片绿，页面直接渲染出 undefined。所以边界上必须加运行时校验，前端用 Zod，后端用 Pydantic。”

最后那句亲身经历是这段话的核心。它把一个背下来的知识点变成了一段有代价的经验 —— 面试官能立刻分辨出这两者的区别。
