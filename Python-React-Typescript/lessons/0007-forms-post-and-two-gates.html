Lesson 0007 · 约 55 分钟

把数据交上去

前六课数据一直是单向流下来的：后端说什么，页面显示什么。这一课方向反过来 —— 而反向的这条路上藏着三个机关，它们都不报错，只是安静地骗你：打不出字的输入框、把整个页面冲掉的提交按钮、被服务器拒绝了却一声不吭的 fetch。

本课的收获

做完之后，你手上会有一个真正能写入后端的表单，并且能解释四件事：为什么 React 的 <input> 非要你写 onChange；为什么「提交中 / 失败 / 成功」不该用三个布尔值存；为什么 fetch 收到 422 不算失败；以及为什么前端已经校验过了，后端还得再校验一遍（第 3 课那两道关，今天终于在同一条请求上一起工作）。

一、受控组件：输入框的值，由 state 说了算

第 6 课那个 Row 里你已经写过一次，只是没点名：

<input value={note} onChange={(e) => setNote(e.target.value)} />

这叫 controlled component（受控组件）。官方定义很直接：

“An input like <input /> is uncontrolled. … your JSX only specifies the initial value. It does not control what the value should be right now.”
“To render a controlled input, pass the value prop to it (or checked for checkboxes and radios). React will force the input to always have the value you passed.”
“Every controlled input needs an onChange event handler that synchronously updates its backing value.” —— react.dev · <input>

注意 force 这个词。React 不是「读一下输入框」，是每次渲染都把 value 按回去。所以只写 value 不写 onChange 的后果不是「值不同步」，而是：

“If you pass value without onChange, it will be impossible to type into the input.” —— react.dev · <input>

键盘完全失灵。你敲的每一个字符，都在下一次渲染时被 React 用旧的 value 覆盖回去。第 2 步你会亲手体验这个「坏掉的输入框」。

C# 参照物：这是「单向绑定 + 手动回写」

WPF / WinForms 里你写 {Binding Text, Mode=TwoWay}，框架双向替你搬运：控件改了自动写回对象，对象改了自动刷新控件。

React 没有双向绑定。它只有一个方向：state → UI。反方向那一段要你自己写，那就是 onChange。麻烦，但换来一个确定的好处：数据只有一个源头（single source of truth） —— 屏幕上显示什么，永远等于 state 里是什么，中间没有第二份真相。这也是为什么可以在 onChange 里顺手做大写转换、过滤非法字符：回写那一步在你手里。

二、提交按钮会把你的页面冲掉

HTML 表单诞生于 1995 年，它的默认行为比 React 老得多：

“By default, the browser will send the form data to the current URL and refresh the page. You can override that behavior by calling e.preventDefault().” —— react.dev · <input>

「refresh the page」在单页应用里意味着核弹级后果：整个 JS 运行时重来，所有 state 归零 —— 不只是这个表单，连你第 6 课那三行备注、那个计数器，全没了。第 3 步你会亲眼看一次。

三、三个状态，不要用三个布尔值

一次提交至少有四种可见状态。官方把它们列成了清单：

“Empty: Form has a disabled ‘Submit’ button. / Typing: Form has an enabled ‘Submit’ button. / Submitting: Form is completely disabled. Spinner is shown. / Success: ‘Thank you’ message is shown instead of a form. / Error: Same as Typing state, but with an extra error message.” —— react.dev · Reacting to Input with State

新手的第一直觉是 const [isSubmitting, setIsSubmitting] = useState(false)，再加一个 isSuccess，再加一个 errorMessage。官方直接点名了这个做法：

“While this code works, it leaves the door open for ‘impossible’ states. For example, if you forget to call setIsSent and setIsSending together, you may end up in a situation where both isSending and isSent are true at the same time.”
“Avoid contradictions in state. When the state is structured in a way that several pieces of state may contradict and ‘disagree’ with each other, you leave room for mistakes.” —— react.dev · Choosing the State Structure

两个布尔值有 4 种组合，其中 1 种非法；再加一个就是 8 种组合、5 种非法。正确做法是让非法状态根本无法被表示：

type Status =
  | { kind: "idle" }
  | { kind: "submitting" }
  | { kind: "error"; message: string }
  | { kind: "success"; note: Note };
C# 参照物：这次是 TypeScript 赢了

这叫 discriminated union（可辨识联合），靠 kind 这个字面量字段区分分支。写 if (status.kind === "error") 之后 TS 会自动收窄类型：这一分支里 status.message 存在且是 string；而在 idle 分支里访问 .message 直接编译报错 —— 这正是第 2 课那套结构化类型 + 收窄的兑现。

C# 到今天都没有真正的联合类型。要表达同一件事，你得写抽象基类 + 若干子类 + switch 模式匹配，或者上 OneOf<T1,T2> 这类第三方库。「TS 有什么是 C# 没有的」是很好答的一道面试题 —— 答联合类型 + 字面量类型，比答别的都实在。

四、fetch 不认为 422 是失败

这是本课第一个反直觉点，而且它与 React 无关 —— 是 Web 平台本身的设计：

“A fetch() promise only rejects when the request fails, for example, because of a badly-formed request URL or a network error. A fetch() promise does not reject if the server responds with HTTP status codes that indicate errors (404, 504, etc.). Instead, a then() handler must check the Response.ok and/or Response.status properties.” —— MDN · fetch()

实测（Node 24 打向本课的 FastAPI 后端，故意提交空标题）：

throw? no. ok = false status = 422
json = {"detail":[{"type":"string_too_short","loc":["body","title"], … }]}

把插头拔掉（换成一个连不上的端口）才会真的抛：

network error DOES throw: TypeError | fetch failed
如果你不查 res.ok 会怎样

后果不是崩溃，是一句莫名其妙的错误提示。你会兴高采烈地 await res.json() —— 拿到的是 FastAPI 的 422 错误体；然后交给 Zod 的 Note schema 一 parse，它当然不通过，于是屏幕上写着「响应格式不对」。

而真相是格式一点问题都没有 —— 是你的数据被拒绝了。整整两层误导，全都源于漏了一行 if (!res.ok)。

C# 参照物：这个你早就会了 
// C#：SendAsync 收到 404/500 同样不抛
var res = await http.PostAsJsonAsync(url, dto);
res.EnsureSuccessStatusCode();   // ← 你得自己叫它抛

// JS：一模一样的设计，只是没人替你写 EnsureSuccessStatusCode
if (!res.ok) { /* 自己处理 */ }

res.ok 就是 IsSuccessStatusCode（状态码落在 200–299）。面试里能顺口把这两个对上，比背 MDN 更能说明你真的理解了「HTTP 层面成功」与「业务层面成功」是两件事。

五、两道关，终于一起工作

第 3 课你分别造了两道校验关：前端的 Zod、后端的 Pydantic。当时它们各管各的。今天同一份数据要连着穿过两道，问题就来了：既然前端已经拦住了空标题，后端为什么还要拦一次？

因为前端的校验不是安全措施

第 6 步你会亲手绕过它 —— 一条 curl 命令就够了。浏览器里的代码全部在用户手上：改 JS、改请求、干脆不用浏览器，随便哪一种都能让你的 Zod 形同虚设。

所以分工是：前端校验负责体验（即时反馈，不用等一个来回），后端校验负责信任（它是唯一真正的关卡）。写在浏览器里的规则永远只是建议。这是本课最值钱的一句话，也是安全类面试题的标准答法。

后端这一侧，FastAPI 几乎不用你动手：

“With just that Python type declaration, FastAPI will: Read the body of the request as JSON. Convert the corresponding types (if needed). Validate the data. If the data is invalid, it will return a nice and clear error, indicating exactly where and what was the incorrect data.” —— FastAPI · Request Body

实测那个 “nice and clear error”（提交 {"title":""}，且缺 body）：

HTTP/1.1 422 Unprocessable Content

{"detail":[
  {"type":"string_too_short","loc":["body","title"],
   "msg":"String should have at least 1 character","input":""},
  {"type":"missing","loc":["body","body"],
   "msg":"Field required","input":{"title":""}}
]}

loc 里的第一个 "body" 指请求体（相对的还有 "query"、"path"），第二个才是字段名。这个结构化错误体是可以直接喂给前端逐字段显示的 —— 本课先不做，但面试聊到「表单错误怎么展示」时，说得出「后端返回结构化的 loc + msg，前端按字段名摊到各个输入框下面」就够了。

顺手记一条：Zod 的 schema 不只是校验，它还改数据

z.string().trim().min(1) 里的 .trim() 是一个 transform，先执行，再校验。实测：输入 " "（三个空格）会被判不通过。

所以 safeParse 成功之后，该用的是 parsed.data（首尾空格已去掉的新对象），而不是原始 state。「Zod 是 parser，不是 validator」 —— 进去 unknown，出来是干净且有类型的数据。这跟 C# 的 FluentValidation（只回答是/否，不改数据）分野明显。

六、看不见的第三个请求

这一课你的浏览器会悄悄多发一个请求，而 uvicorn 的日志会把它抓个正着：

“For ‘preflighted’ requests the browser first sends an HTTP request using the OPTIONS method to the resource on the other origin, in order to determine if the actual request is safe to send.” —— MDN · CORS

触发条件里最关键的一条：「简单请求」只允许三种 Content-Type —— application/x-www-form-urlencoded、multipart/form-data、text/plain。application/json 不在其中，也就是说几乎每一个现代 API 的 POST 都会被预检。实测日志：

INFO: 127.0.0.1:9296 - "OPTIONS /api/notes HTTP/1.1" 200 OK   ← 你没写过这个请求
INFO: 127.0.0.1:9297 - "POST /api/notes HTTP/1.1" 200 OK

第 1 课那个 CORSMiddleware 就是在这里第二次救你 —— 它替你回答了这个 OPTIONS。「为什么我 GET 好好的，一改成 POST 就跨域报错」是极高频的实战问题，答案通常就是：预检没被正确响应。

七、动手

两个终端照旧：后端 uvicorn（这一课要一直盯着它的日志），前端 pnpm dev。再开第三个终端跑 curl。

  1. 后端：开一个能写入的端点

    backend/main.py，加两个模型和两个路由（Field 记得从 pydantic 导入）：

    from pydantic import BaseModel, Field

class NoteCreate(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    body: str = Field(min_length=1)

class Note(BaseModel):
    id: int
    title: str
    body: str

notes: list[Note] = []          # 内存里存着就行，重启即丢

@app.get("/api/notes")
def list_notes() -> list[Note]:
    return notes

@app.post("/api/notes")
def create_note(payload: NoteCreate) -> Note:
    note = Note(id=len(notes), title=payload.title, body=payload.body)
    notes.append(note)
    return note

    先不碰前端，用 curl 验两发：

    curl.exe -X POST http://127.0.0.1:8000/api/notes -H "Content-Type: application/json" -d "{\"title\":\"a\",\"body\":\"b\"}"
→ {"id":0,"title":"a","body":"b"}

curl.exe -i -X POST http://127.0.0.1:8000/api/notes -H "Content-Type: application/json" -d "{\"title\":\"\"}"
→ HTTP/1.1 422 Unprocessable Content
→ {"detail":[{"type":"string_too_short","loc":["body","title"], …

    PowerShell 里 curl 是 Invoke-WebRequest 的别名，要写 curl.exe 才是真的 curl；引号转义按上面的 Windows 写法。

    注意这个顺序：后端先于前端可用。这本身就是个值得说出口的工作方式 —— API 能用 curl 验通，前端出问题时你才知道该怪谁。

  2. 造一个打不出字的输入框

    在 App 里加 state 和一个故意残缺的表单：

    const [title, setTitle] = useState("");
const [body, setBody] = useState("");

// JSX：
<form>
  <input name="title" value={title} />          ← 只有 value，没有 onChange
  <input name="body" value={body} />
  <button type="submit">提交</button>
</form>

    保存，往输入框里使劲敲字。Console 里：

    You provided a `value` prop to a form field without an `onChange` handler.
This will render a read-only field. If the field should be mutable use
`defaultValue`. Otherwise, set either `onChange` or `readOnly`.

    然后把 onChange 补上，两个都补：

    <input name="title" value={title} onChange={(e) => setTitle(e.target.value)} />

    顺手做个小实验：把它改成 setTitle(e.target.value.toUpperCase())，输入框会强制大写。这就是「force」的字面意思 —— 屏幕上显示的从来不是你敲的，而是 state 里的。看完改回来。

  3. 先预测，再按下提交

    表单现在能打字了，但 <form> 上还没有 onSubmit。

    先预测 · 别偷看

    在两个框里填上字，点「提交」。没有 onSubmit、也没有 preventDefault —— 屏幕上会发生什么？地址栏呢？那三行备注和计数器呢？

    整页刷新。地址栏变成 http://localhost:5173/?title=你填的&body=你填的 —— 浏览器把表单数据拼进 URL、GET 提交给了当前地址（1995 年就定下的默认行为，用的正是 name 属性）。
    后果是整个 JS 运行时重来：第 6 课那三行备注清空、计数器归零、Hello from Python 重新请求了一遍。一个按钮，把全应用的 state 冲掉了。
    如果你预测的是「什么都不发生」—— 这正是它阴险的地方：它不报错，它成功地做了一件你根本不想要的事。

    照做，盯住地址栏那一刻。这是本课最便宜的一次教训。

  4. 接管提交：三态 union + 第一道关

    先在 api.ts 里加 schema 和 postNote（请求、响应各一个 schema）：

    export const Note = z.object({ id: z.number(), title: z.string(), body: z.string() });
export type Note = z.infer<typeof Note>;

export const NoteCreate = z.object({
  title: z.string().trim().min(1, "标题不能为空").max(50, "标题最多 50 字"),
  body: z.string().trim().min(1, "内容不能为空"),
});
export type NoteCreate = z.infer<typeof NoteCreate>;

export async function postNote(input: NoteCreate) {
  const res = await fetch("http://127.0.0.1:8000/api/notes", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(input),
  });
  if (!res.ok) return { ok: false as const, message: `服务器拒绝了：HTTP ${res.status}` };
  const json: unknown = await res.json();
  const parsed = Note.safeParse(json);
  if (!parsed.success) return { ok: false as const, message: "响应格式不对：" + z.prettifyError(parsed.error) };
  return { ok: true as const, note: parsed.data };
}

    false as const 让类型是字面量 false 而不是 boolean；有了它，if (result.ok) 之后 TS 才能收窄出 note。这就是你刚在第三节读到的 discriminated union，只是判别字段叫 ok。

    然后在 App.tsx 里：

    import { type FormEvent, useEffect, useState } from "react";
import { NoteCreate, postNote, type Note } from "./api";

type Status =
  | { kind: "idle" } | { kind: "submitting" }
  | { kind: "error"; message: string } | { kind: "success"; note: Note };

const [status, setStatus] = useState<Status>({ kind: "idle" });

async function handleSubmit(e: FormEvent<HTMLFormElement>) {
  e.preventDefault();
  const parsed = NoteCreate.safeParse({ title, body });     // 第一道关：Zod
  if (!parsed.success) {
    setStatus({ kind: "error", message: z.prettifyError(parsed.error) });
    return;
  }
  setStatus({ kind: "submitting" });
  const result = await postNote(parsed.data);              // ← 用 parsed.data，不是 title/body
  if (result.ok) {
    setStatus({ kind: "success", note: result.note });
    setTitle(""); setBody("");                             // 受控组件清空 = 把 state 清空
  } else {
    setStatus({ kind: "error", message: result.message });
  }
}

    JSX 改成 <form onSubmit={handleSubmit}>，并加上状态显示：

    <button type="submit" disabled={status.kind === "submitting"}>
  {status.kind === "submitting" ? "提交中…" : "提交"}
</button>
{status.kind === "error" && <pre style={{ color: "crimson" }}>{status.message}</pre>}
{status.kind === "success" && <p>已保存 #{status.note.id}：{status.note.title}</p>}

    试三遍：① 两个框都留空直接提交 → 红字两行（✖ 标题不能为空 → at title），而且 uvicorn 日志一条请求都没有 —— 被前端拦下，根本没出门。② 标题只填三个空格 → 照样拦（.trim() 先跑）。③ 正常填写 → 成功，输入框自动清空。

    顺手体验一次收窄：把 {status.kind === "error" && …} 的条件删掉，直接写 {status.message}，看 TS 报什么。看完改回来。

  5. 抓住那个你没写过的 OPTIONS

    清空 uvicorn 终端，提交一次，数一数日志有几行：

    INFO: … "OPTIONS /api/notes HTTP/1.1" 200 OK
INFO: … "POST /api/notes HTTP/1.1" 200 OK

    两条。再打开 DevTools 的 Network 面板重做一次，同一件事的另一个视角。为什么 GET /api/hello 没有这一条？因为它没有 Content-Type: application/json，属于「简单请求」。

  6. 绕过你自己的前端

    前端的 Zod 限制标题最多 50 字。现在无视它：

    curl.exe -i -X POST http://127.0.0.1:8000/api/notes -H "Content-Type: application/json" -d "{\"title\":\"（粘 60 个字符）\",\"body\":\"x\"}"
→ HTTP/1.1 422 Unprocessable Content   ← 第二道关拦住了

    然后把后端的 Field(min_length=1, max_length=50) 临时删掉，改成光秃秃的 title: str，再跑一次同样的 curl：200，脏数据落库（curl.exe http://127.0.0.1:8000/api/notes 能看到它躺在那儿）。

    把 Field(…) 加回去。刚才这 60 秒，就是「前端校验不是安全措施」的全部证据。

    顺带注意一件事：同一条规则你写了两遍（Zod 一遍、Pydantic 一遍），而且它们会各自漂移。这是真实的工程痛点 —— 主流解法是从后端的 OpenAPI schema 自动生成前端类型/校验。想看怎么做，随时问我。

  7. 加餐：被 CORS 拒绝的请求，其实已经写进去了

    把后端的 allow_origins 改成一个错的地址：

    allow_origins=["http://localhost:9999"],

    回到页面提交一条。前端显示失败，Console 里是 CORS 报错 —— fetch 抛出 TypeError: Failed to fetch。注意这次是真的抛了：它属于「请求失败」，不是「服务器返回了错误码」。

    现在去终端查一下服务器里到底有什么：

    curl.exe http://127.0.0.1:8000/api/notes

    那条笔记好端端地躺在里面。我用 curl 带错误 Origin 实测过同一件事：服务器照常执行并返回 200，只是响应里少了 access-control-allow-origin 这个头，于是浏览器拒绝把结果交给你的 JS。

    这条推论值一道面试题

    CORS 是浏览器执行的，不是服务器执行的。它保护的是「用户的浏览器不被别的网站利用」，它从来不是服务器端的访问控制 —— curl、Postman、任何后端程序都完全不受它约束。所以「我加了 CORS 白名单所以接口是安全的」是错的；真正的门禁是认证授权。

    把 allow_origins 改回 ["http://localhost:5173"]。收尾：pnpm lint 与 pnpm build 零错误。

    你现在拥有的

    一条完整的双向链路：受控输入 → Zod（体验关）→ JSON over HTTP（外加一次预检）→ Pydantic（信任关）→ 后端内存 → 带类型的响应 → Zod 再校验 → 回到 state → 渲染。这条链路就是「一个网站是怎么工作的」这道面试题的全部内容，而且每一环你都亲手断过一次。

八、检验一下

测验 1 / 5

<input value={x} /> 但没写 onChange，实际后果是：

官方原话：“If you pass value without onChange, it will be impossible to type into the input.” 因为 React 会 force 输入框始终等于你传进去的 value，你敲的字符在下一次渲染就被按回原样。
Console 里会有 You provided a value prop to a form field without an onChange handler. —— 但只是 warning，不是错误。
一句话记住：屏幕上显示的永远是 state，不是你敲的东西。这就是受控组件的定义。

测验 2 / 5

fetch 拿到 HTTP 422 之后，代码里会发生什么？

MDN：“A fetch() promise does not reject if the server responds with HTTP status codes that indicate errors (404, 504, etc.).” 只有请求本身失败（网络断了、URL 非法、被 CORS 拦下）才 reject。
实测：422 → ok = false, status = 422，无异常；换成连不上的端口 → TypeError: fetch failed。
C# 对照：HttpClient 也不抛，要自己叫 EnsureSuccessStatusCode()；res.ok ≡ IsSuccessStatusCode。
漏掉 if (!res.ok) 的典型症状：屏幕上显示「响应格式不对」，而真相是数据被拒了。

测验 3 / 5

用 isSubmitting / isError / isSuccess 三个布尔值存提交状态，主要问题是：

官方点名了这个写法：“it leaves the door open for ‘impossible’ states… both isSending and isSent are true at the same time.” 原则叫 “Avoid contradictions in state.”
换成 discriminated union（{ kind: "error"; message: string } 那一套）之后，非法状态根本表示不出来，而且 message 只在 error 分支存在 —— 类型收窄替你把关。
第四个选项说反了：React 会 batch（第 4 课）。问题从来不是性能，是正确性。

测验 4 / 5

前端已经用 Zod 校验过了，后端仍必须校验，根本原因是：

你在第 6 步亲手做过：一条 curl 就绕过了整个前端。凡是运行在用户机器上的规则，都只是建议。
正确的分工说法：前端校验为了体验（即时反馈，省一个来回），后端校验为了信任（唯一真正的关卡）。
Zod 当然能表达长度约束（.min() / .max()）—— 它甚至还能改数据（.trim() 是 transform，先跑再校验，所以要用 parsed.data）。Zod 是 parser，不是 validator。

测验 5 / 5

跨域 POST 被浏览器以 CORS 报错拦下时，服务器那边：

实测：带错误 Origin 的 POST，服务器照常执行、照常返回 200，笔记真的进了列表；只是响应缺了 access-control-allow-origin，于是浏览器不把结果交给 JS（MDN 明说：“specifics about the error are not available to JavaScript”）。
推论 —— CORS 是浏览器执行的，不是服务器的访问控制。curl / Postman / 任何后端程序都不受约束。「加了 CORS 白名单所以接口安全」是错的，真正的门禁是认证授权。
第四个选项是个像样的干扰项：预检失败时确实不会发出真请求；但这里预检是成功的（allow_methods=["*"]），被拒的是真请求的响应。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒：
（1）从你在输入框里敲下一个字符，到这条笔记存进后端，数据一共变了几次形态、经过几道关？
（2）为什么 onSubmit 里第一行就得写 e.preventDefault()？
（3）「我配了 CORS 白名单，所以这个接口是安全的」—— 反驳它。

(1) 敲键盘 → onChange 把 e.target.value 写进 state（受控：屏幕显示的一直是 state）→ 提交时 NoteCreate.safeParse（第一道关，顺便 trim，产出 parsed.data）→ JSON.stringify 成文本 → HTTP 请求（先来一次 OPTIONS 预检，因为 application/json 不是简单请求）→ FastAPI 把 body 解析成 NoteCreate（第二道关，不合法直接 422 且函数体不执行）→ 存入 → 返回 Note（FastAPI 按返回类型校验并剥掉多余字段，第 3 课实测过）→ 前端查 res.ok → Zod 再 parse 一次响应 → 进 state → 渲染。

(2) 因为 <form> 的默认行为是把数据拼进 URL、GET 提交给当前地址并刷新整页。在 SPA 里这等于把整个 JS 运行时和全部 state 清零 —— 不只是这个表单。它不报错，它「成功地」做了一件你根本不想要的事。

(3) CORS 由浏览器执行。服务器该干的活照样干完（实测：带错 Origin 的 POST 返回 200，数据真的写进去了），只是响应少了个头，浏览器不把结果给 JS。curl、Postman、任何服务端程序都完全不受它约束。CORS 保护的是用户的浏览器，不是你的接口。接口的门禁是认证授权。

九、面试回答模板

如果面试官问：“说说 React 里表单怎么做？” / “前端校验过了，后端还要校验吗？”

“我一般用受控组件：value 绑 state，onChange 里回写。React 没有双向绑定，反向那一段要自己写 —— 代价是啰嗦，好处是只有一个数据源，屏幕上显示的永远等于 state。只写 value 不写 onChange 的话，输入框会直接打不进字，因为 React 每次渲染都把 value 强制按回去。
提交我会注意三点。第一，onSubmit 里先 e.preventDefault()，否则浏览器会按老规矩把表单 GET 提交给当前 URL 并刷新整页，SPA 的全部 state 直接清零。第二，状态不用几个布尔值存，用一个 discriminated union：idle | submitting | error | success，这样 isSubmitting 和 isSuccess 同时为 true 这种非法组合根本表示不出来，而且错误消息只在 error 分支上存在，类型收窄帮我兜底 —— 顺带一提这也是 TS 比 C# 强的地方，C# 至今没有真正的联合类型。第三，fetch 收到 422 是不抛异常的，必须查 res.ok，跟 C# 的 EnsureSuccessStatusCode 是一回事。我踩过这个坑，症状很有迷惑性：漏了这行，422 的错误体会被当成正常响应拿去校验，屏幕上报『响应格式不对』，而真相是数据被拒了。
校验两边都要做，但目的不同：前端为了体验，后端为了信任。前端那道关一条 curl 就绕过去了 —— 凡是跑在用户机器上的规则都只是建议。后端我用 FastAPI，Pydantic 模型直接当请求体类型，不合法自动 422 并给出结构化的 loc + msg，函数体根本不执行。两边规则重复是真实痛点，成熟做法是从 OpenAPI schema 生成前端类型。
还有个容易被忽略的细节：Content-Type: application/json 不是简单请求，每个 POST 之前浏览器都会先发一条 OPTIONS 预检。『GET 好好的、一改 POST 就跨域失败』基本都是预检没被正确响应。而且 CORS 是浏览器执行的，不是访问控制 —— 我实测过带错 Origin 的 POST，服务器照样执行并写入了数据，只是响应被浏览器扣下了。”

四个分水岭句子：「屏幕上显示的永远是 state，不是你敲的东西」、「前端为了体验，后端为了信任」、「422 不是失败，网络断了才是失败」、「CORS 保护的是浏览器，不是你的接口」。最后一句尤其少见 —— 大多数候选人只会说「跨域要配 CORS」。
