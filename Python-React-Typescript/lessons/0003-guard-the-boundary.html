Lesson 0003 · 约 50 分钟

在边界上立一道检查

上一课你造出了一个 undefined。这一课你把它逼到边界上炸掉 —— 后端用 Pydantic，前端用 Zod。

本课的收获

你会拿到一句能贯穿整个技术栈的判断：「类型注解管系统内部，边界上必须有运行时校验」。做完之后，同样把后端字段改坏，你会在两个不同的位置各得到一条说人话的错误 —— 而不是一个飘到组件里才炸的 undefined。顺带你会理解 TS 生态里一个方向反直觉的做法：先写 schema（值），再从 schema 推出类型。

接上一课（第 2 课）的结论：fetchHello(): Promise<HelloResponse> 是一句承诺，编译器信了，然后自己被擦除了，运行时无人核对。现在我们派个人去核对。

一、什么是「边界」

边界就是类型系统管辖权的国境线。线内，编译器替你担保；线外，什么都可能进来。数一数你的项目里有多少条边界：

边界线外那边是谁
HTTP 响应 res.json()另一个进程、另一门语言，可能昨天刚改过字段名
HTTP 请求体（后端视角）任何人。包括拿 curl 来试你的人
localStorage / URL 参数用户自己，以及三个月前版本的你写进去的旧格式
环境变量 / 配置文件部署脚本，全是字符串
第三方 SDK 回调别人的代码，类型声明未必和实现一致
你熟悉的世界

C# 里这件事你其实一直在做，只是被框架藏起来了：[ApiController] + DataAnnotations 让 ASP.NET Core 在 model binding 阶段自动校验请求体，不合法直接返回 400，你的 action 方法根本不会被调用。System.Text.Json 反序列化到 DTO 时也会因类型不匹配抛异常。
差异在于：C# 的运行时本身就带类型信息，校验是顺带的；TS / Python 的运行时没有，校验必须由一个库显式地做。所以 Pydantic 和 Zod 在这两个生态里的地位，比 FluentValidation 在 .NET 里重要得多 —— 它们不是「加强校验」，它们是唯一的一道检查。

二、后端：Pydantic

Pydantic 是 FastAPI 的底座。它的核心把戏是：在运行时读取你写的类型注解，并据此生成校验代码（回顾术语表里的 type hint —— Python 自己从不检查注解，是 Pydantic 主动去读）。

from pydantic import BaseModel

class HelloResponse(BaseModel):
    message: str

看起来就是个 C# record / DTO。关键在于把它挂到路由的返回类型注解上：

@app.get("/api/hello")
def hello() -> HelloResponse:          # ← 这个注解就是 response model
    return HelloResponse(message="Hello from Python")
“FastAPI will use this return type to: validate the returned data … add a JSON Schema for the response, in the OpenAPI path operation … And most importantly: It will limit and filter the output data to what is defined in the return type.” —— FastAPI · Response Model - Return Type

三件事，逐条对着 C# 想：

Pydantic 做的意味着什么
校验返回的数据缺字段或类型不对 → 抛 ResponseValidationError，客户端收到 500。错误发生在产生它的地方，不再往下游流。
过滤模型里没声明的字段会被静默剥掉。这是安全特性：你不小心把整个 user 对象（含 password_hash）返回出去，也只有声明过的字段会出网。等价于 C# 里手写一次 DTO 投影，只不过它是自动的。
生成 schema模型会变成 OpenAPI 里的 JSON Schema，出现在 /docs。这就是第 1 课埋的伏笔 —— 前端将来可以据此自动生成 TS 类型。

请求方向同理：把 BaseModel 写成参数类型，FastAPI 就会解析并校验请求体，不合法直接返回 422，你的函数体不会执行 —— 和 [ApiController] 的自动 400 是同一个套路（官方文档）。

三、前端：Zod，以及一个反过来的方向

后端守住了自己这一侧，但浏览器依然只能选择相信网线那头。所以前端要有自己的一道检查。TS 生态的事实标准是 Zod。

import { z } from "zod";

const HelloResponse = z.object({
  message: z.string(),
});
这里必须停一下 —— 方向反了

HelloResponse 在这里不是一个类型，是一个值。它是一个真实存在于运行时的 JS 对象，有方法可以调用。这正是关键：类型会被擦除，值不会。要在运行时检查东西，就只能用值去做。
然后用 z.infer 反推出静态类型：

type HelloResponse = z.infer<typeof HelloResponse>;
// 得到 { message: string } —— 和上面的 schema 永远同步

C# 的方向是「类型是源头，校验规则挂在类型上（attribute）」。TS 这边是倒过来的：schema 是唯一的事实来源，类型是它的投影。理由很实在 —— 如果两边分开手写，它们迟早会不一致，而不一致的那一天，编译器不会告诉你。
（typeof HelloResponse 里的 typeof 是 TS 的类型运算符，作用是「把这个值的类型取出来」，和 JS 运行时那个 typeof 是同名的两回事。）

校验有两种调用法，差别只在失败时的行为：

方法失败时
.parse(data)抛 ZodError。适合「这里出错就该炸」的场合。
.safeParse(data)不抛，返回 { success: true, data } 或 { success: false, error }。适合需要在 UI 上显示错误的场合。
注意返回值是个可辨识联合（discriminated union）：if (r.success) 之后，TS 就知道 r.data 存在了 —— 这是类型收窄（narrowing）的典型用法。
顺手还掉一笔知识债：any vs unknown

res.json() 的类型是 any —— 上一课的谎言就是从这里进来的，因为 any 关闭一切检查，能被赋给任何东西。unknown 是它的解药：同样表示「不知道是什么」，但在收窄之前你什么都不能做。所以正确的接法是先落到 unknown，再让 Zod 把它收窄成可用的类型。校验之后拿到的类型，是挣来的，不是宣称的。

四、动手

两个终端开着（fastapi dev 与 pnpm dev）。

  1. 后端：定义模型

    backend\main.py，加导入与模型，并改掉路由的返回类型：

    from pydantic import BaseModel

class HelloResponse(BaseModel):
    message: str

# ...中间的 CORS 配置不动...

@app.get("/api/hello")
def hello() -> HelloResponse:
    return HelloResponse(message="Hello from Python")

    页面应当照常显示 Hello from Python。顺便打开 http://127.0.0.1:8000/docs —— HelloResponse 现在作为 schema 出现在里面了。

  2. 再撒一次同样的谎

    把返回改成一个字典，键名写错：

    @app.get("/api/hello")
def hello() -> HelloResponse:
    return {"msg": "Hello from Python"}

    刷新浏览器。这次不是 undefined 了 —— 请求直接 500，后端终端里印着：

    fastapi.exceptions.ResponseValidationError: 1 validation error:
  {'type': 'missing', 'loc': ('response', 'message'),
   'msg': 'Field required', 'input': {'msg': 'Hello from Python'}}

    字段名、文件、行号，一次给全。 对比上一课那个飘到 <h1> 里才显形的 undefined —— 同一个 bug，诊断成本差了两个数量级。

  3. 看一眼「过滤」

    改成多返回一个字段：return {"message": "Hello from Python", "secret": "leak"}。刷新，看 DevTools 的 Network 面板里响应体的内容。

    secret 不见了，也没有报错 —— 声明之外的字段被静默剥离。想清楚这一条对「不小心返回了整个 user 对象」意味着什么。看完把这行改回 return HelloResponse(message="Hello from Python")。

  4. 前端：装 Zod 
    pnpm add zod

    注意是 add 而不是 add -D —— Zod 的代码要进生产包，因为它在运行时真的要执行。这个区分本身就是本课的注脚：类型工具（typescript）是 devDependency，运行时校验库不是。

  5. 用 schema 重写 api.ts 
    import { z } from "zod";

export const HelloResponse = z.object({
  message: z.string(),
});

export type HelloResponse = z.infer<typeof HelloResponse>;

export async function fetchHello(): Promise<HelloResponse> {
  const res = await fetch("http://127.0.0.1:8000/api/hello");
  const json: unknown = await res.json();
  return HelloResponse.parse(json);   // ← 承诺变成了检查
}

    （同名的 const 和 type 可以共存：TS 的值命名空间与类型命名空间是分开的。这是 Zod 代码里非常常见的写法。）

    页面应当照常显示。pnpm build 也应当零错误。

  6. 让前端自己抓住它

    为了单独试前端这一侧，先把后端的返回类型注解去掉（def hello():），再返回 {"msg": "Hello from Python"} —— 相当于拆掉后端的守卫，模拟「一个你管不着的第三方 API 改了字段」。

    刷新页面。页面空白，但 DevTools Console 里躺着：

    ZodError: [
  {
    "expected": "string",
    "code": "invalid_type",
    "path": [ "message" ],
    "message": "Invalid input: expected string, received undefined"
  }
]

    path 直接指到出问题的字段。这就是全部意义：错误出现在数据进门的那一刻，而不是在下游某个组件里。

  7. 把错误显示给用户

    .parse 抛出的异常在 .then 链里会被悄悄吞掉。换成 safeParse，把结果交给 UI：

    // api.ts
export async function fetchHello() {
  const res = await fetch("http://127.0.0.1:8000/api/hello");
  const json: unknown = await res.json();
  return HelloResponse.safeParse(json);
}
    // App.tsx —— useEffect 内部
fetchHello().then((result) => {
  if (result.success) {
    setMessage(result.data.message);      // ← 这里 TS 知道 data 存在
  } else {
    setMessage("数据格式不对：" + z.prettifyError(result.error));
  }
});

    （App.tsx 顶部需要 import { z } from "zod";。）现在页面上会直接显示 数据格式不对：✖ Invalid input: expected string, received undefined → at message。

    试试把 if (result.success) 这个判断删掉，直接写 result.data —— TS 会立刻报错。这就是可辨识联合在替你干活。

  8. 全部恢复

    后端改回 -> HelloResponse 与 return HelloResponse(message="Hello from Python")，确认页面正常。前端的 safeParse 版本保留 —— 那是后面几课要一直用下去的形态。

    你现在拥有的

    一条两端都有守卫的链路。后端保证「我发出去的一定符合契约」，前端保证「我收进来的一定符合契约」。中间那根网线仍然什么都不保证 —— 它从来就不该保证。

五、检验一下

测验 1 / 4

Zod 的 schema 必须写成「值」而不是「类型」，根本原因是？

回到上一课的核心：interface 编译后一个字节都不剩，你没法在运行时「拿到」它去比对什么。而 z.object({...}) 产生的是一个普通 JS 对象，它活到运行时，所以能真的去检查数据。「先有 schema，再从 schema 推类型」这个方向，是类型擦除逼出来的。

测验 2 / 4

路由声明了 -> HelloResponse，但函数返回了模型里没有的额外字段。结果是？

缺字段是错误（500），多字段是过滤。这个不对称是有意设计的：过滤是一道安全闸门，防止内部字段意外出网。
顺带对照上一课的 TS excess property check —— 那是编译期对多余属性报错，这里是运行时对多余字段剥离。两个生态在同一个问题上做了相反的选择，理由也不同：TS 是为了抓拼写错误，Pydantic 是为了防数据泄漏。

测验 3 / 4

前端请求体不合法时，FastAPI 返回 422 而不是 500，因为：

4xx = 你的错，5xx = 我的错。请求体不合法是调用方送错了东西，函数根本没被调用 → 422（Unprocessable Entity，比笼统的 400 更精确）。响应体不合法是服务端自己违反了契约 → 500。
同一个 Pydantic 模型、同一套校验，出现在边界的两侧，语义完全不同。这个对称性是很好的面试素材。

测验 4 / 4

既然后端已经用 Pydantic 校验了响应，前端再用 Zod 校验一次是多余的吗？

后端保证的是「当前这个版本的后端发出的东西合法」。但用户浏览器里跑的可能是缓存了一天的旧前端，而后端今早刚上线了新版本；或者中间有网关改写、有代理返回了一个 HTML 错误页。校验的价值来自「不信任」，而不信任的对象是网线那头的一切，不只是数据本身。
这也是为什么它叫「边界」校验，而不是「后端」校验 —— localStorage 那一侧根本没有服务端，同样需要它。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒，把这三课串成一条线：
（1）为什么 Zod 的 schema 是值而不是类型？
（2）后端已经有 Pydantic 了，前端为什么还要 Zod？
（3）第 1 课的 CORS、第 2 课的类型擦除、第 3 课的边界校验，共同的那条主线是什么？

(1) 类型编译后被擦除，运行时不存在，无法用来检查任何东西；值活到运行时。所以先写 schema（值），再用 z.infer 反推类型 —— 单一事实来源在运行时那一侧。

(2) 因为它们是两个独立部署、可以各自升级的进程。前端信任的不是「后端的代码」，而是「此刻网线那头返回的字节」，这两者不是一回事。

(3) 三课都在回答同一个问题：「谁在检查、什么时候检查」。CORS —— 浏览器在检查，服务端不检查。类型 —— 编译器在检查，运行时不检查。边界校验 —— 补上「运行时没人检查」这个缺口。
能主动把三件事串成这一条线讲出来，含金量远高于分别答对三道题。面试官听到的是一个有结构的心智模型，而不是三个背下来的知识点。

六、面试回答模板

如果面试官问：“你们前后端怎么保证数据契约？”

“分两层。后端用 Pydantic，把响应模型写成路由的返回类型注解，FastAPI 会在运行时校验、过滤，并生成 OpenAPI schema —— 过滤这一点其实是安全特性，模型里没声明的字段出不了网。请求方向同理，不合法直接 422，函数体不执行，和 ASP.NET Core 的 [ApiController] 自动 400 是一个套路。
前端用 Zod。因为 TS 的类型编译后就擦除了，运行时没有任何检查，我们的做法是先定义 Zod schema，再用 z.infer 反推出静态类型 —— schema 是单一事实来源，这样类型和校验规则不可能漂移。res.json() 先落到 unknown，经过 safeParse 才拿到可用的类型。
有人会问后端都校验过了前端为什么还要校验 —— 因为那是两个独立部署的进程，用户浏览器里可能跑着昨天的前端。再往前一步的做法是从 FastAPI 的 OpenAPI schema 自动生成前端类型，让契约真正只有一份。”

最后那句主动抛出的「再往前一步」是钩子。它表明你知道当前方案的局限，也知道下一步往哪走 —— 这是区分「用过」和「想过」的地方。
