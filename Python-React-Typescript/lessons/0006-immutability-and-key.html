不可变更新与 key

Object.is 已经咬了你两次。这一课它咬第三次 —— 但这次它不报错、不卡住、也不打爆后端，它只是安静地把你的改动藏起来，等一个你意想不到的时刻再全部倒出来。

本课的收获

两条规则，一个共同的根：state 里的对象和数组要当只读的用；key 不是「给列表编个号」，是「告诉 React 这一个是谁」。做完之后你能解释四件事：为什么 arr.push(x); setArr(arr) 界面纹丝不动；为什么它过一会儿又自己变了；为什么用数组下标当 key 会造成静默的数据错位（不是「性能问题」）；以及怎么反过来用 key 主动重置一个组件的 state。

一、第三次被同一颗牙咬

先把前两次摆出来，你会发现它们是同一件事：

出现在症状根因

比的是引用，

第 5 课
Effect 失控		setData(新对象) 无限循环

前两次是「本该相等却判成不等」，这一次反过来 —— 「本该不等却判成相等」。你确实往数组里塞了新东西，但 React 拿到的还是同一个数组对象，于是它说：没变，不用重渲染。

“But without using the state setting function, React has no idea that object has changed. So React does not do anything in response. It's like trying to change the order after you've already eaten the meal.” —— react.dev · Updating Objects in State

官方给的规则很短：

“In other words, you should treat any JavaScript object that you put into state as read-only.”
“Arrays are mutable in JavaScript, but you should treat them as immutable when you store them in state. … you shouldn't reassign items inside an array like arr[0] = 'bird', and you also shouldn't use methods that mutate the array, such as push() and pop().” —— react.dev · Updating Arrays in State
C# 参照物：这个你其实早就会了

这就是 record 与 with 表达式的世界观，也是 ImmutableList<T> 的世界观：想改，就造一个新的。

// C#
var next = person with { Age = 31 };        // 新实例
var next = list.Add(item);                  // ImmutableList：返回新表，原表不动

// React 里一模一样的动作
setPerson({ ...person, age: 31 });
setItems([...items, item]);

差异在于强制力：C# 的 record 和 ImmutableList 由类型系统替你把关，你想 mutate 都编译不过。JS 的数组永远是可变的，没有任何东西拦你 —— arr.push() 编译通过、lint 不报、运行不报错。这条纪律百分之百靠自觉。这正是面试官想听你说出口的那句差异。

二、幽灵变更：它没丢，它在潜伏

大多数教程讲到「mutate 了界面不更新」就停了。但真实项目里的 bug 长得比这难看得多，因为那次 mutation 并没有被丢弃。我实跑了一遍，数的是组件函数被调用的次数：

动作渲染次数屏幕上
初始：state = ["a"]—a
arr.push("x"); setArr(arr)+0a ← 没反应
再点一次无关的按钮（比如那个计数器）+1a,x,x ← ？！

实测环境：React 19.2.8 + @testing-library/react + jsdom。第 2 步你会在真浏览器里复现它。

看懂那个 a,x,x

你点了两次「加一行」，两次都被 Object.is 判为「没变」而跳过渲染。但 push 是真的执行了 —— 数组里已经躺着两个 x，只是屏幕还停在旧的那一帧。

直到某个完全不相干的 state 变化触发了一次渲染，组件函数被重新调用，读到那个早就被改烂了的数组 —— 积压的变更一次性全部倒出来。
所以 mutation 的真实症状不是「不更新」，是 「点了没反应，过一会儿一堆东西突然全变了」。这种 bug 复现困难、日志干净、责任人难找。能在面试里描述出这个形状的人，明显是真踩过的。

三、不可变更新速查

官方这张表建议直接背下来 —— 它是本课唯一需要死记的东西：

要做的事避免（会 mutate）改用（返回新数组）
增push、unshiftconcat、[...arr, item]
删pop、shift、splicefilter、slice
改splice、arr[i] = ...map
排序reverse、sort先复制一份再排

来源：react.dev · Updating Arrays in State

“Unfortunately, slice and splice are named similarly but are very different: slice lets you copy an array or a part of it. splice mutates the array (to insert or delete items).” —— react.dev · Updating Arrays in State

slice / splice 这对是面试常见的一击：名字差一个字母，行为正好相反。sort 也值得单独记 —— C# 的 list.OrderBy() 返回新序列，JS 的 arr.sort() 是原地排序并返回同一个数组，直觉会骗你。

但是：刚造出来的东西随便改
“Mutation is only a problem when you change existing objects that are already in state. Mutating an object you've just created is okay because no other code references it yet. … This is called a ‘local mutation’. … Very convenient and completely okay!” —— react.dev · Updating Objects in State

所以 const next = [...items]; next.sort(...); setItems(next); 是完全合法的。规则不是「禁止一切 mutation」，是「禁止改已经在 state 里的那个对象」。说清这个边界，比背「React 要求不可变」高一档。

四、key：state 其实不住在组件里

现在换一个话题 —— 你会发现它其实是同一个话题。

先纠正一个几乎人人都有的默认假设。你大概以为组件的 state「存在组件里面」。不是：

“When you give a component state, you might think the state ‘lives’ inside the component. But the state is actually held inside React. React associates each piece of state it's holding with the correct component by where that component sits in the render tree.”
“React preserves a component's state for as long as it's being rendered at its position in the UI tree. If it gets removed, or a different component gets rendered at the same position, React discards its state.” —— react.dev · Preserving and Resetting State

state 的身份证是「位置」，不是「组件实例」。这跟 C# 差得很远：C# 里对象的身份就是引用本身，一个 Counter 实例的字段当然属于那个实例。React 里没有「那个实例」这回事 —— 组件函数每次渲染都重新跑一遍（第 4 课），能把新旧两次对上号的，只有它在树里的位置。

而 key 做的事，就是改写「位置」的定义：

“By default, React uses order within the parent (‘first counter’, ‘second counter’) to discern between components. But keys let you tell React that this is not just a first counter, or a second counter, but a specific counter — for example, Taylor's counter.”
“Specifying a key tells React to use the key itself as part of the position, instead of their order within the parent.” —— react.dev · Preserving and Resetting State

所以「key 是为了性能」这个说法本末倒置了。key 首先是身份；性能只是身份认对了之后的副产品。官方的比喻很好记：

“Imagine that files on your desktop didn't have names. Instead, you'd refer to them by their order — the first file, the second file, and so on. You could get used to it, but once you delete a file, it would get confusing.” —— react.dev · Rendering Lists

五、用下标当 key 到底会怎样

网上最常见的说法是「用 index 当 key 会有性能问题」。这话轻描淡写得离谱。我实测了一遍：三行列表，每行是一个带自己 state 的子组件（输入框里填了备注），然后删掉第一行。

key 怎么写删掉「苹果」这一行之后，剩下两行的备注
key={item.id}香蕉 = BBB　橘子 = CCC　✅ 正确
key={index}香蕉 = AAA　橘子 = BBB　❌ 整体上移了一格

「苹果」的备注跑到「香蕉」头上去了。不报错、不警告、控制台干干净净。如果这一列是「已勾选」「输入到一半的金额」「上传中的文件」，你就得到了一个会串数据的生产事故。

为什么会串

删掉第一项后，原来的「香蕉」从 index 1 挪到了 index 0。如果 key 就是 index，React 看到的是：位置 0 上还是那个 key 为 0 的组件，没变嘛 —— 于是它保留了位置 0 的 state，只是把 label 这个 prop 换成了「香蕉」。

于是：props 换了，state 没换。屏幕上就是「香蕉」的标题配「苹果」的备注 —— 和第 5 课那个竞态 bug（Bob 的标题配 Alice 的数据）是同一个形状的事故：身份对不上号。

“You might be tempted to use an item's index in the array as its key. In fact, that's what React will use if you don't specify a key at all. But the order in which you render items will change over time if an item is inserted, deleted, or if the array gets reordered. Index as a key often leads to subtle and confusing bugs.”
“Similarly, do not generate keys on the fly, e.g. with key={Math.random()}. This will cause keys to never match up between renders, leading to all your components and DOM being recreated every time. Not only is this slow, but it will also lose any user input inside the list items.” —— react.dev · Rendering Lists

注意第一句里那个信息量很大的事实：不写 key ≡ 用 index 当 key。所以「漏写 key」和「用 index 当 key」是同一个 bug 的两种拼法。

三条规则，官方原文：

“Keys must be unique among siblings. However, it's okay to use the same keys for JSX nodes in different arrays.”
“Keys must not change or that defeats their purpose! Don't generate them while rendering.”
“JSX elements directly inside a map() call always need keys!” —— react.dev · Rendering Lists

那 id 从哪来？数据库主键最理想；纯前端造的数据用一个自增计数器或 crypto.randomUUID()，在「创建这条数据」的那一刻生成一次并存进 state —— 不是在渲染时生成。

六、反过来用：key 是重置按钮

既然 key 决定身份，那么换一个 key 就等于「这是另一个组件了」，React 会丢掉旧 state、重新挂载。这不是黑魔法，是官方推荐的手法。实测：

写法把 name 从 Alice 切到 Bob（此前已点了 2 次）
<Counter name={who} />Bob:2 ← Bob 继承了 Alice 的计数
<Counter key={who} name={who} />Bob:0 ← 干净的新组件

典型用法：一个编辑表单，切换编辑对象时要清空用户输入到一半的内容 —— <EditForm key={userId} ... /> 一行搞定，不需要写一个 useEffect 去手动清空每个字段（这正是「You Might Not Need an Effect」点名的场景之一）。

七、动手

两个终端照旧开着。这一课全程在浏览器里做，盯着页面和 Console，FastAPI 那边不用管。只改 App.tsx。

  1. 先搭一个能出事的列表

    在 App.tsx 里，组件函数外面加一个子组件和一个 id 计数器：

    type Item = { id: number; label: string };

let nextId = 3;                                   // 模块级，不是 state

function Row({ label }: { label: string }) {
  const [note, setNote] = useState("");           // ← 每行有自己的 state
  return (
    <li>
      {label}：<input value={note} onChange={(e) => setNote(e.target.value)} />
    </li>
  );
}

    然后在 App 里加 state，并在按钮下面渲染列表 —— 这一步故意不写 key：

    const [items, setItems] = useState<Item[]>([
  { id: 0, label: "苹果" },
  { id: 1, label: "香蕉" },
  { id: 2, label: "橘子" },
]);

// JSX 里：
<ul>
  {items.map((item) => <Row label={item.label} />)}
</ul>

    保存，看浏览器 Console：

    Each child in a list should have a unique "key" prop.

    再跑 pnpm lint：

    warning react(jsx-key): Missing "key" prop for element in iterator.

    又是 warning，又是退出码 0。和上一课的 exhaustive-deps 一样 —— 记住这条线：第 4 课的 rules-of-hooks 是 error，第 5 课的 exhaustive-deps 是 warning，而第 5 步你会看到更狠的。

  2. 召唤幽灵：mutate 一次，再等它自己冒出来

    加一个按钮，用错误的方式加一行：

    <button onClick={() => {
  items.push({ id: nextId++, label: "新条目 " + nextId });   // ← mutate
  setItems(items);                                          // ← 同一个引用
}}>加一行（错误写法）</button>

    保存前先预测：

    先预测 · 别偷看

    点三下「加一行（错误写法）」，屏幕上什么都没发生。接着去点那个和列表毫无关系的 count 按钮一次 —— 屏幕会怎样？

    三条「新条目」一次性全部出现。
    那三次 push 都真的执行了，数组里早就躺着六项 —— 只是 Object.is 判定引用没变，React 三次都跳过了重渲染。count 变化触发了一次真正的渲染，组件函数重新读那个早已被改烂的数组，积压的变更就全倒出来了。
    如果你预测的是「永远不显示」—— 差之毫厘：mutation 不是丢失，是潜伏。这才是它在真实项目里难查的原因。

    照做：点三下加一行（观察：毫无反应），再点一下 count。盯着那一刻。

    这十秒和上一课「打爆后端」那十秒同等重要。区别是：那次很吵，这次悄无声息。

  3. 改成不可变更新

    把上一步那两行换成一行：

    <button onClick={() => {
  setItems([...items, { id: nextId++, label: "新条目 " + nextId }]);
}}>加一行</button>

    现在每点一下立刻多一行。唯一的变化是「造了个新数组」。

    顺手把 key 补上，Console 的警告消失：

    {items.map((item) => <Row key={item.id} label={item.label} />)}
  4. 制造数据错位事故

    加一个删除按钮，删掉第一行（注意用 slice 而不是 splice）：

    <button onClick={() => setItems(items.slice(1))}>删掉第一行</button>

    现在做这个实验，顺序很重要：

    1. 把 key={item.id} 改成 key={index}（记得把 map 的参数改成 (item, index)）
    2. 刷新页面，在三个输入框里分别填 AAA / BBB / CCC
    3. 点「删掉第一行」

    结果：香蕉那一行的备注变成了 AAA，橘子变成 BBB。数据整体上移了一格 —— 而标题是对的。这就是最难查的那种 bug：一半对一半错。

    改回 key={item.id}，刷新后重复一遍：备注跟着各自的行走，正确。

  5. 让 lint 彻底失守

    再把 key={index} 那个有 bug 的版本改回来一次，跑 pnpm lint：

    （什么都没有）

    零警告。你刚亲眼看到数据错位，而工具链一声不吭 —— 因为默认规则集里没开这条。手动开一次看看：

    pnpm exec oxlint -D react/no-array-index-key src
    error react(no-array-index-key): Usage of Array index in keys is not allowed

    规则存在，只是默认不开。三课下来这条线索完整了 ——
    第 4 课 error（拦得住）→ 第 5 课 warning（提醒你）→ 第 6 课默认不报（全靠你自己）。
    把 key 改回 item.id，确认 pnpm lint 干净。

    面试价值：被问「你们怎么保证代码质量」时，能说出「lint 能拦什么、拦不住什么」，比罗列工具名有说服力得多。

  6. 反过来用 key：一行代码重置一个组件

    给 App 加一个「改名」按钮，整批替换 label，但 id 保持不变：

    <button onClick={() => setItems(items.map((it) => ({ ...it, label: it.label + "*" })))}>
  给每一行改名
</button>

    先在输入框里填点东西，再点它：标题变了，备注还在（id 没变 = 身份没变 = state 保留）。这通常正是你想要的。

    现在把 key 改成 key={item.label}，刷新，重填，再点一次：所有备注被清空。label 变了 → key 变了 → React 认为这是全新的组件 → 旧 state 丢弃。

    把 key 改回 item.id。刚才那两次的差别，就是「什么算同一个东西」的定义权在你手上。

    收尾：pnpm lint 与 pnpm build 零错误；页面上有 Hello from Python、计数按钮、三行可编辑列表。

    你现在拥有的

    你见过一次「改动潜伏、稍后集体爆发」，也见过一次「标题对、数据错」。两件事的根都是同一句话：React 靠身份判断「这还是不是原来那个」—— 对数据来说身份是引用，对组件来说身份是位置（或 key）。

八、检验一下

测验 1 / 5

arr.push(x); setArr(arr) 之后界面没反应，真正的后果是：

push 真的执行了，数组已经变了；只是 Object.is 看到引用没变，React 跳过重渲染。等某个不相干的 state 变化触发渲染，积压的改动一次性全部出现（实测：连 push 两次后点别的按钮 → 屏幕从 a 直接跳到 a,x,x）。
mutation 不是丢失，是潜伏 —— 这才是它难查的原因。React 也不会为此报错：JS 没有任何机制拦得住你改数组。

测验 2 / 5

下面哪一组全都是会 mutate 原数组的方法？

最后一组正好相反 —— concat / slice / map / filter 全部返回新数组，是安全的那一批。
两个高频陷阱：slice 复制、splice 原地改（名字只差一个字母）；sort 和 reverse 是原地的 —— 这一条特别容易被 C# 背景骗到，因为 OrderBy() 返回的是新序列。要排序就先 [...arr] 复制一份。

测验 3 / 5

用数组下标当 key，删掉列表第一项之后会发生：

实测：三行填了 AAA/BBB/CCC，删掉第一行后 香蕉=AAA，橘子=BBB。
因为 key 是 index 时，「位置 0」在 React 眼里始终是同一个组件 —— 它保留 state，只换 props。于是标题是新的、state 是旧的。
「只是性能问题」是流传最广的误解。官方的措辞是 “Index as a key often leads to subtle and confusing bugs”。另外要记住：完全不写 key，React 用的就是 index —— 两者是同一个 bug。

测验 4 / 5

React 判断「这还是不是原来那个组件」，依据是：

官方原话：“the state is actually held inside React… by where that component sits in the render tree.” 而 key 的作用是 “use the key itself as part of the position” —— 它改写位置的定义。
这一条和 C# 差得最远：C# 里对象身份就是引用，React 里根本没有「组件实例」这个东西可抓（第 4 课：组件只是每次渲染被重新调用的函数）。
推论：同一位置、key 不变 → state 保留；key 变了 → 旧 state 丢弃、重新挂载。这就是「用 key 重置组件」的全部原理。

测验 5 / 5

下面哪一种 mutation 是官方明确认可的？

叫 local mutation：“Mutating an object you've just created is okay because no other code references it yet.” 所以 const next = [...items]; next.sort(f); setItems(next); 完全合法。
规则不是「禁止一切 mutation」，而是「禁止改已经在 state 里的那个对象」。
第二个选项是最常见的错误直觉：setItems(items) 传的还是同一个引用，Object.is 判相等 → 直接跳过重渲染，调不调 setState 都一样。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒：
（1）你点了三下「加一行」都没反应，然后点了个不相干的按钮，三行一起冒出来了 —— 完整解释这个过程；
（2）「index 当 key 只是性能问题」错在哪？用你第 4 步看到的现象讲；
（3）为什么 <Form key={userId} /> 能在切换用户时清空表单？

(1) push 真的改了数组，但 setItems(items) 传的是同一个引用，Object.is 判「没变」→ React 跳过重渲染（这是第 5 课那条 bail-out 规则的第三次现身）。数组内容已经是新的，屏幕停在旧帧。count 变化触发真渲染时，组件函数读到那个早已被改烂的数组 → 积压的改动一次性显现。mutation 不是丢失，是潜伏。

(2) state 不住在组件里，住在 React 里，按位置索引。key 是 index 时，删掉第一项后「位置 0」在 React 眼里没变 → 保留 state、只换 props → 标题是香蕉、备注还是苹果的。这不是重绘开销，是静默的数据错位，而且默认的 lint 完全不报。

(3) key 参与构成「位置」。userId 变了 → key 变了 → React 认定这是另一个组件 → 卸载旧的（连同它全部 state）、挂载新的。所以不需要写 useEffect 去逐个字段清空 —— 那正是「You Might Not Need an Effect」点名的反模式。

九、面试回答模板

如果面试官问：“为什么 React 要求不可变更新？” / “key 是干什么的？为什么不能用 index？”

“两个问题其实是一个：React 靠『身份』判断东西变没变，而不是靠内容。
对数据来说，身份就是引用。Object.is 是浅比较，所以 arr.push(x) 之后再 setArr(arr)，React 看到同一个引用，直接跳过重渲染。我踩过这个坑，它最坑的地方不是『不更新』 —— 那次 push 是真的生效了，只是屏幕没跟上；等某个不相干的 state 一变，积压的改动会一次性全部冒出来。所以症状是『点了没反应，后来一堆东西突然全变了』，很难查。正确写法是 [...arr, x]；顺带一提 slice 是复制、splice 是原地改，sort 和 reverse 也是原地的，要先复制。不过 local mutation 是允许的 —— 改自己刚复制出来、还没交给别人的对象完全没问题。
对组件来说，身份是位置。state 其实不存在组件里，是 React 按组件在渲染树里的位置存着的；key 的作用是把 key 本身变成位置的一部分。所以用 index 当 key 不是『性能问题』这么轻 —— 删掉第一项之后，React 认为『位置 0』还是同一个组件，于是保留 state、只换 props，结果是标题对、数据错。我实测过：三行备注填 AAA/BBB/CCC，删掉第一行后备注整体上移一格，控制台一声不吭，默认 lint 也不报。
反过来这一点还能主动用：<EditForm key={userId} />，切换用户时表单自动重置，不用写 Effect 手动清字段。”

三个分水岭句子：「mutation 不是丢失，是潜伏」、「保留 state、只换 props」、「key 可以反过来当重置按钮用」。第一句证明你真调试过，第二句说明你懂机制而不是背结论，第三句说明你会用它解决问题。
