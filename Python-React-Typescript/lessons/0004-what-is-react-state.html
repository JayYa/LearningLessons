Lesson 0004 · 约 45 分钟

React 的状态到底是什么

三课下来你一直在用 useState，却没人告诉你它凭什么工作。该还债了。

本课的收获

一句能解释掉 React 大半「诡异行为」的话：每一次渲染都是你的组件函数的一次独立调用，state 在那一次调用里是一个不会变的常量。 做完之后，这三件事你都能讲出原因：为什么连写三次 setCount(count + 1) 只加一；为什么 setTimeout 里读到的是旧值；为什么 hook 不能写在 if 里。

一、组件是函数，渲染是一次调用

先把最底层的模型摆正，后面所有反直觉的现象都是它的推论。

你熟悉的世界

WinForms / WPF 是命令式的：控件是一个长期存活的对象，你抓住它去改属性 —— label.Text = "hi"。对象在，你改它，界面跟着变。
React 是反过来的。你的组件是一个函数，它接收当前 state，返回一段「界面应该长什么样」的描述。你永远不去改界面，你改 state，然后 React 重新调用你的函数，拿到一份新描述，自己去算差异并更新 DOM。
写成一个式子：UI = f(state)。这就是「声明式 vs 命令式」，是 React 面试题里最常见的第一问。

关键推论：你的组件函数会被调用很多次。第一次渲染调一次，每次 state 变化再调一次。每一次调用，函数体从头到尾重新执行一遍，里面的局部变量全部重新创建。

二、为什么普通变量不够用

既然函数每次都重新跑，用一个普通的 let 存计数为什么不行？官方文档给了两条理由，请分开记，它们是两个独立的问题：

“Local variables don't persist between renders. When React renders this component a second time, it renders it from scratch—it doesn't consider any changes to the local variables.”
“Changes to local variables won't trigger renders. React doesn't realize it needs to render the component again with the new data.” —— react.dev · State: A Component's Memory

一个是保存不住，一个是叫不醒。useState 正好一次给你这两样：

你拿到的解决哪个问题
count（state 变量）Retain —— 跨渲染保住数据。React 替你存着，函数重跑时再交还给你。
setCount（setter）Trigger —— 更新数据并且通知 React「该重新调用这个函数了」。

第一步动手你会亲手撞一次「叫不醒」：变量的值确实变了，界面纹丝不动。

三、快照：本课的核心

现在看这段代码。它是本课全部难度的所在：

const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}

点一下，count 只加 1。原因简单得让人不适应：

“Setting state only changes it for the next render.”
“A state variable's value never changes within a render, even if its event handler's code is asynchronous.” —— react.dev · State as a Snapshot

count 是一个 const。在这一次渲染里它就是 0，谁也改不了它。所以那三行其实是：

setCount(0 + 1);
setCount(0 + 1);
setCount(0 + 1);   // 三句一模一样
这里要停一下 —— 和 C# 的闭包正好相反

C# 的 lambda 捕获的是变量，所以变量之后变了，lambda 看到的也跟着变：

int n = 0;
Action a = () => Console.WriteLine(n);
n = 5;
a();   // 打印 5 —— 捕获的是变量，不是值

React 里，每一次渲染都产生全新的一批 const。这次渲染创建的事件处理函数，捕获的是这一次的那个 count —— 它是个常量，永远不会变成别的值。
所以两边的「闭包陷阱」方向恰好相反：C# 的坑是「捕获的变量偷偷变了」，React 的坑是「捕获的值顽固地不变」。把这句说给面试官听，比背「state 是异步的」有说服力得多 —— 顺带一提，「异步」是个坏解释：就算你等上三秒再读，读到的还是那个旧值，因为它压根不是同一个变量。

那么需要连续累加时怎么办？传函数而不是值：

setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);   // 这次真的加 3
“Here, a => a + 1 is your updater function. It takes the pending state and calculates the next state from it.” —— react.dev · useState 参考

差别在于「谁来提供上一个值」：传值时，是你在这次渲染的快照里算；传函数时，是 React 在处理队列时把上一个结果喂给你。判断标准就一句：新值要依赖旧值 → 用函数形式；不依赖 → 直接传值。

四、hook 为什么不能写在 if 里

这个问题的答案，比大多数人以为的要朴素得多。看官方文档怎么说 React 内部是怎么存 state 的：

“Internally, React holds an array of state pairs for every component. It also maintains the current pair index, which is set to 0 before rendering. Each time you call useState, React gives you the next state pair and increments the index.”
“Hooks rely on a stable call order on every render of the same component.” —— react.dev · State: A Component's Memory

把这句话的分量掂清楚：const [count, setCount] = ... 里的名字 count，React 完全不知道。 它只知道「这是本次渲染的第 0 个 hook」。名字是你写给自己看的，配对靠的是顺序。

现在把第二个 useState 包进 if：某次条件为假，它没被调用，于是 useEffect 变成了第 1 个 hook —— 它会去拿 slot[1]，也就是字符串 state 的格子。整排数据错位一格。

对照 C#

C# 的字段靠名字绑定，编译期就定死了，怎么写都不会错位。React 的 state 靠调用顺序绑定，运行期才确定 —— 这是用「语法极简」换来的，代价就是必须有一条纪律性的规则来兜底：

“Don't call Hooks inside loops, conditions, nested functions, or try/catch/finally blocks. Instead, always use Hooks at the top level of your React function, before any early returns.” —— react.dev · Rules of Hooks

注意那句 before any early returns —— 提前 return 和写在 if 里是同一个错误，这一条最容易被忽略。

你有两道防线会拦住这个错误，动手环节会把两道都触发一次：lint 在写代码时拦，React 在运行时拦。React 之所以拦得住，正是因为它数得出 hook 的个数。

五、动手

两个终端开着（fastapi dev 与 pnpm dev）。全程只改 App.tsx。

  1. 先用普通变量，撞一次「叫不醒」

    在 App.tsx 里加一个计数器按钮，故意用 let：

    export default function App() {
  const [message, setMessage] = useState("加载中…");
  let count = 0;                          // ← 一个普通变量

  useEffect(() => { /* …原样不动… */ }, []);

  return (
    <>
      <h1>{message}</h1>
      <button onClick={() => { count = count + 1; console.log("count =", count); }}>
        count: {count}
      </button>
    </>
  );
}

    连点五下。Console 里数字在涨，按钮上的数字一直是 0。

    变量确实变了 —— 只是没有人重新调用这个函数，界面就还是上一次调用留下的那份。这就是「叫不醒」。

    （顺手还一笔债：<>...</> 是 Fragment。JSX 必须返回单个根节点，Fragment 是一个不会产生真实 DOM 元素的空壳包装，专门用来满足这条规定。）

  2. 换成 state，但一次点三下

    把 let count = 0; 换成 state，并让点击连续调用三次：

    const [count, setCount] = useState(0);

// button 的 onClick 改成：
onClick={() => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}}

    先预测 · 别偷看

    从 0 开始，点一次按钮之后，界面上的数字会变成几？写下来再点击。

    1。这次渲染里 count 是 0，三句话都是 setCount(1)。
    如果你预测的是 3 —— 很好，这个错误值钱：你刚刚把 C# 的「变量」直觉套到了 React 的「快照」上，而这正是本课要拆掉的那个直觉。

  3. 用 updater 修好它

    三句改成函数形式：

    onClick={() => {
  setCount(c => c + 1);
  setCount(c => c + 1);
  setCount(c => c + 1);
}}

    点一次，数字跳到 3。同样是三次调用，同样在一次点击里，结果不同 —— 差别只在于「上一个值由谁提供」。

  4. 直接看见快照

    把 onClick 临时改成：

    onClick={() => {
  setCount(c => c + 1);
  setTimeout(() => console.log("3 秒后我看到的 count =", count), 3000);
}}

    点一下，然后立刻再连点四下。等三秒，看 Console。

    第一条打印的不是 5，而是 0 —— 你按第一下时那次渲染的值。后面几条依次是 1、2、3、4。每一条都停在自己那次渲染的快照上。

    这就是为什么「state 更新是异步的」是个糟糕的解释：等待并不会让你读到新值，因为你手里的根本不是同一个变量。看完把 setTimeout 那行删掉。

  5. 把 hook 塞进 if，触发两道防线

    在组件里加上这段明知故犯的代码：

    if (count > 2) {
  const [extra] = useState("boom");
  console.log(extra);
}

    第一道防线 —— 另开一个终端跑 pnpm lint：

    error react-hooks(rules-of-hooks): React Hook "useState" is called
conditionally. React Hooks must be called in the exact same order in
every component render.

    第二道防线 —— 无视它，回到浏览器把数字点过 2。页面炸掉，Console 里是：

    Error: Rendered more hooks than during the previous render.

    （反过来，如果 hook 是被提前 return 跳过的，你会看到另一条：Rendered fewer hooks than expected. This may be caused by an accidental early return statement.）

    请把这两条报错读进去：React 说的是「比上次多／少」—— 它在数个数。这就是第四节那个 array + index 机制留在报错信息里的指纹。看完把这段删掉。

  6. 收尾

    保留第 3 步的 updater 版本计数器，确认页面正常：Hello from Python + 一个能加 3 的按钮。pnpm lint 与 pnpm build 都应零错误。

    你现在拥有的

    一个能讲清楚为什么的心智模型，而不只是「useState 会更新界面」。你亲手制造并观察了三个现象：变量改了界面不动、三次加一、三秒后读到旧值 —— 它们全部是同一句话的推论。

六、检验一下

测验 1 / 4

连写三次 setCount(count + 1) 却只加了 1，根本原因是？

不是「合并」，也不是「异步」—— 三次调用全都发生了，只是三次都在说同一句话：「把 state 设成 1」。count 在这次渲染里是个 const，值为 0，三行代码里的 count + 1 算出的都是 1。
「异步」这个解释之所以特别糟，是因为它暗示「等一等就能读到新值」—— 第 4 步的 setTimeout 实验已经证伪了这一点。

测验 2 / 4

hook 不能写在 if 里，是因为 React 内部：

React 维护一个数组和一个游标，每调用一次 hook 就取下一格并把游标 +1。名字对它毫无意义。少调用一次，后面所有 hook 集体错位一格。
报错信息本身就是证据：Rendered more hooks than during the previous render —— 它在数个数。
顺带记住那条容易漏的：提前 return 之后再调 hook，和写在 if 里是同一个错误。

测验 3 / 4

点击后 setTimeout 延迟三秒打印 count，打印出的是：

每次渲染都创建了新的一批 const 和新的一批闭包。那个 setTimeout 回调是「第 N 次渲染」创建的，它捕获的就是第 N 次渲染的 count，一个常量。时间流逝不会改变一个常量。
连点五下会得到 0、1、2、3、4 —— 五个回调，五份互不相干的快照。

测验 4 / 4

什么时候必须写 setCount(c => c + 1) 而不是传值？

判断标准只有一条：下一个值依不依赖上一个值。依赖就用函数形式，让 React 在处理队列时把最新的中间结果喂给你；不依赖（比如 setMessage(result.data.message)，值来自外部）就直接传值，没必要绕。
最后一个选项是陷阱：两种写法都会触发重新渲染，那不是它们的区别。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒：
（1）「渲染是一张快照」这句话，用第 4 步那个 setTimeout 实验讲一遍；
（2）hook 不能写在 if 里，讲到 React 内部的数据结构为止；
（3）第 2 课的类型擦除和这一课的快照，有没有共同点？

(1) 组件是函数，每次渲染是一次独立调用，函数里的 const 每次都是新的一批。事件处理函数和定时器回调都是那一次渲染创建的闭包，捕获的是那一次的常量。所以连点五下，五个回调各自打印 0、1、2、3、4 —— 时间过去多久都不会变，因为它压根不是同一个变量。

(2) React 为每个组件维护一个 state 数组和一个游标，游标每次渲染前归零，每调用一个 hook 就取下一格并 +1。配对靠顺序，不靠名字。写在 if 里会导致某次渲染的 hook 数量变化，后面所有 hook 错位一格。报错说的是「比上次多/少了 hook」，因为它在数个数。

(3) 两课都在说：你写的代码和真正在跑的东西之间，隔着一层你必须知道的转换。类型擦除是「你写的类型编译后不存在了」；快照是「你写的 count 不是一个会变的变量，而是每次调用重新绑定的常量」。
两次都是同一个教训：把 C# 的直觉直接搬过来，会在运行时被打脸。

七、面试回答模板

如果面试官问：“React 的状态是怎么管理的？” / “hooks 是什么？”

“核心模型是 UI = f(state)：组件是个函数，每次渲染就是把它重新调用一遍，我不去改 DOM，我改 state 让 React 重新调用。这和 WPF 那种抓住控件对象改属性的命令式写法是相反的。
普通变量不行有两个原因 —— 跨渲染保不住，而且改了不会触发重新渲染。useState 正好给这两样。
最容易踩的坑是 state 是快照：一次渲染里 state 是常量，所以连写三次 setCount(count + 1) 只会加一。我自己试过用 setTimeout 延迟三秒去读，读到的还是点击那一刻的值 —— 所以说它「异步」是不准确的，它是每次渲染各自绑定的常量。要连续累加就得用 updater 形式 setCount(c => c + 1)，让 React 把上一个结果喂进来。
至于 hooks 为什么不能写在条件里 —— React 内部是一个 state 数组加一个游标，靠调用顺序配对，不靠变量名。少调一次后面全部错位，所以它的报错是『比上次多/少了 hook』。这条规则不是风格约定，是数据结构决定的。”

最后那句是分水岭。大多数人答到「这是 hooks 的规则」就停了；能说出「因为内部是数组 + 游标」的，面试官知道你读过或调试过，而不只是背过规则。

八、去读原始资料

本课首选阅读：react.dev · State as a Snapshot（约 10 分钟）。官方文档里写得最好的一篇，配有可交互的例子，把你刚才手动做的实验又做了一遍。读完顺手看下一页 Queueing a Series of State Updates，它画出了 updater 函数在队列里被逐个执行的过程。

规则那一侧：react.dev · Rules of Hooks（约 5 分钟）。很短，但那张「哪些地方不能调用」的清单值得逐条过一遍 —— try/catch 里也不行这一条，多数人不知道。

如果还有余力：react.dev · useState 参考的 Caveats 小节。里面有一条本课没展开、但迟早会咬你的：如果新值经 Object.is 判定与当前 state 相同，React 会跳过这次重新渲染 —— 这正是为什么直接 arr.push(x) 再 setArr(arr) 界面不动（同一个对象引用），必须传新数组。
