Lesson 0008 · 约 60 分钟

state 该住在哪里

你的 App.tsx 现在是一个函数里挤了四件事。这一课把它拆开 —— 而拆组件这件事本身有一个致命且完全静默的陷阱：一个位置放错的 function，会让子组件的 state 在每次父组件渲染时全部清零、连光标都跳走，而代码看起来完全正常。

本课的收获

做完之后，你的 App.tsx 会变成三个组件，并且能解释四件事：state 应该住在哪个组件里（lifting state up 的判定规则）；为什么「把数据传下去」和「把回调传下去」是同一件事的两半；为什么组件定义绝不能嵌套；以及 prop drilling 到底该不该用 context 解决（官方的答案可能和你想的不一样）。收尾时 Mantine 进场，页面第一次不难看。

一、拆组件的两个方向

组件之间只有两条通道，而且都是 props：

<NoteForm /* 数据向下 */ disabled={busy}
          /* 事件向上 */ onCreated={handleCreated} />

第二条通道没有任何新语法 —— 函数也是值，把它当 prop 传下去而已。子组件不知道父组件是谁，它只知道「出事了我就调用手上这个函数」。数据向下流，事件向上冒，这就是 React 单向数据流的全部。

C# 参照物：这是 Action<T>，不是 event

C# 里子控件通知父级用 event EventHandler：父级 += 订阅，可以有多个订阅者，解绑要记得 -=。

React 里没有订阅、没有解绑、没有多播。onCreated: (note: Note) => void 就是一个 Action<Note> 字段，每次渲染重新传一个进去。命名约定要记住（面试会看）：prop 叫 onXxx，实现它的函数叫 handleXxx。Blazor 的 EventCallback<T> 其实更接近 React 的写法 —— 如果面试官问过 Blazor，这是个能拿分的类比。

二、state 该住在哪 —— 官方的三步法

你的 Row 组件现在有一个自己的 note state。父组件读不到它。如果 App 想显示「已填备注 2 / 3 行」，做不到 —— 数据在孩子手里。这就是那个信号：

“Sometimes, you want the state of two components to always change together. To do it, remove state from both of them, move it to their closest common parent, and then pass it down to them via props. This is known as lifting state up, and it’s one of the most common things you will do writing React code.” —— react.dev · Sharing State Between Components

官方给的是一套机械可执行的步骤，不是感觉：

“1. Remove state from the child components. 2. Pass hardcoded data from the common parent. 3. Add state to the common parent and pass it down together with the event handlers.” —— react.dev · Sharing State Between Components

注意第 2 步：先传写死的数据，跑通，再加 state。这一步看起来多余，实际上它把「结构对不对」和「状态对不对」拆成了两个可以分别调试的问题。

“For each unique piece of state, you will choose the component that ‘owns’ it. This principle is also known as having a ‘single source of truth’. It doesn’t mean that all state lives in one place—but that for each piece of state, there is a specific component that holds that piece of information.” —— react.dev · Sharing State Between Components
「所有 state 都放最上面」是错的

读到「single source of truth」很容易得出「那我全放 App 里最安全」。不对：state 放得越高，重渲染的范围越大，中间层要转发的 props 越多，组件越不可复用。规则是「最近的共同父级」，不是「最高的父级」。提得太高和放得太低都是错误，只是后者报错、前者不报错 —— 所以前者更常见。

三、同一个词的两个层面：controlled

第 7 课你学过：<input value onChange> 叫受控组件。现在官方在组件这个层面又用了同一个词：

“It is common to call a component with some local state ‘uncontrolled’. … In contrast, you might say a component is ‘controlled’ when the important information in it is driven by props rather than its own local state. … Uncontrolled components are easier to use within their parents because they require less configuration. But they’re less flexible when you want to coordinate them together. Controlled components are maximally flexible, but they require the parent components to fully configure them with props.” —— react.dev · Sharing State Between Components

这不是两个概念，是同一个概念的两个尺度：「这个东西的真相在自己肚子里，还是在别人手上？」`` 是它的最小实例，你的 Row 是它的组件级实例。

而这段话真正的价值是最后一句 —— 它明确说了 uncontrolled 不是坏事。「用起来省事」是真实收益。所以判定规则是：

一句话判定

只有一个组件关心这份数据 → 留在它自己肚子里（uncontrolled，省事）。
两个以上组件必须一起变 → 提到最近的共同父级（controlled，灵活）。
不确定的时候先放低，等到真的有第二个人要用再提上去 —— 提升很容易，下沉很痛苦。

四、绝不要在组件里定义组件

这是本课的核心机关，也是新手拆组件时最容易踩、最难自己看出来的一个。官方的措辞异常强硬：

“Components can render other components, but you must never nest their definitions: … 🔴 Never define a component inside another component! The snippet above is very slow and causes bugs.” —— react.dev · Your First Component

原因你在第 6 课已经有一半的答案了 —— React 靠位置 + 类型判定组件身份：

“Every time you click the button, the input state disappears! This is because a different MyTextField function is created for every render of MyComponent. You’re rendering a different component in the same position, so React resets all state below.” —— react.dev · Preserving and Resetting State

位置没变，类型变了 —— 因为 function 每次渲染都是一个新的函数对象。又是 Object.is 的引用比较（第 4、5、6 课那位老朋友），这次比的是组件函数本身。

我实测过一次（React 19.2.8 + jsdom，父组件渲染一次，子组件里有个输入框）：

// 版本 A：Child 定义在 Parent 内部
A 打字后输入框里是: "hello"
A 父组件渲染一次后: ""   mounts = 2      ← 内容没了，而且组件重新挂载了一次

// 版本 B：Child 提到外面（唯一的差别）
B 父组件渲染一次后: "hello"  mounts = 1

// 版本 A 里那个 DOM 节点本身：
C 父渲染后 DOM 节点还是同一个吗? false  | 还有焦点吗? false
这个 bug 在真实项目里长什么样

不是「报错」，是用户投诉：「我打字打到一半光标自己跳出去了」、「下拉框刚展开就收起来了」、「滚动位置每次都被重置」。因为整棵子树连同真实 DOM 节点被销毁重建了 —— 焦点、滚动、动画、CSS 过渡，全部归零。

而且它随父组件渲染频率放大：父组件里有个受控输入框的话，你每敲一个字符就重建一次整棵子树。官方说的 “very slow” 是字面意思。

好消息：这条 lint 抓得住

实测 oxlint 1.80（就是 pnpm lint 用的那个，playground 的默认配置即可触发）：
warning react(static-components): Cannot create components during render  help: Components created during render will reset their state each time they are created. Declare components outside of render
注意仍是 warning，退出码 0 —— pnpm lint 照样「通过」。要养成读 warning 的习惯，不要只看退出码。

五、prop drilling：官方叫你先别上 context

拆完组件，一个新烦恼会出现：数据在最上面，用它的组件在最下面，中间几层什么都不干，只负责转发。

“But passing props can become verbose and inconvenient when you need to pass some prop deeply through the tree, or if many components need the same prop. … lifting state up that high can lead to a situation called ‘prop drilling’.” —— react.dev · Passing Data Deeply with Context

标准答案是 useContext。但官方对此的态度值得逐字读 —— 这才是能让你在面试里显得有判断力的部分：

“Context is very tempting to use! However, this also means it’s too easy to overuse it. Just because you need to pass some props several levels deep doesn’t mean you should put that information into context.”
“1. Start by passing props. If your components are not trivial, it’s not unusual to pass a dozen props down through a dozen components. It may feel like a slog, but it makes it very clear which components use which data!”
“2. Extract components and pass JSX as children to them. If you pass some data through many layers of intermediate components that don’t use that data …, this often means that you forgot to extract some components along the way. … Instead, make Layout take children as a prop, and render <Layout><Posts posts={posts} /></Layout>.” —— react.dev · Passing Data Deeply with Context

第 2 条是大多数人不知道的那一条，而且它很反直觉：prop drilling 常常不是「层数太多」的问题，是「组件切错了」的问题。把中间层改成接 children，转发链直接消失 —— 数据从提供它的组件直接给到用它的组件，中间层根本不经手。

C# 参照物：children ≈ RenderFragment；context ≈ 一个作用域受限的 DI 容器

children 就是 Blazor 的 RenderFragment ChildContent：把一段「待渲染的东西」当参数传进去。在 React 里它没有任何特殊之处 —— <Card>里面这些</Card> 只是 props.children 的语法糖。

context 则很像 ASP.NET Core 的依赖注入：上面注册一次，下面任意深度直接取，中间层不用知道。裂缝：DI 容器是全应用一份、按类型解析；context 是按组件树位置解析的 —— 同一个 context 可以在树的不同分支里提供不同的值（嵌套 provider）。另一条裂缝更重要：DI 让依赖关系变隐式在 C# 里是常态，在 React 里官方明确把它列为「最后手段」，因为它同时也让 谁用了这份数据 变得不可见。

六、组件库进场

你从第 1 课到现在没写过一行 CSS，页面也确实很难看。现在是换渲染层成本最低的一刻 —— 因为组件刚刚拆好，替换是局部的。

本课程选 Mantine（v9.5.2 实测）。而它的安装步骤里藏着一个刚好呼应上一节的东西：

<MantineProvider>
  <App />
</MantineProvider>

这就是 context。我翻了它的源码，是字面意义上的：

// @mantine/core/src/core/MantineProvider/Mantine.context.ts
export const MantineContext = createContext<MantineContextValue | null>(null);

export function useMantineContext() {
  const ctx = use(MantineContext);
  if (!ctx) throw new Error(
    '[@mantine/core] MantineProvider was not found in tree');
  return ctx;
}

主题正是官方列出的 context 头号用例（“Theming: If your app lets the user change its appearance …”）。你今天不用写 createContext，但你会用一个真实的 context，并且亲手把它拆掉看报错 —— 这比先学语法再找用途要牢得多。

七、动手

两个终端照旧：后端 uvicorn，前端 pnpm dev。这一课不碰后端，main.py 一行都不用改。

  1. 先补一个 fetchNotes，让列表有真数据

    api.ts 末尾加（Note schema 已经有了，直接复用）：

    export async function fetchNotes() {
  const res = await fetch("http://127.0.0.1:8000/api/notes");
  if (!res.ok) return { ok: false as const, message: `HTTP ${res.status}` };
  const json: unknown = await res.json();
  const parsed = z.array(Note).safeParse(json);          // ← 数组也要校验
  if (!parsed.success) return { ok: false as const, message: z.prettifyError(parsed.error) };
  return { ok: true as const, notes: parsed.data };
}

    注意 z.array(Note)：后端返回的是列表，schema 也得是列表。第 3 课那句「边界上的东西都要 parse」在这里再兑现一次。

  2. 把表单整个搬出去 —— 数据向下，回调向上

    在 App.tsx 底部（App 函数外面）新建组件，把 title / body / status 三个 state 和 handleSubmit 整段剪切进去：

    function NoteForm({ onCreated }: { onCreated: (note: Note) => void }) {
  const [title, setTitle] = useState("");
  const [body, setBody] = useState("");
  const [status, setStatus] = useState<Status>({ kind: "idle" });

  async function handleSubmit(e: FormEvent<HTMLFormElement>) {
    /* …原样搬过来… */
    if (result.ok) {
      setStatus({ kind: "success", note: result.note });
      setTitle(""); setBody("");
      onCreated(result.note);                  // ← 唯一的新代码：向上通知一声
    } else { setStatus({ kind: "error", message: result.message }); }
  }
  return ( /* …原来那段 <form>… */ );
}

    type Status 也一并移到 App 外面（它现在只服务于 NoteForm）。然后 App 里：

    const [notes, setNotes] = useState<Note[]>([]);

useEffect(() => {
  let ignore = false;
  fetchNotes().then((r) => { if (!ignore && r.ok) setNotes(r.notes); });
  return () => { ignore = true; };
}, []);                                        // 第 5 课那套，原样复用

// JSX：
<NoteForm onCreated={(note) => setNotes([...notes, note])} />   // 不可变更新（第 6 课）
<ul>{notes.map((n) => <li key={n.id}>{n.title} —— {n.body}</li>)}</ul>

    验一下：提交一条 → 列表立刻多一行；刷新页面 → 它还在（来自后端）。NoteForm 完全不知道 App 拿这条笔记去干什么 —— 它只负责喊一声。这就是可复用组件的样子。

  3. 先预测，再把 NoteForm 挪进 App 里

    现在故意犯那个错：把 function NoteForm(...) 整个剪切到 App 函数体内部（放在 return 之前）。代码逻辑一个字不改，只改位置。

    先预测 · 别偷看

    保存后，在标题框里打字 —— 但记住 App 里还有那个 count 按钮。先在表单里填半句话，然后点一下 count 按钮，会发生什么？光标呢？

    表单里的字全没了，光标也跳走了。点 count → App 重渲染 → function NoteForm 被重新创建成一个新函数 → 同一个位置上换了「不同的组件类型」→ React 卸载整棵子树再重新挂载，title/body/status 三个 state 全部回到初始值，真实 DOM 节点被销毁重建，焦点随之丢失。
    实测数据：mounts = 2（挪出去则是 1）、DOM 节点还是同一个吗? false、还有焦点吗? false。
    没有任何报错。如果你预测的是「没区别，反正逻辑一样」—— 这正是它可怕的地方：JS 语法上完全合法，React 语义上是另一个组件。

    照做，亲眼看一次。然后跑 pnpm lint，找到那行 react(static-components)，再看一眼退出码是 0。把 NoteForm 挪回 App 外面。

  4. lifting state up：让 App 知道有几行填了备注

    按官方三步法改造第 6 课那个 Row（它现在是 uncontrolled 的 —— 备注锁在它自己肚子里）。

    第 1 步，删：去掉 Row 里的 useState。第 2 步，父级传写死的值先跑通。第 3 步，把 state 加到 App 并连同回调传下去：

    function Row({ label, note, onNoteChange }: {
  label: string; note: string; onNoteChange: (v: string) => void;
}) {
  return <li>{label}：<input value={note} onChange={(e) => onNoteChange(e.target.value)} /></li>;
}

// App 里：
const [rowNotes, setRowNotes] = useState<Record<number, string>>({});
// …
{items.map((item) => (
  <Row key={item.id} label={item.label}
       note={rowNotes[item.id] ?? ""}
       onNoteChange={(v) => setRowNotes({ ...rowNotes, [item.id]: v })} />
))}
<p>已填备注 {Object.values(rowNotes).filter((v) => v !== "").length} / {items.length} 行</p>

    现在 App 能读到备注了 —— 这是刚才做不到的事。注意三处旧知识在这里合流：{ ...rowNotes, [item.id]: v } 是不可变更新（第 6 课），?? "" 保证输入框永远受控（第 7 课，给 undefined 会触发 “changing an uncontrolled input to be controlled” 警告），key={item.id} 仍然管着组件身份（第 6 课）。

    顺手感受一下代价：Row 从 2 个 props 变成了 3 个，而且父组件必须替它管状态。这就是官方说的「controlled 更灵活，但要父级完全配置它」。如果 App 根本不需要这个数字，刚才那一步就是纯亏损。

  5. 装 Mantine，并亲手拆掉它的 context

    前端目录下（四条命令，注意第二条是 -D）：

    pnpm add @mantine/core @mantine/hooks
pnpm add -D postcss postcss-preset-mantine postcss-simple-vars

    新建 frontend/postcss.config.cjs（扩展名必须是 .cjs，因为 package.json 里是 "type": "module"）：

    module.exports = {
  plugins: {
    'postcss-preset-mantine': {},
    'postcss-simple-vars': {
      variables: {
        'mantine-breakpoint-xs': '36em', 'mantine-breakpoint-sm': '48em',
        'mantine-breakpoint-md': '62em', 'mantine-breakpoint-lg': '75em',
        'mantine-breakpoint-xl': '88em',
      },
    },
  },

    src/main.tsx：

    import "@mantine/core/styles.css";            // 必须在自己的样式之前
import { MantineProvider } from "@mantine/core";

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <MantineProvider><App /></MantineProvider>
  </StrictMode>,

    然后把 NoteForm 的 JSX 换掉（App.css / index.css 里自带的样式建议先清空）：

    import { Alert, Button, Card, Group, List, Stack, TextInput, Textarea, Title } from "@mantine/core";

<Card withBorder shadow="sm" radius="md" p="md">
  <form onSubmit={handleSubmit}>
    <TextInput label="标题" value={title} onChange={(e) => setTitle(e.currentTarget.value)} />
    <Textarea label="内容" mt="sm" value={body} onChange={(e) => setBody(e.currentTarget.value)} />
    <Group mt="md">
      <Button type="submit" loading={status.kind === "submitting"}>提交</Button>

  </form>

    关键观察：受控组件那一套一个字没变 —— value + onChange 照旧，Status union 照旧，只是 disabled 换成了更好看的 loading。组件库换的是渲染层，不是你的状态模型。这也是为什么先拆组件、后换 UI 是正确顺序。

    现在拆掉 context：把 <MantineProvider> 那两个标签删掉，保存，看页面。

    Error: @mantine/core: MantineProvider was not found in component tree,
       make sure you have it in your app

    这就是 context 缺失时的样子：不是「样式丢了」，是组件直接抛异常，因为 useMantineContext() 拿到了 null。加回去。顺带一提：主题这件事如果用 props 传，你得给树上每一个组件传一遍 —— 这正是官方 context 用例清单的第一条。

  6. 收尾：看一眼组件库的价码

    pnpm lint（读 warning，不只看退出码）与 pnpm build。对比我实测的两组数字：

    // 空的 Vite react-ts 模板
dist/assets/index.js   193.28 kB │ gzip: 60.63 kB
dist/assets/index.css    4.10 kB │ gzip:  1.47 kB

// 加上 Mantine，用了 9 个组件
dist/assets/index.js   269.15 kB │ gzip: 82.63 kB   ← +76 kB
dist/assets/index.css  231.22 kB │ gzip: 33.80 kB   ← +227 kB (!)

    JS 只涨了 76 kB，CSS 涨了 227 kB。为什么不对称？因为 JS 走 ES module，打包器能 tree-shake 掉你没 import 的组件；而 styles.css 是一整个文件，你 import 了它就全都进来了（Mantine 也提供按组件拆分的 CSS 入口，这里不展开）。

    「引入一个组件库要付什么代价」是很实在的面试题，能说出这个不对称、并说出原因是 tree-shaking 只对 ESM 有效，比说「体积会变大」强得多。

    你现在拥有的

    App.tsx 从一个四合一的大函数变成了 App（拥有 notes）+ NoteForm（拥有提交状态）+ Row（什么都不拥有）：每份 state 都有明确的归属，数据向下、事件向上，一条链都没断。这是「组件化」这个词落到实处的样子 —— 而且你亲手见过它坏掉时是什么样。

测验 2 / 5

「single source of truth」这条原则，正确的做法是：

官方特意澄清过：“It doesn’t mean that all state lives in one place—but that for each piece of state, there is a specific component that holds that piece of information.”
关键词是 closest common parent（最近的共同父级），不是最高的。提得太高的代价：重渲染范围变大、中间层被迫转发、组件不可复用 —— 而且不报错，所以比放得太低更常见。

测验 3 / 5

React 官方对「prop drilling 太烦了，上 context 吧」的态度是：

原话：“Just because you need to pass some props several levels deep doesn’t mean you should put that information into context.” 甚至说 “it’s not unusual to pass a dozen props down through a dozen components… it makes it very clear which components use which data!”
第二个替代方案是多数人不知道的那个：“Extract components and pass JSX as children” —— 因为 prop drilling 常常是组件切错了的症状，而不是层数的问题。改成 <Layout><Posts posts={posts} /></Layout>，转发链直接消失。
context 的真实用例官方也列了：主题、当前账号、路由 —— 你装的 MantineProvider 正是第一条。

测验 4 / 5

说一个组件是 “uncontrolled”，准确含义是：

官方：“a component is ‘controlled’ when the important information in it is driven by props rather than its own local state.”
这个词有两个尺度，别搞混：第 7 课的 <input> 层面（value+onChange，第二个选项说的是那件事），和本课的组件层面。核心问题是同一个：真相在自己肚子里，还是在别人手上？
而且 uncontrolled 不是坏事：“easier to use… because they require less configuration”，代价是 “less flexible when you want to coordinate them together”。判定规则：只有一个组件关心 → 放低；两个以上必须一起变 → 提到最近共同父级。

测验 5 / 5

引入 Mantine 后，构建产物 CSS 涨了 227 kB 而 JS 只涨 76 kB，因为：

tree shaking 靠的是 ES module 的静态可分析性：打包器能确定你 import 了哪 9 个组件、没 import 哪些，剩下的删掉。
import "@mantine/core/styles.css" 则是一整个文件，里面是全库所有组件的样式，打包器没有依据判断哪条规则用得上（CSS 的可达性分析需要运行时 DOM 信息）。
实测：空模板 193.28 kB JS / 4.10 kB CSS → 加 Mantine 后 269.15 kB / 231.22 kB。gzip 后 CSS 只剩 33.80 kB —— 因为它高度重复，压缩率极好，所以实际影响比裸体积小。
Mantine 也提供按组件拆分的 CSS 入口，想优化可以走那条路。

回忆练习 · 出声说，别只在心里过

合上这一页，连着讲 60 秒：
（1）给你一份 state，你怎么判断它该住在哪个组件里？说出可执行的规则，不要说「看情况」。
（2）为什么把组件定义写在另一个组件里面会出 bug？用第 6 课的词来解释。
（3）「层数太深了，上个 context 吧」—— 给出官方的两个先决替代方案。

(1) 数数有几个组件必须一起看到这份数据。只有一个 → 留在它自己肚子里（uncontrolled，省配置）。两个以上 → 提到它们的最近共同父级（不是最顶层），再连同回调一起传下去。不确定就先放低，提升容易、下沉痛苦。官方三步法：删掉子组件的 state → 父级先传写死的数据跑通 → 再把 state 加到父级。原则叫 single source of truth：每份 state 有唯一属主，不复制。

(2) React 判定组件身份靠位置 + 类型。function 写在渲染路径上，每次渲染都产生一个新的函数对象（Object.is 不相等）→ 同一位置换了不同类型 → React 卸载整棵子树再重新挂载 → 下面所有 state 清零，真实 DOM 被销毁重建，焦点和滚动位置一起丢。症状是「打字打一半光标跳走」，而且完全不报错。lint 只给 warning。

(3) ① 就老老实实传 props —— 官方说十几层传十几个 prop 并不反常，好处是谁用了哪份数据一目了然。② 抽组件、用 children 传 JSX —— 中间层如果只转发不使用，说明组件切错了；改成 <Layout><Posts posts={posts} /></Layout>，转发链直接消失。两条都不行，再上 context（主题 / 当前账号 / 路由是它的标准用例）。

九、面试回答模板

如果面试官问：“你怎么划分 React 组件？” / “state 该放哪？” / “prop drilling 怎么办？”

“我的判定标准很简单：数一数有几个组件必须一起看到这份数据。只有一个就留在它自己那儿，两个以上就提到最近的共同父级 —— 注意是最近，不是最顶层，提太高会导致重渲染范围变大、中间层被迫转发、组件没法复用，而且这个错误不报错所以特别常见。React 官方管这叫 lifting state up，给的是三步：先删掉子组件的 state，父级先传写死的数据跑通，最后再把 state 加到父级、连同事件处理函数一起传下去。
组件之间只有两条通道，都是 props：数据向下，事件向上。回调没有任何特殊语法，函数就是值 —— 相当于 C# 的 Action<T>，但没有 event 的多播和解绑。命名约定是 prop 叫 onXxx、实现叫 handleXxx。
有一个坑我踩过，值得单说：绝对不能把组件定义写在另一个组件里面。因为 React 靠『位置 + 类型』认组件身份，而内嵌的函数每次渲染都是新的函数对象，等于同一位置换了个组件，React 会把整棵子树卸载重建 —— 下面所有 state 清零、DOM 节点被替换、光标和滚动位置一起丢。症状是用户投诉『打字打一半光标跳走』，而代码一行错都不报。我实测过：挪进去 mounts=2、输入框清空、焦点丢失，挪出来就正常。lint 能报，但只是 warning。
prop drilling 我不会条件反射上 context。官方明确说 context 太容易被滥用，建议先试两件事：一是老实传 props，十几层传十几个 prop 不算反常，好处是数据流显式可见；二是抽组件、用 children 传 JSX —— 中间层只转发不使用，往往说明组件切错了，改成 <Layout><Posts /></Layout> 转发链就没了。context 的合理用例是主题、当前用户、路由这类真正全局的东西。我项目里用 Mantine，它的 MantineProvider 就是一个真实的 context，拿掉它组件会直接抛异常而不是掉样式。
顺带说组件库的代价：我实测加 Mantine 之后 JS 只涨了 76 kB，CSS 涨了 227 kB。不对称是因为 JS 走 ESM 能 tree-shake，而整包 CSS 一旦 import 就全都进来；gzip 后 CSS 剩 33 kB，因为重复度高压得动。”

四个分水岭句子：「最近的共同父级，不是最高的父级」、「数据向下，事件向上」、「内嵌的组件定义每次渲染都是新类型，所以子树被重建」、「prop drilling 常常是组件切错了，不是层数问题」。第三句最能证明你真写过项目 —— 它是只有踩过才说得出的那种细节。
