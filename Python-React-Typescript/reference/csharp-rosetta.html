C# ↔ Python / TypeScript 对照表

你已有的知识是杠杆。但每个类比都有裂缝，裂缝处才是面试真正考的东西。

怎么用这份表

「⚠ 裂缝」一列是重点。类比让你上手快，裂缝让你不在面试里露怯。当面试官问「你从 C# 转过来，觉得最不适应的是什么」，答案应该直接从这一列里取 —— 那是一道送分题。

后端框架概念

C# / ASP.NET CoreFastAPI⚠ 裂缝
[HttpGet("/api/x")] @app.get("/api/x") attribute 是编译期元数据，靠反射读取；decorator 是运行时执行的函数调用，直接修改/注册被装饰的对象。
Middleware 管道 app.add_middleware(...) 概念高度一致 —— 洋葱模型、顺序敏感。这是你可以直接迁移的知识。
DTO + 模型绑定
+ FluentValidation		 Pydantic BaseModel Pydantic 一个类同时干了 DTO、绑定、校验、序列化四件事，而且校验规则就写在类型注解里。
内置 DI 容器 Depends() FastAPI 没有全局容器和生命周期注册（singleton/scoped/transient）；依赖是在函数签名上按需显式声明的。这是个高频追问点。
async Task<T> async def 语法几乎一样，模型差别很大：Python 有 GIL，单进程内只有一个事件循环、无线程池并行。CPU 密集任务在 Python 里不能靠 async 解决。

类型系统（第 2 课）

C#TypeScript⚠ 裂缝
名义类型
（nominal）		 结构化类型
（structural）		 C# 看声明：没写 : IFoo 就不是 IFoo。TS 看形状：只要属性对得上就通过，无需任何声明关系。官方为 C#/Java 开发者写的说明
类型在运行时存在
（reified）		 类型被擦除
（erased）		 C# 有 GetType()、反射、泛型实化。TS 的类型在编译后完全消失，运行时一行都不剩，没有任何 TS 层面的反射。
interface interface / type 同名不同物。TS 的 interface 只是「形状约束」，可以描述函数、数组、任意对象，且无需被实现方知晓。
class Foo : IBar class Foo implements Bar TS 的 implements 什么也不建立。它只是请编译器帮你自查形状是否对得上；写不写都不影响这个类能被赋给谁。C# 里它是身份的一部分。
private 成员 private 成员 结构化规则的唯一例外。含 private/protected 成员的 class 按声明位置比较 —— 两个字段完全相同的类互不兼容（TS2322）。面试时补上这一句，比只说「TS 是结构化的」强得多。
反序列化时校验
（JsonSerializer + DTO）		 没有对应物 最大的裂缝。res.json() 返回 any，你写的返回类型只是一句承诺，运行时无人核对。跨边界的数据必须自己加运行时校验（Zod / Pydantic）。

数据校验（第 3 课）

C# / ASP.NET CorePython / TypeScript⚠ 裂缝
DTO + DataAnnotations
（[Required]、[Range]）		 Pydantic BaseModel + Field(...) C# 的 attribute 是编译期元数据，运行时由框架反射读取；Pydantic 是在类定义时读取类型注解并当场生成校验代码。结果相似，机制完全不同。
[ApiController] 自动 400 FastAPI 自动 422 行为一致：校验失败时函数体不执行。状态码不同 —— 422 Unprocessable Entity 比 400 更精确，是 FastAPI 的默认选择。
手写 DTO 投影
（防止实体字段外泄）		 response model 自动过滤 路由返回类型注解写成 -> SomeModel 后，模型里没声明的字段被静默剥离，不报错。这是安全特性，不是便利特性。官方说明
FluentValidation Zod（前端） 地位完全不同。FluentValidation 是补充（.NET 运行时本就带类型信息）；Zod 是前端唯一的一道运行时检查 —— 没有它就什么检查都没有。
类型是源头，校验挂在类型上 schema 是源头，类型由它推出 方向相反，这是最反直觉的一点。const S = z.object({...}) 是值（活到运行时），type S = z.infer<typeof S> 是它的投影。类型擦除逼出来的设计。
TryParse 模式 .safeParse() 思路一致（不抛异常，返回成败）。差别在返回值是可辨识联合：if (r.success) 之后 TS 自动收窄，能直接访问 r.data，不需要 out 参数。

React 的状态模型（第 4 课）

C#对应物⚠ 裂缝
label.Text = "hi"
（WinForms / WPF）		 setMessage("hi") 命令式 vs 声明式。C# 抓住一个长期存活的控件对象改属性；React 里你改 state，React 重新调用你的组件函数拿到新的 UI 描述，再自己去更新 DOM。式子：UI = f(state)。你永远不碰 DOM。
字段 private int _count; const [count, setCount] = useState(0) C# 字段靠名字绑定，编译期定死。React 的 state 靠 hook 的调用顺序绑定（内部是数组 + 游标），运行期才确定 —— 这就是 hook 不能写在 if / 循环 / try 里、也不能写在提前 return 之后的全部原因。
lambda 捕获变量
Action a = () => W(n);		 事件处理函数捕获
本次渲染的 const		 方向相反的闭包陷阱。C# 捕获的是变量，之后变量变了 lambda 就看到新值；React 每次渲染产生全新一批 const，回调捕获的是那一次的常量，永远不会变。所以 setTimeout 三秒后读到的仍是点击那一刻的值。
_count += 1; 连写三次 setCount(c => c + 1) 连写三次 写 setCount(count + 1) 三次只加一 —— 本次渲染里 count 是常量，三句算出同一个值。要连续累加必须用 updater 形式，由 React 在处理队列时把上一个结果喂进来。判据：新值依赖旧值就用函数形式。
list.Add(x) 后刷新绑定 必须 setArr([...arr, x]) 直接 arr.push(x) 再 setArr(arr) 界面不动：React 用 Object.is 比较新旧值，同一个引用会被判定为没变，直接跳过重新渲染。C# 的 ObservableCollection 靠事件通知，React 靠引用相等。

React 的副作用与清理（第 5 课）

C#对应物⚠ 裂缝
Loaded / Unloaded
构造函数 / Dispose		 useEffect(setup)
与它 return 的 cleanup		 「配对」的直觉对，「一次性生命周期」的直觉错。更准的类比是 event += / event -=，而且写在一个会被反复执行的地方：依赖一变，React 先 cleanup 再 setup。官方用词是 synchronizing，不是 lifecycle。
using / IDisposable return () => { ... } 作用相同（释放/撤销），触发时机完全不同：using 是词法作用域结束时确定性释放；cleanup 由 React 在「依赖变了」或「组件卸载」时调用，你不控制什么时候。
CancellationToken AbortController
或 let ignore = false		 两条路而非一条：AbortController 真的取消请求（对应 CancellationToken）；ignore 标记不取消，请求照发照回，只是结果被丢弃。后者能生效靠的是每次渲染有独立闭包（第 4 课的快照模型）。
Debug 构建里的额外断言 <StrictMode> 让 effect 双跑 都是「开发期故意加严、生产期消失」。但 StrictMode 检查的东西很特别：它在测你的 cleanup。C# 没有对应物 —— 最接近的心态是「Debug 下故意 Dispose 一次再重建，看你有没有写对」。删掉它 = 把体温计摔了。
async void 事件处理器
的竞态问题		 useEffect 里手写 fetch
的竞态问题		 这条是可以直接迁移的知识。两边同样是「多个异步操作在飞，返回顺序不保证，后到的旧结果覆盖新结果」。C# 里你用 CancellationToken 或版本号解决；React 里用 cleanup + ignore。面试时主动提这个场景，含金量很高。

不可变更新与对象身份（第 6 课）

C#对应物⚠ 裂缝
record + with 表达式
person with { Age = 31 }		 展开语法
{ ...person, age: 31 }		 动作完全一样：不改原件，造个新的。裂缝在强制力：C# 由类型系统把关，想 mutate 都编译不过；JS 的对象/数组永远可变，arr.push() 编译过、lint 不报、运行不报错。这条纪律 100% 靠自觉 —— 这正是面试要说出口的差异。
ImmutableList<T>
list.Add(x) 返回新表		 [...arr, x]
filter / map / slice		 C# 里「返回新表」是方法签名写死的，你不可能拿错。JS 里 push（原地）和 concat（新表）长得一样无辜，得靠记。最阴的一对：slice 复制 / splice 原地改。
list.OrderBy(...)
返回新序列		 arr.sort(...)
原地排序		 这里 C# 直觉会直接骗你。LINQ 全是惰性 + 返回新序列；Array.prototype.sort 和 reverse 都是原地改并返回同一个引用。对 state 数组排序必须 [...arr].sort(...)。
对象身份 = 引用
一个实例的字段属于那个实例		 组件身份 = 位置（或 key）
state 存在 React 里		 整份对照表里差得最远的一条。React 里根本没有「组件实例」可抓（组件只是每次渲染被重新调用的函数）。React 靠渲染树中的位置把新旧两次渲染对上号；key 的作用是把 key 本身变成位置的一部分。
推论：用 index 当 key，删掉第一项后 React 认为「位置 0 没变」→ 保留 state、只换 props → 标题对、数据错。
局部变量上随便改
（还没暴露给别人的对象）		 local mutation
const next = [...a]; next.sort();		 这条可以直接迁移：两边的判据都是「有没有别人持有这个引用」。官方原话 “Mutating an object you've just created is okay because no other code references it yet.” 所以规则不是「禁止 mutation」，是「禁止改已经在 state 里的那个」。

表单、HTTP 与错误建模（第 7 课）

C#对应物⚠ 裂缝
WPF 双向绑定
{Binding Text, Mode=TwoWay}		 受控组件
value={x} onChange={...}		 React 没有双向绑定。只有 state → UI 一个方向，反向那一段要你手写。裂缝在心智模型：React 每次渲染都把 value 强制按回去，所以只写 value 不写 onChange 时输入框直接打不进字（不是「不同步」）。收益是只有一个数据源，且回写那一步在你手里（可顺手做大写、过滤）。
res.EnsureSuccessStatusCode()
IsSuccessStatusCode		 if (!res.ok) 这条可以直接迁移，而且是本课最省力的一条。两边设计一致：4xx/5xx 都不算「失败」，不抛。只有请求本身失败（网络错误、URL 非法、被 CORS 拦下）fetch 才 reject 一个 TypeError。裂缝只在于：JS 没人替你写 EnsureSuccessStatusCode，漏了就会把 422 错误体当正常响应去解析。
抽象基类 + 子类 + switch 模式匹配
或 OneOf<T1,T2>		 discriminated union
{kind:"error";message:string} | …		 这一条是 TypeScript 赢 C# 的地方，值得在面试里主动提。TS 靠字面量字段 + 自动收窄，几行类型就让非法状态无法表示；C# 至今没有真正的联合类型。
典型用途：提交状态 idle | submitting | error | success，取代三个互相打架的布尔值。
FluentValidation
（回答是/否）		 Zod
（parse，不是 validate）		 裂缝在产出：FluentValidation 校验完，你手上还是原来那个对象；Zod 进去 unknown、出来是干净且有类型的新数据（.trim() 这类 transform 先跑再校验）。所以成功后要用 parsed.data。「Zod 是 parser」这句话本身就是一个考点。
ASP.NET 的 [ApiController]
自动 400 + ModelState		 FastAPI + Pydantic
自动 422 + detail		 思路完全一致（模型即校验，不合法则方法体根本不执行），差别在细节：状态码是 422 不是 400；错误体是 detail 数组，每项带 loc（["body","title"]）+ msg —— 结构化到可以直接摊回各个输入框。
（无对应物）
服务端之间调用不受限		 CORS / 预检 OPTIONS 纯浏览器概念，C# 后端开发最容易误解的一条。application/json 不是「简单请求」，所以几乎每个 JSON POST 都会先来一条 OPTIONS。
更关键：CORS 由浏览器执行 —— 实测带错 Origin 的 POST，服务器照常执行并写入、照常返回 200，只是浏览器扣下了响应。它不是访问控制，curl / Postman / 任何后端程序都不受约束。
