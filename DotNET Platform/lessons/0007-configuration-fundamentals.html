第 7 课：配置系统基础——多源、分层、热重载

模块：配置系统（1/2） |  预计阅读/练习时间：25 分钟

Framework 4.8 时代，配置只有一个地方：web.config（或 app.config）， 通过 ConfigurationManager.AppSettings["key"] 读取。想区分开发/生产环境？靠 web.Debug.config 的 XML 变换。想从环境变量覆盖？自己写逻辑。

现代 .NET 的配置系统彻底重构了这一切——多源聚合、分层覆盖、支持热重载。 这一课我们从零搭建一个控制台应用的配置，理解它的核心模型。

  • 理解 IConfiguration 管道模型：Builder → Sources → Build → Root
  • 掌握四种常用配置源：JSON、环境变量、命令行、内存集合
  • 理解 "最后胜出"的覆盖规则——和 Framework 4.8 的 XML 变换完全不同
  • 掌握配置的分层读取：GetSection()、GetValue<T>()、Bind()

Framework 4.8 vs 现代 .NET：思维转变

先做一次彻底的思维切换——这不是 API 名称的变化，而是配置哲学的变化：

Framework 4.8现代 .NET
配置在哪 web.config / app.config——单一 XML 文件 多个源聚合：JSON + 环境变量 + 命令行 + Key Vault + 数据库……任意组合
读取方式 ConfigurationManager.AppSettings["key"] IConfiguration["Section:Key"]——分层 key，注进 DI
环境切换 web.Debug.config XML 变换（编译时） 按环境加载不同文件 + 环境变量覆盖（运行时）
类型转换 全是 string，手动 int.Parse() GetValue<int>()、Bind() 到强类型对象
热重载 ❌ 改配置必须重启应用 ✅ JSON 文件改了，程序自动感知（配合 Options 模式）
包依赖 System.Configuration.dll（Framework 内置） Microsoft.Extensions.Configuration.*（NuGet，按需安装）

核心管道模型：Builder → Sources → Build → Root

整个配置系统的架构可以用四个步骤概括。理解这个管道，后面所有配置源都是"往里添加数据"。 

// 1. 创建 Builder
var builder = new ConfigurationBuilder();

// 2. 添加配置源（可以加多个！）
builder.AddJsonFile("appsettings.json")          // JSON 文件
       .AddEnvironmentVariables()                 // 环境变量
       .AddCommandLine(args);                     // 命令行参数

// 3. Build——读取所有源，聚合为一个树
IConfigurationRoot config = builder.Build();

// 4. 读取配置
string value = config["Database:ConnectionString"];

// 这三行代码就是整个配置系统的核心模型。
// 所有复杂的场景（Key Vault、数据库配置、自定义源）都是"往里加 Source"。

配置管道

appsettings.json ──┐
环境变量 ──────────┤
命令行参数 ────────┤  ┌──────────────────┐    ┌─────────────────┐
内存集合 ──────────┼──│ConfigurationBuilder│──▶│IConfigurationRoot│
Key Vault ─────────┤  └──────────────────┘    └─────────────────┘
自定义 Provider ───┘                                  │

                                              │ GetSection() │

四种核心配置源

1. JSON 文件——最常见

// appsettings.json
{
  "Database": {
    "ConnectionString": "Server=localhost;Database=MyDb;...",
    "Timeout": 30
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft": "Warning"
    }
  },
  "FeatureFlags": {
    "EnableNewCheckout": true
  }
}

// 注册——需要 NuGet: Microsoft.Extensions.Configuration.Json
builder.AddJsonFile("appsettings.json", optional: false, reloadOnChange: true);
//                                        ^ 文件不存在时？   ^ 文件改了自动重读？

// 按环境覆盖——Framework 4.8 时代需要 XML 变换才能做到的事
var env = Environment.GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT") ?? "Production";
builder.AddJsonFile($"appsettings.{env}.json", optional: true);
// appsettings.Development.json —— 只在开发环境加载，覆盖开发专用配置
// appsettings.Staging.json     —— 只在预发布环境加载
// 文件不存在？optional: true 跳过，不报错

2. 环境变量——生产环境的秘密

// 注册——需 NuGet: Microsoft.Extensions.Configuration.EnvironmentVariables
builder.AddEnvironmentVariables();

// 环境变量的层级用双下划线 __ 或冒号 : 表示
// export Database__ConnectionString="Server=prod;..."
// 等价于 JSON 中的 {"Database": {"ConnectionString": "..."}}

// 典型用法：开发时 JSON 里写连接字符串，生产时用环境变量覆盖
// 代码不变，运维改环境变量——十二要素应用 (12-Factor App) 的第三条

3. 命令行参数——CI/CD 和 Docker

// 注册——需 NuGet: Microsoft.Extensions.Configuration.CommandLine
builder.AddCommandLine(args);

// dotnet run -- --Database:ConnectionString="Server=prod;..." --FeatureFlags:EnableNewCheckout=true
// 命令行自动映射到分层 key——最高优先级，覆盖 JSON 和环境变量

4. 内存集合——测试和默认值

// 直接在代码里提供配置——测试时特别好用
builder.AddInMemoryCollection(new Dictionary<string, string?>
{
    ["Database:ConnectionString"] = "Server=test;...",
    ["Database:Timeout"] = "5"
});

"最后胜出"：配置源的覆盖规则

多个源提供同一个 key 时，后注册的覆盖前面的。这就是为什么注册顺序很重要： 

// 标准注册顺序（ASP.NET Core 模板项目的默认做法）
builder.AddJsonFile("appsettings.json")                     // 1. 基础默认值
       .AddJsonFile($"appsettings.{env}.json", optional: true)  // 2. 环境特定覆盖
       .AddEnvironmentVariables()                           // 3. 运维/K8s 覆盖
       .AddCommandLine(args);                               // 4. 命令行最高优先级

// "Database:ConnectionString" 在 4 个源里都有？
// → 命令行里的值胜出（最后一个注册的）
💡 心智模型：把配置源想象成一层层叠起来的透明纸。最底下的层（先注册的）提供默认值， 每往上一层（后注册的）可以遮住下面的部分内容。key 相同时，你看到的是最上面那层。 这和 MSDI 的"最后注册胜出"是同一套哲学——列表顺序决定优先级。

读取配置：从 string 到强类型

基础读取：indexer 和 GetSection

IConfiguration config = builder.Build();

// 方式一：直接按 key 读——返回 string（或 null）
string connStr = config["Database:ConnectionString"];
// key 用冒号分层：Database → ConnectionString

// 方式二：切出一个 Section——相当于 "进入子目录"
IConfigurationSection dbSection = config.GetSection("Database");
string conn = dbSection["ConnectionString"];    // Server=...
string timeout = dbSection["Timeout"];          // "30"
// 你可以把 Section 传给只关心 Database 配置的方法

GetValue<T>：自带类型转换

// 不再需要 int.Parse()！
int timeout = config.GetValue<int>("Database:Timeout");       // 30
bool enabled = config.GetValue<bool>("FeatureFlags:EnableNewCheckout"); // true

// 键不存在时可以指定默认值
int retries = config.GetValue<int>("Retry:MaxCount", 3); // 没配置就返回 3

Bind：映射到强类型对象

// 定义配置类——POCO，全用属性
public class DatabaseOptions
{
    public string ConnectionString { get; set; }
    public int Timeout { get; set; }
}

// 一行绑定
var dbOpts = new DatabaseOptions();
config.GetSection("Database").Bind(dbOpts);
// dbOpts.ConnectionString == "Server=localhost;..."
// dbOpts.Timeout == 30

// 👆 这就是 Options 模式的基础——下一课展开

和 DI 集成：配置天然就是服务

在 ASP.NET Core（以及 Generic Host）里，配置系统已经自动搭好。你不需要手动 new ConfigurationBuilder——直接把 IConfiguration 注入到任何服务里： 

public class ReportService
{
    private readonly string _connectionString;

    // ✅ IConfiguration 已经在 DI 里注册好了，直接用
    public ReportService(IConfiguration config)
    {
        _connectionString = config["Database:ConnectionString"];
    }
}

控制台应用需要自己搭——但一行代码就行（下一课的 Host 模型模块会讲如何用 Host.CreateDefaultBuilder() 自动拿到和 ASP.NET Core 完全相同的配置栈）。

检查理解

❓ 同一个 key 在 JSON 和环境变量里都有值，最后解析到哪个？
JSON 优先——因为 JSON 是主配置文件
报错——不允许同一 key 出现在多个源中
后注册的源优先——环境变量覆盖 JSON
随机选一个——取决于 Provider 的加载时机
❓ config["Database:ConnectionString"] 中的冒号表示什么？
文件路径——"Database" 是文件名，"ConnectionString" 是 key
层级分隔——Database 是 Section，ConnectionString 是其中的 key
只是命名惯例——可以用任意分隔符
这是错误写法——应该用 GetSection() 分开读
❓ int timeout = config.GetValue<int>("Timeout", 30);——如果配置里没有 "Timeout"，timeout 是多少？
0
null
30
抛异常 InvalidOperationException
❓ config["A:B"] 在多个源中都有值（JSON、环境变量、命令行），最终取哪个源的？
第一个注册的源
所有源的值合并成一个数组
JSON 源——因为它通常是主配置文件
最后一个注册的源

关键术语

IConfigurationBuilder
配置管道的入口。收集所有配置源（Provider），调用 Build() 时把它们聚合为一个 IConfigurationRoot。NuGet 包：Microsoft.Extensions.Configuration。
IConfigurationRoot
聚合后的配置根对象。内部持有一个有序的 Provider 列表。读取 key 时从头到尾遍历所有 Provider——第一个返回非 null 值的 Provider 决定最终值。
配置源（Configuration Source / Provider）
数据来源。内置提供：JSON (AddJsonFile)、环境变量 (AddEnvironmentVariables)、命令行 (AddCommandLine)、内存集合 (AddInMemoryCollection)、INI 文件 (AddIniFile)、XML (AddXmlFile)。可自定义实现 IConfigurationSource。
分层 Key
用冒号 : 表示配置的层级结构。"Database:ConnectionString" 对应 JSON 中 {"Database": {"ConnectionString": "..."}}。环境变量中用双下划线 __ 替代（某些 shell 不允许冒号）。
GetSection
从配置树中切出一个子节点，返回 IConfigurationSection。它"记住"了自己的路径前缀——config.GetSection("Database")["ConnectionString"] 等价于 config["Database:ConnectionString"]。
Bind
把配置 Section 映射到强类型 POCO 对象。自动匹配属性名（不区分大小写）。config.GetSection("Database").Bind(myObj)。配合 Options 模式使用时会被 services.Configure<T>() 自动调用。
reloadOnChange
AddJsonFile 的可选参数。设为 true 时，JSON 文件内容变化会自动刷新配置值——不需要重启应用。底层用 FileSystemWatcher 监听文件变更。热重载配合 IOptionsSnapshot / IOptionsMonitor 使用（下一课）。
optional: true
AddJsonFile 的参数。文件不存在时不抛异常，静默跳过。环境特定配置文件（appsettings.Development.json）应该设为 optional——开发配置只在开发机上存在。

Framework 4.8 写法现代 .NET 写法
