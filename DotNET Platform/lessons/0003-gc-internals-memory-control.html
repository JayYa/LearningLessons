第 3 课：GC 内部机制与内存控制

模块：运行时架构（2/2） |  预计阅读/练习时间：25 分钟

上一课你知道了 GC 有两种模式可以切。但选完模式还不够——GC 在回收时到底在干什么？ Framework 4.8 开发者可以一辈子不关心 GC 内部细节，现代 .NET 给了你绕开 GC 的工具， 但前提是你要理解它怎么运作。这一课从 GC 的"代"机制出发，到 Span<T> 如何直接在栈上操作内存， 再到 AssemblyLoadContext 如何替代你熟悉的 AppDomain。

  • 理解 GC 三代机制（Gen0/Gen1/Gen2）和三种堆（SOH/LOH/POH）的物理分界
  • 掌握 Span<T> 和 Memory<T> 如何绕开 GC 堆，以及两者在什么场景用哪个
  • 理解 AssemblyLoadContext 为何取代 AppDomain——加载、隔离、卸载程序集的新模型

代机制：GC 不是"扫全堆"

Framework 4.8 时代你可能听过"GC 回收会暂停所有线程"——但 GC 并不是每次都扫整个堆。 现代 .NET 的 GC 是分代（generational）的，基于一个简单假设：新对象死得快，老对象活得久。

三代模型

托管堆的物理布局

┌─────────────────────────────────────────────────────┐
│  Gen0          │  Gen1          │  Gen2             │
│  (ephemeral)   │  (buffer)      │  (long-lived)     │
│                 │                │                   │
│  新创建的       │  熬过 1 次     │  熬过 Gen0 +     │
│  小对象         │  Gen0 回收     │  Gen1 各 1 次    │
│  临时字符串     │  上升至此      │  回收后提升至此   │
│  LINQ 临时结果  │                │  静态变量等       │
│                 │                │                   │
│  回收频率：极高  │  回收频率：中   │  回收频率：低     │
│  暂停时间：<1ms │  暂停时间：短   │  暂停时间：较长    │
└─────────────────────────────────────────────────────┘

回收的逻辑：

  1. Gen0 满了 → 只回收 Gen0。存活对象提升（promote）到 Gen1，死亡对象的内存直接回收。
  2. Gen1 满了 → 回收 Gen0 和 Gen1。Gen1 的存活对象提升到 Gen2。
  3. Gen2 满了 → 回收 全部三代（full GC）。这是最贵的回收，但发生频率最低。
💡 Framework 4.8 的 GC 也是分代的——这点新旧是相同的。区别在于现代 .NET 让你对 GC 有更细的控制： 可以压缩 LOH（以前不行）、可以限制堆硬上限（容器友好）、可以用 GC.Collect(2, GCCollectionMode.Aggressive) 精确控制回收行为。

SOH / LOH / POH：对象的三个"家"

GC 堆不是一个整体——对象根据自己的大小和特性，被分配在三个不同的堆区域：

堆全称存放什么回收时压不压缩代支持

（绝大多数对象在这）		 ✅ 压缩（移动存活对象，消除碎片） Gen0/Gen1/Gen2
LOH Large Object Heap ≥ 85,000 字节的对象
（大数组、大字符串、大 byte[]）		 ❌ 默认不压缩
（移动大对象太贵）		 只有 Gen2
（大对象直接进 Gen2）

（传给 native 代码的 buffer）		 ❌ 不压缩
（固定了就不能移动）		 只有 Gen2
（.NET 5 新增）
⚠️ LOH 碎片的坑：Framework 4.8 中最头疼的问题之一——大对象分配后释放，LOH 产生空洞， 后续分配找不到足够大的连续空间 → OutOfMemoryException（明明空闲内存还很多）。 现代 .NET 可以通过 GCSettings.LargeObjectHeapCompactionMode 手动触发 LOH 压缩， 或配置 DOTNET_GCLOHThreshold 调整大对象阈值。

POH 是 .NET 5 才加入的——以前被 fixed 固定的对象留在 SOH 里，像钉子一样阻碍 Gen0 压缩。现在它们被单独隔离到 POH，SOH 的回收效率大幅提升。

压缩（Compaction）到底是什么？

每次 GC 回收结束时，如果开启了压缩，运行时会做一件事：把存活对象挤到一起，把空洞消灭掉。不压缩的话，死亡对象留下的空隙散布在堆里，堆像被虫蛀过的木头——空洞到处都是，分配新对象时可能找不到足够大的连续空间。

压缩前（碎片化）
┌────┬════┬────┬════┬────────┬════┐
│ 活 │ 死  │ 活 │ 死  │  活    │ 死  │
└────┴════┴────┴════┴────────┴════┘

压缩后（存活对象移到一起，空闲空间连成一片）
┌────┬────┬────────┬──────────────────┐
│ 活 │ 活 │  活    │   一整块空闲空间    │
└────┴────┴────────┴──────────────────┘
              ↑
         分配指针只需往右移（bump pointer）
压缩的好处为什么重要
消灭碎片后续分配总能找到连续空间，不会"明明有空闲内存却 OOM"
分配极快空闲空间是一整块，分配只需移动一个指针
缓存友好相关对象物理上更近，CPU 缓存命中率更高

一句话：压缩是用回收时的移动成本，换取回收后的分配速度和空间利用率。

LOH 强制压缩有多贵？

SOH 压缩移动的是小对象（< 85KB），一次 memcpy 几百字节到几十 KB，几微秒的事。

LOH 里的对象动辄几百 MB。移动一个 500MB 的 byte[] 意味着：实际复制 500MB 数据（不是指针游戏）、更新所有引用（指向这个对象的所有指针都要改）、整个过程线程挂起。

SOH Gen2 回收LOH 压缩
典型暂停几十 ms几百 ms 到秒级
主要开销标记 + 清理内存拷贝（memcpy）
自带压缩✅ 总是❌ 需手动触发 CompactOnce

生产环境里一个 2GB LOH 上做压缩，暂停 1-3 秒是正常的。

⚠️ 正确的策略：不是在每次 full GC 后压，而是在感觉到 LOH 碎片问题时才压。典型姿势：应用启动 → 分配大量临时大对象 → 程序空闲时做一次 full GC + LOH 压缩。也可以从根本上避免——用 ArrayPool<byte>.Shared 租用大 buffer、用完归还，而不是频繁 new 大数组又扔掉。LOH 压缩是重症手术，不是日常养生。

Span<T>：绕开 GC 堆操作内存

Framework 4.8 时代你想操作一段内存，几乎只有三条路：数组（在 GC 堆上）、不安全代码（unsafe + 指针）、Marshal.AllocHGlobal（非托管内存，手动释放）。 数组产生 GC 分配，不安全代码太难维护，AllocHGlobal 忘了释放就是内存泄漏。

现代 .NET 给了你第四种选择：Span<T>——一个可以指向任意内存的类型安全切片视图。

Span<T> 是什么？

Span<T> 可以指向三种内存来源

  ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
  │  托管堆上的数组   │    │  栈上的内存      │    │  非托管内存      │
  │  (GC 管理的)     │    │  (stackalloc)   │    │  (native heap)  │
  └────────┬────────┘    └────────┬────────┘    └────────┬────────┘
           │                      │                      │
           ▼                      ▼                      ▼
  ┌─────────────────────────────────────────────────────────────┐
  │                    Span<T>（ref struct）                    │
  │  · 只存在栈上（不能被装箱、不能作为类字段）                   │
  │  · 零分配——不对 GC 产生任何压力                              │
  │  · 切片（Slice）只是移动指针，不复制数据                      │
  │  · 编译器保证生命周期安全（比 unsafe 指针安全得多）            │
  └─────────────────────────────────────────────────────────────┘

典型用法

// 1. 从数组创建 Span——不分配新内存
byte[] buffer = new byte[1024];
Span<byte> span = buffer.AsSpan();
Span<byte> firstHalf = span.Slice(0, 512);  // 不复制，只是新视图

// 2. 栈上分配——完全绕开 GC
Span<int> nums = stackalloc int[128];  // 在栈上，0 GC 压力

// 3. 字符串切片——以前要 Substring（分配新字符串），现在不用了
ReadOnlySpan<char> slice = "Hello, World!".AsSpan(0, 5);  // "Hello"，零分配

// 4. 解析数据不产生临时 string
ReadOnlySpan<char> text = input.AsSpan();
int commaIndex = text.IndexOf(',');
var key = text.Slice(0, commaIndex);    // 零分配
var value = text.Slice(commaIndex + 1); // 零分配
💡 和 Framework 4.8 的 ArraySegment<T> 有什么不同？ ArraySegment<T> 只能指向数组，而且是个普通 struct（可以放堆上，没有 ref 安全保证）。 Span<T> 可以指向任何内存，并且是 ref struct——编译器强制它只能在栈上，确保它引用的内存在使用期间有效。这是 C# 7.2 引入的语言级安全特性。

Span<T> vs Memory<T>：什么时候用哪个？

Span<T> 有一个致命限制——它是 ref struct，不能作为类字段、不能装箱、不能在 async 方法中使用。对于异步场景，你需要它的堂兄弟 Memory<T>：

Span<T>Memory<T>
类型ref structstruct（普通值类型）
存储位置只能在栈上栈上、堆上（类字段）、lambda 捕获
async 方法❌ 不能✅ 可以
作为类字段❌ 不能✅ 可以
零 GC 分配✅ 是✅ 是（但 Memory 本身可在堆上）
性能更快（无间接层）略慢（内部有 Span 属性）
典型场景同步方法、本地变量、循环内切片async 管道、类字段、跨方法传递
// Memory<T>：异步场景中零分配的缓冲区操作
async Task ProcessAsync(Memory<byte> buffer, PipeWriter writer)
{
    // Memory 可以跨 await 使用
    await writer.WriteAsync(buffer.Slice(0, 128));
    await DoMoreAsync(buffer);
}

// 从 Memory 取出 Span 做实际读写（取 Span 的瞬间是同步的）
void ParseHeader(Memory<byte> buffer)
{
    Span<byte> span = buffer.Span;  // 同步方法里拿到 Span
    int version = span[0];
}
⚠️ 常见错误：在 async 方法里试图用 Span<T> 跨 await——编译器会报错 CS4012。 这是 C# 的保护机制：ref struct 跨 await 意味着它的栈帧在恢复时可能已经失效。 规则很简单：同步用 Span，异步用 Memory，在同步回调里通过 .Span 拿到 Span 做实际读写。

AssemblyLoadContext：AppDomain 的现代替代

Framework 4.8 中你熟悉的 AppDomain 在现代 .NET 中几乎全砍了。原因很简单：AppDomain 太重了——创建和卸载 AppDomain 需要序列化跨越边界的对象，性能极差，而且不能单独卸载一个程序集 （一个程序集加载到 AppDomain 后，必须卸载整个 AppDomain 才能释放）。

现代 .NET 的答案是 AssemblyLoadContext（ALC）——轻量、可单独卸载、支持隔离。

对比

AppDomain（Framework 4.8）AssemblyLoadContext（现代 .NET）
创建成本高（独立运行时隔离）低（轻量逻辑边界）
卸载卸载整个 AppDomain
（含其中所有程序集）		卸载单个 ALC
（含其中所有程序集）
跨边界通信需 MarshalByRefObject / 序列化不需要（同一进程，纯类型边界）

核心概念：加载链

每个 ALC 都有一个名称，构成一个加载链。当你在一个 ALC 中尝试加载程序集时：

MyPluginContext（自定义 ALC）
  │ 尝试加载 PluginUtils.dll
  │
  ├── 自己先处理（Load 重载 → 从 plugins/ 目录加载）
  │   └── 如果返回 null（表示"我不处理这个"）
  │
  └── 回退到 Default ALC
      └── 从应用程序目录加载

插件系统最小示例

// 自定义 ALC：从指定目录加载程序集
class PluginLoadContext : AssemblyLoadContext
{
    private readonly string _pluginPath;

    public PluginLoadContext(string pluginPath)
        : base(isCollectible: true)  // ← 关键：允许卸载！
    {
        _pluginPath = pluginPath;
    }

    protected override Assembly? Load(AssemblyName name)
    {
        string dllPath = Path.Combine(_pluginPath, name.Name + ".dll");
        if (File.Exists(dllPath))
            return LoadFromAssemblyPath(dllPath);  // 从文件加载

        return null;  // 回退到 Default ALC
    }
}

// 使用：加载插件 → 执行 → 卸载
var context = new PluginLoadContext("./plugins/greeter");
Assembly pluginAssembly = context.LoadFromAssemblyName(
    new AssemblyName("GreeterPlugin"));
// ... 执行插件代码 ...
context.Unload();  // 卸载整个 ALC 及其中所有程序集
// 注意：Unload 是异步的，实际释放要等 GC 回收
💡 isCollectible: true 是关键——不设这个标志，ALC 中的程序集永远不能被 GC 回收。 这是 Framework 4.8 开发者最容易踩的坑。另外即使调了 Unload()，程序集也不会立即释放——需要等 GC 检测到 ALC 和所有相关对象不再被引用后才回收。

典型应用场景

场景怎么做FW 4.8 时代怎么搞

实际开发中什么情况下用到 ALC？

大部分开发者不会直接写 ALC 代码，但你已经在用它了。而且有几个场景不自己写就绕不过去。

你已经在用的（框架替你做）

框架ALC 在背后做什么
ASP.NET Core 热重载 每次 Ctrl+S 保存 .cs 文件：卸载旧 ALC（含旧版本程序集）→ 等待 GC 回收 → 新建 ALC 加载新编译的程序集。旧请求在旧 ALC 上跑完自然结束，新请求走新 ALC。

💡 什么时候不需要 ALC？普通服务注入（DI 容器管理生命周期就够了）、只想热加载配置（JSON 文件监听就够了）、微服务架构（进程隔离天然优于 ALC 隔离）。规则：当你需要"加载一个 .dll，用完后能彻底卸载它"时，ALC 是唯一正确解。其他场景一般不需要碰。

关键术语

Gen0 / Gen1 / Gen2
GC 的三代回收机制。Gen0：新创建的小对象，回收最频繁（暂停 <1ms）。Gen1：熬过一次 Gen0 回收的对象，作为 Gen0 和 Gen2 之间的缓冲。Gen2：熬过 Gen0 和 Gen1 各一次回收后提升至此。存放静态变量、长期缓存等，回收触发 full GC。
提升（Promotion）
回收时，存活对象从当前代"升"到更老一代的过程。Gen0 存活 → Gen1；Gen1 存活 → Gen2。提升意味着对象会活得更久，所以别让临时对象不小心升到 Gen2。
SOH（Small Object Heap）
存放 < 85,000 字节对象的堆区域，支持三代回收和压缩（移动存活对象消除碎片）。
LOH（Large Object Heap）
存放 ≥ 85,000 字节（即 ≳83KB）对象的堆区域。对象直接标记为 Gen2，默认不压缩。碎片可能导致 OOM。现代 .NET 支持手动压缩。
POH（Pinned Object Heap）
.NET 5 新增——存放被 fixed 固定（不能移动）的对象。将"钉子"从 SOH 中分离出来，SOH 回收效率更高。
压缩（Compaction）
GC 回收后将存活对象移到一起、消除碎片空洞的过程。压缩后空闲空间连续，分配只需移动指针（极快），对象物理位置更近（缓存友好）。代价是压缩时需暂停线程并 memcpy 存活对象。SOH 总是压缩，LOH 默认不压缩（移动大对象太贵），POH 不压缩（固定了不能移动）。
Span<T>
ref struct，只能存在于栈上。可以提供对托管堆、栈、非托管内存的类型安全零分配视图。Slice 不复制数据。不能作为类字段、不能在 async 中使用。
Memory<T>
Span<T> 的堆安全版本。普通 struct，可以存储在类字段中、在 async 方法中跨 await 使用。通过 .Span 属性在同步回调中取出 Span 做实际读写。
AssemblyLoadContext（ALC）
现代 .NET 中替代 AppDomain 的程序集加载边界。轻量、可单独卸载（isCollectible: true）、不需要跨边界序列化。用于插件系统、热重载、程序集版本隔离。
Default ALC
应用程序启动时的默认 AssemblyLoadContext，从应用程序目录加载程序集。所有自定义 ALC 的回退目标。
