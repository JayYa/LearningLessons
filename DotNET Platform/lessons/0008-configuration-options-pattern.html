第 8 课：Options 模式——强类型、热重载、校验

模块：配置系统（2/2） |  预计阅读/练习时间：28 分钟

上一课我们学会了从多个源聚合配置、用"最后胜出"覆盖。但 config["Database:ConnectionString"] 仍然有两个痛点：分散的魔法字符串和没法热重载。这一课引入 Options 模式—— 把配置映射到强类型 POCO 对象，并通过三个接口精准控制重载行为。

  • 理解 IOptions<T>、IOptionsSnapshot<T>、IOptionsMonitor<T> 的精确区别
  • 掌握 services.Configure<T>() 的标准注册方式
  • 学会 IOptionsSnapshot 实现"改 JSON 自动生效"（热重载）
  • 学会 Options 校验——启动时确保配置完整，而非运行时才发现缺字段

为什么需要 Options 模式？

直接把 IConfiguration 注入到每个服务里，代码很快变成这样： 

// 🔴 反模式：到处散落魔法字符串
public class UserService
{
    public UserService(IConfiguration config)
    {
        var conn = config["Database:ConnectionString"];   // "Database:ConnectionString"
        var timeout = config.GetValue<int>("Database:CommandTimeout");  // 又重复一次路径
        var retries = config.GetValue<int>("Database:MaxRetryCount");
        // 如果 JSON 里把 "CommandTimeout" 改成了 "Timeout"……
        // 编译通过，运行时拿到 0——静默出错
    }
}

// ✅ Options 模式：注入一个强类型对象——编译器保护你
public class UserService
{
    public UserService(IOptionsSnapshot<DatabaseOptions> options)
    {
        var db = options.Value;
        var conn = db.ConnectionString;   // ← 属性名拼错？编译器直接报错
        var timeout = db.CommandTimeout;
    }
}

三个价值：强类型（编译期检查） → 热重载（改 JSON 不重启） → 校验（启动时失败，而非凌晨 3 点因为缺配置炸掉）。

三个接口，一句话区分

// 同一个 DatabaseOptions 类，三种注入方式——行为完全不同
public class DatabaseOptions
{
    public string ConnectionString { get; set; }
    public int CommandTimeout { get; set; } = 30;
    public bool EnableRetryOnFailure { get; set; }
}
接口生命周期热重载？变更通知？一句话
IOptions<T> Singleton ❌ ❌ "程序启动时拍一张照，之后一直用这张"
IOptionsSnapshot<T> Scoped ✅ ❌ "每个请求重新拍一张——下次请求看到新配置"
IOptionsMonitor<T> Singleton ✅ ✅ OnChange 回调 "配置改了会通知我——我能立即反应"
💡 选择口诀：不需要热重载→IOptions<T>；需要热重载但不能是 Singleton→IOptionsSnapshot<T>（注意它本身是 Scoped）；Singleton 里要热重载→IOptionsMonitor<T>。 Scoped 注入 Snapshot，Singleton 注入 Monitor。

注册：从配置到 POCO

// NuGet: Microsoft.Extensions.Options.ConfigurationExtensions

var builder = WebApplication.CreateBuilder(args);

// 方式一：绑定到 Configuration 的某个 Section（最常用）
builder.Services.Configure<DatabaseOptions>(
    builder.Configuration.GetSection("Database"));

// 方式二：混合——Section + 代码覆盖
builder.Services.Configure<DatabaseOptions>(opts =>
{
    // 先读 JSON
    builder.Configuration.GetSection("Database").Bind(opts);
    // 代码中强制覆盖某些值
    opts.EnableRetryOnFailure = true;
});

// 方式三：纯代码（没有 JSON）
builder.Services.Configure<DatabaseOptions>(opts =>
{
    opts.ConnectionString = "Server=localhost;...";
    opts.CommandTimeout = 60;
});

// 无论哪种方式，注入的都是同一个 T——注入 IOptionsSnapshot<DatabaseOptions> 就能拿到

IOptions<T>：启动时快照，之后不变

// IOptions<T> 是 Singleton——程序启动时"拍一张照"
// JSON 文件改了？代码里还是旧的值。直到程序重启。

public class AuthService
{
    private readonly AuthOptions _options;

    public AuthService(IOptions<AuthOptions> options)
    {
        _options = options.Value;  // ← 启动时快照，之后 _options 不变
    }
}

为什么需要它？ 有些配置就不该在运行时变——JWT 密钥、加密算法参数、第三方 SDK 初始化参数。改了应该走发布流程，不是偷偷热重载。

IOptionsSnapshot<T>：每个 Scope 重新读

// IOptionsSnapshot<T> 是 Scoped——每个请求（Scope）重新从 Provider 读取
// JSON 文件改了？下一个请求自动用新值

public class ReportService
{
    private readonly DatabaseOptions _db;

    // ⚠️ 注意：IOptionsSnapshot 是 Scoped！
    // 不能注进 Singleton 服务——Semantic Captive Dependency（回顾第 4 课）
    public ReportService(IOptionsSnapshot<DatabaseOptions> options)
    {
        _db = options.Value;  // ← 每次构造 ReportService（一个新 Scope）时重新读
    }
}

工作流程：

请求 1 ── Scope A ── IOptionsSnapshot<T>.Value ── 读取 JSON（Timeout=30）
  │
  │  改 JSON → Timeout=60
  │
请求 2 ── Scope B ── IOptionsSnapshot<T>.Value ── 重新读取 JSON（Timeout=60 ✅）

→ 不重启，新请求自动拿到新配置
⚠️ 生命周期陷阱：IOptionsSnapshot 本身是 Scoped。如果你把它注入 Singleton 服务， 就会制造 Semantic Captive Dependency——Snapshot 在 Singleton 构造时"被囚禁"，此后再也不更新。 正确做法：Singleton 里用 IOptionsMonitor<T> 而非 IOptionsSnapshot<T>。

IOptionsMonitor<T>：Singleton 友好的热重载

前两个接口覆盖了 90% 的场景。但有一个缝——Singleton 服务也需要热重载怎么办？ IOptionsSnapshot 是 Scoped，不能用；IOptions 是 Singleton 但不热重载。 IOptionsMonitor 填补了这个缝：Singleton + 实时热重载 + 变更通知。 

// IOptionsMonitor<T> —— Singleton 生命周期，但每次 .CurrentValue 都反映最新配置
public class CacheWarmer : BackgroundService  // BackgroundService 本质是 Singleton
{
    private readonly IOptionsMonitor<DatabaseOptions> _options;
    private readonly ILogger<CacheWarmer> _logger;

    public CacheWarmer(
        IOptionsMonitor<DatabaseOptions> options,
        ILogger<CacheWarmer> logger)
    {
        _options = options;
        _logger = logger;

        // ✅ 注册变更回调——JSON 文件改了立即收到通知
        _options.OnChange(async (newOpts, name) =>
        {
            _logger.LogInformation(
                "数据库配置已变更！新连接串：{Conn}", newOpts.ConnectionString);
            // 可以立即重建连接池、刷新缓存、调整线程数……
        });
    }

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // 每次都拿最新值
            var db = _options.CurrentValue;  // ← 不是 .Value，是 .CurrentValue
            await Task.Delay(db.CommandTimeout * 1000, ct);
        }
    }
}

IOptionsMonitor vs IOptionsSnapshot：

IOptionsSnapshotIOptionsMonitor
生命周期ScopedSingleton
获取当前值.Value（属性）.CurrentValue（属性）
变更通知❌ 无回调.OnChange(callback) 注册回调
典型使用Controller / Service（Scoped）HostedService / Singleton 组件
何时重新读取每个 Scope 创建时配置源变更时（实时）

Named Options：同一 POCO，多份配置

同一个 CacheOptions 类，Redis 和本地内存的配置不同怎么办？ Options 模式支持"命名选项"——同一个 POCO 类型，注册多份。 

// 定义——一个 POCO 类就够了，不用写两个
public class CacheOptions
{
    public string Host { get; set; }
    public int Port { get; set; }
    public int ExpirationMinutes { get; set; }
}

// 注册——不同 name，绑定到不同 Section
services.Configure<CacheOptions>("Redis",     // name = "Redis"
    config.GetSection("Cache:Redis"));
services.Configure<CacheOptions>("Local",     // name = "Local"
    config.GetSection("Cache:Local"));

// 注入——明确取哪个 name
public class CacheService
{
    public CacheService(
        IOptionsMonitor<CacheOptions> options)  // 未指定 name —— 取默认（无 name 那个）
    {
        var redis = options.Get("Redis");       // 按 name 获取
        var local = options.Get("Local");

        // IOptionsSnapshot 同理—— .Get("name")
    }
}

// 对应的 JSON
{
  "Cache": {
    "Redis": {
      "Host": "redis.contoso.com",
      "Port": 6379,
      "ExpirationMinutes": 15
    },
    "Local": {
      "Host": "localhost",
      "Port": 6379,
      "ExpirationMinutes": 5
    }
  }
}

Options Validation：启动时校验

这是 Framework 4.8 时代做不到的：应用启动时就检查配置是否完整/有效，而不是等到运行时 某个请求因为 ConnectionString 为空而炸 500。尽早失败，尽早发现，尽早修复。 

// 方式一：Data Annotations 标记（适合 80% 场景）
public class DatabaseOptions
{
    [Required(ErrorMessage = "数据库连接串不能为空")]         // ← 必填
    public string ConnectionString { get; set; }

    [Range(1, 300, ErrorMessage = "超时时间必须在 1-300 秒之间")]
    public int CommandTimeout { get; set; } = 30;

    [RegularExpression(@"^Server=", ErrorMessage = "连接串必须以 Server= 开头")]
    public string AdditionalConnectionString { get; set; }
}

// 注册时加上 ValidateOnStart
services.AddOptions<DatabaseOptions>()
        .Bind(config.GetSection("Database"))
        .ValidateOnStart();  // ← 启动时立即校验！校验失败 → 应用启动失败

// 如果连接串为空，你的应用会在启动时抛出 OptionsValidationException：
// "DatabaseOptions.ConnectionString: 数据库连接串不能为空"
// 而不是等某个用户访问功能时 500

// 方式二：自定义复杂校验逻辑（跨字段校验）
services.AddOptions<DatabaseOptions>()
        .Bind(config.GetSection("Database"))
        .Validate(opts =>
        {
            if (opts.EnableRetryOnFailure && opts.MaxRetryCount <= 0)
                return false;  // 启用了重试但没设置次数——不合理
            return true;
        }, "启用了 EnableRetryOnFailure 但 MaxRetryCount 必须大于 0");

// 方式三：IValidateOptions<T> 接口（注入其他服务的复杂校验）
public class DatabaseOptionsValidator : IValidateOptions<DatabaseOptions>
{
    private readonly IConfiguration _config;

    public DatabaseOptionsValidator(IConfiguration config)
    {
        _config = config;
    }

    public ValidateOptionsResult Validate(string name, DatabaseOptions options)
    {
        // 可以访问其他配置、其他服务——比 Data Annotations 更灵活
        if (string.IsNullOrEmpty(options.ConnectionString))
            return ValidateOptionsResult.Fail("连接串是必填的！");

        return ValidateOptionsResult.Success;
    }
}

// 注册验证器
services.AddSingleton<IValidateOptions<DatabaseOptions>, DatabaseOptionsValidator>();
💡 ValidateOnStart = 什么也不做？只有当 Options 被第一次解析时才会触发校验。 Singleton 服务通常在第一次注入时解析——也就是启动时。但如果你只想"校验一下依赖图，实际上不用这些服务"， 可能需要手动触发一次解析或依赖 Host 的默认行为（ASP.NET Core 启动时会解析大量服务）。

Framework 4.8 时代 vs 现代 .NET Options

Framework 4.8现代 .NET Options

检查理解

❓ IOptions<T> 注入后，appsettings.json 改了——代码里拿到的是新值还是旧值？
新值——因为配置系统支持热重载
取决于 reloadOnChange 是否为 true
抛异常——运行时不支持配置变更
旧值——IOptions 是启动时快照，不热重载
❓ 一个 Singleton 服务需要感知配置热重载，应该注入哪个接口？
IOptions<T>——Singleton 就用 Singleton 的 Options
IOptionsSnapshot<T>——因为 Snapshot 支持热重载
IOptionsMonitor<T>——Singleton 生命周期 + 实时热重载
IConfiguration——绕过 Options 直接读
❓ services.AddOptions<T>().Bind(...).ValidateOnStart() ——配置文件缺了必填字段，应用会怎样？
正常运行，只是那个字段为 null/default
运行时第一次访问该字段时抛异常
应用启动失败——抛出 OptionsValidationException
输出一个警告日志，然后继续启动
❓ IHostedService（Singleton）需要监听数据库连接串变化并重建连接池，选哪个？
IOptions<DatabaseOptions>.Value
IOptionsSnapshot<DatabaseOptions>.Value
IOptionsMonitor<DatabaseOptions>——CurrentValue + OnChange 回调
IServiceProvider.GetRequiredService + 手动 ReadJson

关键术语

Options 模式
将配置映射到强类型 POCO 对象，通过 DI 注入的架构模式。核心 NuGet 包：Microsoft.Extensions.Options 和 Microsoft.Extensions.Options.ConfigurationExtensions。解决了魔法字符串、无类型安全、无法热重载的痛点。
IOptions<T>
Singleton 生命周期，启动时快照——创建后 JSON 文件变化不会更新 .Value。适合不该在运行时变的配置（JWT 密钥、第三方 SDK 初始化参数），或者你确定配置在部署后不变。
IOptionsSnapshot<T>
Scoped 生命周期，每个 Scope 构造时重新从配置源读取。同一请求内 .Value 不变，下一个请求自动拿到新值。不能注入 Singleton 服务——否则变成 Semantic Captive，失去热重载能力。
IOptionsMonitor<T>
Singleton 生命周期，但每次访问 .CurrentValue 都反映最新配置。额外提供 .OnChange(callback) 注册变更回调——配置源变化时立即收到通知。适合 Singleton 组件（HostedService、缓存管理器）需要热重载。
Named Options
同一 POCO 类型，通过 name 参数注册多份配置。注入时用 .Get("name") 获取指定那份。典型场景：多个数据库连接、多个缓存后端、多个外部 API 端点——都映射到同一个 Options 类，按名称区分。
ValidateOnStart
.ValidateOnStart() 在 Options 首次被解析时立即运行 Data Annotations 校验（[Required]、[Range]、[RegularExpression]）。校验失败抛 OptionsValidationException——应用启动失败。Fail Fast 哲学：配置问题应该在部署时发现，不是凌晨 3 点。
IValidateOptions<T>
自定义校验逻辑接口。实现 Validate(string name, T options) 方法，返回 ValidateOptionsResult.Success 或 .Fail("原因")。可以注入其他服务——实现跨字段校验和外部依赖校验。
