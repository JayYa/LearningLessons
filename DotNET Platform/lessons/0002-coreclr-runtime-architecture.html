第 2 课：运行时架构

模块：运行时架构（1/2） |  预计阅读/练习时间：15 分钟

.NET Framework 4.8 的 CLR 是一个只跑在 Windows 上、20 年没大改的庞然大物。 现代 .NET 把它拆了重写——CoreCLR 不仅是跨平台的，GC、JIT、部署方式都是可选的、可配置的。 这一课帮你建立心智模型：当你用 dotnet run 启动一个程序时，底层到底发生了什么。

  • 理解 CoreCLR 为什么要重写，而不是在旧 CLR 上修修补补
  • 知道两种 GC 模式（Workstation / Server）的区别和什么时候切
  • 理解分层编译默认在做什么——为什么冷启动快、热路径也快
  • 建立 JIT → R2R → NativeAOT 的编译光谱概念

起点：Framework 4.8 CLR 为什么必须重写？

旧 CLR 身上背着三个不可调和的包袱：

包袱为什么改不了CoreCLR 怎么解决
Windows 耦合 CLR 内部大量调用 Win32 API（内存管理、线程调度、文件 IO 都走 OS） 所有 OS 交互抽象为 PAL（Platform Abstraction Layer），一套接口，多套实现
单 GC 模式 Workstation GC 一个线程跑回收，Server 机器也这样——浪费多核 Workstation / Server 两种 GC 可切换，Server GC 每核一个堆，并行回收
JIT 一刀切 要么全 JIT（启动慢），要么全 NGen（镜像大、不灵活） 分层编译：先快编保证启动，后台再重编优化热路径
💡 一句话概括：Framework 4.8 CLR 是一座 20 年没拆过的老房子——地基是 Windows，管线是单线程，装修是 JIT 一刀切。 CoreCLR 拆了重盖：地基换成 PAL（跨平台），管线可切（Workstation/Server GC），装修分层（tiered JIT + R2R + NativeAOT）。

GC 模式：这次你真的要关心

在 Framework 4.8 中大多数开发者从来不碰 GC 配置——默认就够了。现代 .NET 中选错 GC 模式可能是 10× 级别的吞吐差异。

两种模式

Workstation GC
  • 一个堆，一个 GC 线程
  • 回收时暂停所有用户线程
  • 延迟低（暂停短），吞吐低
  • 默认模式
  • 适合：桌面应用、单实例服务
Server GC
  • 每核一个堆，每核一个 GC 线程
  • 所有 GC 线程并行回收
  • 吞吐高，但每次暂停稍长
  • 需显式开启
  • 适合：Web 服务、后台任务、高吞吐场景

怎么切？

在 csproj 里加一行：

<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
</PropertyGroup>

或者用 runtimeconfig.json：

{
  "runtimeOptions": {
    "configProperties": {
      "System.GC.Server": true
    }
  }
}
⚠️ 注意：ASP.NET Core 项目模板默认已经开了 Server GC（通过 Microsoft.NET.Sdk.Web SDK）。 控制台应用和类库默认是 Workstation GC——你如果用 Generic Host 跑后台服务，记得自己开关。

Background GC

两种模式都支持后台 GC（默认开启）。意思是 Gen2 回收（最慢的那种）可以在后台线程上做，不暂停用户线程。只有 Gen0/Gen1 回收（快）才会短暂暂停。

如果你发现 Gen2 回收的暂停时间不可接受，可以关掉后台 GC（让 Gen2 也暂停，但总时长可能更短）：

<ConcurrentGarbageCollection>false</ConcurrentGarbageCollection>

这对应 Framework 4.8 的 <gcConcurrent enabled="false"/>——概念一样，配置路径不同。

JIT 编译：你写的 IL 怎么变成机器码？

Framework 4.8 中的 JIT：调用一个方法 → 即时编译 → 执行。简单粗暴。问题是首次调用慢——大型应用启动时要编译大量方法。

💡 "首次调用慢"是运行时的事，不是编译时。dotnet build 只是把你的 C# 转成 IL（中间语言），这一步很快，跟 JIT 无关。 JIT 的"即时编译"发生在程序运行时、方法第一次被调用的时候——跟 Debug 还是 Release 没关系（Release 下优化更多反而编译更慢，只是生成的代码跑得更快）。 打个比方：JIT 不是你打开 IDE 加载项目慢，而是用户双击你的 exe 后第一次弹窗慢。 分层编译解决的就是这个运行时的冷启动问题：Tier 0 快编先让程序跑起来，热方法后台升 Tier 1。

现代 .NET 的 JIT 完全不同——分层编译（Tiered Compilation）是默认：

方法首次调用
  │
  ▼
Tier 0：Quick JIT（极快编译，不优化）
  │  目标：让启动尽可能快
  │
  ▼
运行时统计：这个方法被调了多少次？
  │
  ├── 冷方法（没被反复调）→ 保持 Tier 0，不浪费编译时间
  │
  └── 热方法（调用次数 > 阈值）→ Tier 1：Optimizing JIT
       目标：全面优化（内联、循环展开、边界检查消除）

结果是：启动快（Tier 0），热路径也快（Tier 1），冷代码不浪费优化时间。

你不需要做任何事——.NET Core 3.0 起默认开启。如果想关闭（某些低延迟场景不想有后台编译线程）：

<TieredCompilation>false</TieredCompilation>
💡 .NET 6 起引入了 Dynamic PGO（动态 Profile-Guided Optimization）——Tier 0 时插入探针，Tier 1 编译时根据真实运行时数据做优化。 比如发现某个虚方法调用 99% 是同一个具体类型，就直接去虚拟化（devirtualization）。CSProj 加 <TieredPGO>true</TieredPGO> 开启。

编译光谱：JIT → R2R → NativeAOT

这是 Framework 4.8 用户最陌生的概念。在现代 .NET 中，代码怎么从 IL 变机器码，有三种选择：

JITR2RNativeAOT
编译时机运行时发布时预编译 IL 布局 + 运行时轻量 JIT发布时全编译
启动速度慢较快极快
峰值性能最高（tiered + PGO）高（再加 tiered JIT 可达峰值）高（但无 PGO 优化）
文件体积最小中（多预编译代码）大（含整个运行时）
需要运行时安装是是否（自包含）
反射/Emit全支持全支持受限
适用场景开发、桌面、通用SDK 库、桌面应用、服务CLI 工具、微服务、容器

R2R：Framework 的 NGen 重生版

R2R 是 Framework 时代 NGen 的精神续作，但做得更好：把 IL 编译成中间态的预编译代码，运行时只需做少量修正（地址重定位、跨程序集引用解析），而非从头编译。

用翻译作类比，三种模式的区别一目了然：

模式类比编译实际发生
纯 JIT现场翻译——外国人（IL）来了才找翻译（JIT），边说边翻运行时每个方法首次调用时编译
R2R提前翻译好了讲稿，现场只填几个名字和日期发布时预编译大部分，运行时只做轻量修正
NativeAOT直接给对方一个母语者，不需要翻译发布时全部编译好，运行时就是纯原生代码
# 发布时开启 R2R
dotnet publish -c Release -p:PublishReadyToRun=true

R2R 代码 仍然可以叠加分层编译——先跑 R2R 的 Tier 0 代码保证启动，热方法再由 JIT 重编译到 Tier 1。这是现代 .NET 的默认行为。

NativeAOT：.NET 编译成独立 exe

如果你想要一个没有依赖、直接启动、体积可控的单一可执行文件：

<PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>
dotnet publish -r win-x64 -c Release

代价是：反射受限、不能动态加载程序集、不能用 Expression.Emit。而且不是所有 NuGet 包都标记了 AOT 兼容。但有AOT 分析器（IsAotCompatible）在编译时帮你检查哪些代码不兼容。

💡 和 Framework 的 ngen.exe 有什么不同？NGen 生成的代码仍然依赖完整的 CLR 运行时，只是把 IL 提前转成了机器码。 NativeAOT 是把整个运行时也裁剪、链接、编译进去——发布出来的是一个不依赖任何 .NET 运行时的独立二进制。

选型决策流程

你的应用是什么？
│
├── 桌面应用 / 通用后端服务
│   └── 默认 JIT + 分层编译 ✅
│       （开发体验最好，峰值性能最高）
│
├── 对启动速度有要求（SDK 工具、CLI）
│   └── R2R（发布时预编译）
│       或 NativeAOT（如果依赖兼容）
│
├── 容器化微服务 / 短生命周期
│   └── NativeAOT（镜像小、启动快）
│       ⚠️ 先检查所有依赖是否 AOT 兼容
│
└── 控制台后台服务 / Worker
    └── Server GC ← 别忘了这个！
        （控制台模板默认 Workstation GC）

检查理解

❓ 你的控制台应用用 Generic Host 跑后台任务，高并发下吞吐很差。最可能的原因？
分层编译默认关闭了
默认是 Workstation GC，应该切到 Server GC
没有开启 NativeAOT
Background GC 没关
❌ 以下哪个是错误的？
Tier 0 编译快但不优化，Tier 1 后台优化热方法
R2R 可以在运行时叠加分层编译
NativeAOT 不支持 Assembly.LoadFile
Server GC 是 .NET 的默认 GC 模式

关键术语

CoreCLR
现代 .NET 的运行时引擎。从 .NET Framework CLR 分叉后重写，跨平台、模块化。源码在 dotnet/runtime。
PAL（Platform Abstraction Layer）
CoreCLR 与操作系统的抽象层——所有 OS 调用（线程、内存、IO）走 PAL 接口，Windows/Linux/macOS 各有实现。
Workstation GC / Server GC
两种 GC 模式。Workstation：一个堆一个线程，低延迟。Server：每核一个堆一个线程，高吞吐。ASP.NET Core 默认 Server，控制台默认 Workstation。
分层编译（Tiered Compilation）
JIT 的方法编译策略：Tier 0 快速编译优先启动速度，热方法升到 Tier 1 做全面优化。.NET Core 3.0+ 默认开启。
R2R（ReadyToRun）
发布时预编译 IL 为中间态机器码，运行时只需轻量修正。类似 Framework 的 NGen，但可叠加分层编译。
NativeAOT
发布时把 IL 和裁剪后的运行时全部编译为原生机器码，生成独立 exe。不需要安装 .NET 运行时。代价是反射和动态代码生成受限。
Dynamic PGO
动态 Profile-Guided Optimization——Tier 0 时插探针，Tier 1 根据真实运行时数据做优化（如去虚拟化、内联决策）。
