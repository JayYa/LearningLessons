第一部分：System.Threading.Channels

它解决的问题

一个"数据生产者"和一个"数据消费者"跑在不同的异步循环里，中间需要一条异步、线程安全、有容量控制的队列。 Framework 4.8 的工具箱里没有满足这三个条件的东西：

Framework 4.8问题
BlockingCollection<T>Take() 阻塞线程——消费者必须独占一根线程，无法 await
ConcurrentQueue<T> + 轮询没有"等有数据"的原语，要么 Thread.Sleep 轮询，要么自己拿 SemaphoreSlim 拼
BufferBlock<T>（TPL Dataflow）能用，但是重量级流水线框架的一部分，单独用一个队列杀鸡用牛刀

Channel<T>（System.Threading.Channels，.NET Core 3.0+ 内置，Framework 4.8 可装同名 NuGet）就是那个"只做队列、全异步"的原语。 Stephen Toub 在 An Introduction to System.Threading.Channels 里用 20 行代码从零实现了一个，值得读——它本质就是 ConcurrentQueue + 一个可 await 的信号。 

生产者 BackgroundService                Channel<Job>                    消费者 BackgroundService
────────────────────────         ──────────────────────────         ───────────────────────────
await writer.WriteAsync(job) ──→  [ job | job | job | ... ]  ──→  await foreach (var job in
                                   ↑容量满时 WriteAsync 挂起            reader.ReadAllAsync(ct))
writer.Complete()            ──→  标记"不再有数据"           ──→  ReadAllAsync 排空后循环自然结束

三行 API

// 创建：两种
var unbounded = Channel.CreateUnbounded<Job>();               // 无上限——生产快于消费时内存无限涨
var bounded   = Channel.CreateBounded<Job>(new BoundedChannelOptions(capacity: 100)
{
    FullMode     = BoundedChannelFullMode.Wait,               // 满了：Wait（背压，默认）/ DropOldest / DropNewest / DropWrite
    SingleReader = true,                                      // 承诺只有一个消费者 → 内部走无锁快路径
    SingleWriter = false,
});

// 写：Writer 一端
await channel.Writer.WriteAsync(job, ct);                     // 满了就异步等（Wait 模式）
bool ok = channel.Writer.TryWrite(job);                       // 不等，满了返回 false
channel.Writer.Complete();                                    // 宣告结束；之后 Write 抛 ChannelClosedException
channel.Writer.TryComplete(exception);                        // 带错误结束，消费者的 ReadAllAsync 会抛出它

// 读：Reader 一端
await foreach (var job in channel.Reader.ReadAllAsync(ct))    // 推荐：排空 + Complete 后自动退出
    await Handle(job);

while (await channel.Reader.WaitToReadAsync(ct))              // 手动版：等到有数据或已 Complete
    while (channel.Reader.TryRead(out var job)) { ... }       //   然后同步 drain，减少 await 次数
⚠️ 默认用 Bounded。 Unbounded 的意思是"生产者永远不会被拦"，代价是消费者跟不上时队列吃光内存——生产环境里这是一次事故，不是一个选项。 Bounded + Wait 就是背压：消费者慢下来，生产者自动慢下来。只有确定生产量有天然上限（比如每秒一条心跳）才用 Unbounded。 官方文档 Channels 的选项表把四种 FullMode 讲得很清楚。

接进 Host：一个 Channel 连两个 BackgroundService

// Program.cs —— Channel 本身是 Singleton；把两端拆开注册，让服务只依赖自己需要的那一端
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100) { SingleReader = true });
builder.Services.AddSingleton(channel.Reader);
builder.Services.AddSingleton(channel.Writer);

builder.Services.AddHostedService<JobConsumer>();     // 先注册 → 后关闭（第 10 课 LIFO）
builder.Services.AddHostedService<JobProducer>();     // 后注册 → 先关闭，关闭时 Complete()

// 生产者：只看得到 Writer
public sealed class JobProducer(ChannelWriter<Job> writer) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        try
        {
            using var timer = new PeriodicTimer(TimeSpan.FromSeconds(1));
            while (await timer.WaitForNextTickAsync(stoppingToken))
                await writer.WriteAsync(new Job(DateTime.UtcNow), stoppingToken);
        }
        catch (OperationCanceledException) { }
        finally
        {
            writer.Complete();                             // 关键：告诉消费者"没有了"
        }
    }
}

// 消费者：只看得到 Reader
public sealed class JobConsumer(ChannelReader<Job> reader, ILogger<JobConsumer> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // 注意：这里故意【不传】stoppingToken——让它把队列里剩下的 job 处理完再退出，
        // 退出条件是生产者 Complete()。如果你希望关闭时立刻丢弃余量，就传进去。
        await foreach (var job in reader.ReadAllAsync())
            log.LogInformation("Handled {JobAt}", job.CreatedAt);
    }
}

注意关闭顺序怎么和第 10 课接上：Host 按注册倒序关闭 → 先停 JobProducer（它的 finally 调 Complete()）→ 再停 JobConsumer，此时 ReadAllAsync 已经在排空最后几条，排完自动退出。整个过程不丢数据，也不需要任何锁。 如果反过来注册，消费者先被取消，队列里的东西就丢了。这是 HostOptions.ShutdownTimeout（默认 30 秒）要覆盖的时间。

💡 这就是 ASP.NET Core 里"后台队列"的标准做法。 官方文档 Queued background tasks 的 IBackgroundTaskQueue 内部就是一个 Channel<Func<CancellationToken, ValueTask>>： Controller 往 Writer 塞工作，一个 BackgroundService 从 Reader 消费。你已经能自己写出来了。

第二部分：PeriodicTimer

上面生产者里已经用了。它是 .NET 6 加的，专门解决 BackgroundService 里"每 N 秒做一件事"的三个老写法各自的毛病 （API 文档）：

老写法毛病
while (true) { DoWork(); await Task.Delay(1000, ct); }周期 = 1 秒 + DoWork 耗时，会漂移；每次 Delay 分配一个 Timer 对象
new System.Threading.Timer(callback, ...)回调是同步 void，async 得写 async void；回调可能重叠——上一次没跑完下一次就来了
System.Timers.TimerFramework 时代 WinForms 味的 API，Elapsed 事件同样重叠、异常被吞
using var timer = new PeriodicTimer(TimeSpan.FromSeconds(5));
while (await timer.WaitForNextTickAsync(stoppingToken))    // 取消时抛 OperationCanceledException；Dispose 后返回 false
{
    await DoWorkAsync(stoppingToken);                       // 跑多久都行：下一次 tick 要等这次 await 回到循环头才会被观察到
}                                                           // → 天然不重叠；如果 DoWork 超过周期，中间错过的 tick 只算一次
// .NET 8+：timer.Period = TimeSpan.FromSeconds(10);        // 运行中可改周期（比如从 IOptionsMonitor 热重载）

规则：一个 PeriodicTimer 只能有一个等待者（同时两个 WaitForNextTickAsync 会抛）。它是为"一个循环一个 timer"设计的，不是事件广播器。

第三部分：Span / Memory 在 I/O 里的实际用法

第 3 课和 Span 速查 讲了类型本身。这里回答"BCL 里哪些 API 已经吃 Span 了、我该怎么喂"。 记一条原则就够：凡是 Framework 时代接 byte[] + offset + count 三个参数的 API，现代 .NET 都有一个接 Span<byte> / Memory<byte> 的重载； 同步用 Span，异步用 Memory（Span 是 ref struct，不能跨 await）。 

// 1. Stream：同步 Span，异步 Memory —— 配 ArrayPool 是标准搭配
byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);          // 拿到的数组 ≥ 4096，可能更大，内容是脏的
try
{
    int n;
    while ((n = await stream.ReadAsync(buffer.AsMemory(), ct)) > 0)   // Memory 重载，.NET Core 2.1+
        Process(buffer.AsSpan(0, n));                                    // 只看实际读到的那段
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer);                   // 必须归还；别在归还后继续用
}

// 2. 文本编码：Encoding 直接写进 Span，不再 GetBytes() 分配新数组
Span<byte> utf8 = stackalloc byte[256];                    // 小缓冲区栈上分配，零 GC
int written = Encoding.UTF8.GetBytes(text.AsSpan(), utf8);
await stream.WriteAsync(utf8.Slice(0, written).ToArray(), ct);  // ⚠️ 异步边界要么 ToArray，要么一开始就用 ArrayPool + Memory

// 3. 解析：字符串切片不再产生子串
ReadOnlySpan<char> line = "id=42;name=foo";
int eq = line.IndexOf('=');
int semi = line.IndexOf(';');
int id = int.Parse(line.Slice(eq + 1, semi - eq - 1));      // int.Parse(ReadOnlySpan<char>)，无 Substring
// .NET 8+：直接从 UTF-8 字节解析——int.Parse(ReadOnlySpan<byte>)（IUtf8SpanParsable），跳过解码

// 4. 构造字符串：string.Create 一次分配、直接写目标内存
string hex = string.Create(bytes.Length * 2, bytes, static (span, src) =>
{
    for (int i = 0; i < src.Length; i++)
        src[i].TryFormat(span.Slice(i * 2, 2), out _, "x2");
});

这些不是"高性能专家专属"——System.Text.Json、ILogger 源生成、Kestrel、HttpClient 内部全是这套写法， 你写应用代码时主要在热路径（每请求都跑、大文件、高频循环）上用。冷路径上 Substring 和 ToArray() 完全没问题，别为了 Span 而 Span （官方使用指南）。

第四部分：System.IO.Pipelines——知道它在哪，别急着用

上面第 1 段代码有一个隐藏问题：Process(buffer.AsSpan(0, n)) 假设一次 ReadAsync 恰好读到一个完整的"消息"。 在 TCP 上这从不成立——一条消息可能分两次到，两条消息可能一次到。 正确处理需要：跨读取保留半条消息、缓冲区满了扩容、消费完把剩余部分挪到开头…… David Fowler 在 System.IO.Pipelines 文档 开头写了 40 行"正确的 ReadLine"来说明这有多难写对。

Pipelines 就是把这 40 行抽成基础设施：PipeReader 给你一个 ReadOnlySequence<byte>（可能跨多个内存块），你告诉它消费到哪、检查到哪，缓冲区管理、内存池、背压它全包。 

// 读取 stream 里以 \n 分隔的行——用 Pipelines
var reader = PipeReader.Create(stream);
while (true)
{
    ReadResult result = await reader.ReadAsync(ct);
    ReadOnlySequence<byte> buffer = result.Buffer;

    while (TryReadLine(ref buffer, out ReadOnlySequence<byte> line))   // 找 \n，切出一行，推进 buffer
        ProcessLine(line);

    reader.AdvanceTo(buffer.Start, buffer.End);   // consumed：到这为止的可以丢；examined：到这为止的我看过了，没新数据别叫我
    if (result.IsCompleted) break;
}
await reader.CompleteAsync();

什么时候该用哪个？

  拿 byte[] / Span 手工读 ──→ 消息边界固定（定长帧、整个文件一次读完、HTTP 已经帮你切好）
  Pipelines               ──→ 自己在 socket / 长流上解析协议（Redis、MQTT、自定义 TCP 协议、大文件流式解析）
  两者都不用             ──→ 你在写普通业务代码。HttpClient、Kestrel、SignalR、gRPC 内部已经用了 Pipelines，你享受结果就行

在本系列的定位里，Pipelines 是"知道它存在、知道 Kestrel 为什么快"的层次。真要用到时再回来看 David Fowler 的视频。

检查理解

🎯 上一课的教训：这四题考的是机制，不是"现代 .NET 大概会怎么做"。答之前回想课文里对应的那段代码或那句话。
❓ Channel.CreateBounded<T>(100) 用默认选项，队列满了之后生产者再调 WriteAsync 会怎样？
抛出 ChannelClosedException，生产者必须先检查 Count 再写入才安全
返回未完成的 ValueTask，生产者异步等待直到消费者读走一条为止
静默丢弃队列里最旧的一条，然后把新的写入，返回已完成的任务
阻塞当前线程直到有空位，和 BlockingCollection 的 Add 行为完全一样
❓ 生产者关闭时调 writer.Complete()，想让消费者把队列排空再退出。两个 AddHostedService 应该怎么排？
先注册生产者再注册消费者，因为启动顺序决定谁先拿到 Channel 引用
先注册消费者再注册生产者，因为关闭是倒序，生产者要先停下来
顺序无关，Host 会等所有 BackgroundService 的 ExecuteAsync 都结束再退出
顺序无关，Complete 之后 Channel 会自动把余量投递给消费者再关闭
❓ PeriodicTimer(5s) 循环里 DoWorkAsync 某次跑了 12 秒，这期间会发生什么？
第 5 秒和第 10 秒各再并发启动一次 DoWorkAsync，三次执行同时进行
错过的两个 tick 会排队，DoWorkAsync 结束后立刻连续补跑两次
不会重叠执行；错过的 tick 合并成一个，结束后下一次等待立即返回
WaitForNextTickAsync 检测到超过周期，返回 false 并结束这个循环
❓ 为什么 Stream.ReadAsync 的现代重载接 Memory<byte>，而同步的 Read 接 Span<byte>？
Memory 在异步场景下性能更好，因为它内部做了缓存避免重复分配
Span 是 ref struct 不能跨 await 存活，异步方法只能接受 Memory
历史原因：ReadAsync 先出现时还没有 Span，后来为了兼容没有改
两者可以互换，Memory 只是为了让调用方能传 ArrayPool 租来的数组

关键术语

Channel<T>
System.Threading.Channels 的异步生产者/消费者队列。Writer / Reader 两端可拆开注册到 DI。Complete() 宣告结束，ReadAllAsync 排空后自然退出。
Bounded / Unbounded / FullMode
有容量上限 vs 无上限。Bounded 满时的策略：Wait（背压，默认）/ DropOldest / DropNewest / DropWrite。默认选 Bounded。
背压（Backpressure）
消费者慢时让生产者自动慢下来的机制。Bounded Channel 的 Wait 模式、Pipelines 的 PauseWriterThreshold 都是它。
PeriodicTimer
.NET 6+ 异步周期定时器。await WaitForNextTickAsync(ct) 驱动循环；不重叠、错过的 tick 合并、单等待者；.NET 8+ 可运行时改 Period。
ArrayPool<T>.Shared
共享数组池。Rent(n) 返回 ≥ n 的脏数组，Return 必须在 finally 里；归还后不得再用。避免 LOH 分配和 Gen0 压力。
Span / Memory 重载
BCL 中 (byte[], offset, count) 三参数 API 的现代对应。同步 Span，异步 Memory——Span 是 ref struct 不能跨 await。
System.IO.Pipelines
PipeReader / PipeWriter。解决"流上的消息边界 + 缓冲区管理"问题；ReadResult.Buffer 是 ReadOnlySequence<byte>，AdvanceTo(consumed, examined) 推进。Kestrel/SignalR 内部使用；应用代码只在自写协议解析时用。
ReadOnlySequence<byte>
可能跨多个不连续内存块的只读字节序列。Pipelines 的缓冲区表示；用 SequenceReader<byte> 或 PositionOf 在其中查找分隔符。
