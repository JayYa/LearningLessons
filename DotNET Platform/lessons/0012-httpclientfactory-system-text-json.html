第一部分：HttpClient

Framework 时代的写法为什么错

HttpClient 实现了 IDisposable，于是所有人本能地写 using (var client = new HttpClient())。 在 Framework 4.8 里这曾是教科书写法，也是 .NET 世界最著名的一个坑：

每次请求 new HttpClient() + using。
释放 client 会释放底层 handler 和连接，但 TCP 连接进入 TIME_WAIT 状态（默认约 4 分钟）。高并发下端口很快耗尽——Socket 耗尽（SocketException: Only one usage of each socket address）。
全局 static HttpClient 单例，永不释放。
连接一直复用，DNS 结果被缓存在连接上。对方换了 IP（蓝绿部署、故障转移），你的进程永远打旧地址，直到重启。

两个坑指向同一个根源：连接池的生命周期没人管。短了耗尽端口，长了 DNS 陈旧。现代 .NET 有两条正路 （官方 HttpClient guidelines）：

  1. 短命 client + 工厂管 handler：IHttpClientFactory——DI 项目的默认选择，本课主角
  2. 长命 client + 连接自动轮换：new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(2) }——没有 DI 的小工具、脚本用这个

IHttpClientFactory 做了什么

你的代码            IHttpClientFactory                     底层
──────────          ────────────────────────────           ──────────────
CreateClient("x") → new HttpClient(handler)   ─┐
CreateClient("x") → new HttpClient(handler)   ─┼─ 共享同一个 ─→ HttpMessageHandler ─→ 连接池
CreateClient("x") → new HttpClient(handler)   ─┘  (按名字缓存)      │
                                                                     │ 2 分钟后
                                                     handler 过期，新请求拿新 handler；
                                                     旧 handler 等没人用了再释放 → DNS 刷新、无泄漏

官方原文（HttpClient lifetime management）： "A new HttpClient instance is returned each time CreateClient is called ... One HttpClientHandler instance is created per client name ... The default handler lifetime is two minutes." 所以 HttpClient 变成了廉价的一次性外壳： 随便 new、随便 dispose（dispose 它不会释放 handler），贵的连接池由工厂按名字缓存、按时轮换。

三种用法

// NuGet: Microsoft.Extensions.Http（ASP.NET Core 项目已隐含引用）

// ① 基本用法：注入工厂，按需创建——适合改造老代码，把 new HttpClient() 直接替换掉
builder.Services.AddHttpClient();
public sealed class Crawler(IHttpClientFactory factory)
{
    public Task<string> FetchAsync(string url) => factory.CreateClient().GetStringAsync(url);
}

// ② 命名客户端：多个不同配置的下游，按名字区分
builder.Services.AddHttpClient("github", client =>
{
    client.BaseAddress = new Uri("https://api.github.com/");
    client.DefaultRequestHeaders.UserAgent.ParseAdd("my-app");
})
.SetHandlerLifetime(TimeSpan.FromMinutes(5));           // 每个命名客户端可单独设 handler 寿命
var gh = factory.CreateClient("github");

// ③ 类型化客户端：一个类 = 一个下游 API，构造函数收 HttpClient——推荐
public sealed class GitHubClient(HttpClient http)
{
    public Task<Repo?> GetRepoAsync(string owner, string name)
        => http.GetFromJsonAsync<Repo>($"repos/{owner}/{name}");   // System.Net.Http.Json，见下半课
}
builder.Services.AddHttpClient<GitHubClient>(client =>
{
    client.BaseAddress = new Uri("https://api.github.com/");
});
// 之后任何地方直接注入 GitHubClient——它被注册为 Transient，每次拿到新 HttpClient 外壳

类型化客户端是 DI 思维的自然延伸：调用方不知道 HTTP 的存在，只依赖 GitHubClient； BaseAddress、默认头、超时、重试策略全部在注册处集中配置——和第 8 课 Options 模式把配置集中到注册处是同一个思路。

⚠️ 类型化客户端不能注入 Singleton——这是第 10 课 Scoped 陷阱的翻版。 类型化客户端是 Transient，它持有的 HttpClient 绑定了创建时的 handler；被 Singleton 捕获后， handler 永远不轮换，DNS 刷新的目的就废了（官方）。 Singleton（比如 BackgroundService）里要么注入 IHttpClientFactory 每次 CreateClient， 要么给它配 SocketsHttpHandler.PooledConnectionLifetime 让连接层自己轮换。

顺手得到的：出站中间件、重试、日志

builder.Services.AddHttpClient<GitHubClient>(c => c.BaseAddress = new Uri("https://api.github.com/"))
    .AddHttpMessageHandler<AuthHeaderHandler>()        // DelegatingHandler：出站管道，给每个请求加 token
    .AddStandardResilienceHandler();                   // NuGet: Microsoft.Extensions.Http.Resilience
                                                       // 重试 + 断路器 + 超时 + 限流，一行搞定（基于 Polly v8）

// 日志：工厂创建的 client 自动记录每个请求
// Category：System.Net.Http.HttpClient.GitHubClient.LogicalHandler（整个管道）
//          System.Net.Http.HttpClient.GitHubClient.ClientHandler（实际网络）
// 想看请求耗时：appsettings.json → "System.Net.Http.HttpClient": "Information"

DelegatingHandler 是 HTTP 出站方向的"中间件"：认证、压缩、缓存、trace 头传播都在这一层。 ASP.NET Core 系列讲入站中间件时你会发现两者是镜像。

第二部分：System.Text.Json

设计哲学：严格优先

Newtonsoft.Json 是 Framework 时代的事实标准，宽松、聪明、什么都能猜。.NET Core 3.0 起内置的 System.Text.Json（STJ） 是另一种哲学（官方迁移文档）：

"System.Text.Json is strict by default and avoids any guessing or interpretation on the caller's behalf, emphasizing deterministic behavior. The library is intentionally designed this way for performance and security. Newtonsoft.Json is flexible by default."

它基于 Span<byte> 直接处理 UTF-8，不经过 string，比 Newtonsoft 快且分配少——这也是下一课 Span 的实际应用之一。 ASP.NET Core、HttpClient.GetFromJsonAsync、配置绑定源生成器，现代 .NET 里凡是内置的 JSON 都是它。

五个会咬你的默认差异

行为Newtonsoft 默认System.Text.Json 默认怎么对齐
属性名大小写 反序列化不区分 区分——"orderId" 填不进 OrderId，静默留默认值 PropertyNameCaseInsensitive = true，或用 Web 预设
输出命名 按属性名（PascalCase） 按属性名（PascalCase） PropertyNamingPolicy = JsonNamingPolicy.CamelCase；Web 预设已含
引号包着的数字 "42" 能读成 int 抛 JsonException NumberHandling = AllowReadingFromString；Web 预设已含
注释、尾逗号 允许 抛异常 ReadCommentHandling = Skip、AllowTrailingCommas = true
多态 / $type TypeNameHandling（有 RCE 风险，多次 CVE） 默认只序列化声明类型的属性；永远不支持 TypeNameHandling.All .NET 7+ [JsonDerivedType] 显式声明白名单

还有三个静默的：字段（public int X;）默认不序列化（需 IncludeFields）；DateTime 只认 ISO 8601，没有 Newtonsoft 那套时区/格式转换；JSON null 写进不可空值类型直接抛。

实用写法

// 1. 和 Web API 打交道，用 Web 预设：camelCase + 不区分大小写 + 允许字符串数字
var options = new JsonSerializerOptions(JsonSerializerDefaults.Web);
// ⚠️ JsonSerializerOptions 要复用（缓存成 static），每次 new 会重建元数据缓存，是常见性能坑

// 2. 属性名映射、忽略、必填
public sealed record Order(
    [property: JsonPropertyName("order_id")] int Id,       // 对方是 snake_case 时逐个映射
    [property: JsonIgnore] string? InternalNote,
    [property: JsonRequired] string Customer);              // 缺字段直接抛，不再静默留 null
// 全局 snake_case：options.PropertyNamingPolicy = JsonNamingPolicy.SnakeCaseLower（.NET 8+）

// 3. 多态：显式白名单 + 鉴别器，替代 TypeNameHandling
[JsonDerivedType(typeof(Circle), "circle")]
[JsonDerivedType(typeof(Square), "square")]
public abstract record Shape;
// 序列化输出 {"$type":"circle","radius":1}；反序列化只认白名单里的两个，别的名字直接抛

// 4. 源生成（NativeAOT / 启动性能 / 剪裁必需）：编译期生成序列化代码，零反射
[JsonSerializable(typeof(Order))]
[JsonSerializable(typeof(List<Order>))]
internal partial class AppJsonContext : JsonSerializerContext { }
var json = JsonSerializer.Serialize(order, AppJsonContext.Default.Order);
var back = JsonSerializer.Deserialize(json, AppJsonContext.Default.Order);

// 5. 不想定义类型：JsonNode / JsonDocument（对应 Newtonsoft 的 JObject / JToken）
JsonNode node = JsonNode.Parse(json)!;
int id = (int)node["order_id"]!;
node["status"] = "shipped";                               // JsonNode 可写；JsonDocument 只读但更省
💡 什么时候还该用 Newtonsoft？ 需要 JsonPath 查询、JObject 上的大量动态操作、 或者依赖 [DataContract]/[DataMember] 这类旧特性。ASP.NET Core 也允许一行切回 （AddNewtonsoftJson()）。但新代码默认 STJ，它在 .NET 7/8/9 每一版都在补功能（多态、required、snake_case、JsonSchema 导出）。

检查理解

❓ IHttpClientFactory.CreateClient() 每次返回什么？底层连接怎么管？
返回同一个缓存的 HttpClient 单例；连接永久复用，直到进程退出为止
返回新的 HttpClient；底层 handler 按名字共享，默认两分钟轮换一次
返回新的 HttpClient 和新的 handler；dispose 时一起释放，靠 GC 回收
返回池化的 HttpClient；dispose 时归还池中，池大小由 HandlerLifetime 决定
❓ 把类型化客户端 GitHubClient 直接注入一个 BackgroundService（Singleton），会有什么问题？
Development 下 ValidateScopes 会拒绝启动，因为类型化客户端是 Scoped
没有问题——类型化客户端本身就是为长期持有设计的，随便注入
能跑，但它持有的 handler 永不轮换，DNS 变更后一直打旧地址
两分钟后 handler 被工厂释放，后续请求抛 ObjectDisposedException
❓ 用默认的 JsonSerializer.Deserialize<Order>("{\"orderId\":42}")，Order 有属性 int OrderId。结果是？
OrderId = 42——和 Newtonsoft 一样，反序列化默认不区分大小写
OrderId = 0——默认区分大小写，匹配不到的属性静默保持默认值
抛 JsonException——默认区分大小写，遇到无法匹配的属性即报错
OrderId = 42——STJ 会自动识别 camelCase 并转换为 PascalCase
❓ Newtonsoft 里用 TypeNameHandling.All 做多态反序列化，迁移到 System.Text.Json 该怎么办？
设置 options.TypeNameHandling = All——STJ 从 .NET 7 起提供了同名选项
写一个自定义 JsonConverter 读取 $type 字段并用 Type.GetType 反射实例化
基类上用 [JsonDerivedType] 显式列出允许的子类型和鉴别器字符串
无法迁移——这是 STJ 不支持的功能，涉及多态的类型只能继续用 Newtonsoft

关键术语

Socket 耗尽 / DNS 陈旧
HttpClient 两个经典坑。频繁 new + dispose → 连接进 TIME_WAIT，端口耗尽；永久单例 → 连接不重建，感知不到 DNS 变化。根源都是连接池生命周期无人管理。
IHttpClientFactory
Microsoft.Extensions.Http 提供。CreateClient 每次返回新 HttpClient（廉价外壳），底层 HttpMessageHandler 按名字缓存共享，默认 2 分钟轮换（SetHandlerLifetime 可调）。dispose client 不释放 handler。
命名客户端 / 类型化客户端
AddHttpClient("name", cfg) 按字符串区分；AddHttpClient<TClient>(cfg) 注册一个构造函数收 HttpClient 的类（Transient）。类型化客户端不可注入 Singleton。
PooledConnectionLifetime
SocketsHttpHandler 的属性，让连接池定期重建连接以刷新 DNS。是"长命 HttpClient 单例"路线的必要配置，也可与工厂组合使用。
DelegatingHandler
HTTP 出站管道的中间件基类。AddHttpMessageHandler<T>() 挂到客户端上，用于认证头、重试、追踪等横切逻辑。
System.Text.Json（STJ）
.NET Core 3.0+ 内置 JSON 库，基于 UTF-8 / Span，严格优先：默认区分大小写、PascalCase 输出、拒绝字符串数字/注释/尾逗号、无 TypeNameHandling。
JsonSerializerDefaults.Web
预设：camelCase + 不区分大小写 + 允许从字符串读数字。ASP.NET Core 和 GetFromJsonAsync 默认用它。JsonSerializerOptions 实例应缓存复用。
[JsonDerivedType]
.NET 7+ 多态序列化：在基类上显式声明子类型白名单和鉴别器（默认 $type）。替代 Newtonsoft 的 TypeNameHandling。
JsonSerializerContext（源生成）
[JsonSerializable(typeof(T))] 标注的 partial 类，编译期生成序列化代码。NativeAOT 和剪裁必需，也提升启动性能。
