第 5 课：DI 进阶：工厂模式与 Keyed Service

模块：依赖注入（2/3） |  预计阅读/练习时间：25 分钟

上一课我们掌握了三种生命周期和 Captive Dependency。这一课解决一个你迟早会遇到的问题： 同一个接口有多个实现，怎么办？Framework 4.8 中 Autofac 有 .Named<T>() 和 .Keyed<T>()——但 MSDI 直到 .NET 8 才有类似功能。在此之前，社区发展出了三套方案， 而 .NET 8 的 Keyed Service 统一了其中最核心的需求。

  • 掌握 Func<T> 工厂委托——无需注册，MSDI 自动提供
  • 理解 IEnumerable<T> 注入——一次性获取接口的所有实现
  • 掌握 Keyed Service（.NET 8+）——同一接口按 key 区分实现
  • 建立直觉：什么时候用哪种方案？

问题场景：同一接口，多个实现

这是一个真实的业务场景：

public interface IPaymentProcessor
{
    Task<PaymentResult> ProcessAsync(Payment payment);
}

// 三个实现——针对不同支付渠道
public class AlipayProcessor : IPaymentProcessor { /* ... */ }
public class WeChatPayProcessor : IPaymentProcessor { /* ... */ }
public class CreditCardProcessor : IPaymentProcessor { /* ... */ }

现在 OrderService 需要根据用户选择的支付方式，调用不同的 IPaymentProcessor。 如果只注册一个： 

// ❌ 解析单个 T 时只拿到最后一个——但两个都注册了！
services.AddTransient<IPaymentProcessor, AlipayProcessor>();
services.AddTransient<IPaymentProcessor, WeChatPayProcessor>(); // 最后注册，"胜出"
// 解析 IPaymentProcessor → 永远是 WeChatPayProcessor（最后注册胜出）
// 但两个实现都在容器里——解析 IEnumerable<IPaymentProcessor> 能拿到全部

MSDI 提供了三种解决方案，从简单到复杂依次展开。

方案一：Func<T> 工厂——MSDI 的内置"免费午餐"

这是 MSDI 中最被低估的特性。Func<T> 不需要你自己注册——容器自动理解它。 当你注入 Func<ITalker> 时，容器给你一个每次调用都返回新实例的工厂委托。

基础用法：延迟解析 + 每次新建

// 不需要在 ServiceCollection 中注册 Func<T>！
// MSDI 自动理解 Func<T> 是"按需解析 T 的工厂"

public class ReportService
{
    private readonly Func<IEmailSender> _createSender;

    // ✅ 直接注入 Func<T>——容器自动提供
    public ReportService(Func<IEmailSender> createSender)
    {
        _createSender = createSender;
    }

    public async Task SendReportAsync()
    {
        // 每次调用 _createSender() 都返回新实例（Transient 行为）
        var sender = _createSender();
        await sender.SendAsync("report");
    }
}
💡 Func<T> 的关键规则：
  • 如果 T 注册为 Transient：每次调用返回新实例
  • 如果 T 注册为 Scoped：同一 Scope 内每次调用返回同一实例
  • 如果 T 注册为 Singleton：每次调用返回同一实例
Func<T> 只是创建了一个"延迟解析点"——它不会改变 T 原本的生命周期。

进阶：Func<T> 解决 Captive Dependency

回忆上一课的 Singleton → Transient 语义囚禁问题——Func<T> 正是解药：

// Singleton 需要 Transient 的"每次新建"行为
services.AddSingleton<CacheWarmer>();
services.AddTransient<IDbContext, AppDbContext>();

public class CacheWarmer
{
    private readonly Func<IDbContext> _createDb;

    // ✅ 注入工厂，而不是 IDbContext 本身
    public CacheWarmer(Func<IDbContext> createDb)
    {
        _createDb = createDb;
    }

    public async Task WarmAsync()
    {
        var db = _createDb();  // 每次调用 → 新 DbContext ✅
        // ...
    }
}

带参数的工厂：Func<string, T>

有时候你需要根据运行时参数决定用哪个实现。比如支付场景——根据支付方式名称选不同的 Processor：

public interface IPaymentProcessor
{
    Task<PaymentResult> ProcessAsync(Payment payment);
}

public class OrderService
{
    private readonly IServiceProvider _provider;

    public OrderService(IServiceProvider provider)
    {
        _provider = provider;
    }

    public async Task CheckoutAsync(Payment payment)
    {
        // 根据运行时数据选实现
        IPaymentProcessor processor = payment.Method switch
        {
            "Alipay" => _provider.GetRequiredKeyedService<IPaymentProcessor>("alipay"),
            "WeChat" => _provider.GetRequiredKeyedService<IPaymentProcessor>("wechat"),
            _        => _provider.GetRequiredService<CreditCardProcessor>()
        };

        await processor.ProcessAsync(payment);
    }
}
⚠️ 注意：上面的代码直接用 IServiceProvider 手动解析——这是 Service Locator 模式！ 在这个场景中它可以接受，因为支付方式确实是运行时决定的。但更好的方案是 .NET 8 的 Keyed Service（下文方案三）。

方案二：IEnumerable<T>——一次性拿到所有实现

当你需要对所有实现执行同一操作时——比如"用所有支付渠道验证一笔交易"或"用所有通知渠道发送消息"—— IEnumerable<T> 是最自然的方案。

基础用法

// 注册所有实现——同一个接口，多次注册（不会互相覆盖！）
services.AddTransient<IPaymentValidator, AlipayValidator>();
services.AddTransient<IPaymentValidator, WeChatValidator>();
services.AddTransient<IPaymentValidator, CreditCardValidator>();

// ✅ 注入 IEnumerable<T>——拿到所有实现
public class PaymentValidationPipeline
{
    private readonly IEnumerable<IPaymentValidator> _validators;

    public PaymentValidationPipeline(IEnumerable<IPaymentValidator> validators)
    {
        _validators = validators;  // 包含全部 3 个实现
    }

    public async Task<bool> ValidateAllAsync(Payment payment)
    {
        foreach (var validator in _validators)
        {
            if (!await validator.ValidateAsync(payment))
                return false;
        }
        return true;  // 全部通过
    }
}

关键区别：IEnumerable<T> 不会覆盖——每次 AddXxx<T, U>() 都追加到列表中。 解析单个 T 时返回最后一个注册的；解析 IEnumerable<T> 时返回全部。

经典用例：责任链 / 管道模式

public interface IMiddleware
{
    Task InvokeAsync(Message msg, Func<Task> next);
}

// 多个中间件组成管道
public class MessagePipeline
{
    private readonly IEnumerable<IMiddleware> _middlewares;

    public MessagePipeline(IEnumerable<IMiddleware> middlewares)
    {
        _middlewares = middlewares;
    }

    public async Task ProcessAsync(Message msg)
    {
        // 把所有中间件链起来
        Func<Task> handler = () => Task.CompletedTask;
        foreach (var m in _middlewares.Reverse())
        {
            var next = handler;
            handler = () => m.InvokeAsync(msg, next);
        }
        await handler();
    }
}

ASP.NET Core 的中间件管道就是这么实现的。 你每次写的 app.UseXxx() 本质就是在 IEnumerable<IMiddleware> 上追加一个元素。

IEnumerable<T> 的生命周期细节

如果注册了三个 IPaymentValidator，解析 IEnumerable<IPaymentValidator> 时：

  • 每个实现都遵循各自的注册生命周期
  • 如果 A 是 Singleton、B 是 Scoped、C 是 Transient——容器照样正确管理
  • 但 IEnumerable<T> 本身的生命周期取决于谁注入了它（集合被注入的时机）
⚠️ 陷阱：如果 PaymentValidationPipeline 是 Singleton，而某个 Validator 是 Scoped， 这依然是 Captive Dependency！IEnumerable<T> 不会魔法般地解决生命周期冲突。

方案三：Keyed Service（.NET 8+）

.NET 8 终于把"按 key 区分实现"这个需求内置了。不用再自己写工厂 Switch，不用再依赖命名约定。

注册 Keyed Service

// .NET 8+ —— 同一个接口，按 key 区分
services.AddKeyedTransient<IPaymentProcessor, AlipayProcessor>("alipay");
services.AddKeyedTransient<IPaymentProcessor, WeChatPayProcessor>("wechat");
services.AddKeyedScoped<IPaymentProcessor, CreditCardProcessor>("credit");

// key 可以是任意 object——string 最常用，但 enum、int 都行
services.AddKeyedSingleton<ICache, RedisCache>("remote");
services.AddKeyedSingleton<ICache, MemoryCache>("local");
⚠️ 重复 key 不会报错：和普通注册一样，ServiceCollection 是列表不是字典——同一个 (TService, key) 组合可以注册多次。GetRequiredKeyedService<T>(key) 返回最后一个， GetKeyedServices<T>(key) 返回全部。所以 key 不会自动保证唯一性——需要你自行保证每个 key 只注册一个实现，否则可能出现难以调试的"最后注册意外胜出"。

注入 Keyed Service

// 方式一：通过 [FromKeyedServices] 特性（构造函数注入）
public class OrderService(
    [FromKeyedServices("alipay")] IPaymentProcessor alipay,
    [FromKeyedServices("wechat")] IPaymentProcessor wechat)
{
    public async Task PayAsync(string method, Payment payment)
    {
        var processor = method switch
        {
            "Alipay" => alipay,
            "WeChat" => wechat,
            _ => throw new NotSupportedException()
        };
        await processor.ProcessAsync(payment);
    }
}

// 方式二：通过 IServiceProvider（方法内动态选择）
public class PaymentDispatcher
{
    private readonly IServiceProvider _provider;

    public PaymentDispatcher(IServiceProvider provider)
    {
        _provider = provider;
    }

    public async Task DispatchAsync(string method, Payment payment)
    {
        var processor = _provider.GetRequiredKeyedService<IPaymentProcessor>(method);
        await processor.ProcessAsync(payment);
    }
}
💡 [FromKeyedServices] 的限制：它只能在构造函数参数上用。如果你需要在方法内根据运行时数据 动态选择，还是要通过 IServiceProvider.GetRequiredKeyedService<T>(key)。但这时候不是反模式——因为 key 本身就是运行时数据，无法在构造时确定。

Keyed Service 与 IEnumerable<T> 共存

// Keyed 和 non-keyed 可以同时存在
services.AddKeyedTransient<INotifier, SmsNotifier>("sms");
services.AddKeyedTransient<INotifier, EmailNotifier>("email");
services.AddTransient<INotifier, DefaultNotifier>();  // 默认实现（无 key）

// 解析不带 key 的 INotifier → DefaultNotifier
// 解析 IEnumerable<INotifier> → 只包含 DefaultNotifier（keyed 的不在 IEnumerable 中）
// 解析 [FromKeyedServices("sms")] INotifier → SmsNotifier

Keyed Service 被明确排除在 IEnumerable<T> 之外——这是故意的设计选择。 如果你两种都需要，注册两个非 keyed 的实现到 IEnumerable，再用 keyed 做精确选择。

三方案对比：什么时候用哪个？

场景推荐方案为什么
"我需要延迟解析，或者每次调用时新建实例" Func<T> 零配置，MSDI 自动支持。Singleton 需要 Transient 行为时必用。
"对所有实现执行同一个操作"（验证器链、中间件管道、复合处理器） IEnumerable<T> 天然表达"一组东西"的语义。注册即追加，无需额外配置。
"根据运行时 key 选一个特定实现"（支付渠道、数据库分片、租户隔离） Keyed Service .NET 8 原生支持。类型安全，key 可以是任意 object。取代以前的工厂 switch。
"同一个接口，但不同消费者需要不同实现"（Controller A 用实现 A，B 用 B） Keyed Service + [FromKeyedServices] 在构造函数中精确指定——调用方不需要知道选择逻辑。
需要 Autofac 的 .Named<T>() 等效功能 Keyed Service .NET 8 的 Keyed Service 就是 MSDI 对命名注册的官方回答。

Autofac → MSDI：命名/Keyed 注册迁移

AutofacMSDI（.NET 6-7）MSDI（.NET 8+）
.Named<T>("name") 工厂 + 手动 switch；或 Scrutor + 约定 AddKeyedXxx<T>("name")
.Keyed<T>(enum) 工厂 switch + IServiceProvider AddKeyedXxx<T>(enum)
IIndex<K, T>（按 key 获取） 不支持，手动 IDictionary<K, Func<T>> IServiceProvider.GetRequiredKeyedService<T>(key)

检查理解

❓ 使用 Func<T> 工厂模式前，需要先在 ServiceCollection 中注册 Func<T> 吗？
不需要，MSDI 自动理解
需要 services.AddFactory<T>()
需要 services.AddTransient<Func<T>>()
只有 Transient 注册的 T 才支持 Func<T>
❓ 多次调用 services.AddTransient<INotifier, Xxx>() 注册不同实现，解析 IEnumerable<INotifier> 会发生什么？
最后一次注册覆盖前面的，只得到一个实现
拿到所有注册的实现
编译时抛异常——不允许重复注册同一接口
随机返回其中一个实现
❓ Keyed Service 注册的实现会出现在 IEnumerable<T> 的解析结果中吗？
会，和普通注册的实现一起返回
取决于 key 的类型（string 会在，enum 不会）
取决于注册顺序
不会，Keyed Service 被明确排除
❓ 如果 IEmailSender 注册为 Transient，注入 Func<IEmailSender> 并调用两次，两次结果相同吗？
相同——Func<T> 总是缓存第一个结果
取决于调用时所在 Scope
不相同——每次调用返回新实例
只有第一次调用返回实例，之后返回 null

关键术语

Func<T> 工厂委托
MSDI 自动提供的延迟解析机制。不需要注册——容器自动理解 Func<T> 为"按需创建 T 的工厂"。每次调用遵循 T 的注册生命周期。Singleton 需要 Transient 行为时的首选解。
IEnumerable<T> 注入
一次性获取接口的所有注册实现。每次 AddXxx<T, U>() 追加到列表，不会互相覆盖。解析单个 T 返回最后一个注册的，解析 IEnumerable<T> 返回全部。适用于责任链、管道、复合处理器。
Keyed Service
.NET 8 新增——同一接口按 object key 区分不同实现。注册：AddKeyedTransient/Scoped/Singleton<TService, TImpl>(key)。注入：构造函数用 [FromKeyedServices(key)] 特性，方法内用 IServiceProvider.GetRequiredKeyedService<T>(key)。Keyed Service 不出现在 IEnumerable<T> 中。
[FromKeyedServices]
.NET 8 特性——标记构造函数参数要从 keyed 注册中解析。只能用于构造函数参数。运行时动态选择时仍需 GetRequiredKeyedService。
Service Locator（服务定位器）
在方法体内手动调用 GetService/GetRequiredService 而不是通过构造函数注入。通常被视为反模式，但在运行时根据数据选择实现的场景中有正当性——key 本身无法在构造时确定。
