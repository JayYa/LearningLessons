第 11 课：ILogger 与结构化日志——从"拼字符串"到"记事件"

模块：日志（1/1） |  预计阅读/练习时间：30 分钟

Microsoft.Extensions.* 四件套——DI、配置、Host、日志——你已经拿下三件。日志是最后一块， 也是 log4net / NLog 用户思维转换最大的一块。 Framework 时代你写 log.Info("Order " + id + " processed in " + ms + "ms")——日志是一行文本， 出了事用 grep 找。现代 .NET 的 ILogger 记的不是文本，是一个带命名字段的事件—— 文本只是这个事件的一种渲染方式。

  • 理解消息模板为什么不是字符串拼接——占位符名字会变成可查询的字段
  • 掌握 Category / Level / EventId 三个坐标，以及 appsettings.json 里 Logging 节的过滤规则
  • 会用 Scope 给一段操作内的所有日志自动附加上下文（TransactionId、OrderId）
  • 会用 [LoggerMessage] 源生成器写零分配、强类型的日志方法（推荐写法）
  • 知道 Provider 是什么、Serilog 在这个体系里站在哪

Framework 4.8 vs 现代 .NET：日志的三个思维差异

log4net / NLog（Framework 时代用法）Microsoft.Extensions.Logging
日志是什么 一行格式化好的文本 一个事件：Category + Level + EventId + 命名字段 + 模板 + 异常
怎么拿 logger LogManager.GetLogger(typeof(Foo)) 静态获取 构造函数注入 ILogger<Foo>——Host 已经注册好了
怎么控制输出 log4net.config XML，appender + logger 层级 appsettings.json 的 Logging 节，Provider + Category 前缀；支持热重载
库之间 每个库绑死一个日志框架，ASP.NET / EF 各写各的 所有库只依赖 ILogger 抽象，EF Core / HttpClient / Kestrel 的日志和你的日志走同一条管道
💡 log4net / NLog / Serilog 并没有被淘汰——它们变成了 ILogger 后面的 Provider（输出端）。 你的代码只认 ILogger，换日志框架不用改一行业务代码。Serilog 是现在最流行的 Provider，本课末尾讲它怎么接。

一个事件的六个字段

看官方对一条日志的定义（Logging in C#）——所有 Log* 扩展方法最终都调用这一个接口方法：

public interface ILogger
{
    void Log<TState>(
        LogLevel logLevel,                              // ① 严重程度
        EventId eventId,                                // ② 事件编号（可选）
        TState state,                                   // ③ 命名字段 + 原始模板
        Exception? exception,                           // ④ 异常（可选）
        Func<TState, Exception?, string> formatter);    // ⑤ 怎么渲染成文本——Provider 决定要不要调
    IDisposable? BeginScope<TState>(TState state);      // ⑥ 附加上下文
}
// 还有一个隐含的坐标：Category——创建 logger 时就定了，通常是类的全名

重点是 ③ 和 ⑤ 的关系：字段和渲染是分开的。Provider 拿到的是 {OrderId = 42, Elapsed = 17} 这样的键值对， 控制台 Provider 会调 formatter 渲染成一行文本；写到 Seq / Elasticsearch / OpenTelemetry 的 Provider 则直接存字段——之后你就能查 "Elapsed > 1000 的所有 order"，而不是写正则去解析文本。

消息模板：为什么 {Name} 不是字符串插值

❌ 字符串拼接 / 插值
logger.LogInformation(
    $"Order {id} took {ms}ms");

// 传给 Provider 的：
// "Order 42 took 17ms"
// 字段：无。信息已经被压扁成文本。
// 而且不管日志级别开没开，
// 插值都先执行了——白白分配字符串。
// 分析器会警告 CA2254。
✅ 消息模板
logger.LogInformation(
    "Order {OrderId} took {Elapsed}ms", id, ms);

// 传给 Provider 的：
// 模板 "Order {OrderId} took {Elapsed}ms"
// 字段 OrderId = 42, Elapsed = 17
// 级别没开 → 直接返回，不格式化。
// JSON Provider 输出：
// { "Message": "Order 42 took 17ms",
//   "OrderId": 42, "Elapsed": 17,
//   "{OriginalFormat}": "Order {OrderId}..." }

模板的三条规则（官方）：

  1. 占位符用名字，不用序号：{OrderId} 不是 {0}。名字就是字段名。
  2. 参数按位置匹配，不按名字：LogInformation("{B} {A}", a, b) 会把 a 填进 {B}。名字只决定字段叫什么，顺序决定值是谁——这是最常见的 bug。
  3. 支持格式说明符：{Timestamp:yyyy-MM-dd}、{Ratio:P2}。字面大括号写 {{。
⚠️ 命名习惯：占位符用 PascalCase（{OrderId}），因为它会成为 JSON / 数据库里的字段名。 同一个概念在全项目用同一个名字——{OrderId} 和 {orderId} 在 Seq 里是两个不同字段，查的时候会漏。

三个坐标：Category、Level、EventId

Category——谁记的

注入 ILogger<OrderService>，Category 就是 OrderService 的全名（含命名空间）。 它是过滤的主要依据："Microsoft" 这条规则匹配所有以 Microsoft 开头的 Category—— Microsoft.EntityFrameworkCore.Database.Command、Microsoft.Hosting.Lifetime 全在内。 这和 log4net 的 logger 层级是同一个思路，只是不用你配 XML。

Level——多严重

Level值官方定义你该记什么
Trace0最详细，可能含敏感数据，生产禁用请求/响应原文、SQL 参数值
Debug1开发调试用，量大分支走向、中间值
Information2应用的一般流程，默认级别"订单 42 已创建"
Warning3异常或意外，但应用没失败重试成功、配置缺省回退
Error4当前操作失败，不是整个应用一个请求 500
Critical5需要立即处理：数据丢失、磁盘满启动失败、连不上数据库
None6关闭该 Category 的所有输出用在配置里做静音

对应 LogTrace / LogDebug / LogInformation / LogWarning / LogError / LogCritical 六个扩展方法。 Error 和 Critical 的边界比 log4net 的 ERROR/FATAL 更清楚："这个请求挂了" 是 Error；"整个进程要挂了" 才是 Critical。

EventId——哪类事件

可选的整数（加可选名字），把"同一类事件"编号。控制台里显示在 Category 后的方括号：info: OrderService[1001]。 手写 Log* 时很少有人用；用了 [LoggerMessage] 之后它自然就有了（见下文）。

appsettings.json 的 Logging 节：过滤规则

Worker 模板生成的 appsettings.Development.json 长这样，现在你能读懂每一行了：

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",              // 所有没被单独指定的 Category
      "Microsoft": "Warning",                // Category 以 Microsoft 开头的 → 只要 Warning 以上
      "Microsoft.Hosting.Lifetime": "Information"  // 更长的前缀更具体，覆盖上一条
    },
    "Console": {                             // 只对 Console Provider 生效的规则（用 Provider 别名）
      "IncludeScopes": true,                 // 控制台显示 Scope（默认关）
      "LogLevel": { "Default": "Debug" }
    }
  }
}

规则怎么选（官方算法），对每个 Provider × Category 组合：

① 先挑指定了这个 Provider 的规则；没有 → 挑没指定 Provider 的规则
② 从中挑 Category 前缀最长匹配的；没有 → 挑没指定 Category 的（Default）
③ 还有多条 → 取最后一条
④ 一条都没有 → SetMinimumLevel（默认 Information）

三个实用推论：(1) 这个节走的是第 7 课的配置管道，所以 Logging__LogLevel__Default=Debug 环境变量能覆盖它， 而且 reloadOnChange 让你改文件就能在线调级别，不用重启。 (2) Provider 级规则优先于全局规则——"控制台只看 Warning，但 Seq 收 Debug" 这种需求就靠它。 (3) 生产环境常见配法：Default: Warning，再对自己的命名空间开 Information。

Scope：给一段操作自动附加上下文

处理一个订单要记 5 条日志，每条都想带 OrderId——不用每次都写进模板。BeginScope 返回一个 IDisposable， 在它释放之前，这个 logger 的所有日志都自动附带 scope 里的字段： 

public async Task ProcessAsync(int orderId)
{
    // 用字典（或 KeyValuePair 列表）当 state，字段才能被结构化 Provider 拿到
    using (logger.BeginScope(new Dictionary<string, object> { ["OrderId"] = orderId }))
    {
        logger.LogInformation("Validating");          // → 自动带 OrderId = 42
        await paymentService.ChargeAsync(orderId);    // paymentService 里的日志也带（同一个异步流）
        logger.LogInformation("Done");                // → 自动带 OrderId = 42
    }
}

Scope 通过 AsyncLocal 传播，所以 await 之后、调用链里其他类的 logger 也在 scope 内。 ASP.NET Core 就靠它给每条日志自动附上 RequestId / TraceId。控制台 Provider 默认不显示 scope， 要开 IncludeScopes: true；结构化 Provider（Serilog、OTel）默认就把它们当字段存。

⚠️ BeginScope("Order {OrderId}", orderId) 这种模板写法也行，但传字典更明确——你要的是字段，不是一段文本。 而且不要在 scope 里放大对象：它会跟着每条日志被 Provider 遍历。

[LoggerMessage] 源生成器：推荐写法

官方现在的建议（原文）： "Compile-time source generation for logging is usually a better alternative to ILogger extension methods like LogInformation." 原因是 LogInformation(string, params object[]) 每次调用都要把参数装箱进 object[]， 即使这个级别没开。源生成器在编译期生成强类型方法，先查 IsEnabled，零装箱、零临时分配。 

// 类和方法都要 partial；.NET 9+ 可直接用主构造函数里的 ILogger
public sealed partial class OrderService(ILogger<OrderService> logger)
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Information,
                   Message = "Order {OrderId} took {Elapsed}ms")]
    private partial void LogOrderProcessed(int orderId, long elapsed);

    [LoggerMessage(EventId = 1002, Level = LogLevel.Error,
                   Message = "Order {OrderId} failed")]
    private partial void LogOrderFailed(Exception ex, int orderId);   // 第一个 Exception 参数自动当异常，不进模板

    public async Task ProcessAsync(int orderId)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            await DoWorkAsync(orderId);
            LogOrderProcessed(orderId, sw.ElapsedMilliseconds);       // 强类型：传错类型编译不过
        }
        catch (Exception ex)
        {
            LogOrderFailed(ex, orderId);
            throw;
        }
    }
}

几条规则（官方）：

  • 方法必须 partial void；静态方法要把 ILogger 作为参数传入（可加 this 做成扩展方法）
  • 签名里第一个 ILogger、LogLevel、Exception 参数被特殊对待；LogLevel 参数让级别在运行时决定
  • 占位符和参数名按名字、不分大小写匹配——模板写 {OrderId}、参数叫 orderId 即可。这修掉了手写模板"按位置匹配"的坑
  • 重复的 EventId 会有编译警告——你顺手就得到了一套事件编号
💡 团队约定的一种常见做法：每个类底部放一组 [LoggerMessage] 私有方法，或者集中在一个 static partial class Log 里。 业务代码里就不再出现字符串模板——"日志长什么样"和"什么时候记"分开了。

Provider：日志去哪

第 9 课讲过 CreateApplicationBuilder 默认加了 Console / Debug / EventSource / EventLog（Windows）四个 Provider。 Provider 就是 log4net 里的 appender。生产上你通常会 ClearProviders() 再加自己要的： 

builder.Logging.ClearProviders();
builder.Logging.AddJsonConsole();                    // 内置：每行一个 JSON 对象，容器里给 fluentd / Loki 收
builder.Logging.AddOpenTelemetry(o => o.AddOtlpExporter());   // OTLP：现代可观测性栈的标准入口

// 或者 Serilog——最流行的第三方 Provider
// NuGet: Serilog.Extensions.Hosting / Serilog.AspNetCore + 各种 Sink
builder.Services.AddSerilog(cfg => cfg
    .ReadFrom.Configuration(builder.Configuration)   // 从 "Serilog" 配置节读 sink 和级别
    .Enrich.FromLogContext()
    .WriteTo.Console()
    .WriteTo.Seq("http://localhost:5341"));

Serilog 的定位：它本身就是一个结构化日志框架，消息模板语法和 ILogger 完全一致 （两者都遵循 messagetemplates.org）。接入 Host 之后，你的代码依然只注入 ILogger<T>； Serilog 负责 sink（文件滚动、Seq、Elasticsearch）、enricher（机器名、进程 ID）。 从 log4net 迁移的推荐路径：业务代码全改成 ILogger，输出端选 Serilog。

⚠️ 没有异步日志方法——这是设计决定，不是遗漏 （官方）。 日志应该快到不值得 async。慢目标（数据库、HTTP）应由 Provider 内部用队列 + 后台线程批量写——Serilog 的 Async sink、OTel 的 BatchExporter 都是这么做的。 你的 Log* 调用永远是同步的、非阻塞的。

动手：给第 9 课的最小 Host 加上结构化日志

打开第 9 课的 MinimalHost 项目，把 Program.cs 里的 logger.LogInformation("Hello, {Name}!", ...) 改成 [LoggerMessage] 方法。

在 appsettings.json 里加 "Logging": { "Console": { "IncludeScopes": true } }，并把 builder.Logging.AddJsonConsole() 加上。

用 BeginScope(new Dictionary<string, object> { ["RunId"] = Guid.NewGuid() }) 包住主逻辑，运行——看 JSON 输出里的 Scopes 数组和 State 里的字段。

不重启进程，把 appsettings.json 里 Default 改成 Warning 并保存——观察日志立即消失（热重载）。

故意写一条 logger.LogInformation($"Hello {name}")，看 IDE 的 CA2254 警告。

检查理解

❓ logger.LogInformation("Order {OrderId} for user {UserId}", userId, orderId)——结构化 Provider 收到的字段是？
OrderId = orderId，UserId = userId——运行时按占位符名字匹配参数名
OrderId = userId，UserId = orderId——参数按位置填入，名字只决定字段名
编译错误——分析器检测到占位符名字和参数名字不一致会拒绝编译
运行时抛出 FormatException——占位符数量和参数顺序校验失败时中止
❓ 配置 "LogLevel": { "Default": "Warning", "Microsoft": "Warning", "Microsoft.EntityFrameworkCore": "Information" }。Category 为 Microsoft.EntityFrameworkCore.Database.Command 的 Information 日志会输出吗？
不会——Microsoft 规则在前面，先匹配到的规则生效，后面的被忽略
不会——多条规则冲突时取最严格的那一条，Warning 比 Information 严格
会——Microsoft.EntityFrameworkCore 是更长的前缀匹配，比 Microsoft 更具体
会——但仅当在 Console Provider 节下再写一遍这条规则，否则用 Default
❓ OrderService 里 using (logger.BeginScope(...)) 之内 await paymentService.ChargeAsync()，PaymentService 用自己注入的 ILogger<PaymentService> 记了一条日志。这条日志带 scope 字段吗？
不带——Scope 只作用于调用 BeginScope 的那个 ILogger 实例本身
不带——await 切换线程后 Scope 丢失，只有同步代码内才有效
带——Scope 通过 AsyncLocal 沿异步调用链传播到所有 logger
带——但仅当 PaymentService 也是 Scoped 生命周期并在同一 DI Scope
❓ 相比直接调用 logger.LogInformation("...{OrderId}", id)，[LoggerMessage] 源生成器的主要收益是？
日志可以异步写入慢目标，不阻塞调用线程，吞吐更高
避免参数装箱和 object[] 分配，先查 IsEnabled，强类型编译检查
自动把日志同时发到所有已注册 Provider，不需要 ClearProviders
日志级别可以在运行时通过配置热重载，而普通方法级别是固定的

关键术语

结构化日志（Structured Logging）
日志作为带命名字段的事件而非文本记录。ILogger 把模板和参数分开传给 Provider，Provider 可存字段供查询。
消息模板（Message Template）
"Order {OrderId} took {Elapsed}ms"。占位符用名字（PascalCase），参数按位置匹配。禁止用字符串插值代替（CA2254）。
Category
logger 的名字，ILogger<T> 即 T 的全名。过滤规则按 Category 前缀匹配，最长前缀优先。
LogLevel
Trace(0) → Debug → Information(默认) → Warning → Error(当前操作失败) → Critical(应用级失败) → None(6, 静音)。
EventId
可选的整数编号 + 名字，把同类事件归组。[LoggerMessage] 强制你写它。
Provider
日志的输出端，相当于 log4net 的 appender。内置 Console / JsonConsole / Debug / EventSource / EventLog；第三方 Serilog / OpenTelemetry。在配置里用别名（"Console"）写 Provider 级规则。
Scope
BeginScope(state) 返回的 IDisposable，释放前该异步调用链内所有日志自动附带 state 中的字段。通过 AsyncLocal 传播。控制台需 IncludeScopes: true。
[LoggerMessage]
源生成器特性，标在 partial void 方法上，编译期生成零分配、强类型的日志方法。占位符与参数按名字（不分大小写）匹配；第一个 Exception / LogLevel 参数被特殊处理。官方推荐的默认写法。
