第 10 课：IHostedService 与生命周期——后台任务、启动顺序、优雅关闭

模块：Host 模型（2/2） |  预计阅读/练习时间：30 分钟

上一课的 Host "建好、用一下、退出"。但 Host 真正的价值在长驻进程：定时任务、队列消费者、Windows 服务。 Framework 4.8 时代你要继承 ServiceBase、写 OnStart/OnStop、自己开线程、自己处理停止信号——或者装 TopShelf。 现代 .NET 用一个接口统一了这一切：IHostedService。

  • 掌握 IHostedService 和 BackgroundService 的写法与区别
  • 背下 Host 的启动 / 关闭精确顺序——这决定了"我的初始化代码该放哪"
  • 理解 ExecuteAsync 里的三个陷阱：同步阻塞启动、异常静默、Scoped 服务
  • 掌握 HostOptions：30 秒关闭超时、并发启动、异常策略
  • 知道 UseWindowsService() / UseSystemd() 如何替代 ServiceBase 和 TopShelf

IHostedService：两个方法的契约

public interface IHostedService
{
    Task StartAsync(CancellationToken cancellationToken);  // Host 启动时调用，await 完成后才继续启动下一个
    Task StopAsync(CancellationToken cancellationToken);   // Host 关闭时调用，token 在超时（默认 30s）后取消
}

注册方式只有一种：builder.Services.AddHostedService<T>()——它本质是 AddSingleton<IHostedService, T>()， 所以hosted service 永远是 Singleton（记住这点，后面的 Scoped 陷阱就从这来）。

StartAsync 的语义是"启动"不是"运行"：Host 会 await 它，等它返回才启动下一个服务、才算应用启动完成。 如果你在里面 while(true)，Host 永远启动不完。所以直接实现 IHostedService 适合"启动时做一件事就返回"的场景（预热缓存、注册服务发现）； 真正的长循环要用下面的 BackgroundService。

BackgroundService：长循环的标准写法

// 抽象基类，帮你实现了 StartAsync / StopAsync，你只写 ExecuteAsync
public sealed class QueueConsumer(
    ILogger<QueueConsumer> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // stoppingToken 在 Host 开始关闭时被取消——这是你唯一的退出信号
        while (!stoppingToken.IsCancellationRequested)
        {
            logger.LogInformation("Polling at {Time}", DateTimeOffset.Now);
            await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);  // 把 token 传进去，关闭时立即醒来
        }
    }
}

// Program.cs
builder.Services.AddHostedService<QueueConsumer>();

BackgroundService 的 StartAsync 内部做的事只有一件：调用 ExecuteAsync， 不 await 它，把返回的 Task 存起来就返回。所以 Host 启动不会被你的循环卡住。StopAsync 则是取消 token，然后等你的 Task 结束（或超时）。

⚠️ 陷阱 1：ExecuteAsync 第一个 await 之前的代码是同步跑的。 "不 await 它"只对异步部分成立——async 方法在遇到第一个未完成的 await 之前，是在调用者线程上同步执行的。 如果你的 ExecuteAsync 开头有一段耗时同步初始化（读大文件、建连接池），它会阻塞 Host 启动，其他 hosted service 排在后面干等。 解决：在方法开头 await Task.Yield();，或把同步初始化挪到真正的 StartAsync 里（记得 await base.StartAsync(ct)）。

启动与关闭的精确顺序

这是本课要背下来的东西。Host 的所有钩子按这个顺序触发 （官方示例输出， 源码 Host.cs）： 

host.Run() / StartAsync()
 │
 ├─ IHostLifetime.WaitForStartAsync          ← ConsoleLifetime 在这里挂 Ctrl+C 处理器
 ├─ IStartupValidator.Validate               ← 第 8 课的 ValidateOnStart 在这里跑
 │
 ├─ 对每个 hosted service（默认按注册顺序、串行）：
 │    ├─ ① IHostedLifecycleService.StartingAsync
 │    ├─ ② IHostedService.StartAsync          ← BackgroundService 在此启动 ExecuteAsync
 │    └─ ③ IHostedLifecycleService.StartedAsync
 │
 └─ ④ IHostApplicationLifetime.ApplicationStarted 触发
      "Application started. Press Ctrl+C to shut down."

──── 收到 Ctrl+C / SIGTERM / StopApplication() ────

 ├─ ⑤ IHostApplicationLifetime.ApplicationStopping 触发
 │
 ├─ 对每个 hosted service（按注册顺序的【倒序】，LIFO）：
 │    ├─ ⑥ IHostedLifecycleService.StoppingAsync
 │    ├─ ⑦ IHostedService.StopAsync           ← BackgroundService 在此取消 stoppingToken
 │    └─ ⑧ IHostedLifecycleService.StoppedAsync
 │
 ├─ ⑨ IHostApplicationLifetime.ApplicationStopped 触发
 └─ IHostLifetime.StopAsync
     Main 继续往下执行 → 进程退出

三个直接推论：

  • 注册顺序有意义。A 依赖 B 先启动？先 AddHostedService<B>()。关闭时 A 先停 B 后停——正好是依赖的反向。
  • "应用完全启动后才做"的事挂在 ApplicationStarted 上（比如向注册中心报到），不要放在某个 StartAsync 里——那时其他服务可能还没起。
  • 关闭是两阶段的。ApplicationStopping 是"要停了，别接新活"；StopAsync 是"把手上的活收尾"。Kestrel 就是在 ⑤ 停止接受新连接、在 ⑦ 等待现有请求完成。
💡 IHostedLifecycleService（.NET 8+）是 IHostedService 的扩展，多了 Starting/Started/Stopping/Stopped 四个钩子。 大多数时候用不到；需要"在所有服务的 StartAsync 之前先跑一段"时才用 StartingAsync。

陷阱 2：ExecuteAsync 抛异常会怎样

这个行为在 .NET 6 前后不同，而且默认值出人意料：

.NET Core 3.x / .NET 5.NET 6+
ExecuteAsync 未捕获异常 ❌ 静默吞掉——服务悄悄死了，进程继续跑，日志里什么都没有 ✅ 记录日志 → StopApplication() → 整个 Host 关闭，进程以非零退出码结束
控制开关 无 HostOptions.BackgroundServiceExceptionBehavior，默认 StopHost；可改为 Ignore 恢复旧行为

.NET 6+ 的默认（StopHost）是对的——一个死掉的后台服务比一个崩掉的进程更危险，因为编排器（K8s、Windows SCM）会重启崩掉的进程，却不知道进程里有个服务已经死了。 但这也意味着：你的循环里必须自己 try/catch 可恢复的错误（网络抖动、队列暂时不可用），否则一次瞬时故障就让整个进程重启。 

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        try
        {
            await ProcessBatchAsync(stoppingToken);
        }
        catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
        {
            break;                          // 正常关闭，不是错误
        }
        catch (Exception ex)
        {
            logger.LogError(ex, "Batch failed, retrying in 10s");   // 可恢复错误：记日志、退避、继续
            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
        // 真正不可恢复的错误（配置错、程序 bug）——让它抛出去，StopHost 是正确的
    }
}

陷阱 3：Singleton 里用 Scoped 服务

hosted service 是 Singleton，将来你会想在里面用 DbContext（EF Core 默认 Scoped）。直接注入 = 第 4 课的 Captive Dependency， Development 环境下 ValidateScopes 会直接拒绝启动。正确做法：每次迭代自己开一个 Scope。 

public sealed class OrderSyncWorker(
    IServiceScopeFactory scopeFactory,          // ← 注入工厂，不注入 Scoped 服务本身
    ILogger<OrderSyncWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using (var scope = scopeFactory.CreateScope())          // 一次迭代 = 一个 Scope（对应 Web 里的一个请求）
            {
                var sync = scope.ServiceProvider.GetRequiredService<IOrderSyncService>();  // Scoped
                await sync.RunOnceAsync(stoppingToken);
            }                                                        // Scope 结束，DbContext 等 IDisposable 被释放
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}

HostOptions：关闭超时与并发启动

属性默认含义
ShutdownTimeout 30 秒 StopAsync 的总预算。超时后传给各服务的 token 被取消，Host 不再等待，直接往下走。你的 ExecuteAsync 如果 30 秒内没退出，会被丢下
StartupTimeout 无限 StartAsync 的总预算。生产上建议设一个，避免某个服务的 StartAsync 卡死让进程"假活"
ServicesStartConcurrently false true 时所有 hosted service 并行启动——启动更快，但失去"注册顺序 = 启动顺序"的保证
ServicesStopConcurrently false 同上，用于关闭
BackgroundServiceExceptionBehavior StopHost 见陷阱 2 
// 代码配置
builder.Services.Configure<HostOptions>(o =>
{
    o.ShutdownTimeout = TimeSpan.FromSeconds(60);
    o.StartupTimeout  = TimeSpan.FromSeconds(30);
});

// 或 appsettings.json —— Host 会从配置里读这几个键
// { "shutdownTimeoutSeconds": 60, "startupTimeoutSeconds": 30, "servicesStartConcurrently": true }
⚠️ 容器里的 30 秒。docker stop 和 K8s 的 terminationGracePeriodSeconds 默认也是 30 秒——发 SIGTERM，30 秒后 SIGKILL。 如果你把 ShutdownTimeout 调到 60 秒，编排器会在第 30 秒直接杀进程，你调的 60 秒毫无意义。两边要一起调。

替代 ServiceBase / TopShelf：作为 Windows 服务或 systemd 运行

同一个 Worker 项目，加一行就能作为系统服务运行——这就是 IHostLifetime 可替换的价值： 

// NuGet: Microsoft.Extensions.Hosting.WindowsServices
// NuGet: Microsoft.Extensions.Hosting.Systemd
var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddWindowsService(o => o.ServiceName = "OrderSync");  // 换成 WindowsServiceLifetime：SCM 的 Start/Stop 映射到 Host 的 Start/Stop
builder.Services.AddSystemd();                                          // 换成 SystemdLifetime：支持 Type=notify，向 systemd 报告"已就绪"

// 两个都加没关系——各自检测运行环境，不在对应环境下就什么都不做，退回 ConsoleLifetime

# 安装（Windows）
sc.exe create OrderSync binPath= "C:\svc\OrderSync.exe"
sc.exe start OrderSync
⚠️ 作为 Windows 服务运行时最常见的第一个错误：找不到 appsettings.json。 上一课讲过 ContentRoot 默认是当前工作目录——服务由 SCM 启动时当前目录是 C:\Windows\System32。 现代版本（.NET 6+）的 Host builder 有一个专门的特判：当前目录恰好是 System32 时，退回 AppContext.BaseDirectory（exe 所在目录）， 源码注释直接点名了 Windows 服务和 MSIX 这两个场景（HostingHostBuilderExtensions.SetDefaultContentRoot）。 老版本没有这个特判，需要自己 UseContentRoot(AppContext.BaseDirectory)。另外注意：这个特判只认 System32，如果你的服务被配置成其他工作目录，还是会找不到文件。

检查理解

❓ 直接实现 IHostedService，在 StartAsync 里写 while(!ct.IsCancellationRequested) 轮询循环，会发生什么？
正常运行——这就是 IHostedService 的设计用法
Host 永远卡在启动阶段——后续服务和 ApplicationStarted 都不会触发
编译错误——StartAsync 必须在 StartupTimeout 内返回
Host 检测到未完成的 Task，自动改为后台运行
❓ .NET 8 上，一个 BackgroundService.ExecuteAsync 抛出未捕获的 InvalidOperationException，默认结果是？
该服务停止，其他服务和进程继续运行，异常写入日志
异常被静默吞掉，什么都不会发生，服务悄悄死亡
记录日志后整个 Host 关闭，进程以非零退出码结束
Host 自动重启该服务，最多重试三次后放弃
❓ 后台服务 A 依赖 B 已经启动（B 建好连接池 A 才能用）。默认配置下，应该怎么注册？
先 AddHostedService<A> 再 AddHostedService<B>——Host 会解析依赖自动排序
先 AddHostedService<B> 再 AddHostedService<A>——注册顺序即启动顺序
顺序无关——所有 hosted service 默认并行启动
在 A 的构造函数注入 B——DI 会保证 B 先构造即先启动
❓ 一个 BackgroundService 每分钟需要用 EF Core 的 DbContext（Scoped）同步一次数据，正确写法是？
构造函数直接注入 DbContext——Host 会为 hosted service 自动创建 Scope
把 DbContext 改注册为 Singleton——后台服务本来就只需要一个
注入 IServiceScopeFactory，每次迭代 CreateScope() 后解析 DbContext
注入 IServiceProvider，每次迭代 GetRequiredService<DbContext>()

关键术语

IHostedService
StartAsync / StopAsync 两个方法的接口。通过 AddHostedService<T>() 注册，本质是 Singleton。StartAsync 被 Host await——它是"启动"不是"运行"，长循环不能放这里。
BackgroundService
IHostedService 的抽象基类，你只实现 ExecuteAsync(CancellationToken stoppingToken)。基类的 StartAsync 调用 ExecuteAsync 但不 await，StopAsync 取消 token 后等待其结束。stoppingToken 是唯一的退出信号，必须传给所有 await。
IHostedLifecycleService
.NET 8+ 扩展接口，在 StartAsync/StopAsync 前后各加一个钩子：StartingAsync → StartAsync → StartedAsync，StoppingAsync → StopAsync → StoppedAsync。
启动顺序 / 关闭顺序
默认串行：启动按注册顺序，关闭按注册顺序的倒序（LIFO）。ApplicationStarted 在所有服务启动完成后触发；ApplicationStopping 在任何服务停止之前触发。
BackgroundServiceExceptionBehavior
HostOptions 的属性。.NET 6+ 默认 StopHost：ExecuteAsync 未捕获异常 → 记日志 → 关闭整个 Host。Ignore 恢复 .NET 5 的静默吞掉行为（不推荐）。
ShutdownTimeout
HostOptions 的属性，默认 30 秒。StopAsync 的总预算，超时后各服务收到的 token 被取消，Host 不再等待。要与容器编排器的 grace period 一起调。
IServiceScopeFactory
在 Singleton（如 hosted service）中安全使用 Scoped 服务的方式：注入工厂，每次工作单元 CreateScope()，从 scope.ServiceProvider 解析，using 结束时释放。一次迭代对应 Web 里的一个请求。
AddWindowsService / AddSystemd
替换 IHostLifetime 为 WindowsServiceLifetime / SystemdLifetime，让同一个 Worker 项目作为系统服务运行。替代 Framework 时代的 ServiceBase 和 TopShelf。检测到不在对应环境时自动退回 ConsoleLifetime。
