第 4 课：依赖注入基础

模块：依赖注入（1/3） |  预计阅读/练习时间：25 分钟

前三个模块我们都在讲运行时——项目怎么编译、GC 怎么回收、内存怎么控制。 但 Framework 4.8 开发者进入现代 .NET 面临的最大范式转变不是运行时，而是这里： 依赖注入从"第三方容器的第三方用法"变成了内置的、处处渗透的基础设施。

  • 理解 MSDI 是什么，以及为什么它不是又一个 Autofac
  • 掌握 Transient / Scoped / Singleton 三种生命周期的行为和适用场景
  • 理解 IServiceCollection + IServiceProvider 的注册与解析模型
  • 识别 Captive Dependency——DI 第一杀手

Framework 4.8 时代：DI 是"别人的事"

回忆一下你当年怎么用 DI：

Framework 4.8 + Autofac
// Global.asax.cs — Application_Start
var builder = new ContainerBuilder();
builder.RegisterType<UserService>()
       .As<IUserService>()
       .InstancePerLifetimeScope();
builder.RegisterType<LogService>()
       .As<ILogService>()
       .SingleInstance();
var container = builder.Build();

// 获取服务——Service Locator
var service = container.Resolve<IUserService>();
现代 .NET
// Program.cs — 一行一行链下去
var builder = Host.CreateApplicationBuilder();
builder.Services.AddScoped<IUserService, UserService>();
builder.Services.AddSingleton<ILogService, LogService>();
var host = builder.Build();

// 不手动 Resolve——构造函数注入
class MyController(IUserService userService)

区别不在语法，在系统地位：

Framework 4.8现代 .NET
DI 容器第三方（Autofac/Ninject/Unity）— NuGet 自己装内置——Microsoft.Extensions.DependencyInjection
使用方式Service Locator（container.Resolve<T>()）构造函数注入——框架自动解析
配置方式XML / Module 类 / 分散在各地扩展方法——services.AddXxx() 链式调用
渗透程度Web 项目才用，控制台几乎不用所有项目类型都用同一套（控制台/WPF/Worker/Web）
框架集成需要胶水代码ASP.NET Core / EF Core / HttpClientFactory / Logging 全部原生基于这套 DI
💡 关键心智转变：Framework 4.8 时代你可能写过 new UserService() 来创建服务实例。 在现代 .NET 中，你应该几乎永远不写 new——所有依赖都通过构造函数注入。 这不仅仅是"最佳实践"，而是整个平台的设计契约——ASP.NET Core、EF Core、HttpClientFactory 的整个生命周期都依赖 DI 容器管理。

核心模型：IServiceCollection → IServiceProvider

MSDI 的架构极其简单——只有三个核心接口：

MSDI 架构

IServiceCollection               IServiceProvider           你的类
┌────────────────────┐          ┌────────────────┐        ┌──────────┐
│ 注册表（一堆描述符）  │  Build()  │  服务容器       │ Resolve│          │
│                    │ ───────→ │                │ ─────→ │ 构造函数  │
│ AddTransient<A,B>()│          │ 单例缓存        │        │ 拿到实例  │
│ AddScoped<C,D>()   │          │ Scope 工厂      │        │          │
│ AddSingleton<E,F>()│          │ 生命周期管理     │        └──────────┘
└────────────────────┘          └────────────────┘

// 最小完整示例
using Microsoft.Extensions.DependencyInjection;

// 1. 创建 ServiceCollection（注册表）
var services = new ServiceCollection();

// 2. 注册服务
services.AddTransient<IMessageWriter, ConsoleMessageWriter>();
services.AddSingleton<App>();

// 3. Build → 得到 IServiceProvider（容器）
ServiceProvider provider = services.BuildServiceProvider();

// 4. 解析入口对象
App app = provider.GetRequiredService<App>();
app.Run();

// 5. 释放容器（释放所有 Singleton + 清理）
provider.Dispose();

三个接口的分工：

接口角色你用它的方式
IServiceCollection注册表——记录"什么接口映射到什么实现"在启动代码中 services.AddXxx()
IServiceProvider容器——根据注册表创建/缓存/返回实例框架用；你只在极少数情况下手动 GetRequiredService<T>()
IServiceScopeFactoryScope 工厂——创建子容器Singleton 中需要 Scoped 服务时，或在 IHostedService 中

三种生命周期：DI 的灵魂

这是整个 MSDI 中最需要理解透彻的东西。选错生命周期是最常见的 bug 来源。

生命周期对比——同一个请求 / Scope 内多次解析

        第 1 次 GetService<T>()           第 2 次 GetService<T>()
        ┌───────────────────┐          ┌───────────────────┐
Transient │ new → 返回实例 A   │          │ new → 返回实例 B   │  ← 每次不同
Scoped    │ new → 缓存 → 返回 A│          │ 命中缓存 → 返回 A  │  ← Scope 内相同
Singleton │ new → 缓存 → 返回 A│          │ 命中缓存 → 返回 A  │  ← 永远相同
        └───────────────────┘          └───────────────────┘

Transient：用完即弃

services.AddTransient<IEmailSender, SmtpEmailSender>();

// 每次 GetService → 新对象
// 同一个请求里解析两次 → 两个不同实例
// "无状态的小工具类"最适合 Transient

用 Transient 的场景：无状态的工具类（序列化器、映射器）、每次执行逻辑都不同的轻量服务。

⚠️ 陷阱：如果你注册了 Transient 但把它注入到 Singleton 中，它会被 Singleton 持有引用—— 虽然它"名义上"是 Transient，但只被创建了一次，变成事实上的 Singleton。 这不是 MSDI 的 bug，是类型系统无法阻止的引用持有问题。

Scoped：一个 Scope 内共享

services.AddScoped<IUnitOfWork, EfUnitOfWork>();

// HTTP 请求 → 框架自动创建一个 Scope
//   同一个请求里解析 100 次 → 返回同一个实例
//   不同请求 → 不同实例

// 自己创建 Scope
using (var scope = provider.CreateScope())
{
    var uow1 = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();
    var uow2 = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();
    // uow1 == uow2  ✅ 同一个 Scope 内相同
}
// Scope 结束 → 其中所有 Transient 和 Scoped 服务自动 Dispose

用 Scoped 的场景：Unit of Work、DbContext（EF Core 默认 Scoped）、请求级别的上下文信息、需要在一个业务操作内共享状态的服务。

Singleton：全应用唯一

services.AddSingleton<ICache, RedisCache>();

// 整个应用生命周期内只创建一次
// 所有线程、所有请求共享同一个实例
// 容器 Dispose 时才释放

用 Singleton 的场景：无状态且创建成本高的服务、全应用共享的缓存、配置快照。必须是线程安全的。

⚠️ Singleton 的真正代价（不仅仅是线程安全）：
  • 可能把大对象图一直锁在内存里，直到进程退出
  • 如果 Singleton 或其依赖树中任何一环挂了，无法恢复
  • 不支持"热重载"配置——创建时读了配置，后续配置变了它不知道
  • 可能意外"捕获"Scoped 服务（Captive Dependency——见下文）
大多数业务服务应该用 Scoped，不是 Singleton。

快速决策表

你的服务…用
无状态，每次调用都是独立逻辑Transient
在一个请求/操作内需要共享状态Scoped
全应用共享，线程安全，创建成本高Singleton
EF Core 的 DbContextScoped（默认，别改）
HTTP Client / HttpClientFactory 创建的 ClientScoped 或 Transient

注册模式：不止 AddXxx<T,U>()

接口→实现（最常用）

services.AddScoped<IUserRepository, EfUserRepository>();
// 请求 IUserRepository → 返回 EfUserRepository 实例

只注册具体类型

services.AddScoped<MyService>();
// 只能通过 MyService 类型解析，没有接口抽象
// 适用于简单类型或值对象

已有实例（Singleton 专用）

var cache = new RedisCache("connection-string");
services.AddSingleton<ICache>(cache);
// 你手动控制创建和生命周期——容器不帮你 Dispose！

工厂注册（需要构造逻辑时）

services.AddScoped<IUserService>(sp =>
{
    var repo = sp.GetRequiredService<IUserRepository>();
    var logger = sp.GetRequiredService<ILogger<UserService>>();
    return new UserService(repo, logger, Environment.MachineName);
});
// sp 是当前 Scope 的 IServiceProvider——可以解析其他已注册的服务

TryAdd——"我有默认值，但允许覆盖"

// 在库/framework 代码中：提供默认实现
services.TryAddSingleton<ICache, MemoryCache>();

// 在应用代码中：覆盖默认
services.AddSingleton<ICache, RedisCache>();  // 这个生效！
// TryAdd 不会覆盖已有的注册
💡 开放泛型注册：MSDI 支持 services.AddSingleton(typeof(IRepository<>), typeof(EfRepository<>))—— 当你请求 IRepository<Order> 时自动返回 EfRepository<Order>。 这是你天天在用的 ILogger<T> 的底层机制。

构造函数注入：服务怎么拿到依赖？

现代 .NET 中你看到的构造函数注入：

public class OrderService
{
    private readonly IUserRepository _users;
    private readonly IOrderRepository _orders;
    private readonly ILogger<OrderService> _logger;

    // 构造函数——DI 容器自动解析每个参数
    public OrderService(
        IUserRepository users,
        IOrderRepository orders,
        ILogger<OrderService> logger)
    {
        _users = users;
        _orders = orders;
        _logger = logger;
    }

    public async Task<Order> PlaceOrderAsync(int userId, OrderItem[] items)
    {
        _logger.LogInformation("创建订单 {UserId}", userId);
        var user = await _users.GetByIdAsync(userId);
        var order = Order.Create(user, items);
        await _orders.SaveAsync(order);
        return order;
    }
}

// Primary Constructor（C# 12+）——更简洁
public class OrderService(
    IUserRepository users,
    IOrderRepository orders,
    ILogger<OrderService> logger)
{
    public async Task<Order> PlaceOrderAsync(int userId, OrderItem[] items)
    {
        logger.LogInformation("创建订单 {UserId}", userId);
        // ...
    }
}

如果构造函数有多个重载，DI 容器会选参数最多的那个（能全部解析的前提下）。有歧义就抛异常。

⚠️ 别用 Service Locator 模式：在 Framework 4.8 时代你可能习惯 container.Resolve<T>() 到处取服务。在现代 .NET 中这是反模式——它隐藏依赖关系、让单元测试变困难。 唯一的例外：在 IHostedService 或 Singleton 中需要 Scoped 服务时， 通过 IServiceScopeFactory 创建 Scope 再获取——但这是有意识的选择，不是偷懒。

Captive Dependency：DI 第一杀手

这是现代 .NET DI 中最常见的 bug——也是 Framework 4.8 开发者最容易踩的坑。

什么是 Captive Dependency？

// ❌ 错误：Singleton 注入了 Scoped 服务
services.AddSingleton<CacheWarmer>();     // 全应用唯一
services.AddScoped<IDbContext, AppDbContext>();  // 每个请求一个

public class CacheWarmer
{
    public CacheWarmer(IDbContext db)  // ← db 是 Scoped！
    {
        // db 被"囚禁"在 CacheWarmer 中
        // CacheWarmer 活到应用关闭 → db 也活到应用关闭
        // 但 db 本该在每个请求结束后释放！
    }
}

为什么会出问题？

正常情况：Scoped 服务的生命周期

HTTP 请求 1 开始 → Scope 1 创建 → 创建 AppDbContext 实例 A
HTTP 请求 1 结束 → Scope 1 释放 → AppDbContext A 释放 ✅

Captive Dependency：Scoped 被俘虏

应用启动 → 创建 Singleton CacheWarmer
           └── 构造函数要 IDbContext → 容器创建 AppDbContext 实例 B
                                       └── B 被 CacheWarmer 持有引用
HTTP 请求 1 结束 → Scope 1 释放 → 但 AppDbContext B 还在！
HTTP 请求 2 结束 → Scope 2 释放 → 但 AppDbContext B 还在！
...
应用关闭 → CacheWarmer 释放 → AppDbContext B 终于释放 💀
             （可能已经持有几万个过期实体的引用）

怎么发现？

// 开发环境启用 Scope Validation
ServiceProvider provider = services.BuildServiceProvider(
    new ServiceProviderOptions
    {
        ValidateScopes = true  // ← 开发环境开这个
    });

// 如果有 Singleton → Scoped 的依赖，直接抛异常：
// InvalidOperationException: Cannot consume scoped service
// 'IDbContext' from singleton 'CacheWarmer'.

怎么修？

方案何时用
把 Scoped 升级为 Singleton只有确认服务本身支持全应用共享（如无状态连接池）
把 Singleton 降级为 Scoped该服务本身就不该是全局的——大多数情况应该用这个方案
IServiceScopeFactorySingleton 确实需要 Scoped，但它只在方法内临时用——手动创建 Scope
// ✅ 方案 3：Singleton 通过 IServiceScopeFactory 临时获取 Scoped 服务
public class CacheWarmer
{
    private readonly IServiceScopeFactory _scopeFactory;

    public CacheWarmer(IServiceScopeFactory scopeFactory)  // 不是 IDbContext
    {
        _scopeFactory = scopeFactory;
    }

    public async Task WarmCacheAsync()
    {
        using var scope = _scopeFactory.CreateScope();  // 手动创建 Scope
        var db = scope.ServiceProvider.GetRequiredService<IDbContext>();
        // 用 db 做缓存预热...
    }  // Scope 结束 → db 释放 ✅
}

深入：Singleton 注入 Transient 算不算 Captive Dependency？

这是一个在面试和实际项目中经常被问到的问题。技术上需要分两层来看：

Singleton → Transient：语义上的 Captive Dependency

// ⚠️ 灰色地带：Singleton 注入了 Transient
	services.AddSingleton<BackgroundWorker>();
	services.AddTransient<IEmailSender, SmtpEmailSender>();

	public class BackgroundWorker
	{
	    private readonly IEmailSender _email;  // Transient！

	    public BackgroundWorker(IEmailSender email)
	    {
	        _email = email;  // ← 这个 Transient 实例被 Singleton 永久持有
	    }
	}
	
	Singleton → Transient：引用囚禁

	应用启动 → 创建 Singleton BackgroundWorker
	           └── 构造函数要 IEmailSender（Transient）
	               → 容器 new SmtpEmailSender 实例 A
	               → A 被 BackgroundWorker._email 持有

	此后无论解析多少次 BackgroundWorker，它内部的 _email 永远是 A
	→ "名义上 Transient，事实上 Singleton"

	更隐蔽的问题：
	- SmtpEmailSender 可能持有 HttpClient（应短命）
	- 如果有多个 Singleton 各注入同一个 Transient，每个 Singleton 得到不同的实例
	  → 行为不一致，极难调试

为什么 ValidateScopes 不报？ 因为 Transient 没有 Scope 归属——从 MSDI 的角度看，把 Transient 给 Singleton 在技术上是"合法"的（不会像 Scoped 那样在 Scope 释放后留下 dangling 引用）。但这不代表它是对的——它违背了你注册 Transient 时的语义意图：每次解析都创建新实例。

要不要修？取决于你的意图

你的真实意图正确做法
"我只需要一个实例跟着 Singleton 走"把它注册为 Singleton，让意图明确
"我需要每次调用时都新建实例"注入 Func<T> 或 IServiceScopeFactory，在方法内解析
"这个服务本身创建成本极低、无状态、用完就扔"检查父服务真的需要是 Singleton 吗？也许降级为 Scoped 更合适
// ✅ 方案：用 Func<T> 在每次调用时获取新实例
	public class BackgroundWorker
	{
	    private readonly Func<IEmailSender> _createSender;  // 工厂

	    public BackgroundWorker(Func<IEmailSender> createSender)
	    {
	        _createSender = createSender;
	    }

	    public async Task SendAsync(string message)
	    {
	        var email = _createSender();  // 每次调用 → 新实例 ✅
	        await email.SendAsync(message);
	    }  // 使用完即丢弃
	}

Scoped → Transient：通常安全

// ✅ 这通常没问题
	services.AddScoped<OrderService>();
	services.AddTransient<IPriceCalculator, DefaultPriceCalculator>();

	public class OrderService
	{
	    private readonly IPriceCalculator _calc;  // Transient

	    public OrderService(IPriceCalculator calc)
	    {
	        _calc = calc;  // 被 Scoped 持有 → 跟着 Scoped 一起释放
	    }
	}

关键区别：Scoped 服务的生命周期是有限的（一个请求结束就释放），被它持有的 Transient 也会一起释放。下一个请求创建新的 Scoped → 新的 Transient。虽然同一个 Scope 内多次解析 Scoped 时不会重新创建它内部的 Transient（因为 Scoped 只构造一次），但在实践中几乎没有影响——Scope 本来就短命。

安全矩阵：谁注入谁

父（长）→ 子（短）Transient 子Scoped 子Singleton 子
Transient 父✅ 安全✅ 安全✅ 安全
Scoped 父✅ 通常安全✅ 安全✅ 安全
Singleton 父⚠️ 语义 Captive❌ 真正 Captive✅ 安全

规则很简单：短生命周期可以依赖长生命周期；长生命周期依赖短生命周期就是 Captive Dependency。Singleton → Transient 处于灰色地带——MSDI 不报错，但违背了 Transient 的语义。理解这一点，你就比大多数 .NET 开发者对这个概念理解得更深。

关键术语

MSDI（Microsoft.Extensions.DependencyInjection）
现代 .NET 内置的 DI 容器。极简设计——不支持属性注入、不支持程序集扫描、不支持装饰器模式。但这些可以用第三方库（Scrutor）或替换容器（Autofac/Lamar）补上。
IServiceCollection
服务注册表——启动时通过 AddTransient/AddScoped/AddSingleton 填写，Build 后变成 IServiceProvider。一个 ServiceDescriptor 的列表。
IServiceProvider
服务容器——根据注册表创建、缓存、返回服务实例。线程安全。通过构造函数注入自动使用，你几乎不需要手动调用。
Transient
每次解析都创建新实例。适用无状态的轻量工具类。注意：如果被 Singleton 持有引用，会产生"事实上的 Singleton"。
Scoped
在一个 Scope 内共享同一实例。HTTP 请求是最典型的 Scope——同一个请求里所有解析返回同一实例。EF Core 的 DbContext 默认 Scoped。
Singleton
全应用生命周期内唯一实例。必须线程安全。创建成本高、全应用共享的服务用这个。大多数业务服务不该用 Singleton。
Scope（IServiceScope）
由 IServiceScopeFactory 创建的子容器。ASP.NET Core 中每个 HTTP 请求自动创建一个 Scope。手动创建：using var scope = provider.CreateScope()。
Captive Dependency（囚禁依赖）
DI 反模式——长生命周期服务持有短生命周期服务的引用。分为两个级别：真正 Captive（Singleton 注入 Scoped——ValidateScopes 可检测）和语义 Captive（Singleton 注入 Transient——容器不报错，但 Transient 变成事实上的 Singleton）。规则：短可依赖长，长不可依赖短。
Service Locator（服务定位器）
反模式——在代码中手动调用 GetService<T>() 而不是通过构造函数注入。隐藏依赖关系、难以测试。Framework 4.8 时代的 container.Resolve<T>() 就是典型的 Service Locator。
TryAdd
只在服务尚未注册时才注册——允许框架/库提供默认实现，用户代码可覆盖。不覆盖已有注册。
