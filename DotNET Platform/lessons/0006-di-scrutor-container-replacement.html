第 6 课：超越 MSDI——Scrutor、容器替换与反模式总结

模块：依赖注入（3/3） |  预计阅读/练习时间：32 分钟

前两课我们掌握了 MSDI 的全部内置能力——三种生命周期、Captive Dependency、Func<T>、 IEnumerable<T>、Keyed Service。这些占了日常 DI 使用的 80%。 但 Framework 4.8 开发者从 Autofac 迁移过来时，有两个高频痛点 MSDI 故意不解决： 程序集扫描和装饰器模式。这一课来补上它们，并做一个完整的反模式总结。

  • 理解 MSDI 为什么不做程序集扫描——以及用 Scrutor 怎么补
  • 掌握 装饰器模式在 MSDI 中的实现（Scrutor.Decorate）
  • 判断标准：什么时候该换容器，什么时候不该
  • DI 反模式全面总结——从 Service Locator 到 async 工厂死锁

MSDI 的极简哲学：为什么不内置这些功能？

很多从 Autofac 过来的开发者第一反应是"MSDI 太弱了"——没有程序集扫描、没有装饰器、没有属性注入、 没有基于约定的注册（"所有以 Service 结尾的类都注册"）。

这恰恰是 MSDI 的设计意图。 回顾一下 MSDI 的定位：

设计原则说明
极简内核只做 DI 容器最基本的事情——注册 + 解析 + 生命周期管理。每个功能都经过大量用户验证，零依赖。
不做 Convention over ConfigurationAutofac 的 AsImplementedInterfaces()、模块扫描看起来很酷，但隐式行为让新人难以调试。MSDI 要求你显式声明每一个注册。
不做"框架级"功能属性注入、拦截器（AOP）、装饰器——这些是应用层关注点，不是容器内核职责。
可以扩展，也可以替换整个容器设计为可替换——ASP.NET Core 不关心底下是 MSDI 还是 Autofac。第三方库（Scrutor）在 IServiceCollection 上扩展，不修改内核。
💡 心智模型：MSDI 不是"穷人的 Autofac"——它是"DI 容器的 HTTP 协议"。简单、稳定、 无歧义。你需要高级功能时，要么用扩展库（Scrutor），要么换完整的容器（Autofac/Lamar）。设计者故意不给"半个功能"。

Scrutor：MSDI 的"半官方"扩展

Scrutor 是 MSDI 社区最广泛使用的扩展库， 提供两个核心能力：程序集扫描和装饰器。它不是替换容器——它只是帮你自动写 services.AddXxx()。 

// 安装：dotnet add package Scrutor

程序集扫描（Assembly Scanning）

如果你有 50 个 Service 类，手写 50 行 AddScoped 既枯燥又容易漏。Scrutor 帮你做：

using Scrutor;

// ✅ 扫描整个程序集，按约定自动注册
services.Scan(scan => scan
    .FromAssemblyOf<IMarker>()          // 扫描包含 IMarker 的程序集
    .AddClasses(classes => classes
        .Where(t => t.Name.EndsWith("Service")))  // 只注册以 "Service" 结尾的类
    .AsImplementedInterfaces()          // 映射到它们实现的所有接口
    .WithScopedLifetime());             // 统一注册为 Scoped

// 上面一行 = 手写 50 行 services.AddScoped<IXxxService, XxxService>()

常见的扫描模式：

// 模式 1：按接口注册（最常用）
services.Scan(scan => scan
    .FromAssemblyOf<Program>()
    .AddClasses(classes => classes.AssignableTo<IService>())
    .AsImplementedInterfaces()
    .WithScopedLifetime());

// 模式 2：按命名约定注册
services.Scan(scan => scan
    .FromExecutingAssembly()
    .AddClasses(classes => classes.InNamespaces("MyApp.Services"))
    .AsMatchingInterface()              // UserService → IUserService
    .WithTransientLifetime());

// 模式 3：组合筛选
services.Scan(scan => scan
    .FromAssemblies(assembly1, assembly2)
    .AddClasses(classes => classes
        .Where(t => t.IsClass && !t.IsAbstract)
        .AssignableTo<IHandler>())
    .AsSelfWithInterfaces()             // 既注册具体类型，也注册接口
    .WithSingletonLifetime());
⚠️ 扫描的代价：隐式行为难以调试。新人看到一个 Service 被正确注入，但找不到 services.AddScoped<...>() 在哪儿——原来是 Scrutor 扫描自动注册的。如果你的项目不到 20 个服务，手写注册比扫描更可维护。扫描的价值在大型项目中才显现。

装饰器模式（Decoration）

装饰器是 DI 容器中最强大的扩展机制之一——不修改原类，在外面包一层来做日志、缓存、验证。 这是 Autofac 的 .Decorate<T>() 在 MSDI 中的等效方案。 

// 原始服务（你不想改它）
public interface IUserRepository
{
    Task<User> GetByIdAsync(int id);
}

public class EfUserRepository : IUserRepository
{
    public async Task<User> GetByIdAsync(int id)
    {
        // EF Core 数据库查询
        return await _db.Users.FindAsync(id);
    }
}

// ✅ 装饰器：加上缓存层——不修改 EfUserRepository
public class CachedUserRepository : IUserRepository
{
    private readonly IUserRepository _inner;  // 被装饰的对象
    private readonly IMemoryCache _cache;

    public CachedUserRepository(IUserRepository inner, IMemoryCache cache)
    {
        _inner = inner;
        _cache = cache;
    }

    public async Task<User> GetByIdAsync(int id)
    {
        var key = $"user:{id}";
        return await _cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpiration = TimeSpan.FromMinutes(5);
            return await _inner.GetByIdAsync(id);  // 缓存未命中 → 调用原始实现
        });
    }
}

// 注册：先注册原始实现，再装饰
services.AddScoped<IUserRepository, EfUserRepository>();
services.Decorate<IUserRepository, CachedUserRepository>();  // Scrutor

// 解析 IUserRepository → CachedUserRepository(EfUserRepository(_db))
// 即：CachedUserRepository 包装了 EfUserRepository

多层装饰——按注册顺序层层包裹：

// 装饰器可以叠加
services.AddScoped<IUserRepository, EfUserRepository>();         // 内层：数据库
services.Decorate<IUserRepository, CachedUserRepository>();      // 中层：缓存
services.Decorate<IUserRepository, LoggingUserRepository>();     // 外层：日志

// 解析结构：
// LoggingUserRepository(
//   CachedUserRepository(
//     EfUserRepository(_db)))
//
// 调用链：Logging → Caching → EF Core
//            ↓         ↓         ↓
//         记录日志   检查缓存   查数据库
💡 Scrutor 不是"换容器"，是"帮助注册"：Scan() 和 Decorate() 最终都转化为 services.AddXxx() 调用。解析时仍然是 MSDI 在工作。Scrutor 只是帮你写注册代码。

什么时候该换容器？

Scrutor 解决了扫描和装饰。但有四个能力它做不到——这时候你需要换完整的 DI 容器：

需求MSDI + Scrutor替换容器方案
程序集扫描 ✅ Scrutor .Scan() 不必要换
装饰器 ✅ Scrutor .Decorate() 不必要换
属性注入 ❌ 不支持 换容器或重新设计（大多数场景构造函数注入更优）
AOP / 拦截器 ❌ 不支持 Autofac + Castle DynamicProxy；或用 Source Generator（.NET 7+）
子容器 / 多租户 Scope ❌ 只有一个扁平的 Scope 模型 Autofac 的多层 Lifetime Scope；Lamar 的 Nested Container
Autofac Module 兼容 ❌ 不支持 直接接 Autofac（见下文）

那性能呢？MSDI 更快吗？

是的——MSDI 的解析速度通常优于 Autofac。但这几乎从不成为换不换容器的理由。

容器解析方式单次解析 ≈备注
MSDI 编译好的表达式树（Expression<T>） ~50–100 ns 接近 new 的开销，路径极其精简
Autofac 反射 + 表达式树混合 ~100–300 ns 启用拦截器时额外开销：每次解析时 Castle DynamicProxy 织入
Simple Injector 编译到委托（Func<T>） ~30–80 ns 公认最快的 .NET DI 容器之一

为什么 MSDI 更快？ 一句话：它做更少的事，所以做更快。没有拦截器、没有属性注入、 没有多层 Scope 树——表达式树编译路径极其精简。

但你需要关心吗？ 把纳秒换算成现实的请求：

一次解析 MSDI            ~100 ns
一个请求解析 20 个服务     = 2,000 ns = 0.002 ms
一次 EF Core 数据库查询    ~1–50 ms  = 1,000,000–50,000,000 ns
一次 HTTP 请求延迟         ~10–100 ms

结论：DI 解析的开销相比数据库查询 / 网络 IO，
      差了 5–6 个数量级，完全可以忽略。

什么时候性能差异才重要？ 两种场景：

  • 高吞吐场景——每秒解析百万级对象（消息队列消费者、游戏服务器后端）。这时 Simple Injector 的"编译到委托"策略有明显优势。
  • 启动时间——表达式树编译只在 BuildServiceProvider() 时做一次。Scrutor 扫描 200 个服务也就几毫秒，不是瓶颈。
💡 结论：不要为了"性能"换容器。MSDI 对一个典型请求的 DI 解析开销约 0.002ms——相比几十毫秒的 数据库查询，这不是你的性能瓶颈。换容器的真正理由只有表中那四个：AOP 拦截器、属性注入、子容器、Autofac Module 兼容。

如何替换容器：Autofac 示例

// ASP.NET Core 中换 Autofac
// 1. NuGet: Autofac.Extensions.DependencyInjection

var builder = WebApplication.CreateBuilder(args);

// 2. MSDI 部分——照常用 services.AddXxx()
builder.Services.AddScoped<IUserService, UserService>();

// 3. Autofac 部分——高级功能
builder.Host.UseServiceProviderFactory(new AutofacServiceProviderFactory());
builder.Host.ConfigureContainer<ContainerBuilder>(containerBuilder =>
{
    // Autofac 的增强能力
    containerBuilder.RegisterType<LoggerInterceptor>()
                    .As<IInterceptor>()
                    .SingleInstance();

    containerBuilder.RegisterType<UserService>()
                    .As<IUserService>()
                    .EnableInterfaceInterceptors()  // AOP
                    .InstancePerLifetimeScope();
});

// 解析时：框架自动用 Autofac 容器，而不是 MSDI
// 但你的代码完全不用改——你注的还是 IServiceProvider
⚠️ 换容器的代价：
  • 你绑定了特定容器的 API（Autofac Module、Interceptor 配置）——未来换容器成本高
  • 团队成员需要对两个 DI 系统都有基本了解
  • 行为差异——例如 MSDI 的"最后注册胜出" vs Autofac 的默认行为不同
  • 大多数项目其实不需要换——MSDI + Scrutor 足够
建议：先写完 80% 的代码用 MSDI。如果确实遇到了 Scrutor 解决不了的需求（AOP、子容器、多租户 Scope），再引入 Autofac/Lamar。不要"预防性换容器"。

DI 反模式全面总结

这三课覆盖了 MSDI 的核心用法。这里是所有常见反模式的集中总结——作为长期参考：

反模式表现正确做法危害级别
Service Locator 在方法内调用 provider.GetService<T>() 获取依赖 通过构造函数注入；运行时动态选择时用 Func<T> 或 Keyed Service 🔴 严重
Captive Dependency Singleton 注入 Scoped → Scoped 被囚禁，永不释放 降级为 Scoped；或用 IServiceScopeFactory 创建临时 Scope 🔴 严重
语义 Captive Singleton 注入 Transient → Transient 变成事实 Singleton 改注册为 Singleton（明确意图）；或用 Func<T> 在方法内解析 🟡 中等
Transient IDisposable 泄漏 容器持有所有 Transient IDisposable 引用直到 Scope 结束 用工厂模式创建、手动 Dispose；或注册为 Scoped 🟡 中等
根容器解析 Scoped 从根 IServiceProvider（非 Scope）解析 Scoped → 事实 Singleton 始终在 Scope 内解析 Scoped 服务 🟡 中等
async 工厂死锁 DI 工厂中使用 .Result / .Wait() 保持工厂同步；异步初始化用 IHostedService 🔴 严重
过度 Singleton 所有服务都注册为 Singleton"省事" 默认用 Scoped，只有全应用共享且线程安全的服务才用 Singleton 🟡 中等
多构造函数歧义 一个类有多个构造函数，DI 容器选错了 只保留一个构造函数；或用 [ActivatorUtilitiesConstructor] 指定 🟢 轻微

反模式详解：async 工厂死锁

DI 工厂委托是同步的——IServiceProvider.GetService<T>() 返回的是 T，不是 Task<T>。当你需要一个对象的初始化需要 async（登录、握手、读密钥）， 新手最常见的错误是在工厂里 .Result： 

// 🔴 反模式：工厂中 .Result 阻塞——可能死锁！
services.AddSingleton<IApiClient>(sp =>
{
    var config = sp.GetRequiredService<IConfiguration>();

    var client = new ApiClient();

    // 🚨 在同步工厂里"硬塞"异步方法
    client.LoginAsync(config["Api:Username"], config["Api:Password"]).Result;

    // 同样致命的写法：
    // client.LoginAsync(...).GetAwaiter().GetResult();
    // client.LoginAsync(...).Wait();

    return client;
});

死锁是怎么发生的？ 假设工厂跑在 ASP.NET Core 请求线程上（有 SynchronizationContext）：

工厂委托（同步线程）
  └─ LoginAsync() 开始
       └─ await ReadAsync(socket)        ← 等待网络 IO，控制权交出
            ↓
       异步操作完成，准备回到原线程继续...
            ↓
       ❌ 但原线程被 .Result 阻塞着！      ← 永远等不到释放
            ↓
       💀 死锁：任务等线程，线程等任务

关键在于 SynchronizationContext（ASP.NET Core 早期版本）或线程池饥饿（高并发时）。 await 捕获了调用上下文，完成后需要回到原上下文继续执行——但那个上下文正被 .Result 死死阻塞。这就是"一步等，两边死"。

✅ 正确做法一：工厂保持同步

// 如果初始化不需要网络/IO——就别用 async，保持同步
services.AddSingleton<IApiClient>(sp =>
{
    var config = sp.GetRequiredService<IConfiguration>();
    var client = new ApiClient();
    client.Configure(config["Api:Username"], config["Api:Password"]); // 同步配置
    return client;
});

✅ 正确做法二：异步初始化用 IHostedService

// 初始化确实需要异步——放到 IHostedService 里
// StartAsync 本身就是 async Task，不会阻塞
public class ApiClientInitializer : IHostedService
{
    private readonly IApiClient _client;
    private readonly IConfiguration _config;

    public ApiClientInitializer(IApiClient client, IConfiguration config)
    {
        _client = client;
        _config = config;
    }

    public async Task StartAsync(CancellationToken ct)
    {
        // ✅ 真正的异步上下文，await 一路到底，不会死锁
        await _client.LoginAsync(
            _config["Api:Username"],
            _config["Api:Password"]);
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

// 注册
services.AddSingleton<IApiClient, ApiClient>();
services.AddHostedService<ApiClientInitializer>();
💡 分清两个阶段：
  • 注册阶段（工厂委托）——构建依赖图，必须同步。只做对象的 new 和配置注入，不做 IO。
  • 初始化阶段（IHostedService.StartAsync）——执行异步工作（网络调用、文件读取、密钥拉取）。整个调用链保持 async，没有 .Result 阻塞。

启用开发时检测

// 开发环境——打开所有验证
ServiceProvider provider = services.BuildServiceProvider(
    new ServiceProviderOptions
    {
        ValidateScopes = true,           // 检测 Captive Dependency
        ValidateOnBuild = true           // 检测注册图中的问题（Build 时立即报错，而不是运行时报错）
    });

// Host Builder 中这样开：
builder.UseDefaultServiceProvider(options =>
{
    options.ValidateScopes = true;
    options.ValidateOnBuild = true;
});
💡 内存技巧：记住"短可依赖长，长不可依赖短"。每次注册服务时，心想："这个服务活多久？ 它依赖的服务又活多久？如果它活得比依赖久，就出问题了。"

DI 模块到此结束——与下一个模块的关系

DI 是整个现代 .NET 平台的胶水层。你已经掌握了容器本身，但 DI 的真正威力体现在它 被框架使用的场景中。接下来你会看到： 

DI 在现代 .NET 栈中的位置

┌──────────────────────────────────────────────────────┐
│  你的应用代码（构造函数注入 Func<T> Keyed 等）        │
├──────────────────────────────────────────────────────┤
│  ASP.NET Core  │  EF Core  │  HttpClientFactory     │
│  (每个请求自动  │  (DbContext│  (管理 HttpClient      │
│   创建 Scope)   │   默认 Scoped)│  生命周期避免端口耗尽)  │
├──────────────────────────────────────────────────────┤
│  Configuration    │  Logging      │  Host 模型       │
│  (Options 模式    │  (ILogger<T>   │  (IHostedService │
│   通过 DI 注入)    │   通过 DI 注入) │   通过 DI 托管)   │
├──────────────────────────────────────────────────────┤
│            IServiceProvider（MSDI 容器）               │
└──────────────────────────────────────────────────────┘

下一个模块——配置系统——你会看到 IConfiguration 和 Options 模式如何通过 DI 注入到服务中。然后 Host 模型 会展示 DI 容器如何被托管、启动、停止。整个平台是围绕 DI 搭建的。

关键术语

Scrutor
MSDI 的"半官方"扩展库。提供程序集扫描（.Scan()）和装饰器（.Decorate()）能力。不替换容器，只在注册阶段帮你自动生成 services.AddXxx() 调用。GitHub: khellang/Scrutor。
程序集扫描（Assembly Scanning）
按约定（命名模式、接口继承、命名空间）批量注册服务，替代手写 N 行 AddXxx。Autofac 内置此功能，MSDI 需要 Scrutor 补充。适合大型项目（50+ 服务），小项目手写更清晰。
装饰器模式（Decorator Pattern）
不修改原类、在外面包裹一层实现额外行为（缓存、日志、重试）。DI 容器通过"注册顺序决定包裹顺序"来支持多层嵌套。Scrutor 的 Decorate<T>() 是 MSDI 中的标准实现方式。
容器替换（Container Replacement）
用 Autofac/Lamar/Simple Injector 替换 MSDI 的 IServiceProvider 实现。使用 UseServiceProviderFactory 集成。表面上你的代码仍通过 IServiceProvider 使用，实际解析由第三方容器执行。适合需要 AOP、属性注入、子容器的项目。
ValidateOnBuild
在 BuildServiceProvider() 时立即验证整个服务注册图（依赖是否都能解析、是否有循环依赖），而非等到运行时第一次解析才报错。与 ValidateScopes 互补——前者验证图结构，后者验证生命周期规则。
Transient IDisposable 泄漏
容器会追踪所有它创建的 IDisposable 实例。Transient 服务如果实现了 IDisposable，其引用被容器持有直到所属 Scope 释放——即使业务代码早已不再使用它。这就是为什么"Transient 用完即弃"的说法不完全准确——容器在幕后记着它。
