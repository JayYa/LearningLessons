Lesson 04 · 主线 B：运行与配置

不改镜像，只改配置

同一个镜像，换个端口、换个问候语、换个数据库密码 —— 全部在 docker run 那一刻决定，一次 build 都不用。

前三课你学会了造镜像。但日常工作里更多的时刻是：拿到一个别人的镜像（postgres、redis、nginx）， 要让它按你的方式跑起来。镜像是只读的，你改不了它 —— 那配置从哪进去？ 答案只有三个入口：环境变量、挂载文件、端口映射。 这一课把三个入口全部走一遍，先用你自己的 hello-api，再用 postgres。

一、原理：运行期的三个入口

镜像（只读）

build 时冻结

  • 程序文件、依赖
  • ENV 写的默认值
  • appsettings.json 的默认值
→
docker run

容器（可配）

run 时注入

  • -e KEY=VALUE 覆盖环境变量
  • -v 宿主机路径:容器路径 覆盖文件
  • -v 卷名:容器路径 持久化数据
  • -p 宿主机端口:容器端口
参数做什么典型用途
-e KEY=VALUE给容器进程设一个环境变量，覆盖镜像里 ENV 的同名值密码、端口、连接串、开关
-v C:\path\file:/app/filebind mount：把宿主机上的文件/目录"叠"到容器路径上，遮住镜像里原来的覆盖配置文件、挂初始化脚本
-v pgdata:/var/lib/…named volume：Docker 自己管理的一块存储，容器删了它还在数据库数据、上传文件
-p 5000:8080宿主机 5000 → 容器 8080。只是转发，不改应用监听什么对外暴露服务

怎么区分 -v 的两种用法？看冒号左边：是路径（含 \ 或 /）就是 bind mount，是个名字就是 named volume。 权威说明：Bind mounts · Volumes。

.NET 怎么读这些？ASP.NET Core 的配置是分层的：appsettings.json → appsettings.{Env}.json → 环境变量 → 命令行参数， 后加载的覆盖先加载的。所以 -e 能压过 appsettings.json，无论那个文件是镜像里的还是你挂进去的。 见 Configuration in ASP.NET Core。

二、动手

在 demo\hello-api 目录下操作。约 8 分钟。

  1. 不重新 build，把监听端口从 8080 改成 5000。

    cd demo\hello-api

docker run -d --rm --name hello -p 5000:5000 -e ASPNETCORE_HTTP_PORTS=5000 hello-api:1.1
curl http://localhost:5000
# → Hello from a container!
docker logs hello
# 里面有一行：Now listening on: http://[::]:5000
docker rm -f hello

    ASPNETCORE_HTTP_PORTS 是 aspnet 镜像里 ENV 预设的变量（默认 8080），-e 把它覆盖了。 -p 5000:5000 是另一件事：宿主机 5000 转发到容器 5000。上一课第 5 题的坑 —— 只改 -p 不改监听端口，容器里没人接电话。 --rm：容器停止后自动删除，做实验免得留一堆尸体。

  2. 唯一一次 build：让应用读一个配置项。这是代码改动，所以必须重建 —— 对照后面几步，感受"什么要 build、什么不要"。

    (Get-Content Program.cs) -replace 'app.MapGet\("/", \(\) => "Hello from a container!"\);', 'app.MapGet("/", (IConfiguration cfg) => cfg["Greeting"] ?? "Hello from a container!");' | Set-Content -Encoding utf8 Program.cs
Get-Content Program.cs

docker build -t hello-api:1.2 .

    现在 / 返回配置里的 Greeting；没配就回退到原句。restore 那层依旧 CACHED。

  3. 同一个镜像，三种方式喂配置。

    # 准备一个要挂进去的配置文件
mkdir config
'{ "Greeting": "Hello from a mounted file!" }' | Set-Content -Encoding utf8 config\appsettings.json

# ① 什么都不给 → 回退值
docker run -d --rm --name hello -p 8080:8080 hello-api:1.2
curl http://localhost:8080
docker rm -f hello

# ② 环境变量
docker run -d --rm --name hello -p 8080:8080 -e Greeting="Hello from an env var!" hello-api:1.2
curl http://localhost:8080
docker rm -f hello

# ③ bind mount 覆盖 appsettings.json
docker run -d --rm --name hello -p 8080:8080 -v "${PWD}\config\appsettings.json:/app/appsettings.json" hello-api:1.2
curl http://localhost:8080
docker exec hello cat /app/appsettings.json     # 容器里看到的已经是你的文件
docker rm -f hello

# ④ 两个都给 → 谁赢？
docker run -d --rm --name hello -p 8080:8080 -v "${PWD}\config\appsettings.json:/app/appsettings.json" -e Greeting="Hello from an env var!" hello-api:1.2
curl http://localhost:8080
docker rm -f hello

    ① Hello from a container! → ② Hello from an env var! → ③ Hello from a mounted file! → ④ Hello from an env var!

    镜像一个字节没动，行为换了三次。④ 证明了 .NET 的覆盖顺序：环境变量压过文件。

    Windows 上 bind mount 的路径写法：冒号左边必须是绝对路径，所以用 ${PWD} 拼出来； 反斜杠、正斜杠 Docker Desktop 都认；整段用双引号包住，防止 PowerShell 把冒号当别的东西。 路径写错不会报错 —— Docker 会在容器里创建一个空目录盖住原文件，应用启动就崩。用 docker exec hello ls -la /app 验证。

  4. 第三方镜像：先让它告诉你缺什么。不查文档，直接跑 postgres：

    docker run -d --name pg postgres:17-alpine
docker ps -a --filter name=pg      # STATUS: Exited (1)
docker logs pg
    Error: Database is uninitialized and superuser password is not specified.
       You must specify POSTGRES_PASSWORD to a non-empty value for the
       superuser. For example, "-e POSTGRES_PASSWORD=password" on "docker run".

    容器秒退 → 第一反应永远是 docker logs。写得好的镜像会把缺的配置直接告诉你。 再去 Docker Hub 的 postgres 页面核对：POSTGRES_PASSWORD 必需，POSTGRES_DB 可选，数据在 /var/lib/postgresql/data。 这三类信息（必需 env、可选 env、数据路径）是读任何镜像文档时要找的东西。 

    docker rm -f pg

  5. 用 named volume 让数据活过容器。

    docker run -d --name pg -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=shop -p 5432:5432 -v pgdata:/var/lib/postgresql/data postgres:17-alpine
Start-Sleep 5
docker exec pg psql -U postgres -d shop -c "CREATE TABLE orders(id int); INSERT INTO orders VALUES (1),(2);"

# 干掉容器 —— 连同它的文件系统
docker rm -f pg

# 同样的命令再跑一次，接上同一个卷
docker run -d --name pg -e POSTGRES_PASSWORD=secret -e POSTGRES_DB=shop -p 5432:5432 -v pgdata:/var/lib/postgresql/data postgres:17-alpine
Start-Sleep 5
docker exec pg psql -U postgres -d shop -c "SELECT count(id) FROM orders;"
# → 2

docker volume ls --filter name=pgdata

    容器删了又建，orders 表还在。数据不在容器里，在 pgdata 卷里；容器只是"插上"它。 自己试试：去掉 -v 重复这一步，表会消失。

    顺手回忆上一课：docker exec pg sh -c 'echo $POSTGRES_PASSWORD' 能打印出 secret —— 因为 -e 是运行期环境变量， 和只活在构建期的 ARG 正相反。

三、检索练习

1. 想让 hello-api 容器里的应用监听 5000 而不是 8080，且不重新 build。怎么做？

-e ASPNETCORE_HTTP_PORTS=5000。-p 只是转发，不改应用监听什么；EXPOSE 是纯元数据，改了也没用。

2. 同时给了 -e Greeting=X 和挂载了一个 Greeting 为 Y 的 appsettings.json。.NET 应用读到什么？

ASP.NET Core 默认配置源顺序：appsettings.json → 环境变量 → 命令行，后者覆盖前者。这是实验 ④ 亲眼看到的。

3. docker run -d --name pg postgres:17-alpine 之后容器立刻退出。第一步做什么？

docker logs pg。容器退出前的输出还在，官方镜像通常会明确说缺什么。这是排查一切"跑不起来"的第一步。

4. 只写出 docker run 里那一个参数：把 named volume pgdata 挂到 postgres 的数据目录 /var/lib/postgresql/data。

5. 你要用本机的一个 appsettings.json 覆盖容器 /app 里的同名文件。用哪种方式？

要指定"宿主机上的哪个文件" → bind mount。named volume 由 Docker 管理，你不直接指定它在宿主机的位置，适合数据库数据这类"我不关心它存哪，只要别丢"的东西。

6. 拿到一个从没用过的第三方镜像，去 Docker Hub 看它的文档时，你要找哪三类信息？容器跑不起来时第一条命令是什么？

  1. 必需的环境变量（如 POSTGRES_PASSWORD）—— 少了就启动失败
  2. 可选的环境变量（如 POSTGRES_DB、POSTGRES_USER）—— 改默认行为
  3. 数据/配置的路径（如 /var/lib/postgresql/data、/docker-entrypoint-initdb.d）—— 决定 -v 挂哪里

外加：它监听哪个端口（决定 -p）。跑不起来 → docker logs 容器名。速查见运行期配置速查。
