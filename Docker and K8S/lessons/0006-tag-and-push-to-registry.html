Lesson 06 · 主线 A：构建（收尾）

给镜像一个全名，推到 registry

把 hello-api:1.2 推到一个 registry，删掉本地副本，再让 compose 从 registry 拉回来跑。这是 K8s 的前置条件：集群只认 registry 里的镜像。

到现在为止 hello-api:1.2 只存在于你这台机器的 Docker 里。docker build 出来的镜像别人拿不到，K8s 集群也拿不到。 让镜像"离开本机"只有一条路：推到 registry。而推之前，镜像得有一个包含 registry 地址的全名——这一课的主角就是这个名字。

一、原理：一个镜像名分四段

localhost:5050 / hello-api : 1.2
└─ registry ─┘  └─ repo ─┘  └tag┘

docker.io / library / postgres : 17-alpine
└registry┘  └namespace┘ └ repo ┘  └─ tag ──┘
段省略时默认说明
registrydocker.io（Docker Hub）含 . 或 : 的第一段才被当作 registry 地址。所以 localhost:5050/x 指向本地 registry，myteam/x 仍然指向 Docker Hub
namespacelibrary（Hub 官方镜像）Hub 上就是用户名/组织名。postgres 其实是 docker.io/library/postgres
repo—镜像名本身
taglatest一个可移动的指针，不是版本号。latest 只是默认名字，不代表"最新"，也不会自动存在

权威定义：docker image tag（"An image name is made up of slash-separated name components, optionally prefixed by a registry hostname"）。

docker tag 不复制任何东西。它只是给同一个镜像 ID 再贴一个名字——本课第 3 步你会看到两个名字的 ID 一模一样。 真正的内容标识是 digest（sha256:…），由内容算出，不可变；tag 只是指向某个 digest 的便签，随时可以被 push 覆盖成指向另一个 digest。 见 Pull an image by digest。

内部机制：push 到底传了什么

registry 是一个 HTTP 服务，只有两种东西：blob（按 digest 存的层和配置）和 manifest（一份 JSON，列出这个 tag 由哪些 blob 组成）。 docker push 对每个层先 HEAD /v2/<repo>/blobs/<digest> 问"有没有"，有就跳过（输出 Layer already exists），没有才上传；最后 PUT manifest 把 tag 指过去。 所以第二次 push 只改了一层的镜像几秒就完——和 build 缓存是同一个思路：内容寻址，按 digest 去重。 协议见 Registry HTTP API V2；本课会用 curl 直接戳它两下。

二、动手

在 demo\hello-api 目录下操作。约 12 分钟。用官方 registry:2 镜像在本机跑一个 registry——不需要任何账号，原理和 Docker Hub 完全一样。

  1. 先看默认值是怎么被补全的。

    docker pull postgres:17-alpine
# Status: Image is up to date for postgres:17-alpine
# docker.io/library/postgres:17-alpine      ← 全名在最后一行

docker image inspect postgres:17-alpine --format "{{.RepoDigests}}"
# [postgres@sha256:…]                        ← 这就是 digest，内容的指纹

    你写的 postgres:17-alpine 被补成了 docker.io/library/postgres:17-alpine。K8s 的 YAML 里写 image: postgres:17-alpine 也会走同样的补全规则。

  2. 起一个本地 registry。

    docker run -d --name registry --restart unless-stopped -p 5050:5000 -v regdata:/var/lib/registry registry:2

curl http://localhost:5050/v2/_catalog
# {"repositories":[]}                        ← 空的，活着

    三个参数都是第 4 课的：-p 暴露端口、-v 把镜像数据放进 named volume（否则 rm 容器就没了）、--restart 让它随 Docker Desktop 自启，后面几课一直要用。 registry 容器里监听 5000，但宿主机侧用 5050：Windows 把 4904–5003 保留给了 Hyper-V（netsh interface ipv4 show excludedportrange protocol=tcp 可查），映射到 5000 会报 bind: An attempt was made to access a socket in a way forbidden。 镜像文档：Docker Hub — registry。

  3. 贴全名，推上去。

    docker tag hello-api:1.2 localhost:5050/hello-api:1.2

docker images --format "{{.Repository}}:{{.Tag}}  {{.ID}}" | findstr hello-api
# localhost:5050/hello-api:1.2  37da9bb747ca     ← 同一个 ID
# hello-api:1.2                 37da9bb747ca     ← tag 只是加了个名字

docker push localhost:5050/hello-api:1.2
# 40bf7c125e4b: Pushed
# …
# 1.2: digest: sha256:37da9bb7… size: 856

curl http://localhost:5050/v2/_catalog
# {"repositories":["hello-api"]}
curl http://localhost:5050/v2/hello-api/tags/list
# {"name":"hello-api","tags":["1.2"]}

    名字里的 localhost:5050 就是"推到哪"——docker push 没有 --registry 参数，目的地全靠名字。 这个 registry 走 HTTP 不走 HTTPS，Docker 默认只对 localhost 放行明文；换成 IP 或域名就要在 Docker Desktop 设置里加 insecure-registries。

  4. 踩坑：latest 不会自动存在。

    docker pull localhost:5050/hello-api
# Error response from daemon: … localhost:5050/hello-api:latest: not found

docker tag localhost:5050/hello-api:1.2 localhost:5050/hello-api:latest
docker push localhost:5050/hello-api:latest
# 40bf7c125e4b: Layer already exists         ← 8 层全部 already exists
# …
# latest: digest: sha256:37da9bb7… size: 856  ← 和 1.2 同一个 digest

curl http://localhost:5050/v2/hello-api/tags/list
# {"name":"hello-api","tags":["1.2","latest"]}

    不写 tag 就是 :latest，而 latest 只是一个你得亲手推上去的普通名字。第二次 push 一个字节都没传——registry 按 digest 认出所有层都已经有了，只新建了一份 manifest。

  5. 删掉本地副本，让 compose 从 registry 拉。这一步模拟"另一台机器 / K8s 节点"的视角。

    docker rmi hello-api:1.2 localhost:5050/hello-api:1.2 localhost:5050/hello-api:latest
docker images | findstr hello-api
# 只剩 1.0 和 1.1

    把 compose.yaml 里 api 的 image: 改成 registry 全名：

      api:
    image: localhost:5050/hello-api:1.2
    docker compose pull api
# Image localhost:5050/hello-api:1.2 Pulled
docker compose up -d
curl http://localhost:8080
# → Hello from .env!
docker compose ps --format "{{.Service}} {{.Image}} {{.Status}}"
# api localhost:5050/hello-api:1.2 Up …
# db  postgres:17-alpine Up … (healthy)

    镜像完成了一次"离开本机再回来"的旅程。从现在起 image: 写的是一个任何机器都能解析的地址，而不是只有你本机认识的名字——K8s 的 Deployment 里 image: 也将是这一行。

  6. （可选）推到 Docker Hub。如果你有 Docker Hub 账号，流程完全一样，只是名字里的 registry 段换成你的用户名（省略 = docker.io）：

    docker login
docker tag localhost:5050/hello-api:1.2 <你的用户名>/hello-api:1.2
docker push <你的用户名>/hello-api:1.2

    注意 Hub 上的仓库默认公开，含密码/密钥的镜像别推；匿名拉取有速率限制。没账号可以跳过，后面的课都用本地 registry。 官方流程：Build, tag, and publish an image。

三、检索练习

1. docker tag hello-api:1.2 localhost:5050/hello-api:1.2 之后，磁盘上多了什么？

两个名字指向同一个 image ID（第 3 步 docker images 可见）。tag 是指针，不是拷贝。

2. YAML 里写 image: postgres:17-alpine，引擎实际去哪拉？

省略 registry → docker.io；省略 namespace → library。全名 docker.io/library/postgres:17-alpine。第一段含 . 或 : 才算 registry 地址。

3. 推了 x:1.2，然后 docker pull localhost:5050/x 报 not found。为什么？

latest 是默认 tag 名，不是"最新版本"的别名。你没推它，registry 里就没有。

4. 第二次 push 同一镜像的新 tag，输出全是 Layer already exists。registry 靠什么判断？

内容寻址：push 前对每层 HEAD /v2/<repo>/blobs/<digest>。和 build 缓存看内容哈希是同一个思想。

5. 镜像已经叫 localhost:5050/hello-api:1.2，写出把它推到本地 registry 的命令。

6.（回顾第 5 课）.env 里写了 FOO=bar，compose.yaml 里没有任何 ${FOO}。容器里有 FOO 吗？

.env 自动被读，但只用来替换 YAML 里的 ${…}。要整文件进容器用 env_file:。

7. 不看课文，写出 docker.io/library/postgres:17-alpine 的四段各是什么，以及省略哪几段时会补什么默认值。

docker.io = registry（默认）；library = namespace（Hub 官方镜像默认）；postgres = repo；17-alpine = tag（省略默认 latest）。 只有第一段含 . 或 : 才被当成 registry 地址，否则整个都算 Hub 上的路径。速查见镜像命名与 registry。
