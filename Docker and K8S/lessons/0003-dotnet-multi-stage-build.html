Lesson 03 · 主线 A：构建

.NET 多阶段构建

编译需要 SDK，运行只需要 runtime。把两个时刻拆到两个镜像里，体积从 1.24 GB 降到 329 MB。

上一课你亲手证明了：RUN 在构建期执行完就被冻结，运行期只需要它留下的产物。 那问题来了 —— 编译 .NET 用的整套 SDK（1.24 GB），运行期一个字节都用不上，为什么要留在镜像里？ 多阶段构建就是把它扔掉的办法，而且它顺手解决了另一件事：改一行代码，不用重新 restore 依赖。

一、原理：两个 FROM，一次 COPY --from

阶段 build

FROM sdk:9.0 · 构建期用完即弃

  • COPY *.csproj + dotnet restore
  • COPY . .
  • dotnet publish -o /app
  • 产物落在 /app
→
COPY --from=build

最终镜像

FROM aspnet:9.0 · 只有它会被 push / run

  • COPY --from=build /app .
  • ENTRYPOINT dotnet HelloApi.dll
  • 没有 SDK、没有源码、没有 obj/

一个 Dockerfile 里可以有多个 FROM，每个开启一个阶段（stage）。 FROM ... AS build 给阶段起名；COPY --from=build 源 目标 从那个阶段的文件系统里拿文件。 最终产出的镜像只包含最后一个阶段的层 —— 前面阶段的一切都不会进去。

.NET 镜像家族：sdk（编译+运行，1.24 GB）⊃ aspnet（跑 Web，329 MB）⊃ runtime（跑控制台，更小）。 构建期用最大的，运行期用刚好够的。详见 Introduction to Docker for .NET。

二、动手：先做胖的，再做瘦的

先看到问题，再解决问题。整个实验约 3 分钟（两个基础镜像你已预拉）。

  1. 在课程目录的 demo 下生成一个最小 Web API。

    mkdir demo\hello-api
cd demo\hello-api

dotnet new web -n HelloApi -o . --no-restore
# 本机 SDK 是 .NET 10，把目标框架改成 9.0，对齐已拉的镜像
(Get-Content HelloApi.csproj) -replace 'net10.0','net9.0' | Set-Content -Encoding utf8 HelloApi.csproj

# .NET 项目必备的忽略文件（回想上一课：COPY . 会把整个目录送过去）
"bin/`nobj/" | Set-Content -Encoding utf8 .dockerignore

    Program.cs 只有一句 app.MapGet("/", () => "Hello World!")。本机 dotnet 只负责生成模板，编译全在容器里做。

  2. 胖版本：单阶段，直接用 SDK 镜像跑。

    @'
FROM mcr.microsoft.com/dotnet/sdk:9.0
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app
CMD ["dotnet", "/app/HelloApi.dll"]
'@ | Set-Content -Encoding utf8 Dockerfile.fat

docker build -f Dockerfile.fat -t hello-api:fat .
docker images hello-api

    约 1.24 GB。能跑，但里面装着整套编译器、NuGet 缓存和你的源码。

  3. 瘦版本：多阶段。注意 ARG 在这里的用法 —— 它只在 build 阶段有意义。

    @'
# ---- 阶段 1：构建 ----
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
ARG BUILD_CONFIGURATION=Release
WORKDIR /src
COPY HelloApi.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c $BUILD_CONFIGURATION -o /app --no-restore

# ---- 阶段 2：运行 ----
FROM mcr.microsoft.com/dotnet/aspnet:9.0
WORKDIR /app
COPY --from=build /app .
EXPOSE 8080
ENTRYPOINT ["dotnet", "HelloApi.dll"]
'@ | Set-Content -Encoding utf8 Dockerfile

docker build -t hello-api:1.0 .
docker images hello-api

    329 MB，和 aspnet:9.0 基础镜像几乎一样大 —— 你的应用本身只有 1 MB 左右。 1.24 GB 的 SDK 阶段干完活就被丢掉了。

  4. 跑起来。.NET 8+ 容器内默认监听 8080，不是 80。

    docker run -d --rm --name hello -p 8080:8080 hello-api:1.0
curl http://localhost:8080
# → Hello World!

  5. 证明缓存分层有用。改一行代码，重新 build，盯住每一步是 CACHED 还是真的跑。

    (Get-Content Program.cs) -replace 'Hello World!','Hello from a container!' | Set-Content -Encoding utf8 Program.cs

docker build -t hello-api:1.1 .

    你会看到：

    [build 3/6] COPY HelloApi.csproj .     CACHED
[build 4/6] RUN dotnet restore          CACHED   ← 依赖没变，跳过
[build 5/6] COPY . .                    DONE     ← 从这里开始失效
[build 6/6] RUN dotnet publish ...      DONE 3.9s

    这就是为什么要先 COPY csproj 单独 restore，再 COPY 全部源码： 层缓存的规则是「某一层的输入变了，它和它之后的所有层全部重建」。 csproj 很少变，源码天天变 —— 把少变的放前面，多变的放后面，restore 那几十秒就省下来了。 

    docker rm -f hello
docker run -d --rm --name hello -p 8080:8080 hello-api:1.1
curl http://localhost:8080
# → Hello from a container!
docker rm -f hello

  6. 上一课的 ARG，这次真的用上。用 --build-arg 切成 Debug 编译：

    docker build --build-arg BUILD_CONFIGURATION=Debug -t hello-api:debug .

# 验证：容器里有没有 BUILD_CONFIGURATION 这个变量？
docker run --rm --entrypoint sh hello-api:debug -c 'echo "[$BUILD_CONFIGURATION]"'

    输出 []。ARG 影响了 publish 的参数（构建期），但容器里查无此人（运行期）—— 和上一课 frozen.txt 的实验是同一件事。--entrypoint sh 用来临时替换掉 ENTRYPOINT， 是钻进任何镜像里看一眼的常用手法。

三、检索练习

第 3、4 题是上一课 ARG 错题的重考。先凭记忆答。

1. 多阶段 Dockerfile 有 FROM sdk AS build 和 FROM aspnet 两个阶段。最终 docker build -t x . 产出的镜像包含什么？

最终镜像 = 最后一个阶段。前面的阶段只是"临时车间"，除了被 COPY --from 显式拿走的文件，其余全部丢弃。

2. 下面两种写法，改一行 .cs 后重新 build，哪种能跳过 dotnet restore？
甲：COPY . . → RUN dotnet restore → RUN dotnet publish
乙：COPY *.csproj . → RUN dotnet restore → COPY . . → RUN dotnet publish

甲的 COPY . . 输入变了（.cs 改了），它之后的 restore 也一并失效。乙的 restore 只依赖 csproj 那一层，csproj 没变就命中缓存。

3. build 阶段写了 ARG BUILD_CONFIGURATION=Release。跑起最终容器后执行 echo $BUILD_CONFIGURATION，输出？

ARG 只活在构建期，而且只活在声明它的那个阶段（跨阶段还要重新声明）。要让容器里有，用 ENV。

4. 写出完整命令：在当前目录构建 api:2.0，构建参数 BUILD_CONFIGURATION 设为 Debug。

5. 你的 .NET 9 应用容器跑起来了，docker run -p 80:80 myapi，但浏览器访问 localhost 拒绝连接。最可能的原因？

.NET 8 起容器内默认监听 8080。-p 80:80 把宿主机 80 映射到容器 80，但容器 80 上没人。应写 -p 80:8080，或用 -e ASPNETCORE_HTTP_PORTS=80 改监听端口（下一课的主题）。

6. 不看上面，默写多阶段 .NET Dockerfile 的骨架：两个 FROM 各用什么镜像、中间哪一行把产物搬过去、csproj 为什么要单独 COPY。

FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:9.0
WORKDIR /app
COPY --from=build /app .
EXPOSE 8080
ENTRYPOINT ["dotnet", "HelloApi.dll"]

csproj 单独 COPY：让 restore 层只依赖依赖清单，源码改动不会让它失效。完整注释版见.NET 多阶段 Dockerfile 模板。
