Lesson 02 · 主线 A：构建

构建期与运行期

Docker 里几乎所有"我明明配了却没生效"的困惑，根源都是搞混了这两个时刻。

上一课你答错的两题 —— build 末尾的 .、以及 EXPOSE 不加 -p —— 共享同一个根因： 没有时间轴模型。这节课把这条断层补上。它是后面多阶段构建、层缓存、改第三方镜像配置的共同前提。

一、两个时刻，一条铁律

docker build

构建期 · 只发生一次

  • FROM 拉基础镜像
  • RUN 真的执行命令
  • COPY 从 build context 复制文件
  • ARG 构建变量生效
  • 每步结果固化成 layer
→

docker run

运行期 · 每次启动都发生

  • 基于 image 加一层可写层
  • 执行 ENTRYPOINT + CMD
  • -e 注入环境变量
  • -p 建立端口映射
  • -v 挂载卷

铁律：构建期结束的那一刻，image 就被冻结了。 运行期不会回头重新执行 RUN / COPY，Dockerfile 此时已经跟这个 image 没有关系了。

这条铁律解释了你上一课的两个错误：.（build context）是构建期的输入，run 时早就不存在了； EXPOSE 则两个时刻都不做事，它只是写进 image 的一行元数据， 相当于镜像作者留的一张便条：「我打算监听这个端口」。便条不会替你打通网络。

二、动手证明它

与其记结论，不如亲手做出可观察的证据。整个实验基于 alpine（约 8 MB），几秒钟跑完。

  1. 建目录，写一个刻意暴露时间差的 Dockerfile。

    mkdir $HOME\timing-lab
cd $HOME\timing-lab

@'
FROM alpine:3
ARG BUILD_NOTE=unset
ENV RUN_NOTE=unset
RUN echo "frozen-in-image: BUILD_NOTE=$BUILD_NOTE" > /frozen.txt
EXPOSE 9999
CMD echo "at-run-time: RUN_NOTE=$RUN_NOTE" && cat /frozen.txt
'@ | Set-Content -Encoding utf8 Dockerfile

    这里刻意全用英文：容器内是 Alpine 的极简环境，中文输出容易受终端编码影响， 会让实验结论被无关噪音干扰。做实验时，减少变量。

  2. 构建，并注意看 RUN 那一步的输出。

    docker build -t timing:1.0 --build-arg BUILD_NOTE=first-build .

    RUN 在这一刻真的跑了 echo，把结果写进 /frozen.txt，然后这一层被封存。

  3. 运行它。

    docker run --rm timing:1.0

    你会看到两行：RUN_NOTE=unset，和 BUILD_NOTE=first-build。 --rm 表示容器退出后自动删除，做实验时很省事。

  4. 试着在运行期改这两个变量。一个能改，一个改不动 —— 这就是全部要点。

    # ENV 是运行期变量：能改 ✅
docker run --rm -e RUN_NOTE=changed-at-run timing:1.0

# BUILD_NOTE 是 ARG：容器里根本不存在，改不动 ❌
docker run --rm -e BUILD_NOTE=i-want-to-change timing:1.0

    第二条命令里 /frozen.txt 依然是 first-build。你刚刚亲手证明了： 构建期写进去的东西，运行期无论如何都改不了，只能重新 build。

  5. 验证 EXPOSE 的真面目。

    docker run -d --name t timing:1.0 sleep 120

# 实际的端口映射：空的
docker port t

# 元数据里却确实有 9999
docker inspect --format "{{.Config.ExposedPorts}}" t

docker rm -f t

    顺带一提：docker run 镜像 sleep 120 里的 sleep 120 覆盖了 CMD。 CMD 只是"默认命令"，命令行给了就以命令行为准。

三、那个 . 到底送出去了什么

build context 不是抽象概念，它有实实在在的体积。做个实验：

# 造一个 50 MB 的大文件，放进目录
$f = [IO.File]::Create("$PWD\big.bin"); $f.SetLength(50MB); $f.Close()

# 重新构建，盯住输出里的 transferring context
docker build -t timing:1.1 .

输出里会出现类似 => transferring context: 52.43MB 的一行。 Dockerfile 里根本没有 COPY big.bin，它却还是被送走了 —— 因为送的是整个目录，不是被引用的文件。

# 排除掉它
"big.bin" | Set-Content -Encoding utf8 .dockerignore

docker build -t timing:1.2 .

transferring context 应该掉到几百字节。这就是 .dockerignore 的全部作用， 也是为什么 .NET 项目一定要忽略 bin/、obj/、.git/ —— 它们又大又对构建无用。

同理，COPY ../shared/config.json . 永远失败， 报 forbidden path outside the build context。因为 .. 不在你交出去的那个目录里。 解决办法是把 context 提到上层：docker build -f app/Dockerfile . （-f 指定 Dockerfile 位置，末尾的 . 才是 context）。

四、检索练习

前两题是上一课错题的重考，换了问法。先凭记忆答，别翻上面。

1. 镜像的 Dockerfile 里有 EXPOSE 8080。你跑 docker run -d 镜像 后执行 docker port 容器，看到什么？

EXPOSE 只写元数据，两个时刻都不建立映射。元数据能用 docker inspect 看到，但 docker port 显示的是真实映射，所以是空的。

2. 你的目录里有个 2 GB 的 data.zip，Dockerfile 里完全没提它。docker build . 会怎样？

context 是整个目录，与是否被 COPY 无关。它不会进最终镜像，但每次 build 都要传输一遍。这正是 .dockerignore 存在的理由。

3. Dockerfile 里写了 ARG TOKEN。容器跑起来后进去执行 echo $TOKEN，结果是？

ARG 只活在构建期，不会进入容器环境。想让容器里有这个变量，得用 ENV，或者 docker run -e 注入。（另：ARG 传密码不安全，它留在构建历史里。）

4. 下面哪一件事必须重新 docker build 才能生效？

装依赖是 RUN，属于构建期，被冻结在层里。其余三项都是运行期参数（-p / -e / -v），改命令行即可 —— 这也正是你能不重新构建就修改第三方镜像配置的原因。

5. 写出完整命令：在当前目录构建 app:1.0，并把构建参数 VERSION 设为 2。

6. 不看表格，说出至少 3 条只在构建期起作用的指令，和 2 条只在运行期起作用的。

只在构建期：FROM、RUN、COPY / ADD、ARG

只在运行期：CMD、ENTRYPOINT（它们在构建期只被写成元数据，不执行）

两边都作用：ENV、WORKDIR、USER　哪边都不做事：EXPOSE、LABEL

完整对照见指令时机速查表。
