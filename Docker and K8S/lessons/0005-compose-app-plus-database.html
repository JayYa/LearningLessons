Lesson 05 · 主线 B：运行与配置

一个文件，拉起应用 + 数据库

把上一课那两条六七个参数的 docker run 翻译成 compose.yaml，一条 docker compose up 同时启动 hello-api 和 postgres，让它们互相能找到对方。

上一课你已经能把任何镜像配置好跑起来。问题是每次都要敲一长串参数，两个服务就是两长串，还要自己保证启动顺序。 docker compose 做的事很朴素：把 docker run 的参数写进一个 YAML 文件，加上"这几个容器是一组"的概念。 你上一课学的 -e / -v / -p 一个不少，只是换了写法。

一、原理：参数 → 字段，一一对应

--name pgservices: 下的键名 db:服务名。容器实际叫 项目名-db-1；服务名同时是DNS 名，见下

-p 5432:5432ports: ["5432:5432"]同样是"宿主机:容器"，加引号——YAML 会把 22:22 这种当成六十进制数

权威对照：Compose file reference — services。 每个字段都能在那页查到；本课只用最常见的六个。

docker compose up

按项目名创建一组资源

  • network hello-api_default
  • volume hello-api_pgdata
  • container hello-api-db-1
  • container hello-api-api-1
→
down

docker compose down

删容器和网络，留卷

  • container ✗
  • network ✗
  • named volume 保留
  • down -v 才连卷一起删

项目名（project name）默认是 compose.yaml 所在目录的名字。compose 创建的一切都以它做前缀， 所以你在 docker volume ls 里会看到 hello-api_pgdata，而不是你写的 pgdata。 这是 compose 隔离不同项目的手段——也是本课第 3 步要亲手踩一下的坑。 见 Specify a project name。

服务名就是主机名。compose 会给这组容器建一个私有网络，并注册内部 DNS： api 容器里访问 db:5432 就到了 postgres。注意用的是容器端口（5432），不是宿主机端口； ports: 只对"从 Windows 侧访问"有意义，容器之间不经过它。 见 Networking in Compose。

二、动手

在 demo\hello-api 目录下操作。约 10 分钟。上一课留下的 hello-api:1.2 镜像和 pgdata 卷（里面有 2 行 orders）这一课都会用到。

  1. 用编辑器在 demo\hello-api 下新建 compose.yaml，内容如下。先照抄，每一行的"为什么"在上面的表里。

    services:

  api:
    image: hello-api:1.2
    ports:
      - "8080:8080"
    environment:
      Greeting: ${GREETING:-Hello from compose!}
      ConnectionStrings__Default: Host=db;Port=5432;Database=shop;Username=postgres;Password=secret
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine
    ports:
      - "5432:5432"
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    volumes:
      - type: volume
        source: pgdata
        target: /var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d shop"]
      interval: 2s
      timeout: 3s
      retries: 10

volumes:
  pgdata:

    三处新东西：${GREETING:-默认值} 是插值——值从你 shell 或 .env 文件里取，没有就用冒号后面的默认值（第 5 步用）。 ConnectionStrings__Default 里 Host=db：连接串写的是服务名，不是 localhost——hello-api 现在还没用它，但这就是以后真实项目的写法。 healthcheck.test 用 postgres 自带的 pg_isready 探活； depends_on … condition: service_healthy 让 api 等到它绿了才起。 见 depends_on 与 healthcheck。

  2. 一条命令拉起两个服务。

    cd demo\hello-api
docker compose up -d
# Network hello-api_default  Created
# Volume  hello-api_pgdata   Created
# Container hello-api-db-1   Healthy      ← 等到它健康
# Container hello-api-api-1  Started      ← 才起这个

docker compose ps
curl http://localhost:8080
# → Hello from compose!

    docker compose ps 里 db 一行 STATUS 是 Up … (healthy)——这就是 healthcheck 的结果。 compose up -d 之后所有的 docker compose 子命令（ps / logs / exec / down）都在这个目录下执行，它靠目录找到 compose.yaml。

  3. 踩坑：上一课的 2 行 orders 呢？

    docker compose exec db psql -U postgres -d shop -c "SELECT count(*) FROM orders;"
# ERROR:  relation "orders" does not exist

docker volume ls
# hello-api_pgdata   ← compose 新建的，空的
# pgdata             ← 上一课的，数据在这

    你写的 pgdata 被加了项目前缀，变成了另一个卷。要接上原来那个，在顶层 volumes: 里指定确切的名字： 

    # 把文件末尾改成：
volumes:
  pgdata:
    name: pgdata

docker compose up -d
# Container hello-api-db-1  Recreated   ← 只重建了变化的服务
docker compose exec db psql -U postgres -d shop -c "SELECT count(*) FROM orders;"
# → 2

docker volume rm hello-api_pgdata          # 那个空的没用了

    2 行回来了。你现在知道两件事：compose 给资源加前缀；改了 YAML 再 up，compose 只重建受影响的容器，不动其他的。

  4. 服务名 = DNS 名。在 api 容器里查 db 这个名字：

    docker compose exec api getent hosts db
# 172.18.0.2      db

    aspnet 镜像里没有 ping/curl，getent hosts 是 glibc 自带的查名工具。这个 IP 每次 up 都可能变——所以永远写服务名，别写 IP。 也顺便验证一下 docker compose exec api env | findstr Connection：连接串已经在容器里了，指向 db。

  5. 不改 YAML，用 .env 换配置。

    'GREETING=Hello from .env!' | Set-Content .env

docker compose config | Select-String Greeting
#       Greeting: Hello from .env!     ← 插值后的最终结果

docker compose up -d
# Container hello-api-api-1  Recreated
curl http://localhost:8080
# → Hello from .env!

    docker compose config 打印插值和合并之后的完整文件——"配置没生效"时先看它，别猜。 .env 只参与插值（替换 YAML 里的 ${…}），它本身不会直接变成容器的环境变量；要整文件喂给容器是另一个字段 env_file:。 优先级见 Environment variables precedence。

  6. 拆掉，看什么留下来。

    docker compose down
# Container hello-api-api-1  Removed
# Container hello-api-db-1   Removed
# Network hello-api_default  Removed

docker volume ls
# pgdata   ← 还在

    down 删容器和网络，不删 named volume。docker compose down -v 才会连卷一起删——那是"我要彻底重来"时用的，敲之前想一秒。 见 docker compose down。

三、检索练习

1. api 容器里的连接串该写 Host= 什么，才能连到同一 compose 文件里的 postgres？

Host=db;Port=5432。compose 内部 DNS 按服务名解析；容器间走容器端口，ports: 映射只服务于宿主机侧。localhost 在容器里指它自己。IP 每次可能变。

2. YAML 里写了 source: pgdata，docker volume ls 却看到 hello-api_pgdata。为什么？

默认项目名 = 目录名，volume / network / container 都加此前缀。要用确切名字，顶层 volumes: 里写 name: pgdata（或 external: true 表示"已存在，别替我建"）。

3. docker compose down 之后，哪个还在？

默认删容器 + 网络，留 named volume（和 docker rm 一样，宁可留垃圾不丢数据）。down -v 才删卷。

4. 改了 .env 里的值，curl 结果却没变。第一步查什么？

docker compose config。它显示插值后的最终 YAML；值不对就是插值/优先级问题，值对了就是忘了 up -d 重建容器（改 .env 不会自动重建）。

5. 写出那条"删容器、删网络、连 named volume 一起删"的命令。

6.（回顾上一课）第 4 课不带 -v 直接跑 postgres，事后 docker volume ls 多了一个 64 位哈希名的卷。它从哪来？

postgres 的 Dockerfile 有 VOLUME /var/lib/postgresql/data：该路径必须是卷，你不指定就得到一个匿名卷。docker rm 默认不删它（rm -v 才删），docker volume prune 清理。

7. 不看文件，默写一个最小 compose 服务：镜像 postgres:17-alpine，密码 secret，数据持久化到 named volume pgdata（长格式），宿主机 5432 可访问。

services:
  db:
    image: postgres:17-alpine
    ports:
      - "5432:5432"
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - type: volume
        source: pgdata
        target: /var/lib/postgresql/data

volumes:
  pgdata:

检查点：ports 有引号；named volume 顶层声明了；长格式三个键 type / source / target。速查见Compose 速查。
