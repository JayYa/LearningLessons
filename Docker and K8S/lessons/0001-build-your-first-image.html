Lesson 01 · Docker & Kubernetes

构建你的第一个镜像

用 5 条命令，把一个文件变成一个能在任何装了 Docker 的机器上运行的 image。

这节课只做一件事：让你亲手完成 Dockerfile → image → container 这条链路。 它是后面所有内容的地基 —— 推镜像到仓库、跑别人的镜像、部署到 K8s，全都建立在这三个词的关系上。

一、三个词，一个心智模型

初学 Docker 最大的混乱来自把 image 和 container 混为一谈。它们的关系是：

概念是什么类比
Dockerfile一份文本配方，写明怎么造菜谱
image造好的只读模板，可分发做好的预制菜（可复制无数份）
containerimage 的一次运行，带可写层端上桌正在吃的那一盘

关键推论：改 Dockerfile 不会改变已有的 image，必须重新 build； 删掉 container 不会删掉 image。一个 image 可以同时跑出 100 个 container，互不干扰。

image 由一层层 layer 叠成，Dockerfile 里大部分指令各产生一层。层可以被缓存、被多个 image 共享 —— 这就是为什么第二次 build 通常快得多。层的顺序会直接决定构建速度，这是下一课的主题。 （概念详解见 Docker 官方 Building images）

二、动手：把一个网页装进镜像

这个例子刻意不依赖任何语言工具链 —— 你机器上只要有 Docker Desktop 就能跑通。 打开 PowerShell，逐步执行：

  1. 建一个目录，作为 build context。

    mkdir $HOME\hello-docker
cd $HOME\hello-docker

  2. 写一个要放进镜像的文件。

    @'
<!DOCTYPE html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>Hello</title></head>
<body>
<h1>Hello from inside a container</h1>
<p>这个页面来自我自己构建的 image。</p>
</body>
</html>
'@ | Set-Content -Encoding utf8 index.html

    为什么一定要写 <meta charset="utf-8">？ 文件本身是 UTF-8，但 nginx 默认以 Content-Type: text/html 返回，不带 charset 声明。 浏览器只好靠猜，在中文 Windows 上常常猜成 GBK —— 中文就变成乱码。 这是一个典型的「容器里的服务怎么配置」问题：真正的修法有两条， 改内容（加 meta 标签，就是这里做的），或改服务配置（在 nginx.conf 里设 charset utf-8;）。 后者要往镜像里挂配置文件，正是主线 B 后面要教的。

  3. 写 Dockerfile。注意文件名就叫 Dockerfile，没有扩展名。

    @'
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
'@ | Set-Content -Encoding utf8 Dockerfile

    三行分别是：FROM 选一个已经装好 nginx 的基础镜像； COPY 把本地文件复制进镜像里 nginx 默认的网站目录； EXPOSE 仅仅是声明「这个镜像打算监听 80 端口」，它不会真的开放端口 —— 开放端口是 docker run -p 的事。

  4. 构建 image。

    docker build -t hello-docker:1.0 .

    -t 给 image 打 tag（名字:版本）。末尾那个 . 不是句号， 它是 build context：当前目录会被整体发给构建引擎，COPY 只能取到这里面的文件。

    确认它存在：

    docker images hello-docker

  5. 运行成 container。

    docker run -d -p 8080:80 --name web hello-docker:1.0

    -d 后台运行；-p 8080:80 把 Windows 的 8080 映射到容器的 80；--name 起个好记的名字。

    浏览器打开 http://localhost:8080。

✓ 你的第一个小胜利。页面出来了，说明你已经完成了完整链路：写配方 → 造镜像 → 跑容器 → 从宿主机访问到它。 这个 hello-docker:1.0 现在是一个可以推到 Docker Hub、被任何人一条命令跑起来的制品。

顺手做三件事（收尾也是技能）

# 看正在跑的容器
docker ps

# 看容器日志（排查问题的第一步，永远是它）
docker logs web

# 停掉并删除容器 —— 注意 image 还在
docker rm -f web
docker images hello-docker

验证一下上面那句话。删完容器后再跑一次 docker images hello-docker， image 仍然列在那里。这就是 image 与 container 生命周期分离的直接证据。

三、检索练习

别翻回上面找答案 —— 先从记忆里取。取不出来才是学习真正发生的地方。

1. 你改了 index.html，然后直接 docker run 之前那个 image。页面会变吗？

image 是构建那一刻的只读快照。COPY 发生在 build 期间，不是 run 期间。改了源文件就要 docker build 一次。

2. docker build -t app:1.0 . 末尾的 . 是什么？

它是 build context 路径。COPY / ADD 只能引用 context 内的文件 —— 这也是 COPY ../foo 一定失败的原因。

3. Dockerfile 里写了 EXPOSE 80，但 docker run 时没加 -p。结果是？

EXPOSE 只是写给人和工具看的文档性声明。真正打通网络的是 -p 主机端口:容器端口。

4. 写出完整命令：在当前目录构建一个 tag 为 myapp:2.0 的镜像。

5. 用自己的话说：image 和 container 的关系是什么？先在心里说完整一句，再展开对照。

image 是只读模板，container 是它的运行实例（image 加了一层可写层跑起来）。 一个 image 可以起任意多个 container；删 container 不影响 image；改 Dockerfile 必须重新 build 才影响 image。 对应关系类似 class 与 instance、安装包与进程。
