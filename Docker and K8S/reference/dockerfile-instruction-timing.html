Dockerfile 指令：
构建期还是运行期？

写 Dockerfile 时最该反复回看的一张表。判断一条指令有没有效果，先问它在哪个时刻起作用。

两个时刻

时刻触发命令发生了什么
构建期 builddocker buildDockerfile 被逐行执行，每步的结果固化成 layer，最终产出一个只读 image。结束后 Dockerfile 就与这个 image 无关了。
运行期 rundocker run基于 image 创建 container，加一层可写层，执行 ENTRYPOINT + CMD。Dockerfile 的其他指令不会在此时重新执行。

指令对照表

指令构建期运行期要点
FROM✅ 拉取基础镜像—决定起点层
RUN✅ 真的执行命令—结果被固化进层；改了也要重 build 才生效
COPY / ADD✅ 从 build context 复制—只能读 context 内的文件，COPY ../x 必失败
WORKDIR✅ 影响后续指令✅ 容器启动目录两个时刻都作数
ARG✅ 构建变量❌ 容器里不存在--build-arg 传入；不要用来传密码，会留在构建历史里
ENV✅ 后续指令可见✅ 进程环境变量run 时可用 -e 覆盖 —— 配置第三方镜像的主力手段
USER✅ 影响后续 RUN✅ 容器默认用户
EXPOSE⚪ 只写元数据⚪ 只写元数据不开放任何端口。真正打通靠 docker run -p
LABEL⚪ 只写元数据⚪ 只写元数据docker inspect 可读
VOLUME⚪ 只写元数据✅ 启动时自动建匿名卷声明"这个路径的数据不该留在容器层"
ENTRYPOINT⚪ 只写元数据✅ 容器主进程"这个镜像是什么程序"
CMD⚪ 只写元数据✅ 默认参数 / 默认命令"默认怎么跑"；docker run 镜像 <命令> 会覆盖它

✅ 真的做事　⚪ 只是写进 image 的元数据　❌ 不存在

三条推论

  1. 改 Dockerfile / 源码 ⇒ 必须重新 build。重启容器没用。
  2. 改运行方式（端口、环境变量、挂载）⇒ 不用重新 build，改 docker run 参数即可。这就是为什么第三方镜像可以不重新构建就改配置。
  3. 层缓存只在构建期存在。Docker 从上到下比对，遇到第一个变化的指令，那一行及其之后所有行的缓存全部失效 —— 所以「变化频率低的指令写在前面」。

build context 速记

docker build -t 名字:标签 -f Dockerfile路径 上下文路径
  • 末尾那个路径（通常是 .）= build context，整个目录会被打包送给构建引擎。
  • context 太大 ⇒ 每次 build 都慢。用 .dockerignore 排除 bin/ obj/ .git/ node_modules/ 等。
  • 看 build 输出里的 transferring context: … B 就知道送了多少。
