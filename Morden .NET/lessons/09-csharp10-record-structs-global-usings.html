Lesson 09: C# 10

四个特性，每个只省一点点——但加在一起，你的项目模板瘦了一半

前置 / Prerequisite：已完成 Lesson 08（C# 9 小特性集），熟悉 C# 9 的 Top-level Statements顶级语句 和 Target-typed new。
C# 10 ↔ .NET 6：C# 10 随 .NET 6 LTS（2021.11）发布。C# 10 特性在 .NET 6+ 上全部可用。
本课目标：掌握 File-scoped Namespaces文件范围命名空间、Global Usings全局引用、Record Structs记录结构体、Constant Interpolated Strings常量内插字符串。四个特性覆盖了"新建项目后你最先看到的那些变化"。

一、钩子——.NET 6 模板打开的第一眼，你看到了什么？

用 dotnet new console 创建 .NET 6 项目，你看到的 Program.cs 长这样：

// .NET 6 console app —— 就一行
Console.WriteLine("Hello, World!");

回到 .NET Core 3.1 / .NET 5 时代，同一个文件长这样：

using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;

namespace MyConsoleApp
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello World!");
        }
    }
}

从 11 行到 1 行，发生了什么？

你已经在 Lesson 08 学过了 Top-level Statements——它消掉了 class Program 和 Main。但还有两件事没解释：

  1. 那些 using System; 去哪了？——Global Usings + 隐式导入Implicit Usings
  2. namespace 去哪了？——File-scoped Namespaces（虽然没有显式缩进，但编译器仍然生成了）

这两个特性，加上 Record Structs（C# 9 Records 的值类型版本）和 Constant Interpolated Strings（const 终于支持插值），就是 C# 10 的主题。

本课的视角：C# 10 不像 C# 8（Nullable）或 C# 9（Records）那样有一个"杀手级特性"。它是 C# 9 的打磨版本——消除摩擦、减少仪式、补全 C# 9 留下的"为什么 record 只能 class 不能 struct"这类缺口。面试中能说出这个定位，比背特性列表更有说服力。

二、文件范围命名空间 File-scoped Namespaces

2.1 痛点——整个文件白缩进一级

传统 namespace 需要一对大括号，导致文件里所有代码都缩进一级。一个典型的服务类：

namespace MyApp.Services
{
    public class OrderService  // ← 缩进 4 格
    {
        public async Task<Order> GetAsync(int id)  // ← 缩进 8 格
        {
            // ... 真正的逻辑，缩进 12 格
        }
    }
}

屏幕左边的 12 格空白——其中 4 格是 namespace 送的。一个文件只有一个 namespace 时，这 4 格纯粹是浪费。

C# 10 的答案：

namespace MyApp.Services;  // ← 分号结尾，没有大括号

public class OrderService  // ← 不缩进！顶格写
{
    public async Task<Order> GetAsync(int id)
    {
        // ... 真正的逻辑，缩进 8 格
    }
}

省掉了整个文件的一级缩进。你会惊讶于这个变化对可读性的影响——特别是那些本来嵌套就深的代码。

一个文件只能有一个 File-scoped Namespace。如果你之前在一个文件里嵌套了多个 namespace（如 namespace A { namespace B { } }），不能用 File-scoped 语法。不过那种写法本身就不常见。

2.2 编译器生成——完全一样的 IL

File-scoped Namespace 和传统 namespace 编译出的 IL 完全相同。这是纯粹的语法糖——编译器只是在解析时把分号变回大括号：

// 你写：
namespace MyApp.Services;

public class OrderService { }

// 编译器等价（简化）：
namespace MyApp.Services
{
    public class OrderService { }
}

面试常考："File-scoped Namespace 和传统 namespace 有什么区别？"——答：语义上完全没有区别，纯粹是语法糖。编译产物（IL、元数据）一模一样。它的存在理由只有一个：一个文件一个 namespace 是 99% 的场景，为什么要为这 99% 多缩进一级？

2.3 什么时候用？

✅ 用 File-scoped❌ 继续用传统 namespace
一个文件只有一个 namespace（99% 的情况）一个文件有嵌套 namespace
新项目——.NET 6+ 模板默认就是这个老项目迁移——没必要为这个全局重构
配合 Top-level Statements 使用代码风格工具强制要求（极少见）

2.4 隐式命名空间 Implicit Namespace——SDK 自动帮你加的 namespace

回到本课开头的钩子——.NET 6 控制台项目只有一行代码。你不但没看到 using，也没看到 namespace：

// Program.cs (.NET 6 console app) —— 就一行，没有 namespace
Console.WriteLine("Hello, World!");

这个文件确实没有显式的 namespace，但编译器仍然把它放进了某个命名空间——那就是项目的根命名空间Root Namespace。

它是怎么来的？

.NET SDK 在每个项目创建时自动设置根命名空间。对于 Top-level Statements 文件（没有显式声明 namespace），编译器自动将其包裹在根命名空间中：

// 你看到的 Program.cs：
Console.WriteLine("Hello");

// 编译器实际编译的等价代码：
namespace MyApp;  // ← SDK 自动注入的 File-scoped Namespace（隐式）

internal partial class Program
{
    private static void $Main(string[] args)
    {
        Console.WriteLine("Hello");
    }
}

根命名空间从哪来？

来源说明
.csproj 中 <RootNamespace>显式设置，优先级最高：
<RootNamespace>MyCompany.MyApp</RootNamespace>
项目文件名（默认）没设 RootNamespace 时，SDK 用 .csproj 文件名去掉扩展名
dotnet new console -n MyApp创建项目时模板自动设置 RootNamespace
只有 Top-level Statements 文件没有显式 namespace 时，隐式命名空间才生效。如果你在文件中写了 namespace Foo;（File-scoped）或传统 namespace Foo { }，那声明优先——隐式命名空间不会覆盖你写的。

隐式 Namespace 和 File-scoped Namespace 的关系

SDK 注入的隐式命名空间正是以 File-scoped Namespace 语法注入的（分号结尾，无大括号）。两者不是竞争关系——隐式是 SDK 自动帮你在 Top-level Statements 文件中"补上"了一行 File-scoped Namespace。

// 隐式 namespace（SDK 自动注入）」是 File-scoped Namespace 语法的"自动化应用"
//   SDK 等价于在每个无 namespace 声明的文件顶部插入了：
//   namespace <RootNamespace>;
//
// File-scoped Namespace 是你手动写的：
namespace MyApp.Services;  // ← 显式的 File-scoped Namespace——覆盖隐式
和隐式 Using 的对称设计：SDK 有两个"隐式"机制——隐式 Using（自动注入 global using，本课 3.4）和隐式 Namespace（自动注入 File-scoped Namespace，本节）。两者都是为了同一个目标：消灭项目中每个文件都重复的样板代码。Using 消除的是文件顶部的重复，Namespace 消除的是文件最外层的缩进。

你可以在 .csproj 中控制根命名空间：

<!-- 显式设置根命名空间 —— 隐式 namespace 会使用这个值 -->
<PropertyGroup>
    <RootNamespace>MyCompany.MyApp</RootNamespace>
</PropertyGroup>

三、全局引用 Global Usings

3.1 痛点——每个文件头顶都重复同样的 10 行 using

打开任何一个中等规模的 C# 项目，每个文件的顶部都一样：

using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;
using Microsoft.Extensions.Logging;
using Microsoft.Extensions.DependencyInjection;
// ... 还有 8 行

每个文件重复一遍——80% 的 using 在所有文件里都是一样的。这纯属体力活。

C# 10 的答案：把那些"全项目都需要的 using"声明为全局的：

// GlobalUsings.cs —— 一个文件，管整个项目
global using System;
global using System.Collections.Generic;
global using System.Linq;
global using System.Threading.Tasks;
global using Microsoft.Extensions.Logging;

有了这个文件后，项目里其他所有 .cs 文件不用再写这些 using——它们自动可见。

惯例：社区实践中通常创建一个 GlobalUsings.cs（或 Usings.cs）放在项目根目录，集中管理全局 using。这个文件不包含任何类或逻辑——就是纯 using 声明。

3.2 global using 的完整语法

// ① 基本形式：整个项目可用
global using System.Text.Json;

// ② global + static：全局静态导入
global using static System.Math;  // 所有文件都能直接用 Abs(), Round(), PI

// ③ global + alias：全局别名
global using DateOnly = System.DateOnly;  // 需要 System.DateOnly 的地方，直接用 DateOnly

// ④ 可以放在任何 .cs 文件中，不限于 GlobalUsings.cs
// 但集中管理是社区推荐做法

3.3 两种声明方式对比——.cs 文件 vs .csproj

你可以在 C# 代码里用 global using，也可以在 .csproj 里用 <Using> 元素。编译结果完全一样——那到底该用哪个？

GlobalUsings.cs 推荐.csproj <Using>
语法global using System.Text.Json;<Using Include="System.Text.Json" />
可见性Solution Explorer 里一眼看到文件藏在 .csproj 里，多数人不会点开看
新人上手打开文件立刻知道全局有什么没人告诉就不知道这里藏了 using
Code ReviewPR 里改这个文件很明显.csproj 改动容易被忽略
static 导入global using static System.Math;<Using Static="True" Include="System.Math" />
别名global using Foo = Bar;<Using Alias="Foo" Include="Bar" />
编译产物完全一样——都生成程序集级 using 指令
发现成本低——和所有 .cs 文件一样可见高——需要知道去 .csproj 找
社区共识：用 GlobalUsings.cs。代码是写给人看的——把全局 using 放在 .cs 文件里，让它们像所有其他代码一样：可见、可审查、可发现。.NET 官方项目模板（ASP.NET Core、MAUI）也都采用 GlobalUsings.cs 模式。

那 .csproj 的 <Using> 什么时候用？几乎只有一种场景：SDK 自动生成的隐式导入（Implicit Usings）本身就是通过这种机制注入的——但那是 SDK 干的活，不需要你操心。你自己加的项目特定 global using，放 GlobalUsings.cs。两者可以共存——SDK 管它的，你管你的。

核心洞见：.csproj 告诉 MSBuild 做什么，GlobalUsings.cs 告诉人项目里有什么。编译结果一样，但维护成本不同。如果项目里别人不知道某个类型为什么可以直接用，他们要么困惑、要么去 .csproj 里翻、要么在你的 GlobalUsings.cs 里一眼找到——你选哪个？

3.4 隐式导入 Implicit Usings——SDK 自动帮你加的 global using

回到本课开头的钩子——.NET 6 控制台项目只有一行代码。那些 using 不只靠 GlobalUsings，还有一个更深的机制：隐式导入。

.NET 6+ SDK 根据项目类型自动生成一套 global using。你的项目里看不见这些文件，但编译时它们被注入：

// ===== .NET 6+ SDK 自动生成的隐式 using（不同项目类型不同） =====

// 控制台 / 类库 → Microsoft.NET.Sdk 自动导入：
//   System, System.Collections.Generic, System.IO,
//   System.Linq, System.Net.Http, System.Threading,
//   System.Threading.Tasks

// ASP.NET Core → Microsoft.NET.Sdk.Web 额外导入：
//   Microsoft.AspNetCore.Builder,
//   Microsoft.Extensions.DependencyInjection,
//   Microsoft.Extensions.Hosting,
//   Microsoft.Extensions.Logging, ...

你可以在 .csproj 里控制这个行为：

<!-- 关闭隐式导入 -->
<PropertyGroup>
    <ImplicitUsings>disable</ImplicitUsings>
</PropertyGroup>

<!-- 或只加额外的隐式 using -->
<ItemGroup>
    <Using Include="System.Text.Json" />
</ItemGroup>
global using 和隐式导入有什么区别？隐式导入是 SDK 根据项目类型自动生成的 global using（你看不见），而 global using 关键字是你自己写的。两者机制相同——都编译为全局可见的 using。你的 global using 会叠加在隐式导入之上。

3.5 什么时候用？

✅ 适合 global using❌ 不适合
全项目高频使用的命名空间（如 System.Text.Json）只在 1-2 个文件用的命名空间——留在文件里更清晰
全局静态导入（如 Math, Console）和已有扩展方法冲突的 namespace
为冗长类型创建全局别名团队不熟悉这个机制——突然找不到类型从哪来的

四、记录结构体 Record Structs

4.1 C# 9 的遗憾——record 只能是 class

你在 Lesson 07 学了 C# 9 Records：

public record Person(string Name, int Age);

// 等价于：
// public record class Person(string Name, int Age);

C# 9 的 record 默认是 引用类型——分配在堆上，有空引用开销。如果你想做一个轻量的、分配在栈上的不可变数据对象，C# 9 说：不行，自己回去写 struct + 手写 Equals。

C# 10 补上了这个缺口：

// C# 10: record struct —— 值类型的 record
public readonly record struct Point(double X, double Y);

var p1 = new Point(3, 4);
var p2 = new Point(3, 4);
Console.WriteLine(p1 == p2);  // True——值相等语义

4.2 record class vs record struct —— 一张表讲清楚

record class 引用类型record struct 值类型
分配位置堆 Heap栈（优先）Stack
GC 压力有——每次 new 产生堆分配无——除非装箱或被引用类型字段拖累
可为 null✅ 是引用类型，天然可 null❌ 值类型不可 null（需 Point?）
不可变性默认不保证（需加 readonly）需显式 readonly record struct
值相等✅ Equals 基于所有属性✅ Equals 基于所有属性（且不走反射）
with 表达式✅ shallow clone✅ 值拷贝
ToString()✅ 自动生成✅ 自动生成
继承✅ 支持（record class 之间）❌ struct 不支持继承（可实现接口）
分配开销每次 new → 堆分配 + GC 跟踪每次 new → 栈上拷贝 + 无 GC

4.3 两种 record struct

// ① readonly record struct —— 完全不可变（推荐默认）
public readonly record struct Point(double X, double Y);
// 所有属性自动 init-only，编译器强制不可变

var p = new Point(1, 2);
// p.X = 3;  // ❌ 编译错误——readonly

// ② record struct（不加 readonly）——可变值类型 record
public record struct Counter(int Value);
// 属性是 { get; set; }，可修改

var c = new Counter(0);
c.Value++;  // ✅ 可以——不是 readonly
什么时候用 readonly record struct？几乎所有时候。C# 的 struct 如果可变，会有一系列反直觉的行为（防御性拷贝Defensive Copy、隐式修改丢失等）。readonly record struct 给你 record 的便利（自动 Equals/ToString/Deconstruct）+ 值类型的性能 + 不可变的安全性。不加 readonly 只在一种场景：你需要一个高频修改的小数据载体（计数器、累加器），且清楚可变 struct 的所有陷阱。

4.4 为什么 record struct 需要显式 readonly？Language Design

你可能已经注意到一个不对称：

默认行为想不可变？
record class属性自动 { get; init; }——默认不可变 ✅不需要额外操作
record struct属性自动 { get; set; }——默认可变 ❌必须显式加 readonly

为什么？这不是疏漏——是 C# 团队对值类型和引用类型截然不同的设计哲学：

根因 1：值类型天然隔离，引用类型天然共享

// struct：赋值 = 拷贝，修改副本不影响原值
var p1 = new Point(1, 2);
var p2 = p1;       // 完整拷贝——p1 和 p2 是两个独立的对象
p2.X = 5;           // p1.X 还是 1——安全

// class：赋值 = 拷贝引用，修改影响所有持有者
var r1 = new Person("Alice", 30);
var r2 = r1;       // 只拷贝引用——r1 和 r2 指向同一个对象
r2.Name = "Bob";    // r1.Name 也变成 "Bob"——危险！

值类型"拷贝即隔离"的天然属性，意味着可变 struct 的破坏力远小于可变 class。对 class 来说，不可变是安全必需品；对 struct 来说，不可变是锦上添花。

根因 2：struct 的 readonly 有历史传承

C# 团队对 struct 的 "opt-in to readonly" 哲学早已建立：

版本特性设计逻辑
C# 7.2readonly struct编译器可跳过防御性拷贝Defensive Copy——性能优化
C# 8.0readonly 实例方法声明"此方法不修改状态"——编译器验证
C# 10readonly record struct延续上述传统——struct 默认可变，想不可变就显式声明

如果 record struct 默认不可变，就破坏了 struct 世界"默认可变、按需锁定"的一贯规则。readonly 在 struct 语境下不只是"不可变"的声明——它还触发编译器优化（消除防御性拷贝）。

根因 3：性能敏感场景需要可变 struct

// 热循环中的累加器——可变 struct 是刻意为之
public record struct Stats(int Count, double Sum);

var stats = new Stats(0, 0);
foreach (var item in items)
{
    stats.Count++;   // 原位修改——如果 readonly 就要每次 new 一个新对象
    stats.Sum += item.Value;
}

record class 的主要场景是"数据建模"，不可变是核心诉求。record struct 的主要场景之一是"高性能数据载体"，可变性可能正合需求。C# 团队把选择权交给你。

readonly 在 record struct 上到底做了什么？

// 不加 readonly：
public record struct Point(double X, double Y);
// → 属性 { get; set; }——可读写
// → 编译器不保证不可变，不触发防御性拷贝优化

// 加 readonly：
public readonly record struct Point(double X, double Y);
// → 属性 { get; init; }——只可在构造/with 时赋值
// → 编译器标记整个 struct 为 readonly → 跳过所有防御性拷贝
// → 所有自动生成的方法（Equals、ToString、Deconstruct）标记为 readonly
一句话总结：record class 默认不可变，因为引用类型共享时可变性是 bug 工厂。record struct 默认可变，因为值类型拷贝即隔离 + struct 世界有 "opt-in to readonly" 的历史传统 + 高性能场景有时需要可变。这不是不一致——是对两种类型截然不同的安全模型和性能权衡。
面试金句："C# 的不可变性策略遵循类型身份——引用类型默认不可变（安全第一），值类型按需不可变（性能第一）。record 关键字尊重了这一哲学：record class 默认 init-only，record struct 需要显式 readonly。"

4.5 with 表达式——浅拷贝的真相 Shallow Copy

with 表达式做的是浅拷贝——无论 record class 还是 record struct，行为一致。但 struct 有个关键区别：如果你的 record struct 只含值类型字段，浅拷贝在效果上就等于深拷贝。

场景 1：纯值类型字段——深拷贝的效果

public readonly record struct Point(double X, double Y);

var p1 = new Point(3, 4);
var p2 = p1 with { X = 5 };

// Point 只有两个 double（值类型）→ with 逐字段拷贝 → 完全独立
// p2.X == 5, p2.Y == 4, p1 不受影响
层面发生了什么
struct 整体逐字节拷贝——值类型赋值就是全量复制，不走引用
X（double，值类型）完整复制，p2.X 和 p1.X 完全独立
Y（double，值类型）完整复制，p2.Y 和 p1.Y 完全独立
结论不含引用类型字段 → 效果上就是深拷贝

场景 2：含引用类型字段——浅拷贝的陷阱

public readonly record struct Person(string Name, List<string> Tags);

var p1 = new Person("Alice", new List<string> { "admin" });
var p2 = p1 with { Name = "Bob" };

p2.Tags.Add("staff");
Console.WriteLine(p1.Tags.Count);  // 输出 2 —— p1.Tags 和 p2.Tags 指向同一个 List！

Name（string）独立了，但 Tags（List<string>，引用类型）只复制了引用——p1.Tags 和 p2.Tags 指向堆上同一个 List 对象。这就是浅拷贝的经典表现。

record struct 的推荐场景就是纯值类型的小数据载体（Point、Color、UserId 等），所以实际使用中几乎不会踩这个坑。如果你的 struct 需要持有 List 或数组，那它可能根本不适合做成 struct——考虑 record class 或重新设计。

record struct vs record class 的 with 对比

record class withrecord struct with
实现机制调用 <Clone>$ → 成员克隆 → new值类型拷贝 → 直接用构造函数+新值
拷贝深度浅拷贝浅拷贝
全是值类型字段效果即深拷贝效果即深拷贝
含引用类型字段引用共享，改一个影响另一个引用共享，改一个影响另一个
为什么不需要 <Clone>$需要——引用类型需"创建副本再修改"不需要——值类型赋值就是完整逐字段拷贝，编译器直接用构造函数搞定
编译器视角：var p2 = p1 with { X = 5 }; 等价于 var p2 = new Point(X: 5, Y: p1.Y);——直接调用主构造函数，不需要 <Clone>$。这是 struct 的天然优势：值类型拷贝就是天然的"clone"，不需要额外机制。

4.6 编译器生成——record struct 生成什么？

和 record class 类似，但适配了值类型语义：

// 你写：
public readonly record struct Point(double X, double Y);

// 编译器生成（简化）:
//   - init-only 属性 X, Y（因为是 readonly）
//   - 主构造函数，赋值给属性
//   - Equals(Point other) —— 逐字段比较（不像 class 用 EqualityContract，因为没有继承）
//   - Equals(object) 装箱重载
//   - == 和 != 运算符
//   - GetHashCode() —— HashCode.Combine 模式
//   - ToString() —— "Point { X = 3, Y = 4 }" 格式
//   - Deconstruct(out double X, out double Y)
//   - 没有 <Clone>$ —— struct 直接拷贝，不需要成员克隆方法
//   - 没有 EqualityContract —— struct 不支持继承，不需要类型判别
和 record class 的关键区别：① 没有 <Clone>$ 方法——struct 赋值就是拷贝，不需要 shallow clone；② 没有 EqualityContract——struct 不能继承，不需要类型判别；③ Equals 不走反射，纯字段比较——更快；④ 不重载 ReferenceEquals——struct 没有引用。

4.7 真实场景——什么时候用 record struct？

// ✅ 完美场景：小而不可变的数据载体
public readonly record struct GeoPoint(double Lat, double Lng);
public readonly record struct Color(byte R, byte G, byte B);
public readonly record struct UserId(long Value);

// ✅ 适合：高频创建、用完就丢的临时对象
var points = Enumerable.Range(0, 10000)
    .Select(i => new Point(i, i * 2))  // record struct → 无 GC 压力
    .ToList();

// ❌ 不适合：需要多态/继承的场景
// struct 不支持继承——这种场景用 record class

// ❌ 不适合：大对象（> 16 字节）且频繁拷贝
// struct 赋值 = 全量拷贝——字段多了反而比 class 慢
选择场景
record class需要继承、可能为 null、字段多（> 16B）、生命周期长
readonly record struct小而不可变（≤ 16B）、高频创建销毁、无 GC 要求
record struct需要可变 + 值语义 + 自动生成——极少用
纯 struct需要完全手控 Equals/ToString

五、常量内插字符串 Constant Interpolated Strings

5.1 痛点——const string 和字符串插值水火不容

C# 6 引入了字符串插值 $"Hello {name}"——非常好用。但如果你想要一个 const 字符串，就不能用插值：

// C# 9 及以前：
const string ApiBase = "https://api.example.com";
const string ApiVersion = "v1";

// 想拼一个 const URL？只能用 +
const string ApiUrl = ApiBase + "/" + ApiVersion;  // ✅ 字符串拼接可以在 const 中

// 用插值？不行——编译错误
const string ApiUrl = $"{ApiBase}/{ApiVersion}";  // ❌ C# 9: 插值不是编译时常量

C# 10 的答案：只要插值表达式里的所有部分都是常量，就可以：

// C# 10：
const string ApiBase = "https://api.example.com";
const string ApiVersion = "v1";
const string ApiUrl = $"{ApiBase}/{ApiVersion}";  // ✅ C# 10: 编译时求值 → "https://api.example.com/v1"

5.2 规则和限制

规则示例
所有插值部分必须是常量const string s = $"pi = {Math.PI}" ❌——Math.PI 是静态字段，不是常量
可以使用常量字符串拼接const string s = $"{A}{B}" ✅
可以使用数字常量const string s = $"v{3}" ✅
可以使用 nameof()const string s = $"Class: {nameof(MyClass)}" ✅——nameof 是编译时常量表达式Compile-time Constant Expression
编译期求值，无运行时开销生成的 IL 直接是拼接好的最终字符串——和手写 "https://..." 一模一样

5.3 真实场景——常量模板和配置

// ✅ URL 模板
const string BaseUrl = "https://api.example.com";

const string UserByIdTemplate = $"{BaseUrl}/users/{{0}}";  // {{ → 转义为单个 {

// ✅ 日志模板

// ✅ 内嵌换行的常量（需要 C# 11 raw string literals，这里只是说明思路）
const string AppName = "MyApp";
const string ConnectionName = $"{AppName}Db";  // "MyAppDb"——用于 AddDbContext 的 name
编译器怎么实现的？和字符串拼接 "a" + "b" 一样——编译时常量折叠Constant Folding。编译器在编译期算出最终字符串，IL 里没有插值、没有 String.Format、没有 + 操作符。最终 IL = ldstr "https://api.example.com/v1"——一条指令。
