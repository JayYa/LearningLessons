你每天写的那些"没办法"——C# 11 全给解决了

本课的定位：.NET 7 不是 LTS，很多团队跳过它直接等 .NET 8。但 C# 11 的特性完全不依赖 .NET 7 运行时——它们是纯语言特性，在 .NET 6 甚至 .NET Core 3.1 上就能用（只要把 LangVersion 设为 11）。面试中能说出"语言版本和运行时版本解耦"，是加分项。

二、原始字符串字面量 Raw String Literals

2.1 痛点——字符串地狱三兄弟

C# 里写多行字符串或含引号的字符串，有三个老问题：

// ① 转义地狱：每个引号都加反斜杠
var json = "{\"name\":\"Alice\",\"city\":\"New York\"}";

// ② 拼接地狱：多行字符串用 + 拼接，丢了可读性
var sql = "SELECT Id, Name, Email " +
         "FROM Users " +
         "WHERE Status = 1 " +
         "ORDER BY Name";

// ③ Verbatim 字符串（@）只解决一半——仍然不能含 """
var xml = @"<root>
  <item name=""book""/>
</root>";  // 引号还是要双双写

2.2 答案——至少三个双引号

Raw String Literal 用 至少三个双引号（"""）包裹，内部内容完全原样——不需要转义任何东西：

// ✅ JSON：原样写，引号不用转义
var json = """
    {
        "name": "Alice",
        "city": "New York"
    }
    """;

// ✅ SQL：原样换行，不用 + 拼接
var sql = """
    SELECT Id, Name, Email
    FROM Users
    WHERE Status = 1
    ORDER BY Name
    """;

// ✅ 字符串里有引号也没关系
var html = """
    <div class="container">
        <p>Hello</p>
    </div>
    """;

2.3 关键规则——缩进和引号数量

规则说明示例
至少三个 " 开始/结束各至少 3 个双引号 """...""" 或 """"...""""
内容中 " 少于开始标记数就安全 如果内容含 3 个连续引号，就用 4 个 """" 包裹 """"{"key":"val""extra"}""""
自动缩进修剪 编译器以结束标记的缩进为基准，去掉每行前面的共同空白 见下例
开始 """ 后必须换行 开始引号后紧跟的内容在下一行 """\n..."""
支持内插 加 $ 前缀：$"""..."""，{ } 内的引号不受影响 $"""Hello {name}"""
$$ 减少内插所需大括号数 $$"""{{x}}""" = $"{{{x}}}" 内容本身含大量 { } 时（如 JSON）用 $$

缩进修剪——编译器怎么决定去留？

// 你写（结束 """ 在第 4 列缩进）：
var text = """
        Line 1
            Line 2
        Line 3
    """;

// 编译器处理：
//   结束 """ 从第 4 列开始 → 基准缩进 = 4 格
//   每行去掉 4 格 ← 结果：
// Line 1
//     Line 2    ← 这行的额外 4 格保留了（它相对于基准缩进了）
// Line 3
缩进基准只看结束 """ 的位置。如果结束标记在方法体第 2 层缩进里（比如 8 格），那么每行都会去掉 8 格。如果某行实际内容少于 8 格空白——编译器报错，因为它无法区分"这一行本应被修剪"还是"这一行的空白是故意的"。

2.4 编译器生成——几乎零开销

// 你写：
var json = """
    {"name": "Alice"}
    """;

// 编译器生成（简化）：
//   - 编译时完成缩进去除（纯编译器预处理）
//   - 最终 IL 等价于：ldstr "{\"name\": \"Alice\"}\r\n"
//   - 无运行时开销——和写普通字符串字面量完全一样
//   - $"""...""" 内插版本 → 编译时展开为 string.Format / DefaultInterpolatedStringHandler

Raw String Literal 是纯粹的编译时预处理——编译结果和手写转义字符串一模一样。它只是让你写的时候不用转义。

2.5 真实场景

// ✅ 单元测试中的期望 JSON
var expected = """
    {
        "id": 1,
        "name": "Alice"
    }
    """;

// ✅ SQL 查询模板
var sql = """
    SELECT u.Id, u.Name, o.Total
    FROM Users u
    JOIN Orders o ON u.Id = o.UserId
    WHERE u.Status = @status
    """;

// ✅ 内嵌 XML/HTML
var template = """
    <html>
    <body><h1>Hello</h1></body>
    </html>
    """;

// ✅ 配合 $ 做内插
var name = "Alice";
var json = $"""
    {{ "name": "{name}", "timestamp": "{DateTime.Now:O}" }}
    """;
// $ + """ → 内插使用 {name}，字面 { 需要 {{ 转义

// ✅ 用 $$ 避免和 JSON 的花括号冲突
var json2 = $$"""
    { "name": "{{name}}", "count": {{count}} }
    """;
// $$ → 内插用 {{name}}，字面 { 不需要转义

三、列表模式 List Patterns

3.1 痛点——数组和列表的匹配从未优雅过

你已经在 C# 8 学了属性模式，C# 9 学了 and/or/not。但集合呢？检查数组前三个元素要写一堆 Length + 索引：

// C# 10：想检查数组是 [1, >=10, <=100]
if (arr.Length == 3
    && arr[0] == 1
    && arr[1] >= 10
    && arr[2] <= 100) { }

C# 11 把模式匹配的方括号带给了集合：

// C# 11：列表模式——和数组内容"长得像"
if (arr is [1, >= 10, <= 100]) { }

语法和数组字面量类似，但方括号里的不是值——是模式。这就是 "list patterns"：用模式匹配来解构和检查集合。

3.2 完整语法

// ① 精确匹配——长度和元素都相等
int[] arr = { 1, 2, 3 };
Console.WriteLine(arr is [1, 2, 3]);   // True
Console.WriteLine(arr is [1, 2]);        // False——长度不匹配

// ② 元素使用任意模式（常量、关系、类型、属性……）
if (arr is [1, >= 10, <= 100]) { }
if (arr is [not 0, ..]) { }  // 第一项不是 0

// ③ 切片模式（..）——匹配任意数量元素（含零个）
if (arr is [1, ..]) { }          // 第一个是 1，后面随便
if (arr is [.., 9]) { }          // 最后一个是 9
if (arr is [1, .., 9]) { }        // 第一个 1，最后 9，中间随便
if (arr is [1, .. { Length: 2 }, 9]) { } // 1, [任意两个], 9

// ④ 嵌套模式——元素是对象时匹配属性
if (orders is [{ Status: "New" }, .., { Total: >= 1000 }]) { }
// 第一个订单 Status == "New"，最后一个订单 Total >= 1000

// ⑤ var 捕获——提取匹配到的元素
if (arr is [var first, .. var middle, var last])
{
    // first = arr[0], middle = arr[1..^1], last = arr[^1]
}

3.3 能匹配哪些类型？

类型支持？说明
int[] / T[]✅数组原生支持
List<T>✅实现了 IList 或有 Count + 索引器
Span<T> / ReadOnlySpan<T>✅C# 11 新增——Span 模式匹配
string✅string 有 Length + char 索引器
自定义集合✅有 Length 或 Count + 可访问索引器
编译器怎么判断？列表模式不要求实现特定接口。编译器只检查类型是否有 Length 或 Count 属性，以及是否有 可访问的索引器（this[int] 或 Slice 方法用于 ..）。这是一种鸭子类型Duck Typing模式——编译器不是看接口，而是看成员是否存在。

3.4 switch 表达式中的列表模式

static string Describe(int[] arr) => arr switch
{
    []                    => "空数组",
    [0]                   => "只有一个 0",
    [var x, var y]           => $"两个元素：{x}, {y}",
    [1, .., 1]              => "首尾都是 1",
    [.., 0]                => "最后一个元素是 0",
    [not 0, ..]             => "第一个不是 0",
    _                     => "其他",
};

// 实战：REST API 路由解析
static string ParseRoute(string[] segments) => segments switch
{
    ["api", "users"]             => "用户列表",
    ["api", "users", var id]    => $"用户详情 {id}",
    ["api", "users", var id, "orders"] => $"用户 {id} 的订单",
    ["api", ..]                    => "其他 API",
    _                            => "不是 API",
};

3.5 什么时候用列表模式 vs 传统写法？

✅ 用列表模式❌ 继续传统写法
需要同时检查长度 + 元素条件只需要检查长度
switch 表达式处理多种集合形态用 foreach 遍历处理每个元素
取"第一个"和"最后一个"元素需要随机访问任意索引位置
配合 Span 做高性能切片匹配集合非常大，模式匹配生成的索引访问代码不如手动优化

四、必需成员 Required Members

4.1 痛点——"这个属性必须设值"靠嘴说

很多类型有必填属性——比如 Person.Name 必须有值。C# 10 及以前你有三种办法，但都不够好：

// 方案 1：构造函数强制——可行，但 8 个必填属性 = 8 个参数的构造函数（地狱）
public class Person {
    public Person(string name, string email, int age, ...) { }  // 😫
}

// 方案 2：对象初始化器——方便，但忘了赋值编译器不吭声
var p = new Person { Email = "a@b.com" };  // Name 没赋值——谁告诉你？

// 方案 3：init-only 属性——可以对象初始化器，但仍然不强制
public class Person {
    public string Name { get; init; }  // 可以不设——运行时为 null
}

C# 11 给了第四种：required 关键字——让编译器帮你检查：

public class Person
{
    public required string Name { get; set; }
    public required string Email { get; set; }
    public int Age { get; set; }  // 没有 required——可选
}

var p = new Person { Name = "Alice" };  // ❌ 编译错误：Email 是 required 但未赋值
var p = new Person { Name = "Alice", Email = "a@b.com" };  // ✅
required 将运行时错误变成编译时错误。以前你可能在构造函数里抛出 ArgumentNullException，或者在单元测试里才发现属性没设。现在 IDE 在你还未写完那行代码时就显示红色波浪线——反馈零延迟。

4.2 关键规则

规则说明
只能用在属性和字段上required string Name（字段）、required string Name { get; set; }（属性）
访问级别必须 ≥ 类型如果类是 public，required 成员也必须 ≥ public 的构造函数能访问到
必须通过对象初始化器赋值new Person { Name = "A" } 而非 new Person("A")
构造函数参数可替代对象初始化器构造函数里给 required 属性赋值了 → 可以不写对象初始化器
[SetsRequiredMembers] 可标记构造函数告诉编译器"这个构造函数保证设置所有 required 成员"

4.3 SetsRequiredMembers——当构造函数搞定一切

public class Person
{
    public required string Name { get; set; }
    public required string Email { get; set; }

    // 这个构造函数设置了所有 required 成员
    [SetsRequiredMembers]
    public Person(string name, string email)
    {
        Name = name;
        Email = email;
    }

    // 没有 [SetsRequiredMembers] → 编译器不保证
    public Person(string name)
    {
        Name = name;
        // Email 未赋值——但有 required，调用这个构造函数会怎样？
        // 编译器报错：构造函数没有 SetsRequiredMembers，调用者必须用对象初始化器补齐 Email
    }
}

// 使用第一个构造函数（有 SetsRequiredMembers）
var p1 = new Person("Alice", "a@b.com");  // ✅ 不需要对象初始化器

// 使用第二个构造函数（没有 SetsRequiredMembers）
var p2 = new Person("Alice") { Email = "a@b.com" };  // ✅ 必须补齐 Email
[SetsRequiredMembers] 是承诺，不是验证。编译器不检查这个构造函数是否真的设置了所有 required 成员——你承诺了，编译器就信你。如果承诺了但没做到，运行时访问未初始化的属性就是未定义行为。这是一个"信任程序员"的契约。

4.4 编译器生成——RequiredMembers 到底生成了什么？

required 修饰符通过一个新特性传递到调用侧：

// 你写：
public class Person {
    public required string Name { get; set; }
}

// 编译器生成（简化说明）：
//   1. 在 Person 类型上标记 [RequiredMember]
//   2. 在 Name 属性上标记 [RequiredMember]
//   3. 在每个构造 new Person() 的调用处，编译器检查：
//      - 是否通过对象初始化器给 Name 赋值？或
//      - 构造函数是否有 [SetsRequiredMembers]？
//   4. 都不满足 → 编译错误 CS9035

这是 编译器层面的强制——IL 层面没有"必需成员"这个概念。编译后 required 属性就是普通属性，没有运行时代码来检查它是否被赋值。所有检查发生在编译时。

4.5 Required + init = 编译期强制不可变对象

// 组合技：required + init = 必须设值，设了就不改
public class ApiConfig
{
    public required string BaseUrl { get; init; }
    public required string ApiKey { get; init; }
    public int Timeout { get; init; } = 30;  // 有默认值——不需要 required
}

// ✅ 必须提供 BaseUrl 和 ApiKey，设定后不可修改
var config = new ApiConfig
{
    BaseUrl = "https://api.example.com",
    ApiKey = "sk-xxx",
    // Timeout 用默认值 30
};
// config.ApiKey = "new";  // ❌ init 不可修改

record 的 positional 参数本身就是 init-only 的，所以 required 通常更适用于 class / struct（非 record） 的配置对象、DTO、Options 模式等场景。

五、UTF-8 字符串字面量 UTF-8 String Literals

5.1 痛点——UTF-8 是无处不在的"隐形成本"

HTTP 通讯、JSON 序列化、数据库交互——现代应用中字符串几乎总是以 UTF-8 编码传输。但每次从 C# 的 string（内部 UTF-16）转 UTF-8，都有运行时代价：

// 传统方式——每次调用都做 UTF-16 → UTF-8 编码转换
byte[] data = Encoding.UTF8.GetBytes("application/json");
var span = new ReadOnlySpan<byte>(data);  // 还要再包一层

// 如果你把这一行放在热路径——每次请求都编码一次 "application/json"

C# 11 的答案："..."u8——编译期直接生成 UTF-8 字节序列：

// C# 11：编译期编码，零运行时开销
ReadOnlySpan<byte> contentType = "application/json"u8;

// 等价于运行时手动编码——但没有任何运行时开销
// 编译器直接在 IL 中生成 UTF-8 字节数组

5.2 本质——不是 byte[]，是 ReadOnlySpan<byte>

属性说明
类型ReadOnlySpan<byte>——零分配、栈上即可用
求值时机编译期——C# 编译器把字符串直接编码为 UTF-8 字节序列
存储位置PE 文件的元数据中——和字符串常量一样
运行时开销零——不需要 Encoding.UTF8.GetBytes，不需要堆分配
编译器实现：和 const string 的常量折叠类似。编译器在编译时将 "hello"u8 转为 ReadOnlySpan<byte> 指向 PE 数据段中的 UTF-8 编码字节序列。最终 IL 是 ldsflda（加载静态字段地址）——连分配都不需要。

5.3 真实场景——哪里用？

// ✅ HTTP Headers / Content-Type
var request = new HttpRequestMessage();
request.Content = new StringContent(body, Encoding.UTF8, "application/json"u8);

// ✅ ASP.NET Core 响应
context.Response.ContentType = "application/json"u8;  // ReadOnlySpan<byte>

// ✅ 高性能序列化——System.Text.Json 大量使用
var writer = new Utf8JsonWriter(stream);
writer.WriteString("name"u8, "Alice"u8);  // 属性名直接传 UTF-8

// ✅ 常量 MIME type / header name
ReadOnlySpan<byte> jsonType = "application/json"u8;
ReadOnlySpan<byte> authHeader = "Authorization"u8;

// ✅ 配合 Raw String Literals
ReadOnlySpan<byte> json = """
    {"name": "Alice", "age": 30}
    """u8;  // Raw String Literal + UTF-8 → 编译期生成完整 JSON 字节

5.4 限制

限制说明
只接受编译时常量不能 $"hello {name}"u8——内插后就不是常量了
只能是 ReadOnlySpan<byte>不能隐式转为 byte[]——需要则显式 .ToArray()
不能是 constconst ReadOnlySpan<byte> x = "..."u8 不合法——ref struct 不能是常量
和 Raw String Literal 完美配合"""..."""u8——多行 JSON/XML 直接编译为 UTF-8 字节

六、组合拳——这四个特性怎么一起用？

// 一个高性能 Minimal API 端点——用上了四个 C# 11 特性

// Required Members：配置对象
public class CreateUserRequest
{
    public required string Name { get; init; }
    public required string Email { get; init; }
    public string[] Tags { get; init; } = [];
}

namespace MyApp;  // File-scoped (C# 10)

// List Patterns：路由 / 权限检查
app.MapPost("/api/users", (CreateUserRequest req) =>
{
    // 检查 Tags 列表
    var description = req.Tags switch
    {
        [] => "新用户，无标签",
        [var single] => $"标签：{single}",
        ["vip", ..] => "VIP 用户",
        [.., "admin"] => "管理员用户",
        _ => "多标签用户",
    };

    // UTF-8 String Literals：高性能响应
    var response = $"""
        {{ "id": 1, "name": "{req.Name}", "desc": "{description}" }}
        """u8;  // Raw String Literal + UTF-8 → 零开销 JSON

    return Results.Bytes(response, "application/json"u8);
});

app.Run();

这个端点里：Required 保证请求体不会缺字段（编译时），List Patterns 让标签判断直观易读，Raw String Literal + UTF-8 让 JSON 输出零分配、零编码开销。C# 10 的 File-scoped Namespace / Global Usings / Top-level Statements 把仪式代码消干净——C# 11 在此基础上把业务逻辑的摩擦也消掉了。
