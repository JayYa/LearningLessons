〇、字典初始化——二十年的语法债 The Problem

C# 3.0 引入了集合初始化器，让字典初始化有了第一种语法：

// C# 3.0 集合初始化器（2007）——用花括号 + 大括号
var ages = new Dictionary<string, int>
{
    { "Alice", 30 },
    { "Bob", 25 },
    { "Charlie", 35 }
};
// 问题：{key, value} 和元素语法长得一模一样——它不是"键值对"，是"两个参数的 Add"

C# 6.0 加了索引器初始化器，好歹有了更像字典的写法：

// C# 6.0 索引器初始化器（2015）——稍微好一点
var ages = new Dictionary<string, int>
{
    ["Alice"] = 30,
    ["Bob"] = 25,
};
// 好了一些——但还是要写 new Dictionary<string, int>，类型推断不了

但 C# 12 的集合表达式（[1, 2, 3]）把这件事推到了临界点：

// C# 12：数组、列表、Span——全用同一种简洁语法
int[] arr = [1, 2, 3];
List<int> list = [1, 2, 3];
Span<int> span = [1, 2, 3];

// 但是字典呢？还是老样子：
var dict = new Dictionary<string, int> { ["a"] = 1 };
// 🤔 为什么集合有 [] 语法，字典没有？
字典是唯一没有集合表达式语法的常用集合类型。C# 12 的设计团队承认这只是一个时间问题——字典表达式原本计划随集合表达式一起发布，但因复杂性推迟。经过 C# 13、C# 14 两轮跳票，C# 15 终于开始实际开发。

字典表达式要解决的问题就一个：让字典和其他集合一样，有干净的字面量语法。

一、基本语法——k: v 在方括号里 Basic Syntax

// 字典表达式：键值对用冒号分隔，整体用方括号
Dictionary<string, int> ages = [
    "Alice":   30,
    "Bob":     25,
    "Charlie": 35
];

// 和 C# 12 集合表达式放在一起看——同一个括号，不同的元素
List<int>              numbers = [1, 2, 3];        // 普通元素
Dictionary<string, int> dict   = ["a": 1, "b": 2];  // 键值对元素

核心语法规则只有两条：

1. 键值对写成 expression : expression——冒号左边是键，右边是值。
2. 键值对元素只能出现在字典表达式的目标类型上下文中——你不能写 var x = "a": 1;，冒号语法只在方括号内有效。

可选尾随逗号：

// 尾随逗号——和集合表达式一样，允许、推荐（方便 git diff）
Dictionary<string, string> config = [
    "host": "localhost",
    "port": "5432",          // ← 尾随逗号 OK
];

二、语义——索引器赋值，不是 Add Indexer Semantics

这是字典表达式最核心的设计决策。先看旧语法的两套行为：

语法重复键行为底层调用
集合初始化器 { {"a",1}, {"a",2} }💥 抛出 ArgumentExceptiondict.Add(key, value)
索引器初始化器 { ["a"]=1, ["a"]=2 }✅ 覆盖（第二个值胜出）dict[key] = value
字典表达式 ["a": 1, "a": 2]✅ 覆盖（第二个值胜出）dict[key] = value

LDM 选择索引器语义的理由很实际：

最不意外的选择：集合表达式 [1, 2, 3] 允许重复元素——List、数组都接受。字典表达式也应该对称：允许重复键，后者覆盖前者。如果抛异常，会让你在"看起来能工作"的代码上突然崩溃——比如来自两个数据源的合并：[..defaults, ..overrides]，overrides 故意重复 defaults 的键来覆盖。抛异常反而破坏了最常见的用法。

编译器生成的代码相当于：

// 你写的：
Dictionary<string, int> ages = ["Alice": 30, "Bob": 25];

// 编译器生成的等价代码（伪代码）：
Dictionary<string, int> __result = new();
__result["Alice"] = 30;   // 索引器赋值——不是 Add()
__result["Bob"] = 25;
return __result;

求值顺序：键先于值

// 对于每个 k:v 元素：先求 k，再求 v，最后赋值 result[k] = v
int counter = 0;
Dictionary<int, string> d = [
    counter++: (counter++).ToString()   // 键 = 0, 值 = "1"
];
// 顺序：① 求键表达式 → counter = 1, 键 = 0
//       ② 求值表达式 → counter = 2, 值 = "1"
//       ③ 赋值 d[0] = "1"

三、目标类型——哪些类型能接住字典表达式 Target Types

字典表达式是目标类型推导——方括号里不声明类型，由左边变量类型或方法参数类型决定生成哪个具体类型的字典。

3.1 具体字典类型——字典表达式直接构造

// 标准字典（性能优先）
Dictionary<string, int> d1 = ["a": 1, "b": 2];

// 并发字典
ConcurrentDictionary<string, int> d2 = ["x": 10, "y": 20];

// 不可变字典（通过 CollectionBuilder）
ImmutableDictionary<string, int> d3 = ["pi": 314];

// 冻结字典
FrozenDictionary<string, int> d4 = ["const": 42];

3.2 字典的"资格"条件

一个类型被视为字典类型需要满足两个条件：

1. 元素类型是 KeyValuePair<TKey, TValue>（实现了 IEnumerable<KeyValuePair<TKey, TValue>>）
2. 有可读写的索引器 TValue this[TKey] { get; set; }

满足这两个条件的，字典表达式就用索引器赋值。不满足的（如只有 getter 的只读字典），走其他通路（见第六节）。

3.3 接口目标类型

// IDictionary<TKey, TValue> → 保证生成 Dictionary<TKey, TValue>
IDictionary<string, int> d1 = ["a": 1];
// d1 运行时类型就是 Dictionary<string, int>——可以安全转型

// IReadOnlyDictionary<TKey, TValue> → 编译器生成合规只读类型
IReadOnlyDictionary<string, int> d2 = ["a": 1, "b": 2];
// 运行时类型由编译器决定——不保证是 Dictionary
// 但保证：IsReadOnly = true，所有写操作抛异常
接口目标类型运行时具体类型可变？
IDictionary<K,V>一定是 Dictionary<K,V>✅ 是
IReadOnlyDictionary<K,V>编译器选择（可能是 FrozenDictionary 或合成类型）❌ 否
设计理由：LDM 为 IDictionary<,> 选择"保证 Dictionary"是因为：第一，Dictionary 是 .NET 投入最多优化的字典类型；第二，和集合表达式中 IList<T> → List<T> 的保证对齐。为 IReadOnlyDictionary<,> 选择"编译器自决"是为了给未来优化留空间——编译器今天可能用 FrozenDictionary，明天可能换成更高效的内部类型。

3.4 非字典集合类型——存入 KVP 列表

// 键值对元素也可以填入普通的 KVP 集合
List<KeyValuePair<string, int>> pairs = ["a": 1, "b": 2];
// 每个 k:v 元素包装成 new KeyValuePair<string, int>("a", 1)
// 然后用 Add() 加入列表

四、自然类型推断——var 也能用 Natural Type

和 C# 12 集合表达式一样，字典表达式支持 var 自然类型推断：

// var 推断为 Dictionary<string, string>
var d1 = ["a": "b", "c": "d"];
// d1 的类型是 Dictionary<string, string>——编译器推断键和值的最佳公共类型

// 对 null 字面量也能推断
var d2 = ["a": "hello", null: null];
// d2 的类型是 Dictionary<string?, string?>

自然类型推断的规则：

元素对类型推断的贡献
k: v 元素键表达式→推断 K；值表达式→推断 V
..spread 展开元素被展开集合的 Ki→K 和 Vi→V 提供下界推断
普通表达式元素（KVP）表达式类型的键值类型→K 和 V

自然类型始终是 Dictionary<K, V>——和集合表达式自然类型为 List<T> 的设计保持一致。

五、展开元素与混合元素 Spreads & Mixed Elements

5.1 展开现有字典

// 合并两个字典——后者覆盖前者（索引器语义）
Dictionary<string, int> defaults = ["timeout": 30, "retries": 3];
Dictionary<string, int> overrides = ["timeout": 60];

Dictionary<string, int> merged = [
    ..defaults,     // 先展开默认值
    ..overrides,    // 再展开覆盖值——相同的键（timeout）会被覆盖
    "debug": 1    // 还可以追加新键
];
// 结果：{ "timeout": 60, "retries": 3, "debug": 1 }
展开 + 覆盖模式：这是字典表达式最自然的使用场景之一。配置合并——先展开默认值，再展开覆盖值，后者自动覆盖前者相同的键。如果字典表达式用 Add() 语义，这个模式会直接抛异常——索引器语义让它变得优雅。

5.2 混合元素——KVP 和 k:v 混用

// 混合：手动 KeyValuePair + 键值对语法
Dictionary<string, int> mixed = [
    KeyValuePair.Create("a", 1),   // KVP 表达式元素
    "b": 2,                              // 键值对元素
    "c": 3
];

// 混合：来自列表的 KVP + 追加的 k:v
List<KeyValuePair<string, int>> source = GetPairs();
Dictionary<string, int> result = [
    ..source,           // 展开 KVP 列表
    "extra": 99      // 追加新键值对
];

六、接口转换细节 Interface Translation

6.1 IDictionary<TKey, TValue>——Dictionary 保证

// 编译时类型是接口，运行时一定是 Dictionary
IDictionary<string, object> dict = [
    "name": "Alice",
    "age": 30
];

// 安全转型——LDM 保证
Dictionary<string, object> concrete = (Dictionary<string, object>)dict;

// 你甚至可以依赖 Dictionary 特有的 API
concrete.EnsureCapacity(100);
concrete.TrimExcess();

6.2 IReadOnlyDictionary<TKey, TValue>——真只读保证

// 只读字典——运行时类型不透明，但行为有保证
IReadOnlyDictionary<string, int> readOnly = [
    "pi": 314159,
    "e":  271828
];

// 保证：
// - ((ICollection<KVP>)readOnly).IsReadOnly == true
// - Add / Remove / Clear → 抛 NotSupportedException
// - 通过任何接口视图都无法修改

// 也实现了非泛型 IDictionary（用于数据绑定/动态场景）
System.Collections.IDictionary nongeneric = (System.Collections.IDictionary)readOnly;
bool isFixed = nongeneric.IsFixedSize;  // true
为什么非泛型 IDictionary？这是为了兼容数据绑定场景——WPF、WinForms 和一些旧库通过 IDictionary 接口做运行时内省。如果只读字典不实现它，这些框架会在运行时崩溃。

七、开放问题——比较器、构造参数与时间线 Open Questions

7.1 比较器传参——最大的未决议题

你怎么在字典表达式中指定 StringComparer.OrdinalIgnoreCase？

// 理想语法（尚未确定）：
Dictionary<string, int> d = [
    "Alice": 30,
    "Bob":   25
] with (StringComparer.OrdinalIgnoreCase);   // ← 这个 with 还在讨论

// 或者用集合表达式参数的 with() 前缀（L27 学过）：
Dictionary<string, int> d = [
    with(StringComparer.OrdinalIgnoreCase),   // ← 这个也在讨论
    "Alice": 30,
    "Bob":   25
];

两种语法各有问题：后缀 with 违反求值顺序（键值已经求完了才发现比较器）；前缀 with() 和键值对元素混在一起显得杂乱。LDM 在 2025 年 4 月的会议上只做了初步讨论，尚未形成决议。

7.3 现在就学是不是太早了？

一个诚实的评估：

  • 如果你现在就要写代码：用索引器初始化器 { ["a"] = 1 }。字典表达式还没得用。
  • 如果你在准备面试：知道语法设计（k:v）、索引器语义（覆盖非抛异常）、接口保证（IDictionary→Dictionary）——这些是"问不倒"的层次。
  • 如果你在追踪 .NET 设计方向：字典表达式是集合表达式战略的收官之战——一旦完成，C# 的集合字面量体系就完整了（数组/列表/Span/字典全用 [...]）。

最值得记住的三件事：
1. 索引器语义是灵魂：字典表达式用 dict[key] = value，不是 dict.Add()。重复键覆盖不抛异常——这让 [..defaults, ..overrides] 模式自然工作。
2. K:V 语法只活在方括号里："a": 1 本身不是表达式——只有在字典表达式 [...] 中才有意义。这是目标类型推导的一部分。
3. 还没得用——但设计已成型：语法、语义、接口保证三大核心决策已锁定。剩下的是实现工作和比较器传参的收尾设计。现在学不亏——等它上线时你已经懂了。
