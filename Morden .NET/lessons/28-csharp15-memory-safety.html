〇、unsafe 不是开关，是承诺 The Big Reframe

C# 从 1.0 起就有 unsafe 关键字。它的工作方式二十多年没变：

// C# 1.0 ~ C# 14：unsafe 是一把"所有指针操作的总开关"
unsafe
{
    int* p = &x;       // 声明指针——要 unsafe
    int val = *p;       // 解引用——也要 unsafe
    fixed (int* f = arr)  // fixed——同样要 unsafe
}
// unsafe 块就是一个大麻袋：所有和指针沾边的东西全扔进去

这个模型的问题是：它把"持有指针"和"解引用指针"混在一起。持有指针本身不破坏内存安全——只有通过指针读写内存才会。二十多年来，这两个概念被同一种语法死死绑在一起。

C# 15 开始改变这一点。核心洞察：

指针的存在 ≠ 不安全。解引用指针 = 不安全。
int* p = &x 不会破坏任何东西。但 *p = 42 可能写到错误的地址。
C# 15 的 unsafe 从"标记所有指针操作"转向"标记真正危险的操作"。

这不仅是语法上的放松——它是 C# 对内存安全的根本性反思。设计团队甚至提出了一个长达多版本的路线图。我们来看看第一步。

〇·五、为什么是现在？——三层动机 Why Now?

你可能会问：二十多年没变的东西，为什么现在要改？是对性能的追求吗？

答案是：性能是推手之一，但不是唯一的推手，甚至不是最主要的推手。

第一层：性能——"我们需要指针，但不要 unsafe 的代价"

现代 .NET 越来越多地涉足高性能场景——P/Invoke 互操作、零开销序列化、SIMD 向量化、栈上大块内存分配。这些场景必须用指针，没有替代方案。但旧模型下，一行解引用就要把整段代码塞进 unsafe { } 大麻袋——十行代码只有一行危险，却要全部标记为不安全。这让代码审查无法聚焦真正的风险点。

第二层：正确性——"unsafe 应该是有意义的信号"

这是 C# 15 最主要的动机。旧模型下，unsafe 是一个"大范围广播"——它告诉你"这一大片代码里有不安全的东西"，但不告诉你"具体是哪一行"。代码审查时，你不得不通读整个 unsafe 块。新模型让 unsafe 精确到行——审查者一眼就能定位到真正的危险操作。这不是性能问题，是工程文化问题：关键字必须承载真正有意义的信息。

Rust 的影响：Rust 的 unsafe 块就是精确的——只包裹真正需要绕过编译器检查的操作。C# 15 的新模型明确借鉴了这个思路：unsafe 的范围应该精确对应危险操作的边界，而不是一大片区域的全有/全无开关。

第三层：生态位——"安全语言的舒适 + 系统语言的锋利"

.NET 的竞争对手不只是 Java，还有 Rust、Go、Zig。在高性能服务端、游戏引擎、云原生基础设施领域，完全托管的内存模型有天然的上限。.NET 的策略不是变成 Rust，而是：

用安全的抽象（Span<T>、ref struct、ref readonly）覆盖 90% 的高性能场景；然后对剩下 10% 真正需要指针的场景，把安全模型打磨到极致精确。

C# 15 这项变化属于后半部分——为那 10% 打磨工具。

长线视角：承认指针的合法地位

回顾 C# 7.2~15 跟内存相关的演进，能看到一条清晰的弧线：

C# 7.2   → ref struct, Span<T>        ← "给你安全的指针替代品"
C# 7.3   → stackalloc 改进              ← "栈分配更容易"
C# 12    → ref readonly, inline arrays   ← "更多零开销安全抽象"
C# 13    → ref struct 实现接口           ← "ref struct 成为一等公民"
C# 15    → 指针无需 unsafe 声明          ← "真正指针的安全模型精细化"

这条弧线的名字叫：承认指针的合法地位。二十年前 C# 的态度是"指针是危险的，关在 unsafe 笼子里"。现在的态度是"指针是工具，用对的地方就行，但我们要确保你知道什么时候在做危险的事"。

一句话：不是因为性能而放松安全，而是因为要更好地服务于性能场景，所以把安全模型做得更精确。unsafe 关键字从中世纪的"黑魔法印章"变成现代的"精确审计标记"。

一、两套模型——一张表看懂什么变了 Two Models at a Glance

C# 15 定义了两套内存安全模型。原始模型（C# 1.0）仍然是默认——新模型通过 LangVersion=preview 开启：

操作原始模型（C# 1.0~14）更新模型（C# 15 Preview）
声明指针类型 int* p需要 unsafe✅ 安全代码中允许
取地址 &x需要 unsafe✅ 安全代码中允许
fixed 语句（钉住变量）需要 unsafe✅ 安全代码中允许
stackalloc 转指针需要 unsafe✅ 安全代码中允许
sizeof（任意非托管类型）需要 unsafe✅ 安全代码中允许
指针解引用 *p / p->m / p[i]需要 unsafe仍需要 unsafe
函数指针调用需要 unsafe仍需要 unsafe
固定大小缓冲区元素访问需要 unsafe仍需要 unsafe
调用 unsafe 标记的方法无调用者要求调用者需要 unsafe（新增）

关键的思维转变：unsafe 不再描述"你在做什么"，而是描述"谁负责验证安全"。

二、C# 15 中不再需要 unsafe 的操作 Relaxed Operations

2.1 声明指针 + 取地址——指针变成"一等公民"

// C# 15：这些代码不需要 unsafe 块——指针可以自由创建和传递
int value = 42;
int* pointer = &value;           // 声明 + 取地址——安全
int** pointerToPtr = &pointer;   // 指向指针的指针——也安全

void Process(int* p) { }            // 方法参数可以是指针——安全
int* GetPointer() => &_field;    // 返回值也可以——安全（注意生命周期！）
但你仍然不能解引用：Console.WriteLine(*pointer) 仍然需要 unsafe 块。指针可以"持有"和"传递"，但只有在 unsafe 上下文中才能"看里面"。

2.2 fixed 语句——钉住变量不再需要 unsafe

// C# 15：fixed 本身不需要 unsafe——只有解引用需要
int[] numbers = [10, 20, 30, 40, 50];

fixed (int* first = numbers)        // fixed 在安全代码中——不需要 unsafe
{
    int* current = first;           // 指针运算——也不需要 unsafe
    current += 2;                    // 移动指针——仍然不需要

    unsafe                           // 只有这里！
    {
        Console.WriteLine(*current); // 解引用——需要 unsafe
    }
}

注意结构：整段代码没有外层的 unsafe { } 包裹——fixed 和指针运算都在安全代码中进行。只有真正读内存的那一行才在 unsafe 块中。这在原始模型下是不可能的。

2.3 stackalloc 转指针——不再需要 unsafe

// C# 7.2+：stackalloc 赋给 Span<T>——安全（已有）
Span<int> span = stackalloc int[64];

// C# 15：stackalloc 赋给指针——现在也安全了
int* buffer = stackalloc int[64];  // 创建指针——安全
unsafe { buffer[0] = 42; }          // 写入——需要 unsafe
例外——未初始化 stackalloc 赋给 Span 时收紧：如果一个 stackalloc 不带初始化器、转为 Span<T>、且方法上有 [SkipLocalsInit]，则在更新模型下需要 unsafe 上下文。因为此时 Span 会暴露未初始化的栈内存——违反 Span 的"安全包装"契约。这是少数收紧而非放松的规则。

2.4 sizeof——任意非托管类型均可

// C# 14 之前：sizeof 只对内置类型安全——其他类型需要 unsafe
int size1 = sizeof(int);         // 一直安全
int size2 = sizeof(Guid);        // C# 14：需要 unsafe | C# 15：安全 ✓
int size3 = sizeof(DateTime);    // C# 14：需要 unsafe | C# 15：安全 ✓

三、仍然需要 unsafe 的操作——真正的危险 What Still Requires unsafe

新模型的核心判断标准：凡是"读/写指针指向的内存"的操作，仍然需要 unsafe 上下文。

int value = 42;
int* p = &value;                  // ✅ 安全——只是取了地址

unsafe
{
    int read = *p;                  // ❗ 解引用——需要 unsafe
    p[0] = 100;                       // ❗ 指针元素访问——需要 unsafe
}

struct Point { int X; int Y; }
Point* pp = (Point*)&value;
unsafe
{
    pp->X = 10;                      // ❗ 指针成员访问——需要 unsafe
}

同样需要 unsafe 的操作：

操作为什么仍然危险
指针解引用 *p直接访问任意内存地址——可能越界、空指针、释放后使用
指针成员访问 p->X本质上是 (*p).X——包含解引用
指针元素访问 p[i]本质上是 *(p + i)——可能越界
函数指针调用跳转到任意地址——调用约定不匹配、地址无效
固定大小缓冲区元素访问通过指针访问嵌入 struct 内的缓冲区——同样的解引用风险
调用 unsafe 标记的方法该方法承诺它不安全——调用者必须显式接受审计义务

四、unsafe 的新角色——从"内部许可"到"调用者契约" Caller Contract

4.1 旧模型：unsafe 只是一个内部通行证

// C# 14：unsafe 修饰符只是让方法内部用指针——对调用者完全透明
public static unsafe int ReadInt(byte* source)
{
    return *(int*)source;   // 内部不安全，但调用者完全不知情
}

// 调用方——不需要 unsafe 上下文，即使传了指针
int result = ReadInt(ptr);   // C# 14：OK，调用者无感知

4.2 新模型：unsafe 是对调用者的警告

// C# 15 更新模型：方法的 unsafe 标记是公开契约——调用者必须负责
public static unsafe int ReadInt32(byte* source)
{
    unsafe                              // 注意：方法上的 unsafe 不再建立内部上下文
    {                                    // 需要显式的 unsafe 块来做解引用
        return *(int*)source;
    }
}

// 调用方——必须包裹在 unsafe 中
unsafe
{
    int result = ReadInt32(buffer);  // C# 15：调用者必须接受 unsafe 义务
}

关键时刻：unsafe 修饰符在方法签名上的含义变了： 旧模型："此方法体内可使用指针"（内部许可） 新模型："此方法有不安全操作——调用者审计"（公开契约）

4.3 传播 vs 消除——两条路选一条

当你调用了 caller-unsafe 方法，你有两个选择：

// 选择一：传播——把自己也标记为 unsafe，把义务传递给上层调用者
public static unsafe int Process(byte* data)
{
    unsafe { return ReadInt32(data); }   // 传播——我不消除，我的调用者来审
}

// 选择二：消除——用验证逻辑消解掉不安全风险，对外暴露安全接口
public static int SumBytes(byte[] source)   // 注意：没有 unsafe 修饰符
{
    ArgumentNullException.ThrowIfNull(source);  // 验证输入

    fixed (byte* first = source)               // fixed——安全
    {
        unsafe                                   // 只有真正需要的地方
        {
            // SAFETY: null 检查 + source.Length 确保每次读取都在数组边界内
            int total = 0;
            for (int i = 0; i < source.Length; i++)
                total += first[i];
            return total;
        }
    }
}
// 调用者可以安全使用——不需要 unsafe 上下文
消除模式是 C# 新模型的精髓：你在一小片 unsafe 块里做危险的事，用外围的验证逻辑保证安全，然后用"不带 unsafe 修饰符"的签名告诉世界："我处理好了，放心调用。"这和 Rust 的 unsafe 边界概念非常相似——不安全的具体操作被封锁在安全的抽象墙内。

4.4 安全文档——SAFETY 注释

// 更新模型鼓励两种注释来记录安全决策：

// 1. /// <safety> 文档块——放在方法签名上，说明调用者必须满足的前提条件
// 2. // SAFETY: 行内注释——放在 unsafe 块内，解释为什么这次操作是安全的

public static unsafe byte ReadByte(IntPtr ptr, int offset)
{
    byte* address = (byte*)ptr;
    unsafe
    {
        // SAFETY: 依赖调用者的 /// <safety> 契约——
        // ptr + offset 必须指向调用者有权读取的一个字节
        return address[offset];
    }
}

五、unsafe 表达式——只包裹一个表达式 unsafe() Expression

unsafe { } 块包围语句。但有些语法位置不接受语句——比如 catch 过滤器、字段初始化器、构造函数初始化器。unsafe(expression) 语法解决了这个盲区：

// 场景一：await 一个 caller-unsafe 方法
// await 不能写在 unsafe { } 块里——所以需要 unsafe 表达式
await unsafe(DoUnsafeWork());     // unsafe 只包住方法调用，await 在外面

// 场景二：catch 过滤器调用 caller-unsafe 方法
try { await DoWork(); }
catch (Exception e) when (unsafe(NowUnsafeCall(e)))  // 只包住过滤器表达式
{ }

// 场景三：字段初始化器
static int _value = unsafe(ReadFromPointer());

// 场景四：构造函数初始化器
class C(int x) : base(unsafe(GetBaseValue())) { }
语义：unsafe(expr) 对括号内的单个表达式建立 unsafe 上下文。上下文不超出右括号。结果类型和值就是内部表达式的类型和值。也需要 AllowUnsafeBlocks 编译选项。

六、新的 safe 关键字——编译器不知道的，你必须说清楚 The safe Keyword

有两种情况编译器无法判断安全性——必须由开发者显式标注：

6.1 extern 方法——调用原生代码

// C# 15 更新模型：每个 extern 方法必须标记 safe 或 unsafe
[LibraryImport("libc")]
internal static safe partial int getpid();    // 无参 + 原始类型——作者确认为 safe

[LibraryImport("libc", StringMarshalling = StringMarshalling.Utf8)]
internal static unsafe partial nint strlen(byte* str);  // 接收指针——标记为 unsafe

// 漏标 safe 或 unsafe → 编译错误

6.2 显式布局 struct——字段位置冲突

// [StructLayout(LayoutKind.Explicit)] 下，所有字段必须标注 safe 或 unsafe
[StructLayout(LayoutKind.Explicit)]
struct MyUnion
{
    [FieldOffset(0)] internal safe int IntValue;      // 正常使用——safe
    [FieldOffset(0)] internal unsafe byte* PtrValue; // 持有指针——unsafe
}

safe 是一个上下文关键字——只在特定位置（extern 方法声明、显式布局字段）被识别为关键字，其他地方仍可用作标识符。在 LangVersion=preview 下启用。

七、迁移路径——分阶段上路 Incremental Migration

7.1 第一重——指针宽松（今天就能用）

只要在 .NET 11 Preview SDK 中设置 <LangVersion>preview</LangVersion>，指针声明、fixed、stackalloc 转指针、sizeof 就可以从 unsafe 块中解放出来。这不需要打开任何新的 opt-in 开关。

这意味着你可以逐步把代码中 unsafe 块的范围缩小：

// 迁移前（原始模型）
unsafe
{
    fixed (int* p = arr) { *p = 42; }
}

// 迁移后（指针宽松）
fixed (int* p = arr)
{
    unsafe { *p = 42; }
}
// unsafe 块从 3 行缩为 1 行——范围精确对应唯一的危险操作

7.2 第二重——契约强制（仍在开发）

完整的调用者契约机制需要一个新的项目级 opt-in 属性。当开启时：

  • 方法上的 unsafe 成为调用者契约——调用方必须处于 unsafe 上下文
  • unsafe 修饰符不再自动为方法体建立 unsafe 上下文——需要显式 unsafe { } 块
  • extern 和显式布局字段必须标注 safe 或 unsafe
  • 类型、静态构造器、析构器上的 unsafe 修饰符报错

两重开关独立：

Opt-inAllowUnsafeBlocks效果
OnOff（默认）最安全配置：更新规则生效，不允许任何 unsafe 代码
OnOn更新规则生效，允许 unsafe 代码
OffOff原始模型，不能使用指针
OffOn原始模型，可以使用指针（当前默认）

7.3 兼容模式——保护未迁移的程序集

// 兼容模式：对于使用旧规则编译的程序集，
// 任何签名中含指针的成员都被视为 caller-unsafe
// 这样旧库不会 silently 失去 unsafe 要求

// 旧程序集中的方法：
public static unsafe void OldMethod(int* p);  // 签名有指针

// 新程序集中的调用方——兼容模式下仍需要 unsafe 上下文
unsafe { OldMethod(ptr); }  // 即使 OldMethod 来自旧程序集
设计意图：保证仅更新 LangVersion 不会造成安全性"回退"——旧库中有指针签名的方法不会因为新的宽松规则突然变成可安全调用。兼容模式在高版本中可能成为唯一模式，最终在跨多个 .NET 版本后移除。

七·五、对你意味着什么？——不同角色的影响 Who Benefits?

学完这么多内容，一个诚实的问题：作为普通应用开发者，这项改动对你变化大吗？

角色影响程度说明
框架作者
ASP.NET Core、EF Core、System.Text.Json		🟢 巨大这些库内部充斥着 fixed、指针运算、stackalloc。新模型让它们的 unsafe 块精确缩小——代码审查效率大幅提升。Microsoft 自己就是最大的 unsafe 用户。
库作者
序列化库、网络库、图形库		🟡 显著如果你写高性能 NuGet 包，这项改动让你能在安全代码中持有和传递指针，只在解引用时才进入 unsafe——接口设计更干净。
应用开发者
Web API + 业务逻辑 + CRUD		⚪ 几乎为零你不会写 unsafe。但在 GitHub 上读框架源码时，你不会被"fixed 为什么不在 unsafe 里"困惑。它不是你的日常工具，但是你的认知底盘。
类比：这就像 Span<T> 和 ref struct——你日常不写，但知道它们的存在，理解为什么这是趋势，面试能说出设计动机。这三者属于同一类知识：不是你的日常工具，但是你的认知底盘。

在你的知识体系中，这项改动的定位：

  • 优先级：低。不值得专门花时间练习指针代码。
  • 认知价值：高。它揭示了 .NET 团队的核心思路——在不牺牲安全的前提下逼近原生性能。这个思路贯穿了 C# 7~15 的整个演进。
  • 面试价值：中。如果你被问到"unsafe 在 C# 15 有什么变化"，你能说清楚"指针声明不需要 unsafe 了，但解引用还需要；unsafe 从内部许可变成了调用者契约"——这比 90% 的候选人强。

一句话：知道它存在、知道它为什么存在、知道它对你依赖的框架意味着什么。然后继续写你的业务代码。

最值得记住的四件事：
1. 现在就能缩小 unsafe 范围：把大片的 unsafe { fixed(...) { *p } } 变成 fixed(...) { unsafe { *p } }——unsafe 范围精确对应唯一的危险行。
2. 消除模式是最终目标：用验证逻辑包围 unsafe 操作，对外暴露安全签名——这是 C# 版本的"安全抽象"哲学。
3. 性能不是唯一的动机：让 unsafe 成为有意义的审计信号——这才是 C# 15 最主要的设计目标。指针的存在 ≠ 不安全；解引用指针 = 不安全。
4. 这项改动对你意味着什么：日常不写，但能读懂框架源码。低优先级、高认知价值。知道它存在、知道它为什么存在，然后继续写业务代码。
