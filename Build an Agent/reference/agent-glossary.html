Agent 核心概念速查表

本术语表是 Agent 开发的"压缩字典"——每个术语的精确定义和它在代码中的对应物。持续更新。

Agent（智能体）
一个能够自主感知环境、做出决策、调用工具并执行多步任务的 AI 系统。由一个 LLM + 工具集 + 记忆 + 执行循环（Agent Loop）组成。
对比：聊天机器人 = 单轮问答；Agent = 多步自主执行。
Agent Loop（Agent 循环）
驱动 Agent 运行的反馈循环：感知输入 → LLM 推理 → 调用工具(可选) → 获取结果 → 继续推理 → 生成最终输出。循环终止条件是 LLM 判断任务已完成或达到退出条件。
同义：ReAct Loop（Reasoning + Acting）。
LLM（Large Language Model / 大语言模型）
Agent 的决策中枢。接收「任务描述 + 对话历史 + 可用工具列表 + 工具执行结果」，输出「该调用哪个工具」或「最终回复」。LLM 不做实际动作，只做推理决策。常用模型：GPT-4o、Claude Opus、Gemini 等。
Tool / Plugin（工具 / 插件）
可以被 Agent 调用的外部函数或 API，是 Agent 与外部世界交互的接口。在 Semantic Kernel 中通过 [KernelFunction] 定义，在 OpenAI 中叫 Function Calling。
同义：Function、Plugin、Skill、Action。
Function Calling（函数调用）
LLM 的一种能力——模型不直接执行函数，而是输出一个结构化的函数调用请求（函数名 + 参数 JSON），由框架负责实际执行。这是 Agent 能"做事"的关键机制。
注意：OpenAI 用这个术语，Anthropic 叫 Tool Use，本质相同。
Memory / Context（记忆 / 上下文）
Agent 的信息存储机制，分三层：
· ① Working Memory（工作记忆） = ChatHistory——自动记录所有对话，但受上下文窗口 token 上限约束
· ② Explicit Memory（显式记忆） = Agent 主动调用 remember/recall 工具管理的键值存储——跨会话持久化，容量不受窗口限制
· ③ Vector Memory（向量记忆） = Embedding + 向量数据库 + 语义检索（RAG）——容量无限、按语义检索
关键约束：LLM 的上下文窗口有 token 上限，需要管理策略（滑动窗口 / 摘要压缩 / RAG）。
Context Window（上下文窗口）
LLM 一次推理能"看到"的最大 token 数量。ChatHistory + System Prompt + Tool Definitions 的总 token 数不能超过此上限——超出部分会被截断，导致 Agent"失忆"。
DeepSeek V3: 128K, Claude Sonnet: 200K。Agent 开发的核心约束之一——每一条消息都在消耗这个固定预算。
RAG（Retrieval-Augmented Generation / 检索增强生成）
在调用 LLM 之前，先从外部知识库检索相关文档，将文档注入 Prompt 再让 LLM 回答。解决 LLM 知识过时、幻觉、私有知识三大问题。
流程：查询 → Embedding → 向量检索 → 拼入 Prompt → LLM 生成。
Semantic Kernel (SK)
Microsoft 开源的 AI Agent 编排框架（C# / Python / Java），核心概念：Kernel（编排引擎）、Plugins（工具）、Memory（记忆）、Agents（ChatCompletionAgent 等）。对 C# 开发者是自然选择。
⚠️ 2026 年 4 月起进入维护模式，其 Agent 构建功能已被 Microsoft Agent Framework 正式继承和取代。SK 仍适合学习 Agent 内部机制（API 更透明），但新项目应优先考虑 MAF。
Microsoft Agent Framework (MAF)
Semantic Kernel 的正式继任者（v1.0 GA: 2026.4），融合了 SK 的企业工程基础与 AutoGen 的多 Agent 编排研究。核心变化：
· 统一 Agent 类型——chatClient.AsAIAgent(instructions)
· 原生基于 Microsoft.Extensions.AI（IChatClient）
· 多 Agent 是一等公民（群聊、Handoff、Magentic-One）
· 内置 MCP + A2A 支持、OpenTelemetry 链路追踪
· NuGet: Microsoft.Agents.AI；PyPI: agent-framework
本课程前几课用 SK 教学（API 更透明），后续迁移到 MAF。迁移指南见 learn.microsoft.com。
AIAgent
MAF 中的核心 Agent 抽象类型。通过 chatClient.AsAIAgent(name, instructions, tools) 创建——传入 IChatClient、系统指令、工具数组即可获得一个完整的 Agent。替代了 SK 中的 ChatCompletionAgent。
SK 等价物：new ChatCompletionAgent { Kernel, Name, Instructions }
IChatClient
Microsoft.Extensions.AI 定义的厂商中立聊天模型抽象接口。任何兼容 OpenAI 协议（或通过适配器桥接）的模型都通过 IChatClient 接入 MAF。创建方式：new OpenAIClient(key).GetChatClient(model).AsIChatClient()。
定位：微软主导的 .NET 生态事实标准。不同模型的接入方式不同——OpenAI 需要微软适配器（.AsIChatClient() 扩展），Anthropic SDK (v10+) 原生实现 IChatClient（new AnthropicClient().AsIChatClient(model)），Ollama 社区包直接实现。IChatClient 是接口而非框架——你可以自己手写实现来对接任何不被官方支持的模型。
AIFunctionFactory
MAF 中将 C# 方法转换为 LLM 可调用工具的工厂类。使用方式：AIFunctionFactory.Create(method)——传入一个带有 [Description] 特性的方法，返回一个 AIFunction 对象，可直接注入 Agent 的 tools 数组。替代了 SK 的 [KernelFunction] + KernelPlugin 注册流程。
生产级 DI 集成：两种模式——(1) 构造注入：注册 Plugin 到 DI → 解析 → AIFunctionFactory.Create(instance.Method)；(2) IServiceProvider 参数注入：在工具方法签名加 IServiceProvider 参数，MAF 调用时自动注入，LLM 看不到该参数。
AgentSession
MAF 中自动管理多轮对话历史的会话对象。通过 await agent.CreateSessionAsync() 创建，传给 RunAsync(prompt, session) 或 RunStreamingAsync(prompt, session)。框架在内部自动记录每轮用户/助手消息（包括 tool_call 和 tool_result），你不再需要手动 history.AddUserMessage() / history.AddAssistantMessage()。
序列化：SerializeSession(session) 返回普通 JSON 字符串（非 JSONL），内含 ConversationId + StateBag。框架只负责数据转换，I/O 由开发者决定——返回 string 而非直接写文件，意味着同一个序列化结果可以存入文件、数据库、Redis、Blob 等任意介质。SK 等价物：手动管理的 ChatHistory 对象。
Kernel
Semantic Kernel 的中央编排器。管理 AI 服务连接、注册 Plugins、协调 Agent 执行。每个 Agent 关联一个 Kernel 实例。
类比：ASP.NET 的 Host/ServiceCollection。
ChatHistory
Semantic Kernel 中存储完整对话记录的数据结构。每次 Agent 调用时，ChatHistory 被序列化为 LLM 的消息数组（System + User + Assistant + Tool）。
关键操作：Add、序列化、截断（防止超出 token 限制）。
Instructions / System Prompt（系统指令）
定义 Agent 角色、行为边界和工具使用规则的提示词。在 Semantic Kernel 中通过 ChatCompletionAgent.Instructions 设置。它是 Agent 的"性格"和"道德准则"。
写好 Instructions 是 Agent 工程最重要的技能之一。
ReAct（Reasoning + Acting）
Agent 模式：LLM 交替进行推理（Thought）→ 行动（Action）→ 观察（Observation）的循环。每个推理步骤基于前一次行动的实际结果——而非预判。相比纯 Function Calling Loop（隐式规划），ReAct 的推理过程显式可见，可审计、可调试。Yao et al., 2022 提出。
对比：Implicit Planning（不显式推理，直接调工具）；Plan-and-Execute（先规划好全部步骤再执行）。实际工程中三者常混合使用。
Planning（规划）
Agent 将复杂任务分解为有依赖关系的多个步骤并按正确顺序执行的能力。不是独立组件——它是 Agent Loop（Function Calling Loop）在复杂度上的自然延伸。三种策略：(1) Implicit Planning（隐式，FC Loop 直接驱动）；(2) ReAct（显式 Thought/Action/Observation）；(3) Plan-and-Execute（两阶段：先生成完整计划，再逐步执行）。
SK 废弃了 Stepwise/Handlebars Planner——现代 LLM 的 Function Calling 本身就是规划器。
Plan-and-Execute（先规划再执行）
两阶段规划策略：阶段 1——LLM 生成完整的 JSON 步骤列表（Plan）；阶段 2——按列表逐步执行（Execute），执行结果可汇总（Summarize）。优势是全局视角 + 人工可审核（在 Plan 和 Execute 之间插入确认点），代价是计划基于预判而非实际数据——第 3 步的实际结果可能与第 1 步的计划假设不符，导致整个计划失效。
适用场景：10+ 步的复杂任务、需要人工审批的危险操作、步骤可缓存的重复性任务。
Planning Loop（规划循环）
即 Function Calling Loop 在复杂任务中的表现：LLM 推理 → 调工具 → 拿到结果 → 基于结果继续推理 → 调工具 → …，直到任务完成。每一步的结果是下一步决策的输入。ChatHistory 是这个循环的状态载体——LLM 从中读取"已完成什么"和"还差什么"。
同义：Agent Loop、ReAct Loop、Function Calling Loop。本课程的基石概念。
Multi-Agent（多 Agent 系统）
多个 Agent 分工协作完成复杂任务的架构。每个 Agent 有独立的 Instructions 和工具集，Agent 间通过共享消息或以层级调用协作。MAF 提供五种编排模式：Group Chat（群聊，中央协调）、Handoff（交接，去中心化）、Sequential（顺序执行）、Concurrent（并发执行）、Magentic-One（Manager 领导团队）。
核心判断标准：不是「Agent 越多越好」，而是「单 Agent 的 Instructions 是否出现了不可调和的角色冲突（生成 vs 审查、教练 vs 裁判）」。多 Agent 有真实代价——Token 消耗倍数增长、延迟累积、指令漂移风险。
AgentWorkflowBuilder
MAF Workflows 编排的统一入口（Microsoft.Agents.AI.Workflows 包）。通过静态工厂方法创建不同模式的 Builder：CreateGroupChatBuilderWith(managerFactory)、CreateHandoffsBuilderWith(startAgent)、CreateSequentialBuilder()、CreateConcurrentBuilder()。链式调用 .AddParticipants(agents).Build() 返回一个 Workflow 对象。
NuGet：Microsoft.Agents.AI.Workflows。这是 MAF L5 层（Workflow & Orchestration）的核心 API。
GroupChatManager
Group Chat 模式中的中央发言权决策引擎。每一轮回答三个问题：(1) 下一个该谁发言（SelectNextAgent）；(2) 传给它的上下文是什么（UpdateHistory / Broadcast）；(3) 该结束了吗（ShouldTerminateAsync）。MAF 内置 RoundRobinGroupChatManager（轮转发言 + MaximumIterationCount 终止），开发者可继承它覆写 ShouldTerminateAsync 实现自定义终止逻辑。
类比：圆桌会议的主持人。Manager 不强依赖 LLM——轮转模式是纯代码逻辑。复杂的 SelectionStrategy 可调用 LLM 做判断，但那是可选的。
Handoff（交接）
去中心化的多 Agent 协作模式：当前 Agent 自己决定把对话交给谁——不需要中央 Manager。MAF 通过 AgentWorkflowBuilder.CreateHandoffsBuilderWith(startAgent) 构建，框架自动为每个 Agent 生成 handoff_to_{target} 工具，Agent 调用该工具即触发交接。适合客服分诊、专家路由、升级处理。
类比：接力赛跑——当前选手决定下一棒给谁。对比 Group Chat（圆桌会议，有主持人）。
Broadcast（广播机制）
Group Chat 中 Manager 在每次 Agent 发言后将回复同步到所有其他 Agent 的 Session——确保每个 Agent 在发言前都看到完整对话历史。每个 Agent 拥有独立的 AgentSession（因为不同 Agent 类型可能有不同的 Session 实现），Manager 负责跨 Session 的消息同步。可覆写 UpdateHistory 实现信息隔离——不是所有 Agent 都需要知道所有事。
这是 Group Chat 和 Handoff 的核心机制差异：Group Chat = 广播式上下文共享；Handoff = 接力式上下文传递。
AutoGen
微软研究院（Microsoft Research）2023 年推出的多智能体对话框架（Python 为主）。核心贡献是 Multi-Agent 协作机制——AgentGroupChat（多 Agent 群聊）、Handoff（Agent 间交接）、SelectionStrategy（下一轮发言权决策）。
2024-2025 年与 Semantic Kernel 团队合并，AutoGen 的 Multi-Agent 研究能力 + SK 的企业工程基础 = Microsoft Agent Framework（2026.4 GA）。MAF 的 L5（Workflow & Orchestration）层就是 AutoGen 的继承。
MCP（Model Context Protocol）
微软与 Anthropic 共同推动的 Agent-to-Tool 标准协议。定义统一的工具发现、调用、认证接口，让任何 Agent 能使用任何 MCP Server 提供的工具。三大协议原语：Resources（只读上下文）、Tools（可执行操作）、Prompts（模板）。
2025-2026 年成为行业标准，Anthropic .NET SDK 深度原生集成 MCP，Visual Studio 2026 已将 MCP 作为 AI 治理核心。与 IChatClient 不同——MCP 是真正的跨行业合作标准，IChatClient 是微软主导的 .NET 生态标准。
Token（令牌）
LLM 处理文本的最小单位——不是字也不是词。英文 ~0.75 词/token，中文 ~1-2 字/token。关键在于：token 有数量上限（上下文窗口）和按量计费（in + out tokens）。
Agent 开发的核心约束之一：长对话 = 更多 tokens = 更贵且可能超出窗口。
Temperature
控制 LLM 输出随机性的参数（0~2）。0 = 确定性（相同输入→相同输出），2 = 高随机性。Agent 的工具选择阶段建议低 temperature（0~0.3），创意生成阶段可以更高。
不是所有场景都该用默认值——根据步骤而非整个 Agent 调整。
Tool Chaining（工具链式调用）
Agent 在一个对话回合中连续调用多个工具，每个工具的返回结果作为后续决策的上下文输入。不是硬编码的 pipeline——LLM 在每一步重新推理下一步该调用哪个工具。
示例：「计算 15×23 并保存」→ 先调 calculate → 拿到结果 → 再调 save_note。底层是多次 Agent Loop 迭代。
Parameter Extraction（参数提取）
LLM 从用户的自然语言中推断工具调用所需参数值的能力。不仅做文本匹配——LLM 会在对话历史中搜索线索（如之前提到的文件名），利用参数类型信息（string/int/bool）做值映射。
这是 Agent 交互体验「自然」的关键——用户不需要精确指定每个参数。但也可能猜错，关键操作需确认。
OpenTelemetry (OTel)
CNCF 旗下的可观测性标准框架——定义统一的 API、SDK 和协议来收集 Traces、Metrics、Logs。MAF 原生集成 OTel，遵循 GenAI Semantic Conventions 自动产出 telemetry 数据。
三大信号：Traces（调用链）、Metrics（指标）、Logs（日志）。MAF 中通过 chatClient.AsBuilder().UseOpenTelemetry() 或 agent.WithOpenTelemetry() 开启。
Span
分布式追踪中的最小工作单元——代表一次操作（如一次 LLM 调用、一次工具执行）的起止时间、属性和父子关系。多个 Span 组成一棵 Trace 树。
MAF 自动创建三种 Span：invoke_agent（Agent 调用）、chat（LLM 推理）、execute_tool（工具执行）。
Trace
一个请求端到端的完整调用链——由多个有父子关系的 Span 组成，共享同一个 TraceId。在 MAF 中，一次 agent.RunAsync() 通常对应一条 Trace。
TraceId 是跨 Span 串联的关键——同一 Workflow 中所有 Agent 的 LLM 调用共享同一个 TraceId。
Metrics
可观测性的数值信号——记录一段时间内的聚合数据（计数器、直方图）。不同于 Traces 的"单次请求快照"，Metrics 回答"趋势"问题。
MAF 自动产出三种 Metric：gen_ai.client.operation.duration（延迟直方图）、gen_ai.client.token.usage（token 直方图）、agent_framework.function.invocation.duration（工具执行直方图）。
Aspire Dashboard
微软 .NET Aspire 团队的本地 OpenTelemetry 可视化工具——Docker 一键启动，通过 OTLP 协议接收 telemetry 数据，提供 Traces 甘特图、Metrics 图表和结构化日志查看。MAF 开发阶段的最佳观测伴侣。
启动：docker run -p 18888:18888 -p 4317:18889 mcr.microsoft.com/dotnet/aspire-dashboard:latest。Web UI: http://localhost:18888。
GenAI Semantic Conventions
OpenTelemetry 社区定义的AI/LLM 场景专用属性标准——统一了 gen_ai.system、gen_ai.operation.name、gen_ai.usage.input_tokens 等属性名。MAF 遵循此标准，意味着你的 Agent telemetry 数据可以被任何兼容的 OTel 后端理解。
跨框架通用——LangChain、LlamaIndex、Semantic Kernel 都在向这个标准靠拢。
