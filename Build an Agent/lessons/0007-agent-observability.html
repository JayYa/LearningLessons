Agent 可观测性：让黑盒变成玻璃盒

前六课你在构建 Agent。这一课回答一个运维问题——Agent 在里面做了什么？花了多少 token？哪一步慢了？

OpenTelemetry Tracing Metrics Logging Aspire Dashboard GenAI Semantic Conventions MAF v1.0 C#

Agent 是个黑盒——直到你打开它

传统 API 是可预测的：输入 X → 输出 Y，延迟稳定，错误可重现。Agent 完全不一样——同一个 Prompt 可能触发 3 次工具调用也可能触发 0 次，LLM 推理时间波动在 0.5 到 30 秒之间，每次对话的 token 消耗取决于 LLM 的"心情"。

当你把 Agent 从"玩具"推向"服务"，三个问题会反复出现：

问题 1: "为什么这次回复这么慢？" → 需要 Tracing（哪个 span 耗时最长？） 问题 2: "昨天花了多少 token？" → 需要 Metrics（token 消耗趋势） 问题 3: "Agent 在第 3 步为什么选了 B？"→ 需要 Logging（结构化日志 + 敏感数据）

MAF 对可观测性的回答是原生 OpenTelemetry 集成——遵循 GenAI Semantic Conventions 标准，自动产出 Traces、Metrics、Logs。你不需要手写埋点代码——两行 API 调用，整个 Agent 的内部行为就透明了。

本课产出： 给 Lesson 06 的 Writer + Reviewer 群聊加上 OpenTelemetry 追踪——在控制台看到每次 Agent 调用、每次 LLM 推理、每次工具执行的耗时和 token 消耗。

核心理念： 可观测性不是"出了问题才看"——它是你开发阶段的实时反馈系统。看到 Agent 在第 3 轮群聊中做了 4 次 LLM 调用消耗了 8000 token——这就是你优化 Instructions 的直接信号。

心智模型：三个信号，一个标准

MAF 的可观测性建立在三个支柱上，遵循同一个行业标准（OpenTelemetry + GenAI Semantic Conventions）：

信号回答的问题MAF 中的载体示例
Traces / Spans "一个请求经历了哪些步骤？每步花了多久？" invoke_agent / chat / execute_tool invoke_agent CopyWriter (2.1s) → chat deepseek (1.8s) → execute_tool search (0.3s)
Metrics "token 消耗趋势？平均延迟？错误率？" Histogram（gen_ai.client.operation.duration、gen_ai.client.token.usage） P50 延迟 1.2s，P99 延迟 8.7s，每小时消耗 12 万 token
Logs "具体发生了什么？Prompt 是什么？工具返回了什么？" Microsoft.Extensions.Logging + OpenTelemetry 导出 "Agent CopyWriter invoked with 3 tools available, 1200 input tokens"

Span 层级：一棵调用树

MAF 自动创建三层 Span，形成一棵自然的调用树：

invoke_agent CopyWriter ← 顶层：一次 Agent 调用 ├── chat deepseek-v4-flash ← 第 1 次 LLM 推理 │ └── (prompt + response) ← 敏感数据（dev only） ├── execute_tool search_competitors ← 工具调用 │ └── (arguments + result) ← 敏感数据（dev only） └── chat deepseek-v4-flash ← 第 2 次 LLM 推理（基于工具结果） └── (prompt + response)

关键洞察： 一棵 Trace 树 = 一次 Agent 调用的完整病历。你能精确回答"Agent 为这个请求做了几次 LLM 推理？每次分别花了多少 token？"。这就是 Instructions = 操作系统 的可观测面——你能看到"操作系统"的每一次上下文切换。

动手构建：给 Writer + Reviewer 加上可观测性

以 Lesson 06 的 Writer + Reviewer 群聊为基础——给两个 Agent 加上 OpenTelemetry 追踪，在控制台实时看到每次调用的 trace 输出。

Step 1: 创建项目和安装包

dotnet new console -n AgentObservability

dotnet add package OpenAI --version 2.*
dotnet add package OpenTelemetry --version 1.*
dotnet add package OpenTelemetry.Exporter.Console --version 1.*
📦 新包说明：
· OpenTelemetry — OTel SDK 核心（TracerProvider、MeterProvider）
· OpenTelemetry.Exporter.Console — 新增：将 traces/metrics/logs 输出到控制台——本地开发的最佳起点
· 后续可以替换为 OpenTelemetry.Exporter.OpenTelemetryProtocol（Aspire Dashboard）或 Azure.Monitor.OpenTelemetry.Exporter（生产环境）

Step 2: 配置 OpenTelemetry 管线

在任何 Agent 代码之前，先搭建好 OTel 的"管线"——决定 telemetry 数据去哪：

using OpenTelemetry;
using OpenTelemetry.Trace;
using OpenTelemetry.Metrics;
using OpenTelemetry.Resources;

const string SourceName = "WriterReviewerApp";

// ——— ① 创建 Resource（标识你的服务）———
var resourceBuilder = ResourceBuilder.CreateDefault()
    .AddService("WriterReviewerApp", serviceVersion: "1.0.0");

// ——— ② 配置 Traces 导出到控制台 ———
using var tracerProvider = Sdk.CreateTracerProviderBuilder()
    .SetResourceBuilder(resourceBuilder)
    .AddSource(SourceName)          // ← 必须和 UseOpenTelemetry 的 sourceName 一致
    .AddConsoleExporter()           // ← 输出到控制台（开发用）
    .Build();

// ——— ③ 配置 Metrics 导出到控制台 ———
using var meterProvider = Sdk.CreateMeterProviderBuilder()
    .SetResourceBuilder(resourceBuilder)
    .AddMeter(SourceName)
    .AddConsoleExporter()           // ← 每 30 秒输出一次指标聚合
    .Build();

Console.WriteLine("OpenTelemetry 管线已就绪。\n");
🔑 sourceName 是关键：
· .AddSource(SourceName) 告诉 Provider "监听来自这个名字的 telemetry"
· 如果你不指定 sourceName，MAF 默认用 "Experimental.Microsoft.Agents.AI"——那你就要 .AddSource("Experimental.Microsoft.Agents.AI")
· 显式指定一个名字更清晰——本课用 "WriterReviewerApp"

Step 3: 接入模型 + 定义 Agent（和 Lesson 06 一样，加一行）

using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;
using OpenAI;

// ——— 接入 DeepSeek（同 Lesson 06）———
var apiKey = Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")
    ?? throw new InvalidOperationException("请设置 DEEPSEEK_API_KEY");
var openai = new OpenAIClient(
    new System.ClientModel.ApiKeyCredential(apiKey),
    new OpenAIClientOptions { Endpoint = new Uri("https://api.deepseek.com/v1") });
var chatClient = openai.GetChatClient("deepseek-v4-flash").AsIChatClient();

// ——— ★ 唯一新增：给 ChatClient 加上 OpenTelemetry ———
var instrumentedChatClient = chatClient
    .AsBuilder()
    .UseOpenTelemetry(sourceName: SourceName,
        configure: cfg => cfg.EnableSensitiveData = true)  // dev 环境可见 Prompt
    .Build();

// ——— Agent 定义（同 Lesson 06，仅将 chatClient 换为 instrumentedChatClient）———
var writer = new ChatClientAgent(instrumentedChatClient,
    instructions: """
        你是一位创意文案撰稿人。
        职责：根据用户需求生成口号和营销文案。
        要求：简洁有力、有记忆点。每次输出一个版本。
        如果 Reviewer 给了反馈，根据反馈修改后重新输出。
        """,
    name: "CopyWriter",
    description: "负责创意文案生成");

var reviewer = new ChatClientAgent(instrumentedChatClient,
    instructions: """
        你是一位营销审查专家。
        职责：评估 CopyWriter 的文案。
        审查标准：清晰度、影响力、品牌契合度。
        - 如果文案符合标准，回复"approve"并附最终文案。
        - 如果需要修改，给出具体、可操作的反馈。
        """,
    name: "Reviewer",
    description: "负责文案质量审查");
💡 两种 instrumentation 级别，选一个就够了：

级别 A：只 instrument ChatClient（本课采用）
· chatClient.AsBuilder().UseOpenTelemetry(...)
· 捕获每次 LLM 调用——所有 Agent 共享的模型访问点
· 优势：一处配置，所有 Agent 自动受益；不会重复

级别 B：只 instrument Agent
· agent.WithOpenTelemetry(sourceName, ...)
· 捕获 Agent 级别的元数据（Agent ID、name、instructions）但不捕获底层 LLM 调用细节
· 优势：Agent 语义更丰富，适合多 Agent 场景按 Agent 维度分析

⚠️ 不要两个都开：会导致 Chat 级别的 span 重复（ChatClient 和 Agent 各创建一个）。选一个就够了。

2026.5 后的变化：PR #5750 开始，OpenTelemetryAgent 自动包裹内部 ChatClient——选 Agent 级别时不再丢失 LLM 调用细节。但目前最稳妥的做法仍是只 instrument ChatClient。

Step 4: 构建 Group Chat + 运行

Workflow 代码和 Lesson 06 完全一样——可观测性是横切关注点，不侵入业务代码：

using Microsoft.Agents.AI.Workflows;
using Microsoft.Extensions.AI;

// ——— Workflow（和 Lesson 06 完全相同）———
var workflow = AgentWorkflowBuilder
    .CreateGroupChatBuilderWith(agents =>
        new ApprovalBasedManager(agents, "Reviewer")
        {
            MaximumIterationCount = 8
        })
    .AddParticipants(writer, reviewer)
    .Build();

// ——— 运行 ———
var messages = new List<ChatMessage>
{
    new(ChatRole.User, "为一款环保电动 SUV 创作一个口号。")
};

Console.WriteLine("=== Writer + Reviewer 群聊（可观测） ===\n");

await using var run = await InProcessExecution.RunStreamingAsync(workflow, messages);
await run.TrySendMessageAsync(new TurnToken(emitEvents: true));

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is AgentResponseUpdateEvent update)
    {
        foreach (var msg in update.AsResponse().Messages)
            Console.WriteLine($"[{update.ExecutorId}]: {msg.Text}\n");
    }
    else if (evt is WorkflowOutputEvent)
        break;
}

Console.WriteLine("=== 结束 ===\n");

// ——— 自定义 Manager（同 Lesson 06）———
public class ApprovalBasedManager : RoundRobinGroupChatManager
{
    private readonly string _approverName;
    public ApprovalBasedManager(IReadOnlyList<AIAgent> agents, string approverName)
        : base(agents) => _approverName = approverName;

    protected override ValueTask<bool> ShouldTerminateAsync(
        IReadOnlyList<ChatMessage> history, CancellationToken ct = default)
    {
        var last = history.LastOrDefault();
        return ValueTask.FromResult(
            last?.AuthorName == _approverName &&
            last.Text?.Contains("approve", StringComparison.OrdinalIgnoreCase) == true);
    }
}

观察：你现在能看到——
· 两个 chat span = 两次 LLM 调用（CopyWriter 一次，Reviewer 一次）
· 每次 LLM 调用的耗时（1.823s / 1.512s）
· 每次调用的 token 消耗（input 1247+89, 1456+42）
· 同一个 TraceId = 它们属于同一次群聊请求——可以串联起来分析
· 因为启用了 EnableSensitiveData，Prompt 和 Response 内容也在 Attributes 里

这就叫"玻璃盒"：你不需要猜 Agent 做了什么——每一个 LLM 调用、每一次工具执行都有精确的数字记录。

Step 6: 升级到 Aspire Dashboard（可视化）

控制台输出够用但不够直观。微软的 Aspire Dashboard 是一个本地运行的 Web UI，专门为 OpenTelemetry 数据设计——免费、零配置、Docker 一行命令启动： 

# 终端 1：启动 Aspire Dashboard
docker run --rm -it -d \
    -p 18888:18888 \
    -p 4317:18889 \
    --name aspire-dashboard \
    mcr.microsoft.com/dotnet/aspire-dashboard:latest

# 浏览器打开 http://localhost:18888

然后把控制台 exporter 换成 OTLP exporter：

// ——— 替换 Step 2 中的 exporter 配置 ———
using OpenTelemetry.Exporter;

using var tracerProvider = Sdk.CreateTracerProviderBuilder()
    .SetResourceBuilder(resourceBuilder)
    .AddSource(SourceName)
    .AddOtlpExporter(options => options.Endpoint = new Uri("http://localhost:4317"))
    .Build();

using var meterProvider = Sdk.CreateMeterProviderBuilder()
    .SetResourceBuilder(resourceBuilder)
    .AddMeter(SourceName)
    .AddOtlpExporter(options => options.Endpoint = new Uri("http://localhost:4317"))
    .Build();

运行后打开 Dashboard → Traces 页面，你会看到一棵可视化的调用树——每个 span 的父子关系、甘特图式的时间线、按 span 类型筛选。

📊 Metrics 也自动来了：
Aspire Dashboard 的 Metrics 页面会显示：
· gen_ai.client.operation.duration — LLM 调用延迟分布（P50/P95/P99）
· gen_ai.client.token.usage — token 消耗趋势
不需要额外代码——Metrics 和 Traces 同一条管线。

深入理解：多 Agent 的可观测性

每个 Agent 的调用天然隔离—— 在 ChatClient 级别做 instrumentation 时，Writer 的 LLM 调用和 Reviewer 的 LLM 调用共享同一个 TraceId（因为它们在同一个 Workflow 执行上下文中），但你可以通过 gen_ai.agent.name 属性来区分。

如果换成 Agent 级别的 instrumentation（.WithOpenTelemetry()），框架会自动为每个 Agent 创建 invoke_agent CopyWriter 和 invoke_agent Reviewer 两个顶层 span——你可以按 Agent 维度做性能分析和成本归因。

生产环境的最佳实践：
· 开发阶段——Console exporter + EnableSensitiveData = true，快速定位问题
· 预发布阶段——Aspire Dashboard / Jaeger，可视化分析调用链
· 生产环境——Azure Monitor / Application Insights，设置 EnableSensitiveData = false
· 成本控制——用 gen_ai.client.token.usage 指标设置告警（"Writer Agent 单次调用超过 8000 token 时警告"）

什么时候不需要 OpenTelemetry？

OTel 也有成本——虽然很小，但有：

① Span 创建的内存开销。 每次 LLM 调用和工具执行都会创建 Span 对象。在高并发场景下（每秒数百次 Agent 调用），这些 Span 对象会占用可观的堆内存。

② 导出开销。 Console exporter 几乎是零成本的，但 OTLP exporter 需要序列化 + 网络传输。如果用 Azure Monitor，还涉及采样策略（默认自适应采样可能丢失低频但重要的 trace）。

③ 敏感数据风险。 EnableSensitiveData = true 意味着用户输入、LLM 回复、工具参数和返回值全部记录在 trace 中——这在生产环境是不可接受的。

判断标准：
· 原型/个人项目 → 不开 OTel，靠 Console.WriteLine 观察
· 团队协作/预发布 → OTel + Console exporter，理解 Agent 行为
· 生产服务 → OTel + Azure Monitor，但 EnableSensitiveData = false，搭配结构化日志补充关键决策点
