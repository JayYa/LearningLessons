多 Agent 协作：从单兵作战到团队配合

前五课你在用一个 Agent 解决所有问题。这一课回答一个自然延伸的问题——什么时候该用两个 Agent？怎么让它们配合？

单 Agent 的天花板

前五课你的 Agent 什么都能做——调用工具、管理记忆、执行多步规划。但你会逐渐发现一个问题：Instructions 越来越长。一个 Agent 既要分析文件、又要写报告、还要自我审查——Instructions 变成了几百行的"保姆级说明书"，LLM 在其中迷失。

一个 Agent 的 Instructions： "你是代码分析助手。 第1步：列出文件 第2步：读取每个文件 第3步：统计代码行数 第4步：分析代码质量 第5步：生成报告 第6步：自己审查报告是否有误 ..." ↓ 问题：角色冲突——"写报告的人"和"审查报告的人"是同一套指令。 写代码时你会让一个人既写代码又做 Code Review 吗？

多 Agent 协作的本质不是「更多的 Agent = 更好」——而是职责分离。当一个 Agent 的 Instructions 内部出现角色冲突时，就该拆成两个。这和软件工程中「一个类不要承担两种职责」是同一个原则。

MAF 的独特优势： 多 Agent 协作是 MAF 的 L5 层（Workflow & Orchestration）——这正是 AutoGen 团队合并时贡献的核心能力。在 SK 时代，多 Agent 需要手动管理 ChatHistory 的分发和 Agent 间切换；在 MAF 中，AgentWorkflowBuilder + GroupChatManager 把这些变成了声明式配置。

本课产出： 构建一个 Writer + Reviewer 双 Agent 群聊——Writer 生成内容，Reviewer 审查反馈，两个 Agent 自动轮流发言直到 Reviewer 批准。

心智模型：两种协作拓扑

MAF 提供五种编排模式，但核心就两种拓扑——理解了这两种，其余的（Sequential、Concurrent、Magentic）都是变体：

Group Chat（群聊）Handoff（交接）
类比 圆桌会议 🪑——一个主持人决定谁发言 接力赛跑 🏃‍♂️→🏃‍♀️——当前选手决定下一棒给谁
协调方式 中央协调——GroupChatManager 选择下一个发言的 Agent 去中心化——当前 Agent 自己决定把对话交给谁
上下文 所有 Agent 看到完整的对话历史 只有当前活跃的 Agent 在处理
适用场景 迭代创作、头脑风暴、质量审查 客服分诊、专家路由、升级处理
核心 API CreateGroupChatBuilderWith(managerFactory) CreateHandoffsBuilderWith(startAgent)
Group Chat 拓扑（星型）： Handoff 拓扑（链式）： Reviewer Triage → Billing ╱ ↓ Manager Support ╲ Writer 每个 Agent 决定下一棒给谁

本课聚焦 Group Chat——它是最直观的多 Agent 模式，也最能体现 MAF 的 SelectionStrategy 设计。Handoff 在「挑战练习」里让你自己探索。

SelectionStrategy：谁该说话了？

Group Chat 的核心不是一个"聊天室"——而是一个发言权决策引擎。GroupChatManager 在每一轮回答三个问题：

  1. 下一个该谁发言？（SelectNextAgent）
  2. 传给它的上下文是什么？（UpdateHistory / Broadcast）
  3. 该结束了吗？（ShouldTerminateAsync）

MAF 内置了 RoundRobinGroupChatManager——按顺序轮流发言，达到 MaximumIterationCount 后终止。对于 80% 的场景它够用，而剩下的 20% 你可以继承它，覆写 ShouldTerminateAsync 来自定义终止条件——本课会演示。

Step 2: 定义两个 Agent

每个 Agent 有自己的 Instructions——角色专一、边界清晰：

using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;
using OpenAI;

// ——— 接入 DeepSeek ———
var apiKey = Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")
    ?? throw new InvalidOperationException("请设置 DEEPSEEK_API_KEY");
var openai = new OpenAIClient(
    new System.ClientModel.ApiKeyCredential(apiKey),
    new OpenAIClientOptions { Endpoint = new Uri("https://api.deepseek.com/v1") });
var chatClient = openai.GetChatClient("deepseek-v4-flash").AsIChatClient();

// ——— Agent A: Writer（只负责创作）———
var writer = new ChatClientAgent(chatClient,
    instructions: """
        你是一位创意文案撰稿人。
        职责：根据用户需求生成口号和营销文案。
        要求：简洁有力、有记忆点。每次输出一个版本。
        如果 Reviewer 给了反馈，根据反馈修改后重新输出。
        """,
    name: "CopyWriter",
    description: "负责创意文案生成");

// ——— Agent B: Reviewer（只负责审查）———
var reviewer = new ChatClientAgent(chatClient,
    instructions: """
        你是一位营销审查专家。
        职责：评估 CopyWriter 的文案。
        审查标准：清晰度、影响力、品牌契合度。
        - 如果文案符合标准，回复"approve"并附最终文案。
        - 如果需要修改，给出具体、可操作的反馈（不要生成新文案，交给 CopyWriter 改）。
        """,
    name: "Reviewer",
    description: "负责文案质量审查");
🔍 关键设计：
· 角色互斥——Writer 不审查自己，Reviewer 不写新文案。这是多 Agent 的第一条纪律。
· 明确的交接协议——Reviewer 的 Instructions 定义了"approve"作为终止信号。这比轮数限制更智能。
· 名称即身份——name 参数在对话历史中作为 AuthorName 出现，LLM 据此理解"谁说了什么"。起一个描述性的名字。在 Group Chat 中，所有参与者的 name 必须唯一——GroupChatManager 用它做发言权路由和终止判断（见下方详解）。
🪪 深入：Agent 的身份系统——Name vs Id

MAF 中每个 Agent 有两层身份标识：

属性 来源 唯一性 用途
Id 框架自动生成（GUID） 全局唯一 内部追踪、序列化、Session 关联——你不直接操作它
Name 你创建 Agent 时指定 同一 Workflow 内必须唯一 对话身份标签（→ AuthorName）、Manager 路由 key、LLM 辨识"谁说了什么"

关键机制：
· Name → AuthorName：每次 Agent 发言，框架自动把 Name 写入消息的 AuthorName 字段。这就是 ShouldTerminateAsync 里 last?.AuthorName == "Reviewer" 能工作的原因。
· 官方约束：GroupChatBuilder 文档 明确要求 "Participant names must be unique"——用 list 形式注册参与者时，agent.name 直接作为 participant key，重名即冲突。
· 不指定 name 的后果：框架会兜底为 "UnnamedAgent"。两个 Agent 都不起名 → 都叫 "UnnamedAgent" → Manager 和 LLM 无法区分谁说了什么 → 群聊逻辑失效。
· 最佳实践：起一个描述性、角色明确的名称（如 "CopyWriter"、"Reviewer"），不只是给人类看——LLM 通过 AuthorName 理解对话结构和角色关系，Manager 用它做路由决策。

Step 3: 构建 Group Chat + 自定义终止条件

这是整个多 Agent 协作的核心——三行代码定义一个编排规则：

using Microsoft.Agents.AI.Workflows;

// ——— 自定义 GroupChatManager：Reviewer 批准即终止 ———
public class ApprovalBasedManager : RoundRobinGroupChatManager
{
    private readonly string _approverName;

    public ApprovalBasedManager(IReadOnlyList<AIAgent> agents, string approverName)
        : base(agents)
    {
        _approverName = approverName;
    }

    protected override ValueTask<bool> ShouldTerminateAsync(
        IReadOnlyList<ChatMessage> history,
        CancellationToken cancellationToken = default)
    {
        var last = history.LastOrDefault();
        // 终止条件：最后一句话来自 Reviewer，且包含 "approve"
        bool shouldTerminate = last?.AuthorName == _approverName &&
            last.Text?.Contains("approve", StringComparison.OrdinalIgnoreCase) == true;
        return ValueTask.FromResult(shouldTerminate);
    }
}

// ——— 构建 Workflow ———
var workflow = AgentWorkflowBuilder
    .CreateGroupChatBuilderWith(agents =>
        new ApprovalBasedManager(agents, "Reviewer")
        {
            MaximumIterationCount = 8  // 安全上限：防止无限循环
        })
    .AddParticipants(writer, reviewer)
    .Build();
💡 这是多 Agent 协作的全部 API 表面积：

① AgentWorkflowBuilder —— 编排的入口。你告诉它参与者是谁、用哪个 Manager。
② GroupChatManager —— 发言权决策引擎。内置 RoundRobin；自定义只需覆写 ShouldTerminateAsync。
③ MaximumIterationCount —— 安全网。即使你的自定义终止逻辑有 bug，也不会无限循环烧 token。

对比一下：在 SK 时代实现同样的事，你需要手动管理每个 Agent 的 ChatHistory 分发、手动写 KernelFunctionSelectionStrategy 选择函数、手动写 KernelFunctionTerminationStrategy 终止函数——代码量至少 3 倍。

核心理念：Instruction 仍然是 Agent 行为的唯一可编程接口（见 学习记录 0008），Manager 控制的是谁在什么时候看到什么上下文——Instructions 控制「怎么想」，Manager 控制「谁来说」。

RoundRobin 的发言顺序

RoundRobinGroupChatManager 的"轮转"不是随机的——严格按 AddParticipants 的传入顺序轮流发言。 核心逻辑就是一个索引计数器，每次发言后 (index + 1) % 参与者总数：

AddParticipants(writer, reviewer) → writer → reviewer → writer → ... AddParticipants(reviewer, writer) → reviewer → writer → reviewer → ... AddParticipants(researcher, writer, reviewer) → researcher → writer → reviewer → ...

这纯粹是代码逻辑，不涉及 LLM 判断——Manager 维护一个 _nextSpeakerIndex，取模递增。所以如果你想让 Writer 先发言、Reviewer 后审查，AddParticipants(writer, reviewer) 这个顺序就是你要的（和本课代码一致）。

进阶：让 Manager 动态选择下一个发言人

轮转适合固定流程，但如果发言顺序应该由对话内容决定呢？比如用户问了账单问题就路由到 BillingAgent，问了技术问题就路由到 SupportAgent——这就是 Handoff 模式的强项。但在 Group Chat 中，你也可以覆写 Manager 的 SelectNextAgentAsync，让 LLM 根据上下文动态选人： 

public class DynamicManager : GroupChatManager
{
    private readonly IChatClient _llm;  // 专门做选人决策的 LLM（可用轻量模型）

    public DynamicManager(IReadOnlyList<AIAgent> agents, IChatClient llm)
        : base(agents) => _llm = llm;

    protected override async ValueTask<string> SelectNextAgentAsync(
        IReadOnlyList<ChatMessage> history,
        CancellationToken ct = default)
    {
        // 把所有 Agent 的描述喂给 LLM，让它根据对话历史选人
        var agentList = string.Join("
",
            Agents.Select(a => $"- {a.Name}: {a.Description}"));

        var prompt = $"""
            对话历史：
            {string.Join("
", history.Select(m => $"[{m.AuthorName}]: {m.Text}"))}

            可选 Agent 及其职责：
            {agentList}

            根据对话进展，下一个最应该发言的 Agent 是？（只输出 Agent 名字，不要解释）
            """;

        var result = await _llm.CompleteAsync(prompt, cancellationToken: ct);
        return result.Message.Text.Trim();  // 如 "Reviewer"
    }
}

// 使用——传入一个轻量 LLM 做路由决策
var workflow = AgentWorkflowBuilder
    .CreateGroupChatBuilderWith(agents =>
        new DynamicManager(agents, routerLLM)
        {
            MaximumIterationCount = 8
        })
    .AddParticipants(writer, reviewer, researcher)
    .Build();
⚡ 选人策略的代价与选择：

策略实现方式额外延迟适用场景
固定轮转RoundRobin（默认）无固定流程：写→审→改→审
规则函数覆写 SelectNextAgentAsync，纯代码逻辑无条件明确：Writer 刚说完 → 一定是 Reviewer；Researcher 说完 → Writer
LLM 动态选人覆写 SelectNextAgentAsync，调用 LLM 做决策每次发言 +1 次 LLM 调用角色不确定：需根据对话内容判断该谁来

判断标准：如果发言顺序是确定性的（"A 说完一定是 B"），用规则函数——零额外成本。只有当顺序依赖对话内容（"用户问账单还是技术？"）时，才引入 LLM 做选人。

提示：如果"依赖对话内容决定谁来"是你的核心需求，Handoff 模式可能比 Group Chat 更合适——Handoff 的去中心化设计天然支持当前 Agent 自己判断该把对话交给谁（见下方挑战练习的进阶任务）。

Step 4: 运行并观察 Agent 间对话

执行 Workflow，你会看到两个 Agent 自动轮流发言——你不需要写任何切换逻辑：

using Microsoft.Extensions.AI;

// ——— 启动群聊 ———
var messages = new List<ChatMessage>
{
    new(ChatRole.User, "为一款环保电动 SUV 创作一个口号。")
};

Console.WriteLine("=== Writer + Reviewer 群聊开始 ===\n");

await using StreamingRun run = await InProcessExecution.RunStreamingAsync(workflow, messages);
await run.TrySendMessageAsync(new TurnToken(emitEvents: true));

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is AgentResponseUpdateEvent update)
    {
        AgentResponse response = update.AsResponse();
        foreach (ChatMessage message in response.Messages)
        {
            Console.WriteLine($"[{update.ExecutorId}]: {message.Text}\n");
        }
    }
    else if (evt is WorkflowOutputEvent output)
    {
        Console.WriteLine("=== 群聊结束 ===");
        break;
    }
}

对话过程（示意）：

[CopyWriter]: 「零碳驱动力」——体验电动出行的纯净力量。 [Reviewer]: "零碳驱动力"有记忆点，但缺少产品关联。建议加入 SUV 的空间感， 比如把"驱动力"换成一种空间或旅程的意象。请修改后重新提交。 [CopyWriter]: 「零碳征途」——SUV 的广阔，电动的纯净，一路向前。 [Reviewer]: 这次很好！"征途"兼顾了 SUV 的探险感和环保的使命感。 简洁、有冲击力、品牌契合度高。approve ✓ === 群聊结束 ===
🔬 这段代码在做什么？Workflow 执行 API 逐行拆解

和之前 await agent.RunAsync(...) 的简单模式不同——Workflow 是一个事件驱动的流式状态机。

① InProcessExecution.RunStreamingAsync(workflow, messages)
· 创建进程内执行宿主（MAF 还支持分布式执行，本课用进程内模式）
· 传入 Workflow 定义 + 初始消息，返回 StreamingRun 对象
· 此时 Workflow 还没开始跑——只是"装载"好了，等待你发令
· await using — StreamingRun 是 IAsyncDisposable，跑完自动释放资源

② TurnToken（回合令牌）
· Workflow 不会自己跑——你通过 TurnToken 驱动它
· new TurnToken(emitEvents: true) = "请执行下一个回合，并把详细事件发给我"
· 为什么这样设计？解耦——同一个 Workflow 定义可以由进程内代码驱动、也可以通过消息队列远程驱动、甚至由 UI 按钮手动触发。TurnToken 是统一的"请继续"信号
· TrySendMessageAsync 返回 bool——令牌被接受返回 true，Workflow 已终止则返回 false

③ WatchStreamAsync() → IAsyncEnumerable<WorkflowEvent>
· 返回一个异步事件流——事件到达时立即处理，不需要等全部执行完
· await foreach 每收到一个事件就迭代一次

④ 两种关键事件
事件类型含义关键属性
AgentResponseUpdateEvent某个 Agent 完成了一次发言ExecutorId（谁说的）、AsResponse()（说了什么）
WorkflowOutputEvent群聊终止——ShouldTerminateAsync 返回 true 或达到 MaximumIterationCount无额外数据，纯粹是终止信号

⑤ 完整数据流 
InProcessExecution.RunStreamingAsync(workflow, messages)
        │
        ▼
   StreamingRun（已装载，等待驱动）
        │
        │  TrySendMessageAsync(TurnToken)  ← 你发令
        ▼
   GroupChatManager 选择 Agent → Agent 推理 → 生成回复
        │
        ▼
   AgentResponseUpdateEvent ──→ WatchStreamAsync 的 await foreach
        │                              │
        │                              ▼
        │                       你打印到控制台
        ▼
   ShouldTerminateAsync 判断 → false → 下一轮
                             → true  → WorkflowOutputEvent → break
观察：你没有做的事情——
· 没有手动管理 ChatHistory——Workflow 自动同步所有 Agent 的上下文
· 没有写"下一个该谁发言"的判断逻辑——Manager 处理了
· 没有写"什么时候结束"的循环退出条件——ShouldTerminateAsync 处理了
· 没有手动把 Reviewer 的反馈传回 Writer——Workflow 的 Broadcast 机制自动做了

你只做了三件事：定义两个 Agent 的 Instructions → 选择 Manager → 启动 Workflow。

为什么又用回了 ChatMessage？

前几课用 AgentSession 时，对话历史对你透明——await agent.RunAsync("做个任务", session) 即可。 到了 Workflow 层，ChatMessage 重新浮出水面。这不是设计倒退——是多 Agent 状态下没有"一个 Session"能代表一切：

单 Agent（AgentSession）多 Agent（Workflow）
会话管理一个 Session 管一个 AgentWriter 有自己的 Session，Reviewer 有另一个，Manager 还持有广播记录——三条线交织
ChatHistory框架自动管理，对你透明ChatMessage 是 Agent 间的"通用货币"——Writer 的输出是 ChatMessage，Broadcast 给 Reviewer 的也是 ChatMessage，Manager 读 AuthorName 做路由判断读的还是 ChatMessage
多轮对话session 自动记住历史没有"WorkflowSession"——你需要自己维护 List<ChatMessage>（见下方多轮变体）

简化版：非流式 API（三行搞定）

课程选了流式 API（RunStreamingAsync + WatchStreamAsync）因为它最灵活——适合做实时 UI、适合观察 Agent 间对话过程。但如果你只想要「启动群聊，拿到最终结果」，非流式版本简单得多： 

// 非流式——三行搞定
await using var run = await InProcessExecution.RunAsync(workflow, messages);
await run.TrySendMessageAsync(TurnToken.CompletedTurn);
WorkflowResult result = run.GetResult();
// result.FinalOutput 就是最终结果
💡 两个 API 的选择：
· 流式（RunStreamingAsync）——你需要观察 Agent 间对话的过程（Writer 写了什么 → Reviewer 怎么反馈 → Writer 怎么改）。本课用它，因为多 Agent 场景下过程比结果更重要。
· 非流式（RunAsync）——你只需要最终结果。中间状态被吞掉，但代码量少。
· TurnToken.CompletedTurn 是一个预定义的"请一路执行到终止"令牌——不需要手动发令、不需要 await foreach。

await foreach (WorkflowEvent evt in run.WatchStreamAsync())
{
    if (evt is AgentResponseUpdateEvent update)
    {
        foreach (var msg in update.AsResponse().Messages)
            Console.WriteLine($"[{update.ExecutorId}]: {msg.Text}\n");
    }
    else if (evt is WorkflowOutputEvent)
        break;
}

Console.WriteLine("=== 结束 ===\n");

// ——— 自定义 Manager ———
public class ApprovalBasedManager : RoundRobinGroupChatManager
{
    private readonly string _approverName;
    public ApprovalBasedManager(IReadOnlyList<AIAgent> agents, string approverName)
        : base(agents) => _approverName = approverName;

    protected override ValueTask<bool> ShouldTerminateAsync(
        IReadOnlyList<ChatMessage> history, CancellationToken ct = default)
    {
        var last = history.LastOrDefault();
        return ValueTask.FromResult(
            last?.AuthorName == _approverName &&
            last.Text?.Contains("approve", StringComparison.OrdinalIgnoreCase) == true);
    }
}

变体：多轮对话（交互式）

上面的版本是"单轮"——用户输入一次，群聊跑完就结束。实际应用中，用户往往需要多轮追问（"第一版不错，但能不能加个英文副标题？"）。 多 Agent 场景下没有 WorkflowSession 帮你自动记住历史——你需要自己维护 List<ChatMessage>，每轮手动传入和追加： 

// ——— 替换 Program.cs 中的"交互循环"部分 ———

var history = new List<ChatMessage>();

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (string.IsNullOrWhiteSpace(input)) break;

    // ① 追加用户消息到历史
    history.Add(new ChatMessage(ChatRole.User, input));

    // ② 启动群聊——传入完整历史
    await using var run = await InProcessExecution.RunStreamingAsync(workflow, history);
    await run.TrySendMessageAsync(new TurnToken(emitEvents: true));

    // ③ 监听事件：打印并收集 Agent 发言
    await foreach (WorkflowEvent evt in run.WatchStreamAsync())
    {
        if (evt is AgentResponseUpdateEvent update)
        {
            foreach (var msg in update.AsResponse().Messages)
            {
                history.Add(msg);  // ← 塞回历史，下一轮 Agent 能看到
                Console.WriteLine($"[{update.ExecutorId}]: {msg.Text}\n");
            }
        }
        else if (evt is WorkflowOutputEvent)
        {
            Console.WriteLine("=== 本轮结束 ===\n");
            break;
        }
    }
}
🔑 关键就两步：
· 传入时带上 history——让新一轮 Workflow 知道之前聊了什么
· 结束时把 Agent 回复塞回 history——为下一轮做准备

虽然比单 Agent 的 session 模式多了一些样板代码，但逻辑透明——你知道历史的每一行是什么，没有魔法。

深入理解：多 Agent 的上下文同步

你可能有一个直觉性的担忧：Writer 和 Reviewer 各有各的 AgentSession——它们怎么看到同一段对话？

MAF 的 Broadcast 机制：

在 Group Chat 中，每个 Agent 拥有独立的 AgentSession（因为不同 Agent 类型可能有不同的 Session 实现）。但每次一个 Agent 发言后，GroupChatManager 会把它的回复广播到所有其他 Agent 的 Session——确保每个 Agent 在发言前都能看到完整对话历史。

这不只是"复制消息"—— 广播时 Manager 会决定哪些消息可见。你可以覆写 UpdateHistory 来过滤敏感信息——比如不让 Writer 看到 Reviewer 的某些内部评估标准。这给多 Agent 协作提供了信息隔离的能力：不是所有 Agent 都需要知道所有事。

什么时候不用多 Agent？

多 Agent 不是银弹——它有真实的代价：

① Token 消耗倍数增长。 每个 Agent 的每次发言都是独立的 LLM 调用。一个两 Agent 群聊跑 4 轮 = 8 次 LLM 调用。同一件事用一个 Agent 可能 2 次调用就完成了。

② 延迟累积。 Group Chat 是串行的——Agent A 发言 → Agent B 发言 → Agent A 再发言……每次都是完整的 LLM 推理。4 轮群聊的延迟可能是单 Agent 的 4 倍。

③ 指令漂移。 多轮群聊中，Agent 可能逐渐偏离原始任务。Writer 可能从"写口号"变成"解释为什么这个口号好"——它开始做 Reviewer 的活了。这是角色边界模糊化的信号。

判断标准——先问自己：「这件事用一个 Agent，在 Instructions 里分步骤描述，能做好吗？」如果能，就用单 Agent。只有当 Instructions 内部出现不可调和的角色冲突（生成 vs 审查、提问 vs 回答、教练 vs 裁判）时，才拆成多 Agent。

挑战练习

🛠️ 三个方向，按难度递进：

  1. （基础）添加第三个 Agent： 在 Writer + Reviewer 之间加一个 Researcher——负责在创作前收集与产品相关的市场数据或竞品信息。修改 Instructions，让群聊流程变成：Researcher → Writer → Reviewer → 通过/再改。
  2. （进阶）用 Handoff 实现客服分诊系统： 创建 TriageAgent（分诊）、BillingAgent（账单）、SupportAgent（技术支持）三个 Agent。用 AgentWorkflowBuilder.CreateHandoffsBuilderWith(triage) 构建 Handoff 流程——Triage 根据用户问题内容决定交给谁，专家 Agent 处理后交回 Triage 做满意度确认。
    参考：Handoff Orchestration 官方教程
  3. （高阶）对比单 Agent vs 多 Agent 的 token 效率： 同一个任务——「为环保电动 SUV 写一句口号并确保质量」——先让一个 Agent 做（自写自审），再让 Writer + Reviewer 群聊做。对比两个版本的：(a) 总 LLM 调用次数；(b) 总输出 token 数；(c) 最终口号的质量差异。写一段 200 字的分析，回答：「这个任务用多 Agent 值得吗？」
