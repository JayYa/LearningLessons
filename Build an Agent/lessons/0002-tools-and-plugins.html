Tools & Plugins：让 Agent 真正"做事"

从单一工具到多工具协作——理解 LLM 如何选择工具、提取参数、串联调用，并掌握工具设计五原则。

Lesson 01 的 Agent 少了什么？

在 Lesson 01 中，你构建的 TimeAssistant 只有一个工具——获取时间。它能做的事很有限。现实中的 Agent 需要多种工具：查数据库、调 API、读写文件、发邮件、执行代码……

但工具多了，新问题就出现了：

  • LLM 怎么知道该选哪个工具？
  • 工具需要参数——LLM 怎么从自然语言中提取参数？
  • 多个工具怎么串联完成一个任务？
  • 工具执行失败了——Agent 怎么优雅处理？

本课逐一回答这些问题，并让你构建一个拥有三个工具、能链式调用的 Agent。

心智模型：工具的解剖结构

在 Agent 的世界里，一个工具由四个部分组成。LLM 通过这四个部分来"理解"你的工具：

┌─────────────────────────────────────────────┐ │ TOOL / PLUGIN │ │ │ │ ① Name "save_note" │ │ ↓ │ │ ② Description "将文本保存到文件…" │ │ ↓ │ │ ③ Parameters filename: string │ │ content: string │ │ ↓ │ │ ④ Return "已保存到 note.txt，共 42 字符"│ │ Value (一个字符串) │ └─────────────────────────────────────────────┘

四个部分，各有职责

① Name（函数名）
LLM 用它做初步筛选。动词开头、描述性强——get_weather 比 f1 好 100 倍。LLM 通过函数名进行语义匹配，名字本身就是最重要的 Description。
② Description（描述）
这是 LLM 判断「该不该用这个工具」的唯一依据。要写清楚：工具做什么、什么时候该用它、什么时候不该用它、参数含义、返回格式。这不是给人看的注释——这是你和 LLM 之间的 API 契约。
③ Parameters（参数）
LLM 从用户的自然语言中提取参数值。用户说「把结果存到 result.txt」→ LLM 推断 filename="result.txt"。参数类型（string/int/bool/enum）帮助 LLM 做正确的值映射。
④ Return Value（返回值）
工具返回的内容会作为新的上下文拼入 LLM 的输入。所以返回值必须是人类可读的字符串——LLM 要能理解它、基于它做下一步推理。返回 JSON 也行，但你得在 Description 里告诉 LLM 怎么解读。

核心机制：LLM 如何选择工具

当你的 Agent 拥有多个工具时，LLM 在每个推理步骤都会面临一个选择题：

用户: "帮我把计算结果存到 result.txt" │ ▼ ┌──────────────────────────────────┐ │ 可用工具列表（序列化为 JSON） │ │ │ │ { name: "save_note", │ │ description: "将文本保存到…", │ │ parameters: { filename, │ │ content } } │ │ │ │ { name: "read_note", │ │ description: "读取文件…", │ │ parameters: { filename } } │ │ │ │ { name: "calculate", │ │ description: "计算数学…", │ │ parameters: { expression } } │ └──────────────────────────────────┘ │ ▼ ┌──────────────┐ │ LLM 推理 │ │ │ │ "用户想存结果 │ │ → 需要 save │ │ _note" │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ 输出 tool_call │ │ name:"save_ │ │ note" │ │ args:{ │ │ filename: │ │ "result.txt",│ │ content: │ │ "3588"} │ └──────────────┘

关键点：LLM 不执行代码——它只输出「我想调用 save_note，参数是这些」。框架（Semantic Kernel）截获这个请求，实际执行你的 C# 方法，然后把返回值拼回对话。

工具设计五原则

好的工具让 Agent 聪明；差的工具让 Agent 变成傻子。记住这五条：

原则 ①：名称即文档
用 verb_noun 格式，动词开头。get_weather、save_note、search_customer。
❌ f1、helper、do_stuff——LLM 完全猜不到这些是干什么的。
原则 ②：Description 是 API 契约
写清楚这五个要素：做什么（功能）、何时用（触发场景）、何时不要用（边界条件）、参数含义（每个参数填什么）、返回格式（返回值长什么样）。LLM 只能看到 Description，看不到你的 C# 代码。
好的 Description 示例见下方 Step 2 的代码。
🤔 追问：如果两个工具的 Description 很相似，LLM 会怎么选？

LLM 不做精确匹配，做的是语义相似度排序。Description 越相似，概率分布就越平——LLM 在两个工具之间会「犹豫」。比如用户说「把这个报告存到文件里」，同时存在 save_note（保存文本）和 save_report（保存报告），两者的语义匹配度可能非常接近（比如 0.61 vs 0.58），LLM 可能选错。

但核心问题不是 LLM 的选择算法——而是两个工具为什么需要相似到让 LLM 困惑的 Description。 如果人类开发者看你的 API 文档都会搞混，LLM 一样会搞混。这说明工具职责边界没划清楚。

解法：在 Description 里刻意制造差异。 同时写清楚「什么时候该用我」和「什么时候该用别的工具」：
❌ save_note: "保存文本到文件" / save_report: "保存报告到文件" → 太像
✅ save_note: "保存用户口述的零散文本为 .txt"  +  "如果要保存的是结构化报告，请使用 save_report 工具"
✅ save_report: "保存结构化报告为 .json"  +  "如果用户只是想存零散文本，请使用 save_note 工具"

另外，即使选错了也不必担心——原则 ④ 的兜底机制可以让工具返回错误提示并建议正确的工具，LLM 下一轮会自行修正。这也是为什么 Agent 开发里，工具设计质量 > LLM 推理能力。
原则 ③：一个工具只做一件事
不要写"保存或读取文件"的万能工具。拆成 save_note 和 read_note 两个。LLM 更容易选对，出错也更容易定位。
类比：REST API 的单一职责原则。
原则 ④：返回字符串，而非抛出异常
工具执行失败时，不要 throw——返回一个描述错误的字符串。LLM 会读到这个错误信息，并尝试换一种方式完成任务。
「文件不存在」比一个 500 Internal Server Error 有用 1000 倍——LLM 能读懂前者。
原则 ⑤：把参数类型作为隐式约束
LLM 会看你定义的参数类型（string、int、bool、enum）来推断该传什么值。如果是 enum，LLM 会从选项中选；如果是 int，LLM 会尝试提取数字。利用类型系统减少 LLM 的猜测空间。

动手构建：文件助手 Agent

现在构建一个拥有三个工具、能链式调用的 Agent——FileAssistant。 它能帮你做数学计算、保存结果到文件、再随时读回来。

本课产出： 一个 Agent，能根据自然语言请求自动选择工具（save / read / calculate），在多工具间切换，甚至串联多个工具完成一个复合任务。这是所有实用 Agent 的核心能力。

Step 1: 创建项目

dotnet new console -n FileAssistant
cd FileAssistant
dotnet add package Microsoft.SemanticKernel --prerelease
dotnet add package Microsoft.SemanticKernel.Agents.Core --prerelease

Step 2: 定义三个工具

创建 FilePlugin.cs——包含保存和读取两个工具：

using System.ComponentModel;
using Microsoft.SemanticKernel;

public class FilePlugin
{
    [KernelFunction("save_note")]
    [Description("将文本内容保存到文件中。" +
                 "filename: 要保存的文件名（不含路径，保存在当前目录）。" +
                 "content: 要写入文件的完整文本内容。" +
                 "使用场景：用户说「保存」「存起来」「记下来」「写到文件」等。" +
                 "注意：如果文件已存在会被覆盖。")]
    public string SaveNote(string filename, string content)
    {
        var path = Path.Combine(Directory.GetCurrentDirectory(), filename);
        File.WriteAllText(path, content);
        return $"已保存到 {filename}，共写入 {content.Length} 个字符。";
    }

    [KernelFunction("read_note")]
    [Description("读取之前用 save_note 保存的文件内容。" +
                 "filename: 要读取的文件名。" +
                 "使用场景：用户说「读取」「看看」「打开」「之前存的」等。" +
                 "注意：只能读取 save_note 创建的文件。如果文件不存在，返回错误提示而非崩溃。")]
    public string ReadNote(string filename)
    {
        var path = Path.Combine(Directory.GetCurrentDirectory(), filename);
        if (!File.Exists(path))
            return $"文件 {filename} 不存在。请确认文件名是否正确，或者是否已经保存过。";
        var content = File.ReadAllText(path);
        return $"—— {filename} 的内容 ——\n{content}\n—— 文件结束 ——";
    }
}

创建 CalculatorPlugin.cs——数学计算工具：

using System.ComponentModel;
using System.Data;
using Microsoft.SemanticKernel;

public class CalculatorPlugin
{
    [KernelFunction("calculate")]
    [Description("计算数学表达式的值。" +
                 "expression: 数学表达式字符串，如 '15 * 23'、'(100 + 50) / 3'。" +
                 "支持运算符：+ - * / % ^ 和括号 ()。" +
                 "使用场景：用户说「计算」「算一下」「等于多少」「求值」等。" +
                 "注意：仅支持纯数学运算，不能处理变量或复杂函数。计算失败时返回错误描述。")]
    public string Calculate(string expression)
    {
        try
        {
            var result = new DataTable().Compute(expression, null);
            return $"{expression} = {result}";
        }
        catch (Exception ex)
        {
            return $"计算「{expression}」时出错：{ex.Message}。请检查表达式格式是否正确。";
        }
    }
}
🔍 观察 Description 的写法： 每个 Description 都包含了功能说明 + 参数解释 + 使用场景 + 边界条件。LLM 通过阅读这一段文本来决定「用户说"存起来"→ 应该用 save_note」。如果你的 Description 只写"保存文件"四个字，LLM 在多个工具之间会犹豫不决——它没有足够的信息做判断。

Step 3: 创建 FileAssistant Agent

using System.ComponentModel;
using Microsoft.SemanticKernel;
using Microsoft.SemanticKernel.Agents;
using Microsoft.SemanticKernel.ChatCompletion;
using Microsoft.SemanticKernel.Connectors.OpenAI;

// ——— A：构建 Kernel + 接入 DeepSeek ———
var builder = Kernel.CreateBuilder();

// DeepSeek 兼容 OpenAI 协议
builder.AddOpenAIChatCompletion(
    "deepseek-v4-flash",
    new Uri("https://api.deepseek.com"),
    Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")!);

// 注册两个 Plugin 类——每个类里的 [KernelFunction] 方法自动成为工具
builder.Plugins.AddFromType<FilePlugin>();
builder.Plugins.AddFromType<CalculatorPlugin>();

Kernel kernel = builder.Build();

// ——— B：创建 Agent 并开启 Function Calling ———
var agent = new ChatCompletionAgent
{
    Kernel = kernel,
    Name = "FileAssistant",
    Instructions = """
        你是一个文件助手，可以帮助用户完成以下任务：
        - 计算数学表达式
        - 将文本内容保存到文件
        - 读取之前保存的文件内容

        工作原则：
        - 当用户要求「计算并保存」时，先调用 calculate 计算结果，
          再调用 save_note 保存结果。不要一步完成——先算再存。
        - 当用户要求读取文件时，先确认文件是否存在。
        - 当用户给出的文件名没有扩展名时，默认加上 .txt。
        - 用中文回复，简洁友好。
        - 如果工具返回了错误信息，分析原因并建议用户如何修正。
        """,
    Arguments = new KernelArguments(
        new OpenAIPromptExecutionSettings
        {
            FunctionChoiceBehavior = FunctionChoiceBehavior.Auto()
        })
};

// ——— C：对话循环 ———
var history = new ChatHistory();
Console.WriteLine("=== FileAssistant 已就绪 —— 3 个工具：计算 / 保存 / 读取 ===");
Console.WriteLine("输入 'exit' 退出\n");
Console.WriteLine("试试这些：");
Console.WriteLine("  · 帮我算一下 156 * 23 + 100");
Console.WriteLine("  · 把计算结果存到 result.txt");
Console.WriteLine("  · 帮我算 256 * 1024 并保存到 memory_size.txt");
Console.WriteLine("  · 读取 result.txt\n");

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (input?.ToLower() == "exit") break;

    history.AddUserMessage(input!);

    Console.Write("Agent: ");
    string agentResponse = "";
    await foreach (var item in agent.InvokeStreamingAsync(history))
    {
        string itemMessage = item.Message.Content!;
        Console.Write(itemMessage);
        agentResponse += itemMessage;
    }
    history.AddAssistantMessage(agentResponse);
    Console.WriteLine("\n");
}
📐 Instructions 设计的要点： 注意这里用了 Lesson 01 中学到的通用 Instructions 模式——告诉 Agent 工作原则而非具体流程。比如「当用户要求计算并保存时，先调用 calculate 再调用 save_note」是一条决策原则，不是硬编码的 if-else。Agent 会基于这条原则自行判断何时适用。

Step 4: 运行并测试

# PowerShell
$env:DEEPSEEK_API_KEY = "sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
dotnet run

发生了什么？—— 追踪一次链式调用

当你说「帮我算 156 × 23 并保存到 result.txt」时，Agent Loop 实际转了两圈：

  1. 第一轮推理：LLM 读取系统提示 + 用户请求 + 三个工具的 Definition。判断——「用户要计算 → 用 calculate 工具，参数 expression="156 * 23"」
  2. 框架拦截并执行：Semantic Kernel 截获 tool_call 请求，执行 CalculatorPlugin.Calculate("156 * 23")，返回 "156 * 23 = 3588"
  3. 结果回填：将 tool result（"156 * 23 = 3588"）作为一条 Tool 消息拼入对话上下文
  4. 第二轮推理：LLM 看到「用户要求保存」+「计算结果 = 3588」。判断——「用 save_note 工具，filename="result.txt"，content="156 * 23 = 3588"」
  5. 再次拦截执行：执行 FilePlugin.SaveNote("result.txt", "156 * 23 = 3588")
  6. 结果再次回填："已保存到 result.txt，共写入 18 个字符。"
  7. 第三轮推理：LLM 判断——「任务完成。生成最终回复。」→ "已经帮你算好了：156 × 23 = 3588，结果已保存到 result.txt。"
你刚刚见证的是 Agent 的核心超能力：不是一次调用一个工具——而是基于上一步的结果，自主决定下一步该调用哪个工具。这不是代码逻辑，是 LLM 在每一步重新推理。「计算→保存」的链式调用，和「读取→计算→保存→发邮件」的多步编排，底层是完全相同的机制——LLM 每次看到累积上下文，做出下一步决策。

深入理解：LLM 如何从自然语言中提取参数

这是最容易被低估的能力。看几个例子：

用户说： LLM 提取为： "保存到 hello.txt" → save_note( filename: "hello.txt", content: ??? → 问用户要内容) "算 15 乘以 23" → calculate( expression: "15 * 23") "把 3588 存起来" → save_note( filename: ??? → 可能问，可能用默认值 content: "3588") "读一下刚才那个文件" → read_note( filename: ??? → LLM 查对话历史，找到 之前提到的文件名 "result.txt")

关键洞察： LLM 不仅是"匹配"参数——它会在对话历史中搜索线索。第三个例子中，LLM 回顾上下文，找到之前提到的文件名 "result.txt"，自动填入参数。这种上下文感知能力使得 Agent 的对话体验非常自然——用户不需要精确指定每个参数。

放大看：expression 参数是谁生成的？

回到 CalculatorPlugin——你可能注意到它的参数是一个 string expression，不是两个 int。这个 expression 字符串完全是 LLM 自己生成的。完整链路：

用户: "帮我算 15 乘以 23" ↓ LLM 推理 LLM: 用户想计算 → 用 calculate 工具 calculate 需要 expression 参数（数学表达式字符串） "15 × 23" 翻译成数学表达式 → "15 * 23" ↓ 输出 tool_call tool_call: calculate(expression: "15 * 23") ↓ 框架执行 C# 代码 DataTable.Compute("15 * 23") → 345

LLM 做了"翻译"，不是"计算"。 LLM 不执行 15 * 23 的数学运算——它只负责把自然语言翻译成一个合法的表达式字符串。真正算出 345 的是你的 C# DataTable.Compute()。

更复杂的例子：用户说「一百五十六乘以二十三加一百」→ LLM 同时完成数字转换（中文→阿拉伯）、运算符翻译（"乘以"→*）、优先级保持，最终输出 expression: "156 * 23 + 100"。这不需要你写任何正则或 parser——LLM 的语言理解能力免费完成了这一切。

这也是为什么 Description 里写了 "如 '15 * 23'、'(100 + 50) / 3'"——它在教 LLM 应该输出什么格式。Agent 开发者常说「LLM 是最好的输入解析器」，就是这个意思。

拓展：参数只能用基础类型吗？

技术上支持复杂类型（class/struct）——Semantic Kernel 会通过反射将其序列化为嵌套的 JSON Schema，LLM 填好 JSON 后再反序列化回对象。链路是通的。

但实践中，越复杂的类型，LLM 填参准确率越低：

参数复杂度 LLM 准确率 string, int, bool ████████████████ ~95%+ enum ██████████████ ~90%（偶尔生成不存在的枚举值） string[] █████████████ ~85% 扁平 DTO（2-4 字段） ████████████ ~80% 嵌套对象（2 层+） ██████████ ~60-70%（字段名拼错、层级搞混） 嵌套 + 数组混合 ████████ <60%（不可靠）

核心问题： 每多一层嵌套，LLM 生成出错概率就递增。而出错的体验很差——用户说一句话，Agent 静默填错了某个嵌套字段，你很难排查。

实战建议——三个替代方案：

方案 A：拆成多个基础类型参数（首选）
不传 Search(SearchFilter filter)，而是 Search(string keyword, int maxResults = 10, string? category = null)。参数扁平化后，LLM 直接填基础值而非构造嵌套 JSON。准确率大幅提升。
这也是原则 ③（单一职责）的延伸——如果参数太多拆不平，说明这个工具做的事太多了。
方案 B：用 string 接收 JSON，C# 里自己解析
参数声明为 string filterJson，Description 里给出 JSON 格式示例。好处：如果 LLM 生成的 JSON 有问题，你可以在 C# 里 try/catch 并返回清晰的错误信息——LLM 看到报错可能自行修正（原则 ④ 的延伸）。
方案 C：多个小工具代替一个大工具
用 search_by_keyword(kw) + search_by_category(cat, maxResults) 代替一个万能的 search(kw, cat, max, sortBy, filter, …)。工具越聚焦，参数越简单。

底线： 能用基础类型就不用 DTO，能拆参数就不嵌套，能拆工具就不堆参数。这和 REST API 设计是同一逻辑——好的 API 签名扁而窄，差的 API 深而宽。LLM 就是你的 API 消费者。

⚠️ 注意：参数提取不是 100% 可靠。 LLM 可能猜错参数值，特别是在歧义情况下。对于关键操作（如删除、发送），建议让 Agent 先确认参数再执行。这个设计模式会在后续课程中详细展开。
