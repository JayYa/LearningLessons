MAF 迁移桥梁：从 Semantic Kernel 到 Microsoft Agent Framework

你已经理解了 Agent 的所有核心概念——这一课只做一件事：把你知道的 SK 写法映射到 MAF。

MAF v1.0 AIAgent IChatClient AIFunctionFactory AgentSession SK→MAF C#

为什么现在迁？

2026 年 4 月 3 日，Microsoft Agent Framework (MAF) v1.0 正式 GA。它不是 Semantic Kernel 的"下一个版本"——它是 AutoGen 和 Semantic Kernel 两支团队合并后的统一框架。

Semantic Kernel (2023–2026) AutoGen (2023–2026) \ / \ / Microsoft Agent Framework v1.0 (2026.4 GA) | 统一 Agent 抽象、多模型中立、原生 Multi-Agent

回顾：AutoGen 是什么？

如果你来自 Python 生态，可能对 Semantic Kernel 不熟，但听说过 AutoGen。它是微软研究院（Microsoft Research）2023 年推出的多智能体对话框架，核心概念是让多个 Agent 像团队一样互相聊天、分工、交接任务。

SK vs AutoGen 的原始分工：
· Semantic Kernel（Azure AI 团队）：单 Agent + 插件编排——「如何让一个 Agent 调用工具完成任务？」
· AutoGen（Microsoft Research）：多 Agent 协作——「如何让多个 Agent 互相聊天、分工、交接任务？」

AutoGen 贡献给 MAF 的关键能力：AgentGroupChat（多 Agent 群聊）、Handoff（Agent 间交接）、SelectionStrategy（框架自动判断下一轮该让谁发言）。这些就是 Lesson 06 要讲的内容。

对学习者意味着什么？前四节课你用 SK 看到了 Agent 的「骨头」——手动管理 Kernel、Plugin、ChatHistory。这些概念 100% 通用。MAF 只是换了 API 语法和结构，概念体系不变。

你在用最有效的学习路径： SK 教了你 Agent 内部怎么运转（底层），MAF 教你怎么在生产中构建 Agent（工程化）。两者不是竞争关系——是教学上的前后衔接。

本课产出： 把 Lesson 03 的 MemoryAssistant 用 MAF 重写一遍。同一个 Agent、同一个概念、不同的 API——对比中理解 MAF 的设计哲学。

心智模型：五层架构

MAF 是一个五层架构——你写的 Agent 在 L4，底层 L1-L3 对你是透明的：

┌────────────────────────────────────────────────────────┐ │ L5 Workflow & Orchestration │ │ ┌──────────────────────────────────────────┐ │ │ L4 │ AIAgent — 你的 Agent（这一层是你的代码） │ │ │ └──────────────────────────────────────────┘ │ │ L3 Semantic Kernel (插件、过滤器、Prompt 模板) │ │ L2 IChatClient / IEmbeddingGenerator (MEAI 抽象) │ │ L1 Service Connectors (OpenAI / Claude / Gemini) │ └────────────────────────────────────────────────────────┘ 你在 SK 里做的事分布在 L3+L4。在 MAF 里，L3 退到幕后， L2 的 IChatClient 是新的「模型中立方」。

注意 L3 仍然存在——Semantic Kernel 变成了 MAF 的内部依赖，提供 Plugin、Filter、Prompt Template 等能力。但你不需要显式构建 Kernel 了。MAF 把 SK 从"你关心的东西"变成了"框架自己用的东西"。

SK → MAF：六个核心映射

你已知的每一个 SK 概念在 MAF 中都有直接对应。先看这张表，然后逐个写代码验证：

你关心的Semantic Kernel (前 4 课)MAF v1.0 (本课起)
① 模型接入 Kernel.CreateBuilder().AddOpenAIChatCompletion(model, endpoint, key) new OpenAIClient(key).GetChatClient(model).AsIChatClient()
② Agent 创建 new ChatCompletionAgent { Kernel, Name, Instructions } chatClient.AsAIAgent(name, instructions, tools)
③ 工具定义 [KernelFunction("name")][Description("desc")] 写在 Plugin 类里 [Description("desc")] 写在方法上，用 AIFunctionFactory.Create(method) 注册
④ 工具注册 builder.Plugins.AddFromType<MyPlugin>() AsAIAgent(tools: [AIFunctionFactory.Create(Method)]) ——扁平数组，无 Plugin 层级
⑤ 对话历史 new ChatHistory() + 手动 AddUserMessage / AddAssistantMessage await agent.CreateSessionAsync() ——自动管理，你不需要碰历史
⑥ 调用方法 agent.InvokeAsync(history) / .InvokeStreamingAsync(history) agent.RunAsync(prompt, session) / .RunStreamingAsync(prompt, session)
最关键的三个变化：
① 没有 Kernel 了——模型接入通过 IChatClient，一个纯接口
② 没有 Plugin 层级了——工具直接以 AIFunction 数组注入 Agent，没有 Kernel → Plugin → Function 三级嵌套
③ 手动 ChatHistory → 自动 AgentSession——这是最大的工程改进。你不再需要 history.AddUserMessage(input)、history.AddAssistantMessage(response) 这种样板代码

🔍 变化观察：
· 少了一个 Attribute——MAF 不需要 [KernelFunction("remember")]，只需要 [Description]
· 少了一个 using——不需要 using Microsoft.SemanticKernel
· 方法的签名、逻辑、返回类型完全不变——工具本身不感知框架差异
· 去掉了 [return: Description]——MAF 目前不看返回值的 Description（方法的 Description 描述整体功能就够了）

完整的 MemoryPlugin（三个方法）：

using System.ComponentModel;

public class MemoryPlugin
{
    private readonly Dictionary<string, string> _store = new();

    [Description("存储信息到长期记忆。" +
                 "key: 记忆的唯一标识。info: 要存储的信息内容。")]
    public string Remember(string key, string info)
    {
        _store[key] = info;
        return $"已记住 [{key}]: {info}";
    }

    [Description("从长期记忆中检索信息。" +
                 "key: 要检索的记忆标识。")]
    public string Recall(string key)
    {
        if (_store.TryGetValue(key, out var info))
            return $"回忆 [{key}]: {info}";
        return $"没有找到 key=\"${key}\" 的记忆。";
    }

    [Description("列出所有已存储的记忆键和内容。")]
    public string ListMemories()
    {
        if (_store.Count == 0)
            return "当前没有任何记忆。";

        var items = _store.Select(kv => $"  [{kv.Key}] {kv.Value}");
        return $"共 {_store.Count} 条记忆:\n" + string.Join("\n", items);
    }
}

Step 3: 创建 Agent + 注册工具

这是 MAF 和 SK 差异最大的部分——Agent 创建和工具注册：

using System.ComponentModel;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;
using OpenAI;

// ——— A：接入 DeepSeek（OpenAI 兼容协议）———
var apiKey = Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")
    ?? throw new InvalidOperationException("请设置 DEEPSEEK_API_KEY 环境变量");

var openAIClient = new OpenAIClient(
    new System.ClientModel.ApiKeyCredential(apiKey),
    new OpenAIClientOptions
    {
        Endpoint = new Uri("https://api.deepseek.com/v1")
    });

// IChatClient 是 MAF 的模型抽象层——任何兼容 OpenAI 协议的模型都通过它接入
var chatClient = openAIClient
    .GetChatClient("deepseek-v4-flash")
    .AsIChatClient();

// ——— B：创建工具 ———
var memory = new MemoryPlugin();
var tools = new[]
{
    AIFunctionFactory.Create(memory.Remember),
    AIFunctionFactory.Create(memory.Recall),
    AIFunctionFactory.Create(memory.ListMemories),
};

// ——— C：创建 Agent ———
var agent = chatClient.AsAIAgent(
    name: "MemoryAssistant",
    instructions: """
        你是一个带记忆功能的助手。
        每次对话开始时，先使用 list_memories 检查是否有过去的记忆。
        当用户分享信息或偏好时，用 remember 存储。
        当用户问到过去的事情时，用 recall 检索。
        用中文回复，简洁友好。
        """,
    tools: tools
);
💡 和 SK 的核心差异——三重简化：

扁平注册： SK 是 Plugin 类 → Kernel → Agent 三层嵌套。MAF 是「方法 → AIFunction → Agent 数组」——一级扁平。你不再需要把一个类标记为 Plugin 然后注册到 Kernel，直接 AIFunctionFactory.Create(方法) 就完了。

一行配好模型： SK 需要 Kernel.CreateBuilder().AddOpenAIChatCompletion(...).Build() 三步链式调用 + 单独的 KernelArguments 配置 Function Calling 行为。MAF 只用「创建 OpenAI 客户端 → 包装 IChatClient → 传给 Agent」——模型、端点、API Key 一次性解决。

无显式 Function Calling 配置： 在 SK 中你需要 new OpenAIPromptExecutionSettings { FunctionChoiceBehavior = ... }。在 MAF 中，只要传了 tools 数组，Agent 自动启用 Function Calling——不需要额外配置。

对接不同模型：三行差异

上面的代码用 DeepSeek（OpenAI 兼容协议）接入。但 MAF 的 IChatClient 抽象意味着——换模型只需要改创建 IChatClient 的那三行，Agent 创建、工具注册、Session 管理的代码完全不变。

模型NuGet 包创建 IChatClient（仅这三行不同）IChatClient 来源
DeepSeek / OpenAI OpenAI (v2+) new OpenAIClient(key).GetChatClient(model).AsIChatClient() OpenAI SDK + 微软适配器扩展
Claude / Anthropic Anthropic (v10+) new AnthropicClient().AsIChatClient(model) Anthropic 官方 SDK 原生实现——不需要适配器
Ollama（本地） Ollama (社区) new OllamaChatClient(endpoint, model) 社区包直接实现 IChatClient

进阶：生产级工具注册 —— 用依赖注入替代 new

课上代码用 new MemoryPlugin() 直接创建是为了教学简洁。但在真实项目中，你的工具类迟早需要依赖——数据库连接、ILogger、IMemoryStore 接口等。届时 new 就行不通了。MAF 提供了两种 DI 模式来应对。

模式一：构造注入（适合有状态、可长期复用的工具）

把 Plugin 注册到 DI 容器，在构造函数里声明它需要的依赖：

// ——— DI 注册（Program.cs / Startup）———
builder.Services.AddSingleton<IMemoryStore, SqliteMemoryStore>();
builder.Services.AddSingleton<MemoryPlugin>();  // 它的构造函数可以要 DI 里的任何东西
builder.Services.AddSingleton<AIAgent>(sp => {
    var chatClient = sp.GetRequiredService<IChatClient>();
    var plugin = sp.GetRequiredService<MemoryPlugin>();
    return chatClient.AsAIAgent(
        instructions: "...",
        tools: [
            AIFunctionFactory.Create(plugin.Remember),
            AIFunctionFactory.Create(plugin.Recall),
            AIFunctionFactory.Create(plugin.ListMemories),
        ]);
});

// ——— Plugin 类 ———
public class MemoryPlugin(IMemoryStore store, ILogger<MemoryPlugin> logger)
{
    [Description("存储信息到长期记忆。")]
    public string Remember(string key, string info)
    {
        logger.LogInformation("Storing {Key}", key);
        store.Set(key, info);       // ← 真正的持久化，不是 Dictionary
        return $"已记住 [{key}]";
    }
}

注意——AIFunctionFactory.Create(plugin.Remember) 那三行完全不变。DI 帮你换了 Plugin 的依赖实现，但 Agent 的创建代码不需要感知。

模式二：IServiceProvider 参数注入（适合需要按次解析的服务）

在工具方法签名里加 IServiceProvider 参数——MAF 调用时自动注入，LLM 看不到这个参数：

public class MemoryPlugin
{
    // IServiceProvider 不出现在 LLM 看到的 function schema 里
    // LLM 只知道 key: string, info: string
    [Description("存储信息到长期记忆。")]
    public string Remember(string key, string info, IServiceProvider services)
    {
        var store = services.GetRequiredService<IMemoryStore>();
        store.Set(key, info);
        return $"已记住 [{key}]";
    }
}

// 把 IServiceProvider 传给 Agent
var agent = chatClient.AsAIAgent(
    instructions: "...",
    tools: [...],
    services: app.Services);  // ← 整个 DI 容器传入
核心区分：
· string key, string info → LLM 提供的（不可信输入）
· IServiceProvider services → 框架注入的（可信应用依赖）
· CancellationToken cancellationToken → 框架注入的（超时控制）

MAF 的 schema 生成会自动跳过 IServiceProvider 和 CancellationToken 类型的参数，确保 LLM 看到的函数签名只包含它应该关心的参数。

Step 4: 多轮对话——AgentSession 替代 ChatHistory

这是你作为开发者最直接的体感变化：

SK（手动管理历史）MAF（自动管理 Session）
var history = new ChatHistory();

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (input == "exit") break;

    // 手动添加用户消息
    history.AddUserMessage(input);

    Console.Write("Agent: ");
    await foreach (var item in
        agent.InvokeStreamingAsync(history))
    {
        Console.Write(item.Message.Content);
    }
    // 手动添加助手消息
    history.AddAssistantMessage(response);
    Console.WriteLine("\n");
}
 
// 创建一个 Session —— 历史自动管理
var session = await agent.CreateSessionAsync();

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (input == "exit") break;

    Console.Write("Agent: ");
    await foreach (var update in
        agent.RunStreamingAsync(input, session))
    {
        Console.Write(update.Text);
    }
    Console.WriteLine("\n");
}
观察：少了两行关键代码。 在 SK 中，你每次对话必须手动 history.AddUserMessage(input) 和 history.AddAssistantMessage(response)——漏掉一行，LLM 就看不到之前的对话。MAF 的 AgentSession 在 RunStreamingAsync 内部自动记录每一轮——你只需要把 session 传进去。

对比 Lesson 03 的"失忆"问题： Lesson 03 中 Agent 在长对话中"忘记"初始目标，根因是 ChatHistory 膨胀到了上下文窗口上限。MAF 的 Session 在此基础上提供了内置的序列化支持——session 可以保存到磁盘、恢复、甚至在应用重启后继续： 
// 保存 session 到磁盘
var serialized = agent.SerializeSession(session);
File.WriteAllText("session.json", serialized);

// 下次运行时恢复
var saved = File.ReadAllText("session.json");
var resumed = await agent.DeserializeSessionAsync(saved);
var response = await agent.RunAsync("上次我们聊到哪了？", resumed);

序列化格式：JSON，不是 JSONL

SerializeSession(session) 返回一个普通 JSON 字符串（用 System.Text.Json 生成），不是 JSONL。里面包含两个东西：

  • ConversationId —— 会话的唯一标识
  • StateBag —— 一个字典，装着所有状态：ChatHistoryProvider 写入的对话历史、工具调用记录、workflow 检查点等

你可以把它直接存成 .json 文件，用任何 JSON 工具打开查看。想读里面的具体消息？交给 DeserializeSessionAsync 就行——你不需要手动解析 StateBag 的内部结构。

💡 为什么不是直接读写文件，还要开发者手动 File.WriteAllText？

这是 .NET 的设计惯例：库负责数据转换，应用负责 I/O。SerializeSession 像 ToString()——它把对象变成可传输的字符串。存在哪、怎么存、要不要压缩——这些是你的应用架构决策，框架不该替你做。

如果 API 直接写成 SaveToFile(path)，那想存到数据库、Redis、消息队列、Blob 存储的场景就会被阻塞。返回 string 意味着：

File.WriteAllText("session.json", serialized) —— 本地文件
await db.InsertAsync(new Row { Data = serialized }) —— SQL 数据库
await redis.SetAsync("session:42", serialized) —— Redis 缓存
await blob.UploadAsync(serialized) —— Azure Blob

框架不知道你的应用跑在服务器还是客户端、有没有文件系统权限——所以它只做序列化，I/O 留给你。这也让单元测试更简单：断言字符串内容不需要创建临时文件。

Step 5: 完整 Program.cs

将以上内容组装成完整的交互式 Agent：

using System.ComponentModel;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;
using OpenAI;

// ——— MemoryPlugin（同 Step 2）———
var memory = new MemoryPlugin();

// ——— 模型接入（DeepSeek）———
var apiKey = Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")!;
var openAIClient = new OpenAIClient(
    new System.ClientModel.ApiKeyCredential(apiKey),
    new OpenAIClientOptions { Endpoint = new Uri("https://api.deepseek.com/v1") });

var chatClient = openAIClient
    .GetChatClient("deepseek-v4-flash")
    .AsIChatClient();

// ——— 创建 Agent ———
var agent = chatClient.AsAIAgent(
    name: "MemoryAssistant",
    instructions: """
        你是一个带记忆功能的助手。
        每次对话开始时，先用 list_memories 检查是否有过去的记忆。
        当用户分享信息或偏好时，用 remember 存储。
        当用户问到过去的事情时，用 recall 检索。
        用中文回复，简洁友好。
        """,
    tools: [
        AIFunctionFactory.Create(memory.Remember),
        AIFunctionFactory.Create(memory.Recall),
        AIFunctionFactory.Create(memory.ListMemories),
    ]);

// ——— 对话循环 ———
var session = await agent.CreateSessionAsync();
Console.WriteLine("=== MAF MemoryAssistant 已就绪 ===\n");

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (input?.ToLower() == "exit") break;

    Console.Write("Agent: ");
    await foreach (var update in agent.RunStreamingAsync(input!, session))
    {
        Console.Write(update.Text);
    }
    Console.WriteLine("\n");
}

// ——— MemoryPlugin 类 ———
public class MemoryPlugin
{
    private readonly Dictionary<string, string> _store = new();

    [Description("存储信息到长期记忆。key: 记忆的唯一标识。info: 要存储的信息内容。")]
    public string Remember(string key, string info)
    {
        _store[key] = info;
        return $"已记住 [{key}]: {info}";
    }

    [Description("从长期记忆中检索信息。key: 要检索的记忆标识。")]
    public string Recall(string key)
    {
        if (_store.TryGetValue(key, out var info))
            return $"回忆 [{key}]: {info}";
        return $"没有找到 key=\"{key}\" 的记忆。";
    }

    [Description("列出所有已存储的记忆键和内容。")]
    public string ListMemories()
    {
        if (_store.Count == 0) return "当前没有任何记忆。";
        var items = _store.Select(kv => $"  [{kv.Key}] {kv.Value}");
        return $"共 {_store.Count} 条记忆:\n" + string.Join("\n", items);
    }
}

深入理解：Kernel 去哪了？

你可能会问——SK 时代的 Kernel 是 Agent 的心脏，MAF 里它消失了，那 Plugin、Filter、Prompt Template 这些能力怎么办？

Kernel 没有消失——它变成了框架的内部实现细节。 回忆 MAF 五层架构：L3 仍然是 Semantic Kernel，但 MAF 把它包裹在了 L4 的 AIAgent 下面。你不再需要显式创建 Kernel，因为 chatClient.AsAIAgent(...) 内部自动完成了这些。

这意味着：
· 基本场景（90%）：你只需要 AIAgent + tools + AgentSession——足够了
· 高级场景（10%）：如果将来 Kernel 的高级特性（如 Filter 管道、Prompt Template 引擎）对你有用，MAF 允许你通过 ChatClientAgentOptions 暴露底层的 SK Kernel，按需深度定制

这正是"渐进式抽象"——默认路径极简，深度路径不走弯路。

深入理解：L1/L2 是行业合作标准，还是微软单方面兼容？

这个问题直接关系到你在生产中选择 MAF 的技术风险评估。答案是分层的——而且有一个反直觉的细节。

层级是什么谁主导合作程度
L2 IChatClient .NET 生态的 AI 统一抽象接口（MEAI） 微软主导，开源 非跨行业标准，但已是 .NET 生态的事实标准
L1 Service Connectors 各厂商的 .NET SDK + MEAI 适配器 各供应商独立维护 取决于供应商态度——差异很大
MCP（不在 MAF 层，但相关） 模型上下文协议——标准化工具/资源交互 微软 + Anthropic 共同推动 真正的跨行业合作标准

一个反直觉的事实

OpenAI 的官方 .NET SDK 并不原生实现 IChatClient——你需要通过微软提供的 Microsoft.Extensions.AI.OpenAI 适配器包，调用 .AsIChatClient() 扩展方法来桥接。而 Anthropic 的官方 .NET SDK 原生实现了 IChatClient——不需要适配器。

讽刺之处：作为微软"亲儿子"的 OpenAI SDK 反而不原生实现微软自己的抽象标准，Anthropic 却率先原生支持。这意味着 IChatClient 并非微软自嗨——外部厂商愿意直接实现它，降低了它变成「仅微软生态内可用」的风险。

兼容性与更新延迟风险

风险来自两级依赖链：

模型厂商发布新 API 功能 → 厂商 .NET SDK 更新（第一级延迟） → MEAI 适配器更新（第二级延迟） → MAF 框架更新（第三级延迟）
风险严重程度说明
新模型参数不支持 中 如果 OpenAI 推出新参数（如新的 response_format），需要等 SDK → 适配器 → MAF 三级更新
API 废弃 / breaking change 低 Azure OpenAI 也是 MAF 的核心场景，微软有动力快速适配
非主流模型支持慢 高 OpenAI/Azure 优先级最高，Anthropic 次之，Ollama 等靠社区
流式/工具调用行为差异 中 不同模型的 Function Calling 语义不同，适配器可能掩盖不了所有差异

三重缓冲机制

① IChatClient 是接口，不是框架。 你随时可以绕过微软适配器，自己实现 IChatClient 对接任何模型——接口就几个方法，手写也不难。

② MAF 不限制 IChatClient 来源。 如果适配器滞后，你不需要等 MAF 更新——你只需要一个实现了 IChatClient 的客户端，直接传给 AsAIAgent()。

③ Anthropic 的原生支持是积极信号。 外部厂商愿意直接实现 IChatClient 而不是依赖微软适配器，说明这个接口有生态生命力。

Planning 在 MAF 中怎么实现？

同样的事情。 你在 Lesson 04 中学到的核心洞察——规划策略是 Instructions 的延伸，不是独立组件的职责——在 MAF 中完全不变。

想用 ReAct？在 instructions 参数里写清楚 Thought/Action/Observation 格式。
想用 Plan-and-Execute？写两段 Instructions——一段给 Planner，一段给 Executor。

唯一的差异是语法：Agent 创建方式从 new ChatCompletionAgent { Instructions = "..." } 变成了 chatClient.AsAIAgent(instructions: "...")，工具注册从 [KernelFunction] 变成了 [Description] + AIFunctionFactory.Create()。Instruction 仍然是 Agent 行为的唯一可编程接口。（见 学习记录 0008）
