Memory & Context：让 Agent 不再"失忆"

从对话历史到长期记忆——理解上下文窗口的限制，掌握三种记忆管理策略，并构建一个能跨会话记住信息的 Agent。

FileAssistant 藏了一个 bug

你在 Lesson 02 构建的 FileAssistant 工作得很好——但有一个隐藏的定时炸弹。试试这个场景：

  1. 连续和它对话 50 轮
  2. 每次让它计算不同的表达式并保存到不同文件
  3. 到第 51 轮，问它「我们第一轮算的是什么？」

会发生什么？取决于模型和上下文窗口大小，可能出现三件事之一：

第 51 轮时 ChatHistory 里塞了： System Prompt (~200 tokens) + 第 1 轮: 用户消息 + tool_call + tool_result + Agent 回复 (~200 tokens) + 第 2 轮: ... (~200 tokens) + ... + 第 50 轮: ... (~200 tokens) ───────────────────────────────── = 200 + 50 × 200 = ~10,200 tokens 如果上下文窗口是 8K → 💥 最早的消息被截断，Agent "失忆"

这就是 上下文窗口（Context Window）——LLM 一次能"看到"的最大 token 数量。ChatHistory 会无限增长，但窗口是固定的。超出窗口的消息会被截断，Agent 就会"忘记"早期的对话。

🔍 "截断"的精确含义：FIFO，但有细节

最朴素的实现确实是按消息顺序先进先出（FIFO）——最早的消息最先被丢弃，和排队一样：

[Msg1] [Msg2] [Msg3] … [Msg99] [Msg100]
 ↑ 最先被丢弃         ↑ 最新，保留

伪代码就是：
while (history.EstimateTokens() > maxTokens)
  {
      history.RemoveAt(0);  // 删第一条 → FIFO
  }
但实际框架比这精细，关键区别在三个维度：

① System Prompt 不参与 FIFO： Instructions 是 Agent 的"身份"，截断时永远保留。只删对话消息，不动系统提示。如果你有 200 tokens 的 System Prompt 和 8K 窗口，对话消息只能用 7.8K。

② 截断粒度不同：
粒度做法风险
消息级整条消息为单位丢弃可能丢弃包含关键 tool_call 结果的短消息
Token 级按 token 数精确切割可能截断最后一条消息——tool_call JSON 被截半 → 解析报错 💥

大多数生产级框架（包括 Semantic Kernel）用消息级截断——它安全，不会产生格式损坏的消息。

③ FIFO 的致命缺陷： 它不管内容是"今天天气真好"还是"我的银行账号是 XXX"，一律按时间顺序丢弃。这就是为什么需要策略二（摘要）和策略三（RAG）——保护关键信息不被 FIFO 吞掉。
核心矛盾： 对话越长 → ChatHistory 越大 → 越接近上下文窗口上限 → Agent 越容易失忆。每一条新消息都在把最老的记忆推出窗口。这不是 bug——这是 LLM 的物理定律。

心智模型：Agent 的"记忆系统"

回到 Lesson 01 中 Agent 的四组件——Memory 就是其中之一。但"记忆"不是一块铁板，它分三层：

┌──────────────────────────────────────────────────────────┐ │ AGENT MEMORY SYSTEM │ │ │ │ ┌─────────────────────────────────────────────────┐ │ │ │ ① WORKING MEMORY (Short-term) │ │ │ │ = ChatHistory │ │ │ │ 自动记录所有对话消息 │ │ │ │ ⚠ 有 Token 上限——超出窗口的部分会被截断 │ │ │ │ ⚡ 速度：即时（在 LLM 输入里） │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ │ ┌──────────┴──────────┐ │ │ ▼ ▼ │ │ ┌──────────────────────┐ ┌──────────────────────┐ │ │ │ ② EXPLICIT MEMORY │ │ ③ VECTOR MEMORY │ │ │ │ (Long-term, 文件) │ │ (Long-term, RAG) │ │ │ │ │ │ │ │ │ │ Agent 主动调用 │ │ 嵌入 → 向量库 │ │ │ │ remember/recall │ │ 语义检索 → Top-K │ │ │ │ 存到 JSON 文件 │ │ 注入 Prompt │ │ │ │ │ │ │ │ │ │ ⚡ 速度：毫秒 │ │ ⚡ 速度：毫秒~几十ms │ │ │ │ 📦 容量：MB~GB │ │ 📦 容量：无限 │ │ │ │ 🔍 检索：精确匹配 │ │ 🔍 检索：语义相似 │ │ │ └──────────────────────┘ └──────────────────────┘ │ └──────────────────────────────────────────────────────────┘

三层记忆，各有用途

① Working Memory — ChatHistory（工作记忆）
你已经在用了——每次 history.Add() 和 agent.InvokeStreamingAsync(history) 就是工作记忆。它自动记录所有对话，LLM 在每次推理时都能看到。
局限： Token 有上限。DeepSeek V3 是 128K，Claude Sonnet 是 200K——看起来很大，但如果你每条消息 200 tokens、聊 500 轮，128K 也满了。
② Explicit Memory — 显式记忆（本课重点）
Agent 主动调用工具来存储和检索信息。就像人类「用笔记记住重要的事」——Agent 判断哪些信息值得长期保存，调用 remember 工具存下来，以后用 recall 工具取回。
优势： 不受上下文窗口限制，跨会话持久化。Agent 重启后还能"记得"。
③ Vector Memory — 向量记忆（后续课程）
将所有记忆转换成向量（embeddings），存入向量数据库。检索时用语义相似度而非关键词匹配——「天气不错」能匹配到「今天阳光明媚」。这就是 RAG（检索增强生成）的核心。
本课只讲概念，实战放在后续课程。

核心机制：上下文窗口是"记忆预算"

把上下文窗口想象成一个固定大小的桌子。你可以在桌上放文件（消息），但桌面就那么大。放新文件时，最旧的文件会被挤下去。

Token 怎么算？

粗略估算（实际因模型而异）： 英文：~1 token ≈ 0.75 个单词 ≈ 4 个字符 中文：~1 token ≈ 1-2 个汉字 ≈ 2-4 个字符 代码：~1 token ≈ 3-4 个字符（运算符和标点各占 1 token） 示例： "Hello, how are you?" → ~6 tokens "你好，最近怎么样？" → ~8 tokens "var x = 42;" → ~7 tokens
📐 精确计数： 粗略估算够用于设计，但生产环境应使用模型专属的 tokenizer（如 tiktoken for OpenAI, claude-tokenizer for Anthropic）。SK 中没有内置 token 计数，你可以用 Microsoft.ML.Tokenizers NuGet 包。

三种管理策略

策略一：Sliding Window（滑动窗口，即 FIFO）——最简单
只保留最近 N 条消息，老消息按时间顺序（FIFO）直接丢弃——详见上文截断机制详解。
这是大多数框架（包括 Semantic Kernel）的默认行为，使用消息级截断（整条消息为单位，System Prompt 除外）。
✅ 简单、确定、零成本
❌ 丢掉的可能是关键信息。Agent 突然"忘记"你 10 分钟前说过的话。
❌ 不管内容重要性，一律按时间顺序丢弃——"我的银行卡号"和"今天天气真好"同等对待。
适用场景：短期任务型 Agent（如单次数据分析），不需要跨轮记忆。
策略二：Summarization（摘要压缩）——本课实现
当 ChatHistory 接近窗口上限时，让 LLM 将老消息总结成一段摘要，用摘要替代原始消息。
✅ 保留关键信息的"大意"，压缩比 10:1 以上
❌ 细节会丢失（摘要不是原文），多一次 LLM 调用（有成本和延迟）
适用场景：长对话 Agent（客服、辅导、项目协作），需要记住"聊过什么"但不需要逐字回忆。
策略三：RAG with Vector Search（向量检索）——最强大
将所有记忆编码为向量存入向量库。每次 LLM 推理前，用当前问题做语义检索，只把最相关的 Top-K 条记忆注入 Prompt。
✅ 容量无限，按需检索，语义匹配
❌ 需要向量数据库（Qdrant / Milvus / pgvector），需要 embedding 模型，架构复杂度高
适用场景：知识库 Agent、客服系统、企业级 Agent 产品。
实际工程中通常是组合使用： 近期对话用 ChatHistory（策略一 + 二），历史知识用 RAG（策略三）。本节教你实现策略二。

动手构建：有记忆的 Agent

现在构建一个 MemoryAssistant——它不仅能计算和保存文件，还能记住你告诉它的事实，并在之后的对话中主动回想。即使关闭程序重新启动，它仍然"记得"之前的事。

本课产出： 一个 Agent，具备显式长期记忆——能通过 remember / recall 工具存储和检索信息，数据持久化到 JSON 文件。这是从"单次对话工具"到"持续陪伴助手"的关键跃迁。

Step 2: 定义 MemoryPlugin

这就是本课的核心——一个 JSON 文件作为"大脑"，四个工具操作它：

using System.ComponentModel;
using System.Text.Json;
using Microsoft.SemanticKernel;

public class MemoryPlugin
{
    private readonly string _storePath;
    private Dictionary<string, string> _store;

    public MemoryPlugin(string? storePath = null)
    {
        _storePath = storePath ?? Path.Combine(
            Directory.GetCurrentDirectory(), "agent_memory.json");
        _store = Load();
    }

    // ——— 持久化 ——
    private Dictionary<string, string> Load()
    {
        if (File.Exists(_storePath))
        {
            var json = File.ReadAllText(_storePath);
            return JsonSerializer.Deserialize<Dictionary<string, string>>(json)
                   ?? new();
        }
        return new();
    }

    private void Save()
    {
        var json = JsonSerializer.Serialize(_store,
            new JsonSerializerOptions { WriteIndented = true });
        File.WriteAllText(_storePath, json);
    }

    // ——— 四个记忆工具 ——

    [KernelFunction("remember")]
    [Description("将一条信息存入长期记忆。" +
                 "key: 记忆的唯一标识，用英文下划线命名（如 user_name、project_deadline）。" +
                 "info: 要记住的具体内容。" +
                 "使用场景：用户说「记住...」「帮我记一下...」「别忘了...」等。" +
                 "注意：如果 key 已存在，新内容会覆盖旧内容。返回确认信息。")]
    public string Remember(string key, string info)
    {
        _store[key] = info;
        Save();
        return $"已记住 [{key}]: {info}";
    }

    [KernelFunction("recall")]
    [Description("根据 key 从长期记忆中检索信息。" +
                 "key: 要检索的记忆标识。" +
                 "使用场景：用户问「之前记的...」「回忆一下...」或者你需要某个之前存过的信息。" +
                 "注意：如果 key 不存在，返回提示信息而非报错——这是正常的（可能没记过）。")]
    public string Recall(string key)
    {
        if (_store.TryGetValue(key, out var info))
            return $"记忆 [{key}]: {info}";
        return $"没有找到关于 [{key}] 的记忆。可用 list_memories 查看所有已存储的记忆标识。";
    }

    [KernelFunction("list_memories")]
    [Description("列出长期记忆中所有已存储的记忆标识（key）和对应的内容摘要。" +
                 "使用场景：用户问「我记得什么」「有哪些记忆」「你记了哪些东西」等。" +
                 "不需要参数。")]
    public string ListMemories()
    {
        if (_store.Count == 0)
            return "目前没有任何长期记忆。你可以用 remember 工具来存储一些信息。";

        var lines = _store.Select(kv =>
            $"  · {kv.Key}: {kv.Value}");
        return $"共 {_store.Count} 条记忆：\n{string.Join("\n", lines)}";
    }

    [KernelFunction("forget")]
    [Description("从长期记忆中删除指定 key 的信息。" +
                 "key: 要删除的记忆标识。" +
                 "使用场景：用户说「忘掉...」「删除记忆...」「不用记住...」等。" +
                 "注意：删除前必须先向用户确认。如果 key 不存在，告知用户。")]
    public string Forget(string key)
    {
        if (_store.Remove(key))
        {
            Save();
            return $"已删除记忆 [{key}]。";
        }
        return $"记忆 [{key}] 不存在，无需删除。";
    }
}
🔍 观察模式： MemoryPlugin 和 Lesson 02 的 FilePlugin 结构完全相同——一个类 + [KernelFunction] + [Description]。区别只在于存储的内容：FilePlugin 存任意文本文件，MemoryPlugin 存结构化键值对。

关键设计决策： _store 用 Dictionary<string, string> 而非 Dictionary<string, object>——值也是 string。为什么？回到 Lesson 02 原则 ⑤：LLM 更容易生成基础类型的参数。如果值类型太复杂（嵌套对象），LLM 填参准确率会下降。

另外，注意 forget 的 Description 里有一句"删除前必须向用户确认"——这是 Lesson 02 原则 ②（Description 是 API 契约）的直接应用。LLM 读到这句话后会主动先确认再调用。
🔑 设计深入：Agent 怎么生成和匹配 key？

看上面的代码，remember(key, info) 的 key 是 LLM 自己填的——没有哈希函数，没有查表，没有规则引擎。那两次对话生成的 key 怎么保证一致？

答案是：没有硬保证，全靠 LLM 的语义理解 + 约束引导。这是一个用自然语言契约替代程序逻辑的经典案例。

存储时的推理链（remember）：
用户："我叫小明，我喜欢蓝色"
 ↓
LLM 读 Instructions：「主动记忆——key 用英文下划线命名」
 ↓
LLM 语义理解："名字" → "user_name"
        "颜色偏好" → "user_preference_color"
 ↓
调用 remember("user_name", "小明")
调用 remember("user_preference_color", "蓝色")

检索时的推理链（recall）：
用户："还记得我的名字吗？"
 ↓
LLM 读 Instructions：「主动回想——先用 recall 检索相关记忆」
 ↓
LLM 语义猜测："名字" → 之前存的 key 应该是 "user_name"
 ↓
调用 recall("user_name")

为什么能"大概对"？三层机制：
层机制作用
Instructions 约束"key 用英文下划线命名，让 key 能描述内容"缩小命名空间——不会出现 k1、a、我的名字
Description 示例"如 user_name、project_deadline"给出 few-shot 范式——LLM 模仿 category_specific 模式
LLM 语义恒定性同一模型对同一语义的映射趋于稳定"名字"→user_name 是高概率路径（编程惯例 + 样例共指）

但这不是 100% 可靠——三个常见失败场景：
场景现象本设计的应对
A. 同义不同 key两次存相同信息用了不同 key：
user_name vs name → 记忆分裂		Instructions + Description 示例缩小命名空间，降低概率
B. recall 猜错存在 user_preference_color
LLM 猜 favorite_color → 返回"没找到"		recall 的返回信息引导 LLM 去调 list_memories 做 fallback
C. list 做纠错LLM 不确定 key → 先调 list_memories() 看有哪些 key → 发现 user_preference_color → 再调 recalllist_memories 就是为 self-correction 设计的

这正是 list_memories 工具存在的深层原因——不只是"列出记忆"，更是LLM 自我纠错的 fallback 机制。recall 返回"没找到"时的那句「可用 list_memories 查看所有已存储的记忆标识」，本质上是在引导 LLM 走向正确的恢复路径。

本质提炼： 传统编程中，key 的一致性由哈希函数或数据库约束保证——那是硬契约。在 Agent 系统中，key 的一致性由自然语言描述 + LLM 语义理解保证——那是软契约。软契约不完美，但在足够好的约束下（命名规范 + few-shot 示例 + fallback 机制），实际可用性很高。这是所有 Agent 系统设计的核心权衡。

Step 3: 创建 MemoryAssistant Agent

using System.ComponentModel;
using Microsoft.SemanticKernel;
using Microsoft.SemanticKernel.Agents;
using Microsoft.SemanticKernel.Agents.Chat;
using Microsoft.SemanticKernel.ChatCompletion;
using Anthropic.SDK;
using Anthropic.SDK.Common;

// ——— A：创建 Anthropic 客户端（指向 DeepSeek）———
var anthropicClient = new AnthropicClient(
    new APIAuthentication(
        Environment.GetEnvironmentVariable("DEEPSEEK_API_KEY")!
    )
)
{
    ApiUrlFormat = "https://api.deepseek.com/anthropic/{0}/{1}"
};

IChatClient chatClient = new ChatClientBuilder(anthropicClient.Messages)
    .UseFunctionInvocation()
    .Build();

// ——— B：构建 Kernel + 注册工具 ———
var builder = Kernel.CreateBuilder();
builder.Services.AddSingleton(chatClient);

// 注册 MemoryPlugin——Agent 现在有了"记忆"能力
builder.Plugins.AddFromType<MemoryPlugin>();

Kernel kernel = builder.Build();

// ——— C：创建 Agent ———
var agent = new ChatCompletionAgent
{
    Name = "MemoryAssistant",
    Instructions = """
        你是一个拥有长期记忆的智能助手，名叫「小记」。

        你的核心能力：
        - 记住用户告诉你的任何事实、偏好、计划（使用 remember 工具）
        - 当用户提到之前记过的内容时，主动使用 recall 检索
        - 管理记忆——列出、删除（必须先确认）

        工作原则：
        - 主动记忆：当用户分享个人信息、偏好、计划、决策时，
          主动判断是否值得记住。如果是，调用 remember 存下来，
          并简短告知用户「我记住了」。
        - 主动回想：当用户的问题涉及过去的信息，
          先用 recall 检索相关记忆，再基于记忆回答。
          不要只依赖当前对话——去查你的记忆库。
        - 记忆组织：key 用英文下划线命名（如 user_name、
          user_preference_theme、project_deadline），
          让 key 本身就能描述内容。
        - 删除确认：在调用 forget 之前，先向用户确认
          「确定要删除关于 X 的记忆吗？」。
        - 不确定时：如果用户没有明确要求记住但你觉得有用，
          可以说「要不要我帮你记下来？」。

        用中文回复，温暖简洁。
        """,
    Kernel = kernel
};

// ——— D：对话循环 ———
var history = new ChatHistory();
Console.WriteLine("=== MemoryAssistant 已就绪 —— 拥有长期记忆 ===");
Console.WriteLine("输入 'exit' 退出\n");
Console.WriteLine("试试这些：");
Console.WriteLine("  · 我叫小明，我喜欢蓝色");
Console.WriteLine("  · 我的项目截止日期是 7 月 20 号");
Console.WriteLine("  · 你还记得我的名字吗？");
Console.WriteLine("  · 你都记了些什么？\n");

while (true)
{
    Console.Write("你: ");
    var input = Console.ReadLine();
    if (input?.ToLower() == "exit") break;

    history.Add(new ChatMessageContent(AuthorRole.User, input!));

    Console.Write("Agent: ");
    await foreach (var chunk in agent.InvokeStreamingAsync(history))
    {
        Console.Write(chunk.Content);
    }
    Console.WriteLine("\n");
}
📐 Instructions 设计分析： 注意 Instructions 中有明确的分层：核心能力（Agent 是什么）+ 工作原则（Agent 怎么做）。其中「主动记忆」「主动回想」「记忆组织」「删除确认」「不确定时」五条原则，每一条都对应 MemoryPlugin 中的一个工具或设计约束。

特别关注「主动记忆」原则——"当用户分享个人信息、偏好、计划、决策时，主动判断是否值得记住"。这利用了 LLM 的判断力——不是每条信息都存，而是像人类一样有选择地记忆。这种「自主判断 + 工具执行」的模式，是所有高级 Agent 行为的基础。

#    → Agent 调用 recall("user_name") + recall("user_preference_color")
#    → 回复 "你叫小明，喜欢蓝色！"
# 5. "我记了哪些事？"
#    → Agent 调用 list_memories()
# 6. "忘掉我喜欢的颜色吧"
#    → Agent 先确认 "确定要删除关于颜色偏好的记忆吗？"
#    → 你说"确定"→ Agent 调用 forget("user_preference_color")
💡 跨会话持久化： 注意第 3-4 步——你关闭程序后重启，Agent 仍然记得小明和他的偏好。因为 MemoryPlugin 把数据存在了 agent_memory.json 文件中。这就是长期记忆的最简实现——不需要向量数据库，不需要 embedding，一个 JSON 文件就够了。

当你后续学了 RAG（向量记忆），这个 MemoryPlugin 的接口完全不需要变——remember / recall / list_memories / forget 四个方法签名不变，只是把 Dictionary 替换成向量数据库。这就是好的 API 设计——接口稳定，实现可替换。

发生了什么？—— 追踪一次记忆操作

当你说「我叫小明，我喜欢蓝色」时，Agent Loop 内部发生了这些事：

  1. LLM 推理：读取 Instructions（"主动记忆：当用户分享个人信息时…"）+ 用户消息。判断——「用户分享了姓名和偏好，我应该记住。用 remember 工具存两条」。
  2. 第一次 tool_call：remember(key: "user_name", info: "小明")
  3. 第二次 tool_call：remember(key: "user_preference_color", info: "蓝色")
  4. MemoryPlugin 执行：写入 agent_memory.json： 
    {
  "user_name": "小明",
  "user_preference_color": "蓝色"
}
    返回 "已记住 [user_name]: 小明" 和 "已记住 [user_preference_color]: 蓝色"
  5. LLM 生成回复：「好的，我记住了——你叫小明，喜欢蓝色！以后有需要随时可以问我。」

下次你重启程序问「还记得我吗？」，LLM 的推理链是：

用户: "还记得我吗？" ↓ LLM: 用户问过去的个人信息 → 我应该查记忆库 → 调用 recall("user_name") ↓ MemoryPlugin: "记忆 [user_name]: 小明" ↓ LLM: "用户叫小明。还有其他信息吗？" → 继续调用 recall("user_preference_color") ↓ MemoryPlugin: "记忆 [user_preference_color]: 蓝色" ↓ LLM: 生成回复 "当然记得！你叫小明，喜欢蓝色。"
关键洞察： Agent 在这里展现了两种高级行为：
① 主动存储——LLM 基于 Instructions 中的原则，自主判断「这条信息值得记住」，无需用户说"帮我记下来"。
② 链式检索——LLM 调用一次 recall 后，基于返回结果自主决定是否继续检索更多相关信息。这和 Lesson 02 的"计算→保存"是同一机制——只是工具从 calculate/save 变成了 recall/recall。

深入理解：你的 ChatHistory 还能撑多久？

MemoryPlugin 解决了长期记忆问题，但工作记忆（ChatHistory）仍然有上限。来算一笔账：

你的 Agent 每次对话的 token 消耗： System Prompt ~300 tokens (Instructions) 每轮对话： User Message ~50 tokens (用户输入) Tool Call × N ~100 tokens (每次 tool call + result) Agent Response ~80 tokens (Agent 回复) ───────────────────────── 每轮合计 ~230 tokens 如果平均每轮 ~230 tokens： DeepSeek V3 (128K)：~550 轮之后开始截断 Claude Sonnet (200K)：~870 轮之后开始截断 但这不包括 tool definition（每次请求都要带上所有工具定义）！ 3 个工具 × ~150 tokens/工具 = ~450 tokens 的固定开销/轮

实际数字更小。 因为 tool definition 每轮都要完整发送（LLM 需要知道当前有哪些工具可用）。如果你的 Agent 有 10 个工具，仅工具定义就占 ~1500 tokens——相当于 6 轮对话的预算。

⚠️ 实用建议：
· 保持 Instructions 简洁——每个字都在消耗 token 预算
· 工具别注册太多——只给 Agent 当前任务真正需要的工具
· 长期对话（>100 轮）需要实现摘要压缩策略——这是下一节的内容
· 监控 token 使用——在代码中加简单计数：history.Sum(m => m.Content?.Length ?? 0) / 4 作为粗略估计

实操：给你的 Agent 加一个 Token 计数器

不需要三方库，一个简单的扩展方法做粗略估算：

public static class ChatHistoryExtensions
{
    /// <summary>
    /// 粗略估算 ChatHistory 中的 token 数。
    /// 中文 ~2 chars/token, 英文 ~4 chars/token。取 3 作为折中。
    /// </summary>
    public static int EstimateTokens(this ChatHistory history)
    {
        int total = 0;
        foreach (var msg in history)
        {
            var text = msg.Content ?? "";
            // 简单统计：中文字符按 2 chars/token，非中文按 4 chars/token
            int chineseChars = text.Count(c => c >= 0x4E00 && c <= 0x9FFF);
            int otherChars = text.Length - chineseChars;
            total += chineseChars / 2 + otherChars / 4 + 1; // +1 保底
        }
        return total;
    }
}

把这个加到你的对话循环里，每次打印估计 token 数。当接近 80% 上下文窗口时（约 102K for 128K 窗口），触发警告或自动摘要。自动摘要的实现见下面挑战练习。
