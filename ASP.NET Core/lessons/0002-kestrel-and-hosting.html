第 2 课：Kestrel、反向代理与容器部署

模块：Kestrel & 部署（1/1） |  预计阅读/练习时间：40 分钟  |  前置：第 1 课、Docker Desktop（动手第 4 步）

Web API 2 时代，"Web 服务器"这个词几乎等于 IIS：它监听端口、解析 HTTP、终止 TLS、做 URL 重写、跑认证模块、 再把请求塞进 System.Web 管道——所有层次糊在一个进程里。 ASP.NET Core 把它拆成了三层各司其职，而第 1 课测验第 3 题你答错的地方，正是这三层的边界。

  • 画清 Kestrel → 中间件管道 → 端点 三层，每层只做什么、不做什么
  • 知道 Kestrel 监听地址的 4 种设置方式和优先级，以及容器里 8080 这个默认值从哪来
  • 理解反向代理为什么会"弄丢"客户端 IP 和 HTTPS，以及 UseForwardedHeaders 如何找回来——含一个必踩的死循环坑
  • 不写 Dockerfile，用 dotnet publish /t:PublishContainer 把 HelloApi 打成镜像并跑起来（任务书目标：部署到 Linux 容器）

三层模型：Kestrel 只做一件事

        网络字节流（TCP / TLS）
              │
              ▼
┌─────────────────────────────────────────────────────────────┐
│ ① Kestrel（IServer）                                        │
│    监听 socket · 解析 HTTP/1.1、HTTP/2、HTTP/3 · 终止 TLS    │
│    把每个请求变成一个 HttpContext，然后调用 ↓                 │
│    它不认识 URL 和端点的对应关系，也不认识中间件              │

              │  RequestDelegate（整条管道被编译成一个委托）
              ▼

│    ForwardedHeaders → 异常页 → HTTPS 重定向 → Routing →     │

              │
              ▼

Kestrel 到 HttpContext 为止；从 URL 找端点是 ② 层里 UseRouting 的活

IServer 接口只有一个核心方法：StartAsync<TContext>(IHttpApplication<TContext> application, …)—— 服务器拿到的是整条管道打包成的一个应用委托，对里面的中间件、路由、Minimal API 还是 Controller 一无所知。 这就是为什么第 1 课里"没有 UseRouting"的正确答案是"框架自动补上"而不是"Kestrel 直接分发"：路由匹配发生在 ②，不在 ①。

Web API 2 / IIS 做的事ASP.NET Core 里由谁做
监听端口、解析 HTTP、TLSKestrel（①）
URL Rewrite 模块的 HTTPS 强制UseHttpsRedirection 中间件（②）
Windows 认证 / Forms 认证模块UseAuthentication 中间件（②）
路由表（RouteTable / HttpRouteCollection）UseRouting 中间件（②）
静态文件由 IIS 直接返回UseStaticFiles 中间件（②）
应用池回收、多站点共享 80 端口、进程守护不再有——交给反向代理 / 容器编排（本课下半）
IIS 还在吗？在。Windows 上 IIS 可以作为反向代理（ANCM 进程外模式）或直接在 IIS 工作进程里加载 Kestrel 的替代品（进程内模式，.NET Core 3+ 默认）。 但两种模式下 IIS 都只是①层的替身或前置，②③层完全一样。本系列聚焦 Linux 容器，IIS 细节见 官方 IIS 托管文档。

Kestrel 监听哪里：4 种设置方式

按 Kestrel 文档， 什么都不设时默认 http://localhost:5000（有开发证书时再加 https://localhost:5001）。改它有 4 条路，都汇入第 1 课讲的配置链：

方式示例典型场景
ASPNETCORE_URLS 环境变量 http://+:8080;https://+:8443 容器、systemd、云平台。+ / * = 所有网卡
ASPNETCORE_HTTP_PORTS / HTTPS_PORTS 8080（只写端口，分号分隔） .NET 8 新增的简化版；官方 aspnet 镜像里预设了 ASPNETCORE_HTTP_PORTS=8080
--urls 命令行 dotnet run --urls http://localhost:5100 本机临时换端口（第 1 课已用过）
appsettings.json 的 Kestrel:Endpoints 节 见下方 需要按端点配证书、协议（HTTP/2 only 等）时 
// appsettings.json —— 最完整的方式，可以按端点指定证书和协议
"Kestrel": {
  "Endpoints": {
    "Http":  { "Url": "http://*:8080" },
    "Https": { "Url": "https://*:8443",
               "Certificate": { "Path": "cert.pfx", "Password": "…" } }
  }
}
为什么容器默认是 8080 而不是 80？ .NET 8 起官方镜像以非 root 用户 app 运行，Linux 非特权用户不能绑 1024 以下端口，所以默认从 80 改成了 8080 （破坏性变更公告）。 docker run -p 8000:80 会连不上——要写 -p 8000:8080。这是从 .NET 6/7 迁移时最常见的"容器起来了但访问不到"。

代码里也能配（builder.WebHost.ConfigureKestrel(o => o.ListenAnyIP(8080))），但会覆盖上面所有配置来源—— 运维就改不了端口了。规则：地址用配置，限额用代码。限额的例子（数值来自 Kestrel options 文档）： 

builder.WebHost.ConfigureKestrel(o =>
{
    o.Limits.MaxRequestBodySize = 10 * 1024 * 1024;   // 默认 30,000,000 字节 ≈ 28.6 MB
    o.Limits.KeepAliveTimeout   = TimeSpan.FromMinutes(2);  // 默认 130 秒
    o.AddServerHeader = false;                          // 不发 Server: Kestrel
});

反向代理：为什么需要、它弄丢了什么

Kestrel 可以直接面对互联网（官方支持的部署方式），但 文档 列了四个理由让你在前面放一层 Nginx / YARP / 云负载均衡：缩小暴露面、多一层防御、融入现有基础设施、 集中做 TLS 和负载均衡（只有代理需要证书，代理到 Kestrel 之间走明文 HTTP）。 还有一条硬限制：Kestrel 不能多个进程共享同一个端口——它不看 Host 头分流。IIS 时代一台机器上靠主机名绑几十个站点的玩法，Core 里必须靠代理。 

浏览器 ──HTTPS──▶ Nginx/YARP（终止 TLS）──HTTP──▶ Kestrel :8080
    203.0.113.9              10.0.0.5                   ▲
                                                         │ Kestrel 看到的：
                                                         │   Scheme    = http      ✘（原本是 https）
                                                         │   RemoteIp  = 10.0.0.5  ✘（原本是 203.0.113.9）
                                                         │   Host      = 内网地址  ✘

代理把真实信息塞在约定的请求头里带过来（文档）：

请求头内容中间件写回到
X-Forwarded-For原始客户端 IP（链式代理时逗号分隔）HttpContext.Connection.RemoteIpAddress
X-Forwarded-Proto原始 scheme：httpsHttpContext.Request.Scheme
X-Forwarded-Host原始 Host 头HttpContext.Request.Host
X-Forwarded-Prefix原始路径前缀（代理把 /api 剥掉时用）HttpContext.Request.PathBase

但请求头是任何人都能伪造的，所以 ASP.NET Core 默认不信任它们。你要显式启用，并且告诉它信任谁：

using Microsoft.AspNetCore.HttpOverrides;

builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    // 默认只信任 loopback（同机代理）。代理在别的机器/容器时必须加：
    // o.KnownProxies.Add(IPAddress.Parse("10.0.0.5"));
    // 或 o.KnownNetworks.Add(new IPNetwork(IPAddress.Parse("10.0.0.0"), 8));
});

var app = builder.Build();
app.UseForwardedHeaders();      // ← 尽量放最前面，至少在 UseHttpsRedirection / UseHsts / 认证之前
Rule

三个默认值决定了它是否生效

  • ForwardedHeaders 默认 None——不设等于没启用，中间件跑了也什么都不改
  • KnownProxies / KnownNetworks 默认只有 loopback——来自非本机地址的请求头会被静默忽略，不报错
  • ForwardLimit 默认 1——链式代理只处理最右边一跳

"部署到 Nginx 后 RemoteIpAddress 还是 127.0.0.1 / 10.x"，十有八九是第二条。

必踩坑：HTTPS 重定向死循环。 文档原话： 应用调用了 UseHttpsRedirection，部署到 Nginx / Azure Linux / 任何非 IIS 的代理后面，代理终止 TLS，Kestrel 看到的永远是 http， 于是每次都 301 到 https → 代理再转成 http 过来 → 再 301……浏览器报 ERR_TOO_MANY_REDIRECTS。OAuth/OIDC 回调地址也会生成错的 http://。 解法就是上面的 UseForwardedHeaders，或者环境变量 ASPNETCORE_FORWARDEDHEADERS_ENABLED=true（云平台常用，但它清空了 KnownProxies 限制，只能在网络已隔离时用）。 IIS 进程外模式是唯一自动配好的场景——所以从 IIS 迁到 Linux 时这个坑几乎必中。

容器：不写 Dockerfile 的打包方式

.NET SDK 内置了容器构建（Web SDK 无需额外包， 官方教程）。一条命令： 

dotnet publish --os linux --arch x64 /t:PublishContainer

它按项目类型推断一切（配置参考），你需要知道的默认值：

项默认MSBuild 属性（要改时）
基础镜像mcr.microsoft.com/dotnet/aspnet:10.0（Web SDK 项目）ContainerBaseImage / ContainerFamily（如 alpine）
镜像名 : 标签helloapi:latest（AssemblyName 小写）ContainerRepository / ContainerImageTag
监听端口8080（从基础镜像的 ASPNETCORE_HTTP_PORTS 推断）ContainerPort
运行用户app（非 root，UID 由 APP_UID 给出）ContainerUser
工作目录 / 入口/app · dotnet HelloApi.dllContainerWorkingDirectory / ContainerAppCommand
推送目标本机 Docker daemonContainerRegistry（远程仓库）/ ContainerArchiveOutputPath（tar.gz）
什么时候还是要写 Dockerfile？需要 RUN 指令的时候（apt 装包、建用户、跑脚本）——SDK 方式无法模拟 RUN。 绝大多数 API 项目不需要。另外注意 ASPNETCORE_ENVIRONMENT 在镜像里没有设置，所以容器里跑的就是 Production——和第 1 课"部署后默认 Production"一致。

动手：验证三层边界 → 找回 HTTPS → 进容器

沿用第 1 课的 playground\HelloApi（没有就 dotnet new webapi -n HelloApi -o playground\HelloApi）。全程 PowerShell。

加一个"我看到了什么"端点

在 app.UseHttpsRedirection(); 之后加：

app.MapGet("/whoami", (HttpContext ctx) => new
{
    ctx.Request.Scheme,
    Host = ctx.Request.Host.Value,
    RemoteIp = ctx.Connection.RemoteIpAddress?.ToString(),
    ctx.Request.Protocol,
    XForwardedFor = ctx.Request.Headers["X-Forwarded-For"].ToString(),
    User = Environment.UserName
});

运行并探测（用 --urls 绕开第 1 课提到的 5000 端口保留问题）：

dotnet run --no-launch-profile --urls http://localhost:5100
# 另开一个终端：
Invoke-RestMethod http://localhost:5100/whoami | ConvertTo-Json -Compress

预期：

{"scheme":"http","host":"localhost:5100","remoteIp":"127.0.0.1","protocol":"HTTP/1.1","xForwardedFor":"","user":"xiaos"}

扮演代理：手动塞转发头

Invoke-RestMethod http://localhost:5100/whoami -Headers @{
  'X-Forwarded-Proto' = 'https'
  'X-Forwarded-For'   = '203.0.113.9'
} | ConvertTo-Json -Compress

预期——头到了，但什么都没变：

{"scheme":"http","host":"localhost:5100","remoteIp":"127.0.0.1","protocol":"HTTP/1.1","xForwardedFor":"203.0.113.9","user":"xiaos"}

这就是生产上的死循环起点：代理明明说了 https，应用视而不见。

启用 ForwardedHeaders 中间件

文件顶部加 using Microsoft.AspNetCore.HttpOverrides;；Build() 前后各加一段：

builder.Services.Configure<ForwardedHeadersOptions>(o =>
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto);

var app = builder.Build();

app.UseForwardedHeaders();

重启，重复第 2 步的带头请求。预期：

{"scheme":"https","host":"localhost:5100","remoteIp":"203.0.113.9","protocol":"HTTP/1.1","xForwardedFor":"","user":"xiaos"}
  • scheme 变成 https，remoteIp 变成伪造的公网 IP——中间件把头"写回"了 HttpContext
  • xForwardedFor 变空了——被消费的值会从头里移除，原值搬到 X-Original-For，防止下游重复处理

可选加深：把请求改成从非 loopback 地址发（比如 --urls http://0.0.0.0:5100 然后用本机局域网 IP 访问）， 你会看到 scheme 又回到 http——因为来源不在 KnownProxies 里，头被静默忽略。这就是上面 Rule 的第二条。

打成容器镜像并运行

先确认 Docker Desktop 已启动（docker info 不报错）。然后：

dotnet publish --os linux --arch x64 /t:PublishContainer

预期输出末尾（首次会拉取基础镜像，慢一些）：

在基本映像"mcr.microsoft.com/dotnet/aspnet:10.0"顶部构建标记为"latest"的映像"helloapi"。
将映像"helloapi"推送到本地注册表 …
看到 error CONTAINER1012: 本地注册表不可用 / Cannot find docker/podman executable —— 是 Docker daemon 没在跑，不是项目问题。启动 Docker Desktop 再来。

运行——注意端口映射到 8080，并把环境切到 Staging 复习第 1 课：

docker run --rm -p 8000:8080 -e ASPNETCORE_ENVIRONMENT=Staging helloapi
# 另一个终端：
Invoke-RestMethod http://localhost:8000/whoami | ConvertTo-Json -Compress

预期：

{"scheme":"http","host":"localhost:8000","remoteIp":"172.17.0.1","protocol":"HTTP/1.1","xForwardedFor":"","user":"app"}
  • user 是 app，不是 root
  • remoteIp 是 Docker 网桥地址（172.17.0.1 或类似），不是 127.0.0.1——Docker 的端口转发本身就是一层"代理"，真实客户端 IP 已经丢了
  • 容器日志里 Hosting environment: Staging、Now listening on: http://[::]:8080

试一下反例，确认 80 端口的坑是真的：docker run --rm -p 8000:80 helloapi → 访问 8000 会被拒绝连接。

测验

考的是哪一层负责和默认值。答之前先想本课哪张表/哪条 Rule 讲了它。
❓ 一个请求 GET /orders/42 到达。"决定它由哪个 MapGet lambda 处理"这件事发生在哪一层？
Kestrel 解析完请求行后按路径表直接挑出端点
中间件管道中的路由中间件在匹配后挂到上下文
端点自身在被调用时检查路径是否与自己匹配
反向代理按路径规则转发到对应的端点上去
❓ docker run -p 8000:80 helloapi 后访问 localhost:8000 被拒绝连接，容器日志正常。最可能的原因？
非 root 用户没有权限接受来自宿主机的网络连接
镜像预设监听 8080，容器内的 80 端口无进程在听
未设置 ASPNETCORE_ENVIRONMENT 时 Kestrel 拒绝启动
缺少 HTTPS 证书导致 Kestrel 关闭了全部 HTTP 端点
❓ 已配置 ForwardedHeaders = XForwardedFor | XForwardedProto 并调用 UseForwardedHeaders()。Nginx 跑在另一台机器 10.0.0.5 上，正确发送了两个头，但应用里 RemoteIpAddress 仍是 10.0.0.5。原因？
ForwardLimit 默认为一，链式代理时需要调大才行
UseForwardedHeaders 必须放在 UseRouting 之后才生效
代理地址不在 KnownProxies 中，转发头被静默忽略
Nginx 传的头名不同，需要改 ForwardedForHeaderName
❓ 一个在 IIS 下运行良好的 API 原样部署到 Nginx 后面（Nginx 终止 TLS），浏览器报 ERR_TOO_MANY_REDIRECTS。哪个中间件是直接原因？
UseHsts 在响应头里要求浏览器永久改用 HTTPS 访问
UseHttpsRedirection 看到 http 就重定向，代理又转回来
UseRouting 因路径前缀被代理剥掉而反复匹配失败重试
UseAuthentication 因证书未转发而反复跳转到登录页
