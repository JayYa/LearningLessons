第 3 课：中间件管道——顺序、短路与 OWIN 的血缘

模块：中间件管道（1/2） |  预计阅读/练习时间：35 分钟  |  前置：第 2 课三层模型

第 2 课把 Kestrel 画在 ① 层，它把整条管道当成一个 RequestDelegate 来调。这一课打开 ② 层： 这"一个委托"是怎么由十几个 app.Use… 折叠出来的，为什么响应会按逆序回来， 一个中间件"不调 next"时到底谁还会跑、谁不会——以及这和你熟悉的 OWIN AppFunc、IHttpModule 各差在哪。

  • 用一个心理模型解释全部 Use / Run / Map / MapWhen / UseWhen：洋葱 + 一条 next 链
  • 短路（不调 next）后，前面的中间件仍会执行 next 之后的代码——这和 IHttpModule 的 Response.End() 不一样
  • 响应已开始（HasStarted）后再改头/状态码会抛异常——中间件最常见的运行时错误
  • 背下官方推荐顺序的骨架，并知道 WebApplication 偷偷补的三个中间件放在哪（收尾 LR-0001）

一个中间件 = 一个"拿 next、返回新委托"的函数

官方定义（ASP.NET Core middleware）： 中间件是管道里的一段代码，要么调用下一个，要么短路。落到类型上：

OWIN / Katana（你熟的）
// AppFunc
Func<IDictionary<string, object>, Task>

// 中间件 = 拿 next 返回 AppFunc
Func<AppFunc, AppFunc>

app.Use(async (env, next) => {
    // before
    await next();
    // after
});
ASP.NET Core
// RequestDelegate
delegate Task RequestDelegate(HttpContext ctx);

// 中间件 = 拿 next 返回 RequestDelegate
Func<RequestDelegate, RequestDelegate>

app.Use(async (ctx, next) => {
    // before
    await next(ctx);
    // after
});

形状一模一样——Core 的管道就是 Katana 那套设计的强类型版：IDictionary<string,object> 环境字典换成了 HttpContext， 其他不变。所以你在 Katana 里建立的"洋葱"直觉可以直接搬过来。 Build() 时框架把注册的 Func<RequestDelegate,RequestDelegate> 列表从后往前折叠： 最后一个先拿到"404 兜底委托"当 next，返回的委托再交给倒数第二个……最终得到一个 RequestDelegate，这就是 Kestrel 拿到的东西。 

请求 ──▶ A.before ──▶ B.before ──▶ C.before ──▶ ★ 端点
                                                 │
响应 ◀── A.after  ◀── B.after  ◀── C.after  ◀────┘

注册顺序：A, B, C      请求正序 A→B→C      响应逆序 C→B→A
Rule

所有 app.Use… 的语义只有三种，看它对 next 做了什么

API对 next 的处理什么时候用
Use(async (ctx, next) => …)你决定调不调绝大多数：日志、加头、条件拦截
Run(async ctx => …)没有 next，永远终结兜底、分支末尾
Map("/p", b => …) / MapWhen(pred, b => …)命中 → 走分支，不回主线按路径前缀/任意条件切出独立子管道
UseWhen(pred, b => …)命中 → 走分支，末尾接回主线"只对某些请求多加一层"

MapGet / MapControllers 不在这张表里——它们注册的是 ③ 层的端点，由 UseRouting 匹配、UseEndpoints 执行， 本身不是中间件。第 1 课那道题的教训在此再复习一次。

短路：不调 next，但"外层的 after"照跑

IHttpModule 里 context.Response.End() 直接抛 ThreadAbortException 把整个请求掐断； Core 里没有这种硬中断——短路只是"这个中间件没往里走"，已经进来的外层中间件在 next 返回后照常执行剩余代码 （迁移文档原话： "this doesn't fully terminate the request, because previous middlewares will still be invoked when the response makes its way back"）。 

请求 ──▶ A.before ──▶ B: 写 403，不调 next
                          │
响应 ◀── A.after  ◀───────┘        C、端点、C.after 都没跑；A.after 跑了
HasStarted：中间件最常见的运行时异常。 一旦响应头已经发给客户端（ctx.Response.HasStarted == true），再设状态码或响应头就会抛 InvalidOperationException: Headers are read-only, response has already started （文档警告）。 这几乎总发生在 await next(ctx) 之后的代码里——端点已经把 body 写出去了。 想在响应上加头，要在 next 之前注册 ctx.Response.OnStarting(() => { …加头…; return Task.CompletedTask; })，让框架在头即将发出的一刻回调你。

顺序：官方骨架 + 三条硬规则

文档给的推荐顺序（Web API 用不到的已删）： 

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/error");   // 1. 最外层：能接住后面所有中间件的异常
    app.UseHsts();
}
app.UseHttpsRedirection();               // 2. 第 2 课：代理后面记得先 UseForwardedHeaders
app.UseStaticFiles();                    // 3. 命中即短路，越早越省
app.UseRouting();                        // 4. 匹配端点，挂到 HttpContext（还不执行）
// app.UseRateLimiter();                 //    用了 [EnableRateLimiting] 就必须在 Routing 之后
// app.UseCors();                        //    必须在 Authentication 之前
app.UseAuthentication();                 // 5. 谁在发请求
app.UseAuthorization();                  // 6. 允不允许（要先知道端点，所以在 Routing 后）
app.MapControllers();                    // 7. 端点在此执行（UseEndpoints 由框架补）
硬规则（来源）为什么
UseCors → UseAuthentication → UseAuthorization 顺序固定预检请求（OPTIONS）没有凭据，得先放行
UseCors 必须在 UseResponseCaching 前否则缓存的响应没有 CORS 头（#23218）
UseAuthorization 必须在 UseRouting 后授权要看端点上的 [Authorize] 元数据，路由没匹配就没元数据
Rule

你不写，WebApplication 也会补——补在固定位置

文档： 有端点但没调 UseRouting → 在管道最前面补 UseRouting； 注册了 AddAuthentication / AddAuthorization 但没调对应 Use… → 紧跟着补； 末尾补 UseEndpoints。你写的所有中间件都被夹在自动 UseRouting 和 UseEndpoints 之间。

后果：只要你想让某个中间件在路由匹配之前跑（比如 UseForwardedHeaders、UseStaticFiles），就必须显式写 app.UseRouting() 并把它放在前面——否则它默认已经排在自动 Routing 后面了。 这也是为什么模板里明明"可以省"，正式项目仍建议显式写出来。

练习 ②：动手验证

把 playground\HelloApi\Program.cs 整个替换成下面这份（上面四道题的合体，外加 HasStarted 陷阱）， 然后 dotnet run --no-launch-profile --urls http://localhost:5100。

Program.cs

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (ctx, next) =>
{
    Console.WriteLine("A ▶ in");
    await next(ctx);
    Console.WriteLine("A ◀ out  status=" + ctx.Response.StatusCode);
});

app.Use(async (ctx, next) =>
{
    if (ctx.Request.Headers.ContainsKey("X-Block"))
    {
        Console.WriteLine("B ✂ short-circuit");
        ctx.Response.StatusCode = 403;
        await ctx.Response.WriteAsync("blocked by B");
        return;                       // 没有 next → 后面全部不跑
    }
    Console.WriteLine("B ▶ in");
    await next(ctx);
    Console.WriteLine("B ◀ out");
});

app.MapWhen(ctx => ctx.Request.Query.ContainsKey("branch"), branch =>
{
    branch.Run(async ctx =>
    {
        Console.WriteLine("M ● MapWhen 分支（不回主线）");
        await ctx.Response.WriteAsync("from MapWhen branch");
    });
});

app.UseWhen(ctx => ctx.Request.Query.ContainsKey("tag"), branch =>
{
    branch.Use(async (ctx, next) =>
    {
        Console.WriteLine("U ▶ UseWhen 分支（会回主线）");
        await next(ctx);
        Console.WriteLine("U ◀ out");
    });
});

app.Use(async (ctx, next) =>
{
    Console.WriteLine("C ▶ in");
    await next(ctx);
    Console.WriteLine("C ◀ out  HasStarted=" + ctx.Response.HasStarted);
    if (ctx.Request.Query.ContainsKey("late"))
        ctx.Response.Headers["X-Late"] = "oops";   // 会抛 InvalidOperationException
});

app.MapGet("/", () =>
{
    Console.WriteLine("★ endpoint");
    return "hello";
});

app.Run();

测验

❓ 一个 IHttpModule 在 BeginRequest 里调 Response.End() 拦截请求。迁移成中间件后，行为上最大的差别是？
它前面已进入的中间件仍会执行 next 之后的代码
它后面注册的中间件仍会各自执行一次自己的 before
必须显式抛出异常才能阻止端点被路由中间件执行
短路后框架会自动把状态码从二百改写成四零三
❓ 你只写了 app.UseForwardedHeaders(); app.MapGet(…)，没写 UseRouting。实际管道里 ForwardedHeaders 和 Routing 谁先？
ForwardedHeaders 先，因为它在源码中出现得更早
Routing 先，因为框架把它自动补在了管道最前
两者并行，因为只有终结中间件才有先后之分
编译报错，因为有端点时必须显式调用路由中间件
❓ app.MapWhen(p, b => b.Use(日志中间件))——分支里只有一个会调 next 的 Use，没有 Run。命中 p 的请求最终得到什么？
分支跑完接回主线，由后面的端点正常返回二百
分支末尾没有终结委托，请求以四零四结束
框架检测到分支为空会在启动阶段抛出异常
主线上的端点执行两次，分别来自主线和分支
❓ 想在每个响应上加 X-Request-Id 头。下面哪种写法在端点返回 JSON 后不会抛异常？
在 await next 之后判断状态码为二百再设置该头
在 await next 之前用 OnStarting 注册设置该头
在 await next 之后先清空响应体然后再设置该头
在 Run 终结委托内部设置该头然后不再调用端点
