第 1 课：Program.cs 解剖——从 Global.asax 到 WebApplication

模块：项目基础（1/1） |  预计阅读/练习时间：30 分钟  |  环境：.NET 10 SDK（已安装 10.0.400）

Web API 2 时代，一个项目的"启动"散落在四个地方：Global.asax 的 Application_Start、 App_Start/WebApiConfig.cs 的 Register、web.config 的几十行 XML，以及你看不见的 IIS 管道。 ASP.NET Core 把这四样全部收进一个文件、十几行代码——Program.cs。

好消息：你在 .NET Platform 第 9 课 已经学过 Host.CreateApplicationBuilder。WebApplication.CreateBuilder 就是它再叠三层 Web 专属的东西：Kestrel、 ASPNETCORE_ 环境变量、以及一条自动帮你排好的中间件管道。本课只讲这三层，Host 部分不重复。

  • 把 dotnet new webapi 生成的 Program.cs 逐行对应到 Web API 2 的旧位置
  • 理解启动的两个阶段：builder（注册）→ Build() → app（管道），以及为什么 Build 之后不能再注册服务
  • 搞清 WebApplication.CreateBuilder 在 Generic Host 之上多做了什么
  • 掌握环境管理：launchSettings.json、ASPNETCORE_ENVIRONMENT、appsettings.{Env}.json 三者的分工
  • 亲手跑通一个 API，并让它在 Development / Staging 两个环境下表现不同（任务书目标之一）

Web API 2 vs ASP.NET Core：启动代码去哪了

Web API 2（Framework 4.8）ASP.NET Core做什么
Global.asax → Application_Start Program.cs 顶层语句 进程入口，IIS 触发 → 现在是普通 Main
WebApiConfig.Register(HttpConfiguration) builder.Services.Add…() + app.Map…() 路由、格式化器、过滤器、服务注册
GlobalConfiguration.Configuration.DependencyResolver builder.Services（内置 DI） 依赖注入——不再是可选插件
web.config <appSettings> appsettings.json + 环境变量 业务配置
web.config <system.webServer> / <httpModules> app.Use…() 中间件（第 3–4 课） 请求管道
IIS + System.Web（进程外托管） Kestrel（进程内，自宿主）（第 2 课） Web 服务器
Web.Debug.config / Web.Release.config 转换 appsettings.{Environment}.json 按环境切换配置
OWIN/Katana 熟悉者注意：如果你用过 Startup.Configuration(IAppBuilder app)，ASP.NET Core 的 app.Use… 就是它的直系后代——同样的 "builder 上串中间件" 思路，只是 IAppBuilder 变成了 IApplicationBuilder， Func<IDictionary<string,object>, Task> 变成了 RequestDelegate。

逐行解剖：dotnet new webapi 生成的 Program.cs

下面是 .NET 10 SDK 生成的原文（删掉了 WeatherForecast 示例数据），每一行右侧标注它在 Web API 2 里的"前身"：

// ── 阶段 1：builder（注册） ─────────────────────────────────────
var builder = WebApplication.CreateBuilder(args);   // ≈ Global.asax + web.config 加载 + IIS 启动，一行搞定

builder.Services.AddOpenApi();                       // ≈ WebApiConfig 里 config.EnableSwagger()
                                                     //   builder.Services 就是 IServiceCollection（平台第 4 课）

// ── 阶段 2：Build（冻结） ───────────────────────────────────────
var app = builder.Build();                           // 构建 DI 容器 + Host + Kestrel；此后 Services 只读

// ── 阶段 3：app（管道） ─────────────────────────────────────────
if (app.Environment.IsDevelopment())                 // ≈ #if DEBUG / web.config 的 debug="true"
{
    app.MapOpenApi();                                //   只在开发环境暴露 /openapi/v1.json
}

app.UseHttpsRedirection();                           // ≈ IIS URL Rewrite 的 HTTPS 规则 —— 现在是一个中间件

app.MapGet("/weatherforecast", () => ...)           // ≈ 一个 ApiController 的 GET Action（Minimal API 形式）
   .WithName("GetWeatherForecast");

app.Run();                                           // 启动 Kestrel，阻塞直到 Ctrl+C / SIGTERM

三个阶段，一个铁律

Rule

Build() 是分水岭：之前只能注册，之后只能使用

builder.Build() 会把 IServiceCollection 构建成 IServiceProvider，然后把集合标记为只读。 Build 之后再调 builder.Services.AddScoped<…>() 会抛 InvalidOperationException: The service collection cannot be modified because it is read-only。 这和 Web API 2 完全不同——GlobalConfiguration.Configuration 在运行时随时可改（虽然不该改）。 

WebApplication.CreateBuilder(args)
   │  builder.Configuration   ← 读配置（appsettings / 环境变量 / 命令行）
   │  builder.Services        ← 注册服务（IServiceCollection，可写）
   │  builder.Environment     ← IWebHostEnvironment（此时已可用！）
   │  builder.Logging / builder.WebHost / builder.Host
   ▼
builder.Build()               ← DI 容器构建、Services 冻结、Kestrel 就位
   │
   ▼
app (WebApplication)
   │  app.Services            ← IServiceProvider（只读，可 GetRequiredService）
   │  app.Use…()              ← 中间件，按调用顺序串成管道
   │  app.Map…()              ← 端点（Minimal API / Controller）
   ▼
app.Run()                     ← 启动 IHost → 启动 Kestrel → 监听
为什么 builder.Environment 在 Build 之前就能用？ 因为环境名属于Host 配置（平台第 9 课），在 CreateBuilder 内部第一步就读完了。 所以 if (builder.Environment.IsDevelopment()) builder.Services.Add… 是合法且常见的写法——按环境注册不同实现。

WebApplication.CreateBuilder 比 Host.CreateApplicationBuilder 多做了什么

你已知 Generic Host 默认做的事（DOTNET_ 环境变量、appsettings 链、Console 日志、Development 下 ValidateScopes）。 WebApplication.CreateBuilder 在其上叠加的 Web 层，按 官方文档 和 Andrew Lock 的源码分析，主要是三块：

叠加层内容Web API 2 对应
① 配置 额外读 ASPNETCORE_ 前缀环境变量（ASPNETCORE_ENVIRONMENT、ASPNETCORE_URLS、ASPNETCORE_CONTENTROOT）；命令行 --environment、--urls web.config + IIS 站点绑定
② 服务器与服务 注册 Kestrel、IIS 进程内集成（Windows）、HostFiltering、路由服务；注册 IWebHostEnvironment（比 IHostEnvironment 多一个 WebRootPath = wwwroot） System.Web + IIS
③ 自动中间件 Development 下首位插入 UseDeveloperExceptionPage；若有端点则自动 UseRouting（开头）+ UseEndpoints（末尾）；若注册了认证/授权服务则自动 UseAuthentication / UseAuthorization customErrors + 路由表 + 认证模块

③ 的效果等价于框架替你写了这段（文档原文）：

if (isDevelopment)              app.UseDeveloperExceptionPage();
app.UseRouting();
if (isAuthenticationConfigured) app.UseAuthentication();
if (isAuthorizationConfigured)  app.UseAuthorization();
// ← 你写的 app.Use…() 和 app.Map…() 都在这里
app.UseEndpoints(e => { });
陷阱："自动"只在你没显式调用时生效。一旦你自己写了 app.UseRouting()，框架就不再插入， 位置完全由你负责——这在第 3 课中间件顺序里会反复出现（典型事故：UseAuthorization 放在 UseRouting 之前）。
.NET 8+ 的两个兄弟：WebApplication.CreateSlimBuilder（面向 Native AOT，去掉 IIS 集成、HTTPS 默认配置、正则路由约束等）和 CreateEmptyBuilder（什么都不注册，全手动）。本系列一律用 CreateBuilder； 见 CreateSlimBuilder 文档。

项目里其他文件：谁管环境

dotnet new webapi 生成 6 个文件。和环境有关的三个，职责边界必须分清：

HelloApi/
 ├── HelloApi.csproj                ← <Project Sdk="Microsoft.NET.Sdk.Web">：Web SDK 隐式引用整个 ASP.NET Core 共享框架
 ├── Program.cs
 ├── appsettings.json               ← 所有环境的基础配置（✔ 部署）
 ├── appsettings.Development.json   ← 仅 Development 时叠加覆盖（✔ 部署但生产不读）
 ├── Properties/launchSettings.json ← 仅 dotnet run / VS / VS Code 本机启动用（✘ 不部署）
 └── HelloApi.http                  ← VS / VS Code 的 REST 测试文件，与运行无关

环境名是怎么定下来的

本机 dotnet run

读 launchSettings.json 第一个 commandName: "Project" 的 profile，把其中的 environmentVariables（模板里是 ASPNETCORE_ENVIRONMENT=Development）和 applicationUrl 注入进程。它覆盖系统环境变量。

部署后（dotnet HelloApi.dll / 容器 / IIS）

launchSettings.json 根本不存在。环境只来自真正的环境变量或命令行 --environment。没设就是 Production——开发者异常页、OpenAPI 全部关闭。

两个变量都设了？

官方文档明确： 使用 WebApplication 时，DOTNET_ENVIRONMENT 的优先级高于 ASPNETCORE_ENVIRONMENT （老的 WebHost 相反）。原因是 WebApplicationBuilder 内部先读 ASPNETCORE_ 再读 DOTNET_，后加载者覆盖。 实践建议：一台机器上只用一个，Web 项目统一 ASPNETCORE_ENVIRONMENT。

环境名一旦定下，配置链就按它加载（平台第 7 课的顺序，Web 项目完全相同）：

appsettings.json → appsettings.{Env}.json → User Secrets（仅 Dev） → 环境变量 → 命令行
后者覆盖前者

动手：让 API 在两个环境下表现不同

每一步都有预期输出——看到就对，看不到就停下来问我。全程 PowerShell。

生成并运行

cd D:\teach\ASPNET Core
dotnet new webapi -n HelloApi -o playground\HelloApi
cd playground\HelloApi
dotnet run

预期看到（端口号可能不同）：

info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://localhost:5249
info: Microsoft.Hosting.Lifetime[0]
      Hosting environment: Development
info: Microsoft.Hosting.Lifetime[0]
      Content root path: D:\teach\ASPNET Core\playground\HelloApi

三行信息 = 本课三个概念：Kestrel 在监听、环境是 Development（来自 launchSettings.json）、Content root 是配置文件所在目录。

浏览器打开 http://localhost:5249/openapi/v1.json 应看到 JSON 文档；/weatherforecast 应看到 5 条天气。Ctrl+C 停止。

加一个暴露环境信息的端点

在 app.UseHttpsRedirection(); 之后加：

app.MapGet("/env", (IWebHostEnvironment env, IConfiguration cfg) => new
{
    env.EnvironmentName,
    env.ContentRootPath,
    env.WebRootPath,
    Greeting = cfg["Greeting"] ?? "(未配置)"
});

注意参数直接从 DI 注入——这是 Minimal API 的参数绑定，第 5 课详讲；现在只需知道"注册过的服务可以直接写在 lambda 参数里"。

再运行，访问 /env，预期："environmentName":"Development"，"webRootPath":null（API 模板没有 wwwroot 目录，目录不存在时该属性就是 null），"greeting":"(未配置)"。

给两个环境不同的配置

在 appsettings.Development.json 加 "Greeting": "hi from dev"；新建 appsettings.Staging.json，内容 { "Greeting": "hi from staging" }。

运行 dotnet run，访问 /env，预期 "greeting":"hi from dev"。

绕过 launchSettings.json，切到 Staging

$Env:ASPNETCORE_ENVIRONMENT = "Staging"
dotnet run --no-launch-profile

预期两处变化：

  • Hosting environment: Staging
  • Now listening on: http://localhost:5000——端口变了！因为 applicationUrl 也来自 launchSettings.json，不用它就回到 Kestrel 默认的 5000
这台机器上 5000 端口会绑定失败（Failed to bind to address http://localhost:5000 … SocketException (10013)）： Windows 把 4904–5003 保留给了 Hyper-V/WSL（netsh interface ipv4 show excludedportrange protocol=tcp 可见）。 用命令行参数换端口——这本身就是本课知识点（--urls 是 ASPNETCORE_URLS 的命令行形式）： 
dotnet run --no-launch-profile --urls http://localhost:5100

访问 http://localhost:5100/env → "environmentName":"Staging"、"greeting":"hi from staging"；访问 /openapi/v1.json → 404（MapOpenApi 被 IsDevelopment() 挡住了）。

验证 Build 之后的铁律

在 var app = builder.Build(); 的下一行加 builder.Services.AddSingleton<object>();，运行。预期启动即崩：

Unhandled exception. System.InvalidOperationException:
The service collection cannot be modified because it is read-only.
   at Microsoft.Extensions.DependencyInjection.ServiceCollection.ThrowReadOnlyException()

删掉这一行。最后 Remove-Item Env:ASPNETCORE_ENVIRONMENT 清掉环境变量，免得下节课困惑。

测验

考的是机制，不是"现代框架应该怎么做"的直觉。答之前先回忆本课具体哪一段讲了它。
❓ 系统环境变量里同时有 DOTNET_ENVIRONMENT=Staging 和 ASPNETCORE_ENVIRONMENT=Development，用 dotnet HelloApi.dll 启动。app.Environment.EnvironmentName 是？
Development，因为 ASPNETCORE_ 前缀是 Web 专用、更具体的那个
Staging，因为 DOTNET_ 前缀的变量在其后加载、覆盖了前者
Production，因为两个变量冲突时框架会退回到默认环境名
启动失败，因为两个前缀同时设置会被当作配置冲突而报错
❓ 你 dotnet publish 后把输出目录拷到一台干净的 Linux 机器，直接 dotnet HelloApi.dll。访问 /openapi/v1.json 会得到什么？
200 并返回文档，因为 launchSettings.json 里设了 Development 环境
404，因为环境默认是 Production，MapOpenApi 那段代码没执行
500，因为 Production 环境下 OpenAPI 服务未注册导致启动时抛异常
200 并返回文档，因为 AddOpenApi 已注册、端点映射与环境是无关的
❓ Program.cs 里只有 app.MapGet("/", () => "hi")，从未调用 app.UseRouting()。请求 / 会怎样？
404，因为没有 UseRouting 就没有路由匹配，端点根本不会被命中
启动时抛异常，提示必须先调用 UseRouting 才能映射任何端点
200 返回 hi，因为框架检测到有端点后自动补上了路由中间件
200 返回 hi，因为 Minimal API 的端点不经过路由、由 Kestrel 直接分发
❓ 想在 Development 环境注册 FakeEmailSender，其他环境注册 SmtpEmailSender。下面哪种写法正确？
必须先 Build 拿到 app.Environment 判断，再回头往 builder.Services 里注册
直接在 Build 之前用 builder.Environment.IsDevelopment() 判断后注册即可
在 Build 之前读不到环境，只能两个都注册，运行时再按环境名挑一个
改用 Environment.GetEnvironmentVariable 直接读系统变量，绕过 builder
