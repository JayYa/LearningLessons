vs IHttpModule模块按 HttpApplication 事件 + web.config 顺序；中间件按注册顺序。模块请求/响应同序；中间件响应逆序。Response.End() 硬中断不存在。

四种注册 API

APInext分支后
Use(async (ctx, next) => { …; await next(ctx); …; })自己决定—
Run(async ctx => …)无，终结—
Map("/prefix", b => …) · MapWhen(pred, b => …)—不回主线；分支无终结委托 → 404
UseWhen(pred, b => …)—接回主线

MapGet / MapControllers 注册的是端点，不是中间件；由 UseRouting 匹配、UseEndpoints 执行。

执行模型

请求  A.before → B.before → C.before → 端点
响应  A.after  ← B.after  ← C.after  ←──┘        注册顺序 = 请求顺序；响应逆序

短路  A.before → B(不调 next)                    C/端点不跑；A.after 照跑
异常  A.before → B.before → C 抛                 B.after / A.after 全跳过 → 只有最外层 UseExceptionHandler 能接

HasStarted

症状InvalidOperationException: Headers are read-only, response has already started
原因await next(ctx) 之后改 StatusCode / Headers，但端点已写 body
判断ctx.Response.HasStarted
正解
app.Use(async (ctx, next) =>
{
    ctx.Response.OnStarting(() =>
    {
        ctx.Response.Headers["X-Request-Id"] = ctx.TraceIdentifier;
        return Task.CompletedTask;
    });
    await next(ctx);
});

官方推荐顺序（Web API 精简版）

app.UseForwardedHeaders();      // 代理后面：最前
if (!app.Environment.IsDevelopment()) { app.UseExceptionHandler("/error"); app.UseHsts(); }
app.UseHttpsRedirection();
app.UseStaticFiles();           // 命中即短路
app.UseRouting();               // 匹配端点（不执行）
// app.UseRateLimiter();        // 用 [EnableRateLimiting] 时必须在 Routing 后
// app.UseCors();               // 必须在 Authentication 前、ResponseCaching 前
app.UseAuthentication();
app.UseAuthorization();         // 必须在 Routing 后
// app.UseResponseCaching(); app.UseResponseCompression();
app.MapControllers();           // 端点；UseEndpoints 由框架补在末尾

WebApplication 自动补的中间件

条件补什么补在哪
有端点且未调 UseRoutingUseRouting管道最前
注册了 AddAuthentication 且未调 UseAuthenticationUseAuthentication紧跟 Routing
注册了 AddAuthorization 且未调 UseAuthorizationUseAuthorization再往后
总是UseEndpoints管道末尾

结论：想让中间件在路由匹配前跑（ForwardedHeaders、StaticFiles、CORS 全局策略），必须显式 app.UseRouting() 并放在它前面。用了 UseCors 就要显式写 UseAuthentication / UseAuthorization。
