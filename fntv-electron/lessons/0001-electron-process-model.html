第 1 课 · Lesson 01

Electron 的进程模型

——— 不是抽象讲解，而是落在 fntv-electron 这 12,800 行代码上

这一课的战果：app 在你机器上跑起来；并且拿到仓库里任何一个文件， 你都能立刻说出它跑在哪个进程里。这是后面做「新增播放器」和「进度同步」的地基 —— 因为这两件事都发生在主进程，而你需要先知道那是哪儿。

一、必须先知道的那点知识

Electron 把一个桌面 app 拆成多个进程。官方定义里有三个角色和你有关 （Electron 官方文档 · Process Model）：

角色它是什么能碰到什么
main
主进程		 「应用的入口」，跑在一个 Node.js 环境里。全 app 只有一个。 开窗口、管生命周期、调系统 API。 Node、文件系统、子进程、Electron 全部 API
但碰不到网页的 DOM
renderer
渲染进程		 「负责渲染网页内容」。每个窗口一个，本质就是个浏览器标签页。 DOM、浏览器 API
默认拿不到 Node
preload
预加载脚本		 「在渲染进程的网页内容开始加载之前执行」的脚本。唯一同时站在两边的角色。 Node 和 DOM 都能碰

为什么要这么拆？因为渲染进程里跑的是不完全可信的网页。 如果网页能直接调 fs.unlink()，一个 XSS 就等于本机删文件。 所以 Electron 默认把网页关在浏览器沙箱里，只留 preload 一个受控的口子 （Context Isolation）。

二、这个仓库的反常识之处

大多数 Electron 教程里，你自己写界面，所以 renderer 代码最多。 fntv-electron 反过来——它几乎没有渲染进程代码。

证据在 src/main/common/mainwin.ts，窗口的配置：

webPreferences: {
    partition: 'persist:fntv',
    preload: path.join(__dirname, '../../preload/index.js'),   // ← 注入的桥
    nodeIntegration: false,      // ← 页面拿不到 Node
    contextIsolation: true,      // ← 页面与 preload 隔离
    sandbox: false,
}

这个窗口加载的是飞牛服务器上的 Web UI——界面不是这个项目写的。 项目做的是：用 src/preload/ 里的脚本，往那个别人的页面上 注入自己的标题栏、播放按钮；然后把「真正想干的事」通过 IPC 甩给主进程去做。

所以仓库的重心长这样：

目录进程它在干嘛
src/main/主进程入口、窗口、托盘、IPC handler
src/modules/主进程被主进程 import 的业务模块（API / 播放器 / 配置）
src/preload/预加载往远程页面注入按钮、桥接 IPC
resource/login/渲染进程唯一的本地页面：登录页
判定口诀（记这个，比记目录名有用）：
能 import { app, BrowserWindow } 的 → 主进程
能同时用 fs 和 document 的 → 预加载
只能用 document 的 → 渲染进程

三、任务 A：让它跑起来

动手 · 约 5 分钟

在 repo/ 目录下依次执行

cd repo
npm install
npm run compile
npx electron .

应该弹出一个窗口，让你填 fnOS 地址或登录。能看到窗口 = 任务完成， 先别急着深入用它。

不要用 npm start。 它会先执行 build:proxy:win，那一步要调用 go build 编译 src/modules/proxy/ 里的 Go 代理——而你机器上没装 Go，会直接报错。

npm run compile + npx electron . 是绕开它的等价路径： 只编译 TypeScript，然后启动。代理是个独立的 sidecar 进程，主流程不依赖它也能起窗口。 （想要完整功能时再装 Go 不迟——那属于 Mission 里暂时划到范围外的部分。）

顺手做一个观察

app 起来后，看你的终端。src/main/main.ts 开头有这么几行：

log.info('=== 飞牛影视启动 ===');
log.info('应用版本:', app.getVersion());
log.info('Electron版本:', process.versions.electron);

这些日志只会出现在终端里，不会出现在窗口的 DevTools 里。 为什么？因为 main.ts 跑在主进程——它根本不在浏览器里。 这个现象比任何解释都更能让你记住：两个进程是真的分开的。

四、任务 B：归位练习

下面每一题都是仓库里的真实文件。别翻代码，凭刚才的口诀判断—— 答错比查对更有价值，错误会告诉你哪条界线还没建立。

src/main/handlers/plugins/media.ts——播放编排逻辑

主进程。它在 src/main/ 下，负责接 IPC 请求、拉起播放器。 这个文件是你 Mission 里「进度同步」的中枢，第 3 课会精读它。

src/preload/plugins/titlebar.ts——自定义标题栏

预加载。它要操作远程页面的 DOM 把标题栏画上去（需要 document）， 又要通过 ipcRenderer 告诉主进程「最小化窗口」（需要 Node 侧能力）。 两边都要——这正是 preload 存在的理由。

src/modules/players/impl/mpv.ts——拉起 mpv 播放器

主进程。这题是陷阱：它不在 src/main/ 下，而在 src/modules/。决定进程归属的不是目录名，而是谁 import 它。 media.ts（主进程）import 了它，所以它跑在主进程。
而且它要 spawn 一个 mpv 子进程——只有主进程干得了这事。 这个文件是你 Mission 里「新增播放器」要照抄的范本。

resource/login/ 里页面自己的脚本

渲染进程。全仓库几乎唯一的 renderer 代码。它连 require 都没有——只能用 preload 通过 contextBridge.exposeInMainWorld 递给它的那几个方法。 去 src/preload/index.ts 看 SEND_CHANNELS 白名单， 那就是这个页面被允许做的全部事情。

为什么这个项目的渲染进程代码这么少？

界面由远程服务器提供。窗口加载的是飞牛 NAS 上的 Web UI， 不是本项目写的页面。所以「改 UI」在这个项目里意味着写注入脚本 （src/preload/plugins/），而不是写组件。

nodeIntegration:false + contextIsolation:true 的后果是

无法直接使用 Node。这是 Electron 的安全基线 （Security Checklist）。 加载的是别人服务器上的页面，一旦它能调 fs，风险不可控。
实际影响：你以后想给页面加任何新能力，都必须走 「preload 白名单 → IPC → 主进程 handler」这条路，没有捷径。 第 2 课就练这条路。

六、下一课预告

第 2 课：亲手走通一次 IPC 往返。 你会在 preload 白名单里加一个 channel、在主进程写一个 handler， 让远程页面能问主进程要一个它自己拿不到的东西。 走通这条路，你就具备了给这个项目加任何功能的基本形状。
