二、补偿不是回滚

先给定义。Chris Richardson 的 microservices.io 是这个模式的规范出处：

A saga is a sequence of local transactions. Each local transaction updates the database and publishes a message or event to trigger the next local transaction in the saga.
If a local transaction fails because it violates a business rule then the saga executes a series of compensating transactions that undo the changes that were made by the preceding local transactions.
—— microservices.io, Pattern: Saga

把它对到你那次对接上，一一对应：

Saga 术语你那次是什么
local transaction（本地事务）调第三方的第 1、2、3 个同步接口，每个都是对方的一次本地提交
compensating transaction（补偿事务）第三方提供的那些回退接口
orchestrator（协调者）你的代码——是你在按顺序调、按逆序退
saga 的失败路径第 3 步挂了 → 逆序调第 2、第 1 的回退 → 再撤回自己库里的数据

现在讲这一节最重要的一句话。补偿（compensation）和回滚（rollback）不是一回事，Richardson 明确点出了这个区别：

A developer must design compensating transactions that explicitly undo changes made earlier in a saga rather than relying on the automatic rollback feature of ACID transactions.

数据库回滚Saga 补偿
谁做的数据库引擎自动做你手写的业务代码
做完之后像什么都没发生过留下痕迹：一笔正向记录 + 一笔反向记录
中间状态外界看不见外界看得见，别人可能已经读到并据此做了决定
会不会失败基本不会会——补偿本身也是一次网络调用，见第三节
扩展 · 「外界看得见」这件事有个正式名字

叫 lack of isolation（缺少隔离性）。Richardson：The lack of isolation means that there is risk that the concurrent execution of multiple sagas and transactions can [cause] data anomalies. Consequently, a saga developer must typically use countermeasures, which are design techniques that implement isolation.

ACID 四个字母里，Saga 保住了 A（原子性，靠补偿模拟）、C、D，唯独丢了 I。最常用的对策叫语义锁：给记录加一个中间状态（比如订单从「已提交」先进「处理中」，而不是直接进「已完成」），别人看到这个状态就知道「这笔还没定，别动」。

面试被追问到「补偿期间别人读到了脏数据怎么办」——答Saga 牺牲的是隔离性，实践里用语义锁，给一个业务上的中间态把它挡住，这一句的含金量很高。

三、回退接口自己失败了呢

这是你当年大概率没被逼问过、但面试官一定会问的那一层。补偿调用也是网络调用，Lesson 04 第二节那四种结局，它一个都躲不掉。

下面把「我方调第三方的回退接口」这一跳单独拎出来。先猜，再点：

这一节的一句话

补偿必须是「持久化 + 可无限重试 + 幂等」的；写在 catch 块里调一次的补偿，等于没有补偿。面试里主动说出这句，等于宣告你不是从文章上读来的。

四、补偿的三个坑

这三个坑在国内是标准考点（阿里 Seata 的 TCC 文档把它们列为必须处理的三件事）。它们不是 TCC 专有的，任何补偿型分布式事务都会遇到，包括你那次对接。

坑怎么发生的怎么防
① 空补偿
（空回滚）		正向请求根本没到对方，或者对方还没执行，补偿请求就先到了。对方收到一个「撤销一件从没发生过的事」的请求补偿方查不到对应的正向记录时，直接返回成功并留痕，绝不报错、绝不真的执行反向操作
② 悬挂更刁钻：补偿请求先到达（走了空补偿返回成功），事务已判定结束；结果那个超时的正向请求随后才到，对方老老实实执行了。于是这笔资源被永久占住，再也没人来撤补偿时留下一条「已补偿」的记录；正向请求进来先检查——发现已经被补偿过，就拒绝执行
③ 幂等补偿超时后重试，对方退了两次正向和补偿都用业务唯一键做去重表，就是 Lesson 04 那张 request_id 唯一索引表

注意 ① 和 ② 是互相纠缠的：正因为允许了空补偿（①），才产生了悬挂（②）。所以这两条必须成对实现——只做 ① 不做 ②，你就把一个明显的错误换成了一个安静的资源泄漏。

扩展 · 三个坑用同一张表一起解决

被调方（对方，或者你自己作为被调方）维护一张 tx_log：(biz_id PRIMARY KEY, state)，state ∈ {DONE, COMPENSATED}。

  • 正向请求进来：biz_id 已存在且为 DONE → 幂等，直接返回（③）；已存在且为 COMPENSATED → 拒绝执行（② 防悬挂）；不存在 → 同一个本地事务里插 DONE + 做业务。
  • 补偿请求进来：查不到 biz_id → 插一条 COMPENSATED 并返回成功（① 空补偿，顺手防住 ②）；查到 DONE → 同一事务里改成 COMPENSATED + 做反向业务；已经是 COMPENSATED → 幂等返回（③）。

Seata 从 1.5.1 起内置了一张 tcc_fence_log 自动干这件事，原理就是上面这张表。能在白板上画出这张表并说清这几种分支，这道题就满分了。

五、你的 Solace 那套叫「协同式」

Saga 有两种协调方式，你两种都做过——这很难得：

编排式 Orchestration协同式 Choreography
官方定义An orchestrator tells the participants what local transactions to executeEach local transaction publishes domain events that trigger local transactions in other services
有没有中心有一个协调者，流程写在它里面没有中心，流程散落在各个订阅关系里
你的哪一段经历第三方对接那次：你的代码按顺序调、按逆序退Solace 那十个系统：各自订阅各自的 topic
优点流程一眼看得见，好调试服务之间彻底解耦，加一个新消费者不用改发布方
缺点协调者容易变胖，逐渐吸走业务逻辑没有任何一个地方能看到完整流程，出问题极难追
这里有一个可以主动抛出的钩子

协同式的那个缺点——「没有一个地方看得到完整流程」——正是 Lesson 04 第三节 TraceId 存在的理由。把这两件事连起来说：协同式的代价是流程不可见，所以链路追踪在这种架构里不是加分项，是必需品。我们当时排查跨系统问题主要还是靠时间戳和消息里的业务单号去对，如果重来，我会在消息头里统一带一个 trace 号。

「如果重来我会……」这个句式，是经历有缺口时最好用的一句话——它把短板转成了判断力。

你说的「message 本身就是请求与响应」

这叫 Request-Reply 消息交换模式：用消息中间件做出同步调用的语义。Solace 官方文档说它靠两个字段实现：

字段作用
ReplyTo请求方在消息头里写上「回信寄到哪个 topic / queue」。Solace 的 API 会自动生成一个唯一的 ReplyTo 目的地
CorrelationIdit must be possible for the requestor to correlate the request with the subsequent reply——响应方原样带回这个 id，请求方才能从一堆回来的消息里认出「这条是我那条请求的答复」

再加上你说的 topic 分层订阅：Solace 的 topic 是 a/b/c/.../n 形式的层级字符串，订阅方可以用 *（单层通配）和 >（尾部多层通配）来筛（Solace Docs — Understanding Topics）。这一整段都是你的加分素材——面试官问「几个微服务之间如何交互」，你能答出的东西比只会说「用 HTTP 调」的候选人多得多。

扩展 · 一个必然被追问的问题，请提前想好

「用消息做请求-响应，和直接 HTTP 调用，有什么区别？」好答案有三层：

  • 解耦：发布方不需要知道谁在消费，加消费者不用改代码；HTTP 必须知道对方地址。
  • 削峰与可用性：对方短暂不可用时消息在 broker 里排队，恢复后继续；HTTP 当场就失败了。
  • 代价：延迟更高，而且你必须自己处理超时——HTTP 有天然的连接超时，消息式请求-响应里「回信一直不来」需要你自己设定时器和兜底。而且响应消息一样可能丢，所以消费仍然必须幂等（又回到 Lesson 04 那一句）。

六、三段话术

下面三段全部挂在你的真事上。不要背，要能用自己的话讲出同样的结构。

话术 A · 对应题「微服务的了解」「几个微服务之间如何交互」

结论：我上一个系统是十个左右的服务，每个服务有自己独立的数据库，服务之间不直接调，全部通过 Solace 这个消息中间件通信。

机制：交互方式是主题订阅：每个系统发布到自己的 topic，需要的系统去订阅，Solace 的 topic 是分层的，可以用通配符订阅一整类事件。有些交互是请求-响应式的，消息头里带 ReplyTo 和 CorrelationId，请求方靠 CorrelationId 把回来的响应和自己发出去的请求对上。

取舍（这段最值钱）：这种做法在 Saga 的分类里叫协同式，好处是彻底解耦——加一个新的消费方，发布方完全不用动。代价是没有任何一个地方能看到完整的业务流程，流程散在各个订阅关系里，出问题很难追。我们当时主要靠消息里的业务单号去各系统对日志。如果重来，我会在消息头里统一带一个 TraceId 贯穿全链路。

为什么这样答强：「库独立」是微服务的硬指标，很多号称微服务的系统其实共用一个库、那叫分布式单体。你主动点出这一条，等于告诉面试官你知道真假微服务的分界线在哪。

话术 B · 对应题「和第三方交互时如何保证数据一致性」

结论：那次是同步接口，走的是 Saga 的补偿事务，编排式的——协调逻辑在我这边。第三方提供了每一步的回退接口，任何一步失败，我就按逆序调用前面各步的回退，最后再撤我自己库里的数据。

关键认知：这里最重要的一点是补偿不等于回滚。数据库回滚是引擎自动做的、干净的；补偿是我手写的业务代码，做完之后数据上会留下一正一反两条记录，而且补偿本身也是一次网络调用，它自己也会失败。

踩过 / 想过的坑：所以补偿不能写在 catch 块里调一次就算数。要把补偿意图先落到自己库里的一张状态表，由后台任务持续重试，超过阈值就告警转人工。另外对第三方的回退接口有三个要求：要幂等，因为超时后我一定会重试；要允许空补偿，因为可能正向请求压根没到、它就先收到了回退；还要防悬挂——补偿先到、正向后到的话，那笔资源会被永久占住。

如果被追问「你们当时全做到了吗」：诚实答。幂等我们要求了；空补偿和悬挂当时没有系统性地防，出问题是靠对账发现再人工处理的。这三个坑是我后来复盘才想清楚的。——这个回答比声称全做到了强，因为它证明你事后复盘过，而不是照着文档背。

话术 C · 对应题「RabbitMQ 如何消费 / 用过哪些 MQ」（诚实定位型）

先划边界，别硬撑：RabbitMQ 我用得不深，主要是两类场景：日志文本的异步处理，和各系统之间的缓存失效通知。消息量级和业务重要性都不高。

立刻转成判断力（这是全段的重点）：不过这两个场景恰好说明了一个取舍：它们都是丢一条也不致命的场景——日志丢一条不影响业务，缓存通知丢了下次读会回源。所以当时没做 ACK 之外的额外保障。但如果是业务消息，比如订单状态变更，我就必须加三样东西：发送端用本地消息表，保证「写库」和「发消息」不会只成功一半；消费端必须幂等，因为 MQ 是至少一次投递；ACK 一定手动，业务处理完再 ACK，不能用自动 ACK。

再把重量级经历拉回来：我更主要的消息中间件经历是在 Solace 上，那边是十个系统的主干通信链路。

为什么这样答强：把「用过什么」和「知道该怎么选」分开，是 Lesson 04 网关那段用过的同一招。承认边界再展示判断力，几乎从不扣分；硬撑被追问三层则必崩。

八、下一课与两个问题

下一课（Lesson 06）＝ 原定的选型课：该不该拆、边界怎么划、以及题库那道「运维成本高、交互复杂，为什么还选微服务」。它被推迟了一课，因为你的三条回答改变了它的写法——现在它能用你自己那十个服务当案例，讨论「这十个的边界划得对不对」，而不是拿一个虚构的电商例子。这比原计划好得多。

为了写好它，我需要两个信息：

  1. 那十个系统是按什么划开的？按业务领域（订单 / 结算 / 风控……）、按团队、还是按前后端或历史遗留？有没有哪一次改需求，你不得不同时改三四个系统才能上线？（这个「一改就要改一串」的现象是边界划错的最经典信号，有的话就是最好的素材；没有反而说明边界划得好，同样是素材。）
  2. 题库里「从单一服务扩展到微服务」那道题——你有没有亲历过某个单体被拆开的过程，还是你进去的时候就已经是十个系统了？这两种情况的答法完全不同。
