一、先破一个错觉

「用户遇到访问慢，如何排查」——大多数人的第一反应是列原因：SQL 没走索引、代码里有 .Result、第三方接口慢、网络不好……然后面试官听到的是一张猜测清单。清单再长也是猜，而且面试官随便追一句「你怎么知道是哪一个」就没了。

Google SRE 那本书把监控要回答的问题压成了一句（Monitoring Distributed Systems）：what's broken, and why?——前半句是症状，后半句是原因；先答前半句。「慢」是症状。一次请求的时间总是花在某个具体的地方：某条 SQL、某次下游调用、某段等线程池的空白、某个 4 MB 的响应体在用户的 4G 上下载。排查的本质不是猜原因，是把「慢」定位到那个地方，定位到了，原因通常就是显然的。

这一课唯一必须记死的一句

先定位，再解释：一次慢请求的时间一定花在某一跳上，先用指标缩小到哪一层、用追踪找到哪一跳，再用日志和 profiler 问它为什么慢。

下面按这个顺序走：第二节用三个二分问题把范围缩到一层，第三节在追踪图上找那一跳，第四、五节把工具挂到每一层，第六节讲日志要怎么打才能在第三步派上用场，第七节回答吞吐率。

三、排查实验室：五张追踪图，点出时间去哪了

范围缩到一层之后，下一步是找那一跳。工具是分布式追踪（trace）：一次请求经过的每一段——中间件、SQL、下游 HTTP、序列化——各自记一个 span，带开始时间和时长，画出来就是瀑布图。Lesson 04 讲过它靠 traceparent 头跨进程，.NET 的 Activity 自动产生。这里直接看图。

五个场景，每个都是一条真实形态的慢请求，上方是当时仪表盘上的几个数。先点你认为的瓶颈那一段，再看判定。点错也有提示。

五张图，一个规律

追踪图回答的只有一个问题：时间在哪。它给出四种答案——在某一段里（① ④）、在某一段的次数里（②）、在没有段的空白里（③）、根本不在服务器上（⑤）。第三种最容易被忽略：span 加起来远小于总时长，本身就是发现——差额是排队、等线程、GC 暂停这些没人打点的东西。

四、三根支柱各答一个问题：指标 / 追踪 / 日志

前两节用了两样东西：仪表盘上的几个数（指标）和瀑布图（追踪）。第三样是日志。Microsoft 把这三样叫可观测性的三根支柱（.NET Observability with OpenTelemetry），各自的定义：

支柱原文定义它回答的问题.NET 里的 API
指标 Metricsmeasuring counters and gauges such as number of completed requests, active requests ... or a histogram of the request latency——计数器、仪表和直方图：完成了多少请求、活跃多少、延迟分布什么时候开始的、多严重、影响多大范围。便宜、可长期存、可告警System.Diagnostics.Metrics.Meter
追踪 Tracingtracks requests and activities across components in a distributed system so that you can see where time is spent——跨组件跟踪一次请求，看时间花在哪这一次请求的时间在哪一跳。第三节的图System.Diagnostics.Activity / ActivitySource
日志 Logsrecord individual operations, such as an incoming request, a failure in a specific component——记录单个操作：一次请求、某个组件的一次失败那一跳里到底发生了什么：参数、异常、分支。最贵、最细ILogger<T>

三者的顺序就是排查的顺序：指标告诉你去看哪里，追踪告诉你看哪一跳，日志告诉你那一跳里发生了什么。反过来用（从日志开始翻）是新手最常见的浪费——日志最多、最乱、最没有方向。

扩展 · OpenTelemetry 是什么，以及「用过哪些检测服务」怎么答

三根支柱各有一堆后端：指标常见 Prometheus + Grafana，追踪常见 Jaeger / Zipkin，日志常见 ELK / Seq；Azure 上三样合一叫 Application Insights。以前每家有自己的 SDK，换后端要改代码。OpenTelemetry（OTel）把采集标准化了：a cross-platform, open standard for collecting and emitting telemetry data，应用只对着 OTel 的 API 写（.NET 里就是上表那三个自带 API），用 OTLP 协议发给任意后端。Microsoft 的原话：Using OTel means that applications don't need to use APM-specific APIs or data structures; they work against the OTel standard.——用了 OTel，应用不再依赖任何一家 APM 的 API。所以「用过哪些检测服务」这题的好答法不是报产品名，是先说三根支柱各自回答什么问题，再说采集走 OTel、后端可换——然后接你真用过的那一两个。

六、日志怎么打才能排查

「用过哪些日志服务」——出题人想听的不是 NLog 还是 Serilog，是你的日志能不能用来排查。三个判据：能不能按字段查、能不能按请求串、有没有分级。

1. 结构化，不拼字符串。Microsoft 文档（Logging in .NET）：The log message template can contain placeholders for provided arguments. Use names for the placeholders, not numbers.——模板用命名占位符。为什么：The arguments themselves are passed to the logging system, not just the formatted message template. This enables logging providers to store the parameter values as fields.——参数本身传给了日志系统，不只是拼好的字符串，所以存储端能把它们存成字段。字段才能查 OrderId = 1001；拼进字符串的只能全文搜。

// ✗ 插值：OrderId 变成了字符串的一部分，日志后端里它不是一个字段
_logger.LogInformation($"订单 {order.Id} 支付超时，耗时 {elapsed}ms");

// ✓ 模板：OrderId 和 ElapsedMs 作为属性存储，可以按字段过滤、聚合、告警
_logger.LogWarning("订单 {OrderId} 支付超时，耗时 {ElapsedMs}ms", order.Id, elapsed);

2. 分级，而且生产只开到 Information。六级的官方定义（同上）：

级别原文用在
Tracemay contain sensitive app data ... should not be enabled in production可能含敏感数据，生产禁开
DebugFor debugging and development. Use with caution in production due to the high volume量大，生产慎开
InformationTracks the general flow of the app.主流程：收到请求、订单创建、状态推进
WarningFor abnormal or unexpected events ... that don't cause the app to fail.异常但没失败：重试成功了、降级了、超时后走了查询

级别按类别（category）配，类别默认是类的全名，前缀匹配："Microsoft.AspNetCore": "Warning" 一行就把框架的噪音压掉，自己的命名空间开 Information。排查时可以不重启只把某个类别临时调到 Debug——这是配置热重载给的。

3. 每条日志自动带 TraceId。Lesson 04 里那行是手动把 Activity.Current?.TraceId 写进模板。不用每条都手写——用 scope：A scope can group a set of logical operations. This grouping can be used to attach the same data to each log that's created as part of a set.——scope 把同一份数据附加到一组日志的每一条上。ASP.NET Core 自带的 IncludeScopes 会把 RequestId、TraceId、SpanId 挂进请求范围内的所有日志；Serilog 用 enricher 做同一件事。

// Serilog：结构化 + 自动附 TraceId + 写到能按字段查的后端
builder.Host.UseSerilog((ctx, cfg) => cfg
    .ReadFrom.Configuration(ctx.Configuration)          // 级别、类别覆盖都放 appsettings
    .Enrich.FromLogContext()
    .Enrich.WithProperty("Service", "order-api")
    .Enrich.WithSpan()                                   // Serilog.Enrichers.Span：TraceId / SpanId 自动进每条日志
    .WriteTo.Console(new CompactJsonFormatter())          // 容器里打 JSON 到 stdout，由采集器收
    .WriteTo.Seq("http://seq:5341"));                    // 或 ELK / Loki / App Insights —— 后端可换

// 业务代码：一个 using 把 OrderId 挂到这段里的每一条日志上
using (_logger.BeginScope(new Dictionary<string, object> { ["OrderId"] = order.Id }))
{
    _logger.LogInformation("开始调第三方支付 Provider={Provider}", provider);
    // ... 这里面的每一条日志都自动带 OrderId + TraceId + SpanId
}

三条凑齐之后，第三节场景 ④ 的排查是这样的：追踪图指出 2800 ms 在第三方那一跳 → 拿这条 trace 的 TraceId → 日志后端 TraceId = … AND Provider = … 一查，那一跳里对方到底返回了什么、我方重试了几次，全在。日志是三根支柱里最后用的，但只有前面两步做对了它才有用。

扩展 · 日志本身也会拖慢系统

三件事：① 同步写文件是阻塞 I/O——高并发下日志锁会成为瓶颈，所以生产要用异步 sink（Serilog 的 WriteTo.Async）或直接写 stdout 交给采集器；用户项目里「日志走 RabbitMQ」就是这个思路的一种实现。② 模板格式化有成本——LoggerMessage 源生成器把模板解析提前到编译期，热路径上用它；判断 IsEnabled 再拼昂贵参数。③ Debug 级别开着不写 ≠ 免费——参数装箱仍发生。这些追问时才说，正文不主动展开。

七、提升吞吐率：三个杠杆，一个前提

「如何提升系统吞吐率」。先给定义把题立住：吞吐率 = 单位时间处理完的请求数 = 并发处理数 ÷ 每个请求占用的时间。分母拆开就是三个杠杆：

杠杆做什么原文依据
① 别让线程等全链路 async：Controller → 服务 → 数据访问 → HttpClient。去掉 .Result / .Wait()；不用 Task.Run 包同步代码；返回 IAsyncEnumerable 或先 ToListAsync。这是第三节场景 ③ 的解Asynchronous APIs allow a small pool of threads to handle thousands of concurrent requests by not waiting on blocking calls.——异步让一小池线程处理上千并发。Do not call Task.Run and immediately await it ... calling Task.Run only results in extra unnecessary Thread Pool scheduling.（Best Practices）
② 让每个请求更短少往返（N+1 → JOIN / 批量）、少数据（分页、只取需要的列、只读用 no-tracking）、缓存（MemoryCache / 分布式缓存，接受稍旧的数据）、HttpClient 复用（IHttpClientFactory，否则 socket 耗尽）、避免大对象（≥ 85 KB 进 LOH）Interactions with a data store and other remote services are often the slowest parts of an ASP.NET Core app.——数据访问和远程调用通常是最慢的部分。Do consider caching frequently accessed data ... if slightly out-of-date data is acceptable.
③ 把慢活挪出请求长任务进后台服务 / 消息队列，请求只写中间态就返回；结果用 SignalR 或通知推回去Do not wait for long-running tasks to complete as part of ordinary HTTP request processing.——别在普通请求里等长任务。这正是 Lesson 13 的 PENDING 顺序在性能上的收益

一个前提：先测量。三个杠杆里先拉哪个，取决于第三节的追踪图告诉你时间在哪——空白就拉 ①，SQL 就拉 ②，下游就拉 ③。Microsoft 自己在讲完编译查询之后加了一句：We recommend measuring the impact of the preceding high-performance approaches before committing the code base.——没测量的优化是另一种猜。横向扩容（加实例）放最后说：它的前提是服务无状态（会话不在进程内存里），而且它不解决 ② 的问题——每个实例还是要跑 51 条 SQL。

八、归类练习：这个问题该问哪根支柱

判据一条：要「趋势和范围」→ 指标；要「这一次的时间去哪」→ 追踪；要「那一刻的细节」→ 日志。

九、话术

话术 A · 对应题「用户遇到访问慢，如何排查」

先立框架：「慢」是症状，不是原因，所以我不先猜原因，先定位。三个反问先把范围缩到一层：是一个用户慢还是很多用户慢？是所有接口慢还是某个接口慢？是一直慢还是最近开始慢？一个用户慢先看他的浏览器瀑布图，很可能是响应体大或者网络；所有接口都慢是共享资源的问题——线程池、连接池、CPU、下游；某个接口一直慢是它自己的设计问题；最近才慢就去找拐点，对齐发布记录和数据量。

再给工具链：缩到一层之后看这个请求的追踪，瀑布图上时间在哪一跳一目了然：一条 SQL 占了九成就去 EXPLAIN；五十条一样的小 SQL 是 N+1；span 加起来远小于总时长说明时间在排队、在等线程——配合 CPU 低、线程数缓慢上涨，就是线程池饥饿，dotnet-counters 确认、dotnet-stack 抓栈找那个 .Result。找到那一跳，再拿 TraceId 去日志里看那一跳里发生了什么。指标定层，追踪定跳，日志看细节。

接真事：（这里接一次你真的排过的慢问题，哪怕很小：一条慢 SQL、一个 N+1。用「当时看到的现象 → 定位到哪一跳 → 改了什么」三段说。没有的话说 Lesson 09 那句画像：「有一类我记得很清楚的形态是全站慢、CPU 却很低……」）

话术 B · 对应题「用过哪些日志服务」「用过哪些检测服务」「排除性能问题用过哪些工具」

日志：ASP.NET Core 里统一走 ILogger，底下 Serilog。我关心的是三件事而不是产品名：结构化——用命名占位符的模板不用字符串插值，这样 OrderId 在后端是字段，能按字段查、能聚合；关联——用 scope 或 enricher 把 TraceId 自动挂到每条日志上，不然分布式下日志串不起来；分级——生产只开 Information，框架类别压到 Warning，排查时把某个类别临时调 Debug，不用重启。写日志本身要异步，同步写文件在高并发下会成为瓶颈，我们项目里日志是走 RabbitMQ 异步落的，就是这个考虑。

检测：可观测性三根支柱：指标看趋势和范围、追踪看一次请求的时间分布、日志看细节。指标盯四个黄金信号：延迟看 p99 不看平均、流量、错误率、饱和度——线程池和连接池用了多少。采集用 OpenTelemetry，.NET 自带 Meter 和 Activity 就是它的 API，后端可以是 Prometheus + Grafana、Jaeger，Azure 上是 Application Insights，换后端不改代码。

工具：按层答：SQL 层是 pg_stat_statements 找最贵和最频繁的语句、EXPLAIN ANALYZE 看计划；进程层是 dotnet-counters 看线程数、队列、GC 这些实时读数，dotnet-stack 抓此刻所有线程的栈，dotnet-trace 录一段事件事后用 PerfView 看火焰图，三个都是 dotnet tool 装的，挂到进程 id 上不用改代码；客户端层是浏览器 DevTools 的瀑布图看 TTFB 和下载分别多长。

话术 C · 对应题「如何提升系统吞吐率」

吞吐率是并发处理数除以每个请求占用的时间，所以只有三个杠杆。第一，别让线程等：全链路 async，去掉 .Result 和 .Wait，一小池线程就能撑上千并发——这是 ASP.NET Core 最常见的吞吐问题。第二，让每个请求更短：数据访问通常是最慢的部分，少往返、少数据、只读查询不追踪、热数据缓存、HttpClient 用工厂复用。第三，把慢活挪出请求：长任务进后台或消息队列，请求写个中间态就返回，结果推回去。先拉哪个取决于测量——追踪图上时间在哪就拉哪个，没测量的优化是另一种猜。横向扩容放最后，前提是服务无状态，而且它不解决单请求太重的问题。
