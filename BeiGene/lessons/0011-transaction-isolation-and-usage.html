一、先破一个错觉

教科书的表长这样：四个级别、三种现象、打勾打叉。它给人的印象是「级别越高越安全，怕出事就往上调」。这个模型答不了两个追问：「为什么默认是 Read Committed 而不是最安全的那个」「调高之后代码要不要改」。因为它把机制藏掉了。

这一课唯一必须记死的一句

隔离级别决定的只有一件事：你的 SELECT 看的是哪一刻的快照。Read Committed 每条语句拍一张，Repeatable Read 整个事务只拍一张，Serializable 在这之上再加一道「提交前检查你读过的东西有没有被别人改」。

PostgreSQL 靠 MVCC 实现这句话：每行数据可以同时存在多个版本，每个事务按自己的快照决定看哪个版本。写不阻塞读，读不阻塞写——所以脏读在 PG 里根本不可能发生，哪怕你要求 Read Uncommitted。官方原文：PostgreSQL's Read Uncommitted mode behaves like Read Committed.（PostgreSQL — Transaction Isolation）

两个快照策略的精确定义，都是原文：

  • Read Committed：a SELECT query sees a snapshot of the database as of the instant the query begins to run.——每条语句一张快照。
  • Repeatable Read：sees a snapshot as of the start of the first non-transaction-control statement in the transaction, not as of the start of the current statement.——整个事务一张快照。

剩下的一切——三种现象哪个级别出现、报错什么时候抛、要不要重试——都是这一句的推论。下一节让你亲手推。

二、亲手让三种现象发生

场景沿用第七课的工单系统。两个事务 A、B 同时跑，你单步点。四个标签页，依次做：

  1. 不可重复读 @ Read Committed：A 读两次同一行，中间 B 改了并提交。A 第二次读到什么？
  2. 同一交错 @ Repeatable Read：一模一样的步骤，只换级别。A 第二次读到什么？
  3. 丢失更新 @ Repeatable Read：A、B 都要 UPDATE 同一行。第二个提交的人会怎样？——读一下报错。
  4. 写偏斜 @ Repeatable Read：两位复核员各自检查「至少有两人在岗」后下班。两个事务都提交了，结果在岗几人？
四个标签页，四个结论
  1. RC 每条语句一张快照，同一事务两次读可以不同。对单个 HTTP 请求几乎无害，对多语句报表有害。
  2. RR 整个事务一张快照，代价是可能过时。只读事务的最佳选择。
  3. RR 下的写冲突靠报错解决，不靠重看 WHERE。所以 RR / Serializable 的代码必须带重试——这是「调级别」真正的成本。
  4. RR 防不了写偏斜（读重叠、写不同行）。要么 Serializable（谓词锁 + 报错 + 重试），要么留在 RC 用 FOR UPDATE 把读变成锁。

三、四个级别，一张表，三个 PG 特例

现在再看那张表，每个格子你都能说出为什么了（原表出处）：

级别脏读不可重复读幻读序列化异常（含写偏斜）快照在哪一刻
Read Uncommitted标准允许，PG 不会可能可能可能= Read Committed
Read Committed（默认）不可能可能可能可能每条语句开始时
Repeatable Read不可能不可能标准允许，PG 不会可能事务第一条语句开始时
Serializable不可能不可能不可能不可能同 RR + 提交前谓词锁检查

三个 PG 特例，面试里说出任何一个都是加分项：

  1. PG 只实现了三个级别。原文：internally only three distinct isolation levels are implemented。Read Uncommitted 就是 Read Committed，因为 MVCC 下未提交的版本别人根本看不见。
  2. PG 的 RR 没有幻读。标准允许 RR 出现幻读（同样的 WHERE 第二次返回不同的行集），但 PG 的 RR 是整事务一张快照，行集当然也不变。所以 PG 的 RR 比标准更强——等于其它数据库说的「快照隔离」。
  3. Serializable 不是加锁，是检测。它叫 SSI（Serializable Snapshot Isolation）：正常跑，提交时发现依赖环就回滚一个。所以它比 RR 只多一点开销，但会随机失败——代码必须重试。
扩展 · 四个现象的精确定义（原文，背两个）
  • dirty read：A transaction reads data written by a concurrent uncommitted transaction.
  • nonrepeatable read：A transaction re-reads data it has previously read and finds that data has been modified by another transaction (that committed since the initial read).
  • phantom read：A transaction re-executes a query returning a set of rows that satisfy a search condition and finds that the set of rows satisfying the condition has changed.——和不可重复读的区别：一个是行的值变了，一个是行的集合变了。
  • serialization anomaly：The result of successfully committing a group of transactions is inconsistent with all possible orderings of running those transactions one at a time.——写偏斜是它最常见的形态。

四、回到第七课：抢单为什么不需要升级别

这是这一课和第七课的接缝，也是面试里最可能被追的一层。第七课的推荐写法是默认级别（RC）+ 条件更新：

UPDATE ticket SET status = 'reviewing', claimed_by = @me
 WHERE id = 1001 AND status = 'approved' AND claimed_by IS NULL;   -- 受影响行数 1 = 抢到，0 = 没抢到

它在 RC 下正确，靠的是 RC 独有的一条规则（原文）：第二个 UPDATE 等第一个提交后，The search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches the search condition.——被唤醒后重看一眼最新版本，条件不满足就影响 0 行。没有报错、没有重试、一条语句。

如果你「为了安全」把它改成 RR 会怎样？就是第二节标签页 ③：第二个人拿到的不是 UPDATE 0，而是 could not serialize access 异常。功能上没变好（本来就抢不到），工程上变差了（要 catch、要重试、要区分「没抢到」和「真出错」）。

一句可以直接说的判断

「单行的 check-then-act，RC + 条件更新就是最优解；只有当正确性依赖多行的读（写偏斜那类），才需要 Serializable 或显式锁。」这句话把第七课和这一课接在一起，而且回答了「为什么默认是 RC」：因为它在最常见的场景下既正确又零重试。

五、.NET 里事务的五种写法

题「事务的使用方式有哪些」是一道清单题，但答清单不如答「每种写法的事务边界在哪」。从隐式到显式排：

#写法事务边界什么时候用
1单条语句的隐式事务一条 SQLPG 里每条语句本身就是原子的。第七课那条条件 UPDATE 不需要任何 BEGIN。
2ORM 的自动事务：EF Core SaveChanges()一次 SaveChanges 内的全部变更默认行为。原文：all changes in a single call to SaveChanges are applied in a transaction.（EF Core — Transactions）
3显式事务：EF Core BeginTransaction(IsolationLevel) / SqlSugar db.Ado.BeginTran(IsolationLevel) / UseTran(...)你画的 Begin 到 Commit跨多次 SaveChanges、或要指定隔离级别、或混用 raw SQL。这是日常业务代码的主力。
4环境事务：TransactionScope作用域内所有打开的连接自动加入多个仓储 / 多个 DbContext 共享一个事务、又不想把 transaction 对象一路传下去。Npgsql 原文：automatically enlists if a connection is opened within an ambient TransactionScope。
5保存点：CreateSavepoint / RollbackToSavepoint事务内的一段大事务里某一步允许失败并跳过。EF Core 在事务内调 SaveChanges 时会自动建保存点。

第 3 种写出来（你项目用 SqlSugar，两种都给）：

// EF Core：指定隔离级别的显式事务
await using var tx = await db.Database.BeginTransactionAsync(IsolationLevel.RepeatableRead);
try
{
    // ... 多次 SaveChangesAsync、raw SQL 都在同一事务里
    await tx.CommitAsync();
}
catch (PostgresException e) when (e.SqlState == "40001")   // serialization_failure → 该重试
{
    // 回滚由 Dispose 自动做；这里决定重试几次
}

// SqlSugar：同一件事
var r = await db.UseTranAsync(async () =>
{
    // ... Updateable / Insertable ...
}, ex => log.LogError(ex, "tx failed"));
if (!r.IsSuccess) { /* 已回滚 */ }

// 要指定级别用底层形式：
db.Ado.BeginTran(IsolationLevel.Serializable);  // ... db.Ado.CommitTran() / RollbackTran()
三条工程规则（比清单更值钱）
  1. 事务边界放在服务层，一个用例一个事务。Controller 不开事务，Repository 不开事务——前者太外（会把序列化 JSON 都包进去），后者太内（一个用例调三个仓储就变三个事务）。这和 Lesson 10 里「DbContext 是 Scoped」是一回事：一个请求一个 DbContext、一个用例一个事务。
  2. 事务要短，里面不许有网络调用。行锁从 UPDATE 起一直持有到 COMMIT。事务里 await http.PostAsync(...) 一次 300ms，就是所有想改同一行的人排队 300ms。要调第三方，先提交本地事务，再调，失败走补偿——这正是 Lesson 05 的 Saga。
  3. 用了 RR / Serializable 就必须有重试。SQLSTATE 40001（serialization_failure）和 40P01（deadlock_detected）是「再来一次大概率成功」的错，和业务异常分开处理。
扩展 · TransactionScope 的三个坑
  • async 下必须写 TransactionScopeAsyncFlowOption.Enabled，否则 await 换线程后环境事务就丢了（Lesson 09：续接在任意线程池线程）。EF Core 文档原话：be sure to specify TransactionScopeAsyncFlowOption.Enabled in the TransactionScope constructor to ensure that the ambient transaction flows across async calls.
  • Dispose 是同步的。原文：TransactionScope does not support async commit/rollback; that means that disposing it synchronously blocks the executing thread.——高并发下这就是 Lesson 09 讲的线程池饥饿的来源之一。
  • 作用域里打开第二个连接就会试图升级成分布式事务——下一节告诉你为什么这几乎一定失败。Npgsql 的缓解：连接不重叠地开关时它会复用同一个连接，避免升级。

六、可选：在 psql 里看两条报错

两个模拟器已经把机制演完。如果你想在真库里看到那两条 could not serialize，用第七课那个容器（docker run --rm -e POSTGRES_PASSWORD=x -p 5432:5432 postgres:16，开两个 psql 窗口），不做也不影响后面：

-- 窗口 A                                          -- 窗口 B
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT status FROM ticket WHERE id = 1001;
                                                   BEGIN ISOLATION LEVEL REPEATABLE READ;
                                                   SELECT status FROM ticket WHERE id = 1001;
UPDATE ticket SET status = 'reviewing' WHERE id = 1001;
                                                   UPDATE ticket SET status = 'reviewing' WHERE id = 1001;  -- 卡住
COMMIT;
                                                   -- ERROR: could not serialize access due to concurrent update

-- 写偏斜：两边都改成 SERIALIZABLE，各自 SELECT count(*) 再 UPDATE 自己那行，
-- 第二个 COMMIT 报 could not serialize access due to read/write dependencies among transactions

顺手看一眼当前级别：SHOW transaction_isolation;——默认打 read committed。

七、分布式事务怎么答

题目原句「数据库处理分布式事务」，出题人想听的是你知道它是什么、为什么几乎没人用、那用什么。三段：

它是什么：两阶段提交（2PC / XA）。一个协调者、多个参与者。阶段一 PREPARE：每个库把事务写到持久化状态但不提交，回答「能提交」；阶段二协调者收齐后广播 COMMIT。PG 原生支持：PREPARE TRANSACTION 'x' / COMMIT PREPARED 'x'，但 max_prepared_transactions 默认为 0——默认是关掉的，这本身就是态度。

为什么不用：阶段一到阶段二之间，所有参与者的锁都持有着等协调者；协调者挂了，锁就一直挂着（「in-doubt」事务）。可用性和协调者绑死，吞吐被最慢的参与者拖住。.NET 侧的现实更直接：Distributed transaction support in System.Transactions was added to .NET 7.0 for Windows only（EF Core 文档），Npgsql 明确写了没有实现恢复（recovery）、不建议依赖。你的服务跑在 Linux 容器里——这条路在技术上就是关着的。

那用什么：不追求「多个库同时提交」，追求「每个库各自提交 + 最终一致」。就是 Lesson 05 那套：本地事务 + 补偿事务（Saga），本地事务里顺手写一张 outbox 表再由单独进程发消息（保证「改库」和「发消息」原子）。你那十个 Solace 服务的做法，正式名字就叫这个。

面试话术里的转折句

2PC 我知道，PG 也支持 PREPARE TRANSACTION，但生产上我不会用——它把可用性押在协调者上，而且 .NET 在 Linux 上根本没有分布式事务支持。跨库一致性我用本地事务 + Saga 补偿，我们那十个系统就是这么做的。——先证明你懂，再说不用，最后落到真事。

八、归类练习：这个场景要什么级别

判据就一条：正确性依赖的「读」有多宽。只依赖要改的那一行 → RC + 条件更新；要一个一致的只读快照 → RR；正确性依赖多行的读、又要写 → Serializable 或 FOR UPDATE。

九、话术

话术 A · 对应题「Transaction 级别」

先给机制，不背表：隔离级别决定的只有一件事：SELECT 看的是哪一刻的快照。Read Committed 每条语句一张，Repeatable Read 整个事务一张，Serializable 在 RR 上加一道提交前检查——你读过的东西有没有被别人改。PostgreSQL 是 MVCC，写不阻塞读，所以脏读根本不存在，Read Uncommitted 等于 Read Committed，实际只有三个级别。

推出现象：所以 RC 下同一事务两次读可以不一样——不可重复读；RR 下不会，但代价是看到的可能过时，而且写冲突时 RR 没法重看 WHERE，只能报 could not serialize access 让你重试。RR 还挡不住写偏斜——两个事务读了重叠的数据、写了不同的行，各自都对、合起来违反约束——那要 Serializable 或者 FOR UPDATE 把读变成锁。

落到选型（拉开差距的一句）：我默认留在 RC。单行的 check-then-act 用条件更新就是最优解，零重试；只读报表开 RR 拿一致快照；只有正确性依赖多行读又要写的场景才上 Serializable，而且代码必须带重试循环——调级别不是改一个参数，是改错误处理。

话术 B · 对应题「事务的使用方式有哪些」

按边界从小到大：五种。单条语句本身就是事务；ORM 的 SaveChanges 自动包一个事务；显式 BeginTransaction 可以指定隔离级别、跨多次保存——这是主力；TransactionScope 环境事务让作用域内的连接自动加入，适合跨多个仓储；保存点用来让大事务里某一步可以局部回滚。

三条规则：事务边界放服务层，一个用例一个事务，Controller 和 Repository 都不开；事务要短，里面绝不调 HTTP，行锁从 UPDATE 持有到 COMMIT，一次外部调用就是所有人排队；用了 RR 或 Serializable，SQLSTATE 40001 和死锁 40P01 要单独 catch 重试，和业务异常分开。

顺手带一个坑：TransactionScope 在 async 代码里要加 AsyncFlowOption.Enabled，不然 await 换线程后环境事务就丢了；而且它的 Dispose 是同步阻塞的，高并发下我更倾向显式 BeginTransactionAsync。

话术 C · 对应题「数据库处理分布式事务」

证明你懂：分布式事务的经典方案是两阶段提交：协调者先让每个库 PREPARE，都答应了再广播 COMMIT。PostgreSQL 原生支持 PREPARE TRANSACTION，但 max_prepared_transactions 默认是 0。

说为什么不用：两个阶段之间所有参与者的锁都挂着等协调者，协调者一挂就是 in-doubt 事务；可用性和吞吐都被最慢的一方拖住。而且 .NET 的分布式事务只在 .NET 7+ 的 Windows 上有，Npgsql 没实现恢复——我们跑 Linux 容器，这条路根本不通。

落到真事：跨库一致性我用本地事务加补偿——Saga。每个服务只提交自己的库，在同一个本地事务里写 outbox，再由独立进程发消息；下游失败就调回退接口逆序撤销。我们十个 Solace 服务之间就是这么做的，补偿本身也要幂等、也可能失败，这块我踩过坑。——最后一句把面试官引向 Lesson 05 你最有料的那段经历。
