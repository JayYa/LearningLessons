一、两个问题，四个档位

所有「大数据量排序 / 找数」的题，答案都由两个问题决定：

  1. 数据装得进内存吗？（N × 每条大小 vs 可用堆内存）
  2. 你要的是全部有序，还是只要其中少数几个？（全序 / 第 k 个 / 最大的 K 个）

两个问题两两组合，就是四个档位。这张表是本课的全部骨架：

要全部有序只要少数几个

时间 O(n log n)，空间 O(log n)		 B · 快速选择

这张表就是你的答题模板

面试官抛出「数据量很大怎么排序」时，不要直接开始写代码。先反问两句话：数据总量大概多少？可用内存有多少？你是要完整的有序结果，还是只要前几名？——这两句反问本身就是加分项，它证明你在真实工程里做过容量估算，而不是只会背算法。问完之后，你在这张表里落到哪一格，就讲哪一格。

先把「装不装得下」变成能口算的数

面试现场要能秒算。记住三个锚点：

  • C# 的 long / double 各 8 字节。1 亿个 long ≈ 800 MB（还没算数组对象头和 GC 压力）。
  • 装箱后的 object、或每条带字符串字段的记录，单条动辄 50–100 字节。1 亿条记录 ≈ 5–10 GB。
  • .NET 里单个数组对象默认上限约 2 GB（除非开启 gcAllowVeryLargeObjects），且大对象会进 LOH（大对象堆），默认不参与压缩，容易造成碎片。这一句说出来，面试官会知道你真的在 .NET 上处理过大数据。

所以「1 亿个整数排序」其实勉强装得下（档位 A），而「1 亿条业务记录排序」通常装不下（档位 D）。会算这笔账，就是这道题的分水岭。

二、档位 A：内存内全序

先说库函数——这才是工程答案

面试官说「现场实现一个排序算法」，你当然要手写。但动手之前先说一句：「生产代码我不会自己写排序，会用 Array.Sort；不过我知道它内部是什么，也能手写，这就写。」这一句把你从「刷题的人」变成「写生产代码的人」。

然后你要说得出 Array.Sort 到底是什么。微软官方文档写得很明确：

Microsoft Learn · Array.Sort 原文

「This method uses the introspective sort (introsort) algorithm as follows」：分区元素 ≤ 16 个时用插入排序；分区深度超过 2 × log N 时切换到堆排序；否则用快速排序。并且：「This implementation performs an unstable sort.」
learn.microsoft.com — Array.Sort Method

把这三点记牢，它们能直接回答三个追问：

追问你的回答
快排最坏 O(n²)，.NET 怎么办？内省排序：递归深度超过 2 log N 就切堆排，把最坏钉死在 O(n log n)。
为什么小数组用插入排序？n ≤ 16 时插入排序常数小、缓存友好，且几乎有序时接近 O(n)。
排序稳定吗？Array.Sort / List<T>.Sort 不稳定；要稳定用 LINQ 的 OrderBy（文档明确保证稳定）。

手写快排（这份代码我已编译运行验证过）

// 入口：对外只暴露一个方法
public static void QuickSort(int[] a) => Sort(a, 0, a.Length - 1);

static void Sort(int[] a, int lo, int hi)
{
    while (lo < hi)
    {
        // 优化 1：小区间转插入排序（照抄 .NET 的 16 阈值）
        if (hi - lo < 16) { InsertionSort(a, lo, hi); return; }

        int p = Partition(a, lo, hi);

        // 优化 2：尾递归消除 —— 只递归较短的一侧，较长的一侧用 while 循环
        // 效果：递归栈深度被钉死在 O(log n)，杜绝大数组 StackOverflow
        if (p - lo < hi - p) { Sort(a, lo, p - 1); lo = p + 1; }
        else                 { Sort(a, p + 1, hi); hi = p - 1; }
    }
}

// Lomuto 分区 + 三数取中选 pivot
public static int Partition(int[] a, int lo, int hi)
{
    int mid = lo + (hi - lo) / 2;   // 不写 (lo+hi)/2，避免 int 溢出

    // 三次比较让 a[lo] <= a[mid] <= a[hi]，中位数落在 mid
    if (a[lo]  > a[mid]) Swap(a, lo, mid);
    if (a[lo]  > a[hi])  Swap(a, lo, hi);
    if (a[mid] > a[hi])  Swap(a, mid, hi);

    Swap(a, mid, hi);               // 把中位数挪到末尾当 pivot
    int pivot = a[hi];

    int i = lo - 1;                 // i 指向「已知 <= pivot 区」的最后一个
    for (int j = lo; j < hi; j++)
        if (a[j] <= pivot) Swap(a, ++i, j);

    Swap(a, ++i, hi);               // pivot 归位，此处即它的最终位置
    return i;
}

static void InsertionSort(int[] a, int lo, int hi)
{
    for (int i = lo + 1; i <= hi; i++)
    {
        int v = a[i], j = i - 1;
        while (j >= lo && a[j] > v) { a[j + 1] = a[j]; j--; }
        a[j + 1] = v;
    }
}

static void Swap(int[] a, int i, int j) { (a[i], a[j]) = (a[j], a[i]); }
扩展 · 这段代码里埋了五个加分点
  • lo + (hi - lo) / 2 而不是 (lo + hi) / 2：后者在大数组上会 int 溢出。这是 JDK 里著名的 binarySearch 老 bug。写出来面试官一般会「哦」一声。
  • 三数取中：解决「已排好序的输入让快排退化成 O(n²)」。也可以说随机化 pivot，两者都对。
  • 尾递归消除：只递归短边，栈深度 O(log n)。不做的话，大量已排序元素能直接把栈打爆。
  • 小区间切插排：常数优化，能顺势带出 .NET 的 16 阈值。
  • 如果数据里大量重复值，Lomuto 会退化——这时该说 三路划分（Dijkstra 荷兰国旗），把等于 pivot 的一整段整体跳过。这是「你还知道什么」的最佳弹药。

三、档位 B：快速选择求中位数

「查找数组中位数」是个陷阱题。先排序再取中间是 O(n log n)，能拿分但拿不到高分。正确答案是：你只需要第 n/2 个元素，为什么要把其它 n−1 个也排好？

核心洞察

快排的 Partition 有一个被浪费掉的性质：它返回的下标 p，就是 pivot 在最终有序数组里的确切位置——这一点在分区结束的那一刻就已经确定，不需要再排任何东西。

于是：

  • p == k → a[p] 就是答案，收工。
  • p < k → 答案在右半边，左半边整个丢掉，不再看一眼。
  • p > k → 答案在左半边，右半边丢掉。

快排要处理两边，所以是 T(n) = 2T(n/2) + n = O(n log n)；快速选择只处理一边，T(n) = T(n/2) + n = n + n/2 + n/4 + … < 2n → 期望 O(n)。等比数列求和，这个推导现场能讲，非常加分。

// k 为 0-based 下标：k=0 是最小值，k=n-1 是最大值
// 注意：本方法会「就地打乱」入参数组，调用方若在意要先 Clone
public static int QuickSelect(int[] a, int k)
{
    int lo = 0, hi = a.Length - 1;
    while (lo < hi)                      // 循环而非递归，栈深度 O(1)
    {
        int p = Partition(a, lo, hi);    // 复用上一节那个 Partition
        if (p == k) return a[p];
        if (p < k) lo = p + 1; else hi = p - 1;
    }
    return a[lo];
}

public static double Median(int[] a)
{
    int n = a.Length;
    if (n == 0) throw new ArgumentException("空数组没有中位数", nameof(a));

    // 奇数：正中间那个
    if ((n & 1) == 1) return QuickSelect(a, n / 2);

    // 偶数：中间两个的平均。两次调用作用在同一个数组上——
    // 第一次已经把数组部分划分好了，第二次会更快，且结果依然正确
    // （因为数组始终是同一个多重集的某个排列）
    int hiHalf = QuickSelect(a, n / 2);
    int loHalf = QuickSelect(a, n / 2 - 1);
    return (loHalf + hiHalf) / 2.0;
}
三个必答的追问

Q：最坏情况呢？A：每次 pivot 都选到最值 → O(n²)。工程上用随机化 pivot 或三数取中，实践中不会发生。
Q：有严格 O(n) 最坏保证的做法吗？A：有，中位数的中位数（Median of Medians / BFPRT）——五个一组求中位数，再对这些中位数递归求中位数当 pivot，能保证每次至少切掉约 30%，最坏 O(n)。但常数很大，实际比随机化快速选择慢，所以只在需要最坏保证时用。
Q：偶数长度怎么办？A：取中间两个的平均。别在这翻车——很多人手写时忘了偶数分支。

扩展 · 如果是「流式数据的实时中位数」

这是一道常见的追加题，答案完全不同：用两个堆。一个大顶堆存较小的一半，一个小顶堆存较大的一半，每次插入后调整使两堆大小差 ≤ 1。中位数 = 较大那个堆的堆顶（奇数）或两个堆顶的平均（偶数）。插入 O(log n)、取中位数 O(1)。
这正好是档位 B 和档位 C 的交叉点：数据不是一个静止的数组而是一条流时，「选择」问题就变成了「堆」问题。

四、档位 C：Top-K 小顶堆

题库那句「无序大数据量，找到需要的数据」，标准答案就是这一档。

为什么求「最大的 K 个」要用「小顶堆」

这是最反直觉、也最常被答反的一点。想清楚这个比喻就永远不会记错：

守门员比喻

堆是一个只有 K 个座位的贵宾席。堆顶是席位里最弱的那个人——他是守门员。新人来了，只需要和守门员比：比守门员还弱 → 直接不让进；比守门员强 → 踢掉守门员，自己进来，然后席位里重新选出一个新的最弱者当守门员。

所以：求最大的 K 个 → 小顶堆（堆顶是候选集里的最小值，即门槛）；求最小的 K 个 → 大顶堆。

复杂度：时间 O(N log K)，内存 O(K)。对比整体排序的 O(N log N) 和内存 O(N)——当 K=100、N=1 亿时，log₂K ≈ 7 而 log₂N ≈ 27，快约 4 倍；内存差 100 万倍。内存那一项才是关键：它意味着数据可以从文件里流式读进来，永远不用全装下。

// .NET 6 起有内置的 PriorityQueue<TElement, TPriority>
// 官方文档：array-backed, quaternary MIN-heap（四叉小顶堆），出队的是优先级最小的
public static List<int> LargestK(IEnumerable<int> source, int k)
{
    if (k <= 0) return new List<int>();

    var heap = new PriorityQueue<int, int>(k);   // 元素本身即优先级

    foreach (int x in source)                    // 流式：source 可以是 File.ReadLines(...)
    {
        if (heap.Count < k)
            heap.Enqueue(x, x);                  // 席位没坐满，先进来
        else if (x > heap.Peek())                // Peek() = 当前守门员
            heap.EnqueueDequeue(x, x);           // 一次操作完成「换人」，比 Dequeue+Enqueue 少一次堆调整
    }

    // 堆里倒出来是从小到大，反转成从大到小
    var result = new List<int>(heap.Count);
    while (heap.Count > 0) result.Add(heap.Dequeue());
    result.Reverse();
    return result;
}
扩展 · 四个能拉开差距的补充
  • 手写堆：如果面试官不让用 PriorityQueue，就用数组 + SiftUp / SiftDown：下标 i 的父节点是 (i-1)/2，子节点是 2i+1、2i+2。建堆用 Floyd 自底向上是 O(n)，不是 O(n log n)——这个反直觉的结论值得记。
  • K 也很大怎么办？K 接近 N 时堆就没优势了（O(N log K) ≈ O(N log N)，且内存 O(K) ≈ O(N)），退回档位 A 或 D。
  • 数据分布在多台机器上？每台各自求本地 Top-K，再把这 K×机器数 个候选汇总求全局 Top-K。这就是 MapReduce 的思路，也是「你会不会往分布式想」的探针。注意：Top-K 可以这样分治，中位数不行——局部中位数的中位数不等于全局中位数。这个区分说出来很扎实。
  • PriorityQueue 文档明确写了：相同优先级的元素不保证 FIFO 顺序。要稳定就把入队序号并进优先级里。

五、档位 D：外部归并排序

题目原话：「排序的数据从文本中获取，但占用超出主存资源，从大到小排序若干个数」。这是本课的重头戏。

心智模型：分而治之，但「治」发生在磁盘上

只有一个想法：内存装不下全部，但一定装得下一小块。

  1. Pass 0（切块内排）：每次读入内存装得下的一块（比如 1000 万个数），在内存里排好序，写成一个临时文件。这个有序的临时文件叫一个 run（归并段）。读完整个输入，得到若干个 run。
  2. Pass 1..n（K 路归并）：同时打开这些 run，每个 run 只在内存里保留队头一个元素（实际是一个小缓冲区），反复取出所有队头里的最大值写到输出，然后从它所属的那个 run 里补进下一个。

关键在第 2 步：任意时刻内存里只有 K 个元素（K = run 的个数），与总数据量无关。这就是它能排 1 TB 数据的原因。

归并阶段为什么必须用堆

每次要在 K 个队头里找最大值。线性扫描是 O(K)，总成本 O(N·K)；用一个容量 K 的大顶堆是 O(log K)，总成本 O(N log K)。K=100 时差约 15 倍。这就是档位 C 的堆在档位 D 里的复用——两道题其实共用同一个数据结构。

static readonly IComparer<long> Desc = Comparer<long>.Create((x, y) => y.CompareTo(x));
// PriorityQueue 天生是小顶堆；传入「反序比较器」就变成大顶堆。
// （也可以把优先级取负数，但遇到 long.MinValue 会溢出，比较器更稳妥）

public static void SortDescending(string inputPath, string outputPath,
                                  int chunkSize, string tempDir)
{
    Directory.CreateDirectory(tempDir);
    var runs = new List<string>();

    // ---------- Pass 0：切块 → 内存排序 → 落盘成 run ----------
    using (var reader = new StreamReader(inputPath))
    {
        var buf = new List<long>(chunkSize);
        string? line;
        while ((line = reader.ReadLine()) is not null)   // 逐行读，绝不 ReadAllLines
        {
            if (line.Length == 0) continue;
            buf.Add(long.Parse(line));
            if (buf.Count == chunkSize) runs.Add(FlushRun(buf, tempDir, runs.Count));
        }
        // 最后不满一块的残留，必须再 flush 一次 —— 最常见的 bug 就在这行
        if (buf.Count > 0) runs.Add(FlushRun(buf, tempDir, runs.Count));
    }

    // ---------- Pass 1：K 路归并 ----------
    Merge(runs, outputPath);
    foreach (var r in runs) File.Delete(r);
}

static string FlushRun(List<long> buf, string tempDir, int index)
{
    buf.Sort(Desc);                                       // 从大到小
    string path = Path.Combine(tempDir, $"run-{index:D4}.txt");
    using (var w = new StreamWriter(path))
        foreach (long v in buf) w.WriteLine(v);
    buf.Clear();                                          // 复用同一个 List，不重新分配
    return path;
}

static void Merge(List<string> runs, string outputPath)
{
    var readers = runs.Select(p => new StreamReader(p)).ToList();
    try
    {
        // 堆里存 (值, 它来自第几个 run)，容量 = run 数
        var heap = new PriorityQueue<(long Value, int Run), long>(runs.Count, Desc);

        for (int i = 0; i < readers.Count; i++)           // 每个 run 先放一个队头进堆
            if (TryNext(readers[i], out long v)) heap.Enqueue((v, i), v);

        using var w = new StreamWriter(outputPath);
        while (heap.TryDequeue(out var top, out _))
        {
            w.WriteLine(top.Value);                       // 当前全局最大值
            if (TryNext(readers[top.Run], out long next)) // 从它来的那个 run 补一个
                heap.Enqueue((next, top.Run), next);
        }
    }
    finally { foreach (var r in readers) r.Dispose(); }
}

static bool TryNext(StreamReader r, out long value)
{
    string? line;
    while ((line = r.ReadLine()) is not null)
        if (line.Length > 0) { value = long.Parse(line); return true; }
    value = 0;
    return false;
}
实测

这份代码我编译运行验证过：20 万个 long、每块 1 万（即 20 个 run），排序结果与全内存 Array.Sort + Reverse 逐位一致，耗时 525 ms（含读写临时文件）。第 11 节的实验会让你自己跑出这个结果。

六、趟数与 I/O 成本公式

能背算法的人很多，能算成本的人很少。这一节的公式是本课的「深度炸弹」。

设：N = 数据总页数，B = 可用的内存缓冲页数。

量公式为什么
Pass 0 产生的 run 数⌈N / B⌉每次装满 B 页排一次，写出一个 B 页的 run
总趟数1 + ⌈logB−1 ⌈N/B⌉⌉Pass 0 算 1 趟；之后每趟能把 run 数除以 B−1
总 I/O 次数2N × 总趟数每趟都要把全部 N 页读一遍写一遍

两个「为什么」必须能解释：

  • 为什么是 B−1 而不是 B？B 个缓冲页里，必须留 1 页做输出缓冲，剩下 B−1 页各对应一个输入 run。这是最容易被追问、也最容易答漏的细节。
  • 为什么乘 2？一读一写。
扩展 · 现场算一遍（面试官很可能真的让你算）

N = 1000 页，B = 11 页。
Pass 0：⌈1000/11⌉ = 91 个 run。
总趟数：1 + ⌈log₁₀ 91⌉ = 1 + 2 = 3 趟。
总 I/O：2 × 1000 × 3 = 6000 次。
再体会一下这个公式的含义：趟数里对数的底是 B−1。内存从 11 页涨到 101 页，底数从 10 变成 100，趟数从 3 降到 2——I/O 直接省掉三分之一。这就是「给排序多分点内存」在数据库里效果那么显著的原因，也是下一节的引子。
公式出处：UC Berkeley CS186 — Sorting（Ramakrishnan & Gehrke《Database Management Systems》第 13 章的标准表述）。

七、接回数据库那道题

题库第四节有一问：「数据库有大量数据，大到程序内存完全吃不消，如果排序全部数据，前提是数据库没有索引排序？」

这道题看着像数据库题，其实答案就是本课的档位 D——而且关键在于：你根本不该把数据捞到程序里排。

面试话术 · 这道题的完整回答

首先我不会把数据拉到应用内存里排——那是把数据库最擅长的事搬到最不适合的地方做。没有索引时，PostgreSQL 执行 ORDER BY 走的就是外部归并排序：它先按 work_mem 的额度在内存里排一批、写成临时文件，全部切完之后再多路归并。你在 EXPLAIN (ANALYZE, BUFFERS) 里能直接看到 Sort Method: external merge Disk: 82000kB——这行就是它落盘了的证据；如果内存够，那行会是 Sort Method: quicksort Memory: ...。

所以我的排查顺序是三步。第一，看这个排序是不是真的需要全量——大多数场景其实是分页，那就用 keyset 分页配合排序列上的索引，让排序变成索引顺序扫描，排序成本直接归零。第二，如果真要全量导出，就调大这个会话的 work_mem 减少归并趟数——外部排序总 I/O 是 2N × 趟数，趟数是以「缓冲页数减一」为底的对数，内存翻十倍往往就少一整趟；但要注意 work_mem 是每个操作、每个会话各算一份，一个复杂查询里有多个排序就是多份，所以绝不能在全局配置里往大了调，我一般用 SET LOCAL work_mem 只对当前事务生效。第三，如果这是个常态需求，那就该建索引了——排序列上的 B-tree 索引能让数据库直接按索引顺序吐数据，完全不排序。

如果排序确实必须在应用侧做，比如数据来自文本文件而不是数据库，那就是标准的外部归并排序：分块读入、内存内排序、落盘成有序段，再用一个容量等于段数的堆做多路归并。我实现过这个，核心就是堆里存「值 + 它来自哪个段」这个二元组。

work_mem 的官方定义：「Sets the base maximum amount of memory to be used by a query operation (such as a sort or hash table) before writing to temporary disk files.」默认只有 4MB。来源：PostgreSQL Docs — Resource Consumption。

和 Lesson 01 的接口

这里「第一步：看是不是真的需要全量排序」，直接接上 Lesson 01 的 keyset 分页和索引顺序扫描。两课串起来讲，效果远大于分开讲：面试官问算法题，你能把答案落到数据库执行计划上；问数据库题，你能把答案落到算法复杂度上。这种双向连接就是「5–7 年经验」该有的样子。

八、白板检查清单

现场手写时，这几个坑最容易踩。写完后花 20 秒逐条自查——当着面试官的面自查，本身就是加分项。

检查项说明
空数组 / 单元素a.Length == 0 时 hi = -1，循环条件 lo < hi 直接不进，安全。中位数要显式抛异常。
中点算法lo + (hi - lo) / 2，别写 (lo + hi) / 2。
边界闭开本课全部用闭区间 [lo, hi]。开口一致比开口正确更重要——不一致必错。
k 的基准先说清 k 是 0-based 还是 1-based。中位数：奇数取 n/2，偶数取 n/2-1 和 n/2。
Top-K 的堆向求最大 K 个 → 小顶堆。念一遍「守门员」再动笔。
外部排序最后一块循环结束后 buf 里通常还有不满一块的残留，必须再 flush 一次。漏了这行是最常见的 bug。
逐行读，不要 ReadAllLines整道题的前提就是内存装不下。写出 File.ReadAllLines 等于自己否定了题目。
流要释放using / try-finally。归并时同时开着几十个 StreamReader，漏一个就句柄泄漏。

十、面试话术

话术 1 · 「现场实现一个排序算法」

可以。先说明一点：生产代码我不会自己写排序，会用 Array.Sort——它内部是内省排序，分区小于 16 个元素时走插入排序，递归深度超过 2 倍 log N 时切换成堆排序，所以最坏情况被钉死在 O(n log n)，不会退化。它是不稳定排序，需要稳定的时候我用 LINQ 的 OrderBy。

不过我知道你想看手写，我写一个带优化的快排。（边写边说）三个地方我会特意处理：中点用 lo + (hi-lo)/2 防 int 溢出；pivot 用三数取中，防止输入已经有序时退化成 O(n²)；递归只递归较短的一边、较长的一边用循环，这样栈深度是 O(log n)，大数组不会爆栈。

如果数据里有大量重复值，Lomuto 分区还是会退化，那时我会换成三路划分——把等于 pivot 的一整段直接跳过。

话术 2 · 「查找数组中位数」

先排序再取中间是 O(n log n)，但没必要——我只要第 n/2 个元素，不需要另外 n−1 个也排好。用快速选择：借用快排的分区，分区完成时 pivot 的下标就是它在最终有序数组里的确切位置。如果这个下标正好是 n/2，直接返回；比 n/2 小就只往右半边找，大就只往左半边找，另一半整个丢掉不看。

因为每次只处理一边，递推是 T(n) = T(n/2) + n，展开是 n + n/2 + n/4 + …，小于 2n，所以期望 O(n)。最坏情况是每次 pivot 都选到最值，退化成 O(n²)，工程上用随机 pivot 或三数取中规避。如果必须有最坏 O(n) 的保证，那就是中位数的中位数 BFPRT，但它常数太大、实际反而更慢，所以我只在有硬性延迟保证的场景才考虑。

还有一点：偶数长度要取中间两个的平均，做两次选择就行，第二次因为数组已经被部分划分过会更快。如果数据不是静止数组而是一条流、要实时出中位数，那就换方案——用一个大顶堆存较小的一半、一个小顶堆存较大的一半，保持两堆大小差不超过 1，插入 O(log n)、取中位数 O(1)。

话术 3 · 「无序大数据量，找到需要的数据」

我先确认一下需求：是要全部有序，还是只要最大或最小的若干个？如果只要前 K 个，就不该排序。

做法是维护一个容量为 K 的小顶堆。求最大的 K 个用小顶堆，这一点容易搞反——因为堆顶是当前候选集里最小的那个，它相当于门槛。新元素进来只跟堆顶比：比堆顶小直接丢掉，比堆顶大就把堆顶换出去。全程扫一遍，时间 O(N log K)。

更关键的是内存只占 O(K)。K 是 100 的话，一亿条数据也只在内存里放 100 个，数据可以从文件流式读进来，完全不需要装下。.NET 6 以后有内置的 PriorityQueue，默认就是小顶堆，换元素用 EnqueueDequeue 一次调整就够。如果数据分布在多台机器上，每台先算本地 Top-K，再把候选汇总求全局 Top-K——不过要注意这个分治只对 Top-K 成立，中位数不能这么做，局部中位数的中位数不等于全局中位数。

话术 4 · 「数据超出主存，从大到小排序」

标准的外部归并排序，两个阶段。第一阶段：按内存能装下的大小分块读入，每块在内存里排好序、写成一个临时文件，叫一个归并段。第二阶段：把所有归并段同时打开，每个段在内存里只保留队头，用一个大顶堆在这些队头里反复取最大值写到输出，取走谁就从谁所属的段里补下一个。堆里存的是「值 + 它来自第几个段」这个二元组。

核心性质是：归并阶段内存里只有段数那么多个元素，和总数据量无关，所以这个方法能排任意大的数据。成本上，设数据 N 页、内存 B 页，第一阶段产生 N/B 个段，之后每趟能归并 B−1 路——留一页做输出缓冲，所以是 B−1 不是 B。总趟数是 1 加上以 B−1 为底、N/B 的对数，每趟全量读一遍写一遍，总 I/O 就是 2N 乘趟数。

工程上要注意几点：全程逐行读，绝不能用 ReadAllLines，否则就违背了题目前提；分块循环结束后缓冲区里还有不满一块的残留，必须补一次落盘，这是最常见的 bug；同时打开的几十个流要用 using 保证释放。PriorityQueue 本身是小顶堆，我传一个反序的 Comparer 把它变成大顶堆，不用取负数——取负数遇到 long.MinValue 会溢出。

第 3 步：用随机对拍验证自己

把下面这段贴进 Main。它用 200 组随机数据把你的实现和 .NET 库函数对拍——这就是最紧的反馈回路：几秒钟就知道自己对不对。

var rng = new Random(42);

// A. 快排对拍
for (int t = 0; t < 200; t++)
{
    int n = rng.Next(0, 300);
    var a = new int[n];
    for (int i = 0; i < n; i++) a[i] = rng.Next(-50, 50);   // 窄取值域 → 制造大量重复
    var b = (int[])a.Clone();
    QuickSort(a); Array.Sort(b);
    if (!a.SequenceEqual(b)) { Console.WriteLine($"FAIL quicksort n={n}"); return; }
}
Console.WriteLine("A. QuickSort  OK");

// B. 中位数对拍（务必覆盖偶数长度和 n=1）
for (int t = 0; t < 200; t++)
{
    int n = rng.Next(1, 200);
    var a = new int[n];
    for (int i = 0; i < n; i++) a[i] = rng.Next(-100, 100);
    var s = (int[])a.Clone(); Array.Sort(s);
    double expect = (n % 2 == 1) ? s[n / 2] : (s[n / 2 - 1] + s[n / 2]) / 2.0;
    if (Math.Abs(Median((int[])a.Clone()) - expect) > 1e-9)
        { Console.WriteLine($"FAIL median n={n}"); return; }
}
Console.WriteLine("B. Median     OK");

// C. Top-K 对拍
for (int t = 0; t < 200; t++)
{
    int n = rng.Next(1, 500), k = rng.Next(1, 30);
    var a = new int[n];
    for (int i = 0; i < n; i++) a[i] = rng.Next(-1000, 1000);
    if (!LargestK(a, k).SequenceEqual(a.OrderByDescending(x => x).Take(k)))
        { Console.WriteLine($"FAIL topk n={n} k={k}"); return; }
}
Console.WriteLine("C. TopK       OK");

// D. 外部排序对拍：20 万个数，每块 1 万 → 20 个 run
string dir = Path.Combine(Path.GetTempPath(), "extsort-lab");
Directory.CreateDirectory(dir);
string input = Path.Combine(dir, "input.txt"), output = Path.Combine(dir, "output.txt");
int total = 200_000;
var truth = new long[total];
using (var w = new StreamWriter(input))
    for (int i = 0; i < total; i++)
        { long v = rng.NextInt64(-1_000_000, 1_000_000); truth[i] = v; w.WriteLine(v); }
Array.Sort(truth); Array.Reverse(truth);

var sw = System.Diagnostics.Stopwatch.StartNew();
SortDescending(input, output, chunkSize: 10_000, tempDir: Path.Combine(dir, "runs"));
sw.Stop();

var back = File.ReadLines(output).Select(long.Parse).ToArray();
Console.WriteLine(back.SequenceEqual(truth)
    ? $"D. ExternalSort OK  {total:N0} 个数，{sw.ElapsedMilliseconds} ms"
    : "FAIL external sort");

第 4 步：观察，别只看 OK

  1. 把 chunkSize 从 10000 改成 1000，再改成 100。run 数从 20 变成 200、2000。记录耗时怎么变——这就是「内存越小、run 越多、I/O 越贵」的亲身体验。到 100 时你多半会看到明显变慢，因为 2000 个 StreamReader 同时开着。这正是真实数据库要做「多趟归并」而不是「一次开 2000 路」的原因——那才是第 6 节公式里「趟数」那一项存在的意义。
