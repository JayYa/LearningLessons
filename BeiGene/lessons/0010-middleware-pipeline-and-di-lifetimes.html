一、先破一个错觉

很多人把中间件管道想成一个列表：请求依次经过 A、B、C，每个处理完交给下一个。这个模型答不了「为什么日志中间件能记到 401」「为什么异常处理要放第一个」——因为它漏掉了一半的执行：每个中间件在 await next() 之后还有代码，而那段代码是在所有内层都跑完之后才执行的。

这一课唯一必须记死的一句

管道不是列表，是一个函数套一个函数。Build() 在启动时把 N 个中间件倒着折叠成一个 RequestDelegate；之后每个请求只是调用这一个函数。

这不是比喻，是 ApplicationBuilder.cs 里的原样代码（删掉了诊断分支）：

// app.Use(...) 只是把一个「函数的函数」加进列表
public IApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> middleware)
{
    _components.Add(middleware);
    return this;
}

// 启动时调一次 Build()：从最里层（404）开始，倒着一层层包
public RequestDelegate Build()
{
    RequestDelegate app = context =>
    {
        if (!context.Response.HasStarted)
            context.Response.StatusCode = StatusCodes.Status404NotFound;
        return Task.CompletedTask;
    };

    for (var c = _components.Count - 1; c >= 0; c--)
        app = _components[c](app);       // 把「下一层」传给「这一层」，得到新的「这一层」

    return app;                          // 一个函数。所有请求都从它进
}

注意三件事，它们是这道题的全部「底层逻辑」：

  1. 每个中间件的类型是 Func<RequestDelegate, RequestDelegate>——给它「下一层」，它返回「包着下一层的自己」。app.Use(async (ctx, next) => {...}) 只是这个签名的语法糖。
  2. 折叠是倒着的：先包最后注册的，最后包第一个注册的。所以第一个注册的在最外层，请求最先进它、响应最后出它。
  3. 中间件实例只在这里构造一次。请求进来时没有任何「组装管道」的动作，就是调一个已经折好的委托——这一点在第三节会变成一个真实陷阱。

顺带一句：await next() 这行你上一课已经拆过了——它把中间件的后半段登记成回调然后 return。所以「后置代码在所有内层跑完之后才执行」不是新知识，是 Lesson 09 状态机的直接推论。

二、亲手让请求穿一次

下面这个管道有四层：异常处理、日志、鉴权、终端。先猜再点。依次做这四组实验，每组的结论后面几节都要用：

  1. 默认配置，直接「发一个请求」——数一下 trace 里的箭头方向，进和出各几行。
  2. 把 Auth 改成「短路」——Logging 的后置代码跑了没？它看到的状态码是什么？
  3. 把 Endpoint 改成「抛异常」——谁的后置代码没跑？异常在哪一层被接住？
  4. Logging 改成「先写响应体再调 next」，Auth 保持「短路」——看 Auth 试图写 401 时发生了什么。
四组实验，四个结论（对照你点出来的 trace）
  1. 进出顺序相反。进 1→2→3→4，出 4→3→2→1。这就是「倒着折叠」在运行时的样子。
  2. 短路 ≠ 跳过外层。Auth 不调 next，但 Logging 从自己的 await next() 返回后照样记日志，而且记到的是 401。官方原文：Middleware added to the pipeline before the terminal middleware still processes code after their next.Invoke statements.（Middleware — Short-circuiting）
  3. 异常是往外抛的，谁在外面谁接。Logging 的后置代码被跳过（没有 try/finally），ExceptionHandler 接住。如果它不在最外层，它外面那些中间件抛的异常就没人管——这是「异常处理必须第一个注册」的机制原因，不是规范要求。
  4. 响应一旦开始就不能改头。Logging 往 body 写了字节，HasStarted 变 true，Auth 再想设 401 直接抛 InvalidOperationException。原文警告：Don't call next.Invoke after the response has been sent to the client. Changes to HttpResponse after the response has started throw an exception.
扩展 · Use / Run / Map 三个词的精确含义
拿到 next 吗做什么
Use拿到普通中间件，自己决定调不调 next。不调就是短路。
Run拿不到终端中间件。官方：The first Run delegate is always terminal and terminates the pipeline. 它后面再注册什么都不会被调用。
Map—按路径前缀分叉出一条子管道，匹配上就走分支，不回主线。UseWhen 是会回主线的版本。

面试增量：Run 只是约定——它等于一个不调 next 的 Use。能说出「三个都是往 _components 里加 Func<RequestDelegate, RequestDelegate>」，比背三个定义有分量。

三、自定义中间件：三个约定，一个陷阱

「如何自定义中间件」是送分题，但有一个能拉开差距的陷阱。先给标准答案——它就是 官方文档的例子改成你项目里的样子：

public class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;                       // ① 构造函数必须能收 RequestDelegate
    private readonly ILogger<RequestLoggingMiddleware> _log;      //    其它构造参数由 DI 填

    public RequestLoggingMiddleware(RequestDelegate next, ILogger<RequestLoggingMiddleware> log)
    {
        _next = next;
        _log = log;
    }

    // ② 方法名必须叫 Invoke 或 InvokeAsync，返回 Task，第一个参数是 HttpContext
    public async Task InvokeAsync(HttpContext ctx, ICurrentUser user)   // ③ 这里也能注入 —— 见下面的陷阱
    {
        var sw = Stopwatch.StartNew();
        await _next(ctx);                                            // 不调它 = 短路
        _log.LogInformation("{Method} {Path} → {Status} in {Ms}ms by {User}",
            ctx.Request.Method, ctx.Request.Path, ctx.Response.StatusCode, sw.ElapsedMilliseconds, user.Id);
    }
}

// 惯例：包一个扩展方法，Program.cs 里写 app.UseRequestLogging();
public static class RequestLoggingExtensions
{
    public static IApplicationBuilder UseRequestLogging(this IApplicationBuilder app)
        => app.UseMiddleware<RequestLoggingMiddleware>();
}

官方对约定的原话只有三条：A public constructor with a parameter of type RequestDelegate；A public method named Invoke or InvokeAsync，它必须 Return a Task 且 Accept a first parameter of type HttpContext。没有接口、没有基类——UseMiddleware<T> 用反射找这两样，然后把它包成第一节那个 Func<RequestDelegate, RequestDelegate>。

陷阱：中间件是 Singleton，别在构造函数里要 Scoped 服务

第一节说了：中间件实例在 Build() 时构造一次。官方：Middleware is constructed once per application lifetime. 所以它的构造函数里注入的任何东西，都会被整个进程生命周期持有。你把 DbContext（Scoped）或者「当前用户」（Scoped）塞进构造函数，得到的就是第一个请求的那份，永远不换。

修法就是上面代码里的 ③：需要每请求一份的依赖，放到 InvokeAsync 的参数里。官方：To share a scoped service between middleware and other types, add these services to the InvokeAsync method's signature. 框架会在每次调用时从当前请求的作用域解析它。

这个陷阱和第四节要讲的 Captive Dependency 是同一件事——中间件只是最常见的那个 Singleton。

四、DI 三种生命周期：看编号，不背定义

三个定义很短（Service lifetimes）：Transient created each time it's requested；Scoped created once per client request (connection)；Singleton created the first time they're requested，之后 every subsequent request ... uses the same instance。背下来没用，面试追问的是组合起来会怎样。所以下面不背定义，看编号。

场景：一个 Controller 依赖 OrderService 和 AppDbContext；OrderService 内部也依赖 AppDbContext，外加一个 Clock。做四组实验：

  1. 默认（都是 Scoped）：连发两个请求。同一个请求里 AppDbContext 出现两次，编号一样吗？跨请求呢？
  2. 把 AppDbContext 改成 Transient：同一个请求里的两个 AppDbContext 编号还一样吗？——想一下这对「一个请求一个事务」意味着什么。
  3. 把 OrderService 改成 Singleton（AppDbContext 改回 Scoped），发请求——开发环境炸了。读一下异常消息。
  4. 取消「开发环境」勾选，重来，再发两个请求——看 AppDbContext 的编号，看红色标记。
四组实验，四个结论
  1. Scoped = 一个请求一份。Controller 和 OrderService 拿到的是同一个 AppDbContext；下一个请求换新的。这就是 EF Core 的 AddDbContext 默认注册成 Scoped 的原因——一个请求内所有人共用一个 change tracker，SaveChanges 一次提交。
  2. Transient 会把「一个请求一个事务」打碎。Controller 和 OrderService 各拿一个 DbContext，各自追踪、各自提交——两处修改不在一个事务里。Transient 适合无状态的轻对象，不适合 DbContext。
  3. 开发环境的异常是保护。Cannot consume scoped service from singleton——这是 ValidateScopes 在第一次解析时抛的。官方：By default, in the development environment, resolving a service from another service with a longer lifetime throws an exception.
  4. 生产环境不抛，只是悄悄错。ValidateScopes 默认只在 Development 开。生产里那个 Scoped 的 DbContext 被 Singleton 抓住，所有请求共用一个——症状是偶发的 A second operation was started on this context、内存缓慢上涨、以及最可怕的：一个用户未提交的修改被另一个用户的 SaveChanges 带出去。这个事故有名字：Captive Dependency。
扩展 · Singleton 里真的需要 Scoped 服务怎么办

典型场景是 BackgroundService（它是 Singleton）里要用 DbContext。正解不是把 DbContext 改成 Singleton，是自己开作用域——官方：It's acceptable to resolve a scoped service within a singleton if you create and use an explicit scope with IServiceScopeFactory.

public sealed class OutboxWorker(IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();                       // 手动开一个「请求」
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            // ... 用完随 scope 一起 Dispose
            await Task.Delay(1000, ct);
        }
    }
}

面试增量：「作用域」不是 HTTP 请求的专利，ASP.NET Core 只是替你在每个请求开头 CreateScope()、结尾 Dispose()。消息消费者、定时任务，每处理一条消息就该开一个 scope——你那十个 Solace 服务的 handler，正确形态就是这样。

五、顺序为什么重要：三条判据

官方给了一张推荐顺序表（Middleware order），并说 The order is critical for security, performance, and functionality. 表可以查，但面试要你说为什么。第二节的四组实验已经给了全部理由，压成三条判据：

判据推出的顺序第二节的证据
要接住谁的异常，就得在谁外面UseExceptionHandler 第一个实验 3：异常往外抛，外层才能 catch
能短路的越早越省UseStaticFiles 在 Auth 之前——静态文件不需要鉴权，早点返回实验 2：短路后内层一点开销都没有
用别人产物的，排在别人后面UseRouting → UseAuthentication → UseAuthorization → 端点：授权要知道「打到哪个端点、它要什么策略」，所以必须在路由之后；认证要先于授权填好 User实验 1：进的顺序就是注册顺序

官方推荐的骨架（删掉了 HSTS / Cookie / Session 等可选项）：

app.UseExceptionHandler("/error");   // 1 最外层：接所有人的异常
app.UseHttpsRedirection();           // 2
app.UseStaticFiles();                // 3 能短路就早短路
app.UseRouting();                    // 5 决定「打到哪个端点」
app.UseAuthentication();             // 6 填 HttpContext.User
app.UseAuthorization();              // 7 拿着 User 和端点上的策略做判断
app.MapControllers();                // 10 终端
扩展 · 中间件 vs Filter vs AOP——权限题的那句话

题库第九节：如果每一步都需要验证权限，如何避免不停地调用服务获得权限信息，以及如何减少代码量 —— 涉及到 AOP、自定义中间件、缓存。出题人自己给了答案骨架，你要做的是把三者放到正确的层：

层知道什么适合放
中间件只有 HttpContext，不知道打到哪个 action、参数是什么横切所有请求的事：解析 token、把「当前用户 + 权限集」算一次塞进 HttpContext.Items 或一个 Scoped 的 ICurrentUser
Filter / [Authorize]知道 action、知道路由参数和 model「这个人能不能碰这个接口」——声明式，零代码量
AOP（拦截器 / 特性 + 源生成）知道被调用的方法和参数「这个人能不能碰这条数据」——行级权限，要看 orderId 属于谁

「避免不停地调用服务」的答案是Scoped 缓存：权限集在中间件里查一次，注册成 Scoped 服务，同一个请求里 Filter 和 AOP 拦截器都从它读，请求结束自动释放。跨请求再加一层 IMemoryCache（按用户 id，短 TTL）。三种生命周期在这里各就各位——这一题实际上是第四节的应用题。

两个模拟器已经把机制演完了。如果你想在真实进程里看到同样的编号，20 行就够，不做也不影响后面：

dotnet new web -o pipedemo && cd pipedemo

把 Program.cs 整个替换成：

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddScoped<Marker>();
var app = builder.Build();

app.Use(async (ctx, next) => { Console.WriteLine("→ A"); await next(ctx); Console.WriteLine($"← A  status={ctx.Response.StatusCode}"); });
app.Use(async (ctx, next) => {
    Console.WriteLine("→ B");
    if (ctx.Request.Query.ContainsKey("deny")) { ctx.Response.StatusCode = 401; return; }   // 短路
    await next(ctx);
    Console.WriteLine("← B");
});
app.Run(async ctx => {
    var m1 = ctx.RequestServices.GetRequiredService<Marker>();
    var m2 = ctx.RequestServices.GetRequiredService<Marker>();
    Console.WriteLine($"   endpoint: marker {m1.Id} / {m2.Id}");      // Scoped：同一请求两次解析，Id 相同
    await ctx.Response.WriteAsync("ok");
});
app.Run();

class Marker { public Guid Id { get; } = Guid.NewGuid(); }

dotnet run，然后在浏览器里开 http://localhost:5000/ 两次、http://localhost:5000/?deny 一次。看控制台：正常请求打 →A →B endpoint ←B ←A status=200；?deny 那次没有 endpoint、没有 ←B，但有 ←A status=401——就是第二节实验 2。两次正常请求的 marker Id 各自相同、彼此不同——就是第四节实验 1。把 AddScoped 改成 AddTransient 再跑一次，同一行的两个 Id 就不一样了。

八、话术

话术 A · 对应题「中间件的底层逻辑 / 如何自定义中间件」

先给机制，一句话：中间件管道不是一个列表，是一个函数套一个函数。每个中间件的类型是 Func<RequestDelegate, RequestDelegate>——给它下一层，它返回包着下一层的自己。启动时 Build() 从最里面的 404 委托开始，倒着把所有中间件折叠成一个 RequestDelegate，之后每个请求就是调这一个函数。

推出两个现象：所以第一个注册的在最外层：请求最先进、响应最后出。而且每个中间件 await next() 后面的代码，是在所有内层跑完之后才执行的——这就是为什么日志中间件放在鉴权外面能记到 401，为什么异常处理必须第一个注册。

再给自定义：自定义就是一个普通类，两个约定：构造函数收 RequestDelegate，有个 InvokeAsync(HttpContext) 返回 Task。不调 _next 就是短路。一般再包个 UseXxx 扩展方法。

收在陷阱上（拉开差距的一句）：要注意中间件实例整个进程只构造一次，所以 Scoped 服务不能注进构造函数——会拿到第一个请求那份永远不换。要每请求一份的，放到 InvokeAsync 的参数里。

话术 B · 对应题「依赖注入的理解和使用」

先定义作用域，不先背三个词：DI 容器里有一个根容器，ASP.NET Core 在每个请求开头开一个子作用域、结尾 Dispose。三种生命周期就是三个存放位置：Singleton 存在根容器、Scoped 存在当前作用域、Transient 不存，每次 new。

给使用原则：无状态、线程安全的做 Singleton，比如 HttpClient 工厂、配置、时钟；和一个请求绑定的做 Scoped，典型是 DbContext——一个请求共用一个 change tracker，一次 SaveChanges；轻量无状态又不想共享的才 Transient。

主动讲事故：最经典的坑是 Captive Dependency：Singleton 的构造函数里要了一个 Scoped，那个 Scoped 就被抓成了 Singleton。开发环境 ValidateScopes 会直接抛异常；生产默认关闭，所以症状是上线后才出——DbContext 被所有请求共用，偶发 A second operation was started on this context，还可能把一个用户的未提交修改带进另一个用户的 SaveChanges。修法是 Singleton 拿 IServiceScopeFactory 自己开作用域，后台任务和消息消费者都是这么写的。

话术 C · 对应题「每一步都要验证权限，如何避免反复调用权限服务、减少代码量」

按层拆：我会分三层。中间件层只做「你是谁」——解析 token，把当前用户和他的权限集查一次，放进一个 Scoped 的 ICurrentUser 服务；这个请求里后面所有人都从它读，不再查第二次。接口级权限用 [Authorize] 特性声明，零代码量。行级权限——比如只能改自己的工单——放服务层或用 AOP 拦截器统一做，因为它需要业务数据，前两层拿不到。

点出缓存的层次：「避免反复调用」有两层缓存：请求内靠 Scoped 生命周期天然缓存，请求间用 IMemoryCache 按用户 id 缓存权限集，TTL 设短一点，权限变更时主动失效。

为什么这样答强：出题人自己列了「AOP、中间件、缓存」三个词，多数人会挨个解释这三个词。你把它们放到各自知道多少上下文的层上，并把「缓存」落实成 Scoped 生命周期——这说明你理解的是机制，不是词汇。
