一、为什么索引是 B-tree

大部分人跳过这一节，直接背最左前缀，结果一被追问"为什么范围条件之后就断了"就哑了。所有结论都源自 B-tree 的一个性质：有序。

先问：为什么不是二叉搜索树？

因为数据库不是在内存里找数据，是在磁盘上找。磁盘 I/O 的最小单位是「页」（Postgres 默认 8KB）。读 1 个字节和读 8KB 的代价几乎一样——瓶颈是寻址次数，不是数据量。

于是设计目标变成：用最少的页读取次数定位一行。

  • 二叉树：每个节点 2 个分支，1000 万行需要约 log₂(10⁷) ≈ 24 层 → 最坏 24 次磁盘 I/O。
  • B-tree：一个 8KB 页里能塞几百个键（这个数量叫扇出 fan-out）。假设扇出 = 300，1000 万行只需 log₃₀₀(10⁷) ≈ 3 层 → 3 次 I/O。
            [ 根页：一个 8KB 页，装几百个分隔键 ]
           /              |                \
    [中间页]          [中间页]           [中间页]        ← 第 2 层
    /    |   \        /   |   \          /   |   \
  [叶] [叶] [叶]   [叶] [叶] [叶]     [叶] [叶] [叶]     ← 第 3 层（叶子）
   └──── 叶子层通过双向链表首尾相连，天然支持范围扫描 ────┘

三个关键性质，后面每一节都会用到：

性质带来的能力
树高极低（通常 3–4 层）等值查找 ≈ 3 次 I/O，且行数增长时几乎不变（对数增长）
叶子节点有序且用链表相连范围查询 BETWEEN、> 只需定位起点后顺着链表走；ORDER BY 可直接复用这个顺序，免排序
键在页内也是有序的页内二分查找
对比：为什么默认不用 Hash 索引

Hash 索引等值查找是 O(1)，理论上比 B-tree 快。但它完全没有顺序——不能做范围查询、不能免排序、不能支持最左前缀、不能做 ORDER BY。B-tree 用一点点等值性能换来了全部这些能力，所以是所有主流数据库的默认索引。（PG Index Types）

面试可以这么答：索引选 B-tree 不是因为它查得最快，而是因为它有序。有序带来范围查询、免排序、最左前缀这三个能力，Hash 一个都给不了。

二、联合索引 = 多级排序

忘掉"索引是一本书的目录"这个比喻，它解释不了最左前缀。用这个：

核心模型（本课唯一需要背的东西）

建在 (a, b, c) 上的联合索引，就是一张按 (a, b, c) 做多级排序的有序表——先按 a 排，a 相同的按 b 排，b 也相同的按 c 排。
就像电话簿按 (省, 市, 姓名) 排序。

假设索引建在 study 表的 (status, owner_id, created_at) 上，它在叶子层大致长这样：

status      owner_id   created_at     → 行指针(ctid)
------------------------------------------------------
ACTIVE      1001       2024-01-03     → (0,12)
ACTIVE      1001       2024-05-12     → (3,4)
ACTIVE      1007       2024-02-08     → (7,1)
ACTIVE      1007       2024-09-30     → (2,9)
CLOSED      1001       2024-03-15     → (5,6)
CLOSED      1002       2024-07-21     → (1,3)
DRAFT       1007       2024-11-02     → (9,8)

现在所有结论都能推导出来，不需要背：

  • WHERE status='ACTIVE' → 这些行在索引里是连续的一段，二分定位段首，顺着链表读。✅
  • WHERE status='ACTIVE' AND owner_id=1007 → 在上面那一段里，owner_id 依然有序，继续二分收窄。✅
  • WHERE owner_id=1007（跳过 status）→ owner_id=1007 的行散落在 ACTIVE 段、CLOSED 段、DRAFT 段各处，圈不出连续区间。❌ 这就是最左前缀。

Postgres 官方文档把规则写得很精确：

PostgreSQL Docs · 11.3 Multicolumn Indexes

Equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, will always be used to limit the portion of the index that is scanned.
—— postgresql.org/docs/current/indexes-multicolumn.html

拆开这句话，是两条规则，不是一条。多数候选人只说得出第一条：

规则含义
① 连续等值从最左列开始、连续不断的等值条件，都用来缩小索引扫描范围。
② 一次范围紧跟其后的第一个非等值条件（> < BETWEEN LIKE 'x%'）也能用，但到此为止——它右边的列不再能限定扫描范围。

为什么范围条件会"截断"？——用模型推一遍

索引 (a, b, c)，查询 WHERE a=1 AND b>5 AND c=9：

a   b   c
------------
1   3   9     ← a=1 但 b 不满足
1   6   2     ┐
1   6   9     │  b>5 圈出的区间：注意 c 列是 2,9,1,4,9…
1   7   1     │  在这个区间内部 c 已经不是有序的了！
1   9   4     │
1   9   9     ┘

看 c 那一列：2, 9, 1, 4, 9——无序。因为 c 只在「a 和 b 都相同」的小组内部才有序，而 b>5 跨越了多个 b 值，把这些小组拼在了一起。无序 → 无法二分 → 只能逐行检查。

所以 c=9 的角色从「定位」降级为「过滤」。在 Postgres 的 EXPLAIN 里，这个区别看得见：

Index Scan using ix1 on study
  Index Cond: ((a = 1) AND (b > 5))     ← 定位：决定扫多少行
  Filter: (c = 9)                        ← 过滤：扫完再逐行判断
  Rows Removed by Filter: 48213          ← 这个数字大 = 索引设计有问题
这是一个极强的面试信号

能说出 看 EXPLAIN 里条件落在 Index Cond 还是 Filter，就知道这一列有没有真正参与索引定位，比背十条失效规则更能证明你实际调过 SQL。

三、列顺序的黄金法则

法则

等值列 → 范围列 → 排序列。等值列内部，区分度高的放前面。

-- 目标查询：某负责人名下、近三个月的活跃 study，按创建时间倒序取前 20
SELECT id, title, created_at FROM study
WHERE owner_id = 1007             -- 等值，区分度高（5000 个负责人）
  AND status = 'ACTIVE'          -- 等值，区分度低（3 种状态）
  AND created_at >= '2026-05-01' -- 范围
ORDER BY created_at DESC LIMIT 20;

-- 索引：等值在前（高区分度优先），范围在后
CREATE INDEX ix_study_owner_status_created
  ON study (owner_id, status, created_at DESC);

这个索引一次干掉三件事：定位 owner_id、收窄 status、并且因为最后一列有序，ORDER BY created_at DESC LIMIT 20 可以直接取索引前 20 条就停——执行计划里昂贵的 Sort 节点消失了。

区分度：别凭感觉，去查

Postgres 把每列的统计信息暴露在 pg_stats 视图里，n_distinct 就是区分度指标：

SELECT attname, n_distinct, most_common_vals
FROM pg_stats WHERE tablename = 'study';

-- n_distinct 为正数  → 就是不同值的个数（如 5000）
-- n_distinct 为负数  → 是占总行数的比例（-1 表示每行都唯一，如主键）

选择性（selectivity）= 1 / n_distinct，即一个等值条件平均能筛掉多少。owner_id 有 5000 个值 → 选择性 1/5000，极好；status 只有 3 个值 → 选择性 1/3，很差，单独建索引几乎没意义。

陷阱一：排序方向必须匹配

索引的有序性是有方向的。ORDER BY a ASC, b DESC 这种混合排序，普通索引 (a, b) 用不上——顺读得到 a↑ b↑，倒读得到 a↓ b↓，都不是你要的。Postgres 支持在索引里指定方向：

CREATE INDEX ix_mixed ON orders (x ASC, y DESC);

同理还有 NULL 的位置：NULLS FIRST 是 DESC 的默认，NULLS LAST 是 ASC 的默认。如果查询写了 ORDER BY x DESC NULLS LAST 而索引是默认的，就免不了排序。（CREATE INDEX 文档）

陷阱二：别建冗余索引

索引 (a, b, c) 已经隐含了 (a) 和 (a, b) 的全部能力——因为最左前缀。所以：

-- ❌ 三个索引，其中两个纯属浪费（占空间 + 拖慢写入）
CREATE INDEX ix1 ON t (a);
CREATE INDEX ix2 ON t (a, b);
CREATE INDEX ix3 ON t (a, b, c);   -- 只留这一个就够

-- 但注意：(a,b) 和 (b,a) 不能互相替代，它们是两个不同的排序

查冗余索引（面试里提到这个查询会显得你真的运维过）：

-- 从来没被用过的索引
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes WHERE idx_scan = 0;

部分索引：Postgres 的一张好牌

如果业务只查某个子集，就只索引那个子集。索引体积可以小一两个数量级：

-- 100 万工单里只有 2000 单是待处理的，而 99% 的查询只查待处理
CREATE INDEX ix_pending ON work_order (created_at)
  WHERE status = 'PENDING';

-- 还能用来实现「子集唯一」这种普通唯一约束做不到的事
CREATE UNIQUE INDEX ux_one_active_claim ON claim (order_id)
  WHERE released_at IS NULL;   -- 同一工单同时只能有一个未释放的认领

第二个例子先记着——抢单场景设计题会用到它，用一个部分唯一索引就能在数据库层杜绝重复抢单。

四、回表与覆盖索引

索引里只有索引列和行指针。如果 SELECT 要的列不在索引里，数据库必须拿着指针再去表里捞一次完整行——这就是「回表」。

Postgres 与 MySQL 在这里根本不同

PostgreSQL（堆表）MySQL / InnoDB（聚簇索引）
表数据存放无序堆（heap），插入哪有空放哪按主键排序的 B-tree，数据就在主键索引的叶子里
二级索引叶子存什么ctid（页号,行号）物理位置主键值
回表代价按 ctid 直接访问对应页，一次 I/O拿主键再走一遍主键 B-tree，多几次 I/O
主键设计影响较小主键越大，所有二级索引都跟着变大；主键无序（如 UUIDv4）会导致页分裂

能讲清这张表，面试官基本能确定你不是只背过八股。

覆盖索引：干脆不回表

如果查询需要的列全部在索引里，就不用回表，执行计划显示为 Index Only Scan。Postgres 提供 INCLUDE 语法，把"只是想顺路带上"的列挂到索引上：

CREATE INDEX ix_cover ON study (owner_id, status)
  INCLUDE (title, created_at);

INCLUDE 的列有明确边界，说得出这些限制是加分项（官方文档）：

  • 不参与检索：不能出现在 WHERE 的索引定位里，也不影响最左前缀
  • 不参与排序：不能用来免 ORDER BY
  • 只有 B-tree / GiST / SP-GiST 支持；不能是表达式
  • 会增大索引体积，并且禁用 B-tree 去重（deduplication）
深挖 · Postgres 的 Index Only Scan 有个前提

因为 Postgres 的 MVCC 把行版本可见性信息存在表里而不是索引里，所以走 Index Only Scan 时它还要查可见性图（visibility map）确认那一页是否"全部可见"。如果表最近改动多、VACUUM 没跟上，可见性图不干净，它仍然要回表——执行计划里会显示 Heap Fetches: 很大的数字。

所以在 Postgres 上，「覆盖索引建了但没提速」的经典原因是 autovacuum 没跟上。这句话说出来，是真实生产经验的味道。

五、索引失效清单 · 三类归因

被问"索引失效有哪些情形"时，不要零散罗列。先给三类框架，再往里填例子，回答立刻显得有体系：

A 类 · 违反最左前缀（索引结构决定的"不能用"）

-- 索引 (a, b, c)
WHERE b = 1 AND c = 2          -- ❌ 跳过最左列 a
WHERE a = 1 AND c = 2          -- ⚠️ 只有 a 定位，c 退化为 Filter
WHERE a > 1 AND b = 2          -- ⚠️ a 之后截断，b 退化为 Filter
WHERE a = 1 OR d = 2           -- ❌ OR 的另一侧无索引，整体退化为全表扫

OR 值得单独说：OR 要求"任一条件成立"，只要有一侧无法用索引，就必须扫全表才能保证不漏。修复是拆成 UNION ALL（注意去重语义），或给 d 也建索引让优化器走 BitmapOr。

B 类 · 索引列被"加工"（值对不上了）

索引里存的是列的原始值。一旦对列套函数、做运算、做隐式类型转换，你要找的东西就不在索引里了。

WHERE lower(email) = 'a@b.com'          -- ❌ 函数包裹了列
WHERE created_at::date = '2026-05-01'   -- ❌ 类型转换
WHERE price * 2 > 100                     -- ❌ 列参与运算
WHERE title LIKE '%report'                -- ❌ 前导通配符，定位不到起点

Postgres 官方对第一种给了明确解释：普通索引存的是原值，查询要的是函数结果，两者对不上，只能全表逐行计算（Indexes on Expressions）。两种修复思路：

-- ✅ 思路一（首选）：让列「裸奔」，把加工挪到常量侧
WHERE created_at >= '2026-05-01' AND created_at < '2026-05-02'
WHERE price > 50

-- ✅ 思路二：建表达式索引，让索引里就存加工后的值
CREATE INDEX ix_user_lower_email ON users (lower(email));

表达式索引的代价要主动说出来：写入变慢——每次 INSERT 和非 HOT 的 UPDATE 都要重新计算一次表达式。官方原话：Index expressions are relatively expensive to maintain，适用于"读远多于写"的场景。

C 类 · 优化器主动放弃（"不想用"）

这一类最容易被忽略，也最能体现深度。索引扫描不一定比全表扫快。

索引扫描是随机 I/O（按索引顺序跳着访问表页），全表扫是顺序 I/O（磁盘预读友好）。当预计命中行数占比较高时（经验值 5%–20% 以上），随机 I/O 的总代价反而超过顺序扫全表，优化器会故意选 Seq Scan。

  • WHERE status = 'ACTIVE'，而 ACTIVE 占 60% → 用索引纯属自找麻烦
  • 表很小（几百行，一两个页）→ 全表扫本来就只要一次 I/O
  • 统计信息过期 → 优化器估错行数 → 选错计划。修复：ANALYZE study;
这句话顶十个例子

索引没走，先分清是不能用还是不想用。看 EXPLAIN (ANALYZE, BUFFERS) 里估算 rows 和 actual rows 差多少：差一两个数量级说明统计信息过期，ANALYZE 一下；如果估得准，那就是优化器算过成本认为全表扫更划算——这时候该改的是查询或表设计，不是硬加 hint。

六、C# / SqlSugar 里的索引杀手

这一节是本课和这个岗位结合最紧的部分。实际工作中，绝大多数索引失效不是人手写 SQL 写错的，是 ORM 悄悄翻译出来的。面试时能举出 ORM 层的具体例子，比只讲 SQL 理论有说服力得多。

杀手 1：.Date / .Year —— 类型转换

// ❌ 会被翻译成对列做 cast / date_trunc → 索引失效
var list = db.Queryable<Study>()
    .Where(it => it.CreatedAt.Date == queryDate)
    .ToList();
// 生成： WHERE CAST(created_at AS date) = '2026-05-01'

// ✅ 改成半开区间，列保持「裸奔」
var start = queryDate.Date;
var end   = start.AddDays(1);
var list = db.Queryable<Study>()
    .Where(it => it.CreatedAt >= start && it.CreatedAt < end)
    .ToList();
// 生成： WHERE created_at >= @s AND created_at < @e   ← 走索引
顺带一个正确性问题

用 >= start AND < end 这种半开区间，而不是 BETWEEN start AND end。BETWEEN 两端都闭，对 timestamp 会把 23:59:59.999999 之后、次日零点整的记录算进来，或者漏掉当天最后一毫秒——取决于精度。半开区间没有这个边界问题。

杀手 2：Contains —— 前导通配符

// ❌ 翻译成 LIKE '%report%'，B-tree 定位不到起点
.Where(it => it.Title.Contains(keyword))

// ✅ 前缀匹配可以走索引
.Where(it => it.Title.StartsWith(keyword))   // LIKE 'report%'

但 Postgres 上还有一个坑：在非 C collation 的数据库里，即使是 LIKE 'x%' 也用不了普通索引，需要专门的操作符类：

CREATE INDEX ix_title_pat ON study (title text_pattern_ops);

真要做任意位置的关键词搜索，正确答案不是 LIKE '%x%'，是全文检索（tsvector + GIN 索引）或 pg_trgm 三元组索引。这个回答会让面试官眼前一亮，因为它说明你知道"这个需求根本不该用 B-tree 解"。

杀手 3：Skip(n).Take(m) —— 深分页

// ❌ 第 500 页：OFFSET 10000
db.Queryable<Study>().OrderBy(it => it.Id, OrderByType.Desc)
  .ToPageList(500, 20);
// 生成： ORDER BY id DESC LIMIT 20 OFFSET 10000
// 数据库必须先扫出 10020 行、丢弃前 10000 行 —— 页码越大越慢

正确解法是 keyset pagination（游标分页 / seek method）：不用页码，用"上一页最后一条的 id"当锚点。

// ✅ 无论翻到第几页，代价恒定
var q = db.Queryable<Study>();
if (lastId is not null)
    q = q.Where(it => it.Id < lastId);
var page = q.OrderBy(it => it.Id, OrderByType.Desc).Take(20).ToList();
// 生成： WHERE id < @lastId ORDER BY id DESC LIMIT 20
// 直接在索引上定位到锚点，往后读 20 条就停

代价是不能跳页，只能"下一页"。这正好是取舍题的标准答案形态：后台管理需要跳页就用 OFFSET 但限制最大页数；C 端信息流用 keyset，反正用户也不会跳到第 500 页。

杀手 4：实体全字段查询，挡住 Index Only Scan

// ❌ SELECT * ：只要有一列不在索引里就必须回表
db.Queryable<Study>().Where(it => it.OwnerId == id).ToList();

// ✅ 投影到只需要的列，配合覆盖索引可走 Index Only Scan
db.Queryable<Study>()
  .Where(it => it.OwnerId == id)
  .Select(it => new StudyListItem { Id = it.Id, Title = it.Title })
  .ToList();

杀手 5：类型不匹配导致的隐式转换

C# 侧的 long 参数打到 Postgres 的 integer 列、或实体属性写成 string 而列是 uuid，都可能让数据库在列侧插入一个 cast。排查方法是直接看 ORM 打出来的 SQL：

// SqlSugar：把真实执行的 SQL 和参数打到日志里
db.Aop.OnLogExecuting = (sql, pars) =>
{
    _logger.LogDebug("SQL: {Sql}", sql);
};
面试话术 · 这段能直接用

我们后端用 SqlSugar，我的习惯是把 Aop.OnLogExecuting 打开、在开发环境把生成的 SQL 打到日志。因为 ORM 很容易悄悄写出索引失效的 SQL——最常见的三个是 .Date 被翻成 cast、Contains 被翻成前导通配符 LIKE、还有分页用 Skip/Take 生成大 OFFSET。发现慢查询时，我会把 ORM 生成的原始 SQL 拿出来单独跑 EXPLAIN ANALYZE，看条件落在 Index Cond 还是 Filter。

七、索引的代价

面试问"什么时候该建索引"，如果只答"查得慢就建"，是不及格的。索引是拿写入性能和存储空间换查询性能的交易，你要说得出成本在哪。

成本说明
写放大每个索引都是一棵要维护的 B-tree。一张表 5 个索引，一次 INSERT 就是 6 次结构写入（表 + 5 索引），外加对应的 WAL 日志。
阻断 HOT 更新Postgres 的 HOT（Heap-Only Tuple）优化：如果更新没有涉及任何被索引的列且同页有空间，就能跳过全部索引更新。给一个高频更新的列加索引，等于关掉了这个优化，写性能可能断崖下跌。
索引膨胀（bloat）频繁更新删除会在索引里留下死元组，索引越来越大、越来越慢。需要 REINDEX INDEX CONCURRENTLY 重建。
存储与缓存索引也要占 shared_buffers。无用索引挤占的缓存，本可以用来缓存热数据。
优化器负担候选索引越多，计划枚举空间越大，也更容易选错。

生产环境建索引：必须加 CONCURRENTLY

CREATE INDEX CONCURRENTLY ix_study_owner ON study (owner_id);

普通 CREATE INDEX 会锁住整表的写入直到建完——大表上就是一次生产事故。CONCURRENTLY 避免这个锁，但它的代价同样要说得出来（官方文档）：

  • 要扫两遍表，总耗时明显更长
  • 不能在事务块里执行（所以数据库迁移脚本里要特殊处理——EF Core / Flyway 的迁移默认包在事务里，这是个真实的坑）
  • 失败时会留下一个 INVALID 索引：查询用不上它，但写入仍要维护它。必须 DROP INDEX 后重来。所以建完要检查 SELECT * FROM pg_index WHERE NOT indisvalid;
这是一个很好的"踩坑经历"素材

如果你在项目里给大表加过索引，把上面这段包装成经历讲：我们在 Postgres 上给一张千万行的表加索引，第一次直接 CREATE INDEX 把线上写入卡住了，后来改成 CONCURRENTLY；又踩了一次迁移脚本默认开事务导致执行不了的坑，最后是拆成独立的运维脚本、并且加了 INVALID 索引的检查。三层细节，面试官会信。

八、统计信息与优化器

这一节是「深度炸弹」——大多数候选人到第五节就到顶了。

Postgres 的优化器是基于成本的：它为每个可能的执行计划估算代价，选最便宜的。估算的原料就是 ANALYZE 收集的统计信息（Planner Statistics）：

统计项作用
reltuples / relpages表的行数和页数（在 pg_class）
n_distinct该列不同值的个数 → 决定等值条件的选择性
most_common_vals + 频率高频值列表 → 处理数据倾斜，比如 90% 的行 status 都是 ACTIVE
histogram_bounds值分布直方图 → 估算范围条件能命中多少行

致命假设：优化器认为各列是独立的

估算多条件时，Postgres 默认把选择性相乘。WHERE city='上海' AND zip='200000'，假设 city 选择性 1/300、zip 选择性 1/5000，它估算 1/300 × 1/5000 = 1/1,500,000。

但现实中邮编决定城市——这两列高度相关，实际选择性就是 1/5000。估算差了 300 倍，优化器于是以为只会返回 1 行，选了 Nested Loop，实际返回 30000 行，查询慢到爆炸。

解法是扩展统计信息：

-- 告诉优化器：这两列是相关的，请单独统计它们的组合分布
CREATE STATISTICS stts (dependencies) ON city, zip FROM zipcodes;
ANALYZE zipcodes;

三种类型（官方文档）：

  • dependencies —— 函数依赖（邮编 → 城市）。只对等值条件和 IN 有效。
  • ndistinct —— 多列组合的不同值个数，主要改善 GROUP BY 多列时的计划选择。
  • mcv —— 多列高频值组合。官方例子里，(Washington, DC) 实际出现频率 0.35%，单列统计推出来只有 0.0027%，差 100 倍。
怎么把它用在面试里

不要主动大段讲这个，太显得背书。等面试官问"索引都建了还是慢怎么办"或"优化器选错计划怎么处理"的时候再抛：如果索引没问题、统计信息也 ANALYZE 过了还选错，我会看是不是多个过滤列之间存在相关性。Postgres 的优化器默认假设列与列独立、把选择性直接相乘，遇到像省和市、状态和类型这种强相关的列会严重低估行数，进而选错 join 方式。这种情况可以用 CREATE STATISTICS 建扩展统计信息告诉优化器它们相关。

十、面试话术

Q：讲讲联合索引和最左前缀原则

联合索引在物理上是一棵按索引列做多级排序的 B-tree，比如 (a,b,c) 就是先按 a 排、a 相同再按 b 排。所以能不能用索引定位，本质上取决于查询条件能不能在这个有序结构上圈出一段连续区间——这就是最左前缀。

准确讲是两条规则：从最左列开始连续的等值条件都能用来缩小扫描范围；再加上其后第一个范围条件也能用，但到此为止，范围条件右边的列就只能做过滤了。原因是范围条件跨越了多个值，把若干个小组拼在一起，右边那一列在拼接后的区间里已经不是有序的了。

在 Postgres 的 EXPLAIN 里这个区别是能直接看到的：参与定位的落在 Index Cond，只做过滤的落在 Filter，旁边还有 Rows Removed by Filter，这个数字大就说明索引设计有优化空间。

Q：什么时候该建索引？根据什么建？

我不按字段建，按查询建。先把这张表上真实跑的高频 SQL 捞出来——慢查询日志或者 pg_stat_statements 按总耗时排序——看 WHERE、JOIN、ORDER BY 用到哪些列，再按等值、范围、排序的顺序拼联合索引，等值列内部把区分度高的放前面。

然后要反过来算成本。索引是拿写入换查询：每加一个索引，每次 INSERT 就多一棵 B-tree 要维护，还多一份 WAL；在 Postgres 上给高频更新的列加索引还会破坏 HOT 更新优化，写性能可能明显下降。所以我会看三件事：这列区分度够不够、这张表读写比多少、有没有已存在的索引能覆盖——(a,b,c) 已经隐含了 (a) 和 (a,b)，不用重复建。我还会定期查 pg_stat_user_indexes 里 idx_scan 为 0 的索引，把从来没被用过的清掉。

Q：索引失效有哪些情形？

我一般分三类来看。第一类是违反最左前缀，跳过前导列、或者被范围条件截断，这是索引结构决定的「不能用」。第二类是索引列被加工——套函数、类型转换、参与运算、前导通配符的 LIKE，因为索引里存的是原始值，加工之后就对不上了；修复要么把加工挪到常量侧让列裸奔，要么建表达式索引，代价是写入变慢。

第三类最容易被忽略，是优化器主动放弃。索引扫描是随机 I/O，命中行占比高的时候还不如顺序扫全表，这时候不走索引是正确选择。所以我排查的第一步不是加索引，是看 EXPLAIN ANALYZE 里估算行数和实际行数差多少——差得离谱说明统计信息过期，ANALYZE 就行；估得准那就是成本算下来全表扫更划算。

另外实际工作中，索引失效更多是 ORM 悄悄造成的。我们用 SqlSugar，我会把 Aop.OnLogExecuting 打开、在开发环境打印生成的 SQL。最常见的三个坑是 .Date 被翻成 cast、Contains 翻成前导通配符 LIKE、以及分页用 Skip/Take 生成大 OFFSET。

Q：数据库如何优化查询 SQL 提高执行效率？

我按一个固定顺序走，避免凭感觉乱改。第一步定位：用 pg_stat_statements 按总耗时排序，找真正的大头，而不是猜哪条慢——有时候单次 20ms 但调用百万次的那条才是问题。第二步解释：对候选 SQL 跑 EXPLAIN ANALYZE BUFFERS，看扫描方式、估算与实际行数的差距、有没有 Sort 溢出到磁盘、大表之间有没有 Nested Loop。

第三步改写：让列裸奔、去掉 SELECT *、OR 拆成 UNION ALL、深分页从 OFFSET 换成 keyset。第四步才是加索引，按等值范围排序拼列，生产环境一定加 CONCURRENTLY。再不够才往上走：缓存、物化视图、读写分离、分区表。最后一定要再跑一次 EXPLAIN 验证，用数字说话而不是「感觉快了」。

十一、动手实验（约 25 分钟）

光看不练，三天就忘。亲手看一次执行计划的变化，这些结论才会变成你的。

# 1. 起一个 Postgres
docker run --name pg-prep -e POSTGRES_PASSWORD=pw -p 5432:5432 -d postgres:17
docker exec -it pg-prep psql -U postgres
-- 2. 造 100 万行
CREATE TABLE study (
  id bigserial PRIMARY KEY, owner_id int, status text,
  created_at timestamptz, title text);

INSERT INTO study (owner_id, status, created_at, title)
SELECT (random()*5000)::int,
       (ARRAY['ACTIVE','CLOSED','DRAFT'])[1+(random()*2)::int],
       now() - (random()*400) * interval '1 day',
       'study-' || g
FROM generate_series(1,1000000) g;
ANALYZE study;

-- 3. 无索引基线：记下 Seq Scan 和耗时
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM study WHERE owner_id=1007 AND status='ACTIVE'
ORDER BY created_at DESC LIMIT 20;

-- 4. 建索引，再跑一次：Seq Scan 和 Sort 应该同时消失
CREATE INDEX ix1 ON study (owner_id, status, created_at DESC);

-- 5. 亲手制造失效 A 类：跳过最左列，观察它退回 Seq Scan
EXPLAIN (ANALYZE) SELECT * FROM study WHERE status='ACTIVE' LIMIT 20;

-- 6. 制造失效 B 类：对列做类型转换
EXPLAIN (ANALYZE) SELECT * FROM study
  WHERE owner_id=1007 AND created_at::date = '2026-05-01';
-- 对比：改成半开区间
EXPLAIN (ANALYZE) SELECT * FROM study
  WHERE owner_id=1007
    AND created_at >= '2026-05-01' AND created_at < '2026-05-02';

-- 7. 观察 Index Cond 与 Filter 的区别（范围截断）
EXPLAIN (ANALYZE) SELECT * FROM study
  WHERE owner_id > 4000 AND status = 'ACTIVE';
-- 看 status 落在哪一行，以及 Rows Removed by Filter

-- 8. 深分页的代价：对比这两条的耗时
EXPLAIN (ANALYZE) SELECT * FROM study ORDER BY id DESC LIMIT 20 OFFSET 900000;
EXPLAIN (ANALYZE) SELECT * FROM study WHERE id < 100001 ORDER BY id DESC LIMIT 20;

-- 9. 覆盖索引：观察 Index Only Scan 与 Heap Fetches
CREATE INDEX ix_cover ON study (owner_id, status) INCLUDE (title);
EXPLAIN (ANALYZE) SELECT title FROM study
  WHERE owner_id=1007 AND status='ACTIVE';
-- 然后 UPDATE 几千行再跑一次，看 Heap Fetches 变大；VACUUM study; 后再看
