一、唯一真正改变的那一行

先把「微服务」这个词放一边。看这两段 C#，它们做的是同一件事：工单提交后要扣一件库存。

// 单体里：一次进程内的方法调用
public async Task<Ticket> Submit(TicketDto dto)
{
    var ticket = await _tickets.CreateAsync(dto);
    _inventory.Reserve(dto.PartId, 1);      // ← 就是这一行
    return ticket;
}
// 拆开之后：一次跨进程的网络调用
public async Task<Ticket> Submit(TicketDto dto)
{
    var ticket = await _tickets.CreateAsync(dto);
    await _http.PostAsJsonAsync("/reserve", new { dto.PartId, Qty = 1 });   // ← 还是这一行
    return ticket;
}

整个微服务话题，就是这一行的替换带来的全部后果。其它一切——网关、熔断、链路追踪、最终一致性、服务注册——都是为了把这一行「换掉之后丢失的东西」重新买回来。

那么丢了什么？在进程内，下面四件事是免费的，你从来不用想；换成网络调用之后，四件全部开始收费：

在进程内你免费拥有跨进程之后要花钱买回来
调用一定会返回（要么正常，要么抛异常）可能超时、可能失败、可能成功了但你不知道重试 + 幂等 + 熔断
异常带着完整调用堆栈堆栈在对方进程里，你只收到一个 500分布式链路追踪（TraceId）
一个数据库事务能一起回滚两个库、两个事务，回滚不了对方最终一致性（消息 + 幂等消费）
方法名就是地址，编译器帮你找要知道对方的 IP、端口、版本、是否还活着网关 / 服务发现
这就是你的开场白

面试问「你对微服务的了解」，不要从「独立部署、技术异构、康威定律」开始背——那是所有人都会背的。从这张表开始：微服务的本质是把进程内调用换成网络调用，因此进程内免费的四件事全部开始收费，而微服务的整套技术栈就是这四张账单的付款方式。这个开场立刻把你和背概念的人区分开。

扩展 · 为什么有人愿意付这四笔钱

Martin Fowler 把这叫 Microservice Premium（微服务溢价）：换来的是强模块边界、独立部署、技术异构三项收益，代价是分布式、最终一致性、运维复杂度三项成本，而且只有在系统复杂到一定程度时收益才盖得住成本（Fowler, Microservice Trade-Offs）。「该不该拆」这道题涉及一整套判断，放在 Lesson 05 专门讲——先把这一课的四笔开销吃透，那道题的答案自然就有了骨架。

二、第一笔开销：调用会失败，而且三种失败长得一模一样

进程内调用只有两种结局：返回，或者抛异常。网络调用有四种，而其中三种在调用方看起来几乎无法区分。这是分布式系统里最反直觉的一点，也是面试官最喜欢往下追的地方。

下面这个组件，把上面那行 POST /reserve 单独拎出来。先猜，再点：四种模式下，工单服务分别看到什么？库存到底扣了没有？

这一节只要记住一句话

「超时」和「成功但响应丢失」在调用方看来是同一件事，永远分不清。所以分布式系统里的重试没有意义，除非接口是幂等的。面试时能主动说出这句话，比说得出 Polly 的全部策略名更有分量——因为它说明你知道为什么需要那些策略。

幂等怎么落地（这是最容易被追问的一层）

「幂等」不是加个 if 判断就行。可靠的做法是让数据库来保证，而不是让代码来保证：

-- 库存服务这边：请求去重表，RequestId 上一个唯一索引
CREATE TABLE reserve_log (
    request_id  uuid PRIMARY KEY,      -- 调用方生成，业务上唯一
    part_id     bigint NOT NULL,
    qty         int    NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);
// 同一个事务里：先插去重记录，再扣库存。插不进去就说明重复了。
using var tx = db.BeginTransaction();
try
{
    db.Insertable(new ReserveLog { RequestId = req.RequestId, ... }).ExecuteCommand();
    db.Updateable<Part>().SetColumns(p => p.Stock == p.Stock - req.Qty)
      .Where(p => p.Id == req.PartId && p.Stock >= req.Qty).ExecuteCommand();
    tx.Commit();
}
catch (Exception e) when (IsUniqueViolation(e))   // PostgreSQL 23505
{
    tx.Rollback();
    return Ok("already processed");      // ← 重复请求，直接当成功返回
}

关键在于插日志和扣库存在同一个本地事务里。如果分成两步，就又制造出一个「插了日志但没扣成」的新窗口。这和 Lesson 01 里那个部分唯一索引是同一个思路：把并发正确性下沉到数据库的唯一约束上，而不是靠应用层的判断。

重试与熔断：.NET 里具体怎么配

不要手写重试循环。.NET 8 起官方给了 Microsoft.Extensions.Http.Resilience（内部是 Polly），一行代码挂上五层标准策略：

builder.Services.AddHttpClient<InventoryClient>(c =>
       {
           c.BaseAddress = new Uri("http://inventory");
       })
       .AddStandardResilienceHandler(o =>
       {
           o.Retry.DisableForUnsafeHttpMethods();   // POST/PUT/DELETE 不重试
       });

AddStandardResilienceHandler() 默认从外到内叠这五层（Microsoft Learn 官方默认值）：

#策略它挡住什么默认值
1Rate limiter自己把对方打垮并发上限 1000
2Total timeout含重试在内的总耗时失控30 秒
3Retry瞬时抖动3 次，指数退避 2s 起，带 jitter
4Circuit breaker对方已经挂了还继续打失败率 10%、采样 30s、断开 5s
5Attempt timeout单次调用挂死10 秒

三个细节值得你在面试里主动说出来，每一个都能证明你真的想过这件事：

  • jitter（抖动）：如果一百个实例都「失败后等 2 秒再试」，两秒后会形成一波整齐的重试洪峰，把刚缓过来的服务再打死一次。加随机抖动把重试摊开。
  • 熔断的本质是「保护调用方」，不是保护被调用方。对方挂了还一直调，你的线程和连接会被慢调用占满，故障顺着调用链传染上来——这叫级联失败。熔断就是快速失败，把自己的资源守住。
  • POST 默认不该重试。官方专门给了 DisableForUnsafeHttpMethods()，理由正是上面那张表的第四种情况：if a POST request inserts a new record to a database, then making retries for such a request could lead to data duplication。除非你已经做了幂等键。
面试话术 · 对应题「其中一个微服务故障或调用异常，如何处理」

结论：分三层：调用层做超时和熔断，接口层做幂等，业务层做降级。

原因：网络调用有四种结局，其中「超时」和「对方执行了但响应丢了」在调用方看来完全一样，分不出来。所以我不指望判断真相，而是让真相无所谓——接口做成幂等的，重复调用结果一致，这样重试才是安全的。

取舍：超时值要卡紧，宁可快失败也不要慢。因为慢调用会把我这边的线程和连接占住，故障会顺着调用链往上传染，一个下游拖垮整条链。熔断的目的其实是保护我自己，不是保护对方。另外 POST 这类写接口默认我不开重试，除非已经有幂等键，否则重试等于制造重复数据。

落地：.NET 里我不手写重试循环，用 AddStandardResilienceHandler，限流、总超时、指数退避重试、熔断、单次超时五层是标配，重试一定要带 jitter，否则一百个实例会同时重试形成洪峰。

三、第二笔开销：堆栈断了

单体里出错，你有一条完整的堆栈，从 Controller 一路到出错那行。拆开之后，工单服务收到的只是一个 500——真正的堆栈在库存服务的日志里，而库存服务今天有 6 个实例。

解决办法：给每一次用户请求发一个全局唯一的编号，让它跟着请求跑遍所有服务。这就是分布式链路追踪。三个术语，一次说清：

术语是什么类比
Trace（.NET 里是一棵 Activity 树）一次用户请求的完整过程，横跨所有服务一个快递单号下的全部轨迹
Span其中一段工作：一次 HTTP 调用、一条 SQL轨迹里的一条：「已到达 XX 分拣中心」
TraceId / SpanId16 字节的全局 trace 号 + 8 字节的段号，每段还记着父段的号快递单号 + 每条轨迹的序号与上一站

它是怎么跨进程传的？靠一个 HTTP 头。W3C 定了标准叫 Trace Context，头的名字是 traceparent，长这样：

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^版本 ^--------- TraceId (16B) ---------^ ^-- SpanId --^ ^标志
.NET 的一个大便宜，一定要说出来

Unlike many other language runtimes, .NET in-box libraries such as the ASP.NET web server and System.Net.Http natively understand how to decode and encode Activity IDs on HTTP messages ... with no special coding by the app developer（Microsoft Learn）。也就是说：ASP.NET Core 收到请求时会自动读 traceparent，HttpClient 发请求时会自动带上，Activity.Current 还会自动跟着 async 流转。W3C 格式从 .NET 5 起就是默认。你要做的只有一件事：把 TraceId 写进日志。

// 日志里带上 TraceId —— 这一行是「能排查」和「不能排查」的分界线
_logger.LogError(ex, "扣件失败 TraceId={TraceId} PartId={PartId}",
                 Activity.Current?.TraceId, req.PartId);

有了它，排查流程从「登录 6 台机器 grep 时间段」变成「拿用户报错页面上的那串 TraceId，在日志平台里搜一次，整条链按时间排好」。

扩展 · 采集端怎么选，以及一个必踩的坑

Activity 只是产生数据，还需要一个采集器把它送到集中存储：OpenTelemetry（厂商中立，现在的默认选择）、Application Insights、或各家 APM。坑：全量采集在高流量下开销很大，所以要采样；.NET 里未被采样的 Activity 开销可以低到 100 纳秒以下。但采样有个陷阱——如果按固定比例随机采样，出问题的那条链很可能恰好没被采到。常见对策是「尾部采样」：先缓存，等整条链结束后发现有错误或超慢再决定留下。面试如果被追到这一层，能说出「采样率」和「出错的链要保证留下」就足够了。

面试话术 · 对应题「微服务的异常追踪问题」

结论：核心是让一次用户请求在所有服务里有同一个 TraceId，日志按 TraceId 能串起来。

原因：拆开之后堆栈断在进程边界上，我只收到一个 500，真正的异常在下游某个实例的日志里。没有 TraceId 就只能靠时间戳猜，实例一多就没法查了。

落地：.NET 这块基本是白送的：ASP.NET Core 和 HttpClient 原生认 W3C 的 traceparent 头，.NET 5 起是默认格式，Activity 还会跟着 async 自动流转，不用自己写传递代码。我要做的就是在日志里输出 Activity.Current.TraceId，再把错误返回给前端时也带上，用户截图就能直接定位。

取舍：全量采集成本高，所以要采样；但要注意别把出错的链采掉了，理想是尾部采样——整条链结束后发现有错误或超慢再留。

四、第三笔开销：一个事务变成了两个

回到第一节那段代码。单体版本里，如果 _inventory.Reserve() 抛异常，外面一个事务全部回滚，工单也不会留下。拆开之后，这个保证消失了——工单在你的库，库存在对方的库，你没有任何办法让对方跟着你回滚。

教科书上的答案是分布式事务（2PC）。实践里基本不用，理由 Fowler 说得很直接：distributed transactions are frowned on (for good reason)。原因很实际：2PC 要求所有参与者在第二阶段前一直持锁，任何一方慢或挂，其它人的锁就一直握着，吞吐直接塌掉。

实践里的做法是换一个目标：不再追求「任何时刻都一致」，改成「允许短暂不一致，但保证最终一致」。最常用的一套组合：

步骤做什么为什么这样才安全
① 本地事务建工单 + 往本地的消息表插一条待发消息，同一个事务提交两件事同生共死。不会出现「工单建了但消息没发」
② 投递一个后台任务扫消息表，发到 RabbitMQ，成功后标记已发发送失败可以一直重发，消息不会丢
③ 消费库存服务收到消息，用第二节那张去重表做幂等扣减MQ 保证的是「至少一次」，一定会有重复投递
④ 确认业务处理成功后才手动 ACK处理途中崩溃，消息会重新入队，不会丢

①叫本地消息表 / Outbox 模式。它解决的是一个非常刁钻的问题：你不可能让「写数据库」和「发消息到 MQ」这两件事原子地一起成功——它们是两个系统。Outbox 的技巧是把「发消息」这个动作先变成「往自己库里写一行」，于是它就能和业务数据进同一个本地事务了。

注意，这里出现了闭环

③ 用的正是第二节那张 request_id 去重表。不是巧合：MQ 的投递保证是「至少一次」（at-least-once），因为 ACK 本身也可能丢——这和 HTTP 那个「执行了但响应丢了」是完全同一个问题。所以答案也是同一个：幂等消费。
能在面试里把「HTTP 重试要幂等」和「MQ 消费要幂等」归结成同一个原因，是很强的信号——它说明你理解的是机制，不是背了两条最佳实践。

面试话术 · 对应题「和第三方交互时如何保证数据一致性」/「RabbitMQ 如何消费」

结论：放弃强一致，做最终一致：本地消息表 + MQ + 幂等消费 + 手动 ACK。

原因：跨系统没有共同的事务。2PC 理论上可以，但要长时间持锁，一方慢就拖垮所有人，实践里基本不用。而且对第三方来说，我连让它回滚的权限都没有。

机制：关键难点是「写自己的库」和「发消息」没法原子。所以我把发消息先降级成写自己库里的一张消息表，跟业务数据同一个事务提交；再由后台任务扫表投递，投递失败就重发。消费端因为 MQ 是至少一次投递，必须幂等——用业务唯一键建唯一索引，重复的直接当成功返回。ACK 一定是业务处理完再手动 ACK，不能用自动 ACK，否则处理到一半崩了消息就没了。

取舍：代价是存在一个不一致窗口，所以要配对账任务和告警：超过多少分钟还没最终一致的，捞出来人工处理。这个窗口业务上能不能接受，是拆服务之前就要和业务确认的事。

五、第四笔开销：调用方不知道该往哪儿打

单体只有一个地址。拆成 8 个服务之后，前端难道要记 8 个地址、8 套跨域配置、8 处登录校验？网关的第一职责不是路由，是把所有「每个服务都要做一遍」的横切关注点收到一个地方。

网关承担不放网关会怎样
统一入口 / 路由 / 负载均衡前端要知道每个服务在哪，服务一扩容前端就得改
认证鉴权（验 JWT 签名、解出身份）八个服务各写一遍，改一次密钥要改八个地方
限流、TLS 卸载、跨域、请求日志同上，且策略必然逐渐不一致

.NET 生态里三个选项，足够回答「用过哪些网关，为什么选它」：

选项是什么什么时候选它
YARP微软官方的 .NET 反向代理库，本身就是一个 ASP.NET Core 应用，配置走 JSON；支持 gRPC / WebSocket / HTTP2 / HTTP3（官方文档）团队是 .NET 栈、需要写自定义转换逻辑（改头、灰度、按租户路由）时的当前首选
Ocelot较早的 .NET 开源网关，社区项目老项目里常见；新项目微软已把 YARP 作为推荐方向
Nginx / 云厂商 API 网关与语言无关的成熟基础设施纯路由 + TLS + 限流、不需要业务逻辑时最省事、性能最好
扩展 · 一个能显著加分的追问答案

如果被问「网关会不会成为单点」——会。所以网关本身要多实例部署，前面挂负载均衡；并且网关里绝对不要放业务逻辑，一旦放了，每次业务改动都要动网关，网关就成了新的单体。这条正是拆微服务的人最容易犯的错，说出来说明你见过真实的坑。

面试话术 · 对应题「用过哪些网关，为何选择」

结论 + 诚实定位：我理解网关的核心价值不在路由，而在于把认证、限流、跨域、日志这些每个服务都要做一遍的横切关注点收到一处。——如果你实际只用过 Nginx，就直说 我们的场景比较简单，前面是 Nginx 做路由和 TLS，认证在应用侧；如果要往上做，.NET 栈我会优先看 YARP，因为它本身就是一个 ASP.NET Core 应用，能直接写 C# 的转换逻辑做灰度或按租户路由，不用引第二套技术栈。

为什么这样答更好：把「用过什么」和「知道该怎么选」分开说。面试官真正想知道的是后者。硬说自己用过 YARP，追问一句配置结构就露馅了——而承认边界再展示判断力，几乎从不扣分。

六、一页对照：九道题挂回四笔开销

把题库里微服务板块的题，全部挂回这一课的四笔开销。请遮住右边一列，自己先说一遍：

题库原题其实在问哪笔开销
微服务的了解？开场用第一节那张表：四件免费的事开始收费

八、我需要你的三个素材

这一课给了你机制和话术骨架，但面试官一定会追问「你项目里怎么用的」。你自评微服务经历偏薄，所以我们要做的不是编，而是把你真做过的事，精确地挂到上面四笔开销上。请回答我三个问题，我会据此把话术改写成你的版本：

  1. 你们的系统是几个服务？它们之间是怎么调的——HTTP、MQ、还是直接读同一个数据库？（「共用一个库」也是很常见的答案，而且它本身就是一个很好的可讨论点）
  2. RabbitMQ 你具体做过什么？发过消息还是消费过？有没有遇到过消息重复、消息堆积、或者消费失败的情况？当时怎么处理的？
  3. 第三方对接那次：对方是同步接口还是回调？有没有出现过「我方以为失败，其实对方成功了」这类问题？你们怎么发现和补救的？（哪怕答案是「手工改数据」，也能改写成一段很好的话术——它证明你亲历过不一致）
如果三个问题的答案都很薄

那也完全没问题，而且不要编。经历薄的正确打法是：把「我做过的那一小块」讲到非常具体（具体到表名、字段、当时的错误现象），再接一句更完整的那套我们当时没做到，如果重来我会……。面试官分辨得出「具体但小」和「宏大但空」，前者得分高得多。Lesson 05 会专门把这个策略做成一套可复用的句式。
