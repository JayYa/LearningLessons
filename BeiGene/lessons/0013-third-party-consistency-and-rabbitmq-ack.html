一、先破一个错觉

题目原话：「如果我方更新数据成功第三方返回的 response 失败，或者我方更新数据失败第三方返回的 response 成功，怎么处理」。这句话画出来是一个 2×2：我方 {成功, 失败} × 对方 {成功, 失败}。大多数人顺着这张表答：「成功-失败就回滚我方，失败-成功就调对方的撤销接口」。答完了，面试官追一句：「对方超时了呢？」——表上没有这一列。

这不是刁难。RabbitMQ 官方的可靠性指南把同一件事说得很直白（Reliability Guide）：When a connection fails, messages may be in transit between client and server ... In such events messages in transit will not be delivered — they will need to be retransmitted. 连接断的那一刻，你不知道那条消息到没到。HTTP 一模一样：超时异常抛出来的时候，对方可能没收到、可能收到没执行、可能执行了响应没回来。

这一课唯一必须记死的一句

跨系统的每一步都有三种结果：成功、失败、不知道。前两种一句 if 就能处理；一致性设计里所有看起来复杂的东西——中间态、幂等键、查询接口、对账任务、手动 ACK、去重表——全是为第三种做的。

所以那张 2×2 要改成 3×3，而且真正难的格子只有含「不知道」的那几个。面试里先把这句话说出来，再答具体做法，面试官就知道你不是在背「回滚 + 撤销」。下面按流水线的顺序把三种结果各自的处理立起来：先看顺序，再看「不知道」怎么消解，最后看 MQ 上同一件事叫什么名字。

二、先写库还是先调对方：中间态是一切恢复的锚

「交互怎么实现」这道题的第一个取舍是顺序。三种写法：

顺序对方成功、我方写库失败时对方超时时判定
先调对方，再写库对方做了，我方一条记录都没有。没有任何东西告诉你这笔交易存在过——只能等对方的账单来揭发。这就是题里「我方失败对方成功」的最坏形态：幽灵交易同样无记录✗ 永远别这么写
先写终态，再调对方不会发生（我方已写）库里写着「已支付」，对方可能根本没收到。要么回滚、要么补偿，而两者都要先知道对方到底做没做——你不知道△ 常见，但终态是假的
先写中间态（PENDING），调对方，再推进终态记录停在 PENDING。后台任务扫到超时的 PENDING → 查对方 → 推进到 CONFIRMED。没有幽灵同样停在 PENDING，同样的恢复路径✓ 标准做法

第三种写法的价值在于：不管后面发生什么，本地永远有一条带业务 id、带时间戳、带状态的记录。它是所有恢复动作的锚——重试拿它当幂等键，查询拿它当查询参数，对账拿它当比对基准。没有它，「不知道」就没有办法变成「知道」。

你已经见过这个东西三次了：Lesson 05 叫它语义锁（订单先进「处理中」），Lesson 07 的抢单先写 reviewing 再干活，Lesson 12 的两步登录先发「半张票」。多步流程里，每一步只把状态推进到「刚好能证明走到了这里」，不提前写终态。

现在把这个模型放进故障探索器。我方已经写了 PENDING，正在调第三方支付。四种真相，一个个点：

四个模式，一个结论

先写 PENDING 之后，题目里的 2×2 塌缩了：对方明确失败 → FAILED；对方明确成功 → CONFIRMED；其余一切（超时、我方推进失败、进程被杀）→ 停在 PENDING，由同一条恢复路径处理。面试里把这句说出来，比逐格答「回滚 / 撤销」强得多——它说明你的设计不依赖于知道对方的结果。

三、把「不知道」变成「知道」：三条路

停在 PENDING 的记录不能停一辈子。三条路把它推进到终态，按成本从低到高：

#路前提怎么做什么时候够用
1幂等重试对方接口支持幂等键带同一个 key 再发一次。对方若已执行，返回第一次的结果；若没执行，这次执行。我方拿到确定答案大多数超时。Stripe 的做法是行业标准：if a connection error occurs, you can safely repeat the request without risk of creating a second object or performing the update twice（Stripe — Idempotent requests）
2查询接口对方提供按业务号查状态的接口后台任务扫 PENDING AND created_at < now() - 2min，逐条查对方，按结果推进对方不支持幂等键（国内很多支付 / 物流接口是这个形态：下单不幂等，但有 query 接口）
3对账对方定期给账单文件 / 批量查询接口每天（或每小时）拉对方的全量记录，和我方 CONFIRMED / PENDING 比对，差异进人工处理队列兜底，永远要有。前两条覆盖不到的：对方回调没送到、我方进程在 PENDING 和对方成功之间被杀、对方内部改了状态

三条路不是三选一，是三层：重试解决 95%，查询解决剩下的绝大多数，对账兜住最后的零头并且顺便验证前两层没出 bug。面试里说「我们有对账」，比说任何单一机制都让人放心——它意味着你承认前面的机制会漏。

扩展 · 幂等键的三个细节，追问时用
  • key 按什么粒度做？按业务动作做：「订单 1001 的这次支付」= 本地 biz_id。不要用随机 UUID 每次重新生成——那就不是同一个 key，重试等于发两笔。这和 Lesson 12 黑名单「按 token 还是按用户做 key」是同一类判断：先问要去重的是什么，再定 key。
  • 对方怎么实现的？Stripe 原文：saving the resulting status code and body of the first request made for any given idempotency key, regardless of whether it succeeds or fails ... Subsequent requests with the same key return the same result, including 500 errors. 你自己作为被调方时也这么做——就是 Lesson 05 那张 tx_log(biz_id, state) 表再加一列存响应。
  • 同 key 不同参数？Stripe：compares incoming parameters to those of the original request and errors if they are not the same。你的实现也该报错，不然一次重试悄悄改了金额。

四、操作成功后怎么通知用户

题「数据操作成功后怎么通知用户」看起来是前端题，出题人想听的是两件事：通知由什么触发，以及通知自己丢了怎么办。

触发点：状态推进的那一刻，不是请求线程。用户点「支付」那个 HTTP 请求回来的时候，记录多半还是 PENDING——通知不能在那里发。正确的挂点是 PENDING → CONFIRMED 那条 UPDATE 提交之后，而这条 UPDATE 可能由请求线程执行、也可能由后台查询任务或对账任务执行。所以通知要挂在状态机的转换上，谁推进了状态谁发通知——最省事的办法是推进状态和写 outbox 消息放同一个事务，通知服务消费 outbox。

渠道机制适合丢了怎么办
页面实时推送SignalR（WebSocket，降级 SSE / 长轮询）。服务端 hub.Clients.User(userId).SendAsync(...)用户还停在页面上等结果连接断了就丢。所以页面重连后主动拉一次状态；推送只是加速，不是唯一来源
轮询 / 回到页面刷新前端每 N 秒 GET /orders/{id}，或页面可见时拉一次结果几秒到几分钟内出来天然不丢：读的是库里的状态
站内信 / 邮件 / 短信 / 企业微信状态推进时写 outbox → MQ → 通知服务发送用户已经离开，或者结果要很久通知服务对第三方（短信网关）的调用又是一次跨系统调用——三种结果，同一套处理：至少一次 + 幂等（同一条通知发两次可以接受，发零次不行）
一句可以直接说的判断

「通知挂在状态转换上，走 outbox 至少一次投递；实时推送只做加速，页面重连后一定回源拉一次状态。」——这句同时回答了「怎么通知」和「通知丢了怎么办」。

五、ACK 实验室：亲手丢一条、重复一条、死信一条

换到 MQ 现场。这里「不知道」的形态是：消费者处理完了，但 broker 不知道——ACK 没送到。RabbitMQ 靠一套确认协议处理它，官方定义（Consumer Acknowledgements）：

  • 自动 ACK：a message is considered to be successfully delivered immediately after it is sent，官方直接说它 should be considered unsafe。
  • 手动 ACK 下的崩溃：any delivery (message) that was not acked is automatically requeued when the channel (or connection) on which the delivery happened is closed，并且 Redeliveries will have a special boolean property, redeliver, set to true。
  • 结果就是（Reliability Guide）：Use of acknowledgements guarantees at least once delivery. Without acknowledgements, message loss is possible ... and only at most once delivery is guaranteed.

下面这个实验室有队列、一个消费者、死信队列，和协议给你的每一个按钮。四个场景依次做，点之前先猜。队列里是三条「订单已支付」消息，消费者的业务是写库。

四个场景，四个结论
  1. 自动 ACK = 发出即删。消费者崩溃，消息永久丢失，broker 无从得知。这就是官方说 unsafe 的全部含义。日志、缓存失效通知可以用它；业务消息不行。
  2. 手动 ACK 下 broker 替你记着「谁还没确认」。channel 一断，Unacked 全部回队列，redelivered=true。丢失变成了重投。
  3. 重投的代价是重复。处理完、ACK 前崩溃，同一条会被处理两次——broker 无法区分「没处理」和「处理了没告诉我」，这正是「不知道」。所以消费者必须幂等：按消息 id 或业务键去重，第二次写库变成空操作。手动 ACK 只把「丢」换成了「重」，幂等才把「重」消掉。
  4. NACK 要选方向。requeue=true 回到队列头部，处理必然失败的消息会无限循环；requeue=false 进死信队列等人工。超时未 ACK（默认 30 分钟）broker 会关掉 channel 并重投——长任务要么拆小，要么调 consumer_timeout。

六、RabbitMQ 三问：队列大小 / 如何消费 / ACK 机制与 C# 实现

「RabbitMQ 一个队列的大小？」——这是道陷阱题，标准答案是「没有固定大小」：队列长度只受节点内存和磁盘约束，官方文档只说 You can set a maximum length on a queue（Queue Length Limit），默认不设。面试官想听的是你知道可以设、怎么设、满了怎么办：

参数含义原文
x-max-length最多多少条the x-max-length queue declaration argument with a non-negative integer value
x-max-length-bytes最多多少字节两者都设时 whichever limit is hit first will be enforced
x-overflow = drop-head（默认）满了丢队头（最老的）The default behaviour ... is to drop or dead-letter messages from the front of the queue
x-overflow = reject-publish满了拒绝新的，生产者拿到 nackthe most recently published messages will be discarded
x-overflow = reject-publish-dlx拒绝新的，且被拒的进死信reject-publish-dlx also dead-letters rejected messages

选哪个：业务消息用 reject-publish（宁可生产者报错也不能悄悄丢老消息），日志 / 指标用 drop-head（旧的不值钱）。再往上一层，内存到阈值时 broker 会触发 memory alarm 阻塞所有生产者——这就是「队列大小」在生产上真正的形态：不是队列满，是节点满。

「RabbitMQ 如何进行消费？」——两种 API，一个几乎不用：

  • 推（basic.consume）：注册一个长期消费者，broker 主动把消息推过来。正常都用这个。
  • 拉（basic.get）：每次去问一条。官方（Consumers）：Fetching messages one by one is highly discouraged as it is very inefficient compared to regular long-lived consumers。只在脚本 / 排障里用。
  • prefetch（basic.qos）：defines the max number of unacknowledged deliveries that are permitted on a channel。它是消费者的背压阀：不设 = broker 把整个队列灌给第一个上线的消费者；设 1 = 严格一条一条；设 10–50 = 吞吐和公平的常用折中。

「ACK 的机制和实现？」——机制在第五节已经亲手做过了，这里补协议细节和 C#。协议层四个动作：

方法含义细节
basic.ack处理成功，broker 删除multiple=true 时 acknowledge all outstanding delivery tags up to and including the tag specified——批量确认省往返
basic.nack处理失败requeue=true 回队头；false 进 DLX 或丢弃。支持 multiple
basic.reject同上，AMQP 原生不支持 multiple；basic.nack 是 RabbitMQ 扩展
delivery tag每次投递的编号scoped per channel，deliveries must be acknowledged on the same channel they were received on——换 channel ACK 会报错

C#（RabbitMQ.Client 7.x，全异步 API）：

await channel.QueueDeclareAsync("order.paid", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?> {
        ["x-max-length"] = 100_000,
        ["x-overflow"] = "reject-publish",
        ["x-dead-letter-exchange"] = "order.dlx"
    });

// 背压：手里最多 20 条未确认
await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 20, global: false);

var consumer = new AsyncEventingBasicConsumer(channel);
consumer.ReceivedAsync += async (_, ea) =>
{
    try
    {
        // 幂等在这里面：INSERT ... ON CONFLICT (message_id) DO NOTHING，或 tx_log 查重
        await handler.HandleAsync(ea.Body, ea.BasicProperties.MessageId, ea.Redelivered);
        await channel.BasicAckAsync(ea.DeliveryTag, multiple: false);          // 处理完才 ACK

    catch (TransientException)                                                // 库抖了一下
    {

    }
    catch (Exception)                                                         // 数据本身有问题，重试没用
    {
        await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);  // → DLX
    }
};
await channel.BasicConsumeAsync("order.paid", autoAck: false, consumer);   // 手动 ACK
扩展 · 生产者那一侧也有「不知道」：Publisher Confirms

ACK 是消费者对 broker 说「我做完了」；对称地，publisher confirm 是 broker 对生产者说「我收下了」。原文：For routable messages, the basic.ack is sent when a message has been accepted by all the queues. For persistent messages routed to durable queues, this means persisting to disk. 没开 confirm 就 BasicPublish，等于把消息扔进网络就走——和自动 ACK 是同一种不安全。所以 Lesson 04 的 outbox 后台任务在「标记已发」之前要等 confirm。两侧各一个确认，中间 durable 队列 + persistent 消息，这三样凑齐才叫可靠投递。而 requeue=true 那个无限循环的解法，是给消息加重试计数头（x-death 里有），超过 N 次改 requeue=false。

七、归类练习：这种情况该做什么

判据一条：你现在知道对方的结果吗？知道成功 → 推进；知道失败 → 标失败或补偿；不知道 → 先别动状态，去问。而「怎么问」取决于对方给了你什么工具。

八、话术

话术 A · 对应题「和第三方的交互怎么实现、怎么保证一致性」「我方成功对方失败 / 我方失败对方成功怎么办」

先把框架说破：跨系统调用有三种结果：成功、失败、不知道。前两种好办，一致性设计全是为第三种做的。所以我们的做法不是「成功-失败就回滚、失败-成功就撤销」，而是让设计不依赖于知道对方的结果。

再给机制：顺序上先在自己库里写一条中间态记录——PENDING，带业务 id 和时间——再调对方，拿到明确结果才推进到 CONFIRMED 或 FAILED。对方明确拒绝就标 FAILED，没有东西需要回滚，因为我写的不是终态；对方成功但我推进终态失败，或者对方超时，都停在 PENDING，走同一条恢复路径：后台任务扫超时的 PENDING，对方支持幂等键就带同一个 key 重试，不支持就调查询接口，最后每天对账兜底，差异进人工队列。

接真实经历：我做过的那次对接是对方提供回退接口的编排式 Saga，正向失败逆序撤销——那是「知道失败」的处理；「不知道」的处理靠的是补偿意图落库加后台重试，回退接口必须幂等。（这句把 Lesson 05 的经历接进来，用词是「知道 / 不知道」的框架。）

话术 B · 对应题「数据操作成功后怎么通知用户」

通知挂在状态转换上，不挂在请求线程上——因为用户点按钮那个请求返回时记录多半还是 PENDING，真正成功可能是后台查询任务或对账任务推进的。推进状态和写一条 outbox 通知放同一个事务，通知服务消费 outbox 去发。渠道上，用户还在页面就用 SignalR 推，但推送只做加速，页面重连后一定回源拉一次状态；用户已经离开就走站内信、邮件、短信。发短信又是一次跨系统调用，同样至少一次加幂等——同一条通知发两遍可以接受，发零遍不行。

话术 C · 对应题「RabbitMQ 队列大小」「如何消费」「ACK 机制和实现」

队列大小：没有固定大小，只受节点内存和磁盘限制。可以用 x-max-length 或 x-max-length-bytes 设上限，满了的行为由 x-overflow 决定：默认 drop-head 丢最老的，业务队列我会改成 reject-publish 让生产者报错，宁可失败也不悄悄丢。真正的生产问题通常不是队列满而是节点内存告警把所有生产者阻塞住。

如何消费：用 basic.consume 注册长期消费者让 broker 推，basic.get 轮询官方明确不推荐。配 prefetch 做背压，不然 broker 会把整个队列灌给第一个上线的消费者；一般设 10 到 50。

ACK 机制：自动 ACK 是发出即删，消费者崩溃消息就丢，官方说它 unsafe；业务消息一律手动 ACK，处理完写库成功再 ack，失败按原因分：瞬时故障 nack requeue 回队列，数据本身错的 nack 不 requeue 进死信队列人工处理。手动 ACK 下 channel 断开，broker 会把未确认的自动重投并打上 redelivered。代价是处理完、ACK 前崩溃的消息会被处理两次——broker 分不清「没处理」和「处理了没告诉我」——所以消费者必须幂等，按消息 id 去重。手动 ACK 把丢换成了重，幂等把重消掉。我自己项目里 RabbitMQ 用在日志和缓存失效通知，那两个场景丢一条不致命，所以当时用的自动 ACK 是合理取舍；业务消息就必须是上面这套。
