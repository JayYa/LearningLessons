编译器把你的方法拆成了一台状态机

上一课留了两个没答完的问题：await 之后为什么会换线程，.Result 为什么会死锁。两个答案是同一个——编译器把 async 方法拆成了一台状态机，await 那一行既不是等待、也不是新线程，而是一次登记加一次返回。这一课把这台机器打开看，然后你亲手把它的类名和字段打印出来。还是动手课，交付物是三样能一行报出来的东西。

一、先破一个错觉

面试里问「你对异步的理解」，最常见的错答是把异步等同于多线程：异步就是开一个线程去干活，主线程接着往下走。这句话对 Task.Run 成立，对 await httpClient.GetAsync(...) 完全不成立。

这一课唯一必须记死的一句

await 不创建线程——它把方法剩下的部分登记成一个回调，然后把线程还回去。

一次网络请求发出去之后，等待的那 200 毫秒里，你的进程里没有任何线程在为它工作。数据在网线上飞，网卡收完会给操作系统一个中断，操作系统通过 IO 完成端口通知运行时，运行时这才从线程池抓一个线程来跑「剩下的那半个方法」。Stephen Cleary 用一整篇文章讲这件事，标题就是结论：There Is No Thread。

Task.Run(...)await SomethingAsync()
干的是CPU 活（算东西）IO 活（网络 / 磁盘 / 数据库）
等待期间确实占着一个线程池线程一个线程都不占
目的把活挪走，别卡住 UI提高吞吐——同样的线程数接更多请求
用错的后果在服务端滥用 = 平白多一次线程切换—

这张表是话术 A 的骨架。服务端的 async 从来不是为了「更快」——单个请求用了 async 反而略慢（多了状态机的开销）。它换来的是：等 IO 的时候线程被还回去接别的请求，所以同样一台机器能扛更多并发。

二、编译器拆出了什么

和上一课的 lock 一样，async / await 不是运行时机制，是编译期改写。编译器把你的方法拆成一个状态机（Stephen Toub — How Async/Await Really Works in C#：The compiler has generated a struct named <CopyStreamToStreamAsync>d__0）。

public async Task WorkAsync()
{
    var s = "hello";
    await Task.Delay(1);
    Console.WriteLine(s.Length);
}

编译之后，这个方法体消失了。剩下的是三样东西：

生成物是什么为什么需要它
<WorkAsync>d__0一个 struct，实现 IAsyncStateMachine装下「跑到哪了」和所有跨越 await 的局部变量
MoveNext()你原来的方法体，被切成若干段的 switch每次被唤醒就从上次的段落接着跑
AsyncTaskMethodBuilder建造器负责造出并最终完成你返回的那个 Task

三个字段名你在第五节会亲手打印出来，它们把整个机制暴露得很彻底：

  • <>1__state —— 一个 int，就是「跑到第几段了」。-1 表示正在跑，0 表示停在第一个 await 上。
  • <s>5__1 —— 你那个局部变量 s。它从栈上搬到了状态机里，因为方法要返回、栈帧要销毁，而 await 之后还得用它。
  • <>u__1 —— 一个 TaskAwaiter。await 的对象不是 Task，是 Task 上的 awaiter。

await 那一行，逐字翻译

await x 展开成的伪代码只有四步——把这四步说出来，「你对异步的理解」这道题就答完了：

var awaiter = x.GetAwaiter();

if (awaiter.IsCompleted)          // ① 已经完成了？（缓存命中、同步返回）
{
    result = awaiter.GetResult(); // ② 那就一步不停，继续往下跑
}
else
{
    // ③ 把 state 存成「我停在这」，把 MoveNext 登记成完成时的回调，
    //    然后 return —— 线程立刻回到调用方，最终回到线程池
    awaiter.OnCompleted(MoveNext);
    return;
    // ④ IO 完成后，线程池里某个线程再次调用 MoveNext，从这里接着跑
}
上一课那两个问题，到这里全解了

为什么 await 之后会换线程？因为第 ③ 步 return 之后原线程就走了，第 ④ 步是另一个线程调进来的。Monitor 认线程，所以它跨不过这一行。

为什么 IsCompleted 那条快路径重要？因为 async 方法大多数情况下根本不会挂起（缓存命中、内存流、已完成的 Task），走的是第 ② 步，一次分配都没有。这也是 ValueTask 存在的理由。

扩展 · 为什么状态机是 struct

生成的是 struct 而不是 class，正是为了配合上面那条快路径：只要方法从头跑到尾没挂起过，状态机就一直待在栈上，零堆分配。只有真的要挂起时，运行时才把它搬到堆上（因为栈帧马上要没了）。

面试增量：状态机是 struct，同步完成的路径上不会有堆分配；只有真正挂起才会搬到堆上。所以高频小方法我会考虑返回 ValueTask，把最后那个 Task 的分配也省掉——但 ValueTask 只能 await 一次，不能存起来反复用。

场景：一个 ASP.NET 接口，里面要调一次外部 HTTP。每次点「下一步」之前先猜——③ ④ ⑤ 都是真实的生产事故形态。

四、上下文与 ConfigureAwait

写法 ③ 死在「续接要回到原上下文」这条承诺上。这条承诺由谁做的？——由 await 默认做的。

Stephen Toub 的 ConfigureAwait FAQ 描述了 await 挂起前的动作：it first checks whether there is a SynchronizationContext set, and if there is not, whether there is a non-default TaskScheduler in play. 捕到什么，续接就回到什么上面跑。

ConfigureAwait(false) 做的事只有一句：even if there is a current context or scheduler to call back to, it pretends as if there is not.——假装没有上下文，续接就地在线程池上跑。

环境有同步上下文吗.Result 的后果
经典 ASP.NET（Framework）有，且同时只放一个线程死锁
WinForms / WPF有，绑定 UI 线程死锁
ASP.NET Core没有（ASP.NET Core does not）不死锁，但线程池饥饿
控制台 / 后台服务没有不死锁，浪费线程
该不该写 ConfigureAwait(false)

官方指引就两句（ConfigureAwait FAQ）：

  • if you are writing general-purpose library code, use ConfigureAwait(false)——类库里写，因为你不知道调用方在什么环境里。
  • if you are writing app-level code, do not use ConfigureAwait(false)——应用代码里不写。

而且它不是死锁的解药。它只是让类库在被别人用错时不至于炸。真正的解药是 async 一路到底：Once you go async, all of your callers SHOULD be async.

五、动手：把状态机打印出来

为什么必须亲手跑

「编译器生成了一台状态机」这句话，读过的人很多，见过那个类名的人很少。三分钟之后你会拥有三样东西：await 前后两个不同的线程号、状态机的真实类名和字段清单、以及阻塞版比异步版慢几倍的具体数字。面试里说得出 <WorkAsync>d__0 这个名字，等级立刻不一样。

dotnet new console -o asyncdemo
cd asyncdemo

把 Program.cs 整个替换成：

using System.Diagnostics;
using System.Reflection;
using System.Runtime.CompilerServices;

// ① await 前后，还是同一个线程吗？
Console.WriteLine($"① await 之前 : 线程 {Environment.CurrentManagedThreadId}");
await Task.Delay(100);
Console.WriteLine($"① await 之后 : 线程 {Environment.CurrentManagedThreadId}");

// ② 编译器到底生成了什么？
var method = typeof(Demo).GetMethod(nameof(Demo.WorkAsync))!;
var sm = method.GetCustomAttribute<AsyncStateMachineAttribute>()!.StateMachineType;
Console.WriteLine($"\n② 状态机类型 : {sm.Name}");
foreach (var f in sm.GetFields(BindingFlags.Instance | BindingFlags.Public | BindingFlags.NonPublic))
    Console.WriteLine($"     字段 : {f.FieldType.Name,-28} {f.Name}");

// ③ 阻塞 vs 不阻塞
Console.WriteLine($"\n   SetMinThreads: {ThreadPool.SetMinThreads(4, 4)}");
const int N = 100;

var sw = Stopwatch.StartNew();
Task.WaitAll(Enumerable.Range(0, N).Select(_ => Task.Run(() => IoAsync().Wait())).ToArray());
Console.WriteLine($"③ 阻塞版(.Wait) : {sw.ElapsedMilliseconds,6} ms");

sw.Restart();
await Task.WhenAll(Enumerable.Range(0, N).Select(_ => IoAsync()));
Console.WriteLine($"③ 异步版(await) : {sw.ElapsedMilliseconds,6} ms");

static async Task IoAsync() => await Task.Delay(500);

class Demo
{
    public async Task WorkAsync()
    {
        var s = "hello";
        await Task.Delay(1);
        Console.WriteLine(s.Length);
    }
}

然后 dotnet run。先猜，再看：① 两个线程号会一样吗？③ 一百个各睡 500ms 的任务，两种写法各要多久？

要记录的三件事
  1. ① 的两个线程号分别是多少？（不一样 —— 这就是 lock 跨不过 await 的现场证据）
  2. ② 打印出的状态机类名，字段一共几个？对着第二节逐个认：哪个是 state、哪个是你的局部变量 s、哪个是 awaiter。
  3. ③ 阻塞版是异步版的几倍？——异步版应该贴着 500ms（一百个任务几乎同时在等，因为等待不占线程）；阻塞版取决于线程池往里塞线程的速度。这个倍数就是你说「sync-over-async 会拖垮吞吐」时的实测依据。

加做一分钟：看 async void 掀桌子

把上面 class Demo 之前的位置加进这段，再 dotnet run：

try { Boom(); }
catch (Exception) { Console.WriteLine("catch 抓到了"); }
await Task.Delay(1000);
Console.WriteLine("还活着吗？");

static async void Boom()
{
    await Task.Delay(10);
    throw new InvalidOperationException("爆了");
}

要记录的：那句「catch 抓到了」印出来了吗？「还活着吗？」印出来了吗？——两个都不会。亲眼看一次进程被掀掉，比读十遍「async void 危险」有用。看完记得删掉这段。

报回来一行就够：① 的两个线程号、② 的状态机类名、③ 的两个耗时。上一课你只报了「已完成」——那三个数字我还没拿到，方便的话一起补给我，尤其是裸 ++ 少掉的那个数。我不问你懂了没，只看数字。

六、归类练习：真异步还是假异步

判据只有一个：等待的那段时间里，有没有线程被占着。占着就是假异步。

七、话术

话术 A · 对应题「对异步的理解 async await task」

先破错觉（这一句就分出高下）：先说个容易混的：异步不等于多线程。await 一次数据库查询的时候，进程里其实没有任何线程在等它——线程被还给线程池去接别的请求了，IO 完成之后运行时再抓一个线程从断点继续。

再给机制：async/await 是编译期改写，编译器把方法拆成一台状态机：一个 int 记跑到第几段，跨越 await 的局部变量从栈搬进状态机字段，await 那一行展开成「拿 awaiter → 判断 IsCompleted → 没完成就把 MoveNext 登记成回调然后 return」。Task 是这套东西的句柄——代表一个「将来会有结果」的操作，结果和异常都存在它里面。

收在服务端价值上：所以服务端用 async 不是为了单个请求更快，单请求其实略慢；是为了把吞吐从线程数的限制里解放出来。全同步的服务，吞吐上限就是线程数除以单请求耗时，跟 CPU 多快没关系。

话术 B · 对应追问「为什么不能用 .Result / async void」

分两种环境讲，别只讲死锁：.Result 有两种翻法。在经典 ASP.NET 或 WPF 里会直接死锁：await 默认捕获同步上下文、承诺续接回到那里跑，而那个上下文只允许一个线程，位置正被 .Result 阻塞占着——续接等上下文，上下文等续接。

在 ASP.NET Core 里没有同步上下文，不死锁，但更难查：一个请求会吃掉两个线程，一个躺着阻塞、一个跑续接。压力上来就是线程池饥饿，症状是全站接口都慢、CPU 却很低，而且慢的不一定是出问题那个接口。

async void 单独点一句：async void 更要避开：它没有 Task 可以承载异常，出错会直接变成未处理异常掀掉进程，调用方的 try/catch 根本抓不到。除了 UI 事件处理器没得选，其它一律 async Task。

给原则：规则很短——async 一路到底，中间不要有 .Result / .Wait()。类库里加 ConfigureAwait(false)，但那是防御，不是解药。

话术 C · 对应「你排查过什么性能问题」

症状画像最值钱，先给它：有一类问题的画像很好认：接口整体变慢、CPU 却很低、线程数缓慢上涨。CPU 低说明不是算力瓶颈，那大概率是线程池饥饿——某处在异步链路里用了 .Result 或 .Wait()，把线程池线程阻塞住了。

给定位手段：定位我会看线程池的排队情况和线程数走势，配合 dump 看有多少线程卡在等待上。修法是把那条链路一路改成 async，而不是把线程池的最小线程数调大——调大只是把问题推后。

为什么这样答强：它给的是一个可复用的诊断规则（CPU 低 + 全站慢 = 先查线程池），而不是一次孤立的经历。和上一课的话术 C 同形：症状 → 判据 → 修法 → 沉淀原则。
