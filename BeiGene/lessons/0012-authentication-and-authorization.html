一、先破一个错觉

很多人把「身份验证」和「权限验证」说成一句话：「就是登录之后看他有没有权限」。面试官第一问就是拆这句话：「那 401 和 403 分别是谁返回的？」答不出来，说明脑子里只有一个笼统的「安全检查」。

官方定义只有两句（ASP.NET Core — Authentication overview）：Authentication is the process of determining a user's identity. Authorization is the process of determining whether a user has access to a resource. 前者回答「你是谁」，后者回答「你能不能」。两者之间隔着一个具体的东西——

这一课唯一必须记死的一句

认证的产出只有一样：HttpContext.User——一张 ClaimsPrincipal。之后所有授权——[Authorize]、Policy、行级检查——都只是对这张 claims 表提问，不再碰凭据。

原文就是这么说的：Authentication is responsible for providing the ClaimsPrincipal for authorization to make permission decisions against. 把这句话摊开成流水线：

位置谁做什么失败时
1UseAuthentication 中间件按注册的 scheme（Cookie / JwtBearer / …）调对应 handler，把凭据变成 ClaimsPrincipal，塞进 HttpContext.User不拦。User 是匿名的，继续往里走
2UseAuthorization 中间件看终结点上的 [Authorize] / Policy，对 User 提问User 匿名 → Challenge → 401；User 有身份但不满足 → Forbid → 403
3你的服务层 / IAuthorizationService拿到业务数据后再问：这个人能碰这一条吗403（或按业务返回 404，不暴露存在性）

两个常被答错的细节，都是这张表的推论：

  • 认证中间件不拒绝请求。token 错了它只是不给 User 填身份；拒绝是授权层看到 [Authorize] 之后才做的。所以 [AllowAnonymous] 的接口带一个坏 token 照样能进。
  • 401 和 403 都由认证 handler 执行，但由授权层触发。原文：Challenge 是 invoked by Authorization when an unauthenticated user requests an endpoint that requires authentication；Forbid 是 called by Authorization when an authenticated user attempts to access a resource they're not permitted to access。JwtBearer 的 Challenge = returning a 401 result with a www-authenticate: bearer header，Forbid = returning a 403 result。

顺序为什么是 UseAuthentication 在 UseAuthorization 前面——Lesson 10 的套娃：外层先跑前置代码。授权要读 User，所以填 User 的那层必须在外面。

二、三种凭据，一个出口

题「身份验证方式有哪些」是清单题，但清单要按「状态存在哪」排，才答得出后面「token 怎么失效」：

方式客户端拿着什么服务器存什么Handler 怎么变出 ClaimsPrincipal典型场景
Session Cookie一个 session id（或加密的 ticket）会话表 / 或什么都不存（ticket 自包含、已加密）Cookie handler 解密 ticket → claims。原文：constructing the user's identity from cookies同域的服务端渲染站点
JWT Bearer一串 header.payload.signature，放 Authorization: Bearer只存密钥（对称 HS256）或公钥（RS256）验签 → 检查 exp/iss/aud → payload 里的 claims 直接成为 User。原文：deserializing and validating a JWT bearer token前后端分离、移动端、微服务间
外部身份提供方（OIDC / OAuth 2.0）跳转去 OP 登录，回来带 code，换 id_token只存 OP 的元数据 / 公钥RemoteAuthenticationHandler：requires a remote authentication step ... calls back to the CallbackPath企业 SSO（Azure AD）、社交登录

三种方式的 handler 不一样，出口一样：都是往 HttpContext.User 里放一张 ClaimsPrincipal。你的 Controller、你的 Policy、你的行级检查，完全不知道也不关心用户是靠 cookie 还是 JWT 进来的。这就是 scheme 这个抽象存在的意义：An authentication scheme is a name that corresponds to: an authentication handler; options for configuring that specific instance of the handler.

JWT 要多说三句，因为第三节要动手拆它（RFC 7519）：

  1. 它是 a compact, URL-safe means of representing claims to be transferred between two parties，三段用点分隔，每段都只是 base64url——不是加密，任何人都能解码看 payload。
  2. 安全性全在第三段：签名 = 算法(header + payload, 密钥)。改 payload 一个字，签名就对不上；没有密钥，算不出新签名。
  3. 几个注册 claim 的原文定义，面试会问：sub（the principal that is the subject of the JWT）、exp（the expiration time on or after which the JWT MUST NOT be accepted）、jti（a unique identifier for the JWT ... to prevent the JWT from being replayed）、iss / aud（谁签的 / 签给谁的）。

三、亲手签发、篡改、过期、撤销

下面是一个缩小版的 JWT 世界：左边客户端只有一串 token，右边服务器有密钥、时钟、黑名单和一组可开关的检查。四个场景依次做，每次点「③ 发请求」之前先猜状态码。

四个场景，四个结论
  1. payload 是明文，签名才是防线。改 role 立刻死在「签名 ✗」——服务器用自己的密钥重算，对不上。JWT 防篡改、不防偷看，敏感信息别放进去。
  2. 安全性 = 密钥的安全性。猜错密钥照样签名 ✗；猜中了就是 200——所以对称密钥（HS256）只能在你自己的服务之间用，给第三方验签要用非对称（RS256，只发公钥）。
  3. 撤销之后服务器什么都不查，token 照样 200。这不是 bug，是 JWT 的定义：服务器不存状态，验签 + exp 通过就认。「让客户端 token 失效」这道题的全部难度就在这一格。
  4. 要撤销就得存一点状态：要么按 jti 记黑名单（只记到 exp，所以可以自动清），要么按用户记一个版本号。两种都把「无状态」打了个洞——下一节算这笔账。

四、让客户端 token 失效：四条路，各付什么代价

先把面试官想听的那句说出来：「JWT 天生撤不掉，因为服务器不存它；能撤的都是在某处补了状态。」然后给四条路，从最省到最重：

#做法服务器多存什么失效延迟什么时候够用
1短 exp + refresh token：access token 5–15 分钟，refresh token 长期、存库、可撤销、用一次换一个（rotation）refresh token 表（一行一个）最多一个 access token 的寿命默认选这个。绝大多数「注销」「改密码」容忍 10 分钟延迟
2jti 黑名单：注销时把 jti 写进 Redis，TTL = 该 token 剩余寿命；验签后多查一次只存被撤销的，且会自动过期立即要求「点了退出立刻失效」；每个请求多一次 Redis 读
3用户级版本号 / security stamp：token 里带 ver，改密码、封号、改角色时 +1；验签后比对每用户一个整数（可放缓存）立即，且一次踢掉该用户所有设备封号、权限变更这类「必须全体失效」的场景
4不用自包含 token：发一个随机引用（opaque token），服务器查表还原身份——本质回到 session整张会话表立即对撤销要求极高、又不想维护上面三套的内网系统
一句可以直接说的判断

「撤销的实时性和服务器的无状态是一对矛盾，我按业务容忍度选：一般注销用短 exp + refresh token 轮换；封号和改权限用用户版本号一次踢全体；真要秒级失效才上黑名单，而且黑名单只记到 exp、能自动清。」——这段把第三节四个场景按顺序串起来，面试官听得出你是做过取舍的。

扩展 · 三个细节，追问时用
  • ASP.NET Core Identity 内置的就是路 3。Cookie 方案里 SecurityStampValidator 每隔 ValidationInterval（默认 30 分钟）拿 cookie 里的 stamp 和库里的比一次，改密码 / 注销全部设备会 UpdateSecurityStampAsync。把同样的字段塞进 JWT 就是本课的 ver。
  • 黑名单的 key 用 jti，不要用整个 token 的哈希。OWASP 的 JWT 速查表专门警告：Using the raw JWT or a secure hash of the JWT (SHA-256(token)) as the denylist key is not safe——因为同一 payload 可以被重新编码成字节不同、语义相同的串（malleability）。
  • refresh token rotation 要检测重放。旧 refresh token 被再次使用 = 有人偷了它，此时把这一族全部作废。这是 OAuth 2.0 Security BCP 的要求，也是路 1 和「只是把 exp 调长」的本质区别。

五、授权三层 + 数据层兜底：「一个人不该操作某条数据」

题「如果一个人不应该有权限操作某一条数据，我们如何避免」，出题人想听的是你知道[Authorize] 做不到这件事。原文（Resource-based authorization）：Attribute evaluation occurs before data binding and before execution of any method that loads a resource. Declarative authorization with an [Authorize] attribute doesn't suffice for resource-based authorization.——特性在数据还没加载时就跑完了，它根本不知道你要碰的是哪一条。

所以是三层加一道兜底，每层能看到的信息不同（这张表是 Lesson 10 第五节那张的展开）：

层能看到什么回答哪类问题写法
中间件只有 HttpContext：token、路径、头「你是谁」——把凭据变成 UserUseAuthentication()，一次注册，零业务代码
特性 / Policy（接口级）User 的 claims + 打到哪个 action「这类人能不能调这个接口」：角色、claim、组合规则[Authorize(Roles = "reviewer")]、[Authorize(Policy = "CanReview")]；Policy 里可以是 RequireClaim、也可以是自定义 IAuthorizationRequirement + handler
资源级（行级）User + 已加载的那条数据「这个人能不能碰这一条」：owner 是不是他、工单是不是他抢到的IAuthorizationService.AuthorizeAsync(User, ticket, Operations.Update)，handler 继承 AuthorizationHandler<TRequirement, TResource>
数据层兜底SQL 里的 WHERE就算上面漏了，也改不到别人的行UPDATE ... WHERE id = @id AND claimed_by = @me，受影响行数 0 = 拒绝

资源级那一行写出来（原文示例改成工单）：

// 需求（requirement）：一个空标记类；操作用内置的 OperationAuthorizationRequirement
public static class TicketOps
{
    public static readonly OperationAuthorizationRequirement Review = new { Name = "Review" };
}

// handler：同时拿到 User 和那条数据
public class TicketAuthorizationHandler
    : AuthorizationHandler<OperationAuthorizationRequirement, Ticket>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext ctx, OperationAuthorizationRequirement req, Ticket ticket)
    {
        var me = ctx.User.FindFirstValue(ClaimTypes.NameIdentifier);
        if (req.Name == "Review" && ticket.ClaimedBy == me)   // 只有抢到它的人能复核
            ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
// Program.cs：builder.Services.AddSingleton<IAuthorizationHandler, TicketAuthorizationHandler>();

// 服务层：先加载，再问
var ticket = await repo.FindAsync(id);
var ok = await authz.AuthorizeAsync(User, ticket, TicketOps.Review);
if (!ok.Succeeded) return Forbid();                    // 403；不想暴露存在性就 NotFound()
回到第七课：你已经写过数据层兜底了

Lesson 07 的复核提交语句是 UPDATE ticket SET status = 'reviewed' WHERE id = @id AND claimed_by = @me AND status = 'reviewing'。那时它是并发断言（Lesson 11 说的「前置状态断言」）；现在看它同时也是权限断言——claimed_by = @me 保证别人就算绕过了上面三层，SQL 也影响 0 行。同一条 WHERE，两个身份。面试里把这两课接起来说，比单说任何一层都强。

六、少调服务、少写代码：缓存放哪、AOP 放哪

题「每一步都要验证权限，如何避免不停地调用服务获得权限信息，以及如何减少代码量——涉及到 AOP、自定义中间件、缓存」。出题人给了三个词，你要做的是把它们放到各自的层，并说清缓存的寿命：

要省的是什么放哪寿命失效怎么办
「他有哪些权限」这次查询① 先看能不能直接编进 token（角色、少量权限 claim）——零查询= token 寿命就是第四节的问题：权限变了要等 exp 或版本号踢人
同一个请求里反复查② Scoped 的 ICurrentUser：中间件 / 第一次访问时查一次，请求内所有人从它读一个请求（Lesson 10 的 Scoped）请求结束自动没了，不用管
跨请求反复查③ IMemoryCache / Redis，key = userId，短 TTL（1–5 分钟）TTL权限变更时主动删 key；分布式就发一条「权限变更」消息让各实例删
每个接口都写一遍 if④ 特性 + Policy 覆盖接口级；行级用 AOP 拦截器统一读方法参数里的资源 id 做检查——

AOP 那一格要说得准：ASP.NET Core 自己没有通用 AOP，行级权限的「统一做」有两个落点——Action Filter（能拿到 action 参数，比如路由里的 ticketId，在进 action 之前先加载并 AuthorizeAsync）或者 DI 层拦截器（Castle DynamicProxy / 源生成，在服务方法上打 [RequireOwner("ticketId")]）。两者都是「把那段 if 从每个方法里抽出来，挂在元数据上」。Filter 够用就别上代理——它是框架内置的，调试栈干净。

扩展 · 缓存一致性的反面例子

「把权限缓存 30 分钟」听起来省事，但和第四节撤销是同一个矛盾：管理员刚把某人踢出复核组，他还能复核半小时。所以缓存 TTL 要和撤销策略一起定：要么短 TTL 接受延迟，要么权限变更时同步删缓存 + 升版本号。面试里主动说出这个矛盾，比说「加缓存」本身值钱。

七、SSO 与两步登录：都是「中间态凭据」

SSO。题「对 SSO 的理解」，机制一句话：认证这件事外包给一个身份提供方（OP），每个应用不再自己看密码，只看 OP 签发的 id_token。标准是 OpenID Connect：an interoperable authentication protocol based on the OAuth 2.0 framework；id_token represents the outcome of an authentication process. It contains at a bare minimum an identifier for the user (called the sub aka subject claim) and information about how and when the user authenticated（OpenID — How Connect Works）。「单点」从哪来：浏览器在 OP 的域上有一个会话 cookie；第二个应用把用户重定向到 OP 时，OP 看到 cookie 直接签发，用户没有再输密码。ASP.NET Core 里就是 AddOpenIdConnect(...)，handler 类型是第二节说的 RemoteAuthenticationHandler；企业场景多半对着 Azure AD / Entra ID。

两步登录。题「第一次用户名、密码登录完之后，再进行手机验证码验证，如何做」。错误答案是「密码对了就发正式 token，然后验证码再查一次」——那验证码就是摆设，拿到 token 的人可以直接调业务接口。正确的机制是：密码正确只换来一张「半张票」，它唯一能做的事是提交验证码。

  1. POST /login：校验密码。不签发正式 token。生成 6 位验证码，写 Redis：key = mfa:{userId}，value = 验证码，TTL 5 分钟，另记尝试次数；发短信。
  2. 返回一张中间态凭据：一个短命 JWT（exp 5 分钟），claims 里只有 sub 和 scope: "mfa_pending"（或 amr: ["pwd"]）。所有业务接口的 Policy 都要求 amr 包含 "mfa"，所以这张票调什么都是 403。
  3. POST /login/verify-sms：[Authorize(Policy = "MfaPending")]——只有半张票能进。比对验证码（比对完立刻删 key，一次性；错 5 次锁）。通过后签正式 token，amr: ["pwd","mfa"]，走第四节的 access + refresh。

ASP.NET Core Identity 内置的 2FA 就是这个结构，只是用 cookie 装那半张票：PasswordSignInAsync 返回 RequiresTwoFactor，同时写一个 IdentityConstants.TwoFactorUserIdScheme 的 cookie——官方描述是 the scheme used to identify Two Factor authentication cookies for round tripping user identities（IdentityConstants）；然后 TwoFactorSignInAsync 校验码、换正式 cookie。

把 SSO 和两步登录接到你已经会的东西上

两者的共同点是中间态：OIDC 里的 code（还不是 token）、2FA 里的半张票（还不是正式身份）。这和 Lesson 05 的「语义锁 / 业务中间态」是同一个思路——多步流程里，每一步只发放刚好够走下一步的凭据，不提前给终态。面试里能把这三处说成一件事，是很强的信号。

八、归类练习：这个检查放哪一层

判据就一条：做这个判断需要什么信息？只要 token → 中间件；要 User 和接口 → 特性 / Policy；要那条数据 → 资源级；要「就算前面全漏也不能错」→ 数据层 WHERE。

九、话术

话术 A · 对应题「身份验证和权限验证」「项目中权限怎么实现」

先给机制：认证回答你是谁，授权回答你能不能，中间隔着一张 ClaimsPrincipal。ASP.NET Core 里 UseAuthentication 按 scheme 调 handler——cookie、JWT、OIDC 各一个——把凭据变成 HttpContext.User；它不拒绝请求，只填身份。UseAuthorization 才对 User 提问：匿名就 Challenge 返回 401，有身份但不满足就 Forbid 返回 403。

再给分层：我们项目权限分三层加一道兜底。接口级用 [Authorize] 和 Policy 声明，零代码；行级——比如只有抢到工单的人能复核——特性做不到，因为它跑在数据加载之前，所以用 IAuthorizationService.AuthorizeAsync 传 User 和那条工单进去；最后 SQL 里 WHERE claimed_by = 当前用户兜底，影响 0 行就拒绝。

话术 B · 对应题「每一步都要验权限，如何少调服务、少写代码」

先把「他有哪些权限」尽量编进 token 的 claims，验签即得，零查询。编不进去的，请求内查一次放 Scoped 的 ICurrentUser，同一请求里 Filter、服务层都从它读；跨请求再加 IMemoryCache 或 Redis，按用户 id、短 TTL。代码量靠元数据：接口级全部 [Authorize] 特性，行级用 Action Filter 或拦截器统一按参数里的资源 id 加载再判，业务方法里不写 if。

主动补一句矛盾：缓存和撤销是一对矛盾——权限缓存 30 分钟，被踢出复核组的人还能复核半小时。所以我们权限变更时同步删缓存并升用户的 token 版本号，TTL 只是兜底。

话术 C · 对应题「让客户端 token 失效」「身份验证方式有哪些 / SSO」

先把矛盾说破：JWT 天生撤不掉，因为服务器不存它，验签加 exp 通过就认。能撤的都是在某处补了状态。我按业务容忍度选：一般注销用短 exp 加 refresh token 轮换，access 十分钟以内，refresh 存库可撤、用一次换一个、旧的再被用就整族作废；封号和改权限用用户级版本号，token 带 ver，比对不上就拒，一次踢掉所有设备；真要秒级失效才上 jti 黑名单，Redis 里 TTL 等于剩余寿命，能自动清。

方式与 SSO：身份验证方式按状态存哪分三类：session cookie 状态在服务器、JWT 状态在 token 自己、OIDC 把认证外包给身份提供方。SSO 就是第三类：各应用只看 OP 签的 id_token，浏览器在 OP 域上有一个会话，第二个应用跳过去时 OP 直接签发，不用再输密码。企业里对着 Azure AD 用 AddOpenIdConnect 就行。

话术 D · 对应题「密码登录后再手机验证码，怎么做」

关键是密码通过后不能发正式 token，只发一张半张票：一个五分钟的短命 JWT，claims 里只有 sub 和 amr 等于 pwd。所有业务接口的 Policy 都要求 amr 里有 mfa，所以这张票调什么都是 403，唯一能进的是提交验证码的接口。验证码放 Redis，五分钟 TTL，比对一次就删，错五次锁；通过后再签正式 token，amr 变成 pwd 加 mfa，走正常的 access 加 refresh。ASP.NET Core Identity 内置的 2FA 就是这个结构，只是半张票装在 TwoFactorUserId 那个 cookie 里。

收尾一句：这和 OIDC 的 code、和我们做 Saga 时的业务中间态是一个思路——多步流程里每一步只发刚好够走下一步的凭据。
