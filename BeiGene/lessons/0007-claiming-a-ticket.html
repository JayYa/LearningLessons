抢单
把「先查一下、再改」压成一句话

题库那道场景题有四问，但它们其实是同一个问题的四个切面：多个复核员同时点「抢单」，怎么保证一张工单只被一个人拿走。这一课的核心只有一行 SQL——而它之所以正确，靠的是你可能从没注意过的一条 PostgreSQL 规则。这是一节动手课：你要真的把表建出来，开两个窗口把冲突跑出来。

怎么用这一课

约 40 分钟，其中 15 分钟在敲命令。第三节的赛跑模拟请按顺序一个个点，每点「下一步」之前先在心里猜下一行会发生什么——五种写法里有两种是错的，但错法不一样。第五节是动手环节，做完把输出贴回来给我，这一课就算收了。

一、先反问，别急着画表

场景设计题最容易丢分的地方，是听完题目直接开始画表。面试官给的四行描述里，至少有五个没说的参数会彻底改变设计。Lesson 02 的「先问边界」框架在这里可以原样复用：

要反问的为什么它会改变设计
抢单的并发量级：十个人抢，还是一千个人抢？十个人：一句条件更新就够。上千：要考虑预分配或分片，否则所有人打同一批热点行
抢到之后能不能放弃？能放弃 → 必须有「释放」和「超时自动回收」，认领就不是终态而是中间态
一个人能同时持有几单？限一单 → 约束加在「人」这一侧；不限 → 只约束「单」这一侧
绩效按「抢到」算还是按「完成」算？这一问最关键。按完成算，抢到只是占坑，放弃不计分；按抢到算，会诱发恶意刷单，要加风控
审核被打回后回到哪一步？决定状态机是单向链还是带环，直接影响状态字段的取值集合
这一节的面试价值

先反问 30 秒再作答，本身就是一个信号：你把它当工程问题，不是当八股题。而且反问会给你争取到思考时间。真实面试里，问两到三个就够，别把它变成盘问——问完就自己给出假设：我先按「十几个复核员、可以放弃、绩效按完成算」这个假设往下设计。

二、三段流程的表怎么设计

A 提交 → B 审核 → C 复核，本质是一张工单在一条状态链上前进。新手容易设计成三张表（提交表、审核表、复核表），那是按技术流程切的老毛病：一次查询要连三次表，还没法回答「这张单现在在谁手上」。

正确的骨架是一张主表存当前状态 + 一张流水表存所有流转：

-- 主表：一张工单一行，永远只有一个当前状态
CREATE TABLE ticket (
  id            bigserial    PRIMARY KEY,
  biz_no        text         NOT NULL UNIQUE,   -- 业务单号，对外用，也是幂等键
  payload       jsonb        NOT NULL,          -- 业务数据本体（属性不固定，见 Lesson 01 的 JSONB）
  status        text         NOT NULL,          -- 状态机的当前节点
  submitted_by  bigint       NOT NULL,          -- 用户 A
  approved_by   bigint,                         -- 用户 B
  claimed_by    bigint,                         -- 用户 C：谁抢到了
  claimed_at    timestamptz,
  claim_expires_at timestamptz,                 -- 抢到不干活，到点回收
  reviewed_by   bigint,
  version       int          NOT NULL DEFAULT 0,
  created_at    timestamptz  NOT NULL DEFAULT now(),
  updated_at    timestamptz  NOT NULL DEFAULT now()
);

-- 流水表：每一次状态流转追加一行，只增不改
CREATE TABLE ticket_transition (
  id          bigserial   PRIMARY KEY,
  ticket_id   bigint      NOT NULL REFERENCES ticket(id),
  from_status text,
  to_status   text        NOT NULL,
  actor_id    bigint      NOT NULL,
  action      text        NOT NULL,             -- submit/approve/reject/claim/release/finish
  comment     text,
  created_at  timestamptz NOT NULL DEFAULT now()
);

状态链：

draft ──submit──▸ submitted ──approve──▸ approved ──claim──▸ reviewing ──finish──▸ done
                      ▲                      │                   │
                      └───────reject─────────┘                   └──release/超时──▸ approved
扩展 · 为什么必须有流水表

主表只回答「现在在哪」，流水表回答「怎么走到这的」。题库第四问「如何确定哪个任务被某个用户抢掉了」，靠主表的 claimed_by 只能查到当下的持有人；一旦这单被释放又被别人抢走，那段历史就永久丢失了——而绩效核算、申诉、审计恰恰要的就是那段历史。

这个「当前态放主表、历史放追加表」的模式，和 Lesson 05 的 tx_log(biz_id, state) 是同一个东西。面试里能指出这两处是同一模式，比分别答对两题更有分量。

另外注意 reviewing 这个状态：它就是 Lesson 05 讲的语义锁（semantic lock）——用一个业务上的中间态，把「这行正在被人处理」表达出来，而不是去持有一把数据库的锁。抢单的整个方案，本质上就是语义锁的一次具体实现。

三、抢单的本质与五种写法

把问题剥到最小：多个复核员同时执行「如果这单还没人认领，就把它记到我名下」。它是一个检查—然后—行动（check-then-act），而所有并发 bug 都长在检查和行动之间的那道缝里。

这一课唯一必须记死的一句

不要「先查再改」，要让那一次改自己带着条件。把状态判断从应用代码搬进 UPDATE 的 WHERE 里，检查和行动就发生在同一条语句、同一把行锁之下，缝隙消失。成败看返回的受影响行数：1 就是抢到，0 就是被别人抢了。

下面五种写法请一个个点。每次点「下一步」之前先猜一下这一行会发生什么——猜错的地方才是你真正的知识缺口。

扩展 · 乐观锁（version 字段）算第六种吗

算，但在这道题里它不如写法 ③。乐观锁是 UPDATE ... WHERE id = @id AND version = @v，同样靠受影响行数判断成败——机制和条件更新完全一样，区别只在断言的是版本号还是业务状态。

断言业务状态更好，因为它表达的是意图：「我要抢的是一张还没人认领的单」。断言版本号只能表达「这行没被人动过」——如果别人改的是一个跟认领无关的字段（比如补了条备注），乐观锁会误判失败，让一次本该成功的抢单白白重试。

话术：乐观锁和条件更新是同一个机制，都是靠 UPDATE 的受影响行数做并发控制。我倾向于断言业务状态而不是版本号，因为版本号会把无关的并发修改也算成冲突。version 字段我仍然会留着，用在编辑表单那种「防覆盖」的场景。

四、哪个任务被谁抢掉了

题库第四问。答案分三层，层层递进地说，比一句「查 claimed_by 字段」有分量得多：

层做法回答了什么
当下主表的 claimed_by / claimed_at这单现在在谁手上
历史ticket_transition 里 action = claim 的所有行它被谁抢过、抢过几次、中间被谁放弃过——绩效与申诉的依据
约束部分唯一索引让「同一时刻只能有一个有效认领」成为数据库层面的铁律

第三层直接复用 Lesson 01 的部分唯一索引。如果把认领单独建表（认领可以被释放、可以重复发生，适合独立成表）：

CREATE TABLE ticket_claim (
  id          bigserial   PRIMARY KEY,
  ticket_id   bigint      NOT NULL REFERENCES ticket(id),
  user_id     bigint      NOT NULL,
  claimed_at  timestamptz NOT NULL DEFAULT now(),
  released_at timestamptz,                      -- NULL = 认领仍然有效
  outcome     text                              -- finished / released / expired
);

-- 一张工单，同一时刻最多只能有一条「未释放」的认领
CREATE UNIQUE INDEX uq_claim_active
    ON ticket_claim (ticket_id)
 WHERE released_at IS NULL;
为什么要既有条件更新、又有唯一索引

这两者不是二选一，是两道防线。条件更新是正常路径的并发控制，它把成败干净地表达成受影响行数；唯一索引是兜底，防的是代码里某处漏写了 WHERE status = ...，或者哪天有人写了个补数据的脚本直接改表。

原则：能表达成数据库约束的业务规则，就别只放在应用代码里。应用代码有很多条路径，数据库约束只有一道门。面试里说出这一句，是很典型的资深信号。

抢到不干活怎么办

这是面试官最常追问的一刀，因为它暴露的是你有没有想过失败路径。张三抢到单子就去开会了、或者他的浏览器崩了——这单永远卡在 reviewing，谁也拿不到。

-- 定时任务，每分钟跑一次：把过期的认领放回池子
UPDATE ticket
   SET status = 'approved',
       claimed_by = NULL, claimed_at = NULL, claim_expires_at = NULL
 WHERE status = 'reviewing'
   AND claim_expires_at < now()
RETURNING id;

这就是 claim_expires_at 字段存在的理由——认领是一份租约（lease），不是一份地契，到期不续就收回。前端在页面上开个心跳续期即可。

扩展 · 这和 Lesson 04 是同一个洞

Lesson 04 讲过：动作执行了但确认丢了，调用方分不清。抢单这里是同一个形状——数据库里认领成功了，但响应没回到张三的浏览器。张三看到的是「抢单失败」，于是他去抢下一单；而 1001 号在数据库里已经挂在他名下，被锁死半小时。

租约机制正是这个洞的解药：无论哪一端出问题，超时都会把状态推回正常。面试里能把这两处点破为同一类问题，非常加分。

五、动手：把冲突真的跑出来

为什么必须亲手跑

写法 ① 的 bug 你现在「知道」了，但那是流畅性——看着解释觉得显然。亲手让两个窗口打起来、亲眼看到两条 UPDATE 都返回 UPDATE 1，才会变成你三个月后还记得的东西。而且这段经历本身就是面试素材：说「我实际验证过」和说「书上说」，可信度完全不同。

开两个终端窗口，各自连上同一个库（下称窗口 A / 窗口 B）。

第 1 步 · 建表塞数据（任一窗口）

CREATE TABLE ticket (
  id bigint PRIMARY KEY,
  status text NOT NULL,
  claimed_by text,
  claimed_at timestamptz
);
INSERT INTO ticket VALUES (1001, 'approved', NULL, NULL);

第 2 步 · 重现丢失更新。严格按 A B A B 的顺序交替执行：

-- 窗口 A
BEGIN;
SELECT claimed_by FROM ticket WHERE id = 1001;   -- 读到 NULL

-- 窗口 B
BEGIN;
SELECT claimed_by FROM ticket WHERE id = 1001;   -- 也读到 NULL

-- 窗口 A
UPDATE ticket SET claimed_by = 'A', status = 'reviewing' WHERE id = 1001;
COMMIT;

-- 窗口 B
UPDATE ticket SET claimed_by = 'B' WHERE id = 1001;
COMMIT;

-- 任一窗口
SELECT * FROM ticket WHERE id = 1001;

要记录的：两条 UPDATE 各自返回了什么？最后 claimed_by 是谁？

第 3 步 · 复位，改用条件更新。先 UPDATE ticket SET status='approved', claimed_by=NULL WHERE id=1001;，然后：

-- 窗口 A（先不要 COMMIT）
BEGIN;
UPDATE ticket SET claimed_by = 'A', status = 'reviewing'
 WHERE id = 1001 AND status = 'approved' AND claimed_by IS NULL;

-- 窗口 B（这一句会卡住，这正是预期行为）
BEGIN;
UPDATE ticket SET claimed_by = 'B', status = 'reviewing'
 WHERE id = 1001 AND status = 'approved' AND claimed_by IS NULL;

-- 回到窗口 A
COMMIT;

-- 观察窗口 B：它会立刻解除阻塞。看它打印了什么，然后
COMMIT;

要记录的（本课的关键观察）：窗口 B 解除阻塞后打印的是 UPDATE 1 还是 UPDATE 0？这一个数字就是整节课的证据。

第 4 步 · 看一眼锁。在第 3 步「窗口 B 卡住」的那一刻，开第三个窗口跑：

SELECT pid, state, wait_event_type, wait_event, left(query, 60) AS query
  FROM pg_stat_activity WHERE state != 'idle';

要记录的：阻塞那一行的 wait_event_type 是什么？（这是排查线上「接口突然全卡住」的标准手法，本身就是一段可以讲的经验。）

第 5 步 · 试试 SKIP LOCKED。再插几行 INSERT INTO ticket VALUES (1002,'approved',NULL,NULL),(1003,'approved',NULL,NULL);，然后两个窗口都跑（A 先跑但不提交）：

BEGIN;
SELECT id FROM ticket
 WHERE status = 'approved' AND claimed_by IS NULL
 ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;

要记录的：A 拿到哪个 id？B 拿到哪个？B 卡住了吗？把 SKIP LOCKED 去掉再试一次，对比。

第 6 步 · 收尾：DROP TABLE ticket;

交作业

把第 2、3、5 步的输出贴回来给我（尤其是第 3 步窗口 B 那个数字）。我会据此判断哪一块需要回炉——这一课我不问你「懂了没」，只看输出。

手边没有 PostgreSQL？装一个只要一条命令：docker run --rm -e POSTGRES_PASSWORD=x -p 5432:5432 postgres:16，然后 docker exec -it <容器名> psql -U postgres 开两次即可。

六、权限那一问

题库第二问「每个用户的权限如何控制」。这一问要答出两个维度——只答第一个是及格，两个都答出来才是加分：

维度控制什么怎么实现
功能权限
能做什么动作		A 只能提交、B 只能审核、C 只能复核RBAC：用户 → 角色 → 权限点。接口上用特性标注 [Authorize(Policy = "ticket.approve")]
数据权限
能看到哪些行		B 只能审核自己部门的单；C 只能看到已审核通过的单查询时强制注入过滤条件，由服务端从登录态推导，绝不接受前端传部门 id

再叠一层状态机权限，这是这道题特有的：动作是否允许，不只看角色，还看工单当前状态。C 有复核权限，但他不能复核一张 submitted 状态的单；他也不能复核一张 claimed_by 不是自己的单。

而这一层不需要额外的代码——它已经在你的条件更新里了：

UPDATE ticket
   SET status = 'done', reviewed_by = @me
 WHERE id = @id
   AND status = 'reviewing'
   AND claimed_by = @me;      -- ← 这一行同时是并发控制和权限校验
这一节的记忆点

「前置状态断言」这一个机制，同时解决了三件事：并发抢单、状态机合法性、数据权限。面试里把这三者收束到同一行 SQL 上讲，是这道题最漂亮的收尾。

七、话术

话术 A · 对应题「设计流程和相关表」

先反问再假设：我先确认两件事：复核员大概多少人同时在抢？抢到之后能不能放弃？我先按十几个人、可以放弃来设计。

给骨架：核心是一张工单表加一张流转流水表。工单表存当前状态，一张单一行，状态字段走 draft → submitted → approved → reviewing → done 这条链，打回就退回 submitted。流水表只增不改，每次流转追加一行，记谁在什么时候把它从哪个状态推到哪个状态。

说清为什么不拆三张表：我不会按提交、审核、复核建三张表——那样一次查询要连三次，而且回答不了「这单现在在谁手上」。审批流的本质是一张单在状态链上前进，不是三个独立的业务对象。

加一句收尾：业务数据本身我会放 jsonb，因为不同业务线的工单字段不一样，主表只固定流程相关的列。

话术 B · 对应题「多位用户抢单，系统如何设计」（核心题）

一句话点破本质：抢单的本质是一个 check-then-act：先查还没人认领，再写成我的。所有并发 bug 都长在这两步之间的缝里。所以我的做法是不要先查再改，让那一次改自己带上条件。

给出 SQL 并解释为什么它对：就是一条 UPDATE：set status = reviewing, claimed_by = 我 where id = ? and status = approved and claimed_by is null。检查和行动在同一条语句里，抢到就返回受影响行数 1，被别人抢了就是 0，应用层一个 if 就够。它的正确性靠的是 PostgreSQL 在 READ COMMITTED 下的规则：后到的 UPDATE 会等前一个事务结束，然后拿更新后的行版本重新求值 WHERE，条件不成立就跳过这行。

主动补失败路径（不等他问）：还要处理抢到不干活。我把认领设计成一份租约，加一个 claim_expires_at，定时任务把过期的放回池子。否则有人抢完就下班，那张单永远卡死。

再补兜底：另外我会加一个部分唯一索引 unique (ticket_id) where released_at is null，保证一张单同时只能有一个有效认领。能表达成数据库约束的业务规则，我不会只放在应用代码里——代码有很多条路径，约束只有一道门。

为什么这样答强：三段结构是机制 → 失败路径 → 兜底。绝大多数候选人只讲到第一段，主动讲后两段会立刻拉开差距。

话术 C · 对应追问「为什么不用悲观锁 / 上千人抢怎么办」

不用悲观锁的三条理由：SELECT FOR UPDATE 结果也是对的，但成本更大：要开显式事务、两次往返；锁的持有时间等于整个事务，一旦里面夹了远程调用或者用户思考时间就是长事务，后面全排队，连接池很快见底；多行按不同顺序加锁还可能死锁。这个场景一条语句就能表达完整的抢单逻辑，就不需要显式锁。反过来说，如果认领后还要在同一事务里读一堆别的表做校验，我会选悲观锁。

高并发的答法（换问题形态）：上千人抢同一批单，热点会集中在队首那几行。这时候我会把交互从「抢指定的某一单」改成「给我下一单可做的」，用 FOR UPDATE SKIP LOCKED——锁不住就跳过去拿下一行，两个人同时来会拿到不同的单，谁也不用等谁。PostgreSQL 文档里明确说这个选项就是给队列表的多消费者用的。

再加一层（如果还追问）：再往上就是预分配：按规则先把单分成若干池子，或者用 Redis 做一次预占再落库。但那要引入额外组件和一致性问题，我会先确认量级真的到了那个程度再上。

话术 D · 对应题「权限如何控制」「怎么确定被谁抢掉了」

权限两个维度：功能权限走 RBAC，用户挂角色、角色挂权限点，接口上用 policy 标注。数据权限单独一层，比如 B 只能审自己部门的单——这个过滤条件一定由服务端从登录态推导，不接受前端传部门 id。再加一层状态机权限：有复核权限不代表能复核任意一张单，还得看它当前是不是 reviewing、是不是挂在我名下。而这一层不用额外写代码，它已经在抢单那条 UPDATE 的 where 里了。

谁抢掉了，分三层答：当下看主表的 claimed_by；历史看流水表里 action 是 claim 的记录，能查出被谁抢过、放弃过几次，绩效核算和申诉都要用它；约束靠部分唯一索引兜底。当前态放主表、历史放追加表，这个模式我在做分布式事务补偿的时候也是这么处理的。

八、检验一下
