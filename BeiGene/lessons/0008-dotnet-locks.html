一、先分清两种锁

Lesson 07 的写法 ② 已经埋了这个坑：用 C# 的 lock 保护抢单逻辑，扩容当天就破。现在把这句话说完整——那两种「锁」根本不是同一个物种：

C# 的 lock数据库行锁
保护的边界一个进程里的一段代码一台数据库里的一行数据
谁在排队本进程的线程所有连上来的会话，跨机器
加了第二个副本完全失效照常有效
成本无竞争时几十纳秒一次网络往返

lock 保护的是代码，不是数据。它的承诺只有一句：「这段代码，本进程内同一时刻只有一个线程在跑。」数据是否安全，取决于这段代码是不是访问那份数据的唯一入口。抢单那题里它不是——别的机器上还有九个副本，每个都有自己的一把锁。

这一节的面试价值

被问「.NET 有哪些锁」时，先说这句话再开始列举：先分两层：进程内的同步原语，和跨进程的分布式锁。选哪个不取决于代码长什么样，取决于竞争的资源在哪一层。——绝大多数候选人一上来就背 lock / Mutex / Semaphore 的清单，这一句会立刻把你和他们分开。

二、lock 展开成了什么

lock 不是一个运行时机制，它是语法糖。编译器把它展开成 Monitor 的一对调用（C# 语言参考原文：the lock statement is precisely equivalent to）：

lock (x)
{
    // 你的代码
}

// ↓ 编译器实际生成的，一字不差：

object __lockObj = x;
bool __lockWasTaken = false;
try
{
    System.Threading.Monitor.Enter(__lockObj, ref __lockWasTaken);
    // 你的代码
}
finally
{
    if (__lockWasTaken) System.Threading.Monitor.Exit(__lockObj);
}

三件事从这段展开里直接读得出来，而它们正是面试要你说的：

  • 异常安全是白拿的。释放在 finally 里，body 抛异常锁也会还回去。这也是「为什么不自己写 Monitor.Enter」的答案——自己写就得自己保证这个 finally。
  • 锁挂在那个对象上，不挂在代码上。两段完全不相干的代码只要 lock 同一个对象，就会互相排队；同一段代码 lock 了两个不同对象，就一点保护都没有。
  • 它是可重入的。文档：the thread that holds the lock can acquire and release the lock multiple times。同一个线程递归进入不会把自己锁死——记住这条，第四节会用它来对比。

锁对象该选谁

微软文档明确点名了三个不要拿来当锁对象的东西，理由都是同一个：它们是公开的，外面的代码也能锁它。

别锁为什么
thiscallers might also lock this——调用方拿到你的实例也能 lock 它，你控制不了
typeof(Foo)Type 实例全进程唯一，任何人用 typeof 或反射都能拿到同一个
字符串字面量字符串会被驻留（interned）——你锁的 "lock" 和别人锁的 "lock" 是同一个对象

正确做法：一个私有的、只读的、专用的锁对象，一份被保护的数据配一把：

private readonly object _balanceGate = new();   // .NET 8 及以前

private readonly System.Threading.Lock _balanceGate = new();  // .NET 9 / C# 13 起
扩展 · .NET 9 的 System.Threading.Lock

C# 13 起，如果 x 的静态类型是 System.Threading.Lock，lock (x) 就不再展开成 Monitor，而是：

using (x.EnterScope()) { /* 你的代码 */ }

EnterScope() 返回一个带 Dispose() 的 ref struct，using 保证释放。文档的建议是 lock a dedicated object instance of the System.Threading.Lock type for best performance。

面试增量：.NET 9 加了一个专用的 Lock 类型，比锁 object 快，因为它不用走对象头上的同步块那条老路。而且如果你不小心把它转成 object 再锁，编译器会警告——因为那样就悄悄退回 Monitor 了。——这句话能证明你在跟版本，而不是停在 .NET Framework。

三、五种写法赛跑

场景换成最小的那个：两个线程各给同一个字段加一次。这和 Lesson 07 第 2 步你亲手跑出来的丢失更新是同一个形状，只是从数据库那一层搬到了内存里。

这一课唯一必须记死的一句

lock 认的是线程，不是任务——所以 await 一进去，它就守不住了。

每次点「下一步」之前先猜。写法 ④ 是这一课的正题，别跳过。

四、await 为什么进不去

把写法 ④ ⑤ 的对比压成一张表——这是这一课最值钱的五行：

lock / MonitorSemaphoreSlim
它记住的是哪个线程进来了还剩几个名额
能否跨 await不能（编译器直接拦）能
等待时的线程阻塞，占着不放WaitAsync 把线程还回去
可重入可以不可以，重入即自锁
释放编译器生成 finally你自己写 finally

一句话贯穿全表：Monitor 是「记名」的，信号量是「记数」的。记名的东西过不了 await，因为 await 之后名字就变了。

扩展 · 同一条线索的另一个出口：为什么不该用 .Result / .Wait()

既然 await 的意义是把线程还给线程池，那么在异步链路里写 SomethingAsync().Result 或 .Wait() 就是把这件事反着做一遍：线程被阻塞在那里干等，什么活也不接。

在有同步上下文的环境里（经典 ASP.NET、WinForms、WPF），它会直接死锁：续接需要回到那个被你阻塞住的上下文，而上下文正在等续接。ASP.NET Core 没有同步上下文，不会死锁，但每次都会吃掉一个线程——压力上来就是线程池饥饿，表现为「接口莫名其妙全都变慢」，而且慢的往往不是出问题的那个接口。

规则很短：async 一路到底（async all the way），中间不要有 .Result / .Wait()。参考 Stephen Cleary — Don't Block on Async Code。这条线索会在 Lesson 09 展开。

五、动手：跑出少掉的那个数

为什么必须亲手跑

上一课你已经验证过：看解释和亲手跑出来，是两种记忆。这次要逼出来的东西更难得——_count++ 的丢失更新在低并发下几乎不复现，所以它才能在生产环境里活好几年。这三分钟会给你一个具体的数字，那个数字就是你面试时说「我实际验证过」的凭据。

随便找个空目录：

dotnet new console -o lockdemo
cd lockdemo

把 Program.cs 整个替换成：

using System.Diagnostics;

const int Threads = 8;
const int PerThread = 200_000;
const int Expected = Threads * PerThread;

// ① 裸 ++
int naive = 0;
var t1 = Run(() => naive++);
Console.WriteLine($"① 裸 ++       : {naive,10:N0}   应为 {Expected:N0}，少了 {Expected - naive:N0}   {t1} ms");

// ② lock
int locked = 0;
var gate = new object();
var t2 = Run(() => { lock (gate) { locked++; } });
Console.WriteLine($"② lock        : {locked,10:N0}   {t2} ms");

// ③ Interlocked
int atomic = 0;
var t3 = Run(() => Interlocked.Increment(ref atomic));
Console.WriteLine($"③ Interlocked : {atomic,10:N0}   {t3} ms");

static long Run(Action body)
{
    var sw = Stopwatch.StartNew();
    var tasks = new Task[Threads];
    for (int i = 0; i < Threads; i++)
        tasks[i] = Task.Run(() => { for (int j = 0; j < PerThread; j++) body(); });
    Task.WaitAll(tasks);
    return sw.ElapsedMilliseconds;
}

然后 dotnet run。先猜，再看：① 会少掉多少？③ 会比 ② 快多少？

要记录的三件事
  1. ① 裸 ++ 得到的数字是多少？（这是这一课的交付物）
  2. 再跑三次，① 每次一样吗？——不一样。这正是它可怕的地方：不可复现的 bug，测试抓不住。
  3. ② 和 ③ 的耗时差多少倍？——这是你说「Interlocked 更快」时能给出的具体数量级。

加做一分钟：亲眼看编译器拦你

在 Program.cs 末尾加这么一段，然后 dotnet build：

async Task Broken()
{
    lock (gate)
    {
        await Task.Delay(1);   // ← 编译器会在这里报错
    }
}

要记录的：报错的编号和那句话是什么？记住它——面试里能报出编译器错误号，说明你真的撞过这堵墙。看完记得删掉这段，否则项目编译不过。

交作业

报回来一行就够：① 的那个数字，还有 ② 和 ③ 的耗时。上一课你三次都只给了数字，很好——这一课照旧，我不问你懂了没，只看数字。

六、选型：哪个场合用哪个

机制讲完了，现在才轮到选型。面试里被问「.NET 有哪些锁」，按这张表从上往下说，并且每一行都带上「什么时候不用它」——只会列举的人很多，能说出边界的人很少：

工具用在不要用在
Interlocked单个变量的自增、交换、CAS要同时保持两个字段一致时
lock
= Monitor		默认选它。同步代码里的短临界区body 里有 await；临界区里有 I/O 或远程调用
SemaphoreSlim异步临界区（WaitAsync）；把并发度限制成 N需要可重入时；没把握写好 finally 时
ReaderWriterLockSlim读远多于写，且单次持有时间不算短的共享缓存临界区只有几纳秒时——它自身开销比 lock 大，得不偿失
ConcurrentDictionary 等能用现成并发集合就别自己加锁需要跨多个 key 保持原子性时
Mutex跨进程（同一台机器），如「只允许一个实例运行」进程内同步——它比 lock 慢几十倍
Redis / 数据库跨机器。多副本部署下的唯一选择单机就能解决的问题
这一节的记忆点

选锁只有一个判据：竞争的资源在哪一层，锁就加在哪一层。变量 → Interlocked；进程内的对象 → lock；机器上的资源 → Mutex；数据库里的行 → 条件更新或行锁；多副本共享的状态 → 分布式锁。

把这句话和 Lesson 07 串起来讲，就是一个完整闭环：抢单那个场景，竞争的资源是数据库里的一行，所以我把控制放在那条 UPDATE 的 where 里，而不是在 C# 里加 lock——加了也没用，我们是多副本部署。

七、话术

话术 A · 对应题「.net 锁的使用及种类」

先给判据，别急着列清单：我一般先分两层看：进程内的同步原语，和跨进程、跨机器的分布式锁。选哪个不看代码长什么样，看竞争的资源在哪一层。

再列，每个都带边界：进程内，单个变量的自增或交换用 Interlocked，无锁、最快；一般的临界区用 lock，它就是 Monitor.Enter 加 try/finally 的语法糖；异步代码里用 SemaphoreSlim 配 WaitAsync，因为 lock 里不能 await；读多写少而且持有时间不短的可以考虑 ReaderWriterLockSlim，但临界区很短的时候它反而比 lock 慢。跨进程是 Mutex，跨机器就得上 Redis 或者数据库。

收一句：不过实践里我第一反应是能不能不加锁——换成并发集合，或者把状态收到数据库那一层用条件更新解决，通常比加锁更省心。

话术 B · 对应追问「为什么 lock 里不能 await」（这是拉开差距的一问）

直接给根因：因为 lock 展开成 Monitor.Enter / Exit，而 Monitor 是线程亲和的——谁进的谁出。await 恰恰会把线程还给线程池，续接可能落到另一个线程上，那个线程去 Exit 会抛 SynchronizationLockException。所以编译器干脆禁止了。

补更阴的那一层：还有个更隐蔽的问题：await 的时候锁并没有释放，但那个线程已经被还回去处理别的请求了。如果那条路径也要进同一把锁，因为 Monitor 可重入、认的就是线程，它会直接拿到——两份不相干的业务同时进了临界区，而且不报任何错。

给解法：异步场景我用 SemaphoreSlim(1,1)，它只是个计数器、不记持有者，所以能跨 await。但要注意两点：它不可重入，还有 Release 必须放在 finally，否则 body 抛一次异常这把锁就永远回不来了。

为什么这样答强：大多数人只能答到「编译器不让」。能说出「线程亲和」四个字就已经进前 20%；能补上可重入那一层，面试官会知道你踩过。

话术 C · 对应追问「你项目里怎么用的 / 踩过什么坑」

用上一课那件真事：印象最深的一次是并发场景选错了锁的层级。业务是多个人抢同一批任务，第一版在 C# 里加了一把 lock——单实例测试完全正常，扩到两个副本之后立刻出问题，两个人抢到同一单。原因是锁的作用域是进程，而竞争的资源是数据库的一行，两台机器上的两把锁互不相识。

给修法：后来把控制下沉到数据库：一条 UPDATE ... WHERE status = approved AND claimed_by IS NULL，靠受影响行数判断谁抢到。这件事之后我的习惯就是先问竞争资源在哪一层，再决定锁加在哪一层，而不是顺手在代码里加。

为什么这样答强：它是一个完整的「翻车 → 定位 → 修复 → 沉淀原则」闭环，而且横跨 .NET 和数据库两个板块。上一课你已经亲手把这两种情形都跑出来过了——这段是你能讲的真实经历，不是背的。
