0. 结构与术语

词是什么量级
索引一整棵 B-tree，磁盘上一个文件成千上万个页
页 page/block树上一个节点；数据库 I/O、缓存、空间管理的最小单位PG 8KB（BLCKSZ，编译期定死）/ InnoDB 16KB
键 key/索引项页里一条记录 = 索引列的值 + 行指针；表里一行 = 叶子层一个键几十字节
扇出 fan-out一个页装多少个键 = 一个节点多少分叉int4 单列约 400

因果链（面试可整段说）：页是 I/O 单位 → 一页装多少键 = 扇出 → 扇出决定树高 → 树高决定一次查询几次 I/O。
推论：键越宽，扇出越低，树越高。联合索引多一列、用宽类型（长 text、UUID vs int）都在抬高树高——这是联合索引的隐性成本，也是 InnoDB「主键别太大」的原因（二级索引每个键都存一份主键值）。

单列索引与联合索引不是两种结构，是同一棵 B-tree，区别只在键是一个值还是一个元组（按字典序排）。所以最左前缀不是给联合索引单定的规矩，而是「B-tree 有序」在多列下的自然结果。

B ≠ Binary（最常见错答）。Bayer & McCreight 1970 年从未解释 B 的含义，候选：Balanced / Bayer / Boeing / Broad。中文直接写「B 树」，- 是连字符不是减号。图上画的叶子链表严格说是 B+ tree，即 PG 与 InnoDB 的实际形态。

1. 最左前缀 · 一句话规则

联合索引 (a, b, c) = 按 (a, b, c) 多级排序的有序表。
能用来定位的部分 = 从最左列开始连续的等值条件 ＋ 其后第一个范围条件。范围条件之后的列只能过滤，不能定位。

索引 (a,b,c) 上的查询用于定位的列结论
a=1a✅ 有效
a=1 AND b=2a, b✅ 有效
a=1 AND b=2 AND c=3a, b, c✅ 最佳
a=1 AND c=3a⚠️ 部分：c 退化为过滤
a=1 AND b>2 AND c=3a, b⚠️ 部分：范围截断，c 只过滤
b=2 AND c=3—❌ 跳过最左列（PG18+ 可能 skip scan）
a=1 ORDER BY ba（并复用 b 的有序性）✅ 且免 Sort

列顺序黄金法则

等值列 → 范围列 → 排序列；等值列内部按区分度从高到低。
范围列与排序列冲突时，通常把排序列前置（免掉 Sort 节点往往比多过滤几行更划算），但要以 EXPLAIN ANALYZE 实测为准。

2. 索引失效 · 三类归因

A · 违反最左前缀

  • 跳过最左列
  • 中间列缺失（右侧列退化为过滤）
  • 范围条件之后的列
  • OR 连接的条件中有列无索引 → 整体退化

B · 索引列被加工

  • 函数包裹：lower(col)=…
  • 类型转换：col::date=…、字符串列传数字
  • 列参与运算：price*2>100
  • 前导通配符：LIKE '%x'
  • != / NOT IN（通常命中面过大）
  • 排序规则/collation 不匹配（PG 的 LIKE 'x%' 需 text_pattern_ops）

C · 优化器主动放弃

  • 命中行占比过高（经验 >5–20%）
  • 区分度太低（status、gender）
  • 统计信息过期 → ANALYZE tbl;
  • 表太小，全表扫只需一两个 page

修复手法

-- 让列「裸奔」：把加工挪到常量侧
-- ❌ WHERE created_at::date = '2026-05-01'
-- ✅ WHERE created_at >= '2026-05-01' AND created_at < '2026-05-02'

-- 表达式索引（写入变慢，读取变快）
CREATE INDEX ix_lower_email ON users (lower(email));

-- LIKE 'x%'（前缀）在非 C collation 下需要 pattern ops
CREATE INDEX ix_title_pat ON study (title text_pattern_ops);

-- LIKE '%x'（后缀）→ 反转即变前缀。注意：优化器不会自动改写，查询必须照抄表达式
CREATE INDEX ix_title_rev ON study (reverse(title) text_pattern_ops);
-- ❌ WHERE title LIKE '%report'
-- ✅ WHERE reverse(title) LIKE 'troper%'

-- LIKE '%x%'（任意位置）→ B-tree 无解，上 pg_trgm（模式需 ≥3 字符）
CREATE INDEX ix_title_trgm ON study USING gin (title gin_trgm_ops);

-- 最好的答案：若后缀其实是结构化字段，把它变成真正的列
ALTER TABLE study ADD COLUMN title_ext text
  GENERATED ALWAYS AS (split_part(title, '.', 2)) STORED;

-- 覆盖索引，免回表 → Index Only Scan
CREATE INDEX ix_cover ON study (owner_id, status) INCLUDE (title, created_at);

-- 部分索引：只索引真正被查的子集，体积小得多
CREATE INDEX ix_active ON study (owner_id) WHERE status = 'ACTIVE';

4. 索引的代价（"什么时候该建索引"必答）

  • 写放大：每个索引一棵 B-tree，INSERT 要多写一次 + WAL
  • 阻断 HOT 更新：给高频更新的列加索引 → 关掉 Heap-Only Tuple 优化，写性能可能断崖
  • 膨胀 bloat：频繁增删改 → REINDEX INDEX CONCURRENTLY
  • 挤占 shared_buffers；增大优化器计划枚举空间
  • 生产建索引必须 CREATE INDEX CONCURRENTLY：不锁写，但扫两遍表、不能在事务块里跑、失败留下 INVALID 索引 → 事后查 SELECT * FROM pg_index WHERE NOT indisvalid;
  • 清理无用索引：SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0;

5. EXPLAIN 读法（Postgres）

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT …;
看什么健康危险信号
扫描节点Index Scan / Index Only Scan大表上的 Seq Scan
rows= 估算 vs actual rows=同数量级差 10 倍以上 → 统计信息过期，ANALYZE
Sort 节点不存在（索引已有序）出现 external merge Disk: …kB → 排序溢出到磁盘
Join 方式Hash / Merge Join大表间 Nested Loop
BUFFERSshared hit 占比高shared read 大 → 缓存未命中，I/O 瓶颈
Filter 行数Rows Removed by Filter 小该数字很大 → 索引选择性不足，考虑加列
Bitmap 精度Heap Blocks: exact=N出现 lossy=N → work_mem 不足，Recheck Cond 真的会执行

条件的三档（PG 的 EXPLAIN 会骗你）

档位条件EXPLAIN 显示代价
① 边界连续等值 + 第一个范围Index Cond决定扫描区间，最省
② 索引内过滤列在索引里但被截断Index Cond（与①无法区分）多扫索引项，不回表
③ 堆过滤列不在索引里Filter + Rows Removed by Filter必须回表才能判断，最贵

①②怎么区分：看索引扫描节点吐出的 rows 与最终结果差多少，差得多就说明有②。
MySQL 反而更诚实：②会显式标成 Using index condition（ICP 索引条件下推）。
「退化为 Filter」≠「索引失效」——索引还是走了，只是那一列从定位降级为过滤。

三种扫描形态

形态何时选特点
Index Scan命中行少（<1%）按索引顺序随机访问表页
Bitmap Heap Scan中等命中（几 %）先收集 ctid 成位图、按页号排序再读 → 随机 I/O 变顺序
Seq Scan命中占比高 / 表很小纯顺序 I/O，预读友好

6. SQL 优化的排查顺序（面试可直接背诵这个流程）

  1. 定位：pg_stat_statements 按 total_exec_time 排序，找到真正的大头（而不是凭感觉猜）
  2. 解释：对候选 SQL 跑 EXPLAIN (ANALYZE, BUFFERS)
  3. 判因：不能用索引（A/B 类）还是不想用（C 类）
  4. 改写：让列裸奔、消除 SELECT *、把 OR 改 UNION ALL、深分页用 keyset（WHERE id < ? ORDER BY id DESC LIMIT 20）替代 OFFSET
  5. 加索引：按等值→范围→排序拼列；生产环境务必 CREATE INDEX CONCURRENTLY（不锁写）
  6. 再往上：仍不够就上缓存 / 物化视图 / 读写分离 / 分区表
  7. 验证：改完再跑一次 EXPLAIN，用数字说话

7. JOIN 方向速记

写法"主表"（结果集行数下限）记忆
A LEFT JOIN BA（左边，写在 JOIN 前）A 全保留，B 无匹配则补 NULL
A RIGHT JOIN BB（右边，写在 JOIN 后）B 全保留，A 无匹配则补 NULL
A INNER JOIN B无主表只留两边都匹配的
A FULL JOIN B两边都是两边都保留

"right join 主表在哪边？" → 右边，也就是 JOIN 关键字后面那张表被完整保留。 补一句加分：实践中我们团队统一只用 LEFT JOIN，把驱动表写在前面，可读性好、也不容易在多表串联时把保留侧搞错——RIGHT JOIN 都可以等价改写成 LEFT JOIN。
陷阱：把过滤条件写进 ON 还是 WHERE 结果完全不同。LEFT JOIN B ON … AND B.x=1 保留 A 全部行；写成 WHERE B.x=1 会把补 NULL 的行过滤掉，LEFT JOIN 退化成 INNER JOIN。
