微服务：四笔开销
＋ Saga 与补偿

压缩自 Lesson 04 与 Lesson 05。面试前 10 分钟只看这一页。

0 · 一句话根源

微服务 = 把一次进程内方法调用，换成一次网络调用。进程内免费的四件事，跨进程之后全部开始收费。所有微服务技术栈，都是这四张账单的付款方式。

进程内免费跨进程之后付款方式
调用一定会返回可能超时；可能成功了但你不知道超时 + 幂等 + 重试 + 熔断
异常带完整堆栈只收到一个 500TraceId / traceparent
一个事务能一起回滚两个库，回滚不了对方Outbox + MQ + 幂等消费
方法名就是地址要知道 IP / 端口 / 是否活着网关 / 服务发现

1 · 网络调用的四种结局

结局调用方看到数据状态
成功200一致
快失败500，很快没执行（最友善的失败）
超时异常未知
执行了但响应丢失和超时一模一样已执行
全课最值钱的一句

「超时」和「执行了但响应丢失」在调用方看来永远分不清。所以重试没有意义，除非接口幂等。
同一个机制解释了 MQ 为什么只能承诺 at-least-once：ACK 也会丢。因此 HTTP 重试要幂等、MQ 消费要幂等，是同一个原因。

2 · 幂等的落地写法

CREATE TABLE reserve_log (request_id uuid PRIMARY KEY, ...);

同一个本地事务里：先插去重记录，再改业务数据。捕获唯一键冲突（PostgreSQL 23505）→ 直接返回成功。
要点：把并发正确性下沉到数据库唯一约束，而不是应用层 if。同 索引速查表的部分唯一索引思路。

  • o.Retry.DisableForUnsafeHttpMethods() —— POST/PUT/DELETE 不重试，除非有幂等键
  • jitter：防止一百个实例同时重试形成洪峰
  • 熔断保护的是调用方（防级联失败）；限流保护的才是被调用方

4 · 链路追踪

  • Trace = 一次请求的全过程；Span（.NET 叫 Activity）= 其中一段；TraceId 16B，SpanId 8B
  • 传播靠 W3C 头 traceparent: 00-{traceId}-{spanId}-01，.NET 5+ 默认，自动收发，无需写代码
  • 你要做的只有：Activity.Current?.TraceId 写进日志、返给前端
  • 采集靠 OpenTelemetry / App Insights；要采样，但出错的链要保证留下（尾部采样）

5 · 最终一致性四步

  1. 本地事务：业务数据 + Outbox 消息表，一起提交（解决「写库」与「发消息」无法原子）
  2. 投递：后台任务扫表发 MQ，失败重发
  3. 消费：幂等（唯一键去重）—— 因为 MQ 是 at-least-once
  4. ACK：业务处理完再手动 ACK，禁用自动 ACK

不用 2PC 的理由：第二阶段前长时间持锁，一方慢就拖垮全部；且对第三方你根本没有回滚权。
代价：存在不一致窗口 → 必须配对账任务 + 超时告警。

6 · 网关

第一职责不是路由，是把横切关注点收口（认证、限流、跨域、TLS、日志）。

YARPOcelotNginx / 云网关
微软官方 .NET 反向代理，本身是 ASP.NET Core 应用，可写 C# 转换逻辑（灰度、按租户路由）较早的社区 .NET 网关，老项目常见纯路由 + TLS + 限流时最省事、性能最好

追问准备：网关是单点 → 多实例 + 前置负载均衡；网关里绝不放业务逻辑，否则它变成新的单体。

7 · 开场白模板

「说说你对微服务的了解」

我理解微服务的本质，是把一次进程内的方法调用换成一次网络调用。进程内免费的四件事——调用一定会返回、异常带完整堆栈、一个事务能一起回滚、方法名就是地址——跨进程之后全部开始收费。微服务的整套技术栈，其实就是这四张账单的付款方式：熔断和幂等买第一笔，链路追踪买第二笔，最终一致性买第三笔，网关和服务发现买第四笔。所以选不选微服务，本质是这四笔钱值不值得付。

8 · Saga 与补偿事务

词源（面试可直接引用）：Saga 不是缩写，就是古诺尔斯语的「长篇叙事」。出处是 Garcia-Molina & Salem, Sagas, ACM SIGMOD 1987，解的是单库里长事务（LLT）占锁的问题，与微服务无关；2010 年代才被借来做跨服务一致性。隐喻是精确的：长故事拆成一章一章（子事务各自提交、当场放锁），中途讲不下去时没法「当这本书没写过」，只能再补写几章把情节撤销——那就是补偿事务。

Saga：一串本地事务；任一步失败，就逆序执行前面各步的补偿事务去撤销。补偿由开发者手写，不是 ACID 的自动回滚（microservices.io）。

数据库回滚Saga 补偿
谁做引擎自动手写业务代码
痕迹像没发生过一正一反两条记录
中间态外界看不见看得见（丢的是 ACID 的 I）→ 用语义锁加中间状态挡住
会失败吗基本不会会，它也是一次网络调用

补偿必须「持久化 + 可无限重试 + 幂等」。写在 catch 块里调一次的补偿等于没有补偿。把补偿意图先落 saga 状态表，后台任务重试到成功或告警转人工。

补偿的三个坑（同一张 tx_log(biz_id PK, state) 全解）

坑情形防法
空补偿正向从未执行，补偿先到查不到正向记录 → 插 COMPENSATED，返回成功，什么都不做
悬挂补偿先到并成功，超时的正向随后才到并执行 → 资源永久占住正向进来先查：已是 COMPENSATED → 拒绝执行
幂等补偿超时重试，退了两笔正向与补偿都以 biz_id 唯一索引去重

① 与 ② 必须成对实现：允许了空补偿才产生悬挂；只做 ① 会把明显的错误换成安静的资源泄漏。

9 · 编排 vs 协同

编排 Orchestration协同 Choreography
机制协调者告诉各方执行什么各方发布领域事件，触发彼此
中心有，流程写在协调者里无，流程散在订阅关系里
代价协调者变胖，吸走业务逻辑没有一处看得到完整流程 → 链路追踪是必需品
我的经历第三方对接（顺序调用 + 逆序回退）Solace 十个系统（各订各的 topic）

消息式 Request-Reply

ReplyTo = 回信寄到哪个 topic/queue（API 自动生成唯一目的地）；CorrelationId = 响应方原样带回，请求方据此把回信和自己的请求对上。Solace topic 形如 a/b/c/.../n，订阅可用 *（单层）与 >（尾部多层）通配（Solace Docs）。

vs HTTP：① 解耦（发布方不需知道消费方）② 削峰（对方挂了消息排队）③ 代价：延迟高、超时要自己管、响应也会丢所以消费仍需幂等。

「和第三方交互如何保证一致性」

同步接口，走 Saga 的补偿事务，编排式，协调逻辑在我这边——任一步失败就按逆序调各步的回退接口，最后撤自己的库。关键是补偿不等于回滚：它是我手写的代码，会留下正反两条记录，而且它自己也是网络调用、也会失败。所以补偿意图要先落库、由后台任务持续重试。对第三方的回退接口有三个要求：幂等、允许空补偿、防悬挂。

10 · 选型：该不该拆

一句话尺子：微服务的全部代价，只为换「每个服务能自己上线，不用等别人」。改动必须几个系统一起发 = 分布式单体，成本全付、收益没拿。

收益 buy（Fowler）成本 pay（Fowler）
强模块边界分布式（远程调用慢且会失败）
独立部署 ← 根收益最终一致性
技术异构运维复杂度
痛点该不该拆
多团队互相阻塞、发布排队拆。唯一站得住的理由（且需先有 CD／自动部署／链路追踪）
某模块扛不住量多半不拆——单体也能多副本；除非资源画像截然不同
代码乱想重构不拆（陷阱）——只会把编译期能抓的错换成线上超时
全新项目单体优先。边界一开始必然划错，而服务间挪功能比单体里贵一个数量级

两条禁令：Dont even consider microservices unless you have a system thats too complex to manage as a monolith（MicroservicePremium）；Almost all the cases ... built as a microservice system from scratch ... ended up in serious trouble（MonolithFirst）。

11 · 边界：划在哪、怎么自查

按业务能力划（Decompose by Business Capability），不按技术分层划。拆成界面／逻辑／数据三个服务必错：需求纵向切、边界横向切，永远垂直相交 → 任一需求都穿过三层。

判据（microservices.io）自查
高内聚能一句话说清它「负责什么生意」吗
低耦合别人能绕过 API 直接读你的库吗
团队规模6–10 人一个服务
自治minimal cross-team coordination——minimal 不是 zero；开会不等于失败，「必须一起上线」才等于失败
可独立测试不启动别的服务能否跑完测试
稳定一个需求平均动几个服务——最实用的一条，不需任何工具

康威定律（Conway, Datamation, 1968）：Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure. → 服务边界与团队边界必须配套；组织上划不开，服务边界迟早守不住。

「运维成本高、交互复杂，为什么还选微服务」

先说我同意这个前提——微服务是有溢价的，除非单体复杂到管不动否则不该考虑。成本很具体：调用会失败、强一致变最终一致、排查复杂度上台阶。付这些只换一件事：独立部署，每个团队按自己节奏上线。这个收益随团队数量放大——一个团队时一文不值，十个团队时就是全部。所以我的标准是：拆分解决的是组织问题，不是技术问题。因为代码乱或性能不够去拆，基本都会翻车。

「从单一服务扩展到微服务」（没亲历过拆分时）

我进去时已经拆好了，完整拆分过程没亲历过。如果让我主导：① 先确认动机，只有多团队互相阻塞才拆；② 先补自动化部署、集中日志、链路追踪；③ 绞杀者模式，路由挡在单体前面，一次切一个业务能力，每步可回退；④ 最难的是数据，共享库拆开要经历双写与迁移，工作量通常比拆代码大。
