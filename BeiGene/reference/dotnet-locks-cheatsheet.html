.NET 锁的种类
＋ 为什么 lock 里不能 await

压缩自 Lesson 08。面试前 10 分钟只看这一页。

0 · 一句话判据

竞争的资源在哪一层，锁就加在哪一层。选锁不看代码长什么样，看竞争边界在哪里。

单个变量        → Interlocked
进程内的对象    → lock            （异步链路里换 SemaphoreSlim）
本机多个进程    → Mutex
数据库里的一行  → 条件更新 / 行锁   ← Lesson 07
多副本共享状态  → Redis / 数据库分布式锁

1 · 选型表（每一行都带「不要用在」）

工具用在不要用在
Interlocked单变量自增 / 交换 / CAS，无锁最快要同时保持两个字段一致时
lock = Monitor默认选它，同步代码的短临界区body 里有 await；临界区里有 I/O 或远程调用
SemaphoreSlim异步临界区 WaitAsync；并发度限 N需要可重入时；漏写 finally 时
ReaderWriterLockSlim读远多于写且持有时间不算短临界区只有几纳秒时，它比 lock 还慢
并发集合能用现成的就别自己加锁要跨多个 key 保持原子性时
Mutex跨进程：只允许一个实例运行进程内同步，比 lock 慢几十倍
Redis / DB跨机器，多副本部署的唯一选择单机就能解决的问题

2 · lock 展开成什么（背下来）

lock (x) { /* body */ }

// ↓ 编译器生成，一字不差

object __lockObj = x;
bool __lockWasTaken = false;
try
{
    System.Threading.Monitor.Enter(__lockObj, ref __lockWasTaken);
    /* body */
}
finally
{
    if (__lockWasTaken) System.Threading.Monitor.Exit(__lockObj);
}

三个推论：① 异常安全是编译器白送的 → 别自己写 Monitor。② 锁挂在对象上不挂在代码上 → lock 不同对象＝没锁。③ 可重入，同线程递归进入不会自锁。

.NET 9 / C# 13 起：若 x 是 System.Threading.Lock 类型，则等价于 using (x.EnterScope()) { }，性能更好。

4 · 为什么 lock 里不能 await（高频追问）

根因一句话：Monitor 认线程，await 会换线程。

lock / MonitorSemaphoreSlim
记住的是哪个线程进来了还剩几个名额
跨 await不能（编译器拦）能
等待时阻塞，占着线程WaitAsync 把线程还回去
可重入可以不可以，重入即自锁
释放编译器生成 finally你自己写 finally

手写 Monitor 绕过编译器的后果：await 后续接落到别的线程 → 那个线程 Monitor.Exit → SynchronizationLockException，锁永久卡死。

更阴的一层（说出来＝资深信号）：await 期间锁没释放，而原线程已被还给线程池去处理别的请求；那条路径要进同一把锁时因可重入直接放行 → 两份不相干的业务同时进临界区，且不报错。

private readonly SemaphoreSlim _gate = new(1, 1);

await _gate.WaitAsync();
try   { await _db.SaveAsync(); _count++; }
finally { _gate.Release(); }        // 漏了这行 = 永久泄漏

被问怎么起头
