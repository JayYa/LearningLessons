慢请求排查
＋ 日志 / 指标 / 追踪

压缩自 Lesson 14，接 async 速查表的线程池饥饿画像、索引速查表的 EXPLAIN 三档。面试前 10 分钟只看这一页。

0 · 一句话判据

先定位，再解释：一次慢请求的时间一定花在某一跳上。指标缩到哪一层 → 追踪找到哪一跳 → 日志 / profiler 问它为什么。「慢」是症状（what's broken），原因（why）是定位之后自然出来的。

1 · 三个二分问题（先问，再动手）

问答去看
一个用户还是很多用户？一个，数据不特殊他的浏览器瀑布图：TTFB 小、下载长 = 响应体大 / 网络差
一个，数据量特别大用他的参数跑 EXPLAIN，对比普通用户（掉到 Seq Scan？）
所有接口还是某个接口？所有 + CPU 高算力：dotnet-trace / PerfView 火焰图；GC Gen2 频率
所有 + CPU 低等待：线程池饥饿 / 连接池耗尽 / 下游慢 / 锁。看线程数与队列
一直慢还是最近开始？一直接口设计：看一条 trace——SQL / N+1 / 大响应 / 同步下游
最近找拐点：p99 时间线对齐发布记录；pg_stat_statements 同一语句 mean_exec_time 前后对比

2 · 追踪图的四种答案

看到意思下一步
一个 span 占大头就是它SQL → EXPLAIN；下游 → 超时 / 熔断 / 异步化
几十个一样的小 spanN+1（ORM 延迟加载）JOIN 或 WHERE id = ANY($1)，往返 51 → 2
span 之和 ≪ 总时长空白 = 没人计时的时间：等线程池、GC 暂停、锁配合 CPU 低 + 线程数缓涨 → 线程池饥饿 → dotnet-counters → dotnet-stack
服务端 span 很短，用户仍慢时间不在服务器上客户端瀑布图：下载 / 渲染。分页、少字段、压缩

3 · 三根支柱

支柱回答.NET API常见后端贵贱
指标什么时候开始、多严重、多大范围；告警只能挂这里MeterPrometheus + Grafana / App Insights最便宜，存最久
追踪这一次请求时间在哪一跳（跨进程）Activity / ActivitySource；traceparent 头自动传Jaeger / Zipkin / App Insights中，常采样
日志那一跳里发生了什么：参数、异常、分支ILogger<T>Seq / ELK / Loki / App Insights最贵，最后翻

采集统一走 OpenTelemetry：应用只对 .NET 自带的三个 API 写，OTLP 发给任意后端，换后端不改代码。

4 · 四个黄金信号（SRE Book）

信号要点
延迟看 p99 不看平均；成功与失败分开算——a slow error is even worse than a fast error
流量每秒请求数。「慢」是不是因为「多」
错误显式（500）+ 隐式（200 但内容错）+ 按策略（超 1 s 算失败）
饱和度最紧张的资源用了多少：线程池、连接池、CPU、内存。线程数 212 / 队列 340 就是它

5 · 工具按层

层工具看
SQLpg_stat_statements（需 shared_preload_libraries）按 total_exec_time 找最贵、按 calls 找最频繁；shared_blks_read 高 = 没命中缓存
SQLEXPLAIN (ANALYZE, BUFFERS)Seq Scan / 回表 / Sort Method 溢出磁盘
进程dotnet-counters monitor -p <pid>仪表盘：thread_pool.thread.count 缓涨、queue.length、GC 次数、lock_contentions
进程dotnet-stack report -p <pid>快照：每根线程此刻的栈。栈顶 Task.Wait / GetResultCore → 顺着往下找业务方法
进程dotnet-trace collect -p <pid> → PerfView录像：CPU 采样火焰图；.NET 9 起 --clrevents waithandle 抓阻塞事件（偶发问题用）
进程dotnet-dump → VS Parallel Stacks持续问题的完整快照，可看对象图（内存泄漏）
客户端DevTools Network 瀑布DNS / TLS / TTFB / 下载 / 渲染各占多少；响应体大小

三者关系：counters 是仪表盘，stack 是快照，trace 是录像。都是 dotnet tool install -g，挂进程 id，不改代码不重启。

6 · 线程池饥饿画像（背下来）

全站慢 + CPU 远低于 100% + 线程池线程数缓慢持续上涨（稳定在核数 3 倍以上）+ 队列长度高。原因几乎总是 sync-over-async（.Result / .Wait() / GetAwaiter().GetResult()），偶尔是 lock / SemaphoreSlim.Wait。解法是全链路 await，不是加线程。

7 · 日志三判据

判据做法反例
结构化命名占位符模板：Log("订单 {OrderId} 超时 {ElapsedMs}ms", id, ms)——参数作为字段进后端$"订单 {id}" 插值：只剩字符串，无法按字段查
可关联scope / enricher 自动附 TraceId、SpanId、RequestId；业务 id 用 BeginScope每条手写 TraceId，漏一条就断
分级生产 Information；"Microsoft.AspNetCore": "Warning" 压框架噪音；排查时按类别临时调 Debug，不重启生产开 Debug / Trace（量大、含敏感数据）

六级：Trace（生产禁）→ Debug（慎）→ Information（主流程）→ Warning（异常但没失败：重试成功、降级）→ Error（这次请求失败）→ Critical（数据丢失、磁盘满）。

写日志别拖慢系统：异步 sink 或写 stdout 交采集器；热路径用 LoggerMessage 源生成器。

8 · 吞吐率三杠杆

吞吐 = 并发处理数 ÷ 每请求占用时间。

  1. 别让线程等：全链路 async；去 .Result；不用 Task.Run 包同步（只多一次调度）；IEnumerable 返回前先 ToListAsync
  2. 让每请求更短：少往返（N+1 → JOIN）、少数据（分页、只取需要的列、只读 no-tracking）、缓存（接受稍旧）、IHttpClientFactory 复用连接、避免 ≥ 85 KB 大对象（LOH → Gen2）
  3. 把慢活挪出请求：后台服务 / MQ，请求写 PENDING 就返回，结果推回（SignalR / 通知）

前提：先测量——追踪图上时间在哪就拉哪个。横向扩容放最后：要无状态，且不解决单请求太重。

9 · 三句话术骨架

  • 排查慢：「慢是症状不猜原因；三问缩范围（一人/多人、一接口/全站、一直/最近）；看追踪定跳；拿 TraceId 翻日志。指标定层，追踪定跳，日志看细节。」
  • 日志 / 检测服务：「不报产品名，报三根支柱各答什么问题 + 采集走 OTel 后端可换；日志三判据：结构化、可关联、分级。」
  • 吞吐率：「并发 ÷ 每请求时间 → 三杠杆：别等、更短、挪出去；先测量再拉。」
