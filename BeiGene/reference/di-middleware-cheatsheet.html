中间件管道与 DI 生命周期
＋ Captive Dependency

压缩自 Lesson 10。面试前 10 分钟只看这一页。

0 · 两句话判据

管道：不是列表，是函数套函数。Build() 倒着折叠，第一个注册的在最外层；每个中间件 await next() 后面的代码在所有内层跑完之后才执行。

DI：三种生命周期 = 三个存放位置。Singleton 存根容器、Scoped 存当前作用域（ASP.NET Core 每个请求开一个）、Transient 不存每次 new。短命的不能被长命的持有。

1 · Build() 的 15 行（背下来）

public IApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> mw)
{ _components.Add(mw); return this; }

public RequestDelegate Build()
{
    RequestDelegate app = ctx => { /* 默认 404 */ return Task.CompletedTask; };
    for (var c = _components.Count - 1; c >= 0; c--)
        app = _components[c](app);            // 倒着包：最后注册的最里面
    return app;                               // 一个函数，所有请求都调它
}

出处：ApplicationBuilder.cs。中间件实例只在这里构造一次（constructed once per application lifetime）。

2 · 三个现象与它们的机制

现象机制
Logging 放 Auth 外面能记到 401短路只是「不调 next」，外层从 await next() 返回后照常执行后置代码
UseExceptionHandler 必须第一个异常沿调用栈往外抛，只有更外层能 catch；中间各层后置代码被跳过
写了 body 之后不能改状态码Response.HasStarted 为 true 后改头抛 InvalidOperationException；ExceptionHandler 此时也救不了

3 · Use / Run / Map

app.Use(async (ctx, next) => { /*前*/ await next(ctx); /*后*/ });   // 拿到 next，不调 = 短路
app.Run(async ctx => { ... });        // 拿不到 next，永远终端，之后注册的全不跑
app.Map("/api", b => { ... });        // 按路径分叉，不回主线；UseWhen 会回主线

4 · 自定义中间件（约定式）

public class XxxMiddleware
{
    private readonly RequestDelegate _next;
    public XxxMiddleware(RequestDelegate next, ILogger<XxxMiddleware> log) { ... }   // ① 收 RequestDelegate；其它由 DI 填 —— 但只构造一次

    public async Task InvokeAsync(HttpContext ctx, ICurrentUser user)                 // ② Invoke/InvokeAsync，返回 Task，首参 HttpContext
    {                                                                                // ③ Scoped 依赖放这里，每请求解析
        await _next(ctx);
    }
}
public static IApplicationBuilder UseXxx(this IApplicationBuilder app) => app.UseMiddleware<XxxMiddleware>();
陷阱

构造函数里注入 Scoped（DbContext、当前用户）→ 拿到第一个请求那份，永远不换。要每请求一份的，放 InvokeAsync 参数。原文：To share a scoped service between middleware and other types, add these services to the InvokeAsync method's signature.

5 · 推荐顺序（删掉可选项的骨架）

app.UseExceptionHandler();    // 最外层：接所有人的异常
app.UseHttpsRedirection();
app.UseStaticFiles();         // 能短路就早短路（注意：它不做鉴权）
app.UseRouting();             // 决定打到哪个端点
app.UseAuthentication();      // 填 User（你是谁）
app.UseAuthorization();       // 拿 User + 端点策略判断（能不能）—— 必须在 Routing 后
app.MapControllers();         // 终端

三条判据：要接谁的异常就在谁外面 / 能短路的越早越省 / 用别人产物的排在别人后面。

6 · 三种生命周期

存在哪同一请求两次解析跨请求典型不要用在
AddSingleton根容器同一个同一个IHttpClientFactory、配置、时钟、缓存有请求状态的东西；必须线程安全
AddScoped当前 scope同一个换新DbContext、当前用户、工作单元Singleton 的构造函数里
AddTransient不存不同换新无状态轻对象、ValidatorDbContext（打碎「一请求一事务」）

7 · Captive Dependency（最经典的 DI 事故）

public class OrderService(AppDbContext db) { }          // Scoped 依赖
services.AddSingleton<OrderService>();                  // ← 抓住了它

// 开发环境（ValidateScopes 默认开）第一次解析就炸：
//   InvalidOperationException: Cannot consume scoped service 'AppDbContext' from singleton 'OrderService'.
// 生产环境（默认关）不报错：所有请求共用一个 DbContext ——
//   偶发 "A second operation was started on this context"、内存缓涨、A 的未提交修改被 B 的 SaveChanges 带走

修法（Singleton / BackgroundService / 消息 handler 里要用 Scoped）：

using var scope = _scopeFactory.CreateScope();                      // 自己开一个「请求」
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();   // 随 scope 一起 Dispose

原文：It's acceptable to resolve a scoped service within a singleton if you create and use an explicit scope with IServiceScopeFactory.（Service lifetimes）

反方向随便依赖。规则只有一条：短的可以依赖长的，长的不能依赖短的。Transient 最短，构造函数里注 Scoped / Singleton 都合法；Singleton 最长，谁都不能直接依赖。会出事的是上游：一个 Singleton 抓了这个 Transient，Transient 体内的 Scoped 就跟着被抓——ValidateScopes 会顺着链查出来。

注入不影响 GC。注入只建立「我 → 依赖」的单向引用，Singleton 不会反过来拖住持有它的 Transient。真正让 Transient 活得比预期久的只有两样：

  • 它实现了 IDisposable：容器把它登记在解析它的 scope 里，scope 结束才释放。从根容器解析 IDisposable 的 Transient = 持有到进程退出（官方警告的经典泄漏）。
  • Singleton 里手写了反向引用（List<T>、事件订阅）——那是你的代码，不是注入造成的。

8 · 权限题的三层（题库第九节）

层知道什么放什么
中间件只有 HttpContext解析 token；权限集查一次放进 Scoped 的 ICurrentUser
Filter / [Authorize]知道 action接口级权限，声明式零代码
服务层 / AOP知道业务参数行级权限（只能改自己的工单）

「避免反复调用」= 请求内靠 Scoped 天然缓存 + 请求间 IMemoryCache 按用户短 TTL。

9 · 词汇表

术语一句话
RequestDelegateFunc<HttpContext, Task>，管道里「下一层」的类型；整条管道折叠后也是它
Terminal middleware不调 next 的中间件；Run 注册的永远是终端
Short-circuit不调 next 直接返回；外层后置代码仍执行
HasStarted响应头已发出；之后改状态码 / 头抛异常
Scope一个子容器；ASP.NET Core 每请求开一个、结束 Dispose；也可以手动 CreateScope()
Captive Dependency短命服务被长命服务持有，寿命被拉长到宿主的寿命
ValidateScopes开发环境默认开：Scoped 不能被 Singleton 消费、不能从根容器解析，违反即抛
Root provider根容器；从它直接解析 Scoped 等于把它变成 Singleton
