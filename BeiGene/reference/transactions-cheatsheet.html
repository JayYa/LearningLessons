事务隔离级别与事务用法
＋ 分布式事务怎么答

压缩自 Lesson 11。面试前 10 分钟只看这一页。

0 · 一句话判据

隔离级别决定的只有一件事：SELECT 看的是哪一刻的快照。RC 每条语句一张，RR 整个事务一张，Serializable = RR + 提交前检查「你读过的有没有被别人改」。PG 是 MVCC：写不阻塞读，脏读不存在。

1 · 四级别表（PG 版）

级别脏读不可重复读幻读写偏斜 / 序列化异常快照冲突时
Read UncommittedPG 不会可能可能可能= RC= RC
Read Committed（默认）否可能可能可能每条语句等锁 → 重新求值 WHERE，不报错
Repeatable Read否否PG 不会可能整个事务等锁 → could not serialize access due to concurrent update
Serializable否否否否整个事务 + 谓词锁提交时 could not serialize access due to read/write dependencies

三个 PG 特例：只有三个真实级别（RU = RC）；RR 没有幻读（比标准强，= 快照隔离）；Serializable 是 SSI——检测不加锁，会随机失败，必须重试。

2 · 三种现象一句话

现象形态哪级挡住
不可重复读同事务两次读同一行，值变了RR
幻读同事务两次同样 WHERE，行集变了PG 的 RR
丢失更新两人读后写同一行，后写覆盖前写RC + 条件更新（UPDATE 0）/ RR（报错）
写偏斜读重叠、写不同行，各自对、合起来违反约束只有 Serializable，或 RC + FOR UPDATE

3 · 选型（判据：正确性依赖的「读」有多宽）

场景用为什么
单行 check-then-act（抢单 / 扣库存 / 扣余额）RC + 条件更新被唤醒重看 WHERE，影响 0 行 = 没抢到。零重试、一条语句。升级别只会把 UPDATE 0 变成异常。
多语句只读（报表 / 对账 / 导出）RR一致快照，全程不写所以不会序列化失败
读多行决定写（排班至少 N 人在岗）Serializable + 重试 或 SELECT ... FOR UPDATE写偏斜，RR 挡不住

4 · .NET 五种写法（按边界从小到大）

  1. 单条语句——本身原子，不需要 BEGIN
  2. ORM 自动事务——EF Core SaveChanges()：all changes in a single call to SaveChanges are applied in a transaction
  3. 显式事务（主力）——EF BeginTransactionAsync(IsolationLevel.X) / SqlSugar db.Ado.BeginTran(IsolationLevel.X)、db.UseTranAsync(async () => {...}) → r.IsSuccess
  4. 环境事务——TransactionScope，作用域内连接自动 enlist（Npgsql 支持）
  5. 保存点——CreateSavepoint / RollbackToSavepoint；EF 在事务内 SaveChanges 自动建
await using var tx = await db.Database.BeginTransactionAsync(IsolationLevel.RepeatableRead);
try { /* ... */ await tx.CommitAsync(); }
catch (PostgresException e) when (e.SqlState is "40001" or "40P01") { /* serialization_failure / deadlock → 重试 */ }

5 · 三条工程规则

  1. 事务边界在服务层，一个用例一个事务。Controller 太外，Repository 太内。
  2. 事务要短，里面不许有网络调用。行锁从 UPDATE 持有到 COMMIT。要调第三方：先提交，再调，失败走补偿（Saga）。
  3. RR / Serializable 必须带重试。40001 serialization_failure、40P01 deadlock_detected 单独 catch，与业务异常分开。

TransactionScope 三坑：async 必须 TransactionScopeAsyncFlowOption.Enabled（await 换线程）；Dispose 同步阻塞；作用域里开第二个连接会试图升级为分布式事务。

6 · 分布式事务三段答

  1. 是什么：2PC / XA。PREPARE 全员答应 → 广播 COMMIT。PG 原生 PREPARE TRANSACTION，但 max_prepared_transactions 默认 0。
  2. 为什么不用：两阶段之间锁挂在协调者上，协调者挂 = in-doubt；.NET 分布式事务仅 .NET 7+ Windows，Npgsql 无恢复实现——Linux 容器里根本没这条路。
  3. 用什么：本地事务各自提交 + Saga 补偿 + outbox。落到自己那十个 Solace 服务（Lesson 05）。

7 · 词汇表

术语一句话
MVCC多版本并发控制：一行多版本，每个事务按快照挑版本；写不阻塞读
Snapshot「哪些事务已提交」的一张清单；RC 每语句拍，RR 每事务拍
Snapshot Isolation整事务一张快照；PG 的 RR 就是它
SSISerializable Snapshot Isolation：快照 + 谓词锁检测依赖环，提交时回滚一个
Predicate lockSSI 记录「你读过什么条件」，用来发现别人的写会不会改变你的读
Write skew读重叠、写不同行；RR 放行，Serializable 拦截
Serialization failureSQLSTATE 40001，「再来一次大概率成功」的错
FOR UPDATE把读变成行锁，让 RC 下的多行读也串行化
Savepoint事务内的回滚点
Ambient transactionTransactionScope 建立的环境事务，作用域内连接自动加入
2PC / XA两阶段提交 / 其接口标准；in-doubt = 阶段一之后协调者失联
Outbox改库和「要发的消息」写在同一本地事务，独立进程再发
