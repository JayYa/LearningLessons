认证与授权
＋ 让 token 失效的四条路

压缩自 Lesson 12。面试前 10 分钟只看这一页。

0 · 一句话判据

认证的产出只有一样：HttpContext.User（一张 ClaimsPrincipal）。之后所有授权——[Authorize]、Policy、行级检查——都只是对这张 claims 表提问，不再碰凭据。认证回答「你是谁」，授权回答「你能不能」。

1 · 流水线与状态码

位置做什么失败时
UseAuthentication按 scheme 调 handler，凭据 → ClaimsPrincipal不拦，User 匿名，继续
UseAuthorization看 [Authorize] / Policy，对 User 提问匿名 → Challenge 401（JwtBearer 带 WWW-Authenticate: Bearer）；有身份不满足 → Forbid 403
服务层 / IAuthorizationService加载数据后再问「能碰这一条吗」403 或 404（不暴露存在性）

顺序：认证在授权外层（先注册），因为授权要读 User。[AllowAnonymous] + 坏 token = 照样进（认证不拒绝）。

2 · 三种方式（按状态存哪）

方式状态在哪Handler用于
Session Cookie服务器（会话表）或加密 ticketAddCookie同域服务端渲染
JWT Bearertoken 自己；服务器只有密钥 / 公钥AddJwtBearer前后端分离、移动端、服务间
OIDC / OAuth 2.0身份提供方（OP）AddOpenIdConnect（RemoteAuthenticationHandler）SSO（Azure AD）、社交登录

3 · JWT 三句话

  1. header.payload.signature，前两段 base64url 明文——防篡改不防偷看。
  2. 签名 = alg(header + payload, 密钥)。HS256 对称（只能自家用），RS256 非对称（第三方只拿公钥）。
  3. 注册 claims：sub 主体 / exp 过期 / iat 签发时间 / jti 唯一 id（防重放、做黑名单 key）/ iss 谁签 / aud 签给谁。

4 · 让 token 失效：四条路

矛盾一句话：JWT 天生撤不掉（服务器不存它）；能撤的都是在某处补了状态。

#做法多存延迟选它当
1短 exp（5–15 min）+ refresh token 存库、可撤、rotation、旧的再用整族作废refresh 表≤ 一个 access 寿命默认
2jti 黑名单（Redis，TTL = 剩余寿命，自动清）只存被撤的立即要求秒级失效
3用户级版本号 / security stamp，token 带 ver每用户一个 int立即，踢全体设备封号、改密码、改权限
4不透明引用 token（回到 session）整张会话表立即内网、撤销要求极高

黑名单 key 用 jti，别用 token 哈希（OWASP：malleability）。Identity 内置的 SecurityStampValidator 就是路 3。

5 · 授权三层 + 兜底

层能看到写法
中间件只有 HttpContextUseAuthentication()；查一次权限集放 Scoped ICurrentUser
特性 / PolicyUser + 哪个 action[Authorize(Roles=..)] / [Authorize(Policy=..)]；Policy = RequireClaim / 自定义 Requirement + Handler
资源级User + 那条数据authz.AuthorizeAsync(User, ticket, TicketOps.Review)；handler 继承 AuthorizationHandler<TReq, TResource>
数据层WHEREUPDATE … WHERE id=@id AND claimed_by=@me，0 行 = 拒绝

为什么特性做不了行级：Attribute evaluation occurs before data binding and before execution of any method that loads a resource.

public class TicketAuthorizationHandler : AuthorizationHandler<OperationAuthorizationRequirement, Ticket>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx,
        OperationAuthorizationRequirement req, Ticket t)
    {
        if (req.Name == "Review" && t.ClaimedBy == ctx.User.FindFirstValue(ClaimTypes.NameIdentifier))
            ctx.Succeed(req);
        return Task.CompletedTask;
    }
}
// AddSingleton<IAuthorizationHandler, TicketAuthorizationHandler>();  服务层：先 Find，再 AuthorizeAsync，!Succeeded → Forbid()

6 · 少调服务、少写代码

  1. 能编进 token 的 claim 直接编进去（零查询；代价 = 撤销延迟）。
  2. 请求内：Scoped ICurrentUser 查一次，全请求共用。
  3. 跨请求：IMemoryCache / Redis，key = userId，短 TTL；权限变更时删 key + 升版本号。
  4. 代码量：接口级全靠特性；行级用 Action Filter（按参数 id 先加载再判）或 DI 拦截器。Filter 够用别上代理。

7 · SSO 与两步登录（都是中间态凭据）

SSO：认证外包给 OP，应用只看 id_token（sub + 何时怎么认证的）。浏览器在 OP 域有会话 cookie → 第二个应用跳过去直接签发。

密码 → 短信码：密码对了不发正式 token，发一张 5 分钟半张票（claims 只有 sub + amr:["pwd"]）；业务 Policy 要求 amr 含 mfa → 半张票调什么都 403；验证码 Redis 5 min TTL、比对即删、错 5 次锁；通过后签正式 token（amr:["pwd","mfa"]）。Identity 内置版：PasswordSignInAsync → RequiresTwoFactor + TwoFactorUserIdScheme cookie → TwoFactorSignInAsync。

8 · 话术骨架

  • 认证 vs 授权：你是谁 / 你能不能；中间隔一张 ClaimsPrincipal；401 是 Challenge、403 是 Forbid，都由授权触发。
  • 项目里怎么做：三层加兜底——特性、资源级 AuthorizeAsync、SQL WHERE claimed_by。
  • token 失效：先说矛盾，再按容忍度给 refresh 轮换 / 版本号 / 黑名单。
  • 少调服务：编进 token → Scoped → 短 TTL 缓存；主动说缓存和撤销是一对矛盾。
  • 两步登录：半张票；和 OIDC 的 code、Saga 的中间态是一个思路。
