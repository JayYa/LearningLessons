抢单：五种写法
＋ 审批流表结构

压缩自 Lesson 07。面试前 10 分钟只看这一页。

0 · 一句话根源

抢单是一个 check-then-act，所有并发 bug 都长在「检查」和「行动」之间的那道缝里。解法只有一个形状：把检查搬进那一次写的 WHERE 里，让检查与行动发生在同一条语句、同一把行锁之下。成败＝受影响行数：1 抢到，0 没抢到。

1 · 五种写法对照

写法对不对关键点
① SELECT 判断 + UPDATE错丢失更新。两条 UPDATE 都返回 1，不报错，低并发不复现，能活到生产
② 应用层 lock错锁作用域＝进程，竞争边界＝一行数据。扩容第二个副本当天破，还顺带毁掉吞吐
③ 条件更新（推荐）对一次往返、无需显式事务。默认答案
④ SELECT FOR UPDATE对，但贵两次往返 + 显式事务 + 锁持有到 COMMIT（长事务风险）+ 死锁风险
⑤ FOR UPDATE SKIP LOCKED对（另一种场景）「给我下一单」，不是「抢这一单」。高并发时的答案
⑥ 乐观锁 version对，但不如 ③同一机制，只是断言版本号而非业务状态。无关字段的并发修改会被误判成冲突

2 · 那条 SQL（背下来）

UPDATE ticket
   SET status = 'reviewing',
       claimed_by = @me,
       claimed_at = now(),
       claim_expires_at = now() + interval '30 minutes'
 WHERE id = @id
   AND status = 'approved'      -- ← 前置状态断言
   AND claimed_by IS NULL
RETURNING id;                   -- 有行 = 抢到；无行 = 被别人抢了

为什么它对（PostgreSQL, READ COMMITTED）：后到的 UPDATE 发现行被锁 → 等前一个事务结束 → The search condition of the command (the WHERE clause) is re-evaluated to see if the updated version of the row still matches → 此时 status 已是 reviewing，条件挂掉，跳过该行，返回 0。
—— PG 文档 13.2.1。不需要提升隔离级别，不需要表锁。

派单版（高并发 / 「给我下一单」）

WITH picked AS (
  SELECT id FROM ticket
   WHERE status = 'approved' AND claimed_by IS NULL
   ORDER BY priority DESC, created_at
   FOR UPDATE SKIP LOCKED
   LIMIT 1
)
UPDATE ticket t
   SET status = 'reviewing', claimed_by = @me, claimed_at = now()
  FROM picked p WHERE t.id = p.id
RETURNING t.id;

any selected rows that cannot be immediately locked are skipped ... can be used to avoid lock contention with multiple consumers accessing a queue-like table —— PG 文档，SELECT 的锁定子句

3 · 审批流表结构

ticket              -- 主表：当前态，一单一行
  id, biz_no UNIQUE, payload jsonb, status,
  submitted_by, approved_by,
  claimed_by, claimed_at, claim_expires_at,
  reviewed_by, version, created_at, updated_at

ticket_transition   -- 流水表：历史，只增不改
  id, ticket_id, from_status, to_status,
  actor_id, action, comment, created_at
draft ─submit─▸ submitted ─approve─▸ approved ─claim─▸ reviewing ─finish─▸ done
                    ▲                    │                 │
                    └──────reject────────┘                 └─release/超时─▸ approved

不要建三张表（提交表/审核表/复核表）：一次查询要连三次，且答不了「这单现在在谁手上」。审批流＝一张单在状态链上前进。

当前态放主表、历史放追加表——和 Saga 的 tx_log(biz_id, state) 是同一个模式。reviewing 这个中间态就是语义锁。

4 · 三个必须主动讲的失败路径

问题解法
抢到不干活（人去开会 / 浏览器崩）claim_expires_at 租约 + 定时任务回收。认领是租约，不是地契
认领成功但响应丢了同一条租约兜底。这是 Lesson 04「执行了但确认丢失」的同一个洞
代码里漏写 WHERE 条件部分唯一索引兜底（下一节）
 
-- 回收过期认领
UPDATE ticket
   SET status = 'approved', claimed_by = NULL,
       claimed_at = NULL, claim_expires_at = NULL
 WHERE status = 'reviewing' AND claim_expires_at < now();

5 · 「哪个任务被谁抢掉了」——三层答

层做法回答
当下主表 claimed_by / claimed_at现在在谁手上
历史ticket_transition 里 action='claim'被谁抢过、放弃过几次（绩效 / 申诉依据）
约束部分唯一索引数据库层面保证「同时只能有一个有效认领」
 
CREATE UNIQUE INDEX uq_claim_active
    ON ticket_claim (ticket_id)
 WHERE released_at IS NULL;

原则：能表达成数据库约束的业务规则，就别只放在应用代码里。应用代码有很多条路径，数据库约束只有一道门。

6 · 权限：三个维度

维度控制实现
功能权限能做什么动作RBAC：用户→角色→权限点，接口上 [Authorize(Policy=...)]
数据权限能看哪些行服务端从登录态推导过滤条件，绝不接受前端传部门 id
状态机权限此刻能否做这个动作已经在那条 UPDATE 的 WHERE 里：AND status='reviewing' AND claimed_by=@me

记忆点：前置状态断言一个机制，同时解决并发抢单、状态机合法性、数据权限三件事。

7 · 面试速答骨架

被问答的顺序
设计流程和表反问量级 / 能否放弃 → 主表＋流水表 → 为什么不建三张表 → payload 用 jsonb
抢单怎么设计本质是 check-then-act → 条件更新那条 SQL → 主动讲租约 → 主动讲唯一索引兜底
为什么不用悲观锁结果也对，但：两次往返＋显式事务 / 长事务拖垮连接池 / 死锁 → 再给边界：事务里还要读别的表校验时，悲观锁反而合适
上千人抢怎么办换问题形态：抢指定单 → 派下一单，SKIP LOCKED → 再往上才是预分配 / Redis 预占
权限怎么控功能 → 数据 → 状态机，收束到同一行 SQL
怎么确定被谁抢的当下 → 历史 → 约束（三层）
最容易被追问崩的两处

①「你怎么知道条件更新一定安全？」→ 答 READ COMMITTED 下 WHERE 会拿新行版本重新求值（PG 文档 13.2.1）。答不上来，前面全白讲。

②「抢到之后那个人不做了呢？」→ 答租约 + 定时回收。更好的做法是不等他问，自己讲。
