跨系统一致性
＋ RabbitMQ 消费与 ACK

压缩自 Lesson 13，接 微服务速查表 第 8、9 节。面试前 10 分钟只看这一页。

0 · 一句话判据

跨系统的每一步都有三种结果：成功、失败、不知道。前两种一句 if；中间态、幂等键、查询、对账、手动 ACK、去重表——全是为「不知道」做的。HTTP 的「不知道」叫超时，MQ 的「不知道」叫 ACK 没送到。

1 · 顺序：先写中间态

顺序问题判定
先调对方，再写库对方成功、我方写库失败 → 无记录的幽灵交易✗
先写终态，再调对方超时后终态是假的，回滚 / 补偿都要先知道对方结果△
先写 PENDING → 调对方 → 推进终态不管发生什么，本地永远有 biz_id + 时间 + 状态的锚✓

塌缩规则：对方明确失败 → FAILED（无需回滚）；明确成功 → CONFIRMED；其余一切（超时 / 我方推进失败 / 进程被杀）→ 停在 PENDING，同一条恢复路径。推进终态写成条件更新 WHERE state = 'PENDING'，可重复执行。

2 · 把「不知道」变「知道」：三层

#路前提覆盖
1幂等重试：带同一个 key 再发对方支持 Idempotency-Key~95% 的超时
2查询接口：后台扫超时 PENDING，按业务号问对方有 query 接口对方不幂等时
3对账：定期拉对方全量，比对，差异进人工队列对方给账单 / 批量查询兜底，永远要有

幂等键三细节：按业务动作做 key（= 本地 biz_id），不是每次随机；被调方存第一次的状态码 + 响应体（含 500）原样返回；同 key 不同参数要报错。（Stripe）

3 · 通知用户

挂在状态转换上，不挂在请求线程上（真正成功可能由后台任务推进）。推进状态 + 写 outbox 通知同一事务；通知服务消费 outbox。SignalR 推送只做加速，页面重连后回源拉状态；离线走站内信 / 邮件 / 短信——又是跨系统调用，至少一次 + 幂等（发两次可接受，发零次不行）。

4 · RabbitMQ 三问

题答
队列大小无固定大小，只受节点内存 / 磁盘限制。x-max-length / x-max-length-bytes 设上限；x-overflow：drop-head（默认，丢最老）/ reject-publish（拒新，生产者 nack，业务队列用这个）/ reject-publish-dlx（拒新且进死信）。生产上真正的问题是内存告警阻塞生产者。
如何消费推：basic.consume 长期消费者（正常用）。拉：basic.get 官方 highly discouraged。basic.qos prefetch = 未确认上限 = 背压阀，一般 10–50。
ACK 机制自动 ACK = 发出即删，崩溃就丢，官方 unsafe。手动：处理完再 basic.ack；失败 basic.nack，requeue=true 回队头（瞬时故障）/ false 进 DLX（数据本身错）。channel 断 → 未确认全部重投，redelivered=true。未 ACK 超 30 分钟 → PRECONDITION_FAILED 关 channel。delivery tag 按 channel 作用域，必须在原 channel 上 ACK。

至少一次的代价：处理完、ACK 前崩溃 → 同一条处理两次。broker 分不清「没处理」和「处理了没告诉我」。手动 ACK 把丢换成重，幂等把重消掉（按 messageId / 业务键去重）。

对称的另一侧：publisher confirm = broker 对生产者说「收下了」；durable 队列 + persistent 消息时 means persisting to disk。可靠投递三件套：confirm + durable/persistent + 手动 ACK。

5 · C# 骨架（RabbitMQ.Client 7.x）

await channel.QueueDeclareAsync("order.paid", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?> {
        ["x-max-length"] = 100_000, ["x-overflow"] = "reject-publish", ["x-dead-letter-exchange"] = "order.dlx" });
await channel.BasicQosAsync(0, prefetchCount: 20, global: false);
var consumer = new AsyncEventingBasicConsumer(channel);
consumer.ReceivedAsync += async (_, ea) => {
    try { await handler.HandleAsync(ea.Body, ea.BasicProperties.MessageId, ea.Redelivered);   // 幂等在里面
          await channel.BasicAckAsync(ea.DeliveryTag, multiple: false); }
    catch (TransientException) { await channel.BasicNackAsync(ea.DeliveryTag, false, requeue: true); }
    catch (Exception)          { await channel.BasicNackAsync(ea.DeliveryTag, false, requeue: false); } // → DLX
};
await channel.BasicConsumeAsync("order.paid", autoAck: false, consumer);

6 · 归类判据

  • 知道成功 → 推进；知道失败 → 标 FAILED / 补偿（Saga）；不知道 → 状态不动，去问。
  • 有幂等键 → 同 key 重试；只有 query → 查询；都没有 → 对账。
  • MQ：瞬时故障 → nack requeue；数据本身错 → nack 进 DLX；requeue 循环 → 看 x-death 计数转 DLX。
  • 幽灵交易（对方有、我方无）→ 人工，且查顺序为什么反了。

7 · 话术骨架

  • 一致性：三种结果 → 先写 PENDING → 明确结果推进、不明确停住 → 幂等重试 / 查询 / 对账三层 → 接 Saga 经历（「知道失败」的处理）。
  • 通知：挂状态转换、走 outbox、推送只加速、重连回源。
  • RabbitMQ：无固定大小 + overflow 选 reject-publish；consume 推 + prefetch 背压；手动 ACK 把丢换成重、幂等消重；自己项目日志 / 缓存通知用自动 ACK 是合理取舍。
